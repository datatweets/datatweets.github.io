How to Build a Testable AI Agent System Prompt in Python

Turn a fictional equipment-loan assistant's decisions into a validated policy table, compile those rules into one provider-neutral system prompt, cover every policy with small scenarios, and test controlled JSON outputs without claiming live-model performance.

Mehdi Lotfinejad
August 14, 2026 · 10 min read

Imagine finding these two lines in one agent prompt: “Never change a loan request without approval” and “Cancel a loan when the user asks.” Both sentences sound reasonable alone. Together, they leave the model to decide which rule wins at the exact moment a real action matters.

To build a testable AI agent system prompt, store each decision rule in a table, reject contradictory rows, and compile the validated rules into the prompt. Give every rule labeled scenarios, require a strict JSON output shape, and use Python to check model outputs before application code allows any action.

This tutorial builds that workflow for a fictional equipment-loan assistant. The assistant can search a catalog, check availability, and prepare a request draft. It cannot complete or cancel a loan. That boundary stays visible in the prompt and enforceable in Python.

Setup and the Files You Will Test

You need Python 3.11 or later and basic knowledge of dictionaries, functions, and tables. A pandas DataFrame is a table with named columns. JSON Schema is a standard way to describe the required shape of JSON data.

A controlled output fixture is a fixed response designed to exercise one test path. These fixtures are not responses from a live language model and do not measure prompt quality.

Understanding the Three Contract Layers

A system prompt is a high-priority instruction supplied by an application to guide a model’s behavior. It can describe the role, available actions, decision rules, and expected output. It is still text interpreted by a model, so it is not a permission system.

Keep three layers separate:

  1. The policy table records what should happen for reviewed situations.
  2. The system prompt presents those policies and tool boundaries to the model.
  3. Application code validates the returned data and controls every real side effect.

A side effect is a change outside the model call, such as cancelling a request or reserving equipment. The model may propose such an action. Trusted code must decide whether the action is registered, valid, approved, and safe to execute.

The system prompt is also only one part of an agent’s context. Anthropic’s current context-engineering guide includes tool definitions, external data, message history, and other runtime information in that wider context. This lesson keeps changing user and tool data out of the static prompt. The application supplies them for the current turn.

This separation makes failures easier to name. A missing rule is a policy problem. A leftover template marker is a prompt-build problem. JSON that violates the schema is an output-contract problem. A valid request for an unapproved action is an execution-policy problem.

Compile Only Validated Rules into the Prompt

The compiler uses Python’s string.Template so the document has three visible placeholders: tools, policies, and schema. Use substitute(), not safe_substitute(). The current Python documentation explains that substitute() raises an error for a missing value, while safe_substitute() can leave an unresolved placeholder in the result.

First define the fixed structure. The complete file includes an output contract and a final boundary section after the policy list.

Next, turn each validated row into a labeled policy line. Keeping rule_id in the compiled text connects a prompt instruction to its scenario coverage without exposing private review notes.

Give Every Rule Two Inspectable Scenarios

A prompt can contain a rule that no test reaches. A scenario matrix prevents that blind spot by pairing small inputs with reviewed expectations. Some rows are user requests; others are tool results because an agent must respond to observations as well as messages.

Check JSON Shape Before Policy Meaning

The prompt requests one JSON object with five required fields: decision, tool_name, arguments, missing_fields, and message. The schema restricts decision and tool names and rejects extra top-level fields.

JSON Schema does not require named properties merely because they appear under properties. Its official object reference explains that required must list mandatory names and that extra properties are allowed unless a schema restricts them. This tutorial therefore includes both required and additionalProperties: false.

Create one validator, then check every controlled output. iter_errors() yields all validation failures for an instance, as documented by the jsonschema validator API.

The order matters. Do not read fields until the shape passes. After that, compare the decision and tool with the reviewed case. An object that passes the schema can still request the wrong action.

The build checks 18 controlled fixtures. Twelve match both layers. Three fail the schema: one lacks message, one has an extra property, and one uses an unknown decision. Three more have valid shapes but choose the wrong decision or tool.

Read the left panel as test coverage, not performance: every policy has exactly two scenarios. Read the right panel as evaluator branch coverage. The six failures were inserted deliberately to prove that shape errors and policy errors remain separate.

Move from Controlled Fixtures to a Live Model Safely

The controlled outputs prove that the compiler and evaluator behave as designed. They cannot prove that a model will follow the prompt. Add a separate integration step when you connect a provider:

  1. Freeze the policy CSV, scenario CSV, compiled prompt, tool definitions, model identifier, and sampling settings.
  2. Send each scenario to the model in a sandbox with no real write-capable tools.
  3. Save the raw output and parse status without editing failed responses.
  4. Run the same schema and policy checks.
  5. Inspect disagreements, then keep a final test set separate from prompt development.

If the agent uses several tools across a run, final JSON is not enough. The AI agent trace-assertion tutorial shows how to test tool order, arguments, duplicate writes, failures, and final application state.

Keep hard controls outside the prompt. Validate registered tool names and arguments, enforce permissions, require approval for sensitive actions, limit steps and retries, and use idempotency protection for writes. Idempotency means that repeating the same request after success does not create a second effect.

What Can Go Wrong and How to Fix It

The policy table becomes a second vague prompt. Give each row one specific situation and one reviewed outcome. Split a row that contains several unrelated decisions.

Two rows overlap but use different words. A repeated scope_key catches exact scope collisions, not semantic overlap. Review neighboring situations such as “remove a draft” and “cancel a request” together, then add contrastive scenarios.

A priority number is treated as conflict resolution. Priority controls display order in this lesson. It does not make contradictory policies acceptable. Reject the conflict and decide the rule explicitly.

Schema validation is called behavior validation. A schema checks structure, types, allowed values, and similar constraints. It does not prove that an answer is useful, truthful, or authorized.

Fixture results are reported as model accuracy. Controlled failures test the evaluator. A model evaluation must identify the model and prompt versions, use frozen reviewed cases, and state when the run happened.

The system prompt contains changing records. Keep inventory, dates, user details, and tool results in turn-specific context. Static prompts should contain stable role and policy information.

The model requests an unregistered write tool. Never treat arbitrary model text as permission to call a function. Match the requested tool name against an application allowlist and reject tools that were not registered for that run.

The prompt encourages unsupported success claims. Record precise states such as draft_created, approval_required, or execution_failed in trusted application data. Confirm completion only from a trusted tool result.

Recap and Your Next Test

A testable agent prompt starts outside the prose. Put decisions in a reviewable table, reject conflicts, compile only validated rules, and attach small scenarios to every rule. Then validate output shape before comparing the model’s proposed decision with the expected policy.

Before connecting a real model, you should be able to answer yes to this checklist:

  • Does every rule have a stable ID and one clear outcome?
  • Can the build stop on an unknown tool or conflicting scope?
  • Does every rule have at least two realistic scenarios, including missing-detail and failure cases where relevant?
  • Does the output schema require every field and reject unexpected ones?
  • Can Python distinguish invalid JSON shape from a wrong policy decision?
  • Are approval, permissions, and side effects enforced outside the prompt?

Start the live integration with read-only tools and the same 18 case IDs. The useful result is not one total score. It is a failure table that tells you whether to repair a policy, prompt wording, tool interface, parser, or execution boundary.
