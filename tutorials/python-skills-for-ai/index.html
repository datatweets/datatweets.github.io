Python Skills You Need to Work with AI: JSON, Types, and Streams

Every AI SDK tutorial assumes you already know these six things: reading nested JSON, typing a payload with a dataclass, building an f-string prompt without breaking on embedded braces, consuming a streamed reply with a generator, closing a client session with a context manager, and telling a retryable error from a fatal one. This post teaches all six with one small, dependency-free example.

Mehdi Lotfinejad
August 5, 2026 · 13 min read

Open almost any tutorial about calling an AI model from Python and it starts the same way: install an SDK, paste in a key, send a message, print the reply. That part takes five minutes. What actually eats an afternoon is everything the tutorial assumes you already know — why response["choices"][0]["message"]["content"] doesn’t raise an error until it does, why a dataclass you wrote refuses to compile, why a prompt string throws a ValueError the moment you paste in a JSON example. None of that is an AI problem. It’s ordinary Python, and it shows up whether you’re calling a hosted chat API, a local model, or something that doesn’t exist yet. (If you’ve already got the wrapper working and want to see it become a real request/response loop with tool calls, our post on building an AI chatbot in Python picks up right where a “hello world” script leaves off.)

The Python skills that matter most for AI work aren’t AI-specific: solid JSON navigation for reading a response’s shape, dataclasses or TypedDict so a malformed payload fails loudly instead of quietly, f-strings that don’t collide with embedded braces, a generator loop for consuming a streamed reply, a context manager that closes a session even when a call fails, and exception classes precise enough to tell a retry-worthy hiccup from a dead end. Get comfortable with those six and any AI provider’s official quickstart becomes five minutes of reading, not an afternoon of confusion.

The Model Talks in Text; Your Code Still Speaks Python

Whichever AI provider you use, the shape of the work around the actual model call barely changes. You build a request, usually a nested dictionary of strings and numbers. You send it and get back another nested dictionary. You pull a few fields out of that reply, maybe validate them, and hand the result to the rest of your program — which has never heard of tokens or temperature and doesn’t need to. The model is the one genuinely new piece; everything wrapped around it is the same JSON, typing, and control-flow work you’d do gluing together any two systems that don’t fully trust each other.

That’s the frame for this whole post: nothing below calls a real network endpoint. There’s a small MockAIClient standing in for whatever SDK you’d normally import, built with plain Python so every example runs with no install and no API key — the same trick our post on routing LLM requests across providers uses for its retry and fallback logic. The skills transfer directly the day you swap the mock for openai, anthropic, or anything else.

Reading the Shape of a Response with json

An AI API’s reply almost always lands as a nested structure: a dict containing a list containing a dict containing the text you actually want. Here’s a representative shape, close to what a real chat-completion response looks like once it’s been parsed from JSON:

Once you know the shape, pulling values out is just dict and list indexing:

This exact ["choices"][0]["message"]["content"] path is close to a de facto standard across chat-completion-style APIs, which is exactly why it’s worth being fluent in plain dict/list navigation rather than reaching for a library to do it for you.

Locking Down the Payload with dataclasses and TypedDict

A raw dict works, but nothing stops you from misspelling a key or passing a string where a float belongs, and you won’t find out until the request already failed against a real, possibly paid, API. A dataclass gives the outgoing request a fixed shape:

frozen=True makes an instance immutable after creation — reach for that on anything you build once and send, so nothing later in the pipeline can quietly mutate the request you’re about to log or retry. asdict() turns it straight back into the plain dict json.dumps expects, so the dataclass costs you nothing at the boundary where it actually needs to become JSON. field(default_factory=list) matters more than it looks: build two separate requests and each gets its own list, not a shared one.

For the incoming side, a TypedDict documents a dict’s expected keys and value types without changing how the dict behaves at runtime — useful when you’re not ready to fully wrap the response in a class, but still want a type checker to catch a typo in a key name:

Python read {"summary": "text"} and tried to treat it as an expression followed by a format spec — it saw the string "summary", then a colon, then interpreted everything after the colon as formatting instructions, which "text" isn’t valid syntax for. Any time a prompt template needs to embed a JSON example, a code snippet with braces, or a set literal, doubling the braces is the fix — and it’s worth checking for this before assuming a prompt-building bug is something more exotic.

Consuming a Streamed Reply with a Generator

Most AI APIs can stream a reply piece by piece instead of waiting for the whole thing, which matters for anything user-facing — nobody wants to stare at a blank screen for three seconds. A generator is the natural shape for that: a function that yields values one at a time instead of building and returning a full list up front.

client.stream(prompt) doesn’t run any of the function body yet — calling it just creates the generator object. Each yield hands the loop one chunk and pauses until the next one is requested, which is why "".join(chunks) only holds one chunk in memory at a time instead of the whole reply. The catch: a generator runs once. Iterate over chunks again after it’s exhausted, expecting to print the reply a second time for a log line, and you get nothing back, not an error:

If you need the full text for logging and need to stream it to a user, collect it into a plain string or list the first time through and reuse that — never re-iterate the original generator expecting it to still have something in it.

Keeping a Client Session Honest with a Context Manager

A real AI client usually holds a network connection open behind the scenes, and that connection should get cleaned up whether your code finishes normally or blows up halfway through. That’s what a context manager — the object behind a with block — is for:

__enter__ runs when the with block starts and __exit__ runs when it ends — and critically, __exit__ still runs if something inside the block raises:

The session gets closed either way, then the exception propagates out and is caught normally by the surrounding try. A plain client = MockAIClient(...) with no with block would leave the session open on the failure path unless you wrote a finally yourself — the context manager gives you that for free, which is exactly why almost every real SDK’s client object supports with.

Telling a Retryable Failure from a Fatal One

Real AI API errors fall into two very different buckets: temporary trouble worth retrying (rate limits, timeouts) and permanent trouble that a retry will never fix (a bad API key, a request that violates the API’s own rules). Catching everything with one broad except Exception treats both the same, which means your code either retries something hopeless in a loop or gives up on something that would have worked a second later. The Six Skills, One Sentence Each

  • json — navigate a nested response by index and key; use indent=2 while developing to actually see the shape.
  • dataclasses / TypedDict — give a request or response a fixed shape so a typo fails at definition time or type-check time, not mid-request.
  • f-strings — build prompts by interpolation; double {{ }} the moment a literal brace needs to appear in the text.
  • generators — stream a reply one chunk at a time instead of waiting on the whole thing, and remember they only run once.
  • context managers — close a session with with, so cleanup happens even when the call inside it fails.
  • exception classes — split retryable trouble from fatal trouble instead of catching everything the same way.

None of this required a model, a key, or a network call — which is exactly the point.
