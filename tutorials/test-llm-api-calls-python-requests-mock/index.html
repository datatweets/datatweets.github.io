How to Test LLM API Calls Offline by Mocking Python Requests

Build a small Requests-based LLM client, replace its network call with controlled response fixtures, and execute ten deterministic tests across input, transport, HTTP, JSON, and response-contract failures.

Mehdi Lotfinejad
August 13, 2026 · 10 min read

An LLM client can work for one successful response and still fail when the service returns an error page, incomplete JSON, an empty text field, or no response before the deadline. Waiting for those cases to occur against a paid service makes tests slow, variable, and difficult to repeat.

To test LLM API calls offline, put the HTTP request inside one Python function and replace requests.post with controlled behavior during each test. Return real requests.Response objects for successful and failed HTTP replies, raise requests.Timeout for the timeout case, and compare the client’s normalized result with a predefined expected status.

This tutorial uses a fictional ticket-classification endpoint. The response contract is intentionally small: a successful response must have HTTP status 200 and a non-empty string named output_text. You can later adapt that boundary to the documented fields of the provider you use.

Setup and the Controlled Test Data

You need Python 3.10 or later and basic knowledge of functions, dictionaries, and exceptions. A mock is a controlled replacement for a dependency. Here, the dependency is requests.post, the function that would normally attempt the HTTP request.

Create and activate a virtual environment, then install Requests and Matplotlib. Requests sends the HTTP request in the client code. Matplotlib is needed only to reproduce the results chart.

On Windows PowerShell, use .venv\Scripts\Activate.ps1 for the activation command. The executed build used Python 3.13.2, Requests 2.34.2, and Matplotlib 3.11.0.

Download the ten synthetic API test cases and executed test results. Both files are original teaching data released under CC0-1.0. The ticket IDs, prompts, response fixtures, and expected statuses are fictional. They contain no customer data, live model output, provider measurements, or secrets.

Write the expected status before running the client. If a test decides what it “should” have returned after seeing the output, it cannot detect a regression reliably.

How an Offline Boundary Test Works

An HTTP client crosses several boundaries. Treating every failure as None or one broad exception hides where the problem occurred. This lesson gives each layer a stable result:

Transport means moving bytes between the client and service. A timeout or refused connection fails at that layer. HTTP status is the numeric result returned by the service, such as 401 or 429. A 200 response passes the HTTP check but may still contain invalid JSON. Valid JSON may still violate the response contract, which is the set of fields and types the application expects.

The patch replaces only requests.post. Input validation, exception handling, status checks, JSON parsing, and field checks remain real application code. This differs from replacing the whole model object with a fake. For that wider software boundary, see Test an LLM Pipeline Without API Calls in Python.

Python’s unittest.mock documentation describes patch() as a temporary replacement for a name used by the code under test. In this lesson, FakePost also records each attempted invocation. This lets the test check both the returned result and the arguments passed to requests.post.

Give Every Client Outcome a Clear Shape

Start with one result type. The client always returns a CallResult, so calling code does not need to interpret unrelated Requests exceptions and dictionaries.

The status field identifies the outcome. text is populated only after a valid success. http_status keeps the server’s numeric status when one exists. retry_after_s records a simple whole-second Retry-After header in the rate-limit case; this tutorial records it but does not retry automatically. The HTTP standard also permits a date in that header, so a production parser must support both formats or reject the unsupported one clearly. See the current Retry-After specification.

The order of the two except blocks matters because Timeout belongs to the broader Requests exception family. Catching RequestException first would also catch the timeout and lose the more useful status.

Requests does not apply a timeout unless code supplies one. Its current timeout documentation also explains that this value is not a total wall-clock deadline; it limits how long the underlying socket can go without receiving bytes. A production application may need an additional end-to-end deadline around retries or streaming.

The Requests JSON response guide makes an important distinction: successful JSON decoding does not prove the HTTP request succeeded. A service can return JSON error details with an unsuccessful status. That is why this function reads the status first and the successful response body second.

This contract is fictional, not a universal LLM response shape. Change output_text in one adapter when your provider uses nested content blocks, choices, or another documented schema. Keep the normalized CallResult stable for the rest of your application.

Build Real Response Objects Without Sending Data

The client calls methods on a Requests Response, so the mock should provide that same object type. A helper fills only the attributes this client reads: status, headers, body bytes, encoding, and URL.

_content is an internal attribute, so keep this helper inside test code. It gives response.json() the same body bytes it would receive after a request. Application code should not set private Response attributes.

The callable records whether authorization was present, but it does not store the key itself. Avoid placing credentials, full private prompts, or raw sensitive model output in test logs.

Patch the Lookup Used by the Client

Use patch() only while the cases run. Because the client looks up and calls requests.post, the correct target in this single-file example is "requests.post". If your client module imported the function with from requests import post, patch post in that client module instead. The important rule is to patch the name where the code under test looks it up.

Common Mistakes and Troubleshooting

Patching the wrong name. Patch the name that the client module looks up. If the real network still runs, inspect how that module imports Requests and move the patch target there.

Returning a plain dictionary from the mock. The client expects .status_code, .headers, and .json(). Return a configured requests.Response, or use a test helper that deliberately provides the same interface.

Parsing JSON before checking the status. A 401 or 503 body may be valid JSON. It is still not a model answer. Handle the protocol result before applying the success schema.

Testing only malformed JSON. {} is valid JSON and still violates this contract. Cover missing fields, wrong types, empty strings, lists where objects are expected, and any nested blocks your provider documents.

Using one expected exception for every failure. A timeout, authentication error, rate limit, and bad response body need different caller actions. Stable statuses let the surrounding program decide whether to stop, ask for configuration, or apply a bounded retry policy.

Assuming the mock proves provider compatibility. These tests verify your code against fixtures you designed. Add a small live integration test against a provider’s current documented API, using a separate test account and strict spending limits. Keep deterministic offline tests for every code change.

Testing retries inside the same lesson without limits. This client records Retry-After but does not retry. Before adding automatic retries, decide which statuses are temporary, which operations are safe to repeat, and the maximum attempts and wait time. The Python Requests sessions tutorial covers mounted retry behavior and connection reuse.

Leaking a real key into fixtures or logs. Use an obvious fake value in offline tests. Read real keys from a protected environment only in live integration code, and never print the authorization header.

Recap: Keep the Variable Part at the Edge

An offline LLM API test does not need a model response. It needs a clear client contract and controlled evidence for every path around the network call.

The durable sequence is:

  1. Reject invalid input before sending anything.
  2. Set an explicit request timeout.
  3. Separate transport failures from HTTP status failures.
  4. Parse JSON only on the expected success status.
  5. Validate required fields and types before returning text.
  6. Patch the HTTP function where the client looks it up, using controlled Response objects and exceptions.
  7. Compare every observed status with an expectation written in advance.

The executed table covers ten cases and five decision layers without a network connection, API key, paid request, or variable model output. Keep this fast suite close to the client code. Then use a smaller live integration check to detect provider-side schema or authentication changes that an offline fixture cannot discover.
