How to Merge DataFrames in Pandas Without Duplicating Rows

Merging two DataFrames looks like a one-liner until your row count doesn't match what you expected. This guide works through merge()'s how, suffixes, and validate parameters, the .join() shortcut, and the exact conditions that cause a merge to quietly duplicate or drop rows.

Mehdi Lotfinejad
August 9, 2026 · 11 min read

You’ve got two tables that both describe the same real-world thing — customers and their orders, say — and you need them side by side. You write orders.merge(customers, on="customer_id"), it runs without complaint, and the result looks fine. Then someone asks why the total order count in your report is higher than what’s in the orders system, and you spend twenty minutes staring at a DataFrame that has more rows than either of its inputs.

That’s almost always a key problem, not a pandas bug: merge() matches every row in one table against every row with the same key in the other, and if a key isn’t unique on the side you assumed it was, you get one output row per match — not one per input row. The fix is to be explicit about three things every time you merge: which rows to keep when a key doesn’t appear on both sides (how=), what to do when a key repeats on the side you expected to be unique (validate=), and what happens to columns that exist in both tables (suffixes=). Get those three right and a merge behaves exactly as predicted; skip them and pandas will happily hand you a DataFrame that’s technically correct and practically wrong.

A Merge Is a Lookup, Not a Stack

It helps to separate merge() from the other way people combine tables in pandas, pd.concat(). Concatenating stacks DataFrames on top of each other (or side by side) with no regard for whether the rows relate to each other at all — row 5 of one table just ends up next to row 5 of the other. Merging is different: it looks at a key column in each table, finds rows where that key matches, and pairs them up. Two rows with customer_id = 11 get joined into one row; a customer_id that appears in only one table is a decision point, not an error.

That decision point is what how= controls, and it’s the first thing to get right on any merge. Before we get to it, we need two tables worth merging.

A Small Bookstore’s Customers and Orders

GreenLeaf, a fictional independent bookshop, keeps two tables: one row per customer, one row per order. They’re generated here with a fixed seed so your output matches this post exactly — no download required.

Orders reference a customer_id, but deliberately not a clean one: customer 20 has signed up but never ordered anything, and three orders are tagged with customer_id = 101 — a loyalty card from before GreenLeaf’s last system migration that was never linked to a real account. Picking how=: What Happens to Unmatched Rows

how decides which side’s unmatched rows survive. There are four options, and the difference between them is entirely about those three missing orders and that one order-less customer.

"inner" (the default) keeps only rows with a match on both sides — that’s the 60 rows above. "left" keeps every row from the left table (orders) regardless of a match, filling customer columns with NaN where there isn’t one:

All 63 orders are there now, with those three loyalty-card orders visible instead of silently dropped — exactly the rows how="inner" erased. "right" is the mirror image: every row from customers survives, which surfaces customer 20, who has never placed an order:

And "outer" keeps everything from both sides — the union. Pair it with indicator=True to add a _merge column that tells you exactly where each row came from, which is the fastest way to audit a merge you don’t fully trust yet:

60 matched, 3 orders had no customer, 1 customer had no orders — 64 total, and it adds up to the left and right counts above with no double-counting. The pandas merging user guide covers a few less common how values (like "cross") if you ever need every combination of both tables rather than a keyed match.

If you only remember one thing from this section: before you trust a merge’s output, print len() on the input and the result and account for the difference. It takes one line and it’s the single most effective check against exactly the confusion this post opened with.

.join(): A Shortcut, Not a Different Operation

Worth knowing before it surprises you: .join() refuses to silently auto-suffix a name collision the way merge() does — you have to name at least one side yourself with lsuffix or rsuffix:

.join() is genuinely just merge() with left_index=True (and right_index=True, unless you pass a plain column via on=) baked in as the default — reach for it when your tables are already indexed the way you want to match them, and reach for merge() everywhere else, including any time the key is a normal column.

The Row-Count Blowup: Duplicate Keys and validate=

Here’s the failure mode that started this whole post. Imagine customers picked up an accidental duplicate — a CRM export re-imported on top of itself, say, so customer 5 now has two identical-looking rows:

Merge as usual, and every one of those 4 orders for customer 5 gets matched against both of the duplicate customer rows:

4 orders became 8. Nothing crashed, nothing warned — the total row count crept up by exactly the number of duplicate matches, which on a real dataset with thousands of rows and a handful of accidental duplicates is easy to miss until a downstream sum is mysteriously too high. This is the scenario from the top of this post, reproduced on purpose.

The fix is to tell pandas what you’re assuming about the key before it merges, with validate=. Since every order should match at most one customer, this should be a many-to-one merge (many orders, one customer per key):

Pandas refuses the merge and names the exact key that broke the assumption, before a single duplicated row makes it into your output. Run the same call against the real customers table (no duplicate) and it passes silently, which is exactly what you want a validation check to do:

validate also accepts "one_to_one" and "one_to_many" for the other cardinalities — pick whichever matches what should be true about your two tables, and let pandas catch it the moment that stops being the case.

Two More Ways a Merge Can Quietly Lie to You

Mismatched key types used to match nothing; pandas 3.0 now refuses outright. If one table’s key is an integer and the other’s got coerced to text somewhere upstream (a common side effect of reading a CSV with mixed formatting), older pandas versions would run the merge and just find zero matches. Either way — silent zero matches on older pandas, or this error on 3.0 — the underlying lesson is the same: check orders["customer_id"].dtype against customers["customer_id"].dtype before merging if either column has passed through a CSV read or an API response.

A missing key never matches, not even another missing key. If a handful of orders lost their customer_id somewhere upstream, those rows just fail to match — NaN doesn’t equal NaN as far as a merge key is concerned:

Zero for zero, every time. If you need to keep those rows for a report, a how="left" merge still preserves them (with NaN customer columns) — but they’ll never get customer data back until the customer_id itself is fixed at the source.

Four Decisions, Not One

Every merge worth double-checking comes down to the same four questions: which rows to keep on a mismatch (how), whether the key is really as unique as you’re assuming (validate), what to call a column that exists on both sides (suffixes), and whether .join()’s index-based shortcut fits better than a plain merge() on a column. Answer those explicitly and the row count after a merge stops being a surprise — it’s the one number you should always check first, the same way you’d check len() after any groupby() call that’s supposed to collapse or expand your data in a predictable way.
