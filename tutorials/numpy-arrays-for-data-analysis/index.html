How to Analyze Data with NumPy Arrays in Python

A hands-on introduction to NumPy arrays for data analysis: shape and dtype, indexing and boolean-mask filtering, axis-wise aggregation, and why vectorized math beats a Python loop — verified end to end on the real Iris flower measurement dataset.

Mehdi Lotfinejad
August 10, 2026 · 12 min read

Say you’ve got a table of measurements — sensor readings, survey scores, flower petals, whatever — as rows and columns of numbers, and you want the average of one column, every row above a threshold, or the same formula applied to every row at once. Do that with a Python list and a for loop and it works, right up until the table grows and the loop gets noticeably slower, because every single number in that list is its own separate Python object carrying its own overhead. NumPy exists to fix exactly this. Our post on NumPy broadcasting for column-wise standardization picks up one specific, more advanced piece of that story; this one starts from zero.

The core move is this: load your table into a NumPy array — with np.array(), or a loader like sklearn.datasets.load_iris() — then operate on the whole thing, or a slice of it, or a boolean-filtered subset of it, in one call. data.mean(axis=0) gives you the average of every column at once; data[data[:, 2] > 5] gives you every row where the third column exceeds 5. No loop required. Because every element in the array shares one fixed data type and sits in one contiguous block of memory, that call runs as fast, compiled machine code instead of Python’s own byte-by-byte interpreter loop — which is the entire reason NumPy exists and the entire reason it’s fast.

The Data: 150 Real Flowers, No Download Needed

Rather than typing in numbers by hand, we’ll use a genuinely real dataset that ships with scikit-learn, so there’s nothing to download and nothing to fake: Ronald Fisher’s 1936 iris flower measurements, still one of the most-used small datasets in statistics precisely because it’s small, clean, and real.

Data: the classic iris flower measurement dataset (Fisher, 1936), distributed with scikit-learn under a permissive BSD-style license — via sklearn.datasets.load_iris(), no network fetch required.

data is a 150-by-4 array: 150 flowers, four measurements each, all float64. target is a separate 150-length array of species codes (0, 1, 2), and target_names tells you what those codes mean. Look at the first five rows:

Each row is one flower: sepal length, sepal width, petal length, petal width, in centimeters, in that column order. Two properties are worth checking on any array before you do anything else — how many dimensions it has, and how many numbers it holds in total:

ndim is 2 because there are two axes (rows and columns); size is 600 because 150 rows times 4 columns is 600 individual numbers. shape, which you already saw above as (150, 4), is just those two axis lengths spelled out. (The outputs in this post come from NumPy 2.5 and scikit-learn 1.9 — everything shown also works on NumPy 1.2x.)

Same Type, Same Memory, No Python Loop

Here’s the idea underneath everything that follows. Our recent deep dive on Python lists described a list as a row of boxes holding references to objects scattered elsewhere in memory. That’s true, and it’s expensive: even a single Python float is a small object with its own type tag and reference count sitting behind that reference, and a list of a million numbers means a million of those scattered objects. A NumPy array throws that structure out. Every element is the same fixed-width type — float64, eight bytes, no exceptions — packed edge to edge in one block of memory. There’s no per-element object to unwrap, so an operation like “multiply every value by two” can run as a tight loop in compiled C, never touching Python’s interpreter for each individual number.

You can watch the boundary between the two worlds directly. Converting the first two real rows loaded above back into a plain Python list rebuilds exactly the object-per-value structure NumPy avoided:

Four numbers, four separate Python float objects, each reachable only through a pointer. The array those numbers came from holds no such objects at all — just the raw bytes, back to back. That difference is what every section below is really built on.

Indexing and Slicing Rows and Columns

Array indexing extends Python’s list[i] syntax with a comma: array[row, column]. Leave a side blank with : and you get everything along that axis.

Reading these in order: data[0] is the whole first row (all four measurements of the first flower); data[0, 2] narrows to a single value, that flower’s petal length; data[:5, 1] takes every row up to index 5 but only column 1 (sepal width), giving five separate values; data[10:13, :2] slices both axes at once, rows 10 through 12 and only the first two columns; and data[-1] reaches for the last row the same way negative indexing works on a plain list. (NumPy’s own indexing guide covers the rest of what this syntax supports, including step slices and ellipsis.)

Filtering Rows with Boolean Masks

Compare a whole array to a value and you don’t get one answer — you get a same-shaped array of True/False, one per element. Use that mask to index the array and you keep only the rows where it’s True:

is_setosa is a 150-length boolean array — True where target equals 0, False everywhere else. Summing a boolean array counts its True values (True behaves as 1), so is_setosa.sum() tells you 50 of the 150 flowers are setosa before you’ve even filtered anything. Feeding that same mask into data[is_setosa] keeps only the matching 50 rows, each still a full four-measurement record.

Combine conditions with & (and) or | (or) — not Python’s and/or, which don’t work elementwise — and wrap each condition in parentheses, since & binds tighter than ==:

Fourteen of the fifty versicolor flowers have a petal longer than 4.5cm — a two-part question (species, then a threshold) answered with one array expression and no loop.

When Slicing Shares Memory (and When It Doesn’t)

This is the part of NumPy indexing that catches people off guard: data[0] and data[is_setosa] look like the same kind of operation, but one gives you a view into the original array and the other gives you an independent copy. A basic slice — a plain index, a : range, a step — is a view:

Changing row_view changed data itself, because they’re the same underlying memory — row_view is just a window onto it. np.shares_memory() confirms it directly, and the value gets set straight back to its real 5.1 so the rest of this post keeps using genuine data. Boolean and fancy indexing — indexing with a mask or a list of positions, like data[is_setosa] above — work differently:

subset shares no memory with data, so editing it leaves the original completely untouched — zero rows in data now equal -1.0. Same-looking array[...] syntax, two different behaviors, and the rule is simple once you know it: a plain slice is a view, anything that involves a boolean mask or a list of indices is a copy.

Which Way Does axis Collapse?

Every NumPy reduction — sum, mean, std, min, max, and more — takes an axis argument, and getting it backwards is one of the most common early mistakes. axis=0 collapses down the rows, giving you one result per column; axis=1 collapses across the columns, giving you one result per row:

The axis=0 result is four numbers — the average sepal length (5.84cm), sepal width, petal length, and petal width across all 150 flowers, one per column, which is the question you’d actually ask of this data. The axis=1 result is 150 numbers, one per flower, each the average of that single flower’s four unrelated measurements — a number with no real biological meaning here, but a clean illustration of which direction the axis argument collapses. The same logic extends to every reduction:

Petal length has by far the largest spread (std 1.759, min 1.0, max 6.9) of the four measurements — it varies the most across the dataset, which is exactly the kind of signal that later makes petal length such a strong species predictor. argmax and argmin give you the position of the extreme instead of its value:

Flower #131 (0-indexed) has the single longest sepal in the dataset, #15 has the widest sepal, #118 the longest petal, #100 the widest petal.

This is the section that actually justifies everything above. Multiply two columns together and you get vectorized math on the whole array in one line:

A rough petal-area figure (length times width — not the true ellipse area, but a fine stand-in for comparing flowers) for every one of the 150 flowers, computed in one expression. A Python loop gets you the identical numbers:

Same numbers as petal_area[:5], down to ordinary floating-point rounding — allclose confirms it rather than a strict ==, which is the right call whenever two independent code paths produce the same math. 150 rows is too small to time reliably — noise from the operating system would swamp the real difference — so let’s replicate the same real measurements 2,000 times to get a table big enough to measure honestly:

Same real flowers, just repeated — 300,000 rows now. Time the vectorized version against a Python loop doing the identical multiplication, each measured as the best of several repeated runs to smooth out system noise:

Vectorized: 0.17 milliseconds. The Python loop: 68.9 milliseconds. Same 300,000 multiplications, same result, and the loop takes over 400 times longer on this machine. Exact numbers will differ on yours — timing always does, run to run and machine to machine — but the ratio, not the number, is the actual point: this is the mechanism from the very first section of this post, paying off on real data at real scale.

Finding the Top Rows with argsort

np.sort gives you sorted values; np.argsort gives you the indices that would sort the array, which is almost always more useful, because you can use those indices to pull matching data from every other column at once. Which five flowers have the largest petal area?

argsort sorts ascending by default, so the last five indices are the largest; [::-1] reverses them into largest-first order. Feeding those same five indices into target_names[target[...]] answers a question the petal-area numbers alone couldn’t: all five of the largest-petaled flowers in the entire dataset are virginica — not a coincidence, but the same species signal the standard deviation flagged back in the aggregation section, now showing up at the extremes.

Two Things That Bite Beginners

Aggregations silently return nan if any value is missing. Real data often has gaps; NumPy’s default reductions propagate them rather than skip them:

One missing value out of 150 turns the whole column’s .mean() into nan — not an error, just a silently useless number. Reach for the nan-prefixed version (np.nanmean, np.nanstd, np.nansum) when your real data might have gaps, and it skips them instead.

Comparing two whole arrays with == doesn’t give you one answer. It gives you an array, and Python doesn’t know how to treat an array as a single True or False:

This is the same rule that made the parentheses mandatory back in the boolean-mask section — an if statement needs one unambiguous answer, and an elementwise comparison hands it three. Use .all() (every element matches), .any() (at least one does), or np.array_equal(a, b) (a single bool comparing the whole arrays at once) depending on which question you’re actually asking.

From Arrays to Full Analysis

Every operation above comes back to the same fact from the opening section: one fixed type, one block of memory, no per-element Python overhead. Index and slice to read a piece of the data, a boolean mask to filter rows by a condition, axis=0/axis=1 to pick which direction a reduction collapses, and vectorized expressions instead of loops whenever the shape of the problem allows it — which, for numeric data, is most of the time.
