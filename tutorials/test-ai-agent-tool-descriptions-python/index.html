How to Test AI Agent Tool Descriptions Offline with Python

Build a framework-independent audit that ranks 12 synthetic tool definitions against labeled requests, compares vague and specific wording, measures top-1 accuracy and recall at three, and inspects the cases that a lexical score cannot resolve safely.

Mehdi Lotfinejad
August 13, 2026 · 11 min read

Two tools can both say that they “handle reservations,” yet one reads a booking and the other cancels it. A language model then has to guess which action the author intended. The problem begins in the catalog, before the agent calls any function.

To test AI agent tool descriptions offline, create labeled user requests, convert each tool’s name, description, and parameter help into searchable text, and rank the tools for every request. Compare top-1 accuracy and recall at a small shortlist size before and after each rewrite, then read every changed or unresolved case because a text-similarity score is not a safety decision.

This tutorial uses a fictional facilities help desk with 12 tools for room bookings, access passes, repairs, notices, equipment, and visitors. It does not call a large language model (LLM) or execute a tool. Instead, it tests whether the words in each definition make the intended tool easy to find.

Do not include ambiguous requests in accuracy. There is no single correct tool for those rows, so forcing one label would teach the audit to reward guessing.

How an Offline Description Audit Works

The audit treats a tool catalog as a small search index. Each tool becomes one text document. A user request becomes a search query. The ranker places tools with more relevant words nearer the top.

The process has four parts:

  1. Freeze a set of requests and their reviewed expected tools.
  2. Rank one unchanged catalog using its current wording.
  3. Rewrite descriptions and parameter descriptions without changing tool names or behavior.
  4. Rank the same requests again and compare each request, not only the average.

This separation matters. If you change the requests, tool set, ranking method, and descriptions together, you cannot tell which change affected the result.

The catalog uses three core fields from the current Model Context Protocol tool specification: a unique name, a human-readable description, and an inputSchema that defines the accepted arguments. The protocol does not define TF-IDF as a tool selector. We use it only as a fast, inspectable test for unclear documentation.

TF-IDF, short for term frequency–inverse document frequency, gives more weight to distinctive words and less weight to words that appear in many documents. Cosine similarity then compares the direction of two numeric text vectors. A larger value means stronger word-level similarity in this fitted vocabulary. It is not the probability that a tool is correct.

A useful first draft usually answers four questions in plain English: What action occurs? What object does it affect? When should the tool apply? Which inputs must already be known? Keep validation rules in the schema as well; a good description does not replace input validation.

Turn Each Definition into Searchable Text

The ranker needs one string per tool. Include the name, main description, field names, and field descriptions. Do not include hidden implementation notes that a real model would never see.

Replacing underscores makes the programmatic name readable to the vectorizer. Parameter text matters because a request may mention an asset tag, booking reference, or door zone without repeating the main description.

Next, fit the vectorizer on the 12 tool documents. ngram_range=(1, 2) includes single words and adjacent two-word phrases. The current TfidfVectorizer documentation calls those unigrams and bigrams.

There are 12 tool rows and 381 learned text features. The score matrix has one row per request and one column per tool. scikit-learn defines cosine similarity as a normalized dot product. Normalization makes documents of different lengths easier to compare, but it does not understand intent, negation, or business risk.

Rank the Tools and Measure the Shortlist

For each score row, sort column indexes from largest to smallest. The next small function returns ordered names rather than executing anything:

The first request asks, “What time is reservation R-104?” The expected lookup tool ranks first, while the two other room tools remain nearby. This is a ranking result, not permission to call the first function.

Use three metrics across the 36 clear cases:

  • Top-1 accuracy is the share whose expected tool ranks first.
  • Recall@3 is the share whose expected tool appears anywhere in the first three candidates.
  • Mean reciprocal rank (MRR) averages 1 / rank. Rank 1 contributes 1, rank 2 contributes 0.5, and rank 8 contributes 0.125.

The build calculated each metric separately for the vague and specific catalogs:

Top-1 accuracy rose from 23 of 36 clear requests (63.89%) to 30 of 36 (83.33%). The expected tool appeared in the first three for 35 of 36 requests with the specific catalog. MRR also rose, so the metric gave more weight to expected tools appearing near the front of the rankings.

The right panel prevents a misleading conclusion. Ten requests moved to rank 1 and 20 stayed there, but six still ranked below first. Three requests that were first under the vague catalog also fell to rank 2 after the rewrite. Better aggregate metrics do not mean every request improved.

For example, C17 says, “Check progress on work order M-44.” Its expected maintenance_job_lookup tool ranked eighth because the catalog used maintenance job but the request used work order. This is an actionable vocabulary gap. Add representative wording, rerun the frozen set, and make sure the fix does not create a new collision elsewhere.

Inspect Ambiguous Requests Outside the Accuracy Score

The six ambiguous cases test a different property: how the ranker behaves when no single action is justified. Print the first two candidates and their score gap for the specific catalog:

A01 only says, “Deal with room Cedar tomorrow.” It does not say whether to read, create, or cancel a booking. Its tiny gap of 0.0142 is consistent with that ambiguity. A02, however, says only “Handle badge P-18” and still produces a wider gap. That result shows why a margin threshold cannot identify ambiguity by itself.

A zero score has a specific meaning here: the query contains no term that survived into the fitted vocabulary. Ties then depend on array order, which explains the unrelated visitor tool for A05. Never let that ordering accident trigger a function call.

Use score gaps as review signals, not calibrated confidence. A production policy should separately decide when required arguments are missing, when several actions are plausible, and when a human must confirm a sensitive operation. If you need to evaluate an actual local model after the description audit, the local LLM tool-routing tutorial shows how to keep model predictions and expected labels separate.

Common Mistakes and Troubleshooting

You test only one request per tool. One example rewards copied keywords. Include synonyms, short requests, unusual word order, and realistic missing details.

The expected label changes after seeing the ranking. Freeze labels first. If a reviewer finds a genuine labeling error, record and review the change rather than silently editing it to improve the score.

Descriptions list every neighboring action. A lexical ranker sees the word cancel even inside “do not cancel bookings.” It does not reliably understand the negation. State only the tool’s own action and inputs directly, then test contrastive wording with the real model separately.

A high Recall@3 is reported as routing accuracy. Recall@3 only says that the expected tool reached the shortlist. Another component still has to choose among those candidates. Name the metric precisely.

Similarity is treated as confidence. Cosine similarity measures vector overlap. Its values are not calibrated probabilities, and scores from different catalogs may not be directly comparable because each vectorizer learns a different vocabulary.

The query vocabulary is fitted with the catalog. Fit on tool text, then call transform on requests. Fitting on test requests leaks their wording into the index and makes the exercise less representative.

Specific wording grows without limit. Long definitions can add collisions and hide the main action. Keep one clear responsibility per tool. If two definitions remain nearly identical, the interface may need different names, schemas, or boundaries rather than more adjectives.

The offline audit replaces a model evaluation. It cannot test instruction following, tool-call JSON, argument generation, multilingual behavior, or provider changes. After documentation passes this cheap check, run a frozen evaluation with the exact model, prompt, catalog, and settings you plan to use.

Recap: Treat Tool Text as Tested Interface Code

A tool description is part of the agent interface, so change it with the same care as code. Start with reviewed requests, preserve clear and ambiguous cases, flatten only the metadata the model can see, and compare the same catalog before and after a rewrite.

In this executed audit, specific wording raised top-1 accuracy from 63.89% to 83.33% and moved ten clear requests to rank 1. It also left six requests below rank 1, introduced three rank-2 regressions, and failed to identify every ambiguous request by score gap. Those remaining problems are the useful part of the test: they show which words, tool boundaries, and policies still need attention.

The reusable sequence is freeze, describe, rank, compare, inspect. Use the offline ranker as a fast documentation check, then test the final catalog with the real model and keep execution safety in ordinary application code.
