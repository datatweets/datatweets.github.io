Model Growth Stages in Python with an Enum State Machine

A plant only moves forward through seed, sprout, and mature — never backward, and never past wilted. This post builds that rule as code: an Enum for the stages, a tick() method that's the only thing allowed to change one, and a Garden that runs the same day-by-day loop over any plant type without caring which one it is.

Mehdi Lotfinejad
August 8, 2026 · 7 min read

A tomato seedling doesn’t sprout, un-sprout, then sprout again. It moves in one direction — seed, sprout, mature — and if it wilts, that’s the end of the line; watering it after that doesn’t undo anything. Model that plant with a handful of loose boolean flags (is_sprouted, is_mature, is_wilted) and nothing in the code stops you from accidentally setting is_mature = True on a plant that’s still a seed, or “reviving” a wilted one by flipping is_wilted back to False. The flags don’t know about each other, so they can’t enforce the one rule that actually matters: what can happen next depends entirely on what state you’re already in.

The fix is to stop representing “what stage is this plant at” as several independent booleans and represent it as one value from a fixed, ordered set — Python’s Enum — then route every stage change through a single method that’s the only code in the program allowed to touch it. That method checks the current stage before deciding the next one, so “mature can’t happen before sprout” and “wilted can’t go back to anything” are enforced in one place instead of trusted to every call site that touches the plant.

Four States, One Direction

A plant in this simulator is always in exactly one of four stages: SEED, SPROUT, MATURE, or WILTED. Three of those are a straight line forward; the fourth is a trapdoor that can open from anywhere and never closes.

auto() just hands out increasing integers so you never have to keep two enum members from accidentally sharing a value — the numbers themselves don’t mean anything here. What matters is that GrowthStage.SPROUT is a single, comparable, unmistakable object, not a string you could typo ("Sprout" vs "sprout") or a loose flag that some other code could set out of order.

That diagram is the whole design in miniature: three states connected by one path forward, and a fourth state every other state can fall into but nothing can leave. Everything below is that shape, enforced in code.

A Plant That Guards Its Own Transitions

tick() is the only method that changes self.stage, and it always checks the current stage before deciding what — if anything — happens next:

Notice the shape: every branch either does nothing (already wilted), checks a threshold against the current stage before moving to the next one, or falls through to “no change yet.” There’s no branch that can jump from SEED straight to MATURE, because the elif only fires when self.stage is GrowthStage.SPROUT already. The state you’re in restricts which transitions are even reachable — that’s the entire mechanism, and it fits in about fifteen lines.

The tomato hits SPROUT on day 2 and MATURE on day 6, on schedule with its own class attributes; the sunflower is still SPROUT on day 7 because it needs 9 days to mature. Garden.advance_day() never branches on which subclass it’s looking at — that’s the payoff of putting the state machine on the shared Plant base class instead of duplicating a tick() per plant type.

Neglect Is a One-Way Trip

Skip watering, and the same tick() method that advances a plant toward MATURE is what wilts it — no separate “neglect check” bolted on from outside:

Tomatoes wilt after 2 days without water (max_days_without_water = 2), so the third unwatered day pushes days_since_watered to 3 and the plant wilts. From day 3 onward, age_days stops climbing too — the early-return guard at the top of tick() means a wilted plant is frozen, not just stage-locked.

The more important test is what happens if you try to undo it:

Nothing moves. water() checks the stage first and returns immediately for a wilted plant instead of resetting days_since_watered, and tick()’s own guard does the same thing from the other direction. Two independent checks, both agreeing that WILTED has no way out — which is exactly what the state diagram promised and what a loose is_wilted boolean couldn’t have guaranteed on its own (nothing stops other code from writing plant.is_wilted = False directly).

Why This Beats a Flag for Every Stage

Picture the alternative: is_sprouted, is_mature, is_wilted, all independent booleans on the same object. Every one of the checks above would need to be reimplemented as a chain of if not self.is_wilted and self.is_sprouted and not self.is_mature:-style conditions, repeated at every call site that changes state — and nothing would stop a bug somewhere else in a larger program from setting two of those flags true at once (is_sprouted = True and is_mature = True), a state that shouldn’t exist but that plain booleans can’t rule out. An Enum value can only ever equal one member at a time, so “sprouted and mature simultaneously” isn’t a bug you have to guard against — it’s not representable in the first place.

This is the same idea behind the Discount objects in our post on composing a Python order system — encode a rule as the shape of your types rather than as scattered conditionals, and entire categories of bugs become impossible to write instead of just unlikely.
