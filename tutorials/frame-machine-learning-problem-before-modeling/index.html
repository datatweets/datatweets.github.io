How to Frame a Machine Learning Problem Before Modeling

Turn a vague prediction request into a testable classification task, then audit target timing, feature availability, time drift, and a majority baseline with pandas.

Mehdi Lotfinejad
July 30, 2026 · 11 min read

“Predict which support tickets are at risk” sounds like a clear machine learning request. It is not yet precise enough to implement. Risk could mean a slow first reply, a poor rating, or an unresolved issue. A prediction made when a ticket arrives must also use different information from one made after an agent has replied.

To frame a machine learning problem, specify the decision, one prediction unit, the moment the prediction is made, a measurable target, and the information available at that moment. Then use historical data to verify that the target labels are complete, become known only after prediction time, contain enough examples of each class, and can be evaluated against a simple baseline on later records.

This tutorial turns those questions into a small, executable audit. We will stop before choosing a sophisticated algorithm. That boundary matters: a model cannot repair an unclear target or a feature that arrives too late.

Setup and the fictional ticket data

You need Python 3.11 or later and basic experience running a script or notebook cell. A DataFrame is a pandas table with named columns. A classifier is a model that predicts a category, such as missed or met.

Create a virtual environment and install the packages used here:

On Windows PowerShell, activate the environment with .venv\Scripts\Activate.ps1. The published run used Python 3.13.2, NumPy 2.5.1, pandas 3.0.3, scikit-learn 1.9.0, and Matplotlib 3.11.0.

Download support_ticket_history.csv and place it beside your Python file or notebook. This original synthetic dataset was generated with NumPy seed 20260730 and is released under CC0-1.0. Synthetic means that code created the records. All 960 tickets, customer fields, times, and outcomes are fictional and do not describe a real support service.

The first step loads timestamps as dates instead of plain text. The preview keeps only five columns so you can inspect each row without scrolling across the full table.

There are 960 rows and 13 columns. Each row represents one ticket at the moment it entered the fictional queue. A target value of 1 means the first response took more than eight hours; 0 means it arrived within eight hours.

Understanding the prediction brief

A useful problem statement is a short agreement about how the prediction will be used. Call it a prediction brief. It connects a model score to a concrete decision:

The prediction unit prevents accidental mixing of rows. Here it is one ticket, not one customer or one message inside a conversation. The prediction moment creates a time boundary. Anything known only after queue entry cannot help the live prediction.

The decision also keeps the task useful. The classifier does not solve staffing by itself. It ranks or labels tickets so a coordinator can decide which ones need earlier attention. If no team can act on the output, improving a model score will not improve the response process.

The selected target makes this a binary classification task because it has two possible classes. If the actual need were to estimate the number of response minutes, the target would be numeric and the task would instead be regression. That is a different problem brief, even though it starts from the same table.

Turn the outcome into a label you can audit

The target must describe a measurable event whose result becomes known after the prediction moment. This dataset contains first_response_minutes, but that number is an outcome. Using it as an input would reveal the answer.

For a ticket that receives a reply within eight hours, label_available_at is the response time. For a late ticket, the label becomes known when the eight-hour limit passes. The following checks verify unique units, a complete binary target, and correct event order:

All four results support the brief. Every row has its own ticket ID, every row has a target, both classes exist, and no label is known at prediction time. These checks do not prove that the eight-hour rule is valuable. That choice still needs agreement from the people who own the response process.

Now count the two target classes. This check shows whether the positive event is rare and gives context for later metrics.

The data contains 299 tickets that miss the response target, or 31.1% of all rows. That is enough positive examples for this teaching audit. In a real project, you would also break the count down by region, product, language, or another group that the system must serve. A healthy total can hide a group with very little data.

Check what is available at prediction time

Feature leakage means that an input contains information that would not exist when the prediction is made. It creates an unrealistic evaluation because the model learns from the future.

Write the allowed feature list explicitly. Then compare it with the fields created after the prediction moment. This is more reliable than dropping one known target column and assuming everything else is safe.

An empty list is the required result. first_response_minutes may have a strong relationship with the label, but it is known too late. An agent assignment or internal note could have the same problem in a real system. Ask when every column is created, not only what its name means.

Next, measure missing values only in the proposed inputs. The pandas isna reference explains that the method marks missing values as True.

customer_plan is missing for 1.9% of rows, and previous_30d_contacts is missing for 1.1%. This does not require abandoning the task. It creates two follow-up steps: determine why the values are absent, then choose a preprocessing rule using the training data only. The pandas data quality tutorial shows how to extend this first check to IDs, categories, numeric conversion, and allowed ranges.

Reserve later tickets for the evaluation

A random split assumes that past and future rows come from roughly the same process. Support workload can change over time, so this brief asks a harder and more useful question: can a model learned from earlier tickets work on later tickets?

Sort by prediction_at, place the first 75% in training, and keep the final 25% for testing. The two assertions make the time boundary executable.

The test period begins after the training period ends, with no shared ticket IDs. The missed-response rate also rises from 27.6% in training to 41.7% in testing. This synthetic change is deliberate. It shows why a random split can hide the conditions a deployed model will meet.

For data with repeated customers, patients, or devices, time order may not be enough. Related rows may also need to stay together. The tutorial on preventing duplicate leakage in train-test splits explains that separate grouping boundary.

Establish the score to beat

A baseline is a simple reference result. It tells you whether a later model improves on an easy rule. We will use scikit-learn’s DummyClassifier with strategy="most_frequent". It learns only the most common training class and predicts that class for every test row.

Fit the baseline on earlier tickets, then calculate three metrics on later tickets. Recall is the share of missed-response tickets that the classifier finds. Balanced accuracy calculates accuracy separately for each class and averages the two results, giving equal importance to both classes.

The baseline predicts that every ticket will meet the response target. It is correct 58.3% of the time because that is the larger class in the test period. However, its recall is zero: it finds none of the 100 tickets that miss the target. Its balanced accuracy is 0.500 because it identifies 100% of one class and 0% of the other, then averages those two rates.

This is why the brief names metrics before model selection. If the decision is early review, plain accuracy rewards a system that never identifies the tickets the team wants to find. Recall is necessary, but it is not sufficient by itself. A real review must also measure how many tickets are flagged and whether the team can handle that workload.

Read the feasibility evidence together

The executed build groups target rates by month and plots the chronological boundary beside the baseline metrics.

The left panel shows that the missed-response rate changes during this six-month period: later months contain more tickets that miss the target. It does not show why the rate changed. In this synthetic dataset, backlog grows over time, but a real investigation would check staffing, ticket mix, product changes, and logging changes before claiming a cause.

The right panel sets the minimum modeling requirement. A useful candidate must do more than exceed 58.3% accuracy. It must find some late tickets and improve balanced accuracy while keeping the review volume practical. You can download the executed prediction_problem_audit.csv to inspect the six pass/fail checks produced by the build.

The project is ready for a small modeling experiment, not deployment. The label and time boundary are testable, both classes exist, feature missingness is limited, and the baseline exposes an informative failure. The next stage can fit preprocessing on the training rows only and compare a simple classifier with this reference.

Common mistakes and troubleshooting

The target is a topic, not a measurable event

“Ticket risk” cannot be labeled consistently. Write a rule with an observable result and a time limit, such as “first response exceeds eight hours.” Confirm that the rule matches the decision instead of choosing it only because the column is convenient.

A feature exists in the final table but not at prediction time

Historical exports often join events that happened before and after the decision. Create a list of allowed inputs and record when each one becomes available. Remove outcome fields before any feature search.

Recent rows do not have mature labels

An open ticket cannot yet be called a success if its eight-hour window has not ended. Compare the data snapshot time with label_available_at. Exclude or separately track rows whose outcome window is still open.

A random split gives an easier question

If production always predicts future records, reserve a later period for evaluation. If data also contains repeated entities, add group-aware splitting. Choose the boundary that matches how the system will encounter new cases.

Accuracy hides failure on the important class

Print class counts and a majority baseline before training a complex model. Add recall, balanced accuracy, precision, cost, or capacity measures according to the decision. No single metric describes every operational trade-off.

Missing values are silently removed

Dropping rows can change class balance and remove important cases. Measure missingness first, investigate its source, and fit any imputation rule using training data only. Then apply the learned rule to validation and test data.

The team cannot act on the prediction

A technically valid target can still be unusable. Name the person or process that receives the output, the action they can take, and any capacity limit. If there is no possible action, revise the task before modeling.

Recap: make the question executable

Problem framing is complete when another person can reproduce the decision boundary from the brief and the data checks.

  1. Name the action the prediction will support.
  2. Define one prediction unit and one prediction moment.
  3. Express the target as a measurable future event.
  4. Allow only inputs that exist at prediction time.
  5. Audit IDs, target coverage, class counts, timing, and missing values.
  6. Reserve an evaluation set that matches future use.
  7. Establish a simple baseline and metrics tied to the decision.

For this fictional ticket history, 299 of 960 tickets miss the response target. Later tickets have a higher miss rate, while the majority baseline reaches 58.3% accuracy but finds none of the tickets that miss the target. Those facts turn “predict risk” into a concrete next experiment: build a training-only preprocessing pipeline, fit a simple classifier, and require it to beat the zero-recall baseline on later data while keeping the review queue within the team’s capacity.
