Logistic Regression vs. Random Forest for Heart Disease Prediction in Python

This project tutorial pits a scaled logistic regression model against a random forest on the real Cleveland heart disease dataset, shows how a single train/test split can flip the apparent winner, then settles it with 5-fold cross-validation, a recall-based tie-break, and one honest confirmation on held-out test data.

Mehdi Lotfinejad
August 20, 2026 · 12 min read

Two people can point scikit-learn at the exact same clinical dataset, fit a LogisticRegression and a RandomForestClassifier, and walk away with opposite opinions about which one is “better.” Not because either of them made a mistake — because a single 80/20 train/test split is a noisier measurement than most tutorials let on, and a couple of points of test accuracy can flip depending on nothing more meaningful than which random_state you typed. If you’ve already read our post on logistic regression in Python, you know how to fit and read one model. This one is about the step that comes after: deciding, honestly, whether a second model actually beats the first.

To compare two classifiers properly, don’t trust one train/test split. Fit both models with StratifiedKFold cross-validation on the training data, compare the mean and standard deviation of a real metric — accuracy, ROC AUC, recall — across the folds, and touch the untouched test set exactly once, at the end, to confirm the winner you already picked. If the cross-validated scores overlap within their standard deviations, that isn’t a tie to shrug off; it’s honest information, and you break it with whichever metric matches what an error actually costs.

We’ll build that workflow end to end on a real dataset: predicting whether a patient has heart disease from 13 clinical measurements. (The outputs below come from scikit-learn 1.9.0, pandas 3.0.3, and numpy 2.5.1.)

A Reproducible Setup: the Cleveland Heart Disease Data

This is real data from a cardiology study at the Cleveland Clinic: 297 patients, 13 measurements each (age, blood pressure, cholesterol, exercise-test results, and so on), plus a target column of 1 (disease present) or 0 (absent). Download it and take a first look:

Data: the Cleveland Heart Disease dataset (Janosi, Steinbrunn, Pfisterer & Detrano, 1989; CC BY 4.0), via the UCI Machine Learning Repository. Every column arrives numeric already, so there’s no encoding step standing between you and modeling. The two classes are close enough (160 vs. 137) that plain accuracy stays a meaningful number instead of a trap — a model that always guesses “no disease” would only score 54%, not the 90%+ you’d see on a badly imbalanced problem.

Split off a test set once, before either model sees any of it, and hold X_test/y_test aside until the very end of this post:

stratify=y keeps roughly the same disease rate in both pieces, which matters more than usual with only 297 rows total — an unlucky split could otherwise leave the test set with almost no positive cases to evaluate against.

Round One: Fit Both Models on One Split

Logistic regression needs its features on a comparable scale to behave well and converge quickly, so it gets a StandardScaler in front of it via a pipeline. Random forests split on raw thresholds and don’t care about scale at all, so it goes in unscaled:

On this split, the random forest wins by three points. If this were the only evidence you looked at, you’d write down “random forest is the better model for this problem” and move on. That conclusion is about to look shaky.

Does the Winner Hold Up? Rerunning the Split

The only thing that changed between “logistic regression wins” and “random forest wins” so far is a single number: random_state. Rerun the exact same fit-and-compare loop across six different splits and watch what happens to the scoreboard:

Logistic regression wins three of the six splits, random forest wins two, and they tie on one. There is no split-independent sense in which either model is “the winner” here — the seed you pick decides the headline. This is the whole problem with judging models off a single train/test split: the split itself carries several points of noise on a 297-row dataset, and that noise is easy to mistake for a real difference between models.

Cross-Validation: What the Single Split Was Hiding

Instead of one lucky or unlucky split, run StratifiedKFold cross-validation: the training process rotates through five folds, each time holding out a different fifth of the data to score against, so every row gets used for both training and evaluation across the five runs. The result is a distribution of scores per model, not a single number.

This is the more honest picture, and the more boring one: the two models are statistically indistinguishable here. A 0.006 accuracy gap and a 0.001 ROC AUC gap are both far smaller than either model’s own standard deviation across folds. Cross-validation didn’t hand random forest — or logistic regression — a decisive win; it correctly reported that, on this dataset, there isn’t one. See scikit-learn’s cross-validation guide for the other splitting strategies StratifiedKFold sits alongside.

Breaking a Real Tie

A statistical tie on accuracy and ROC AUC doesn’t mean you can’t choose — it means accuracy and ROC AUC aren’t the metric that should decide it. In a screening context, a false negative (telling a sick patient they’re fine) is worse than a false positive (an unnecessary follow-up test), so the tiebreaker should be recall: of the patients who truly have heart disease, how many does each model catch?

Still close, but logistic regression edges ahead on the metric that matches the real cost. That’s the model we’ll confirm on the test set — chosen for a reason we can state out loud, not because it happened to win the one split we tried first.

Do the Two Models Even Agree on What Matters?

Before trusting either model, it’s worth checking whether they learned the same signal or arrived at similar scores by different, possibly spurious, routes. Random forests expose feature_importances_; logistic regression’s standardized coefficients play the same role, since every feature was scaled to the same units before fitting:

Four of five overlap — ca (number of major vessels visible on fluoroscopy), cp (chest pain type), thal (a thalassemia blood-disorder result), and oldpeak (ST depression from the exercise test) show up as important to both a linear model and a tree ensemble that can capture entirely different patterns. That agreement is reassuring: it’s evidence both models converged on real clinical signal rather than each fitting its own noise. The one mismatch — random forest ranks thalach (max heart rate) fifth, logistic regression ranks sex fifth instead — is a legitimate difference in how the two algorithms weigh a feature that correlates with several others, not a red flag on its own.

Confirming the Winner, Once

Cross-validation picked logistic regression; the test set — untouched since the very first split — gets exactly one job now, which is to report how that specific, already-chosen model performs on data it has never influenced:

On the 60 held-out patients, the model catches 22 of 28 true disease cases (sensitivity 0.786) while correctly clearing 28 of 32 healthy ones (specificity 0.875), for a ROC AUC of 0.950 — a strong ranking of sick patients above healthy ones, independent of any particular threshold. Notice this test accuracy (0.833) sits right in the middle of the six single-split numbers from earlier, which is exactly what you’d expect: it’s not magically better than any one split, it’s just the number you can actually trust, because it came from a model chosen before this data was touched.

Small Traps That Skew a Model Comparison

Scaling barely moved accuracy here — but it changed everything else about the logistic regression fit. Refit on the raw, unscaled features and compare:

The accuracy is identical, so it’s tempting to conclude scaling didn’t matter. It mattered plenty just below the surface: the unscaled fit needed 931 iterations to converge versus 10 for the scaled one, and its top-5 coefficient ranking is a genuinely different list — because a raw coefficient’s size depends on that feature’s raw scale, not its real influence. Skip scaling and your accuracy might look fine while your interpretation quietly becomes wrong.

A random forest not needing scaling isn’t the same as it needing no thought at all. Columns like cp and restecg are small integer codes for categories, not genuine quantities — a tree splits on “is cp ≤ 2.5?” without knowing that’s a category boundary, not a magnitude. It usually works out fine for trees since they only care about ordering within a feature, but it’s worth knowing you’re relying on that, not on the encoding being meaningful.

compare_models_cv’s cv argument inherits scikit-learn’s real limits — it doesn’t validate anything itself. Pass an integer larger than your smallest class and it fails loudly rather than silently:

That’s the right failure mode — a cv value that large would mean folds with essentially one row each, which cross-validation should refuse rather than quietly running with meaningless statistics.

Standard deviations of 0.03-0.06 are ordinary at this sample size, not a sign anything is broken. With 297 rows split five ways, each fold scores roughly 59 patients. A model that’s “really” 82% accurate will bounce around that true value by several points from fold to fold just from sampling noise — treat any single fold’s number as unreliable on its own, and lean on the mean across folds instead.

So, Logistic Regression or Random Forest?

On this dataset, logistic regression, chosen because it edged out random forest on cross-validated recall — not because it won the first split we happened to try. Stop at a single 80/20 split, as the opening of this post did, and you’d have shipped the other model with equal confidence and no idea you’d made an arbitrary call. The fix generalizes past this one dataset: cross-validate before you compare, decide your tiebreak metric before you look at the numbers, and touch the test set exactly once.
