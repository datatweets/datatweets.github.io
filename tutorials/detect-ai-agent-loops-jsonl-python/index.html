How to Detect AI Agent Loops in JSONL Traces with Python

Turn ordered tool events into an inspectable loop report. Rebuild each agent session, measure repeated calls and stalled state, test the rules against labeled cases, and identify the exact step where progress stopped.

Mehdi Lotfinejad
July 15, 2026 · 10 min read

An AI agent can keep calling tools while making no useful progress. The final log line may only say step_limit, which tells you that a guard stopped the run. It does not show whether the agent repeated one broken call, alternated between two tools, or made several valid retries.

To detect AI agent loops from JSONL traces, sort events by session and step, mark a tool call as stalled when its decision-relevant state does not change, then count consecutive stalled and identical-call streaks. Flag sessions that cross limits chosen from labeled traces, while keeping short retries below the limit and enforcing a separate hard step cap at runtime.

This tutorial turns event-level JSON Lines data into a small loop detector. We will analyze fictional sessions from a file-catalog maintenance agent. Some sessions finish normally, some recover after timeouts, and four contain known loops.

Understanding Repetition Without Progress

A session is one complete agent run. A trace is its ordered record of operations. Each row in our trace represents one tool call and contains three kinds of evidence:

  • identity: session_id and step place the event in one trajectory;
  • action: tool_name and argument_key describe what the agent tried; and
  • progress: state_before and state_after describe the decision-relevant state around the call.

The argument_key is a safe comparison value such as catalog-v3, not a raw prompt or full tool payload. In production, create it from normalized, non-secret fields or a keyed digest. A plain hash is not enough protection when the possible values are easy to guess.

The state labels are also compact comparisons. A call makes progress when it adds information or moves the task forward. For example, files-found becoming schema-loaded is progress. A timeout that leaves files-found unchanged is a stalled step.

This gives us two useful loop signals:

  1. A repeated-call streak counts consecutive calls with the same tool and argument key when every call leaves state unchanged.
  2. A stalled-step streak counts any consecutive calls with no state change, even if tool names alternate.

The second signal matters because an agent can cycle between read_schema and compare_columns. Neither call repeats immediately, but the session still stays in the same state.

OpenTelemetry defines a span as one unit of work or operation. Its Generative AI semantic conventions cover agent and tool operations, but the project is still evolving and has moved to a separate GenAI conventions repository. Treat those conventions as a naming reference and keep your own trace schema versioned. The custom progress fields in this lesson express an application decision; they are not standard OpenTelemetry attributes.

For production calibration, ask reviewers to label a larger set of recent traces without looking at the detector result. Include normal long sessions, temporary provider errors, polling tools, multi-agent handoffs, and several loop shapes. Then choose limits that match the cost of a false alarm and the cost of a missed loop.

Detection should complement a runtime stop rule, not replace it. A hard step or cost budget ends runaway work immediately. Offline trace analysis explains what happened and helps improve prompts, tools, state handling, and retry policy. The safe Python agent loop tutorial shows how to enforce a step budget inside the runtime. Common Mistakes and Troubleshooting

Rows are grouped but not ordered. A streak depends on event order. Sort by a session-local sequence number before comparing adjacent calls. Do not trust file order after merging or exporting traces.

Every repeated tool is called a loop. A retry can be correct, and one tool may process several different items. Include the argument key, require consecutive repetition, and check whether decision-relevant state changes.

The state comparison ignores new observations. A read-only tool may not modify a database, but its result should update the agent’s working state. If a successful lookup leaves state_after identical only because instrumentation ignored the returned evidence, the detector will create false alarms.

A step-limit outcome is treated as proof. A long but progressing task can hit a limit. Use the outcome as context, then inspect repeated calls and state movement. Keep separate labels for permission_error, timeout, user cancellation, and normal completion.

Thresholds are copied from this tutorial. Three and four work for these labeled teaching sessions. Measure the normal retry and polling behavior of your own tools. Some tools need tool-specific limits.

Raw prompts, arguments, or results are stored for convenience. Traces may contain personal data, credentials, private documents, or model instructions. Collect the smallest fields needed, redact secrets before export, restrict access, and set a retention period. A comparison key should not make sensitive input recoverable.

Token counts are converted to cost with an old price. Token usage and price are different measures. Use provider-reported usage where possible, and join it to current, versioned pricing only when you need a cost report.

The detector runs without labeled regression tests. Add known retries, alternating cycles, terminal errors, and legitimate long sessions to your test set. A change that catches more loops may also increase false alarms.

Recap

An agent loop is not simply a long session or a repeated tool name. It is repeated activity with no meaningful progress.

We loaded ordered JSONL events, validated session steps, and compared the state before and after every tool call. One counter found identical stalled calls. A second counter found alternating tools that left state unchanged. Session-level limits identified four designed loops while leaving short retries and a permission error unflagged.

The durable workflow is order, compare, count, flag, review. Keep a hard runtime budget to stop waste, and keep enough privacy-aware trace structure to explain why the stop happened. As your agent changes, refresh the labeled cases and recalibrate the limits instead of treating one threshold as permanent.
