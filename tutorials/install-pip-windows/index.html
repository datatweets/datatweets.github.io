Install pip on Windows: Fix the 'Not Recognized' Error

pip almost always ships with Python already — this walks through checking that, rebuilding it with ensurepip if it's missing, and fixing the classic 'pip is not recognized' error by understanding what PATH actually controls.

Mehdi Lotfinejad
August 8, 2026 · 9 min read

You installed Python on Windows, opened Command Prompt, typed pip install requests, and got 'pip' is not recognized as an internal command or operable program or batch file. Or maybe pip works fine on its own but every tutorial you follow assumes a pip command that your machine doesn’t seem to have. Either way, the confusing part is that you probably never had to install pip at all — it’s very likely already sitting inside your Python install, and the problem is something else entirely. (If you haven’t installed Python itself yet, our Python on Windows install guide covers that first step.)

Here’s the direct answer: pip has shipped inside every Python 3.4+ installer since 2014, so open Command Prompt and run python -m pip --version before doing anything else — a version number means you’re already done. If that fails with No module named pip, run python -m ensurepip --upgrade, which rebuilds pip from a copy stored inside your own Python install and needs no internet connection. And if python -m pip --version works but the bare pip command says it isn’t recognized, you don’t have a missing-pip problem at all — you have a PATH problem, and python -m pip <command> sidesteps it completely because it never depends on pip.exe being on PATH in the first place.

Pip Rides Along Inside Python, Not Beside It

The mental shift that fixes most of these errors: pip isn’t a program you install once, system-wide, the way you’d install a browser. It’s a package that lives inside a specific Python interpreter — the one at C:\Users\you\AppData\Local\Programs\Python\Python313\, or the one Anaconda manages, or the one sitting inside a project’s virtual environment. Each of those has its own Scripts folder, and each Scripts folder can hold its own pip.exe.

When you type pip in Command Prompt, Windows searches every folder on your PATH environment variable in order and runs the first pip.exe it finds — or nothing, if none of those folders are on PATH. When you type python -m pip instead, you skip the search entirely: you’re telling one specific python.exe to run the pip module it already has installed, which always exists if that interpreter has pip at all. That’s the whole trick behind almost every fix in this post.

When pip Really Is Missing: Rebuilding It with ensurepip

Occasionally pip genuinely isn’t there — most commonly if you’re using the embeddable zip build instead of the regular installer, since that stripped-down distribution deliberately leaves pip out, or if a site-packages folder got corrupted or partially deleted. ensurepip is the built-in module made exactly for this. It doesn’t download anything from the internet — it installs pip from a wheel file that’s bundled inside the Python standard library itself, which is why it works even with no network connection:

“Looking in links” points at a temp folder rather than PyPI — that’s ensurepip reading its own bundled copy, not fetching one. This is also the fastest fix if pip seems to have quietly broken: rerunning ensurepip --upgrade against the interpreter it belongs to rebuilds it from scratch in a couple of seconds.

‘pip Is Not Recognized’ Is a PATH Problem, Not a Missing-pip Problem

This is the error that sends the most people searching for “how to install pip” when they don’t actually need to install anything. The official Windows installer has a checkbox on its first screen — “Add python.exe to PATH” — and depending on which installer version you used, it may not have been checked by default. Skip it, and Command Prompt has no way to find python.exe or the Scripts\pip.exe next to it, no matter how correctly Python installed underneath.

The result is the exact error from the top of this post:

You have two real fixes, and I’d reach for the second one as a habit, not just a one-off patch:

  1. Add Python to PATH properly. Re-run the installer, choose “Modify,” and check “Add python.exe to PATH” this time — or add ...\Python313\ and ...\Python313\Scripts\ to your PATH environment variable by hand through System Properties → Environment Variables.
  2. Stop depending on PATH for this at all. Use python -m pip instead of bare pip everywhere. If python itself resolves — and it almost always does, since it’s harder to leave off PATH by accident — then python -m pip works too, regardless of whether pip.exe specifically ever made it onto PATH.

The second option is also what keeps you safe once you start using virtual environments: each one has its own python.exe and its own pip, and python -m pip always operates on whichever interpreter you’re currently pointed at, which is exactly the behavior you want.

Multiple Pythons, Multiple pips: the py Launcher

If you’ve ever installed Python from python.org, then later added Anaconda, or picked up a copy from the Microsoft Store, you have more than one interpreter on your machine — and each one can have its own, different version of pip. Keeping pip Itself Up to Date

pip updates more often than Python does, and an old pip occasionally can’t resolve a package’s newer dependency metadata. Upgrading it is a normal, routine step, not a troubleshooting move:

pip just uninstalled its own older version and replaced it — a self-upgrade, which is why python -m pip install --upgrade pip is the one safe way to do this rather than trying to manually delete files. With a current pip in place, install something real to confirm the whole chain works end to end:

requests pulled in four dependencies automatically, and pip freeze lists the exact versions now installed in weatherbot-env — precisely the file you’d save as requirements.txt to hand this environment to someone else. (The full pip user guide covers freeze, requirements.txt, and every other command in more depth than fits here.)

Gotchas Worth Knowing

The “python” command can silently open the Microsoft Store instead of running Python. Windows 10 and 11 ship a stub python.exe that, if you’ve never installed Python, launches the Store listing for it under something called an “app execution alias.” If you’ve genuinely installed Python and python still seems to do nothing useful, check Settings → Apps → Advanced app settings → App execution aliases and turn the Python entries off — a real install and an unrelated alias can otherwise both technically “work” on PATH at once.

pip and pip3 aren’t guaranteed to point at the interpreter you think. With more than one Python installed, pip, pip3, and python -m pip can each resolve to a different installation depending on install order and what modified PATH last. python -m pip is reliable because it removes the ambiguity — it always uses whichever python you just typed, never a separately-resolved pip.exe.

Corporate networks sometimes break pip with SSL errors, not missing-pip errors. If pip install fails with a certificate-verification message on a work laptop, that’s usually a proxy intercepting HTTPS traffic, not a broken pip. It’s a network-configuration problem your IT team needs to solve with the right CA certificate — --trusted-host flags are a workaround for testing, not a real fix, and shouldn’t become a permanent habit.

Once pip is confirmed working, checking it into the same virtual-environment discipline as everything else pays off quickly.
