How to Prevent Dropped Requests During Kubernetes Deploys

"Zero-downtime" isn't a property of Kubernetes rolling updates — it's a property of a Deployment that's actually configured for it. This post runs the same rollout twice against a live cluster, once without a readiness probe and once with one, and measures exactly how many requests each version drops.

Mehdi Lotfinejad
August 9, 2026 · 7 min read

A Deployment with 3 replicas and no other configuration is not zero-downtime by default — it just looks like it should be, because “3 replicas” sounds redundant enough to survive an update. Ship a new version to that Deployment and, without one specific field, some fraction of requests arriving during the rollout get a connection refused. This post doesn’t just assert that: it deploys a real app to a real Kubernetes cluster, hammers it with requests during a rolling update, and counts exactly how many fail — first without a readiness probe, then with one.

The short version, measured, not guessed: the same rolling update, same 3 replicas, same 500 requests fired during it — 113 failed (22.6%) without a readiness probe, 0 failed with one. One field in a YAML file is the entire difference. The rest of this post is what that field does and why its absence causes exactly this failure.

Kubernetes Doesn’t Know Your App Is Ready — Unless You Tell It

When a rolling update creates a new pod, Kubernetes has exactly one question to answer before sending that pod live traffic: is this pod ready? Without a readinessProbe, the answer defaults to “the container process has started” — which is a statement about the OS, not about your application. A container can be Running from Kubernetes’ point of view while your app is still importing modules, warming a cache, or opening a database connection, none of which involve serving a single request yet. The pod gets added to the Service’s list of endpoints the moment it’s Running, and kube-proxy starts routing real traffic to a process that isn’t listening yet.

A readinessProbe closes that gap: Kubernetes polls the pod on its own schedule (an HTTP request, a TCP connect, or a command) and only adds it to the Service’s endpoints once that probe actually succeeds. The pod can be fully Running and still correctly excluded from traffic for as long as it takes to become genuinely ready.

The Test: One App, Two Configurations, One Measurement

The app is a deliberately minimal Python HTTP server — no framework, just enough to control startup timing precisely — deployed with kubectl to a local kind (Kubernetes-in-Docker) cluster, kind v0.27.0 running Kubernetes v1.32.2:

START_DELAY=4 makes the app sleep for 4 seconds before it starts listening — a stand-in for the real warm-up work a production app does (loading a model, opening a connection pool, running migrations). No readiness probe is defined yet, on purpose.

A second pod inside the cluster generates the load — 500 requests, one every 20 milliseconds, logging a timestamp and HTTP status code (or 000 for a failed connection) for each one, hitting the Service by its in-cluster DNS name so the traffic pattern matches how a real caller would reach it:

With the naive Deployment applied and confirmed healthy, the load test starts, and 2 seconds in, a rolling update fires by bumping the VERSION environment variable — the same mechanism a real image-tag update would trigger:

Result: 113 Dropped Requests, No Readiness Probe

Pulling the logged results and counting:

113 of 500 requests — nearly a quarter of everything sent during the 13-second rollout window — came back with a failed connection, not an HTTP error page, a raw connection refusal. That matches the mental model exactly: kubectl created new pods (surged one at a time, by default), each was marked Running and added to the Service’s endpoints immediately, and each spent its first 4 seconds accepting TCP connections that nothing on the other end was listening for yet.

Same Rollout, One Field Added

The only change: a readinessProbe block on the same container, nothing else touched.

periodSeconds: 1 polls every second; failureThreshold: 1 means a single failed probe is enough to keep the pod out of rotation (the default is 3, which is usually the safer choice in production — this test tightens it only to make the probe’s effect on the timeline unambiguous). Re-running the identical experiment — same image, same START_DELAY=4, same 500-request load test, same rollout trigger:

Zero. The new pods still take exactly as long to warm up — nothing about the app changed — but Kubernetes now knows not to route traffic to them until they say so themselves. The 4-second startup delay didn’t disappear; it just stopped being visible to anyone calling the service, because traffic simply waits for a ready pod instead of hitting an unready one.

The Other Half: What a Readiness Probe Doesn’t Cover

A readiness probe only protects the incoming side of a rollout — new pods that aren’t ready yet. It says nothing about pods that are being removed. When Kubernetes terminates a pod, it does two things at roughly the same time: sends the container a SIGTERM, and removes the pod from the Service’s endpoints so no new traffic gets routed to it. Those two things propagate through the cluster independently, and on a real multi-node cluster, the endpoint-removal update can reach kube-proxy on some nodes slightly after the pod itself has already stopped accepting connections — a real, documented race, not a hypothetical one.

The standard fix is a preStop lifecycle hook that simply pauses before the container actually receives its SIGTERM:

This is worth being precise about, because it’s tempting to report a dropped-request number for this too: this post’s own test didn’t reproduce a measurable shutdown-side failure — re-running the same load test with preStop added but no readiness change still showed 0 failures, on this single-node local kind cluster where endpoint propagation is close to instantaneous. That’s a property of this specific test environment, not evidence the race doesn’t exist; on a real multi-node cluster with more network hops between the control plane and every node’s kube-proxy, that propagation delay is large enough to matter, which is why preStop: sleep remains standard advice from Kubernetes’ own documentation even though this particular local rig didn’t demonstrate it numerically. Add it anyway — it costs nothing but a few seconds of slower pod termination, and it’s cheap insurance against a race this test simply wasn’t positioned to trigger.

Two Settings, Two Different Failure Windows

Readiness probes fix “new pod, not ready yet.” Without one, Running is treated as Ready, and that gap is exactly as long as your app’s real startup time — the more your app does before it can serve a request, the bigger the window this bug opens.

preStop sleeps fix “old pod, still receiving traffic while shutting down.” It buys time for the “remove this pod from Service endpoints” message to actually reach every node before the pod stops answering.

Neither one is optional if a rollout needs to be genuinely invisible to callers — they cover opposite ends of the same rollout, not overlapping ground.
