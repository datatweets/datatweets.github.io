Direct vs Recursive XGBoost Forecasts: 14-Day MAE Results

A beginner-friendly comparison of direct and recursive multi-step XGBoost forecasting, using ten historical 14-day plans, legal lag features, a weekly baseline, and error measurements for every horizon.

Mehdi Lotfinejad
August 13, 2026 · 13 min read

A model that predicts tomorrow well may still make a weak two-week plan. The problem is not only model quality. It is also how the model creates days 2 through 14 when none of their actual values are known yet.

To forecast 14 days with XGBoost, either fit one direct model for each horizon or apply one one-day model recursively, feeding each prediction into later lag features. Backtest both strategies at repeated historical forecast starts, hide every actual value inside each 14-day block, and choose based on error by horizon as well as overall error.

This lesson compares those choices for daily repair-part requests at a fictional maintenance warehouse. The warehouse prepares one 14-day purchasing plan at a time, so the test must create all 14 predictions from the same known history.

Setup and prerequisites for the comparison

You need Python 3.11 or later and a way to run a Python file or notebook cell. You should know that a pandas DataFrame is a table with named columns. You do not need previous XGBoost or forecasting experience.

Download daily_repair_part_requests.csv and save it beside your Python file. It contains 560 consecutive daily counts from 1 January 2024 through 13 July 2025.

This is original synthetic data released under CC0-1.0. Synthetic means that code generated the rows. A fixed NumPy seed adds a gradual rise, a weekly pattern, a slow cycle, and related day-to-day changes. The warehouse and every request count are fictional; they do not describe a real organization.

The chart code saves an SVG file. Select Matplotlib’s headless Agg backend before importing pyplot, so the same script can run without a desktop display:

How multi-step XGBoost forecasting works

XGBoost is a supervised learning model: it learns a target from feature columns. It does not automatically know that row 100 occurs before row 101. We must convert the ordered series into examples that respect the forecast date.

A lag feature is an earlier value aligned with a target. If a plan begins on Monday, lag_7 is the request count from the previous Monday. A forecast horizon is the target’s distance from the start: Monday is horizon 1, while the second Sunday is horizon 14.

The two strategies use those ideas differently:

The direct route fits 14 separate models. Each one learns the relationship for one distance and predicts from the same observed history. The recursive route fits one model, but its later lag values may contain earlier predictions. This can carry an early error into later days.

Neither route is automatically better. Direct models have fewer training examples at long horizons and must estimate more model parameters in total. Recursive forecasting reuses more one-step examples, but its training rows contain real history while its later prediction rows contain model output. Only a backtest that matches the 14-day planning task can compare those tradeoffs.

If you need a slower introduction to forecast origins and recursive evaluation, read how to backtest multi-step time series forecasts. That lesson uses linear regression; this one focuses on the strategy choice with boosted trees.

If a real date is missing, do not insert zero without investigation. Zero requests is an observed count; a missing date says that the value is unknown. Reindex to a complete calendar, find the cause, and define a repair rule before creating row-based lags.

Build one feature snapshot without future values

At each forecast start, both methods receive four observed lags, two trailing means, the future target’s weekday, and its day number. The weekday and target date are known before a purchasing plan is made. The request count for that date is not.

Sine and cosine turn weekdays into two circular numeric features. Sunday and Monday are close on a weekly cycle even though their integer labels, 6 and 0, look far apart. These columns describe timing, not future demand.

The day-14 model has 13 fewer examples because the last 13 possible origins do not yet have an observed day-14 target. Including those unknown targets would be leakage, meaning that future information entered model fitting.

Implement direct and recursive XGBoost forecasts

Use one factory function so every fitted model has the same settings. The current XGBoost Python API defines XGBRegressor as its scikit-learn regression interface. The XGBoost parameter guide describes hist as a faster histogram-based approximate tree method.

The fixed seed and one worker make this teaching run reproducible. These settings were not tuned on the final backtest period:

The recursive function trains one horizon-1 model. After each prediction, it appends that value to the working history. Later moving averages and lags can therefore contain predictions, exactly as they would in a real fixed 14-day plan:

The direct function fits a separate model for each horizon. All 14 prediction rows use the same observed history, while the target date and the alignment of the training targets change with the horizon:

At horizon 1, the two methods use the same training table and feature row, so their predictions are equal. From horizon 2 onward, their information paths differ.

Compare overall error with horizon behavior

Mean absolute error (MAE) is the average absolute distance between actual and predicted values. It remains in part-request units, and lower is better. Calculate it for each horizon before reducing all 140 targets to one score:

The complete executed horizon table is available as xgboost_horizon_mae.csv. Its main results are:

Direct XGBoost has the lowest overall MAE, improving on recursive XGBoost by only 0.19 requests and on the weekly baseline by 1.87 requests. Yet recursive XGBoost has lower MAE on eight individual horizons. Direct has lower MAE on five, and horizon 1 is tied because both methods make the same calculation there.

This is not a contradiction. Some horizon differences are larger than others, so winning more horizons does not guarantee the lowest average across all targets. If all 14 days have equal planning cost, the overall MAE slightly favors direct forecasting in this test. If day 10 matters most, recursive is better there: its MAE is 7.07 requests compared with 8.44 for direct.

Read the lower-left panel first. It shows that the strategies exchange the lead as the horizon changes. Then use the upper panel to see whether large misses cluster in one 14-day block. The overall bars are the final summary, not the whole decision.

These results belong to one generated series and ten forecast starts. They do not prove that direct forecasting is generally more accurate. A real choice should include more historical origins, relevant operating periods, and a metric that reflects the cost of errors on each horizon.

Common mistakes that silently change the experiment

Using actual values inside the forecast block. If Monday’s actual count enters Tuesday’s recursive feature row, you have tested repeated one-day updates, not one fixed 14-day plan. Append the Monday prediction instead.

Training a day-14 model on targets after the origin. For horizon h, the last training target must be before the current forecast start. The end_position - horizon boundary in make_training_table() enforces this rule.

Shuffling the rows. A random split allows later behavior to influence models scored on earlier dates. Scikit-learn’s official lagged-feature forecasting example shows that shuffled evaluation can produce an overly optimistic result. Keep forecast starts ordered through time.

Giving the strategies different features. A comparison is difficult to interpret if direct models receive calendar features while the recursive model does not. Keep the available information equal unless the experiment is explicitly testing feature sets too.

Ignoring the weekly baseline. An 8.52-request MAE has little meaning by itself. The 10.39-request baseline shows that both XGBoost strategies add value for this fictional series, while also showing the size of that gain.

Choosing from overall MAE when one horizon drives the decision. A two-week purchasing plan may have expensive shortages in the first three days and more flexibility later. Define horizon weights or report a business-specific cost before selecting the model.

Treating direct forecasting as one model. This implementation fits 14 models. Save and label them by horizon so day-3 and day-13 estimators cannot be exchanged during prediction.

Assuming a stable weekly pattern. Supplier changes, maintenance schedules, reporting gaps, and new ordering rules can change demand. Track errors by forecast start and horizon, then define when the models will be reviewed.

Recap: what to carry into your own forecast

Multi-step XGBoost forecasting starts with an information boundary, not with a model setting. Write down when the full plan is created, which future facts are already known, and when actual target values become available.

Then keep the comparison controlled:

  1. Verify an ordered, complete time index.
  2. Build lag and calendar features from information available at each origin.
  3. Train one model per horizon for the direct route.
  4. Feed predictions, not hidden actuals, into the recursive route.
  5. Repeat complete forecast blocks at several historical starts.
  6. Compare both strategies with a simple baseline on identical targets.
  7. Read error by horizon before using an overall average.

In this backtest, direct XGBoost reaches the best overall MAE at 8.52 requests, while recursive XGBoost wins more individual horizons. The durable lesson is therefore not “always choose direct.” It is to choose the strategy from the evidence that matches the real planning decision, then keep measuring the same evidence as new actual values arrive.
