How to Version FastAPI ML Endpoints Without Breaking Clients

Keep an existing FastAPI prediction response stable while adding a richer v2 route. Train one model on original synthetic data, reuse one inference function, inspect both generated OpenAPI contracts, and detect a deliberate breaking field rename before release.

Mehdi Lotfinejad
August 14, 2026 · 10 min read

An existing client can fail with KeyError: 'needs_review' after a server renames one JSON field. The model may still make the same prediction, but the API contract has changed beneath code that depends on it.

To version a FastAPI machine learning endpoint safely, leave the existing path and response model unchanged, add a new APIRouter under a versioned prefix such as /v2, and make both versions call one shared prediction function. Test each JSON response and compare the generated OpenAPI schema with the required fields and types that existing clients expect.

This tutorial applies that pattern to a fictional repair-queue classifier. You will keep a small /v1 response stable, add probability details under /v2, and prove that a field rename is caught before release.

Understanding How Stable and New API Versions Work Together

An API contract states the request and response fields, their types, and their meaning. OpenAPI is a machine-readable description of that contract. FastAPI generates it from route declarations and Pydantic models.

Our application has one prediction core but two public response views:

Version 1 does not change. A client that knows only ticket_id, needs_review, and model_version keeps receiving those exact fields. Version 2 adds a score, the threshold used for the decision, and a contract label.

This is path versioning: the version appears in /v1 or /v2. It does not mean that every internal code change needs a new version. Add a public version when a necessary contract change would break existing clients, then keep both routes during a documented migration period.

FastAPI’s current router guide shows that APIRouter accepts a shared path prefix and can be included in one application. Its response-model guide explains that a response model validates, documents, serializes, and filters returned data. Those two features form the boundary used here.

This compact checker covers removed required fields and primitive type changes. A production contract tool may also need to inspect nested objects, arrays, enums, optional fields, status codes, content types, request schemas, and semantic changes that OpenAPI cannot express.

Common Mistakes and Troubleshooting

Replacing v1 with v2 at the same path. A new response model does not protect an existing client when the route stays /v1/delay-risk. Keep v1 unchanged and expose the incompatible contract at /v2/delay-risk.

Copying prediction code into each router. Two implementations can select different features, thresholds, or model versions later. Put inference in one function and keep the endpoint wrappers small.

Changing a field’s meaning without changing its name. A schema test sees names and types, not meaning. If needs_review changes from “score at least 0.50” to a different rule, document and test that behavior. Create a new contract when clients cannot safely treat the meanings as equivalent.

Assuming an added response field is always safe. Some clients ignore unknown response fields, while strict decoders reject them. Publishing additions under v2 avoids guessing how every existing client parses JSON.

Testing only one example response. One request cannot prove the generated documentation remains correct. Test both runtime JSON and OpenAPI. Add boundary requests around the threshold if that decision is part of the client contract.

Confusing API version with model version. /v2 describes the HTTP contract. repair-delay-logreg-2026-08-14 identifies the fitted artifact. A new model can often serve the same API contract, while one API version may support several approved model releases.

Removing v1 without a migration plan. Record who uses v1, publish the v2 difference, observe migration, announce a retirement date, and remove v1 only after the agreed support period. This tutorial does not choose that period because it depends on your clients and service policy.

Trusting schema checks as proof of model quality. Contract tests do not measure drift, fairness, calibration, security, latency, or business value. Evaluate those concerns separately with representative data and explicit rules.

Recap: Keep the Old Promise While Adding the New One

API versioning separates two responsibilities. Shared prediction code keeps model behavior aligned. Separate response models let each public path keep its own promise to clients.

The executed lesson trained one synthetic classifier, served it through /v1/delay-risk and /v2/delay-risk, and passed seven runtime, OpenAPI, and compatibility checks. V1 kept its three original fields. V2 added a score, threshold, and contract label, while both paths returned the same Boolean decision.

Carry forward the smallest durable rule: never make an existing client discover a breaking contract change at runtime. Preserve the old route, add the new route deliberately, compare generated schemas in automated tests, and retire older versions through a visible migration process.
