Python Developer Tools: What You Actually Need and Why

Environment tools, formatters, linters, type checkers, test runners — the Python tooling landscape is crowded and everyone recommends something different. This post narrows it to five jobs that actually matter, then verifies black, ruff, mypy, and pytest against one small, deliberately rough running example.

Mehdi Lotfinejad
August 8, 2026 · 12 min read

“pip install this” shows up in nearly every Python setup guide, and it’s rarely the last thing you have to install. Search “python tools” and you land on black vs. ruff vs. flake8, venv vs. virtualenv vs. Poetry vs. uv, and a pre-commit config with six hooks nobody explains. None of the individual advice is wrong — it’s just presented as one long, undifferentiated list, so it reads like all of it is equally urgent to learn on day one. It isn’t.

Almost everything in that list exists to do one of five jobs, and once you can name the job, choosing a tool for it stops being a research project. This post runs black, ruff, mypy, and pytest against one small, deliberately rough Python file, so you can see exactly what each one changes instead of taking “you should use this” on faith. If you haven’t set up an isolated Python environment before, our guide to Python virtual environments covers that specific piece in more depth than this post will — here it’s just the first of five jobs.

Five jobs cover nearly all of it: isolating a project’s dependencies from every other project on the machine (venv, or uv), installing packages into that isolated environment (pip, or uv again), enforcing one consistent code style so people stop arguing about it in review (black), catching real bugs and dead code before anything runs (ruff), and proving the code still works after you change it (pytest). Pick one tool per job, point the editor’s save action at the formatter and linter, and that’s a complete, defensible setup — type checking and everything past it is a refinement you add once this baseline is running, not a prerequisite to get there.

Five Jobs, Five Tools

The reason “which Python tools do I need” produces such a long, contradictory-sounding list is that most answers mix two different questions: which job needs doing and which specific tool does that job today. The first list is short and stable — it barely changes year to year. The second list is the one that generates blog-post debates, because two or three tools often compete for the same job and the winner shifts every couple of years (flake8 was the default linter before ruff mostly replaced it; virtualenv did what venv now does in the standard library).

Two of the five jobs are increasingly handled by a single binary: uv can isolate an environment and install into it, and ruff can lint and — more recently — format. That consolidation is part of why the landscape looks noisier than it is: the tools merged, but the jobs underneath them didn’t change at all. The Python Packaging User Guide’s tutorial on installing packages is the official reference for jobs one and two, if you want more detail than this post covers.

Catching Bugs Before They Run: mypy

Formatting and linting both work on the code as written. mypy works on the code as typed — it reads the type hints on a function signature and checks whether every call site actually respects them, without running anything:

That’s a real bug — passing a string where the function expects a list of dicts would raise a TypeError deep inside the loop the moment it actually ran, on whatever input happened to trigger it. mypy finds it by reading the signature, before a single line executes. Type hints are the one piece of this post genuinely optional in a way the other four jobs aren’t — plenty of real, well-run Python codebases skip them entirely, and retrofitting mypy onto an existing untyped project is a bigger undertaking than turning on a formatter. It earns its place here because the failure mode it catches — a caller passing the wrong shape of data — is common and otherwise invisible until it crashes at runtime, sometimes far from where the actual mistake was made.

mypy’s loudest complaints on a real project are often not about your code at all, but about missing type information for a third-party import:

That specific error is about an import that genuinely doesn’t exist, but the same message shows up for real, installed packages that simply haven’t published type information anywhere mypy can find. A types-<package-name> stub package usually fixes it properly; a targeted # type: ignore[import-untyped] comment is the honest fallback when no stub package exists yet. Neither means your own code is wrong.

Making the Tools Run Automatically, Not by Memory

None of this is worth much if it only runs when you remember to type the command. Every mainstream editor can run the formatter and linter the moment you hit save. In VS Code, that’s a few lines in settings.json (Command Palette → “Preferences: Open User Settings (JSON)”):

formatOnSave runs black on every save; codeActionsOnSave tells VS Code to apply ruff’s auto-fixable checks — not the ones that need a human judgment call, those still show up as warnings — at the same moment. Beyond installing the Python and Ruff extensions, that’s the entire setup. Our guide to setting up VS Code covers the rest of a Python-ready install if you’re starting from a blank editor.

Where a Working Setup Still Trips People Up

black and ruff can disagree about line length if you never tell them to agree. Each tool defaults to 88 characters independently, so leaving both on defaults usually causes no conflict — but the moment either config gets customized alone, they can start fighting over where to wrap a line, each one “fixing” what the other just did. Give both the same number in one file and the disagreement disappears:

A clean mypy run doesn’t mean the code is bug-free, and a noisy one doesn’t always mean your code is wrong — see the missing-stub message above. Treat import-not-found and import-untyped errors as a prompt to check for a stub package first, not as a verdict on your own logic.

Auto-fix only fixes what’s provably safe. ruff check --fix (and codeActionsOnSave) will remove an unused import without asking, because doing so can never change behavior. It won’t silently “fix” a suspicious comparison or an unreachable branch, because those fixes require understanding intent — those still show up as errors you have to read and resolve yourself. Auto-fix narrows the list of things you have to look at; it doesn’t replace looking.

None of the five tools above is complicated once you’ve run each by hand a couple of times — the actual complexity was never in black or pytest themselves, it was in not knowing which of the dozen recommended tools in a random thread actually mattered for you today. Add mypy to a real project once the baseline above feels automatic, and treat uv or Poetry as a single upgrade to jobs one and two rather than a separate ecosystem to learn on top of everything else here.
