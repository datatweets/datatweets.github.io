Reduce Outlier Impact with XGBoost Pseudo-Huber Loss in Python

A beginner-friendly comparison of squared and Pseudo-Huber objectives on synthetic warehouse timing data, with audited validation, a locked test, and practical guidance for tuning the robust-loss slope.

Mehdi Lotfinejad
August 14, 2026 · 11 min read

One broken timestamp can produce a residual much larger than dozens of ordinary misses. With squared-error training, a few such target errors can pull an XGBoost model away from the pattern that most rows follow.

To reduce the influence of large target residuals, use objective="reg:pseudohubererror", set a sensible base_score, and choose huber_slope on trusted validation data. Compare it with reg:squarederror on the same split and tree settings, then use the test set once to check both typical and large errors.

This tutorial follows that process with fictional warehouse pick times. The training logs contain a small number of unmarked recording errors, while the validation and test targets were created as audited values. You will see an improvement in this controlled example, but also where robust loss can hide a real operational event instead of helping.

Understanding how Pseudo-Huber changes the fit

A regression model predicts a number. Here, that number is the time needed to pick one warehouse order. During training, XGBoost evaluates the difference between an observed target and its prediction. That difference is a residual:

An objective tells the training algorithm which quantity to reduce. With squared error, the penalty grows with the square of the residual. A residual of 50 therefore receives 100 times the penalty of a residual of 5.

A target value far from the main pattern is often called an outlier. An outlier is not automatically an error: it may be a valid rare event, a measurement problem, or a value the current model explains poorly.

Pseudo-Huber loss is smooth and behaves differently at two scales. Near zero, it resembles squared loss, so the model still pays close attention to ordinary errors. Far from zero, its growth becomes closer to a straight line, so one extreme residual has less influence.

The next small calculation makes the difference visible. It compares half squared loss with Pseudo-Huber loss at delta = 5:

At a residual of 2, the two penalties are similar. At 50, the squared penalty is 1250.00, while the Pseudo-Huber penalty is 226.25. The large error still matters; it no longer dominates as strongly.

In XGBoost, huber_slope supplies delta. A smaller slope starts reducing the influence of residuals sooner. A larger slope behaves like squared loss across a wider range. The current XGBoost parameter reference describes reg:pseudohubererror as a twice-differentiable alternative to absolute loss and lists 1.0 as the default slope. That default is a candidate, not a value to accept without validation.

Setup and the audited warehouse data

You need Python 3.11 or later and a terminal, notebook, or editor that can run Python. You should know that a pandas DataFrame is a table with named columns. No previous knowledge of robust statistics is required.

Create a virtual environment and install the packages used by the executed lesson. On macOS or Linux, run:

On Windows PowerShell, activate with .venv\Scripts\Activate.ps1. The outputs in this tutorial were executed with Python 3.13.2, NumPy 2.5.1, pandas 3.0.3, scikit-learn 1.9.0, XGBoost 3.3.0, and Matplotlib 3.11.0.

Download warehouse_pick_times.csv. This original synthetic DataTweets dataset is released under CC0-1.0. Its 2,400 orders, conditions, and durations are fictional and do not measure a real warehouse.

The generator added recording errors to 90 of the 1,500 routine training targets. Those individual rows are deliberately not marked, while the validation and test targets are audited. This design lets us test a robust training objective against trusted outcomes, but the measured advantage is constructed teaching evidence rather than a real benchmark.

Load the CSV and inspect only six rows first. A small view makes the split, units, and target easy to check:

Each row is one completed pick. The five numeric features describe the workload and operating conditions. The target, pick_minutes, is the recorded duration that the model learns to predict. order_id, data_split, and review_status document the row; they are not model inputs.

Check the row counts and target range before fitting. The validation and test sets should be audited, and the routine training log should contain the unusually large maximum:

The three median values are close to 30 minutes. The training maximum is 139.34, much larger than either audited maximum. A large value is not proof of an error in real data. Here, we know the data-generating process because the dataset is synthetic.

Keep validation and testing separate

The predefined split gives each part one job. Training rows fit the trees. Validation rows choose the slope. Test rows measure the completed choice once.

Name the features explicitly, then select the three parts. Explicit names prevent identifiers, review notes, and the target from entering the model by mistake:

The audited test rows must remain closed while choosing huber_slope. If you try several slopes on test data and keep the best one, the test result becomes part of model development.

Hold the trees steady and vary the objective

A fair comparison changes the objective while keeping the tree settings fixed. The next factory creates either a squared-error model or a Pseudo-Huber model:

base_score is XGBoost’s starting prediction, also called its intercept. We set it to the training-target median so every candidate starts from the same central value. XGBoost can estimate this value automatically for selected objectives, but its intercept guide also documents setting a constant explicitly.

The remaining values are fixed settings for this example, not general recommendations. tree_method="hist" uses histogram-based tree construction. n_jobs=1 makes the local execution easier to reproduce.

Select the slope with trusted targets

We will compare slopes 1, 5, and 20. The selection metric is mean absolute error, or MAE, which averages the absolute prediction errors in minutes. Median absolute error describes a typical row, while the 90th-percentile absolute error shows a larger miss: 90% of absolute errors are at or below it.

The helper below returns all three values. Keeping them together prevents one attractive average from hiding the upper part of the error distribution:

Fit the squared-error reference once, then fit one Pseudo-Huber model per slope. Only validation MAE chooses the robust candidate:

All three robust candidates have lower validation MAE than squared error in this constructed experiment. Slope 1 has the lowest value, so it becomes the locked choice. The worsening result as the slope rises also fits the intuition: the objective behaves like squared loss across more of the residual range and gives the corrupted targets more influence.

Do not infer that slope 1 is universally best. The slope is measured in the target’s units. A useful value for minutes may not be useful after converting the target to seconds, and a different noise pattern can change the preferred slope.

Open the audited test set once

Now compare three finished methods: a median baseline, squared-error XGBoost, and the selected Pseudo-Huber model. A baseline is a simple reference rule. DummyRegressor(strategy="median") ignores the features and always predicts the training-target median.

Add root mean squared error, or RMSE, to the final comparison. RMSE gives extra weight to larger misses, so it complements MAE and the error percentiles:

Both XGBoost models beat the median rule, so the features contain useful signal. The selected robust model lowers test MAE from 4.08 to 1.92 minutes and the 90th-percentile absolute error from 9.01 to 4.05 minutes. RMSE also falls, even though RMSE emphasizes large errors.

These numbers support one narrow conclusion: for a model trained on this deliberately contaminated log, Pseudo-Huber loss transferred better to audited rows. They do not prove that Pseudo-Huber will beat squared error on clean training data or on valid extreme events.

The generated chart keeps the selection evidence and final evidence separate:

Read the left panel first: it records why slope 1 was selected without using test results. Then read the right panel: every displayed test error is lower for the chosen robust model. The chart is a result of the executed comparison, not a drawing of the expected outcome.

Inspect a few individual predictions last. Individual rows can make an aggregate metric easier to understand and can expose failure patterns worth investigating:

For PICK-1955, squared-error XGBoost predicts 40.41 minutes for an actual duration of 25.76. The robust model predicts 31.70. Five rows are not enough to judge a model, but they make the aggregate errors easier to understand. The complete executed predictions are available in robust_regression_test_predictions.csv.

Common mistakes and what can go wrong

Treating robust loss as data cleaning. Pseudo-Huber loss changes how residuals affect training. It does not identify the wrong timestamp, recover the correct value, or explain why the record failed. Fix known errors at their source and keep data-quality checks.

Assuming every extreme target is wrong. A 140-minute pick may be a valid shutdown or safety event. Reducing its influence could make the model worse for the cases that matter most. Review extreme rows with subject knowledge and report errors for important groups.

Confusing target errors with unusual features. Pseudo-Huber acts on residuals between targets and predictions. It is not a general repair for a strange aisle_distance_m value or a missing feature. Validate input columns separately.

Using the final test to choose the slope. Choose huber_slope, tree depth, and other settings with training and validation data. Keep a final test outside that loop. For a fuller evaluation pattern, see Measure XGBoost Regression Error with Repeated Cross-Validation.

Copying a slope after changing units. A residual of 1 means one minute here. If the target becomes seconds, the same numeric slope represents only one second. Rebuild the validation search after a unit change.

Reading the objective’s metric as the business goal. XGBoost uses mean Pseudo-Huber error as the default evaluation metric for this objective. You can still select a model with MAE, RMSE, or another metric that matches the real decision. State which metric chose the model.

Expecting identical results after changing the starting value. base_score is the global starting prediction. This lesson fixes it to the training median for a controlled comparison. If results differ, check the dataset, XGBoost version, seed, feature order, model settings, and base_score before changing the slope.

Recap: use robust loss as a tested hypothesis

Squared error gives large residuals rapidly increasing influence. Pseudo-Huber loss stays smooth but reduces that growth after a scale controlled by huber_slope. That makes it a reasonable candidate when training targets may contain errors that cannot all be identified.

The safe workflow is more important than the objective name: preserve trusted validation and test targets, keep model settings fixed, choose the slope on validation evidence, and examine several error summaries on the locked test. In this synthetic example, slope 1 reduced audited test MAE from 4.08 to 1.92 minutes compared with squared error.

Carry the limitation with the result. Robust loss can protect a common pattern from corrupted labels, but it can also discount valid rare events. Treat it as a hypothesis to test against reliable outcomes, not as permission to stop investigating the data.
