How to Choose a Time Series Training Window with Python

A beginner-friendly comparison of fixed and expanding training histories for one-day-ahead forecasts, using ordered validation, an untouched test period, and a weekly baseline.

Mehdi Lotfinejad
August 14, 2026 · 12 min read

Keeping every old observation can feel safer than discarding data. That choice becomes risky after opening hours, customer behavior, equipment, or reporting rules change. An older pattern can give a forecasting model more rows but less relevant evidence.

To choose a time series training window, define several history lengths and score each one on the same ordered validation dates. At every date, fit only on earlier rows, make the forecast, and select the window with the lowest validation error. Keep a later test period untouched until that choice is fixed, then compare it with an expanding window and a simple baseline.

This tutorial applies that method to fictional daily admissions at a science center. Its operating schedule changes partway through the series. We will hold the model and features constant, so any difference in error comes from the amount of training history retained.

Setup, dataset, and forecast question

You need Python 3.11 or later and a way to run a Python file or notebook cell. You should know how to call a function and select rows with pandas. You do not need previous forecasting or machine-learning experience.

Create a virtual environment, activate it, and install the packages used in the executed lesson:

On Windows PowerShell, activate the environment with .venv\Scripts\Activate.ps1. The results below were generated with Python 3.13.2, NumPy 2.5.1, pandas 3.0.3, scikit-learn 1.9.0, and Matplotlib 3.11.0.

Download these files into your working folder:

  • science_center_admissions.csv, the input series
  • training_window_validation_scores.csv, the executed window comparison
  • training_window_test_predictions.csv, the row-level final evidence

The input has 448 consecutive daily counts from 1 January 2024 through 23 March 2025. It is original synthetic data, which means code generated it. The science center and admissions are fictional, and the dataset is released under CC0-1.0. A fixed NumPy seed of 20260814 makes the build repeatable.

The generator adds a weekly pattern, a slow six-week cycle, and random changes that partly carry into the following days. It also adds a fictional schedule change on 2 September 2024. Before that date, weekends tend to be quieter. After it, weekend admissions rise. This constructed change gives us a clear reason to ask whether old rows still help.

Our forecast task is one day ahead. After each day’s actual count arrives, the model retrains and predicts the following day. A seven-day plan made all at once needs a different backtest; see How to Backtest Multi-Step Time Series Forecasts in Python for that information boundary.

How a training window works with lag features

A training window is the set of past target rows used to estimate a model. Two common choices are:

  • A fixed-length window, also called a sliding or rolling window, keeps only a set number of recent rows. A 56-day window drops the oldest row when a new actual value arrives.
  • An expanding window begins at a fixed start date and keeps growing. It never discards an earlier training row.

A lag has a different job. It is an earlier value used as an input for one row. Our lag_1 feature is yesterday’s admissions, even when the model is fitted on 56 training rows. The window controls how many examples the model learns from; the lag controls what information describes each example.

The 112-day, 224-day, and expanding histories include rows from before the schedule change. That may hurt adaptation. The 28-day history is current, but it may provide too few examples to estimate stable coefficients. Backtesting measures this recency-versus-sample-size tradeoff instead of deciding it by intuition.

Scikit-learn’s current TimeSeriesSplit documentation provides max_train_size for limiting a training fold. We will use an explicit loop because it makes each one-day forecast and exact training boundary easy to inspect.

Read the input, parse its dates, sort it, and set an explicit daily frequency. A row-based lag means “one day ago” only when there are no missing or duplicate dates.

Do not fill a missing date with zero without investigating it. Zero admissions is a measured count; a missing row says no count is available. Reindex first to reveal gaps, then use a repair rule that fits the real data source.

Build inputs that exist before every target

The model uses three types of input:

  • yesterday’s count, lag_1;
  • the mean of the previous seven known counts, recent_mean_7;
  • six indicator columns for Tuesday through Sunday, with Monday as the reference day.

An indicator column contains 1 when a category applies and 0 otherwise. The current pandas get_dummies() reference calls these dummy or indicator variables. We declare all seven weekday categories before encoding, which keeps the same columns even if a short slice does not contain every day.

Create lagged features before selecting training windows. Both numeric inputs use shift(1), so today’s target never enters its own feature row:

Read the first row from left to right. The target on 8 January is 117. Its lag_1 is the known 7 January count of 68, while recent_mean_7 averages 1–7 January. All weekday indicators are zero because 8 January is a Monday, the reference category.

We use ordinary LinearRegression, which estimates coefficients that minimize squared training errors. It is deliberately simple. A more complex model would make it harder to tell whether performance changed because of history length or model behavior.

Refit one window at every validation date

At each target date, combine earlier features with earlier targets and remove the first seven incomplete rows. For a fixed window, tail(window) keeps only the most recent complete training rows. Passing None leaves the history expanding.

The slice features.iloc[:target_position] ends before the target. The single prediction row is allowed to contain calendar indicators plus lagged values derived from earlier dates. After the actual target arrives, the next loop iteration can use it.

Now compare 28, 56, 112, and 224 days with an expanding history. Every candidate receives the same 56 validation targets:

Mean absolute error (MAE) is the average absolute distance between actual and forecast values. It has the same unit as the target—admissions in this example. Zero is best, and lower is better. This matches the current scikit-learn mean_absolute_error() documentation.

The executed comparison is:

The 56-day window has the lowest validation MAE at 3.74 admissions. The 112-day result is close at 3.86, so a different validation period could reverse their order. In this comparison, 28 days does not provide enough useful history, while the longer windows retain more evidence from the earlier schedule. The error scores show the effect; they do not identify a single cause.

This result selects 56 days for this dataset and forecast policy. It does not establish 56 days as a standard forecasting window.

Freeze the choice and inspect later evidence

Do not compare all five candidates again on the final test and pick a new winner. That would turn the test into another tuning period. Keep 56 days fixed, then compare it with two reference methods:

  • the expanding version of the same regression;
  • a seasonal-naive baseline that predicts the value from seven days earlier.

Run all three on the 56 untouched dates from 27 January through 23 March 2025. By then, the validation-period actuals are known, so they may become training history. Using them does not change the window choice or expose a test target:

On the first date, the same-weekday baseline is closest: it predicts 147 when the actual count is 146. The 56-day model wins across the full period, however, missing by 3.93 admissions per forecast on average. Its error is lower than both reference methods on these synthetic test dates.

The chart does not prove why one candidate wins. It supports a narrower conclusion: under the generated change, fixed model, chosen features, and one-day update schedule, 56 recent rows forecast these validation and test periods better than the alternatives shown.

Common mistakes that make the comparison misleading

Confusing the training window with a lag length. A 56-day training window does not automatically create 56 lag features. State separately how many rows fit the model and which past values enter each feature row.

Letting the target enter its own rolling mean. series.rolling(7).mean() includes the current value. Use series.shift(1).rolling(7).mean() so each row contains only values available before its target.

Using a shuffled split. Random splitting lets later behavior help a model evaluated on earlier dates. Preserve order and forecast forward from every cutoff.

Scoring candidates on different targets. A short window may become available earlier than a long window. Begin validation only when every candidate can fit, then compare identical dates and metrics.

Choosing on the final test. The validation period chooses the window. The final period checks that frozen decision once. If you change candidates after seeing test error, reserve a new untouched period.

Keeping old rows just because they exist. More rows reduce some forms of estimation noise, but they can add stale behavior after a real process change. Check whether policies, definitions, sensors, opening hours, or users changed.

Discarding history without enough evidence. A very short window can miss rare weekdays, seasonal cycles, or unusual operating conditions. Make the shortest candidate large enough to estimate every feature and cover the patterns relevant to the forecast.

Treating a synthetic change as a universal benchmark. These admissions were constructed to make adaptation visible. Use your own ordered validation periods, including quiet and busy conditions, before setting a production window.

Forgetting the retraining policy. This code refits after every daily actual arrives. Weekly or monthly retraining creates different training sets and may select a different window.

Leaving the window fixed forever. A selected window is part of the model configuration. Monitor recent errors, keep row-level predictions, and repeat the comparison when the process or update schedule changes.

Summary: carry this workflow to your own series

A training window controls which historical examples are allowed to shape today’s model. An expanding window favors sample size. A fixed window favors recency. Neither is automatically correct; the right comparison recreates the timing of the real forecast.

For the fictional admissions series, 56 days produced validation MAE of 3.74. After that choice was frozen, it reached 3.93 MAE on 56 later targets, compared with 5.89 for expanding history and 5.55 for the weekly baseline. Those values belong to this constructed dataset.

The reusable sequence is: define the update schedule, build target-safe features, compare several justified windows on identical future-like dates, keep one final period untouched, and retain a simple baseline. Save every target date, training boundary, actual value, and prediction. That evidence makes the next window review a measured decision instead of a guess.
