Python Web Development: Your First API in Flask and FastAPI

What does 'Python for web development' actually mean once you sit down to write code? This post builds a small JSON API twice — once in Flask, once in FastAPI — then times a real sync-vs-async comparison and wires the same process up to a database, so you can see exactly what each layer is doing.

Mehdi Lotfinejad
August 8, 2026 · 9 min read

“Is Python good for web development?” is a strange question to answer in the abstract, because the honest answer depends on what “web development” means to the person asking. If you’ve only ever seen Python used for scripts and data analysis, the idea that the same language answers HTTP requests for real products can feel like a separate skill you’d have to start over to learn. It isn’t — it’s a handful of new vocabulary (routes, requests, responses) sitting on top of functions and dictionaries you already know how to write. If you’ve mostly used Python to call APIs rather than build them, our post on making GET requests with the requests library covers the client side of this same conversation; this post is about the server answering those requests.

Here’s what that looks like in practice: you write a Python function, attach it to a URL path with a decorator, and a framework — Flask or FastAPI, most commonly — turns incoming HTTP requests into calls to that function and turns whatever it returns into an HTTP response. Flask keeps that mapping close to bare Python: you get a dictionary back, it becomes JSON. FastAPI adds one more piece — you describe the shape of the data with a class, and it validates every request against that shape before your function ever runs, rejecting anything malformed automatically. Both talk to the same databases, run on the same servers, and can sit right next to the pandas or scikit-learn code you already know.

Three Layers Between a Request and Your Code

Every Python web app, no matter which framework it uses, is the same three-layer stack:

  1. A server that speaks HTTP. Something has to accept a raw TCP connection, parse the request line and headers, and know when the request body ends. In production this is usually gunicorn or uvicorn, not the dev server the framework ships with.
  2. A gateway interface that hands requests to Python. The server doesn’t call your functions directly — it calls a small, standardized interface. WSGI (Web Server Gateway Interface) is the synchronous version Flask uses; ASGI is its async successor, which FastAPI is built on. This layer is the reason a Flask app and a FastAPI app can both run under gunicorn with the right worker class, despite being written so differently.
  3. Your application code. Routing, validation, business logic, and whatever you do with a database — everything covered in the rest of this post.

Framework choice mostly changes layer three. Layers one and two are close to fixed — which is why a Flask tutorial from 2015 and a FastAPI tutorial from this year both start with “define a route” instead of anything about sockets.

Nothing here validated the shape of anything, though — a POST with {"title": 12345} would sail straight through. That’s the gap FastAPI closes.

Where does that leave Django, the framework most beginners hear about first? Django solves a bigger problem than either example above: a full site with an ORM, an admin interface, authentication, and templating baked in, generated by django-admin startproject. That’s real value for a multi-page application with a database-backed admin panel — but it’s also a lot of scaffolding for “return some JSON,” which is why this post’s hands-on examples stick to the two smaller tools. If your project is a public-facing site with user accounts and a content-heavy backend, Django’s batteries-included approach is worth the extra setup; if it’s an API serving a separate frontend or another program, Flask or FastAPI gets you there with far less ceremony.

WSGI, ASGI, and What Async Actually Buys You

FastAPI’s “async” reputation comes from layer two of the stack above: it runs on ASGI, which lets a single worker hold many requests open at once instead of blocking on each one in turn. The WSGI specification, PEP 3333, defines the older synchronous interface Flask uses by default — one request fully finishes before that worker picks up the next. That difference only matters when a request spends time waiting — on a database, another API, a file — rather than computing. A quick, honest measurement: three simulated 0.3-second waits, run one after another versus run concurrently with asyncio.gather:

Three 0.3-second waits run one after another cost 0.9 seconds; run concurrently, they cost roughly the time of the slowest single one — 0.3 seconds — because the event loop switches to task B the instant task A hits await instead of sitting idle. That’s the entire pitch for async in a web server: while one request waits on the database, the same worker can start handling the next one.

It only works, though, if every wait actually says await. Swap asyncio.sleep for a plain, blocking time.sleep inside an async def — the mistake of calling a synchronous database driver or requests.get() without an async-aware alternative — and the concurrency disappears completely:

Same three tasks, same gather, but back to 0.91 seconds — indistinguishable from running them one at a time. A blocking call inside async def doesn’t just fail to benefit from concurrency; it stalls the entire event loop, so every other request that worker is holding waits behind it too. This is the single most common way people accidentally turn a FastAPI app back into a slow, one-request-at-a-time Flask app without realizing it.

The Same Interpreter Talks to Your Database, Too

This is the part of “Python as a web language” that’s easy to undersell: the process serving your HTTP routes can run the exact same database code you’d write in a data-analysis script, with nothing lost in translation. A small SQLite table, queried directly and then exposed through a route:

long_books runs a plain SQL query — nothing framework-specific about it — and the route just shapes the result into JSON. (check_same_thread=False is needed here only because FastAPI’s sync routes run in a worker thread; a real app typically uses a connection pool or an async driver instead, but the query itself doesn’t change.) Swap sqlite3 for pandas.read_sql, and the analysis you already know how to write becomes an API response with one extra function.

That’s really the case for Python here, more than any single framework: the same language reads the CSV, trains the model, and serves the result over HTTP, so nothing has to be rewritten or handed off at the boundary. Each project still needs its own isolated set of dependencies, though — Flask, FastAPI, and whatever database driver you pick shouldn’t all live in one global Python install, and our guide to Python virtual environments covers setting that up before you start.

Start small: one route, one framework, no database, and grow from there.
