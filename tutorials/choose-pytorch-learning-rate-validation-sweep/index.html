How to Choose a PyTorch Learning Rate with a Validation Sweep

A beginner-friendly PyTorch experiment that keeps the data, model, starting weights, optimizer, and training budget fixed while six constant learning rates compete on validation loss.

Mehdi Lotfinejad
August 3, 2026 · 11 min read

lr=... is often the first unexplained blank in a PyTorch training loop. A value that is too small can make working code appear frozen. A value that is too large can push the loss upward even though every line runs.

To choose a PyTorch learning rate, train fresh copies of the same model with log-spaced rates, give every copy the same starting weights and training budget, and select the lowest validation loss. Keep the test set hidden until one rate is chosen, and expand the sweep if the best result is at an edge.

This tutorial makes that comparison with six constant learning rates and a fictional 3D-print inspection task. Only the learning rate changes. That controlled design lets us connect each final score to the training path that produced it.

Setup, prerequisites, and teaching data

You need Python 3.11 or later and a terminal or notebook that can run Python. You should know how to define a function and select pandas columns. You should also know that a classifier assigns each row to a category. You do not need calculus or previous PyTorch experience.

All 3,000 job IDs, measurements, split labels, and outcomes are fictional. They do not describe a real printer or maintenance policy.

How one learning-rate step works

A neural network has adjustable numbers called weights. Training first calculates a loss, which measures how wrong the current outputs are. It then uses backpropagation to calculate a gradient for each weight. A gradient describes the local slope of the loss; subtracting it moves the weight in a direction that should reduce the loss.

For the optimizer that PyTorch names SGD, the central update is:

The learning rate scales the correction. If it is tiny, every update may be too small to make useful progress within the available time. If it is very large, an update can jump past a useful region. Repeated large jumps can make the loss oscillate, grow, or become a non-finite value such as nan.

The current PyTorch torch.optim guide shows the same training order used here: clear old gradients, calculate loss, call backward(), and then call optimizer.step(). The optimizer receives the rate through lr.

Learning rates are usually compared on a logarithmic scale. The sequence 0.0001, 0.001, 0.01, 0.1, 1, and 10 multiplies by ten at each step. A linear list such as 0.1, 0.2, and 0.3 explores only one narrow region while ignoring much smaller and larger possibilities.

This experiment uses one full batch per epoch. In other words, all 1,800 training rows produce one gradient and one update, so this use of torch.optim.SGD performs full-batch gradient descent. That keeps the comparison easy to inspect. A mini-batch training job may prefer a different rate because batch size, optimizer, model, and data scale all affect the update.

Train fresh models across the logarithmic sweep

A fair sweep must reset the model before each candidate. If rate 0.001 continues from the weights produced by rate 0.0001, the second candidate receives extra training and a different starting point.

Next, train one candidate for exactly 60 epochs. Calling torch.manual_seed(31415) inside the function gives each new model the same starting weights in this tested CPU environment. The current PyTorch reproducibility notes warn that exact results are not guaranteed across releases, platforms, or CPU and GPU runs, so record your environment as well as the seed.

Run six fresh models and retain every epoch. Then compare the validation loss at the end of the shared 60-epoch budget:

Read the validation-loss column from top to bottom. Rates from 0.0001 to 0.01 make little progress in 60 updates. Rate 0.1 learns more, and rate 1.0 has the lowest final validation loss at 0.6172. Rate 10 produces a much larger loss and near-chance accuracy.

Accuracy is useful context, but it is not the selection metric here. Cross-entropy also measures how much probability the model places on the correct class. Writing the metric before the sweep prevents us from switching to whichever column gives a preferred winner.

Read the path, not only the last row

A final score can hide an unstable route. Plot the final comparison beside complete validation curves for a very small rate, the selected rate, and a very large rate. The first axis uses a log scale because the candidate rates span five orders of magnitude:

The right panel explains three different failures and outcomes. At 0.0001, validation loss remains close to 0.700; the steps are too small for this budget. At 1, the curve falls quickly, reaches a lower region, and ends at 0.617. At 10, loss jumps upward and settles near 2.99; the steps are unstable for this setup.

The selected curve reaches 0.6015 at epoch 53 and then rises to 0.6172. That is an early sign that epoch count may need its own validation rule. We deliberately keep the 60-epoch endpoint because this experiment compares constant rates under one fixed budget. To choose a checkpoint with patience, use the separate learning-curves and early-stopping tutorial.

You can inspect the exact executed evidence in learning_rate_sweep.csv and learning_rate_history.csv.

Check the chosen rate once on test data

The 600 test rows have not affected scaling, training, or rate selection. Evaluate only the model already trained with rate 1.0. For context, compare its accuracy with a simple baseline that predicts the most common class in the training rows:

The test loss is close to the selected validation loss, and accuracy is above the training-majority baseline on this generated sample. These numbers support the completed experiment. They do not show that 1.0 is a default for another model. A change to batch size, optimizer, network depth, initialization, feature scaling, or training length creates a new tuning problem.

Do not return to the candidate table after seeing the test result. Adding a rate now would let test evidence shape selection. Reserve new later data or create a new outer evaluation plan if the search must change.

Common mistakes and troubleshooting

Reusing one trained model across candidates. Construct a fresh model and optimizer for every rate. Reset the controlled seed before construction so starting weights match.

Changing several settings together. If optimizer, batch size, layer widths, and rate all change, the result cannot isolate learning rate. Fix the training recipe first, then vary one setting.

Using only nearby decimal values. Start with powers of ten or another log-spaced list. If the best rate is the smallest or largest candidate, expand the range in that direction and rerun validation.

Ranking by training loss. Training rows update the weights, so training loss does not measure performance on unseen rows. Choose with a metric on validation rows that never update the model.

Ignoring the curve when the final value is finite. A run can oscillate or spike without reaching nan. Store every epoch, check np.isfinite, and inspect the path before accepting a final score.

Calling a slow rate broken too early. A tiny rate may learn given many more updates. Under a fixed budget, however, training time is part of the comparison. State the number of epochs or optimizer steps with the result.

Fitting the scaler on all rows. That allows validation and test distributions to affect training inputs. Learn preprocessing from training rows and reuse those stored values elsewhere.

Treating the seed as proof of stability. The reset makes this comparison controlled, not universal. After selecting a training recipe, test neural-network stability across several seeds in a separate experiment.

Expecting identical output on every machine. Record PyTorch, Python, hardware, and device details. Seeds limit randomness in one environment, but current PyTorch documentation does not promise exact results across every release and platform.

What you learned and where to go next

A learning rate is the multiplier on a gradient-based correction. Choosing it becomes a measurable task when everything else stays fixed. Start with log-spaced candidates, reset each model, use the same data and update budget, record complete validation curves, and choose with one metric named in advance.

In this executed sweep, rates below 0.1 moved too slowly for 60 full-batch updates. Rate 10 pushed validation loss near 2.99. Rate 1.0 had the lowest final validation loss at 0.6172, then reached 0.6081 loss and 0.672 accuracy on untouched test rows.

Carry the procedure to your own model, not the selected number. First decide the optimizer, batch size, metric, and training budget. Sweep a wide range on validation data. If the winning point lies on an edge, extend the range. Once the rate is fixed, use separate experiments for early stopping, seed stability, and any learning-rate schedule.
