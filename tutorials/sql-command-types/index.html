SQL Commands by Category: DDL, DML, DQL, DCL, and TCL

Sort every SQL keyword into the five categories that actually explain what it does to a database, then run each one - CREATE and ALTER, INSERT and DELETE, SELECT, GRANT, and COMMIT/ROLLBACK - against a small language-exchange meetup database you can build yourself.

Mehdi Lotfinejad
August 9, 2026 · 13 min read

Look up “SQL commands” and most pages hand you the same thing: an alphabetical glossary of forty-plus keywords, each with a one-line definition and no sense of how any of them relate. That’s not wrong, exactly — ALTER and DELETE are both SQL commands — but it’s not useful either, since knowing the label “SQL command” tells you nothing about when you’d reach for either one, or how much damage running the wrong one can do. The keywords actually sort into five clean groups once you stop asking “is this SQL?” and start asking “what does running this change?” (If you already know WHERE, JOIN, and GROUP BY and want the query-writing side rather than this categorization, our post on six core SQL skills picks up right where this one leaves off.)

Every SQL command sorts into one of five categories, based on what it actually changes when you run it. DDL (CREATE, ALTER, DROP) changes the database’s structure, DML (INSERT, UPDATE, DELETE) changes the rows inside that structure, and DQL (SELECT) reads rows back without changing anything. DCL (GRANT, REVOKE) changes who’s allowed to run any of those, and TCL (COMMIT, ROLLBACK, SAVEPOINT) decides whether a whole batch of changes actually sticks — know which category a keyword belongs to, and you already know roughly what it touches and how much a mistake with it can cost.

What Changes When You Run It

Five categories, five different things at stake:

  1. DDL — Data Definition Language. CREATE, ALTER, DROP. These change the database’s shape — add a table, remove a column, drop an index. Get one wrong and you can lose structure, not just data.
  2. DML — Data Manipulation Language. INSERT, UPDATE, DELETE. These change the rows living inside that shape, one write at a time.
  3. DQL — Data Query Language. SELECT, plus everything you bolt onto it (WHERE, JOIN, GROUP BY, ORDER BY). The only category that’s read-only by definition — run a thousand of them and the database looks exactly the same afterward.
  4. DCL — Data Control Language. GRANT, REVOKE. These change permissions — who’s allowed to run the other four categories, not the data itself.
  5. TCL — Transaction Control Language. BEGIN, COMMIT, ROLLBACK, SAVEPOINT. These don’t touch a table directly; they decide whether the DDL or DML you already ran actually counts.

Two things about that list are worth flagging before running any of it. DQL is the only category where a mistake is free — you can SELECT all day and never damage anything, which is exactly why it’s the one most tutorials teach first and stop at. TCL sits one level above the rest: it doesn’t do anything to a table by itself, it decides whether the DDL or DML you already ran actually took effect.

Here’s a detail that surprises people coming from MySQL: in SQLite, DDL is transactional, same as everything else.

ROLLBACK erased a CREATE TABLE as cleanly as it would erase an INSERT. That’s a real portability trap: MySQL’s own reference manual documents that most DDL statements cause an implicit commit before they run, so ROLLBACK there won’t undo a CREATE TABLE the way it just did here — don’t assume DDL is safely wrapped in a transaction just because it was on whatever database you learned on first.

WHERE on an UPDATE does the same filtering job it does on a SELECT; leave it off and every row in the table gets the same change, which is a much more common way to lose a Friday than a dropped table.

SELECT is also the deepest category by far; WHERE, JOIN, GROUP BY, and window functions are all still SELECT under the hood, just with more clauses attached. SQLite’s own SQL language reference documents every clause SELECT accepts, well beyond what one post can cover.

TCL: Making a Batch of Changes All-or-Nothing

A sign-up for Kenji’s session has to do two things at once: reserve a seat and record who took it. Do those as two separate statements and a crash, a network blip, or another concurrent sign-up between them can leave the seat count wrong forever. DCL: The Category SQLite Doesn’t Have

GRANT and REVOKE are real SQL commands, standardized alongside the other four categories — and SQLite doesn’t support either one:

That’s not a bug or a missing feature to work around; SQLite has no concept of database users at all, by design — a SQLite database is a single file, and whoever has file-system access to it has full access, full stop. DCL only exists on engines with their own user and role system, like PostgreSQL or MySQL. When the Categories Blend

A couple of commands don’t sit neatly in one bucket, and that’s worth knowing rather than memorizing as an exception. CREATE TABLE ... AS SELECT reads like DQL and acts like DDL in the same breath — it runs a query, then creates a brand-new table from whatever that query returned:

The SELECT half decides which rows and columns exist; the CREATE TABLE half is what makes them permanent. It’s genuinely both categories at once, not a DDL command that merely accepts a query as an argument.

INSERT ... ON CONFLICT (often called an upsert) blends the other direction — one statement that’s an INSERT if the row is new and an UPDATE if it isn’t. It’s the standard way to sync a table from an external feed without checking “does this id already exist?” yourself first:

Session 2 already existed, so the ON CONFLICT clause fired instead of a fresh insert: Kenji opened up a second seat, and both seats_total and seats_available went up by one in a single round trip. Whether you call that command DML, DDL, or “both” doesn’t change what it does — the category names are a teaching tool for organizing fifty keywords into five ideas, not a rulebook SQL itself enforces.

That’s the complete set: five categories for what a command changes, plus a couple of commands that borrow from two categories at once. CREATE, ALTER, and DROP shape the tables; INSERT, UPDATE, and DELETE shape the rows; SELECT reads without touching anything; GRANT and REVOKE decide who’s allowed to do any of that on a multi-user server; and COMMIT, ROLLBACK, and SAVEPOINT decide whether a batch of the above actually sticks. If you want the automatic side of DML next — code that runs by itself whenever a row changes, no transaction wrapper required — SQL triggers is the natural stop.
