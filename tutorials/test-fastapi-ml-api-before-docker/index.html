How to Test a FastAPI ML API Before Building a Docker Image

Build an executable contract around a small attendance-prediction service. Train one synthetic-data model, test the same saved artifact through FastAPI's HTTP boundary, inspect seven real pytest results, and package only the files that passed.

Mehdi Lotfinejad
August 11, 2026 · 12 min read

docker build can package files into an image even when the application returns the wrong JSON, accepts a broken request, or serves a different model version from the one the client expects. A successful image build is not proof that the prediction service works.

To test a FastAPI machine learning API before Docker, use FastAPI’s TestClient inside pytest and send requests to the same application object and saved model that the image will start. Check the health response, prediction schema, repeatability, invalid-input status codes, and OpenAPI fields; build the image only after those contracts pass.

This tutorial creates that test boundary for a fictional workshop-attendance service. We will train one small model, save it, exercise seven API contracts without opening a network port, and then place the tested files in a narrow Docker build context.

Understanding the Boundary Before You Package It

A contract test checks behavior that another component can observe. For an HTTP API, that behavior includes the URL, request fields, status code, response fields, and meaning of important values. It should not depend on private variable names inside the endpoint.

Our test path has four parts:

The arrow matters. Tests run against the saved model and service code first. The Docker image later copies those same two artifacts. This arrangement separates two questions:

  • Do the model and API satisfy their public contract?
  • Can Docker package and start the files?

If pytest fails, fix Python behavior. If the image build fails after pytest passes, inspect container configuration. That smaller search area makes failures easier to diagnose.

FastAPI’s current testing guide explains that TestClient sends requests directly to the application and works with normal pytest functions. It behaves like an HTTP client, but it does not need a background server or an available network port.

Troubleshooting: Find the Layer That Failed

Pytest cannot find attendance_model.joblib. Run the training script first and start pytest from the project directory. Keep the model path configurable if tests and production use different working directories.

A test constructs TestClient without with. Lifespan-dependent resources may not start and stop as expected. Use with TestClient(app) as client: whenever the application loads its model in lifespan.

A valid request starts returning 422. Read response.json()["detail"]. The loc field identifies the nested request path that failed. If the API change was intentional, update the client contract, OpenAPI expectation, and model feature mapping together.

The behavioral direction test fails after retraining. First confirm that the test loaded the new artifact and intended dataset. Then decide whether the expected product behavior changed or the assertion was too broad. Do not weaken a contract only to make a new model pass.

Tests pass, but the image cannot import scikit-learn. Compare the installed container packages with the environment that created the joblib file. A copied artifact without matching dependencies is incomplete.

The image contains the training data or virtual environment. Check .dockerignore and inspect the build context. An allowlist is easier to audit than a growing list of exclusions for this small service.

The process runs as root because file access failed. Check ownership on copied files and keep COPY --chown. Avoid removing USER as the first fix; it gives the service more privileges than inference needs.

All seven tests pass, so the model seems production-ready. That conclusion does not follow. Contract tests do not measure fairness, drift, latency under load, calibration, security, or decision quality. Add those evaluations separately with representative data and explicit acceptance rules.

Recap: Carry This Contract Forward

The durable sequence is train, save, exercise, package, smoke-test. Save one trusted model bundle, test it through the same FastAPI routes clients use, and build the image from the exact service and model files that passed.

In this lesson, seven contracts verified startup metadata, JSON shape, probability bounds, repeated-request stability, one intended feature direction, two invalid-input paths, and the OpenAPI schema. That evidence does not make the synthetic model suitable for real attendance decisions, but it does prove that the tested Python service behaves consistently before container configuration enters the picture.

For your own API, begin with one valid request and one failure that matters. Add a contract each time a bug reaches the HTTP boundary, and keep a small container smoke test for packaging errors. The result is a deployment process where each failed layer tells you where to look next.
