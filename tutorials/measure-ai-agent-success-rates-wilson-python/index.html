Measure AI Agent Success Rates with Wilson Intervals in Python

An agent can exceed a target in one test and still leave too much uncertainty for a release. Derive task success from inspectable output checks, calculate overall and per-task rates, add Wilson intervals, and make a conservative decision from the lower bound.

Mehdi Lotfinejad
August 11, 2026 · 12 min read

An AI agent completes 70 of 80 test tasks, so its measured success rate is 87.5%. If your release target is 80%, should the candidate pass? The arithmetic says yes, but it hides how much the result could move with a different sample of tasks.

To measure an AI agent’s task success rate, define a Boolean pass rule for each independent test case, divide passed cases by all cases, and report a Wilson confidence interval beside that percentage. Break the result down by task type, then compare the interval’s lower bound—not only the observed rate—with a release target chosen before evaluation.

This lesson builds that check for a fictional spreadsheet-cleanup agent. It does not call a model or claim performance for a real agent. Instead, it uses controlled saved outcomes so you can inspect the evaluator, reproduce every number, and later replace the teaching data with results from your own frozen test suite.

Understanding a success rate as a range of evidence

Think of each test case as one question with two possible evaluation results: pass or fail. The observed success rate summarizes the cases you tested. The underlying success rate—the rate across other relevant tasks you did not test—remains unknown.

A confidence interval keeps those two ideas separate. It places a range around the observed evidence, while its width shows how much sampling uncertainty remains under the chosen statistical model. More independent, representative cases usually tighten the range; repeated or nearly identical cases may add rows without adding the same amount of new evidence.

The task breakdown supplies a second view. The overall interval asks how strong the combined evidence is, while one interval per task type can reveal a capability that needs attention. Neither view replaces the pass rule: the evaluator must first decide what counts as correct for every case.

Turn output requirements into one task-level pass

Task success means the final artifact satisfies every condition required for that case. This definition must be written before you view aggregate scores. Otherwise, it is easy to weaken a rule after seeing an inconvenient result.

  1. the observed row count equals the expected row count;
  2. the output schema matches the reviewed schema;

Add a Wilson interval to each rate

A confidence interval is a range produced by a statistical procedure. Under the model used here, if we repeatedly drew representative independent task samples and built a 95% interval in the same way, about 95% of those intervals would cover the underlying task success probability. It does not mean that 95% of future tasks will pass, and it does not repair unrepresentative test data.

We will use the Wilson score interval for a binary proportion. Unlike the simple normal interval rate ± 1.96 × standard error, Wilson’s bounds stay between 0 and 1 and behave better for small samples or rates near the ends of that range. The NIST confidence-interval reference gives the formula and explains this advantage.

Make the release rule use the evidence range

Suppose the team chose an 80% minimum success target before running this test. There are two possible rules:

  • point rule: pass when the observed rate is at least 80%;
  • lower-bound rule: pass only when the 95% Wilson lower bound is at least 80%.

The second rule is more conservative. It asks whether the evidence clears the target after accounting for sampling uncertainty, not whether the most optimistic single-number reading clears it.

Under the chosen lower-bound rule, this candidate should not be released. The result does not prove that its underlying success rate is below 80%. It says the 80-task sample does not provide enough evidence to meet the stricter rule.

The decision also needs a capability rule. Mixed-date parsing has an observed rate below the target, so collecting more easy header cases would not address the known failure. Review those five controlled failures, improve the system or narrow its supported scope, then evaluate a fixed candidate on new cases. Do not keep adding cases until the same unchanged score happens to pass.

Know when this interval is not enough

The Wilson calculation treats rows as independent binary trials from the population you want to describe. Several common evaluation designs need more care.

You run the same task many times. Repeated outputs from one prompt can be related because they share the same wording and difficulty. Do not present 20 runs of one task as equivalent to 20 different representative tasks. Report task-level results, run-level consistency, and the sampling unit clearly.

You compare two agent versions. The same task answered by candidate A and candidate B creates paired data. A single interval around each rate does not measure the difference correctly. Use the same case IDs and a paired method, such as the paired bootstrap prompt comparison.

Task risk differs. A harmless formatting error and an unauthorized deletion should not become interchangeable failures hidden inside one average. Keep critical safety checks as zero-tolerance gates, then report ordinary task success separately.

Cases were selected after viewing failures. An interval quantifies sampling variation under its assumptions; it cannot remove selection bias. Freeze the test set and grading rules before scoring a release candidate.

Production traffic changes. Offline evidence describes the test population and evaluated version. Monitor real, privacy-safe outcomes after release and refresh the suite as supported tasks change.

Common mistakes and fixes

You divide by successful rows only. The denominator must include every evaluated task. Filtering failures before aggregation can create a perfect-looking rate.

Missing results disappear. Decide the policy before scoring. For a required task, a missing output should normally fail or stop evaluation; it should not silently reduce the denominator.

One easy category dominates the total. Show counts and rates by capability. If production frequencies are known and appropriate, define weights before evaluation and keep the unweighted breakdown visible.

The confidence interval becomes a guarantee. It covers one source of uncertainty under a statistical model. It does not cover weak labels, private-data leakage, untested languages, system changes, or future model updates.

The target is chosen after reading the score. Write the target, interval level, critical gates, and subgroup rules before executing the suite. Otherwise, the decision rule moves with the result.

Recap: define the pass before trusting the rate

An agent success rate begins with a case-level contract, not a dashboard percentage. Define the expected final artifact, turn every required check into one Boolean pass, keep all tasks in the denominator, and preserve task-type counts so a weak capability cannot hide inside the total.

Then add uncertainty. In this synthetic evaluation, 70 of 80 tasks passed, producing an observed rate of 87.5% and a 95% Wilson interval from 78.5% to 93.1%. The point estimate cleared an 80% target, but the lower bound did not, and mixed-date parsing was weaker than the total suggested.

The durable pattern is define, count, separate, bound, decide. Use it on a frozen, representative suite; keep critical safety rules outside the average; and treat more cases as better evidence only when they add relevant, independently reviewed coverage.
