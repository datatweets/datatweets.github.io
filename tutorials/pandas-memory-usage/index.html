How to Reduce Memory Usage in a Pandas DataFrame

Every numeric column defaults to 8 bytes per value and every repeated string gets stored on its own, whether your data needs it or not. This guide measures where a DataFrame's memory actually goes, then fixes it with dtype downcasting, category conversion, and targeted usecols/dtype loading — all verified on a real 20,000-row flight dataset.

Mehdi Lotfinejad
August 5, 2026 · 13 min read

A 1.2 MB CSV shouldn’t turn into a 2.4 MB DataFrame the moment you load it. But that’s exactly what pd.read_csv does by default on the file this post uses, and it’s not a bug — pandas is quietly rounding every number up to the widest type it has and giving every repeated piece of text its own separate storage, just to be safe. Multiply that by a file with a few million rows instead of twenty thousand, and “safe” turns into “my laptop fan just kicked in.”

If your large file happens to be JSON rather than CSV, our guide to pandas and JSON files covers flattening nested records and reading them in chunks — this post assumes a flat file and goes after a different problem: why the DataFrame in memory is so much bigger than it needs to be, and what to do about it before you ever reach for chunked reading. The short version: check where the bytes are actually going with df.memory_usage(deep=True), shrink numeric columns with pd.to_numeric(..., downcast=...), convert columns where values repeat a lot to category, and tell read_csv about all of this up front with dtype= and usecols= so the wasteful version never gets built in the first place. Do all three and it’s common to cut memory use by 70-80% with zero loss of information — often enough that a file you thought needed chunking fits in RAM just fine.

The Default Width Is Always the Safe One

pandas has no way of knowing, before it reads a single row, whether a column of numbers will top out at 9 or at 9 billion. So it doesn’t guess — it defaults every integer column to int64 and every column of decimals to float64, eight bytes per value either way, regardless of what the actual values turn out to be. A column that only ever holds the numbers 1 through 12 gets the same eight bytes per row as a column of Unix timestamps.

Text works the same way, just with a different mechanism. Older pandas stored each cell of a text column as object — a pointer to a fully independent Python string, with its own overhead on top of the characters themselves; a two-character string like "UA" costs 43 bytes once you count that overhead, not 2. category dtype fixes this the same way a lookup table fixes a spreadsheet full of repeated dropdown values: store the handful of unique strings once, in a shared list, and replace every cell with a small integer code pointing into that list. If a column has 16 distinct values repeated 20,000 times, you want to pay for 16 strings and 20,000 tiny codes — not 20,000 full strings.

Both fixes are the same idea: stop paying for the maximum possible size and start paying for the size the data actually needs. Everything below is that idea applied to one column type at a time, then applied automatically at load time.

20,000 Real Flights You Can Reproduce

Rather than a synthetic table where the “before” numbers are whatever I decided to generate, this post uses a real sample of the nycflights13 dataset — on-time performance for flights that departed New York City airports in 2013, originally published as an R teaching package and released under CC0 (public domain). The full file has 336,776 rows; a 20,000-row random sample (seed 42) keeps the post’s numbers reproducible while staying well under a megabyte and a half.

Data: a 20,000-row seeded sample of the nycflights13 dataset (CC0), via the Rdatasets mirror of the original CRAN package. Twenty thousand rows, fifteen columns, a genuine mix of small integers, delay-and-duration floats (some missing — more on that shortly), and text columns that repeat a lot (carrier, origin) or a little (dest). (Outputs in this post are from pandas 3.0.3 on Python 3.13. The downcasting and category techniques below work the same on pandas 2.x — but pandas 3.0 changed the default string dtype from object to str, which changes one specific comparison later in this post; that section calls out the difference.)

Finding Out Where the Memory Actually Went

df.info() prints a memory estimate, but only if you ask it to look properly:

memory_usage="deep" is the part that matters, and it’s worth understanding why. By default, .memory_usage() (and .info() without the deep flag) only counts the fixed-size slots pandas allocates for a column — for a text column stored as object, that’s just an array of pointers, not the strings those pointers lead to:

On pandas 3.0 those two numbers match, because the new default str dtype already stores text more efficiently and .memory_usage() accounts for it correctly either way. That’s a recent improvement, not something to rely on across versions — the same check against this exact file on pandas 2.3.3, where text columns default to object, gives shallow: 2,400,132 bytes and deep: 5,020,132 bytes. Skipping deep=True on 2.x doesn’t just round differently, it misses more than half the real memory footprint. deep=True costs a bit more time to compute; on any file worth optimizing, it’s worth it regardless of version.

With that settled, here’s where the 2.4 MB actually lives, column by column:

Every numeric column costs exactly 160,000 bytes — 20,000 rows times 8 bytes, whether the column is year (which is 2013 in every single row) or distance (which ranges up to almost 5,000). That flat, identical cost across wildly different columns is the tell that nothing has been sized to the data yet.

Downcasting Integers That Don’t Need Eight Bytes

pd.to_numeric(column, downcast="integer") looks at a column’s actual min and max and picks the smallest integer type that still holds every value — no manual range-checking required:

month, day, hour, and minute all fit in int8 (which holds -128 to 127); year and flight need int16 (-32,768 to 32,767) because 2013 and flight numbers past 127 don’t fit in a single byte. Seven columns, 82% less memory, and every value is still exactly what it was.

Skipping to_numeric and casting directly is the trap here. .astype("int8") doesn’t check the range first — it just truncates the bits that don’t fit, silently:

No error, no warning — a 1,089-mile flight becomes a distance of 65, and a 1,990-mile flight becomes negative 58. pd.to_numeric(..., downcast=...) is worth reaching for by default specifically because it picks a width that fits, rather than a width you hoped would fit.

Floats Default to 64 Bits Too — Downcast the Same Way

The same function, downcast="float", does the equivalent job for decimal columns:

Halved, as expected (float64 is 8 bytes per value, float32 is 4). The question worth asking before downcasting any float column is whether float32’s roughly 7 significant digits are enough — it isn’t for currency totals with many decimal places or scientific data spanning huge ranges, but delay minutes are effectively whole numbers, so nothing is lost:

Identical. Check this on your own data before trusting it, though — this result is a property of these columns (small, low-precision values), not a guarantee float32 gives free.

Repeated Text Doesn’t Need Its Own String Every Time

Back to the mental model from earlier: a category column only pays off when its values repeat. Check that before converting:

Sixteen airlines, three NYC airports, a hundred destinations — all spread across 20,000 rows, so all three are excellent category candidates:

Ninety percent gone, from three columns alone. But cardinality matters — this backfires on a column where almost every value is unique. Build one from this same data to see it happen: combine flight, day, and dep_time into a near-unique key (19,403 distinct values out of 20,000 rows) and compare:

category costs more here — 449,720 bytes versus 415,604 — because you’re now storing almost as many unique category entries as there are rows, plus a full array of integer codes on top of them. The rule of thumb: reach for category when a column’s nunique() is small relative to its row count, not automatically on every text column.

NaN Forces Float, Even for Whole Numbers

dep_delay and the other duration columns have missing values — 516 to 586 nulls out of 20,000, from flights that were cancelled and never departed or arrived. That’s not just a data-quality footnote; it’s why those columns are floats in the first place. Try casting a column with nulls to a plain integer type and pandas refuses:

NaN is a floating-point concept — there’s no bit pattern for “missing” in a plain int16, so pandas has to keep the whole column as float to represent it, even though every present delay value is a whole number of minutes. The fix the error message points to is pandas’ nullable integer dtype, capitalized Int16 rather than int16, which reserves a separate mask for nulls instead of borrowing a float bit pattern:

Int16 is both more honest about the data (these really are whole-minute integers) and smaller than float32 — 2 bytes per value plus a compact null mask beats 4 bytes per value. It’s a good default whenever a numeric column has nulls but every real value is a whole number.

Skip the Cleanup Pass: Set dtype and usecols at Load Time

Every fix above happened after loading the full-width DataFrame first. Once you know the dtypes you want, pd.read_csv’s official documentation shows you can hand them over up front — plus skip loading columns you were never going to use, which astype can’t do for you after the fact:

Same dtypes, same techniques — but doing it at read_csv time means the oversized 2.4 MB version never gets built at all, so peak memory during loading is lower too, not just the final size. Dropping dep_time and arr_time (two columns this particular analysis never used) pushes the saving from 74% to 80%.

When It Still Doesn’t Fit: chunksize

Dtype tuning has a ceiling — if a file is genuinely too large to hold in memory even at its smallest reasonable width, the next lever is chunksize, which turns read_csv into an iterator instead of a single DataFrame. It combines cleanly with everything above:

Four chunks of 5,000 rows, and the per-carrier averages match a direct whole-file computation exactly. This post doesn’t dwell on the chunking pattern itself — the pandas and JSON files post already walks through chunksize and incremental aggregation in detail, including the common mistake of pd.concat-ing every chunk back together and quietly rebuilding the exact thing you were trying to avoid. The point here is narrower: reach for chunksize after dtype tuning, not instead of it — a file that needs 40 chunks at float64 might need only 10 once every column is sized correctly.

Two Numbers Worth Remembering

Everything in this post reduces to two checks, done in this order: look with df.memory_usage(deep=True) before assuming where the weight is, then size each column to what its values actually need — pd.to_numeric(..., downcast=...) for numbers, category for text that repeats, nullable Int types for whole numbers with gaps, and dtype=/usecols= on read_csv so none of the wasteful intermediate version ever gets built. On the 20,000-row file used throughout this post, that took a DataFrame from 2.4 MB down to under 0.5 MB without dropping a single real value — and the same four techniques scale to files with millions of rows, where the difference stops being about tidiness and starts being about whether the script finishes at all.
