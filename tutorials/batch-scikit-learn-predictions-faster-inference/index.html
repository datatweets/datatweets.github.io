How to Batch Scikit-Learn Predictions for Faster Inference

Learn how prediction batch size changes call overhead, compute time per row, and throughput. Build a reproducible single-thread benchmark around one fitted scikit-learn model, compare seven batch sizes on the same rows, and verify that batching does not change prediction values or order.

Mehdi Lotfinejad
July 29, 2026 · 11 min read

A prediction service may receive 2,048 rows and still call model.predict() 2,048 times. The model handles the same data, but Python, pandas, and scikit-learn repeat their fixed per-call work for every row. That overhead can dominate the calculation.

To batch scikit-learn predictions, collect rows in a pandas DataFrame and pass several rows to one predict() call instead of calling the model once per row. Benchmark the same ordered rows at several batch sizes, warm the model before timing, report compute time per row and throughput, and confirm that every batch size returns the same predictions in the same order.

Our executed example uses one HistGradientBoostingRegressor and 2,048 fictional video-transcoding jobs. On the tested machine, single-row calls took a median of 648.383 microseconds per row. One call containing all 2,048 rows took 6.058 microseconds per row, a 107.03× improvement for this specific model and environment.

How Prediction Batching Works

Inference means using a fitted model to produce predictions. A single prediction call has two kinds of cost:

The per-call part includes Python function calls, input validation, and creation of output arrays. The per-row part is the estimator’s calculation for each record. Sending more rows together spreads the fixed cost of one call across those rows.

Compare two ways to process four records:

Scikit-learn’s current computational performance guide describes the first pattern as atomic prediction and the second as bulk prediction. Bulk prediction is generally more efficient. The guide also lists model complexity, feature count, input representation, and feature preparation as important parts of prediction latency.

Two measurements help us read the result:

  • Compute time per row is the elapsed time for the complete prediction workload divided by its number of rows. Lower is better.
  • Throughput is the number of predictions completed per second. Higher is better.

Compute time per row is an amortized cost, not the response time experienced by one request. Batching does not remove computation, and it does not make a model more accurate. It changes how work reaches the estimator. A live service may also wait while a batch fills, so faster computation does not automatically mean a faster response for each user.

Setup and the Synthetic Workload

You need Python 3.11 or newer and basic knowledge of Python functions and table rows. You should know that a fitted regression model predicts a number. Prior experience with web APIs is not required because the benchmark calls scikit-learn directly.

On Windows PowerShell, activate it with .venv\Scripts\Activate.ps1. The executed build used Python 3.13.2, NumPy 2.5.1, pandas 3.0.3, scikit-learn 1.9.0, Matplotlib 3.11.0, and threadpoolctl 3.6.0.

Download synthetic_transcoding_jobs.csv and save it beside your Python file. This original synthetic dataset was generated with NumPy seed 20260805 and is released under CC0-1.0. All 6,000 job IDs, media settings, queue values, and processing times are fictional. They do not describe a real service or media file.

One row represents one fictional transcoding job. Eight features describe the input media and processing conditions. processing_seconds is the target, while job_id is only an identifier and must not enter the model.

Fit One Model Before Measuring It

Prediction benchmarks should not include training time. First define the feature columns and reserve 20% of the data for testing. Then fit one histogram-based gradient-boosting regressor on the remaining rows:

Mean absolute error (MAE) is the average absolute gap between predicted and target values. A constant prediction equal to the training median had an MAE of 77.25 seconds on the same test rows. That comparison shows that the fitted model learned the synthetic pattern well enough for this performance lesson. It does not measure real transcoding accuracy.

If model persistence is part of your next step, save and reload the complete scikit-learn pipeline before connecting it to a service. Keep model loading outside the timed prediction loop.

The final chunk may be smaller than batch_size. Using min() makes the helper work when the row count is not an exact multiple of the chosen size. Concatenating in loop order preserves the original row order.

Benchmark Calls, Not Training or File Loading

Short timing tests are sensitive to startup work and temporary system activity. Warm the fitted model, repeat each complete 2,048-row workload seven times, and keep the median. A median is the middle value after sorting the measurements, so one unusually slow run has less effect than it would have on an average.

Python’s current perf_counter_ns() documentation describes it as a high-resolution performance counter that returns integer nanoseconds. Only the difference between two calls is meaningful.

The benchmark also uses threadpool_limits(limits=1) so every candidate has the same one-thread setting. This makes the comparison easier to repeat; it does not claim that one thread is best for deployment.

The first call before the loop warms the general prediction path. The extra call for each candidate warms that input shape before timing begins. The benchmark then times only calls to the already fitted model and the small chunking helper. It excludes CSV loading, feature construction, network travel, JSON conversion, model loading, and queue delay. Include those stages in a separate end-to-end service benchmark.

Read the Executed Batch Results

The full build also records the number of predict() calls and calculates speedup relative to batch size 1. The executed table is available as prediction_batch_benchmark.csv.

Read the first and last rows together. The single-row path repeats the call boundary 2,048 times and completes about 1,542 rows per second. The largest batch crosses that boundary once and completes about 165,061 rows per second. Per-row model work still exists, which is why the total time does not fall to zero.

Most of the gain appears before the largest batch. Moving from 1 to 64 rows per call cuts per-row time sharply. Moving from 1,024 to 2,048 gives a smaller improvement. This pattern suggests diminishing returns for this workload, not a universal best batch size.

Hardware, package builds, CPU limits, competing processes, model type, and feature preparation can change the numbers. Publish measurements from the environment that will run inference. Do not present this 107.03× result as a promise for another model or computer.

Verify That Batching Preserved the Predictions

A speed change is useful only if the results stay correct. Generate the output for every batch size and compare each array with the one-call reference:

All seven paths returned the same 2,048 values in the same positions. assert_array_equal() also checks the array shape, so the verification fails if a path drops the last partial chunk. A reordering that changes any position also fails.

Exact equality worked for this deterministic CPU estimator and input. Some models, hardware accelerators, or parallel numeric operations can produce very small floating-point differences. In that case, define a justified tolerance with numpy.testing.assert_allclose() and still check output shape and row order.

Choose a Batch Size for the Real Request Pattern

The fastest tested batch is not automatically the right service setting. Start with how predictions arrive:

  • For an offline table, call predict() on the largest block that fits memory. Test several block sizes because feature preparation and output storage also use memory.
  • For a synchronous request that already contains many rows, predict the validated request DataFrame in one call when its size is safe.
  • For unrelated single-row requests, a micro-batcher can wait briefly and combine them. That may raise throughput, but the waiting window adds response latency.
  • For a rare request where response time matters more than capacity, immediate single-row prediction may be the correct trade-off.

A production decision needs at least three values: the maximum acceptable wait, the maximum safe batch size, and the service’s target latency percentile. A percentile such as p95 is the value that 95% of requests finish at or below. The median compute time in this lesson does not describe p95 response time under live traffic.

Measure feature preparation too. Converting request objects to a DataFrame may cost more than predict() for a small model. If it does, optimize or batch that whole path instead of focusing only on the estimator.

Common Benchmark Mistakes and Troubleshooting

Timing training and prediction together. Model fitting is usually offline work. Fit once, warm once, then time the prediction boundary you want to improve.

Giving each batch size different rows. Data values can change branch paths and runtime. Use the same rows in the same order for every candidate.

Running only one timing sample. Background work can disturb one measurement. Repeat the complete workload, store every sample, and report a median plus a useful tail percentile when the test design supports it.

Reporting only total milliseconds. Total time is hard to compare when workloads differ. Record the row count, calls, batch size, total time, compute time per row, and throughput together.

Letting thread counts change between tests. Numeric libraries may use different worker pools. Hold thread settings constant during comparison, then benchmark planned production thread settings separately.

Changing the model while changing the batch size. That mixes two experiments. Keep model bytes, features, and inputs fixed when measuring batching. Compare model complexity in a separate accuracy-speed study such as tuning models with a callable GridSearchCV rule.

Forgetting output order. A chunking or queue layer can return correct values for the wrong records. Carry stable request IDs outside the model features and assert the mapping after prediction.

Assuming larger batches always help. Gains can flatten, memory can grow, and queue wait can become unacceptable. Expand the tested range around the sizes your real traffic can form.

Comparing local compute with HTTP response time. Serialization, validation, network travel, queueing, and worker contention are absent here. Run an end-to-end load test after the direct Python benchmark isolates the estimator behavior.

What You Learned and What to Test Next

Batching makes prediction more efficient when it spreads fixed call work across several rows. A reliable benchmark keeps one fitted model and one ordered input set, warms each candidate, times repeated full workloads, compares compute time per row and throughput, and verifies prediction equality.

The executed model processed the same 2,048 rows at seven batch sizes. One-row calls took 648.383 microseconds per row, while one 2,048-row call took 6.058 microseconds per row. That is strong evidence for batching this exact workload, but the choice for a live service must also include memory, queue wait, and tail latency.

Next, repeat the benchmark with your saved model, production feature representation, and realistic request sizes. Then test the whole service boundary under concurrent traffic. Use the direct benchmark to understand model-call overhead, and use the service test to decide what users will actually experience.
