SQL Subqueries: How to Nest One SELECT Inside Another

A subquery is just a SELECT statement dropped inside another one. This guide builds the habit of writing and testing the inner query first, then works through the three places a subquery can appear on a small bike-rental database you can reproduce yourself.

Mehdi Lotfinejad
August 8, 2026 · 10 min read

You’ve learned WHERE, JOIN, and GROUP BY, and most questions fall to one of them. Then you hit a question where the value you’re filtering on isn’t something you can type in — it’s itself the answer to another query. “Bikes priced above the shop’s average rate.” Typing in a literal number would work today and be wrong tomorrow, the moment a new bike gets added. A subquery is how SQL lets one query’s answer feed straight into another, without you ever computing that number by hand. (If WHERE, JOIN, and GROUP BY themselves aren’t solid yet, our post on six core SQL skills is the right place to start before this one.)

A subquery is a complete SELECT statement wrapped in parentheses and dropped inside another query, wherever that outer query expects a value, a list, or a table. Write the inner SELECT first and run it by itself to see exactly what it returns, then paste it into the outer query in the matching spot: after WHERE column = for a single value, after WHERE column IN for a list, or after FROM for a whole table. SQLite — like every SQL engine — always runs the innermost query first and works outward, so the inner query never needs to know anything about the query wrapped around it.

One Blank, Three Shapes

Think of the outer query as a sentence with a blank in it, and the subquery as whatever fills that blank. What varies from one subquery to the next isn’t the mechanics — it’s always “run a SELECT, use what it returns” — it’s the shape the blank expects:

  • A single value, if the blank sits after =, >, <, or inside a SELECT list next to other columns.
  • A list of values, if the blank sits after IN or NOT IN.
  • A whole table, if the blank sits after FROM, with its own alias.

Get the shape wrong — a subquery that returns three rows where the outer query expects one — and you don’t always get an error telling you so, which is exactly the trap the gotchas section below walks through.

A Value in SELECT: Comparing Every Row to One Number

Same inner query, same 7.375, but this time SQLite re-runs the subquery once per outer row and keeps every bike in the result instead of throwing rows away — the shape of the blank (a single value) is identical in both places, only the clause around it changes what happens with that value.

A List in WHERE: IN and NOT IN

Pair a subquery with IN and the blank stops expecting one value — now it expects a list, and the test becomes “is this a member of that list?” Which members have ever rented an e-bike?

NOT IN asks the opposite question with the identical inner query — which members have never rented an e-bike?

Four and four, and together they account for all eight members — exactly what you’d expect from a question and its exact opposite. One thing worth flagging honestly: if that inner list could ever contain a NULL (say, a rental with no member_id recorded), NOT IN stops working the way you’d expect and silently returns nothing at all. It can’t happen here, since rentals.member_id is never empty in this dataset — but it’s a real trap, and our deep-dive on PostgreSQL subqueries walks through exactly how it breaks and how NOT EXISTS avoids it.

A Table in FROM: Revenue by Category

The third shape: a subquery that returns many rows and many columns becomes a full, temporary table when you put it after FROM and give it an alias. Which bike category brings in the most total revenue?

The inner query never exists as a real table on disk — SQLite builds rental_revenue in memory, groups and sums it, then discards it once the outer query finishes. Road bikes edge out mountain bikes despite renting for less per hour, simply because they’re rented more often; a subquery this shape is how you get from “per-rental revenue” to “per-category revenue” in a single statement instead of two separate queries glued together by hand. (The SQLite subquery-expression documentation covers the full grammar, if you want the formal rules behind everything in this post.)

Where This Goes Wrong Quietly

A scalar subquery that returns more than one row doesn’t raise an error in SQLite — it just picks one, silently. How many road bikes does the shop actually have?

Two rows, not one — the moment you see that, you know the outer query needs IN instead of =. This is worth internalizing early: some SQL engines refuse to run a scalar subquery that returns multiple rows at all; SQLite isn’t one of them, so the discipline of testing the inner query by itself is doing real work here, not just being tidy.

Beyond This Post

Everything here is a standalone subquery — it runs once, on its own, regardless of which outer row is currently being considered. There’s a second flavor, a correlated subquery, that re-runs once per outer row and can answer per-row questions like “orders bigger than this same customer’s usual size.” Correlated subqueries, EXISTS/NOT EXISTS, and common table expressions (WITH) are all one level up from what a first subquery needs to cover, and our PostgreSQL subqueries guide is the deep dive once the three shapes here feel automatic.

Three shapes, one habit: a subquery is a SELECT you write and test on its own first, then drop into the blank shaped like a value, a list, or a table. Get the shape right and SQLite does the rest — get it wrong and, as the gotchas above show, it won’t always tell you.
