Kubernetes Services and Namespaces: A Stable Name for a Moving Target

A Namespace decides what an app's name means; a Service decides what's actually behind that name right now. This post builds both ideas on a real local Kubernetes cluster, then watches a rolling update happen step by step, compares two rollout strategies, and rolls one back with kubectl rollout undo.

Mehdi Lotfinejad
August 10, 2026 · 13 min read

Run the same app twice in the same Kubernetes cluster — once for developers to break, once for whoever tests the next release — and by the time both Deployments are named web, you’re already relying on something you might not have thought about: a Namespace boundary that makes web mean two different things depending on where you’re standing. Our post on readiness probes covers what happens to one of those Deployments during a rollout; this one is about the layer around it — how a Namespace scopes an app’s identity, how a Service gives a moving set of Pods one address that outlives any single rollout, and what a rolling update is actually doing to the objects behind that address while it runs.

A Kubernetes Namespace is a virtual cluster inside your real one: it scopes object names and Service DNS, so a Deployment and Service both named web can exist in dev and staging at once without conflict, and an unqualified name like web only ever resolves to the copy in your own namespace. A Service gives whatever Pods match its label selector one stable ClusterIP and DNS name that doesn’t change no matter how many times those Pods get replaced. A rolling update is that replacement happening gradually, under a maxSurge/maxUnavailable budget you control, while the Service in front of it keeps answering at the same address the entire time.

The Name Doesn’t Move; What’s Behind It Does

Pods are disposable. A rollout deletes them, a node reschedules them, a crash restarts them into a brand new IP — none of that is supposed to be your problem as a caller. A Service exists specifically to absorb that churn: Kubernetes assigns it one ClusterIP and one DNS name the moment it’s created, and that identity is stable for the Service’s entire lifetime, completely independent of which Pods happen to be answering behind it at any given second. The live list of “which Pods right now” is a separate object, Endpoints, that the Service controller keeps rewriting in the background.

A Namespace doesn’t sit inside that relationship — it sits around it. It’s the reason a Service named web even needs a stable identity within a scope in the first place: without namespaces, every app in the cluster would need a globally unique name, the same problem you’d have if every file on your laptop had to live in one folder. Namespaces let dev/web and staging/web both exist, both answer to the plain name web from inside their own namespace, and never once collide.

Put the two together and the rest of this post is really one claim, demonstrated four different ways on a live cluster: the namespace decides what a name means, and the Service decides what’s behind that name right now — a rolling update only ever touches the second part.

Two Environments, One Cluster, No Collisions

Everything below runs against a real local cluster — kind v0.27.0, Kubernetes server v1.32.2, kubectl client v1.33.0 — not a simulation. This is an infrastructure topic, not a data-analysis one, so there’s no dataset to source; the “data” is the cluster’s own live state, read straight from kubectl.

Two namespaces, dev and staging, each get the exact same shape of object: a Deployment named web and a ClusterIP Service named web in front of it. dev runs 4 replicas (enough to see a rollout’s surge and drain steps clearly); staging runs 1, just to prove namespace scoping without needing more.

staging-v1.yaml is identical except for the namespace name, replicas: 1, and VERSION: "staging-v1". Apply both and wait:

Two Deployments named web, two Services named web, four Pods in one namespace and one in the other — and nothing about kubectl apply complained, because dev/web and staging/web are different objects the instant they’re in different namespaces:

Same name, two entirely different ClusterIPs, because a ClusterIP is scoped to the namespace the Service lives in — not to the name alone. (One caution worth flagging early: deleting a Namespace deletes everything inside it, Deployments, Services, all of it, in one cascade. There’s no separate confirmation step, so treat kubectl delete namespace the way you’d treat rm -rf on a directory.)

What an Unqualified Service Name Actually Resolves To

The dev/web and staging/web Services both respond to the plain hostname web — but only from inside their own namespace. A small busybox Pod dropped into each namespace makes this concrete:

From inside dev, the bare name web reaches the dev copy. Reaching the staging copy from dev needs the fully qualified name, web.staging.svc.cluster.local — <service>.<namespace>.svc.cluster.local, the pattern every in-cluster Service DNS name follows. And from inside staging, the same bare name web now means something else entirely: its own copy. The mechanism behind this is ordinary DNS search-domain resolution, visible in the Pod’s own resolver config:

Every Pod gets a search list seeded with its own namespace first. A short name like web gets dev.svc.cluster.local appended before anything is looked up, which is the entire mechanism — no special-casing, just DNS doing what DNS always does with an unqualified hostname. The Kubernetes DNS for Services and Pods documentation covers the full naming scheme, including headless Services and per-Pod DNS records, if you need more than the Service-level lookup shown here.

Watching a Rolling Update Happen, Not Just Trusting It Did

dev/web is still on python:3.13-slim with VERSION=dev-v1. Bumping both to python:3.12-slim / VERSION=dev-v2 in one kubectl apply triggers a real rolling update:

A Deployment doesn’t update its Pods in place. It creates a second ReplicaSet (web-74f47f6588, the new template hash) and shifts replica counts between the old one (web-778d465498) and the new one, one Pod at a time, until the old ReplicaSet is at zero. Reading the events as a running total: the cluster went 4 (old only) → 5 (old 4, new 1) → 4 (old 3, new 1) → 5 (old 3, new 2) → 4 → 5 → 4 → 5 → 4 (new only). It briefly ran 5 Pods at once, one more than the 4 you asked for, and it never had fewer than 3 Pods ready. Those two numbers, +1 and -1, are exactly maxSurge and maxUnavailable:

25% of 4 replicas is exactly 1 — the default RollingUpdate strategy computes both knobs as percentages of the desired replica count (rounding surge up and unavailable down when the math doesn’t land on a whole number), and here it lines up cleanly.

Choosing How Aggressively a Rollout Moves

maxSurge and maxUnavailable are ordinary fields you can override, and setting them changes the actual shape of the event log above, not just a number in a YAML file somewhere. Patching the same Deployment to maxSurge: 0, maxUnavailable: 1 forces a stricter, slower-but-safer rule: never exceed the desired replica count, so an old Pod has to go away before a new one can start.

Repeating the same scaling-events query against this run (a fresh copy of the same two manifests, same commands, strategy patched first) shows a visibly different pattern — every scale-down is now paired with the scale-up that depends on it, not ahead of it:

Running total this time: 4 → 3 → 4 → 3 → 4 → 3 → 4 → 3 → 4. Total Pods never went above 4 — no surge at all — at the cost of briefly running on 3 out of 4 replicas at every step instead of the default’s momentary 5. Neither setting is “correct” in general: maxSurge: 0 is the right call when your cluster has no spare capacity for even one extra Pod; the default surge-first behavior is the right call when a brief drop in redundancy matters more than a brief spike in resource usage. Both still fully replace every Pod — the only thing that changes is which risk you’re accepting while it happens.

The Address Never Moves; the Endpoints Do

Through both of those rollouts, one thing was never touched: the Service object itself. Its ClusterIP was recorded three times — right after dev was created, right after the default-strategy rollout finished, and right after the maxSurge: 0 rollback finished:

Identical, all three times, because nothing in either rollout ever apply’d a change to the Service — only to the Deployment. What did change underneath it, continuously, is the list of Pod IPs actually backing that address:

None of those Pod IPs existed when the namespace was first created — every one of them was born partway through one of the two rollouts above. The Service is the stable half of this relationship; Endpoints is the half that’s supposed to keep changing, and a client talking to web:8000 never has to know or care which specific Pod actually answered.

Undoing a Rollout

Every rollout a Deployment performs is a numbered revision, and kubectl rollout undo steps back to the previous one without you having to remember or re-apply the old manifest by hand:

Only two revisions show up, not three, even though three separate apply/patch operations happened above — the very first apply and the maxSurge: 0 rollback both landed on the identical python:3.13-slim / dev-v1 template, so Kubernetes reused the same ReplicaSet object for both instead of creating a new one, and the reused object’s revision annotation just moved to the latest number. And CHANGE-CAUSE is <none> for both, because nothing here ever set it — in a real workflow you’d run kubectl annotate deployment web kubernetes.io/change-cause="bump to v2" -n dev right after each change, or this column stays useless forever, exactly as it does above.

undo re-ran the exact same rolling-update machinery from the previous two sections — new ReplicaSet scaled up, old one scaled down, under whatever strategy is currently set — just pointed at an older template instead of a newer one. A rollback is not a special code path; it’s a normal rollout with its target picked from history instead of from a fresh apply.

Where Namespaces Stop Drawing Boundaries

Leave off -n and you’re not in a neutral space — you’re in default. A context with no namespace configured resolves silently to the default namespace, not to “everything” or “wherever you last were”:

An empty result there means “unset,” and default is what fills the gap. Forgetting -n staging on a one-off kubectl apply doesn’t error — it quietly creates a second, unrelated copy of your object in default, which then sits there confusing the next person who runs kubectl get all -n staging and doesn’t see it.

Not everything is namespaced. Nodes, PersistentVolumes, Namespaces themselves, and most cluster-wide RBAC and admission-control objects live outside any namespace, visible from every namespace at once:

If you’ve been assuming a Namespace is a hard security or resource boundary the way a virtual machine is, it isn’t one by default — it’s a naming and DNS scope first, with real isolation (network policies, resource quotas, RBAC) as separate features you opt into on top, not something kubectl create namespace gives you automatically.

Putting the Three Pieces Back Together

A Namespace decides what web means where you’re standing. A Service decides what’s actually behind that name right now, and keeps its own address fixed while that changes. A rolling update — under whichever maxSurge/maxUnavailable budget you’ve chosen — is the only thing that ever moves, one Pod at a time, and kubectl rollout undo can always point that same machinery at an older revision instead of a newer one. None of the three pieces do their job without the other two.
