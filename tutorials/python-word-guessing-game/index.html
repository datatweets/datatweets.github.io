Build a Word-Guessing Game in Python That Scores Duplicate Letters Right

A naive letter-by-letter check double-counts repeated letters when scoring a guess. This post builds a small terminal word-guessing game around collections.Counter, using a real word list, that scores every guess correctly on the first try.

Mehdi Lotfinejad
August 9, 2026 · 11 min read

Write the obvious version of a guess-scoring function first: loop over the guess and the secret word position by position, mark an exact match as a hit, and mark anything else “present” if that letter shows up anywhere in the secret. It reads correctly. Then you test it against a secret with a repeated letter, and it quietly lies to you — crediting a guess with two correct-but-misplaced letters when the secret only contains one.

The fix is to score in two passes instead of one. First, sweep the guess against the secret and record every exact position match, removing each matched letter from a running count of what’s left in the secret. Second, sweep again for everything that wasn’t an exact match, and only mark a letter “present” if the leftover count still has a copy of it available — otherwise it’s a genuine miss. Python’s collections.Counter is built to hold that per-letter leftover count, and the two loops together are barely ten lines. The rest of this post builds a small terminal word-guessing game around exactly that scorer, using enumerate and zip to walk the guess and secret together — if those two feel unfamiliar, our post on enumerate, zip, and faster iteration covers them from the ground up.

Two Passes: Claim Exact Matches First

The core rule is that a letter in the secret can only ever be claimed once, no matter how many times it appears in the guess. Take the secret level (two L’s, two E’s) against the guess sneer. An exact-match pass finds exactly one hit — the E at index 3 lines up with the secret’s E at the same position — and removes that one E from the secret’s leftover count, which started at {l: 2, e: 2, v: 1} and drops to {l: 2, e: 1, v: 1}. The second pass then walks the remaining guess letters (s, n, e, r) against that shrunken count: s and n aren’t in the secret at all, e still has one copy left so it’s marked present and the count drops to zero, and r isn’t in the secret either. Nothing after that point can double-claim the E that pass one already spent.

That ordering — hits first, then present-or-miss against what’s left — is the entire idea. Everything below is just wiring it into a playable loop.

A Real Word List, Not a Hard-Coded Secret

Rather than hard-coding one secret word, the game should draw from an actual vocabulary. Public Domain Word Lists is a small collection of plain-text English word lists that its author, Michael Wehar, has explicitly released into the public domain; its 5000-more-common.txt file holds 5,000 everyday English words. Filtering that file down to unique, five-letter, alphabetic-only entries leaves 712 words — small enough to vendor directly alongside this post, and every one of them a real word rather than an invented placeholder. For the rest of this post, though, we’ll hand-pick level as the secret instead — its two L’s and two E’s put both duplicate-letter cases through their paces in one short game, which a random pick isn’t guaranteed to do.

Where the Naive Version Lies to You

Here’s the tempting first-draft scorer, and a guess chosen specifically to expose the problem: eager against the secret acute.

Look at positions 0 and 3 — both are the letter E, and both come back present. But acute contains exactly one E. The naive check only ever asks “is this letter anywhere in the secret?”, so once it’s established that E exists in acute, it happily credits it a second time for the second E in the guess, as if the secret had two of them. A player would read that as “two E’s are in the word, just not here” — which is simply false.

Scoring a Guess Without Overcounting

The two-pass version fixes this by tracking, letter by letter, how much of each secret letter is still “unclaimed.” collections.Counter is a dict subclass built for exactly this — count occurrences, then decrement as they get used:

Same guess, same secret, one real present this time. The first loop only ever assigns "hit", so by the time the second loop runs, remaining reflects exactly what’s left after exact matches are already spoken for. The second loop then spends that leftover count one letter at a time, left to right through the guess — which is also why the order you check the guess’s letters in matters: whichever position claims a letter first gets present, and the same letter appearing again later in the guess only gets it if there’s still a copy left to give. (The outputs in this post come from Python 3.13 — everything shown works unchanged back to Python 3.7, since collections.Counter and f-strings have been stable that whole time.)

Why the Two Passes Can’t Be Merged Into One

Counter is doing the real work above, which raises an obvious shortcut: why not check hits and leftover-presence in the same loop, instead of running two separate ones?

That matches score_guess("sneer", "level") exactly, and it also matches on eager/acute — so on both examples this post has used so far, the shortcut looks like a correct, shorter equivalent. It isn’t. Try sassy against the secret amass (two A’s, two S’s):

They disagree at index 2. secret[3] is a genuine hit (s == s), and the two-pass version reserves it correctly because it scans every position for hits before spending a single leftover count. The single-pass version doesn’t get that lookahead: reading left to right, it reaches index 2’s s before it has any way of knowing index 3 is about to be a hit, so it spends one of the secret’s two s letters on a present that the real hit needed. By the time the loop reaches index 3, the match still registers as "hit" — hits aren’t gated on remaining — but the leftover count is now overdrawn, and index 2 has already been scored wrong. Whichever position gets processed first wins a shared letter, and a single interleaved pass processes hits and presence checks in the same left-to-right order, with no way to give hits priority over guesses that come earlier in the word. That’s the real reason score_guess runs a complete hit-only pass before touching remaining for anything else — it’s not a style preference, it’s what makes “hits are claimed first” true in every case instead of just the cases this post happened to try first.

Turning States into Something Readable

A list of "hit" / "present" / "miss" strings isn’t something a player wants to read. Map each state to a short bracketed symbol next to the letter it belongs to:

[X] is an exact hit, [o] is present-but-misplaced, and [.] is a miss — either the letter genuinely isn’t in the secret, or every copy of it has already been claimed by an earlier match.

What This Simple Version Glosses Over

  • A rejected guess still burns an attempt number. Look at the output above: the valid guesses are numbered 1, 3, 4, 5 — the numbering jumps because 42abc consumed slot 2 in the enumerate, even though it was never scored. An interactive version should track valid attempts on their own counter, or re-prompt in place rather than advancing to the next item in a list.
  • No guess ever has to be a real word. play only checks length and that every character is a letter — zzzzz scores as a valid guess. A stricter version would also check guess in WORDS, at the cost of rejecting perfectly reasonable words that simply aren’t in this particular 712-word list.
  • Module-level random.choice isn’t reproducible. It reads from a global, process-wide random state, so calling it twice in the same run gives you two different words — fine for actually playing, but useless for a test that expects the same secret every time. That’s exactly why the secret-picking example above builds its own random.Random(7) instance instead of using the module-level function.
  • Raw terminal input needs normalizing before it’s safe to compare. input() keeps whatever whitespace and casing the player typed, including the trailing newline some terminals leave in. Comparing "LEVEL\n" == "level" is False even though a person would call that a correct guess — guess.strip().lower() is doing real work in play, not just tidying up for appearance.
  • score_guess itself trusts that guess and secret are the same length, and only play enforces that. Call it directly with a mismatch — score_guess("cat", "level") — and it doesn’t raise; it silently returns ['miss', 'miss', 'miss', None, None], because result is sized to secret but the second loop iterates guess. A guess longer than the secret raises IndexError instead. That’s fine as long as score_guess only ever gets called from inside play’s existing length check — but the next section pitches it as a reusable pattern outside this game entirely, and in that context the guard needs to move with it: add if len(guess) != len(secret): raise ValueError(...) at the top of score_guess before lifting it out.

The Same Trick Works Beyond Games

Nothing about the two-pass scorer is specific to a word-guessing game. Any time you’re comparing two sequences of the same length and need to know, position by position, “does this value also appear somewhere else, without counting the same occurrence twice,” you’re back to a Counter and the hit-first-then-leftover pattern — grading a fill-in-the-blank quiz where an answer key has repeated options, or checking whether a shuffled list is a genuine permutation of another one, both reduce to the same shape.
