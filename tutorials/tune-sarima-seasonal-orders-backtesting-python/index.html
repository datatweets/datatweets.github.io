How to Tune SARIMA Seasonal Orders with Backtesting in Python

A beginner-friendly SARIMA tuning workflow that keeps the nonseasonal model fixed, compares six small seasonal blocks across repeated seven-day forecasts, rejects incomplete fits, and checks the selected model once against a weekly baseline.

Mehdi Lotfinejad
August 13, 2026 · 11 min read

Should a daily forecast use yesterday’s value, the value from the same weekday last week, or last week’s forecast error? All three choices can produce a fitted model. The useful choice is the one that predicts later data under the same timing as the real task.

To tune SARIMA seasonal orders in Python, fix a small nonseasonal order, define a short list of (P, D, Q, s) candidates, and score each candidate at repeated forecast origins that move forward through time. Select the lowest validation error only after confirming that every fit converged. Then compare that unchanged model with a seasonal-naive baseline on a later test period.

This lesson uses daily return counts from a fictional reusable-container collection center. Every Monday, the center makes one plan for the next seven days. That fixed seven-day task determines how we build the backtest.

Before you begin: packages, data, and scope

You need Python 3.11 or later and a way to run a Python file or notebook cell. You should know how to call a function and select a pandas column. You do not need previous experience with seasonal forecasting.

How seasonal-order tuning works

SARIMA extends ARIMA with terms that act one seasonal cycle apart. Its compact notation is:

The lowercase values describe the nonseasonal part:

  • p is the number of autoregressive terms, which use earlier values.
  • d is the number of ordinary differences.
  • q is the number of moving-average error terms, which use earlier forecast errors.

The uppercase values describe the seasonal part:

  • P is the seasonal autoregressive order.
  • D is the number of seasonal differences.
  • Q is the seasonal moving-average error order.
  • s is the number of observations in one cycle.

Here, one row is one day and the operating rhythm repeats weekly, so s=7. A seasonal difference with D=1 compares a value with the value seven days earlier. A seasonal AR term with P=1 lets the model use a relationship one week back. These are related ideas, but they do different jobs.

The current statsmodels SARIMAX reference defines order=(p,d,q) and seasonal_order=(P,D,Q,s). Despite the final X in the class name, external predictor columns are optional. This lesson does not pass exog, so the model uses only the return series.

We will keep the nonseasonal order fixed at (1, 0, 0). This controls the size of the experiment. If lowercase and uppercase terms all change together, a beginner cannot tell whether a result improved because of yesterday’s value, last week’s value, differencing, or an interaction.

The evidence moves through three ordered regions:

Each origin produces all seven forecasts before any actual value inside that week is revealed. This is a rolling-origin backtest: the forecast date moves forward through history while the information boundary remains realistic. Origins are seven days apart, so each target date appears once.

If your application updates a forecast every morning, use repeated one-day forecasts instead. If it creates a 30-day plan once a month, score 30 steps at each origin. Model tuning must answer the actual forecast schedule.

Score repeated seven-day plans

At one forecast origin, fit only on rows before the origin. Keep all seven later actual values hidden while the model predicts the block. The following core loop scores any seasonal order and stores the origin, target, horizon, actual value, SARIMA forecast, and weekly baseline on the same row:

The complete executed builder also catches ValueError, linear-algebra errors, and failed convergence. A candidate receives a validation MAE only when all eight origins succeed. Mean absolute error (MAE) is the average absolute distance between actual and forecast values. It stays in container-return units, and lower is better:

Every candidate completed all eight origins. (1, 0, 1, 7) has the lowest validation MAE at 3.68 returns, so it becomes the selected seasonal order. The runner-up reaches 3.80. That small gap means the ranking could change with another validation period; it does not make the winner universally best.

The model without seasonal terms has an MAE of 8.36. Its poor result is evidence that weekly structure matters in this dataset. It does not show which seasonal form will work for another series.

Check the selected model on untouched dates

Keep (1, 0, 1, 7) fixed and move the same seven-day evaluation through eight final origins. Compare it with a seasonal-naive baseline, which predicts each day with the value from seven days earlier.

What can go wrong during SARIMA tuning

Using a random split. Shuffling allows later dates to influence a model scored on earlier dates. Keep the series ordered and forecast forward from every origin.

Choosing s from row count alone. Seven rows mean one week only for complete daily data. Confirm frequency and use process knowledge. Hourly data with a daily cycle usually uses 24 observations, while monthly data with a yearly cycle usually uses 12.

Searching every term at once. A large search can overfit a short validation region and makes failures difficult to diagnose. Fix justified choices, start with a small candidate list, and expand it only for a stated reason.

Treating AIC as forecast error. Akaike information criterion measures penalized in-sample fit. It is useful for comparable fitted models, but it does not recreate seven-day decisions. Select for the future-facing metric that matches the task.

Ignoring failed convergence. A low error from an optimizer that did not converge is not a reliable winner. Record failures, inspect the configuration, and require candidates to cover the same origins.

Hiding every warning. Suppressing all warnings can conceal missing frequencies, invalid values, or unstable parameters. Catch only the warning you plan to handle and keep the rest visible.

Refitting inside the forecast block. If Tuesday’s actual enters the model before Wednesday’s prediction, you have tested daily updates rather than one Monday plan. Both workflows can be valid, but they answer different questions.

Skipping the weekly baseline. A seasonal model should earn its complexity. Compare it with the same-day-last-week rule on identical origins and horizons. The seasonal-naive forecast tutorial builds that reference from first principles.

Selecting on the final test. The final period gets one job: checking the already selected model. If the result is disappointing, report it. Do not return to the candidate table and quietly choose another order.

Assuming stable behavior after deployment. Calendar changes, collection rules, missing reports, and shifts in user behavior can weaken an old pattern. Monitor recent errors and define when the model will be reviewed.

Where to go next: keep the test frozen

Seasonal-order tuning works best as a controlled comparison. Fix the forecast task and the nonseasonal structure, choose s from the sampling interval and the real cycle, and use several later forecast origins to compare a short candidate list. Reject incomplete fits before ranking candidates by error.

In this executed lesson, eight validation plans selected SARIMA(1,0,0)×(1,0,1,7) with MAE 3.68. Eight later plans produced MAE 2.91, compared with 3.71 for the weekly baseline. Those numbers belong to one synthetic dataset. The reusable result is the boundary between fitting, selection, and final checking.

For a real project, preserve the row-level forecast table. Group errors by horizon, weekday, and forecast origin to find where the average hides risk. If you then tune the nonseasonal (p,d,q) block, do it in a new validation experiment and leave another later period untouched. The site’s ARIMA walk-forward validation guide shows how to organize that nonseasonal selection step.
