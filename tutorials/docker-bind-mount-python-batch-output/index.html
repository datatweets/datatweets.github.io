How to Save Python Batch Output from a Docker Container

Build a small Python batch image that reads a CSV through a read-only bind mount, writes an inspection queue through a separate output mount, runs as a non-root user, and records the input hash so each result can be checked.

Mehdi Lotfinejad
July 31, 2026 · 12 min read

A batch program can print completed and exit successfully while its CSV remains inside a disposable container. Remove that container, and the result disappears with it. A successful process and a saved result are two separate facts.

To save Python batch output from a Docker container, bind-mount one host directory (folder) at a read-only input path and a separate host directory at a writable output path. Write results only to the output path, remove the container automatically with --rm, and verify the files on the host after the process exits.

This tutorial builds that boundary around a fictional greenhouse scoring job. The Python code uses only the standard library inside the image. It writes a short attention queue and a JSON receipt that identifies the exact input file used for the run.

Understanding the Two Mount Directions

A bind mount makes an existing host file or directory appear at a chosen path inside a container. Docker does not copy the files. The host and container see the same mounted data.

Our batch has two one-way responsibilities:

The input mount uses readonly, so the process cannot edit the source CSV through that path. The output mount remains writable, so files created under /output are created in the host’s output directory. Docker’s current bind-mount documentation recommends the explicit --mount syntax and explains that bind mounts are writable by default unless readonly is present.

This is different from copying a result out with docker cp. A copy is a second action that can be forgotten after the job finishes. A mounted output folder makes persistence part of the run command itself.

It is also different from a Docker-managed named volume. A named volume is useful when Docker should manage storage for a database or service. A bind mount fits this batch because a person or a later process on the host needs to open the CSV directly at a known project path. For a longer introduction to images, containers, and persistent notebook files, see Docker and Jupyter for reproducible data science.

Run the Container and Inspect the Host Output

Clear old results first so a failed run cannot be mistaken for fresh output. Then run with a read-only container filesystem and two separate mounts:

The runtime --user value uses the current shell user’s numeric user and group IDs. This usually gives convenient output ownership on Linux and WSL while keeping the process non-root for a normal user account. Docker Desktop translates host-file access through its virtual machine. If your environment rejects this mapping, first try the image’s default user by removing only the --user line. Do not solve a permission problem by making unrelated host directories writable by everyone.

--read-only prevents writes to the container’s own filesystem. The /output bind mount is the deliberate writable exception. PYTHONDONTWRITEBYTECODE=1 prevents Python from trying to create __pycache__ beside the script. The Docker run reference documents both --read-only and the preferred --mount form.

Troubleshooting Missing, Stale, or Unwritable Results

The output directory does not exist. With --mount, Docker reports a missing bind source instead of silently creating the directory. Run mkdir -p input output before docker run. This stricter failure is one reason to prefer --mount over the shorter -v syntax.

The process reports PermissionError under /output. The container user cannot write to the host folder. On macOS, Linux, or WSL, keep the --user "$(id -u):$(id -g)" option. In a CI runner, create the output directory with ownership matching the numeric user used for the job.

The CSV is unchanged after a run. Delete known outputs before starting, require a zero exit status, then inspect run_summary.json. A file’s existence alone does not prove it came from the latest input. Compare the recorded SHA-256 and expected row count.

The input file was edited by the job. Confirm that readonly belongs to the /input mount, not the /output mount. Mounting the whole project as writable gives the batch more access than it needs.

A temporary file remains after an interrupted run. The final CSV is still protected because replacement never happened. A scheduled cleanup can remove old temporary files. Give them a recognizable prefix if your application needs that maintenance step.

The image works today but changes after a rebuild. A language tag can receive a new patch release. Record the tested base image and use a digest when exact base-image bytes matter. Rebuild deliberately to receive security updates; do not let reproducibility prevent maintenance.

The batch receives secrets later. Do not copy credentials into the image or put them in the input CSV. Use the secret mechanism provided by your runtime, give it the narrowest access possible, and avoid writing secrets into the summary.

What You Learned: Make Persistence Part of the Contract

A container’s successful exit does not guarantee that its results survived. The durable pattern is to give each path one role: /input is a read-only view of source data, /output is the only writable host bridge, and the image filesystem is disposable.

The Python side completes the contract. It validates the source before work begins, writes complete files by replacement, and leaves a small receipt with the input hash and row counts. The executed greenhouse batch read 240 snapshots, selected 93 at the teaching threshold, and preserved the input bytes.

For your own batch, replace the fictional scoring rule with your transformation or model, but keep the boundaries and checks. If the job later needs several services, such as a database and a loader, continue with the Docker Compose data engineering lab. The storage question stays the same: decide which data is disposable, which data must survive, and make that decision visible in configuration and tests.
