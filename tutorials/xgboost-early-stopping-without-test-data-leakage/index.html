How to Use XGBoost Early Stopping Without Test Data Leakage

A beginner-friendly XGBoost regression workflow that gives training, validation, and test rows separate jobs, selects the number of trees with validation MAE, reads the zero-based best iteration correctly, and compares the locked model with useful baselines.

Mehdi Lotfinejad
August 21, 2026 · 12 min read

Setting n_estimators=2000 gives XGBoost room to learn, but it also creates a question: which boosting round should the model use for prediction? Choosing that round from test error makes the result look more reliable than it is because the test answers influenced the choice.

To use XGBoost early stopping without test data leakage, split the data into training, validation, and test sets. Fit only on the training rows, put validation data—not test data—last in eval_set, and evaluate the selected model once on the untouched test set.

This tutorial applies that workflow to a regression problem: predicting how many minutes a fictional warehouse order will take to collect. You will see what XGBoost monitors, why it continues for several rounds after the best score, and how to read best_iteration without an off-by-one error.

Setup and data for the lesson

You need Python 3.11 or newer and a terminal, script editor, or notebook. You should know that a regression model predicts a number. You do not need to know the mathematics of gradient boosting. If fit(), features, and targets are new terms, begin with How to Build Your First Machine Learning Model.

On Windows PowerShell, use .venv\Scripts\Activate.ps1 for the activation step. The executed lesson used Python 3.13.2, NumPy 2.5.1, pandas 3.0.3, scikit-learn 1.9.0, XGBoost 3.3.0, and Matplotlib 3.11.0.

Download synthetic_warehouse_picks.csv and save it beside your Python file. This original synthetic dataset is released under CC0-1.0. Synthetic means that code created the data. All 2,400 session identifiers, order details, work conditions, and times are fictional. They do not measure a real warehouse.

Load the CSV and inspect a few columns before modeling. The small view helps you check the unit of the target and the scale of two inputs:

Each row represents one completed picking session. The features are the eight values available before the work finishes, such as the item count, walking distance, congestion, and scanner retries. The target is pick_minutes, the duration that the model learns to predict. session_id is an identifier, so it must not be a model feature.

How early stopping works without leaking answers

XGBoost builds decision trees in sequence. In this regression model, each boosting round adds one tree that adjusts errors left by the trees before it. More trees usually reduce error on the training rows, but that does not mean they improve predictions for new rows.

Early stopping ends training when a metric on separate validation data has stopped improving. In this lesson, the metric is mean absolute error (MAE). MAE is the average absolute difference between the actual time and the predicted time. Lower is better, and the result remains in minutes.

The three data parts have different jobs:

The validation set is part of model development because it helps select the number of trees. The test set must stay outside that process. If you put test data in eval_set, XGBoost checks its error after every round and stops where that error looks best. The test labels have then selected part of the model. That is data leakage: information reserved for final evaluation changes training or model selection.

The current XGBoost scikit-learn interface guide explains that XGBoost does not create this split inside the estimator. You must supply an evaluation set yourself. The XGBRegressor API also states that the last item in eval_set controls early stopping when several sets are present.

early_stopping_rounds=40 means training continues until the monitored metric has failed to improve for 40 consecutive rounds. It does not mean “train exactly 40 trees,” and the best round does not need to be a multiple of 40.

Give every row one clear job

Reserve 480 rows for the final test first. Then take another 480 rows from the remaining data for validation. The rest become the 1,440 training rows:

The fixed random_state reproduces these row assignments. A random split is reasonable for independent fictional sessions from one stable process. It would be wrong if several rows came from the same order or worker and those groups could cross the split. It would also be wrong if the real goal were to predict future sessions after a process change. Use a group-aware or time-aware split in those cases.

Do not merge the validation rows back into training before early stopping. The model needs predictions on unseen validation rows to decide whether another tree is helping.

Read the selected round correctly

After fitting, inspect the attributes created by early stopping. Also count how many rounds exist in the stored booster:

best_iteration is zero-based. A value of 249 therefore identifies the 250th boosting round. The model contains 290 rounds because XGBoost needed 40 later rounds with no new minimum before it could confirm that improvement had stopped.

Those extra rounds do not require a manual correction for normal prediction. In the scikit-learn interface, model.predict(X_test) automatically uses the trees through best_iteration and ignores the later patience rounds. This behavior differs from some calls in XGBoost’s native Booster interface, so check the documentation for the interface you use. The official XGBoost prediction guide describes that distinction.

The evaluation history shows why the validation set selected round 250. The next plotting code chooses Matplotlib’s non-interactive Agg backend before importing pyplot, so it also runs on a server without a display:

Read the blue training curve as evidence about fit to known rows. It keeps falling because later trees can describe those rows more closely. Read the orange validation curve as evidence about predictions on separate development rows. Its minimum marks the selected model size; later changes are too small or move in the wrong direction.

Do not choose the best round by looking for the smallest training error. Training error rewards additional trees even when those trees do not improve generalization, which is performance on new data from the same process.

Open the test set after the choice is fixed

The split, features, metric, model settings, stopping patience, and best round are now fixed. Generate test predictions and compare them with a simple median baseline:

The early-stopped model misses the actual pick time by 3.194 minutes on average across the 480 test sessions. The median rule misses by 13.252 minutes, so the features provide useful signal in this synthetic example. Root mean squared error (RMSE) is higher because it gives more influence to larger errors.

As a controlled comparison, the executed build also fit the same XGBoost settings for all 2,000 trees with early stopping disabled. Its test MAE was 3.280 minutes. The early-stopped result was slightly better, and normal prediction used only the trees through the selected round. This difference belongs to this dataset and split; early stopping does not guarantee a lower test error on every problem.

Inspecting a few predictions makes the average error more concrete. The published test_pick_time_predictions.csv contains all 480 executed test predictions:

Each row is one prediction, not another training example. For PICK-0110, the prediction is about 0.31 minutes from the actual time. For PICK-0443, it is about 5.07 minutes high. The overall MAE combines all 480 absolute errors, so five rows cannot establish model quality by themselves.

Common mistakes and how to fix them

Using test data in eval_set. This makes the test labels select the number of trees. Create a validation set from development data and keep the test set outside every training and selection call.

Passing validation first and training last. With several evaluation sets, XGBoost uses the last one for early stopping. Put (X_validation, y_validation) last, or use a configured EarlyStopping callback when you need to name the monitored dataset and metric explicitly.

Monitoring only training data. Training error often continues falling as trees are added. Stopping on it does not measure whether new rows benefit. Use separate validation data that represents the prediction task.

Reading best_iteration=249 as 249 trees. The attribute starts counting at zero. Add one when you communicate the selected number of boosting rounds to a person.

Assuming the stored model has only the best trees. With the simple early_stopping_rounds setting, the booster can contain the later patience rounds. The scikit-learn estimator uses the best iteration automatically for prediction. For advanced control, XGBoost provides an EarlyStopping callback with save_best=True.

Setting a very small patience value. A validation metric can move slightly from one round to the next. Patience of one or two rounds may stop on ordinary noise. Treat values such as 20, 40, or 50 as candidates, and decide them with development evidence rather than test results.

Treating 2,000 as a recommended tree count. It is only a generous upper limit for this combination of learning rate and data. A higher learning rate may need fewer rounds. A lower learning rate may need more. Tune connected settings together.

Using one validation split when results are unstable. Early stopping selects a round for one partition. If the dataset is small, repeat the development experiment across suitable splits or use a careful cross-validation plan. Keep a final test outside selection. The DataTweets guide to measuring XGBoost regression error with repeated cross-validation explains how to report fold-to-fold variation for fixed model settings.

Refitting on training plus validation without a stopping plan. After selection, you may want a final model that uses more development rows. If you merge the validation set back into training, you no longer have the same early-stopping signal. One practical approach is to create a new estimator with early stopping disabled, set n_estimators=model.best_iteration + 1, fit it on all development rows, and then evaluate it once on the test set. Treat that refit policy as part of the workflow and verify it for your application.

Expecting identical numbers on every machine. Use the same CSV, split seed, feature order, package versions, and model settings. Small floating-point differences can still occur across platforms. A large difference usually indicates a changed split, dataset, or parameter.

Recap: validation chooses, test confirms

Early stopping is a model-selection method. Training rows fit the trees, validation rows choose when improvement has ended, and test rows measure the completed process. Keeping those roles separate prevents the final evaluation labels from influencing the chosen number of trees.

In this executed example, XGBoost found its lowest validation MAE at zero-based iteration 249, which is boosting round 250. It trained through round 290 to satisfy 40 rounds without improvement. Normal prediction then used the trees through the best iteration and reached a test MAE of 3.194 minutes, compared with 13.252 minutes for the median baseline and 3.280 minutes for the fixed 2,000-tree model.

Carry the boundary into your next project: choose a generous maximum, monitor a representative validation set, record best_iteration and best_score, and open the test result only after the training choices are fixed. The exact best round will change. The separation between fitting, selection, and final evaluation should remain.
