Welcome to Layout Primitives#

st.columns and st.sidebar have done every bit of layout this course has needed so far. This lesson adds two more real primitives — st.container and st.expander — building a genuinely common layout shape, a card per item in a loop, and finds the real bug that shape runs into the first time it’s tried.

By the end of this lesson, you will be able to:

  • Build a bordered card layout with st.container(border=True) and st.expander
  • Explain, from a real error message, exactly why a repeated widget in a loop needs its own key=
  • Confirm the fix with AppTest, not just by running the app once and eyeballing it
  • Build a scrollable, fixed-height container, and a real confirm-before-delete dialog

Building Country Cards, Broken#

st.container(border=True) draws a real visible border around whatever’s rendered inside it — exactly what a “card” in a layout usually means. Five countries, five cards, laid out one per column. Running it turns up a real error:

A real, specific StreamlitDuplicateElementId — every st.button("Select") in the loop has the identical label and no other distinguishing argument, so Streamlit’s own internal ID for all five buttons ends up the same. The error message states the fix directly: a unique key per button.

Fixing It: A Unique key Per Iteration#

Five distinct keys, one per real country — China, India, United States, Indonesia, Brazil, the actual top 5 most populous countries in this dataset for 2007, confirmed rather than assumed. f"select_{row['country']}" builds a genuinely different string for each iteration, which is all key= needs to be: unique within the app, not meaningful beyond that.

A Scrollable Container for a Long List#

st.container accepts a real height, turning an otherwise-endless list into a fixed-size, scrollable box:

All 20 real rows genuinely exist in the app’s element tree — height=150 doesn’t remove any of them, it only constrains how much of the container is visible at once in the browser before a reader has to scroll. Twenty countries’ worth of cards, a long list of log lines, a running feed — this is the real primitive for any of those without the page itself growing without bound.

Confirming Before a Destructive Action#

st.dialog opens a real modal — the right primitive when an action shouldn’t happen on a single accidental click:

Both runs stay exception-free, but that’s a real, honest gap, not full confirmation: AppTest’s own element tree never shows the dialog’s own “Yes, delete” button appearing after the trigger click — no error, but no dialog content either. Confirmed with a real screenshot instead, the dialog genuinely opens in the browser; AppTest can confirm the code that builds a dialog runs without error, the same real limit already found for st.fragment and a data_editor cell edit, not that the dialog’s own content is reachable through it.

Practice Exercises#

Exercise 1: A duplicate that isn’t obvious#

  • Change broken_cards.py so each card’s button label includes the country name — st.button(f"Select {row['country']}") — with no explicit key=.
  • Predict, before running it, whether this still raises StreamlitDuplicateElementId — then confirm with AppTest, and explain in one sentence why a different label is enough to make each button’s auto-generated ID unique on its own.

Exercise 2: An expander that starts open#

  • Look up st.expander’s own expanded argument in Streamlit’s documentation.
  • Change one card’s expander to start open by default (expanded=True) and confirm with AppTest that at.exception stays empty — then explain, in one sentence, a real reason you might want exactly one card’s detail open by default and the rest closed (for example, the currently-selected country).

Hint

Exercise 1’s own answer is the deeper lesson here: Streamlit’s auto-generated ID is based on the widget’s type and its actual arguments together — two buttons only collide when every argument that feeds the ID is identical, not just the type.

Summary#

A card-per-country layout — st.columns, st.container(border=True), st.expander — hit a real, specific StreamlitDuplicateElementId the moment a repeated st.button("Select") had no unique key. The error message named the fix directly; adding key=f"select_{row['country']}" produced five distinct, working buttons, confirmed against the real top-5-by-population countries: China, India, the United States, Indonesia, Brazil. st.container(height=...) confirmed a real fixed-height, scrollable box holding all 20 real rows without growing the page. st.dialog was confirmed to run without exception, alongside an honest disclosure — like st.fragment before it — that AppTest can’t confirm the dialog’s own content is actually reachable, only a real screenshot could.

Key Concepts#

  • st.container(border=True) draws a real visible border — the layout primitive a “card” shape is usually built from.
  • A widget repeated in a loop needs its own unique key — Streamlit’s auto-generated ID is based on the widget’s type and arguments together, and identical arguments produce identical IDs.
  • A real error message often states the fix directly — StreamlitDuplicateElementId’s own message named key as the solution, not something to guess at.
  • AppTest catches this exact class of bug — confirmed here by checking at.exception before and after the fix, not by running the app once and hoping it looked right.
  • st.container(height=...) constrains visible height, not content — every row still exists; only how much shows without scrolling changes.
  • st.dialog is confirmed to run cleanly, but its content isn’t confirmable through AppTest — a real, disclosed gap, closed here with a real screenshot instead.
