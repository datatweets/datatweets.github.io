Welcome to Multi-Page Apps the Current Way#

Every app in this course has lived in one file. This lesson builds Streamlit’s real current pattern for more than one — st.Page and st.navigation — and confirms, programmatically, that switching pages actually changes what renders, not just what the sidebar link says.

By the end of this lesson, you will be able to:

  • Wrap separate page scripts with st.Page
  • Build a real sidebar navigation with st.navigation
  • Confirm a page switch with AppTest.switch_page, checking the app’s actual content changed
  • Drive real app state through the URL with st.query_params, so a filter can be shared as a link

Building Two Real Pages#

Each page below is a completely ordinary Streamlit script — nothing here would look out of place as a single-page app on its own. pages/ is just this lesson’s own choice of directory name (create it the normal way, mkdir pages, or let your editor create it the moment you save a file inside it) — not a special convention Streamlit requires: unlike the older pages/-folder-based multi-page system this lesson deliberately isn’t teaching, st.Page accepts a path to a script anywhere, under any folder name.

Wiring Them Together#

st.Page(path, title=..., icon=..., default=...) wraps one page script with real metadata Streamlit uses to build the navigation — default=True marks which page loads first. st.navigation([overview, data]) returns a navigation object; calling .run() on it executes whichever page is currently selected. app.py itself never imports pandas or touches gapminder.csv directly — it only orchestrates which page runs.

Confirming a Page Switch Is Real#

AppTest.from_file("app.py") runs the default page automatically — Overview, confirmed both by its title and its two metric elements. Switching pages, and confirming the switch genuinely changed the content rather than only a label:

Overview to Data, two metric elements to one dataframe — a genuinely different page ran, not the same content under a different sidebar highlight. at.switch_page(path) takes the identical path st.Page was given, confirming the two APIs share the same real notion of “which page.”

A Shareable Filter, Driven by the URL#

st.Page gives each page a real URL path. st.query_params goes one step further — real app state, readable and writable through the URL’s own query string, so a filter can be shared as a link, not just clicked into existence:

st.query_params.get("continent", "Africa") reads a real value straight out of the URL, defaulting to "Africa" when nothing’s there yet — confirmed empty before the click, query_params: {}. st.query_params["continent"] = "Asia" writes a real value back into the URL itself, confirmed here through AppTest’s own query_params accessor: a reader who bookmarks or shares that URL genuinely reopens the app with continent=Asia already applied, no click required on their end at all.

Practice Exercises#

Exercise 1: A hidden page#

  • Look up st.Page’s visibility argument in Streamlit’s documentation.
  • Add a third page, pages/debug.py, with visibility="hidden", and confirm with AppTest.switch_page("pages/debug.py") that the page still runs correctly even though it wouldn’t appear in the sidebar — a real, documented pattern for a page reachable only by direct link.

Exercise 2: Grouped navigation#

  • st.navigation accepts a dict instead of a list, grouping pages under section headers — look this up in Streamlit’s own documentation.
  • Rebuild app.py’s navigation as st.navigation({"Explore": [overview, data]}) and confirm with AppTest that both pages still switch to correctly, with at.exception staying empty.

Hint

Exercise 1’s own point is real and worth sitting with: a hidden page isn’t a secured page — visibility="hidden" only removes it from the sidebar, it doesn’t stop AppTest.switch_page or a reader who already knows the URL from reaching it directly.

Summary#

st.Page wrapped two real page scripts with a title and icon each; st.navigation([overview, data]) built a real sidebar navigation with no manual sidebar code written. AppTest.switch_page("pages/data.py") confirmed the switch was genuine, not cosmetic: the app’s title changed from "Overview" to "Data" and its element tree changed from two metrics to one dataframe — real, different content, not a relabeled link. st.query_params confirmed real app state can live in the URL itself — read with a default, written back with a plain assignment, both round-tripped correctly through AppTest’s own accessor.

Key Concepts#

  • st.Page(path, title=..., icon=..., default=...) wraps an ordinary script with navigation metadata — the page script itself needs no special code to participate.
  • st.navigation([...]).run() builds the sidebar and executes whichever page is selected — two steps, build then run, not one combined call.
  • AppTest.switch_page(path) genuinely re-runs the app with a different page’s content — confirmed by checking the title and element tree changed, not assumed from the method’s name.
  • This is Streamlit’s current multi-page pattern — distinct from the older pages/-folder-based convention this lesson deliberately didn’t teach.
  • st.query_params reads and writes real state through the URL — the same mechanism that makes a page’s own URL path work, applied to a single filter value instead of a whole page.

Why This Matters#

Every widget in this course has updated on every keystroke or click. Lesson 4 asks a genuinely different question — how do you batch several inputs into one single rerun instead — before the guided project splits world_explorer.py itself into real pages using exactly this lesson’s pattern.
