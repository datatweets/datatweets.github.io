Welcome to Session State#

Lesson 3 left a real, confirmed bug: a counter stuck at 1 no matter how many times you click it, because a plain variable is recreated on every rerun. st.session_state is Streamlit’s one answer to “I need this value to survive the next rerun on purpose” — this lesson uses it two different ways and confirms both with the same technique that caught the bug in the first place.

By the end of this lesson, you will be able to:

  • Initialize and update a value in st.session_state so it survives a rerun
  • Bind a widget’s value to st.session_state automatically with its key= argument
  • Run a real function the moment a widget is clicked, with on_click and args
  • Confirm a stateful app reaches the value you expect, using AppTest

Fixing the Counter#

if "count" not in st.session_state: runs on every rerun, but the assignment inside it — st.session_state.count = 0 — only actually happens the very first time, because st.session_state itself isn’t recreated on a rerun; it’s the one object Streamlit deliberately keeps alive for the whole time a reader has the app open. Every later rerun finds "count" already there and skips straight past the initialization. st.session_state.count += 1 then updates the surviving value directly, and st.rerun() triggers an immediate second rerun so the new count shows up right away, without waiting for the reader’s next click.

3, not 1 — the exact fix, confirmed the same way the bug was confirmed. st.session_state.count genuinely accumulated across three separate reruns, because it was never recreated between them.

A Simpler Pattern: key=#

Every widget accepts a key= argument, and giving one wires that widget’s value into st.session_state automatically — no manual assignment needed at all:

"name" exists in st.session_state even before anything is typed — the widget itself registers the key the moment it’s declared, starting at its own default (an empty string for st.text_input). No line in this script ever writes st.session_state.name = ... directly; key="name" is the entire wiring. This is the pattern to reach for whenever a widget’s own current value is all you need to persist — reserve the manual if "x" not in st.session_state pattern from the counter above for a value that isn’t a single widget’s own value (a running total, a list built up over several clicks, anything computed rather than typed).

A Third Pattern: on_click and on_change#

Both patterns above read a value after a rerun happens. A widget can also run a real Python function the moment it’s interacted with, via on_click (buttons) or on_change (every other widget) — useful when updating state is itself the whole point, not a side effect of reading a value:

on_click=log_click, args=("Kenya",) calls log_click("Kenya") the moment that specific button is clicked — before the script even reruns — confirmed here by reading st.session_state.click_log back directly and watching it genuinely grow with each click, not reset.

A real surprise turns up checking the same thing through the rendered st.write line instead of session_state directly:

at3.markdown[0].value is only 'Click log:' — the list never shows up there at all. st.write("Click log:", st.session_state.click_log) doesn’t concatenate its two arguments into one line of text; st.write’s own “magic” dispatch renders each argument through whatever widget fits it best — a plain string becomes markdown, but a list or dict becomes its own separate expandable json element:

Worth knowing before it surprises you the way it surprised this check: confirming a value passed to st.write alongside other arguments sometimes means reading a completely different element type than the one that seems obvious from the code.

The Trap Worth Naming, Not Demonstrating#

st.rerun(), called unconditionally — outside any if, at the top level of a script — creates a genuine infinite loop: the script finishes, immediately reruns itself, finishes, reruns itself, forever, pinning your CPU and never letting a browser render anything. This lesson doesn’t run that on purpose, for the obvious reason that it wouldn’t stop — but it’s worth being explicit about the shape of the mistake, since state_counter.py’s own st.rerun() avoids it by sitting inside if st.button(...), which is only ever True on the rerun where the button was actually clicked. st.rerun() is safe exactly when it’s conditional on something that isn’t true every single rerun; unconditional is the trap.

Practice Exercises#

Exercise 1: A running list, not a single value#

  • Build a small app: a text input plus an “Add” button that appends the typed text to a list stored in st.session_state.items (initialize it to [] the same not in way count was initialized).
  • Confirm with AppTest that adding three different values, one at a time, produces a list of all three — not a list that resets on every add the way the naive counter did.

Exercise 2: key= on a widget that also sets its own default#

  • Rewrite keyed_widget.py to also run if "name" not in st.session_state: st.session_state.name = "anonymous" before the st.text_input(...) line, and give that same st.text_input both value="Bob" and key="name" at once.
  • Run it with AppTest and check at.exception — is it empty, the same way it was for every working app so far in this course?
  • This one genuinely warns rather than raises: Streamlit logs "The widget with key ... was created with a default value but also had its value set via the Session State API" to the console, but at.exception stays empty and the app keeps running. Find that warning in the script’s own stderr output (subprocess.run(..., capture_output=True), not AppTest) and explain, from what you observe, why st.session_state[key] and a widget’s own value= argument are really two different ways of saying the same thing — and why Streamlit can’t always tell which one you meant to win.

Hint

AppTest’s own at.exception only catches something that stops the script running — a warning logged to the console isn’t that. Reach for a real subprocess.run capturing stderr when you need to see a warning AppTest alone won’t surface.

Summary#

st.session_state is the one object Streamlit deliberately keeps alive across reruns, and it fixed the broken counter in three lines: an if "count" not in st.session_state guard that only initializes once, then a direct update that survives every later rerun — confirmed reaching 3 after three clicks, not stuck at 1. A widget’s own key= argument does the identical job automatically for that one widget’s own value, confirmed with "name" in st.session_state reading True even before anything was typed. A third pattern, on_click/args, ran a real function the moment a button was clicked — confirmed correct through session_state directly, and confirmed to hold a real, worth-knowing surprise when checked through st.write’s own rendered output instead: a list argument renders as a separate json element, not appended text. st.rerun() called unconditionally creates a genuine infinite loop — named honestly here, not demonstrated, since it wouldn’t stop once started.

Key Concepts#

  • st.session_state survives reruns; a plain variable doesn’t — the entire fix from Lesson 3’s broken counter to this lesson’s working one.
  • if "x" not in st.session_state initializes exactly once, on the very first rerun, then gets skipped forever after.
  • A widget’s key= argument auto-binds its value into st.session_state — no manual assignment needed for a value that’s just “whatever this one widget currently holds.”
  • on_click/on_change run a real function at interaction time, before the rerun — confirmed by reading session_state directly, the most reliable way to check a callback actually ran.
  • st.write’s “magic” dispatch renders each argument through its own widget — a string becomes markdown, a list or dict becomes a separate json element, not appended text.
  • st.rerun() is safe when conditional, dangerous when unconditional — an unconditional call at a script’s top level never lets a rerun finish reaching a reader.

Why This Matters#

Every real app this course builds from here uses st.session_state for something — filters that should stay set while you explore a chart, a running total, which page of a multi-page app you’re on.
