Welcome to What Streamlit Is#

A Streamlit app is a plain Python script. Not a script that generates HTML, not a script that calls a web framework’s routing decorators — an ordinary .py file where a handful of function calls (st.title, st.write, st.button) each produce one piece of a web page, in the order you call them. This lesson installs Streamlit, runs a real app two different ways, and names precisely what makes the second way different.

By the end of this lesson, you will be able to:

  • Install Streamlit and run a real app with streamlit run
  • Explain, from actual console output, why running a Streamlit script directly with python doesn’t work the way running it with streamlit run does
  • Place Streamlit among the other ways to build a data-facing app, and state honestly what it trades away

Installing Streamlit#

One package, no separate frontend toolchain, no npm install. This course was verified against 1.62.0; if streamlit.__version__ reports something newer when you run this, that’s expected — Streamlit ships new minor versions often, and this course names the specific version anywhere a feature is new enough to matter.

Running It Two Different Ways#

The file is ordinary Python, so it’s tempting to just run it with python:

Real output, not an error — the script executed top to bottom without crashing, and st.title/st.write ran without raising. But nothing appeared in a browser, and Streamlit’s own warning names exactly why: app.py was never given a script run context, the piece of Streamlit that turns each st. call into a real update sent to a browser tab. python app.py runs the Python; it doesn’t start the part of Streamlit that talks to a browser at all.

streamlit run does both — it starts a real local web server, gives the script a script run context, and opens the app in your browser:

That’s the real startup banner, captured directly. localhost:8501 is Streamlit’s default port — the same one every app in this course uses unless a lesson says otherwise. Leave this running in a terminal and edit app.py while it’s up; Streamlit watches the file and offers to rerun automatically the moment you save, the development loop this whole course uses.

Where Streamlit Fits#

A Jupyter notebook is the fastest way to explore data yourself — cells, immediate output, no deployment story. It was never built to hand a working tool to someone who isn’t also running Jupyter. Flask and FastAPI go the other direction: full control over every route, every byte of HTML, at the cost of writing all of it yourself, in a second language (HTML/CSS/JavaScript) alongside Python. Streamlit sits in between on purpose — a real, interactive UI, written entirely in Python, in exchange for less control over exactly how that UI looks. st.button renders a button that already looks reasonable; it doesn’t take a style= argument the way an HTML tag would. That trade is exactly why a data scientist can ship a working tool in an afternoon, and exactly why a five-hundred-page marketing site would reach for something else.

Practice Exercises#

Exercise 1: A third piece of output#

  • Add one more line to app.py: st.write(1 + 1).
  • Run it with streamlit run app.py and confirm the number 2 appears as its own piece of output, in the position you added the line.
  • Predict, before checking: does st.write render a Python int differently than it renders a str? Confirm by comparing st.write(2) against st.write("2").

Exercise 2: Break it on purpose#

  • Add a line to app.py that references a variable you never defined (e.g. st.write(undefined_variable)).
  • Run streamlit run app.py and read what actually happens in the browser — does the app crash silently, or does it show you something?
  • Compare that to what python app.py does with the identical broken line, and explain the difference in one sentence.

Hint

Streamlit renders a Python exception directly in the app itself, as a real traceback in the page — it doesn’t fail silently, and it doesn’t just crash the terminal the way a bare script would.

Summary#

Streamlit installs with one pip install streamlit, and a real app is just Python — st.title and st.write render directly into a page, in call order, with no separate HTML file. Running that file with plain python executes the Python but produces no visible app, confirmed by Streamlit’s own printed warning; streamlit run is what actually starts a local server and gives the script the context it needs to reach a browser, confirmed by the real startup banner. Streamlit trades exact layout control for writing everything in Python — a real, deliberate trade-off, not a limitation to work around.

Key Concepts#

  • A Streamlit app is a plain .py file, no separate frontend file — the Python calls themselves are the layout.
  • python app.py runs the code but reaches no browser — only streamlit run gives the script a real connection to render into.
  • Streamlit prints its own exceptions directly in the app — a broken line shows up as a real traceback in the browser, not a silent failure.
  • Streamlit trades UI control for being pure Python — the right tool when writing HTML/CSS yourself isn’t the point.

Why This Matters#

Every app this course builds from here forward runs with streamlit run. Lesson 2 puts real interactive widgets on screen — text input, a button, layout with columns and a sidebar — the pieces a tool needs before it does anything with real data.
