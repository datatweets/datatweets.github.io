Welcome to Your First Interactive Widgets#

Lesson 1’s app never asked for anything — it only printed two fixed pieces of text. This lesson builds something that actually reacts: a small unit converter with a real number input, a real slider, and real layout. Every widget you add here is one you’ll reuse for the rest of this course.

By the end of this lesson, you will be able to:

  • Take a value from the reader with st.number_input and st.slider
  • Arrange widgets side by side with st.columns and tuck settings away in st.sidebar
  • Confirm a widget actually changes the app’s output, not just that the app runs without error

A Real Unit Converter#

Four new pieces, each doing one job: st.sidebar, a with block whose contents render in a collapsible panel on the left instead of the main page — the natural place for settings that aren’t the point of the app itself. st.slider(label, min, max, default) returns whichever number the reader currently has it set to. st.columns(2) returns two column objects; anything written inside one with col: block renders side by side with the other, not stacked. st.number_input is st.slider’s sibling for when a slider’s range doesn’t fit — a free-typed number instead of a dragged one.

Confirming the Widgets Actually Do Something#

A screenshot proves an app looks right. It doesn’t prove the numbers behind it are correct. streamlit.testing.v1.AppTest runs the real script and lets you change a widget’s value and rerun, exactly like a reader would, without a browser:

AppTest.from_file(...) needs a real path to the app it’s testing, and it’s worth knowing precisely what “relative” means here before it costs you a confusing error: a relative path is resolved against the location of the file calling AppTest.from_file, not against your current working directory the way open(...) or pd.read_csv(...) resolve one. In a script saved next to app.py, a bare "app.py" works fine; the moment your test code runs from anywhere else — a different script, a notebook, this course’s own automated verification — a bare filename can silently look in the wrong place. pathlib.Path("app.py").resolve(), converted to str(...), sidesteps the ambiguity entirely by handing AppTest an absolute path no matter where the calling code happens to live. Every AppTest.from_file(...) call in this course uses this pattern from here on, precisely so it never depends on where the surrounding code is run from.

at.sidebar.slider[0] — the slider lives under at.sidebar specifically because it was written inside a with st.sidebar: block; AppTest tracks not just which widgets exist but where. 1 mile = 1.60934 km, rounded to 2 decimal places by the slider’s own default value, prints exactly 1.61. Changing the number input and rerunning should change that text:

Both changed correctly — 5 × 1.60934 = 8.0467, rounded to 8.05 at 2 decimal places and shown in full at 4. .set_value(...) changes what the widget holds; .run() reruns the whole script with that new value, the same rerun Lesson 3 names precisely. Nothing here was checked by eye — every number printed above is the app’s own real output, read back after a real interaction.

Practice Exercises#

Exercise 1: A third column#

  • Add a third value to convert (pounds to kilograms, 1 lb = 0.453592 kg) in a third column, using st.columns(3) instead of st.columns(2).
  • Confirm with AppTest that changing the new number input changes only its own column’s text, not the miles-to-kilometers conversion in the other column.

Exercise 2: A slider with the wrong range#

  • Change the precision slider’s arguments to st.slider("Decimal places", 0, 4, 6) — a default value outside the slider’s own min/max range.
  • Run the app with streamlit run app.py and read what Streamlit actually does with a default outside the allowed range, rather than guessing.
  • Explain in one sentence why catching this with AppTest (checking at.exception right after .run()) is more useful in a real project than noticing it by eye in a browser.

Hint

AppTest raises the app’s own real exception into at.exception the moment something goes wrong during .run() — you don’t have to open a browser to know a widget’s own arguments are invalid.

Summary#

A real unit converter used four widgets — st.sidebar, st.slider, st.columns, st.number_input — each with one job: sidebar for settings that aren’t the point, columns for side-by-side layout, and two different ways to take a number from the reader. AppTest confirmed every widget actually changes the app’s output, not just that the app runs without crashing: setting the number input to 5 and the precision slider to 4 produced the exact conversion, 8.0467, read back from the app’s own real markdown output.

Key Concepts#

  • st.sidebar and st.columns are containers, not widgets — anything written inside one renders in that container instead of the main page’s default top-to-bottom stack.
  • A widget function always returns its current value — st.slider(...) isn’t a one-time setup call, it’s read every single time the script reruns.
  • AppTest interacts with a real app without a browser — .set_value(...) then .run() is the same action a reader’s click or drag produces.
  • A working screenshot and a correct app are two different claims — only reading the app’s own output after a real interaction confirms the second one.

Why This Matters#

Setting a widget’s value and calling .run() again is doing something worth naming precisely: it’s rerunning the entire script from the top, not patching one line. Lesson 3 names that mechanism directly and shows exactly what it means for values that aren’t stored in a widget.
