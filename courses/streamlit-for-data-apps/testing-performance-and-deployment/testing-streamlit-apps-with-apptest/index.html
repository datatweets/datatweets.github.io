Welcome to Testing Streamlit Apps with AppTest#

Every lesson in this course has run AppTest the same way — interactively, one script pasted into a scratch session. This lesson formalizes that into what it’s actually meant to be: a real, runnable pytest suite.

By the end of this lesson, you will be able to:

  • Write real pytest functions around AppTest, with plain assert statements
  • Run a full test suite with one command and read its real output
  • Recognize what a genuine test failure looks like, not just a passing one
  • Measure how much of the app your tests actually exercise with pytest-cov

Building the App Under Test#

A trimmed version of Module 4’s guided project — one page, kept small so this lesson’s tests stay easy to follow.

Writing Real Tests#

Three real tests, each one a plain function starting with test_, each one making a claim this course has already made informally, somewhere in an earlier lesson: the app doesn’t crash, the default metric is correct, changing the slider genuinely changes a downstream value. pathlib.Path(__file__).parent / "app.py" matters specifically here — it resolves relative to this test file’s own location, the same reasoning Module 1 Lesson 2 established for AppTest.from_file itself, applied one layer up.

Running the Suite for Real#

pytest test_app.py -v — the real command to run outside this course too — discovered all three test_-prefixed functions and ran each one, reporting PASSED for all three, return code: 0 confirming success the way any CI pipeline would check it.

A Real Failure, Shown Honestly#

A passing test suite is only reassuring if a wrong one would genuinely fail. Confirming that, rather than assuming it:

A genuine AssertionError, with pytest’s own real diff — - 999 / + 142, showing exactly what was expected versus what actually happened. return code: 1 is what a CI pipeline checks to know a build should fail. This test served its purpose by failing; it gets removed now, its job done:

How Much of the App Do These Tests Actually Exercise?#

Three passing tests is reassuring, but it doesn’t say how much of app.py, shared.py, and pages/overview.py those three tests actually touched. pytest-cov (pip install pytest-cov) answers that with real, measured numbers, not a guess:

A real, genuine 100% — every line in app.py, shared.py, and pages/overview.py ran at least once across these three tests, confirmed by pytest-cov tracking actual line execution, not estimated. This won’t always read 100% for a bigger app; the real value of running it isn’t the number itself, it’s the Missing column naming exactly which lines never ran during testing — a real, checkable list of what a passing test suite still isn’t proving.

Practice Exercises#

Exercise 1: A test for the year slider’s own bounds#

  • Write test_year_slider_bounds(): confirm at.slider[0].min equals 1952 and at.slider[0].max equals 2007 — Gapminder’s own real range, not assumed from memory.
  • Add it to test_app.py and confirm the full suite still reports 4 passed.

Exercise 2: A test that would have caught a real past bug#

  • This course found a real bug earlier — use_container_width triggering a deprecation warning instead of the current width="stretch". Write a test, test_no_deprecation_warnings(), that runs the app and asserts no warning message containing "deprecated" appears in captured output — look up pytest’s own caplog fixture to capture log records during a test.
  • Confirm this test passes against the current overview.py, which already uses width="stretch" throughout this course.

Hint

Exercise 2 is a real, useful pattern worth internalizing: a good regression test doesn’t just check current behavior is correct — it checks that a bug this course already found and fixed once can’t silently come back.

Summary#

Every scattered AppTest check this course has run interactively became one real pytest suite — three tests, confirmed genuinely passing with subprocess.run([sys.executable, "-m", "pytest", ...]), the real command any CI pipeline would run too. A fourth, deliberately wrong test was shown actually failing, with pytest’s own real AssertionError diff, return code: 1 — proof the suite would genuinely catch a wrong claim, not just pass by construction. pytest-cov closed the lesson with a real, measured number — 100% line coverage across app.py, shared.py, and pages/overview.py — confirming exactly how much of the app these three tests actually exercised, not assumed from them passing.

Key Concepts#

  • A pytest function starting with test_ and a plain assert is a real, complete test — no special framework beyond what this course’s own AppTest checks already were.
  • pathlib.Path(__file__).parent / "app.py" resolves relative to the test file’s own location — the same principle behind AppTest.from_file’s own path-resolution gotcha from Module 1.
  • A passing suite only means something if a wrong one would fail — confirmed here directly, not assumed.
  • return code: 0 versus 1 is what a real CI pipeline checks — the same signal subprocess.run(...).returncode exposes here.
  • pytest --cov measures real line coverage, not estimated — its Missing column names exactly which lines a passing suite still never ran.

Why This Matters#

A real test suite catches a broken app before a reader ever sees it. Lesson 2 turns to a different concern — an app that runs correctly but slowly — and the two real caching tools that fix it.
