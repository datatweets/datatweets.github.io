Welcome to Performance: Caching Strategy and Fragments#

Module 2 established st.cache_data and left one open question, in an exercise: what’s st.cache_resource actually for, and is the difference real? This lesson answers that with a real identity check, then covers st.fragment — honestly, including a real limit in what this course’s own testing tool can confirm about it.

By the end of this lesson, you will be able to:

  • Confirm, with a real identity check, that st.cache_data copies and st.cache_resource doesn’t
  • Use st.fragment to scope a rerun to part of a page
  • Recognize a genuine limit in what AppTest can verify, rather than assume it covers everything
  • Clear a cache on demand with .clear(), and explain a real timing subtlety in exactly when it takes effect

cache_data Copies. cache_resource Doesn’t.#

is checks Python object identity, not equal values — and it’s False. @st.cache_data hands back a fresh, independent copy every single call, even though the values are identical (.equals() confirms that separately). This is exactly right for a DataFrame: if one part of your app mutated the returned object, a copy means no other part of the app is affected.

True — the exact opposite. @st.cache_resource hands back the literal same object every call, never a copy. This is what makes it the right choice for something like a database connection, which genuinely can’t be duplicated the way a DataFrame safely can: there’s only one real connection, and every part of the app needs to share it.

st.fragment: Scoping a Rerun#

@st.fragment marks counter_fragment() as its own independently-rerunnable unit — in a real, live Streamlit app, clicking the button inside the fragment reruns only counter_fragment(), not the whole script above it. This is the real feature: a slow chart or an expensive computation elsewhere on the page doesn’t have to recompute just because a reader clicked a button inside an unrelated fragment.

A Real, Disclosed Limit: AppTest Can’t Prove This#

Confirming the actual partial-rerun claim, rather than assuming it, turns up a genuine limit:

Full script runs climbed to 2 — even though the click happened on a button defined inside the fragment. Checking the actual AppTest source confirms why: streamlit/testing/v1/element_tree.py, the module behind every at.button, at.slider, and every other accessor this course has used, has no fragment-tracking logic at all — AppTest.run() always performs a complete script rerun, regardless of which element triggered it. This is a real, confirmed gap, not a guess: st.fragment’s actual performance benefit — skipping the rest of the script — only shows up in a real, live-running app, where the browser and server genuinely coordinate a partial rerun. AppTest is the right tool to confirm a fragment’s code runs without exception; it is not the right tool to prove the performance claim that’s the entire reason to reach for st.fragment in the first place.

Clearing a Cache on Purpose#

ttl from Module 2 expires a cache entry automatically, after a real amount of time. Sometimes a cache needs to be cleared right now — a reader clicks “Refresh,” or an admin action changed the underlying data. Every cached function has a real .clear() method for exactly that:

A real, subtle, worth-knowing timing detail: clicking “Clear cache” doesn’t reload the data on that same rerun — load_data() already ran earlier in that script, before the button’s own if block ever executes, so it still returns the value it already had. The reload only happens on the next rerun after the clear — confirmed here as a genuine two-step sequence, not assumed to happen instantly.

Practice Exercises#

Exercise 1: Confirm cache_resource still returns fresh values on a new argument#

  • Add a min_year parameter to load_data_resource, cached, filtering by it before returning.
  • Confirm with AppTest that calling it with two different min_year values returns two objects that are not identical to each other (is is False between the two different-argument results) — the identity-preservation only applies to repeated calls with the same arguments, not across different ones.

Exercise 2: A real fragment structure check#

  • Confirm with at3.main, checking [el.type for el in at3.main], that the fragment’s own contents (its markdown and button) still appear in the element tree correctly, structured the same way they would without the @st.fragment decorator.
  • This confirms what AppTest can verify about a fragment — its content renders correctly — distinct from what this lesson already disclosed it can’t verify.

Hint

Exercise 1 is really testing the same principle Module 2 already established for @st.cache_data: a cache is scoped per set of arguments, and that scoping applies to cache_resource identically, not only to cache_data.

Summary#

A real identity check, df1 is df2, confirmed the difference this course had only described until now: @st.cache_data returns False — a fresh, independent copy every call — while @st.cache_resource returns True — the literal same object, correct for something that can’t safely be duplicated. st.fragment was covered with real, working code, alongside an honest, source-verified limit: AppTest’s own element_tree.py has no fragment-tracking machinery, so a fragment’s actual partial-rerun performance benefit can’t be demonstrated through this course’s testing tool — confirmed by checking that a fragment-internal button click still incremented a counter outside the fragment during an AppTest run. load_data.clear() closed the lesson, confirmed to genuinely clear the cache — but only from the next rerun onward, a real timing detail caught by checking the same run that calls .clear() separately from the one after it.

Key Concepts#

  • st.cache_data copies its return value on every call; st.cache_resource never does — confirmed with is, not assumed from the decorator names.
  • st.cache_resource is correct for objects that can’t be safely duplicated — a database connection, a loaded model — the same category Module 2’s own exercise pointed toward.
  • st.fragment scopes a rerun to one function in a live app — real, working code, confirmed to run without exception.
  • A tool that verifies code correctness doesn’t always verify a performance claim — AppTest confirms st.fragment’s code runs; it can’t confirm the partial-rerun benefit that’s the actual point of using it.
  • A cached function’s own .clear() empties the cache starting the next rerun, not the current one — confirmed by checking the exact run that calls it separately from the one after.
