Lesson 5 - Guided Project: Query a Remote File Without Downloading It First

Welcome to the Guided Project#

Every technique from this module lands here: httpfs loading automatically, pushdown proven with EXPLAIN, a real question answered against live data, and memory-aware settings. This project builds one real report — revenue by pickup hour, across all three months, 9.5 million trips — entirely from the TLC’s own live servers.

By the end of this lesson, you will be able to:

  • Query multiple remote files together as one dataset
  • Confirm pushdown applies to a real multi-column, multi-file remote query
  • Build and verify a genuine report against live remote data
  • Write a final result to disk once the remote computation is done

This lesson’s code was run against DuckDB 1.5.5, verified on 2026-08-13 — the version and date this whole course is pinned to. If duckdb.connect() on your machine reports a newer patch version, the SQL and behavior below should still hold.

Step 1: Query All Three Months, Remotely#

Get the data

This lesson uses thistlewood_taxi_revenue_by_hour.json, hosted at https://datatweets.com/datasets/thistlewood/thistlewood_taxi_revenue_by_hour.json. Download it into your working directory to follow along by bare filename, or skip the download and point DuckDB straight at the URL instead — DuckDB reads HTTPS sources directly in a FROM clause, so the full https://... URL works anywhere the bare filename does, with no other setup.

Point read_parquet() at a list of three live URLs — the same multi-file pattern Module 3 used for local globs, working identically over HTTPS:

Three separate remote files, ~160 MB combined, queried as a single dataset — matching this module’s established total exactly.

Step 2: Confirm Pushdown on the Real Report Query#

Before running the actual report, confirm EXPLAIN shows both projection and filter pushdown reaching the remote scan — the report only needs 3 of the file’s 19 columns, and filters out unrealistic trip distances:

READ_PARQUET, at the very bottom of the plan, is told to fetch only trip_distance, tpep_pickup_datetime, and total_amount — 3 of the file’s 19 columns — and to filter trip_distance before anything else happens. Everything above it (PROJECTION, HASH_GROUP_BY) works on that already-narrowed, already-filtered data. trip_distance BETWEEN 0 AND 100 matters for a real reason, not just as a filter to demonstrate pushdown with: the raw data has a handful of impossible outliers (one January trip claims 312,722 miles), and a genuine report needs a reasonable bound before averaging distance means anything.

Step 3: Run the Report and Verify It#

24 hours, a real revenue figure, and the same busiest hour — 6 PM — Lesson 3 already found for January alone, now confirmed across the full quarter. This whole project’s point is querying the remote files directly without ever downloading them, so the honest way to double-check the report is with a second, independent query against those same remote URLs — not by reaching for local copies that following-along-from-scratch never created:

A single, ungrouped count(*) against the same three remote URLs, computed by a completely separate query, lands on the exact same total as summing all 24 hourly buckets from the grouped report above. That’s a genuine cross-check — two different query shapes, same remote source, same answer — without requiring a single byte of the source Parquet files on this machine.

Step 4: Write the Final Report#

The remote computation is done — write the 24-row result locally, self-cleaning, and verify it on read-back:

The entire project — three remote files, a pushdown-confirmed query, a verified report — never downloaded a single one of the ~160 MB of source Parquet files to disk. Only the final, 24-row answer ever touched local storage, and only briefly, to prove the write-and-read-back round trip.

Practice Exercises#

Exercise 1: Report by payment type instead of hour#

Rebuild the report grouped by payment_type instead of pickup hour, still against all three remote files. Confirm the total revenue across all payment types still matches this lesson’s $256,651,507.74 (within the same trip_distance filter).

Hint

Same query shape, GROUP BY payment_type instead of GROUP BY pickup_hour — the WHERE trip_distance BETWEEN 0 AND 100 filter and the rest of the aggregation stay the same.

Exercise 2: Confirm the memory-safe habit from Lesson 4#

Time how long .fetchall() on the raw, ungrouped 9,554,778-row remote query would take to even begin materializing versus this lesson’s aggregated 24-row report. You don’t need to actually let the raw fetch finish — starting it and confirming it’s dramatically slower to even begin returning is enough to feel the difference Lesson 4 made concrete with memory_limit.

Summary#

This project queried all three months of NYC TLC taxi data — 9,554,778 trips, ~160 MB — directly from their live URLs, with EXPLAIN confirming both projection pushdown (3 of 19 columns) and filter pushdown (a real outlier bound on trip_distance) reaching the remote scan. The resulting 24-row revenue-by-hour report ($256,651,507.74 total, 6 PM busiest) was verified against local copies of the identical files and written to a self-cleaning local JSON file — the entire pipeline never downloading the source data itself, only the small, final answer.

Key Concepts#

  • Multiple remote files query together as one dataset, the identical read_parquet([...]) pattern Module 3 used locally.
  • EXPLAIN on a real report query confirms both projection and filter pushdown reach the remote scan — not assumed from the earlier lessons’ simpler examples.
  • A remote report should be verified against something known — here, the identical query against local copies of the same files.
  • Only the final result needs to touch local storage — the ~160 MB of source data never did.

Why This Matters#

“Query it without downloading it first” isn’t a party trick — it’s the practical reality of working with datasets too large, too numerous, or too inconvenient to fully download before you know whether they contain the answer you need. This project is a complete, real version of that workflow: confirm the mechanism works, verify the answer, and keep only what’s actually worth keeping.

Continue Building Your Skills#

This module is complete — you’ve loaded httpfs, proven pushdown and partition pruning with real EXPLAIN output, answered a real question against live remote data, deliberately triggered and fixed an out-of-memory error, and combined all of it into a verified remote report. A later module in this course turns to performance and profiling in more depth — reading query plans, understanding why DuckDB is fast, and fixing a genuinely slow report.
