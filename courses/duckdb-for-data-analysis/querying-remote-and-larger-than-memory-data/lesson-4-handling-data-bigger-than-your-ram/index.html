Welcome to Handling Data Bigger Than Your RAM#

Thistlewood Goods never came close to testing this — a few thousand rows fits in memory without anyone thinking about it. The 9.5 million rows across this module’s three taxi files are still small by real-world standards, but large enough to deliberately run out of memory on purpose, watch it fail honestly, and then fix it — the actual mechanics behind “larger than memory,” not just a claim about them.

By the end of this lesson, you will be able to:

  • Check and set memory_limit, threads, and preserve_insertion_order
  • Deliberately trigger a real out-of-memory error and read what it actually says
  • Apply the error’s own suggested fixes and watch the identical query succeed
  • Explain why keeping computation in SQL matters even more at this scale

This lesson’s code was run against DuckDB 1.5.5, verified on 2026-08-13 — the version and date this whole course is pinned to. If duckdb.connect() on your machine reports a newer patch version, the SQL and behavior below should still hold.

The Default Budget#

Every connection so far has used whatever memory_limit and threads DuckDB picked automatically — worth checking what those defaults actually are:

Your numbers will differ

DuckDB sizes memory_limit and threads from the machine it’s running on by default — roughly 80% of system RAM and one thread per CPU core. These exact figures are specific to the machine that ran this lesson; running it yourself will show your own machine’s defaults, which is expected, not a discrepancy.

Sort all three months by trip_distance under these defaults, as a baseline:

All 19 columns of 9,554,778 rows, fully sorted, in under 2 seconds — the default memory budget on this machine is generous enough that nothing about “larger than memory” shows up yet.

Deliberately Running Out of Memory#

Constrain memory_limit to something genuinely too small for this sort, and watch it actually fail:

A real, honest failure — 200MB genuinely isn’t enough for 10 parallel threads each holding working memory for a full 19-column sort. DuckDB doesn’t hang or silently return wrong results; it fails clearly, with concrete, actionable suggestions in the error message itself.

Applying the Fix#

Take the error message at its word — reduce threads and disable preserve_insertion_order — and run the identical sort again:

The identical sort, the identical 9,554,778 rows, correct — just roughly 10x slower, because DuckDB is now spilling intermediate sort data to temp_directory on disk instead of holding it all in RAM. That’s what “larger than memory” actually looks like in practice: not a crash, not wrong results, a real and honest performance cost in exchange for finishing correctly within a budget that genuinely doesn’t fit the working set.

Fewer threads sounds backwards — here’s why it helps

More threads usually means faster, not slower — but each thread doing a large sort needs its own working memory, so 10 parallel threads under a 200MB ceiling means roughly 20MB each, too little for any of them to make progress. 2 threads under the same ceiling get roughly 100MB each — still tight, but workable. The tradeoff is real: fewer threads means less parallelism, but enough memory per thread to actually finish.

Why This Matters Even at Thistlewood’s Own Scale#

None of this course’s earlier work with Thistlewood Goods needed any of this — a few thousand rows across a handful of columns comfortably fits in memory under any reasonable memory_limit. The discipline that does carry over from every earlier module: keep aggregation and filtering in SQL, and only pull a result into Python (Module 7), never a full dataset. .fetchall() on 9,554,778 raw rows would try to materialize the whole thing as Python objects — dramatically more memory-hungry than DuckDB’s own columnar representation of the identical data. This lesson’s sort stayed inside DuckDB the entire time; nothing tried to load 9.5 million rows into Python at once.

Practice Exercises#

Exercise 1: Find the smallest memory_limit that still succeeds#

Using threads=2 and preserve_insertion_order=false, try memory_limit values below 200MB (150MB, 100MB, 50MB) on the same three-file sort. Find roughly where it stops succeeding, and note how the runtime changes as the limit shrinks.

Hint

Same code as this lesson’s fix, just looping over a few memory_limit values and catching the OutOfMemoryException at whichever point it reappears.

Exercise 2: Confirm the fix works with a projection instead of a full sort#

Repeat the constrained-memory sort, but select only trip_distance and tpep_pickup_datetime instead of *. Confirm it completes faster than the full 19-column sort even under the same 200MB limit — narrower rows mean less working memory needed per thread.

Summary#

DuckDB’s default memory_limit and threads come from the machine it runs on — confirmed here, with an explicit note that those exact numbers are machine-specific. Constraining memory_limit to 200MB made a real 9.5-million-row, 19-column sort genuinely fail with OutOfMemoryException, whose own error message suggested the fix applied here: fewer threads and disabled insertion-order preservation. The identical sort then succeeded — same 9,554,778 rows, roughly 10x slower — by spilling to disk instead of crashing. Every earlier module’s discipline of keeping computation in SQL and pulling only results into Python (Module 7) is what keeps this from mattering even at Thistlewood’s own small scale.

Key Concepts#

  • memory_limit and threads default to values sized from the running machine — expect them to differ across machines.
  • A tight memory_limit can genuinely trigger OutOfMemoryException, not a metaphor — confirmed here on a real 9.5-million-row sort.
  • The error message’s own suggestions are real fixes, not boilerplate — reducing threads and disabling preserve_insertion_order made the identical query succeed.
  • DuckDB spills to temp_directory on disk when memory is tight — correct results, real and honest slowdown, not a crash.
  • Keep computation in SQL; pull only results into Python — the discipline that makes “larger than memory” a DuckDB-side concern instead of a Python-side crash.

Why This Matters#

Every real analytics environment has a memory ceiling somewhere, and a dataset eventually meets it. Knowing DuckDB fails clearly rather than silently, that its own error messages point at real fixes, and that those fixes trade a real, honest performance cost for correctness rather than crashing outright, is what makes working with genuinely large data a manageable engineering tradeoff instead of an unpredictable risk.
