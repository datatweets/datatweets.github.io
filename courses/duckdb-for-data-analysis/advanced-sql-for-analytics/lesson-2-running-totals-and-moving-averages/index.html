Welcome to Running Totals and Moving Averages#

Lesson 1’s window functions ranked rows relative to their whole partition. This lesson adds one more piece: a window frame — ROWS BETWEEN ... AND ... — that controls exactly which rows, relative to the current one, a window function looks at. That’s what turns SUM() OVER (...) into a running total, and AVG() OVER (...) into a moving average.

By the end of this lesson, you will be able to:

  • Build a running total with SUM() OVER (ORDER BY ... ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
  • Build a moving average with a fixed-size ROWS BETWEEN frame
  • Explain what a window frame controls, and how it differs from PARTITION BY
  • Recognize what happens at the start of a series, where a full-size frame isn’t yet available

This lesson’s code was run against DuckDB 1.5.5, verified on 2026-08-12 — the version and date this whole course is pinned to. If duckdb.connect() on your machine reports a newer patch version, the SQL and behavior below should still hold.

A Running Total, Month by Month#

Get the data

This lesson uses thistlewood_order_items.csv, and thistlewood_orders.csv, hosted at https://datatweets.com/datasets/thistlewood/thistlewood_order_items.csv, and https://datatweets.com/datasets/thistlewood/thistlewood_orders.csv. Download them into your working directory to follow along by bare filename, or skip the download and point DuckDB straight at the URLs instead — DuckDB reads HTTPS sources directly in a FROM clause, so the full https://... URL works anywhere the bare filename does, with no other setup.

Start with monthly revenue, then add a running total — the cumulative sum from the first row through the current one:

ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW means “every row from the very first one up through this one” — exactly a running total. Two numbers worth checking here: the March 2024 running total, 1,262,892.88, is this course’s established Q1 2024 revenue figure (Modules 3 and 5 both reconciled to it independently). And the very last row’s running total, 9,195,043.62, is this course’s grand total across all 24 months of data — the running total’s final value is always the same as a plain sum() over everything, which is a useful sanity check on its own.

The Window Frame, Explained#

ROWS BETWEEN <start> AND <end> controls which rows, relative to the current row, get included in the calculation:

  • UNBOUNDED PRECEDING — every row from the start of the partition.
  • CURRENT ROW — the row currently being computed.
  • N PRECEDING — exactly N rows before the current one.

PARTITION BY (Lesson 1) controls which group a row belongs to; the frame controls which rows within that group (or, with no PARTITION BY, within the whole result) a specific row’s calculation looks at. They answer different questions and can be combined — a running total per category, for example, would use both.

ROWS vs. RANGE: A Real Difference on Tied Dates#

Every frame in this lesson so far has used ROWS, but DuckDB also accepts RANGE in the same position — and the two genuinely disagree whenever the ORDER BY column has ties. monthly_revenue’s months are all distinct, which hides the difference completely, so check it against individual orders instead, where many orders can share the same order_date:

Two real differences show up immediately. First, rows_total doesn’t climb in the same order the rows are displayed in — ROWS only guarantees an order for ties if the ORDER BY itself resolves them, and order_date alone doesn’t (this is the exact same tiebreaker issue Lesson 1 raised for ROW_NUMBER(), showing up again here). Second, and more importantly: every order sharing September 4 landed on the identical range_total, 9,235.30 — the full day’s total — not a running value that climbs order by order. RANGE treats every row with the same ORDER BY value as arriving simultaneously: the frame for any one of them includes all of them, every time. ROWS never does that — it only ever looks at physical row position, tie or no tie.

Which one you actually want

ROWS is almost always the right default for a running total or moving average over time-series data — it processes rows one at a time regardless of ties, which is what “as of this exact row” usually means. Reach for RANGE specifically when ties should be treated as a single simultaneous group — a same-day running total that shouldn’t distinguish between orders placed on the same date is a legitimate use, but it’s an unusual enough need that reaching for RANGE should be a deliberate choice, not an accident. Leaving the frame off entirely — writing just OVER (ORDER BY order_date) with no ROWS/RANGE clause at all — silently behaves like RANGE, not ROWS, confirmed by rerunning this exact comparison with the frame clause removed: every tied September 4 row lands on 9,235.30 again, not a climbing per-order total. Naming ROWS or RANGE explicitly, every time, is what keeps that choice deliberate instead of accidental.

A Moving Average with a Fixed-Size Frame#

Swap UNBOUNDED PRECEDING for a fixed count — 2 PRECEDING AND CURRENT ROW is a 3-row window (the current row plus the 2 before it) that slides forward one row at a time:

January’s 3-month moving average is just January’s own revenue — there’s no “2 preceding” available yet. Confirm exactly what’s happening with a row count:

DuckDB doesn’t produce NULL or error when the requested frame extends past the start of the data — it simply uses however many rows actually exist: 1 row for January, 2 for February, and the full 3 starting in March. That’s worth knowing explicitly, since a moving average’s first few values are computed over a genuinely smaller window than the rest.

Practice Exercises#

Exercise 1: A 7-day moving average by exact day#

Group revenue by exact order_date (not truncated to month), and compute a 7-day moving average with ROWS BETWEEN 6 PRECEDING AND CURRENT ROW. Confirm the first 6 days have a frame smaller than 7 rows, the same way this lesson’s monthly example did for its first 2 months.

Hint

Same pattern as this lesson’s monthly_revenue, just GROUP BY order_date instead of date_trunc('month', order_date), and 6 PRECEDING instead of 2 PRECEDING.

Exercise 2: A running total per channel#

Add PARTITION BY channel to this lesson’s running-total query (you’ll need to bring channel into monthly_revenue first). Confirm each channel’s running total ends at that channel’s own full-period total, and that summing the three channels’ final running totals reproduces the $9,195,043.62 grand total.

Summary#

ROWS BETWEEN <start> AND <end> is a window frame — it controls which rows, relative to the current one, a window function includes. UNBOUNDED PRECEDING AND CURRENT ROW built a running total that reached exactly $9,195,043.62 by the final month, this course’s established grand total, with an intermediate checkpoint (March 2024’s 1,262,892.88) matching the Q1 anchor this course has reconciled to twice before. ROWS and RANGE were confirmed to genuinely disagree on tied dates — ROWS processes rows one at a time regardless of ties, RANGE gives every tied row the same, full-group value — and leaving the frame off entirely was confirmed to default to RANGE-like behavior, not ROWS. A fixed 2 PRECEDING AND CURRENT ROW frame built a 3-month moving average, and DuckDB was confirmed to use a smaller frame — not NULL — for the first two months, where a full 3-row window isn’t yet available.

Key Concepts#

  • A window frame (ROWS BETWEEN ...) controls which rows relative to the current row are included — separate from what PARTITION BY controls.
  • UNBOUNDED PRECEDING AND CURRENT ROW grows by one row each step — a running total.
  • ROWS and RANGE genuinely disagree on tied ORDER BY values — ROWS walks row by row regardless of ties; RANGE treats every tied row as arriving simultaneously, confirmed here on real same-date orders.
  • Omitting the frame clause entirely defaults to RANGE-like behavior, not ROWS — name one explicitly rather than relying on the default.
  • A fixed N PRECEDING AND CURRENT ROW slides a constant-size window — a moving average.
  • A frame that extends past the start of the data uses however many rows exist, not NULL — confirmed directly with count(*) OVER (...).

Why This Matters#

“How are we trending over time” and “what’s the cumulative total so far” are two of the most common real reporting questions, and both come directly from window frames — no self-join, no correlated subquery, no manual loop required. Knowing exactly what happens at the edges of a series (the first few rows of a moving average) is what keeps a trend line honest instead of silently misleading for its first few points.
