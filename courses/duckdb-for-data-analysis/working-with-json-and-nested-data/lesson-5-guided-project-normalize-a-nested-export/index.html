Welcome to the Guided Project#

Every skill from this module lands here: reading nested JSON directly, querying its structs and lists, flattening with UNNEST, and writing results back out. This project takes thistlewood_orders_nested.json — one denormalized file, orders with their line items bundled inside — and splits it into two proper tables: orders and order_items, the same normalized shape this course’s CSV sources have used since Module 2.

By the end of this lesson, you will be able to:

  • Split one nested source into two normalized tables in a single script
  • Reconcile both tables against independently-sourced canonical CSVs, exactly
  • Write a normalized result back out to JSON
  • Recognize normalization as the reverse of the convenience nesting provides for storage

This lesson’s code was run against DuckDB 1.5.5, verified on 2026-08-12 — the version and date this whole course is pinned to. If duckdb.connect() on your machine reports a newer patch version, the SQL and behavior below should still hold.

Step 1: Read the Nested Source#

Get the data

This lesson uses thistlewood_customers.csv, thistlewood_order_items.csv, thistlewood_order_items_normalized_export.json, thistlewood_orders.csv, thistlewood_orders_nested.json, and thistlewood_orders_normalized_export.json, hosted at https://datatweets.com/datasets/thistlewood/thistlewood_customers.csv, https://datatweets.com/datasets/thistlewood/thistlewood_order_items.csv, https://datatweets.com/datasets/thistlewood/thistlewood_order_items_normalized_export.json, https://datatweets.com/datasets/thistlewood/thistlewood_orders.csv, https://datatweets.com/datasets/thistlewood/thistlewood_orders_nested.json, and https://datatweets.com/datasets/thistlewood/thistlewood_orders_normalized_export.json. Download them into your working directory to follow along by bare filename, or skip the download and point DuckDB straight at the URLs instead — DuckDB reads HTTPS sources directly in a FROM clause, so the full https://... URL works anywhere the bare filename does, with no other setup.

Practice Exercises#

Exercise 1: Normalize to Parquet instead of JSON#

Repeat Step 4, but export orders_normalized and order_items_normalized to Parquet instead of JSON (Module 3’s COPY ... (FORMAT PARQUET)). Confirm the row counts still verify correctly on read-back.

Hint

Same COPY calls, swap (FORMAT JSON, ARRAY true) for (FORMAT PARQUET) and the file extensions for .parquet.

Exercise 2: Confirm customer_id values agree between JSON and CSV sources#

orders_normalized’s customer_id column came from the nested JSON; thistlewood_customers.csv has its own list of valid customer IDs. Join orders_normalized to thistlewood_customers.csv and confirm every one of the 792 orders matches a real customer — no NULLs from a failed join.

Summary#

This project split one nested, denormalized JSON export into the exact two-table normalized shape this course’s canonical CSV sources have always used: orders_normalized (792 rows, matching the canonical orders.csv row for row and column for column) and order_items_normalized (1892 rows, $1,262,892.88, matching the canonical CSV join exactly). Both were written back out to JSON and verified by reading them straight back. Every number in this project traces back to a source this course had already independently verified — nothing here was taken on faith.

Key Concepts#

  • Normalizing a nested source means splitting it into the flat, related tables it was compressed from — the opposite direction of the convenience nesting provides for storage or transport.
  • Reconcile completely, not just by count — comparing all 792 rows and all 5 columns of orders_normalized against the canonical CSV is a stronger check than comparing counts alone.
  • A format change (JSON to normalized tables, tables back to JSON) should never change the underlying numbers — every reconciliation in this project confirmed exactly that.
  • Writing a normalized result back out closes the loop — the same data, now available in whichever shape the next consumer actually needs.

Why This Matters#

Nested exports are a genuinely convenient way to move related data around — but almost nothing downstream wants to keep working with it that way. This project is a complete, small version of the real task: take a nested source, split it into tables you can actually join, filter, and aggregate the way this entire course has taught, and prove — not assume — that nothing was lost in the process.

Continue Building Your Skills#

This module is complete — you’ve read nested JSON directly, queried its structs and lists in place, flattened it with UNNEST, written results back out in both JSON shapes, reversed a flattening with list(struct_pack(...)), and normalized a full nested export into two verified tables. A later module in this course moves into more advanced SQL for analytics — window functions, running totals, and the kind of reporting a normalized table like the one you just built is made for.
