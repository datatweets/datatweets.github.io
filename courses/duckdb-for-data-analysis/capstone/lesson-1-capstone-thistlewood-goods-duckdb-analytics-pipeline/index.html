Welcome to the Capstone#

Every module in this course built one reusable piece: Module 3 taught you to read files directly and convert between formats. Module 5 taught you to flatten nested JSON into tables a join can use. Module 6 taught you window functions. Module 4 and Module 10 taught you to persist a result somewhere durable. This lesson runs all of it once, in order, against Thistlewood Goods’ first quarter of 2024 — the same quarter Module 1’s very first guided project already worked with.

By the end of this lesson, you will be able to:

  • Build a complete ingest-join-aggregate-export pipeline out of tools from five different modules
  • Ingest the same kind of data from three different file formats and reconcile them against each other
  • Verify each stage of a pipeline before moving to the next one, rather than checking only the final output
  • Recognize and fix a real, verified DuckDB behavior where tied rows after a GROUP BY aren’t returned in a guaranteed order

This lesson builds up one script, section by section, the same way you’d build it yourself: read the code in order, and each block uses tables the block before it created.

This lesson’s code was run against DuckDB 1.5.5, verified on 2026-08-14 — the version and date this whole course is pinned to. If duckdb.connect() on your machine reports a newer patch version, the SQL and behavior below should still hold.

Get the data

This capstone uses six files: thistlewood_customers.csv, thistlewood_products.csv, thistlewood_orders_nested.json, thistlewood_orders.csv, thistlewood_order_items.csv, and thistlewood_returns.csv — all hosted at https://datatweets.com/datasets/thistlewood/, e.g. https://datatweets.com/datasets/thistlewood/thistlewood_customers.csv. Download all six into your working directory to follow along by bare filename, or point DuckDB straight at each URL instead — no other setup required. There is no seventh file to fetch for the products Parquet table: this pipeline creates that one itself from thistlewood_products.csv in Stage 1, the same COPY ... TO ... (FORMAT PARQUET) conversion Module 3 taught.

Stage 1: Ingest — Three Formats, One Pipeline#

Thistlewood Goods’ data doesn’t arrive in one tidy format, and this capstone doesn’t pretend otherwise: the customer directory arrives as CSV, and the transactional order data arrives as nested JSON (the same export format Module 5 flattened). The product catalog arrives as CSV too — but a catalog like this one gets queried repeatedly across a pipeline, so this stage deliberately converts it to Parquet on the way in with COPY ... TO ... (FORMAT PARQUET) (Module 3’s pattern) before reading it back. That’s a genuinely common real-world move — standardize a small, frequently-reused reference table into a columnar format once, rather than re-parsing CSV text on every run — and it’s why this capstone can honestly claim to ingest CSV, JSON, and Parquet: one of the three is produced by the pipeline itself, not received that way.

Four tables, three source formats, no format-specific code beyond the read itself — read_json_auto(), read_parquet(), and a bare 'file.csv' in a FROM clause all hand back an ordinary DuckDB table, exactly as every earlier module in this course demonstrated one format at a time.

Verify the Ingest#

Three tables were derived — flattened from JSON, converted to Parquet — rather than read as-is. Confirm each one against a canonical source before building anything on top of them:

The nested JSON export reconstructs the exact same 792 orders and 1,892 line items as the normalized CSV tables — the same cross-check Module 5’s guided project already ran on this file, confirmed again here before this capstone relies on it. The Parquet round trip is even simpler to verify: same row count, because COPY ... TO ... (FORMAT PARQUET) changes nothing about the data, only its storage format.

Stage 2: SQL-Transform — Join Into One Fact Table#

Four tables become one: every order line item, enriched with its order’s date/channel/status, its customer’s segment/state, and its product’s name/category. A small diagnostic — the SQL equivalent of a habit this course has used informally since Module 2 — confirms each join step does what it’s supposed to before the next one runs:

Every enrichment join stays flat at 1,892 rows — customer_id and product_id are each genuinely unique keys on their respective dimension tables, so joining in customer and product details never duplicates a line item. Row-count discipline like this doesn’t prove the values are right, but it catches the single most common join mistake — a fan-out from a key that wasn’t as unique as assumed — the instant it happens, instead of silently inflating every total downstream.

Stage 3: Aggregate — The Questions a Stakeholder Would Ask#

With fact built and verified, answer four real business questions, scoped to completed orders where a revenue question is being asked — cancelled and pending orders never shipped, so they don’t belong in a revenue report.

Bath leads at $223,675.54, and the running total — Module 6’s ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW frame, applied here to this capstone’s own data — reaches exactly $1,171,856.43 by March, the same figure the plain category sum lands on independently.

A Ranking Gotcha: Ties After a GROUP BY#

Before ranking the top products by units sold, a real gotcha worth catching on purpose rather than by accident. Two products, P018 and P046, both sold exactly 125 units this quarter — an exact tie. Run the identical query eight times in a row on the same connection and compare:

Eight calls to the identical query, on the identical connection and data, and the order of the tied pairs (P018/P046 at 125, P042/P010 at 122) changes from run to run — runs 4 and 6 even disagree with each other on both pairs at once. This is a real, verified behavior of the installed DuckDB version (1.5.5): GROUP BY can execute in parallel across threads for speed, and its output row order isn’t guaranteed — an ORDER BY on a column with ties inherits whatever order the rows happened to arrive in, which can differ call to call. You might see True if you run this yourself; that would just mean the parallel execution happened to interleave the same way eight times, not that the underlying order is guaranteed.

The fix is the same one this course has already relied on for LIMIT/OFFSET queries: a deterministic tie-break — add a second sort key that has no ties, like product_id, so every tied group resolves the same way every time.

Revenue and units don’t have to agree on a leader

P018 sells more units-per-dollar than P046 — $31,558.75 in revenue for the same 125 units P046 sold for only $2,980.00. Ranking by units and ranking by revenue are different, both legitimate questions; a top-5-by-units list is not a top-5-by-revenue list, and this capstone deliberately asks the units question here to demonstrate the tie-break gotcha, not because units matter more than revenue.

Last, a return rate — how many completed orders had at least one item come back:

(order_id, product_id) is the join key thistlewood_returns.csv needs — the same composite-key pattern joining on order_id alone would risk a fan-out on, since one order can return more than one product.

Verify the Aggregate#

Two checks: does each breakdown sum back to the same total, and does that total match a number this course has already proven correct — twice, from two completely different angles?

This is the strongest kind of reconciliation this course uses: not “does this pipeline agree with itself,” but “does this pipeline, built today from JSON and Parquet sources this capstone ingested itself, land on the exact numbers three other modules already established from completely different files.” $1,171,856.43 across 733 completed orders is Module 1 Lesson 6’s own total, computed from a pre-joined flat CSV this capstone never touches. $1,262,892.88 across 792 all-status orders is the figure Modules 3, 5, and 6 have each already reconciled to independently — this capstone is the fourth. No new grand total was invented for this project; it connects to numbers the course already proved.

Stage 4: Export#

Persist the full fact table and its aggregates to a real local .duckdb file — Module 4’s persistence pattern — and write a short JSON report a stakeholder could read without running any code, the same idea Module 5 and Module 10 both already used.

ATTACH opens a second, named database alongside the in-memory one this whole pipeline has been building in — writing capstone_db.fact doesn’t touch the in-memory fact table at all, it copies its current contents into the on-disk file. DETACH closes it cleanly, the same lifetime discipline Module 4 established for every file-backed database this course has opened.

Verify the Round Trip#

Open the file back up in a completely fresh connection and confirm the data survived:

A brand-new connection, pointed at nothing but the file on disk, reproduces the identical row count and the identical $1,171,856.43 — the file genuinely holds what this pipeline built, not just a print statement’s claim that it does.

Stage 5: The Summary Report#

The last piece is the one a stakeholder actually reads — a short JSON file, and a printed summary built from numbers this lesson has now verified three separate times: once against each other, once against the round trip, and once against two other modules’ independently-established totals.

Five lines, and every number in them traces back through a verified step: ingest (three formats, each checked against a canonical source), join (every step flagged OK), aggregate (reconciled to two other modules’ totals, and a real tie-order gotcha caught and fixed), export (round-tripped back off disk), report. That chain is the entire point of this course — not any single trick, but the habit of checking before trusting, applied consistently enough that a report like this one can be handed to someone who’ll act on it.

Practice Exercises#

Exercise 1: Net-of-returns revenue#

Using fact filtered to completed orders with a return, compute the refund amount for returned line items (return_quantity * unit_price_at_sale, summed and rounded to 2 decimals — join thistlewood_returns.csv in for the return_quantity column) and subtract it from total_completed to get a net-of-returns figure. Report what percentage of gross revenue was refunded.

Hint

Join thistlewood_returns.csv to fact on (order_id, product_id), the same composite key this lesson’s return-rate calculation used, then sum return_quantity * unit_price_at_sale over just the matched rows.

Exercise 2: Confirm the pipeline is idempotent#

Run every code block on this page a second time in the same session. Confirm thistlewood_capstone.duckdb and thistlewood_capstone_report.json end up identical to the first run (the deterministic parts — everything except the “unfixed” tie-order demonstration, which is non-deterministic on purpose). Explain in one sentence why the os.path.exists(...) checks before each write make this safe to re-run.

Summary#

This capstone built one pipeline out of five modules’ tools: customers ingested from CSV, orders and order items flattened from nested JSON (Module 5’s pattern), and products converted to and read back from Parquet (Module 3’s pattern) — each source verified against a canonical file before use. A three-step join, checked at every stage, produced a 1,892-row fact table with zero unexpected row-count changes. Aggregation surfaced a real, verified DuckDB behavior — tied rows after a parallel GROUP BY aren’t returned in a guaranteed order — caught with eight repeated calls on the same connection and fixed with a deterministic tie-break key. The resulting $1,171,856.43 in completed-order revenue matched Module 1’s own total exactly, and the $1,262,892.88 all-status figure matched the number Modules 3, 5, and 6 had each already reconciled to independently. A local .duckdb file and a JSON report, written idempotently, round-tripped back to the identical numbers, closing with a five-line report any Thistlewood stakeholder could read.

Key Concepts#

  • A capstone reconciles to numbers the course already proved, not a new total invented for the occasion — this lesson’s two independent matches (Module 1, and Modules 3/5/6 together) are stronger evidence than any single new calculation could be on its own.
  • Ingesting the same business data from three formats is routine, not exotic — read_json_auto(), read_parquet(), and a bare CSV path all hand back an ordinary DuckDB table, verified here against each other before anything gets built on top of them.
  • A join-quality diagnostic should run on every step of a full pipeline, not just an isolated lesson example — check_join() flagged every step OK here, confirming the enrichment joins never fan out.
  • GROUP BY’s output order isn’t guaranteed under parallel execution, so an ORDER BY on a column with ties needs an explicit, unique tie-break key to be reproducible — verified directly on the installed DuckDB version across eight repeated calls on the same connection, not assumed.
  • ATTACH/DETACH persists an in-memory result to a real file without disturbing the in-memory session it came from — Module 4’s pattern, reused here unchanged.

Why This Matters#

An analytics pipeline is rarely one clever trick — it’s ingesting, joining, aggregating, and persisting, each done carefully and each checked before the next step builds on it. This lesson’s biggest number, $1,171,856.43, isn’t impressive because it’s large; it’s trustworthy because it was computed by four different lessons, from four different files and formats, and landed on the identical figure to the cent every time. That is the entire argument this course has been making from Module 1 onward: verify, don’t assume, and a result you can reconcile against something else you already know is worth infinitely more than one that merely looks plausible.
