Lesson 1 - Why DuckDB? Fast, Embedded SQL Analytics

Welcome to Why DuckDB?#

DuckDB is a SQL database, but it doesn’t behave like the database software you might already picture: no separate server process to start, no port to open, no connection string with a hostname in it. You import duckdb, create a connection, and run SQL — all inside the same process as whatever program you’re writing. That single design choice, called in-process (or embedded), shapes everything else about how DuckDB works and what it’s good at.

This lesson doesn’t just describe that design — it shows it. You’ll run a query and read DuckDB’s own execution plan to see its columnar engine at work, and you’ll run a small two-process experiment that shows exactly where DuckDB’s design draws a line: it is not built to be a shared, many-writer production database.

By the end of this lesson, you will be able to:

  • Explain what “in-process” (embedded) means for how DuckDB runs, in contrast to a database server
  • Read a DuckDB query plan and point to where its columnar engine only touches the columns a query needs
  • Describe, in plain terms, what “vectorized execution” means for how DuckDB processes data
  • State plainly what DuckDB is not built for, backed by an error message you produced yourself

You don’t need DuckDB installed yet to follow along — every code block below already shows its real output, so you can read this lesson before installing anything. If you’d rather install it now and run the code yourself, Lesson 3 walks through installing both the CLI and the Python package; either order works. Every code block below was run against DuckDB 1.5.5, verified on 2026-08-11 — the version and date this whole course is pinned to. DuckDB releases new versions regularly, so if duckdb --version on your machine reports something newer by the time you’re reading this, that’s expected, not a sign you did something wrong — the SQL and concepts here should still hold, though exact output formatting or a specific number (like the thread count in the next section) could differ slightly.

In-Process: No Server, No Port, No Separate Install to Run#

Open a terminal, start Python, and this is a complete DuckDB session:

Nothing was started in the background. There’s no duckdbd daemon listening on a port the way postgres or mysqld would be, and no separate step where you “start the database” before you can talk to it. duckdb.connect() loads DuckDB’s engine directly into your Python process’s own memory, and every query after that runs as a normal function call — not a network request to some other process.

This is what in-process (also called embedded) means: the database is the library you imported, not a service you talk to. A file path passed to connect() becomes a durable database file DuckDB reads and writes directly; leave it out, as above, and you get a private in-memory database that disappears when the process ends.

The DuckDB CLI is the same engine, just a different front door

The duckdb command-line tool you’ll install in Lesson 3 is not a client that talks to a server — it’s a small program that embeds the exact same in-process engine and gives you an interactive SQL prompt on top of it. There’s no server anywhere in this course.

Why This Matters for Local Analytics#

Being in-process removes an entire category of setup: no installing a database server, no managing its lifecycle, no network hop between your code and your data. For a data analysis task that runs on one machine — read a file, ask it questions, get an answer — that overhead was never buying you anything. This is the specific problem DuckDB is built to solve well: fast, local, single-user analytical queries, with nothing to install beyond the library itself.

Columnar: See It in a Query Plan#

Columnar means DuckDB stores and processes data organized by column, not by row. To see why that matters, run a query against Thistlewood Goods’ product catalog — 60 rows and 7 columns — and ask DuckDB to explain how it plans to execute it, instead of just running it.

Get the data

This lesson (and the next one) query thistlewood_products.csv, hosted at https://datatweets.com/datasets/thistlewood/thistlewood_products.csv. Download it into your working directory to run these queries by bare filename the way the examples below do, or skip the download entirely and point DuckDB straight at the URL — it reads HTTPS sources directly, so FROM 'https://datatweets.com/datasets/thistlewood/thistlewood_products.csv' works in place of FROM 'thistlewood_products.csv' with no other change.

Look at the bottom node, READ_CSV_AUTO, under Projections:. The query only asked for category and unit_price, and that is exactly what DuckDB reads — not the other five columns in thistlewood_products.csv (product_id, product_name, subcategory, cost, supplier). This is projection pushdown: DuckDB’s columnar, vectorized execution engine decides which columns a query touches before scanning any data, and skips the rest.

Worth being precise about what’s proven here, though: thistlewood_products.csv is a plain CSV file — text on disk, stored row by row, not columns. DuckDB’s CSV reader still supports projection pushdown, so it can skip parsing the five unneeded columns’ text into typed values, which is real, measurable work saved. But it still has to scan past those columns’ raw bytes on disk to find the ones it wants, since a row-oriented text file has no way to jump straight to one column the way a columnar file can. Module 3’s Parquet lesson shows the sharper version of this same idea: Parquet stores each column in its own contiguous block, so DuckDB can skip reading the bytes at all for a column a query never touches, not just skip parsing them. Both are genuinely “columnar” behavior — DuckDB’s own engine processes everything it reads in columns, regardless of the source format — but only Parquet’s on-disk storage is columnar. A row-oriented engine reading either file, CSV or Parquet, couldn’t selectively skip columns this way at all; reading a row means reading all of it.

The ~85 rows and ~136 rows figures in the plan are the query optimizer’s own estimates of how many rows will flow through each node, not actual counts — thistlewood_products.csv only has 60 rows total, so those numbers describe DuckDB’s cardinality guess before running the query, not what it found after running it.

On a 60-row file the difference is invisible. On a file with fifty columns and only two of them needed, columnar storage is the difference between reading a sliver of the file and reading all of it — and that gap only grows with the file’s size.

Vectorized: Whole Batches of Values at Once, Not One Row at a Time#

Columnar storage explains what DuckDB reads. Vectorized execution explains how it processes what it reads: instead of evaluating one row through the whole query pipeline before moving to the next, DuckDB processes data in batches — internally, chunks of up to 2,048 values at a time — running each operation (filter, comparison, aggregation) across a whole batch in tight, compiled code before moving to the next batch. That’s a fundamentally different execution shape from a loop that visits one row, does all its work, then visits the next.

You can see the effect of this, plus DuckDB’s parallelism, in how fast the grouped aggregation above runs, and how many threads it’s willing to use:

This machine gives DuckDB 10 threads to work with by default, and the grouped aggregation over thistlewood_products.csv finished in about 7 milliseconds. That number by itself doesn’t prove much on 60 rows — the point isn’t “DuckDB is fast,” which is a claim that needs a much bigger file to mean anything (a later module in this course measures that properly). The point is why it has room to be fast at all: vectorized batch processing plus multi-threaded execution, confirmed here directly from a running connection rather than assumed.

What DuckDB Is Not: A Test, Not a Guess#

Every design choice above trades away something, and it’s worth seeing exactly what, rather than taking a general “DuckDB isn’t for X” claim on faith. DuckDB allows many processes to read a database file at once, but only one process may hold it open for writing at a time. Prove it: start a Python process that opens a database file and keeps it open, then try to open the same file from a second, separate process while the first is still running.

The script below spawns two genuinely separate OS processes itself — process A, which opens the file and holds it, and process B, which tries to open the same file a second later while A is still holding it — so this is a real inter-process test, not a simulation of one, even though it’s one script you run once:

That error came from two separate Python processes touching the same file. It’s not a bug — it’s DuckDB enforcing the boundary its design implies: one process may hold a database file open for read-write at a time, with the lock held at the OS level. That’s not the same as “one write at a time” — within that single process, DuckDB itself supports multiple concurrent writer threads and multiple concurrent writes to the same connection or its cursors, using MVCC and optimistic concurrency control internally. The line this test actually draws is at the process boundary, not the thread boundary: a production system with many separate application server processes all trying to write to the same database file concurrently — the shape Postgres is built for — will hit this immediately. DuckDB was never designed to be that; it’s designed to be fast and simple for the far more common analytics shape, one process (yours), one file, at a time — however many threads that one process uses internally.

Not a multi-user production database

Keep this test in mind for Lesson 2: DuckDB is not a replacement for a server-based, multi-user OLTP database like Postgres in production settings with concurrent writers, connection pooling, and role-based access control. It’s a different tool for a different job — fast local and embedded analytics — not a smaller version of the same job.

Practice Exercises#

Exercise 1: Widen the projection#

With SELECT *, DuckDB has no columns it can safely skip, so the projection list should grow to include every column in thistlewood_products.csv — the columnar column-pruning trick only works when a query tells DuckDB which columns it actually needs.

Summary#

DuckDB is an in-process (embedded) SQL engine: no server, no port, just a library loaded directly into your program. It stores and scans data by column, which this lesson confirmed directly in a query plan — asking for two columns out of seven meant DuckDB only read two columns, not all seven. It processes those columns in vectorized batches across multiple threads, which is why even a tiny query finished in milliseconds with genuine parallelism behind it. And it draws a plain line: a two-process test showed DuckDB enforcing a single-writer lock at the OS level, the concrete shape of “not a multi-user production database.”

Key Concepts#

  • In-process / embedded — the database engine runs inside your own program’s process; there’s no separate server to start or connect to.
  • Columnar execution — DuckDB’s engine processes data in columns regardless of source format, so a query only needs to touch the columns it references (confirmed above via EXPLAIN’s Projections: list). Whether that also means skipping unread bytes on disk, not just skipping their parsing, depends on the storage format too — CSV is row-oriented text, so DuckDB still scans past a skipped column’s raw bytes; Parquet (Module 3) is columnar storage, so it skips reading those bytes entirely.
  • Vectorized execution — operations run against batches of values (up to 2,048 at a time) in compiled code, not row by row in an interpreted loop.
  • Single-writer process — DuckDB allows many concurrent readers of a database file, but only one process at a time may hold it open for writing, enforced at the OS file-lock level. That one process can still run multiple writer threads concurrently against the same file — the boundary this test proved is between processes, not between threads.

Why This Matters#

Knowing exactly what a tool trades away is what lets you use it well instead of fighting it. DuckDB’s in-process, columnar, vectorized design makes it fast for the analytics questions this course teaches — reading files, aggregating, joining — precisely because it isn’t trying to also be a shared, many-writer production database. That’s not a limitation to work around; it’s the same design decision that makes the rest of this course possible on your own laptop with nothing else installed.
