Welcome to the Guided Project#

Every skill from this module comes together here: connect to DuckDB, query a file directly with SQL, and produce a small, trustworthy summary of what’s in it. “Trustworthy” is doing real work in that sentence — this project’s rule, and the rule for every guided project in this course from here on, is that a number doesn’t count until you’ve confirmed it a second, independent way. A single query that returns a plausible-looking answer is not the same thing as a verified one.

By the end of this lesson, you will be able to:

  • Connect to DuckDB and inspect a file’s shape (rows, columns, schema) before analyzing it
  • Compute a small business summary — revenue, order counts, a category breakdown — with SQL
  • Cross-check an aggregate two independent ways and recognize when they agree
  • Explain why “the query ran without an error” is not the same standard as “the number is correct”

This project uses thistlewood_orders_flat.csv, the same file Lessons 4 and 5 already queried — Thistlewood Goods’ first quarter of 2024, one row per order line item.

This lesson’s code was run against DuckDB 1.5.5, verified on 2026-08-11 — the version and date this whole course is pinned to. If duckdb.connect() on your machine reports a newer patch version, the SQL and behavior below should still hold.

Step 1: Connect and Inspect#

Get the data

This lesson uses thistlewood_orders_flat.csv, hosted at https://datatweets.com/datasets/thistlewood/thistlewood_orders_flat.csv. Download it into your working directory to follow along by bare filename, or skip the download and point DuckDB straight at the URL instead — DuckDB reads HTTPS sources directly in a FROM clause, so the full https://... URL works anywhere the bare filename does, with no other setup.

Before asking any business question, confirm what you’re working with — how many rows, how many columns, and what type DuckDB inferred for each:

1,749 rows, 8 columns, and order_date correctly inferred as a DATE — the same shape Lesson 4 first showed. This step costs nothing and catches a wrong-file or wrong-delimiter mistake immediately, before you’ve built anything on top of it.

Step 2: A Small Business Summary#

Three numbers a stakeholder would actually ask for: total revenue, how many distinct orders that came from, and the date range covered.

$1,171,856.43 across 733 distinct orders, covering exactly the first quarter of 2024. That’s a complete-looking answer — but “looks complete” isn’t the bar this project holds itself to. The next step checks it.

Step 3: Verify Two Ways#

Check 1 — does the revenue total agree with its own breakdown? If you group the same data by category and add the pieces back up by hand, you should land on the same total revenue as Step 2’s single aggregate — if you don’t, one of the two queries has a bug. Be plain about what this check actually proves: both queries scan the identical file and the identical total column, just partitioned differently, so agreement here catches a GROUP BY or filter mistake — it would not catch a wrong file, a misread column, or a parsing error that corrupted every row the same way. That’s still a real, useful check; it’s just not an independent-of-the-data check the way Check 2 below is.

Eight category totals, added up by hand in Python (not by DuckDB’s sum), land on $1,171,856.43 — the same number Step 2’s single query reported, within a cent.

Why ‘within a cent’ instead of an exact ==

This check sums the unrounded per-category revenue in Python and compares it to Step 2’s rounded total with a small tolerance, rather than rounding each category to the cent first and checking exact equality. Rounding eight separate numbers and adding the rounded results can land a cent away from rounding one combined sum — not here, but the gap is real in general (floating-point cents drift depending on which values happen to round up or down), and a verification check that can fail on rounding noise alone, independent of whether the data is actually correct, isn’t testing what it claims to test.

Check 2 — does the distinct order count agree with a differently-shaped query? count(DISTINCT order_id) is one way to count unique orders; grouping by order_id first and counting the groups is a differently-shaped query that should give the identical answer if both are correct — with one genuine difference between them worth naming rather than glossing over: count(DISTINCT order_id) ignores NULL values entirely, while grouping by order_id would produce its own group for NULL if the column had any, which count(*) over those groups would then include. The two checks agreeing below isn’t just confirming the row count — it’s also confirming order_id has zero NULL values in this file, since a single NULL order ID would make these two numbers disagree by exactly one.

Both checks agree, and Check 2 confirms why they agree — zero null order IDs — rather than leaving that as an unstated assumption. That’s the actual habit this course is built around: a query that runs without an error has only cleared the lowest bar. A query whose answer you’ve confirmed a second, independently written way, understanding exactly what agreement does and doesn’t prove, has cleared a much higher one — and it’s the second bar every guided project in this course holds itself to.

Step 4: The Same Numbers, Explored in the UI#

Everything above ran through the Python API, but nothing about it is Python-specific — Lesson 5’s DuckDB UI reads the identical file the identical way. Opening a notebook there and running this lesson’s Step 2 query would show the same $1,171,856.43 and 733 orders in an interactive result grid, sortable and scrollable, with the same inferred schema in the side panel Lesson 5’s screenshots already showed. That’s worth remembering as this course moves on: the CLI, the Python API, and the UI are three ways to reach one engine, and a number confirmed in one is confirmed in all three.

Step 5: One More Question, For Later Modules#

Every number above answered a “how much” question. Close with a “how” question this course hasn’t touched yet, to preview what’s ahead: on average, how many line items does a single order contain, and does that match what a quick look at busiest single days suggests?

A typical order carries just under two and a half line items, and the three highest-revenue single days each had roughly 35 line items — consistent with each other, and a sensible-looking number for a business this size. This is exactly the kind of question a later module in this course formalizes properly: GROUP BY on something other than category, joins across Thistlewood Goods’ other tables instead of one pre-joined file, and the CTEs and subqueries this project’s verification queries already previewed informally.

Practice Exercises#

Exercise 1: A fourth verification#

Compute the average order value (total revenue divided by distinct order count) two ways: once as total_revenue / n_orders using Step 2’s numbers, and once as a fresh SQL query that first sums total per order_id, then averages those per-order sums directly in SQL (avg(...) over a subquery). Confirm both approaches land on the same number.

Hint

The subquery version looks like: SELECT avg(order_total) FROM (SELECT order_id, sum(total) AS order_total FROM 'thistlewood_orders_flat.csv' GROUP BY order_id). Compare it to total_revenue / n_orders computed in Python — division order matters less than making sure both paths are logically doing the same thing.

Exercise 2: Break a check on purpose#

Take Step 3’s Check 1 and deliberately introduce a bug: change the category GROUP BY query to filter out one category first (e.g., add WHERE category != 'Bath') before summing. Confirm the two totals now disagree, and explain in a sentence why that disagreement is exactly the signal this verification habit is designed to catch.

Summary#

This project connected to DuckDB, inspected thistlewood_orders_flat.csv’s shape, and computed a three-number business summary — $1,171,856.43 in revenue across 733 distinct orders over Q1 2024 — then held both headline numbers to a higher standard than “the query ran”: the revenue total was re-derived by hand-summing an independent category breakdown, and the order count was re-derived through a differently-shaped GROUP BY query. Both checks agreed exactly, which is what earned the numbers a place in the summary rather than just a print statement.

Key Concepts#

  • Schema inspection first — DESCRIBE and a row count before any analysis, catching a wrong file or malformed data early.
  • Independent verification — computing the same fact two structurally different ways and requiring agreement before trusting it.
  • One engine, three front doors — the CLI, Python API, and UI all answer an identical query identically, because they share the same underlying DuckDB engine.

Why This Matters#

“It ran without an error” and “the answer is correct” are different claims, and conflating them is one of the most common ways bad numbers reach a report. Every guided project in this course, starting here, holds itself to the second, harder standard — and that habit is worth more than any single SQL technique this module taught.
