Welcome to Your First Queries#

Every SQL database you’ve heard of before DuckDB probably needed a step before you could query anything: create a table, define its columns, load a file into it, and only then run SELECT. DuckDB skips that step entirely for a file on disk — you write the file’s path where you’d normally write a table name, and DuckDB reads it. This lesson puts that to work: one Thistlewood Goods file, four SQL clauses, and no CREATE TABLE anywhere.

By the end of this lesson, you will be able to:

  • Query a CSV file directly in a FROM clause, with no separate load or import step
  • Filter rows with WHERE, sort them with ORDER BY, and cap the result with LIMIT
  • Run the identical query from both the DuckDB CLI and the Python API
  • Inspect a file’s inferred schema before querying it, using DESCRIBE

This lesson’s code was run against DuckDB 1.5.5, verified on 2026-08-11 — the version and date this whole course is pinned to. If duckdb.connect() on your machine reports a newer patch version, the SQL and behavior below should still hold.

Point DuckDB at a File — No Load Step#

Get the data

This lesson uses thistlewood_orders_flat.csv — the same 1,749-row Thistlewood Goods file this module’s overview page introduced — hosted at https://datatweets.com/datasets/thistlewood/thistlewood_orders_flat.csv. Download it into your working directory to follow along by bare filename, or skip the download and point DuckDB straight at the URL instead — DuckDB reads HTTPS sources directly in a FROM clause, so the full https://... URL works anywhere the bare filename does, with no other setup.

Worth knowing up front, since this file recurs throughout the course: it’s pre-filtered to completed orders only — there’s no status column at all, and cancelled/pending orders were already excluded before this file was generated. Any total or revenue figure computed from it, here or in a later lesson, is a completed-orders figure, not an all-status one. The capstone (Module 11) draws that exact distinction explicitly, reconciling to both a completed-only total ($1,171,856.43, this file’s own grand total) and a separate all-status total from the raw order tables — worth remembering here so a number from this file is never mistaken for “every order, whatever its status.”

Start by asking what’s in the file before asking anything about its contents:

'thistlewood_orders_flat.csv' in that FROM clause is a quoted file path, not a table name — DuckDB recognizes the .csv extension and reads the file directly, inferring every column’s type from its contents (notice order_date came back as a proper DATE, not text, and quantity as BIGINT). There was no CREATE TABLE, no COPY ... FROM, no import wizard. The file is the thing you queried.

What’s happening under the hood

Writing a bare file path in a FROM clause is shorthand for read_csv_auto('thistlewood_orders_flat.csv'), the same function Lessons 1 and 2 called explicitly. EXPLAIN confirms it: both forms produce an identical READ_CSV_AUTO node in the query plan. Use whichever form reads more clearly — this course uses the short quoted-path form from here on, since most of its queries read one obvious file.

SELECT, WHERE, ORDER BY, LIMIT#

With the schema in hand, ask a concrete question: what were the five highest-value Bath-category line items in this file?

Four familiar clauses, doing exactly what they’d do against any table: WHERE category = 'Bath' keeps only Bath-category line items, ORDER BY total DESC, order_id puts the highest-value ones first (breaking ties by order_id — more on why in a moment), and LIMIT 5 caps the result. All five top rows turn out to be the same product — a Slate Gray Washcloth Set, ordered five units at a time — which is a reasonable check on the result: a single bulk order of an expensive item can dominate a “top line items” list, and now you know that’s exactly what happened here rather than five different high-value purchases.

Why order_id is in the ORDER BY: six rows tie exactly

Check how many Bath rows actually share the value 2209.8: SELECT count(*) FROM 'thistlewood_orders_flat.csv' WHERE category = 'Bath' AND total = 2209.8 returns 6 — one more than this query’s LIMIT 5 shows. ORDER BY total DESC alone has no way to prefer one of those six tied rows over another; DuckDB is free to return them in whatever order its query plan happens to produce, which is not guaranteed to be the same order on every run — especially with parallel execution across threads, the ordering among tied rows can vary. Adding order_id as a second sort key breaks the tie deterministically: now there’s exactly one correct answer for “the top 5,” not five out of an ambiguous six, and rerunning this exact query will always return the same five rows in the same order. Without a tiebreaker, the next section’s OFFSET query could return one of these six rows again, or skip one of them entirely — a real, silent pagination bug, not a hypothetical one.

The Same Query, From the CLI#

The CLI reads the same file the same way — no Python, no separate setup:

Same five rows, same order, same numbers — just formatted as a terminal table instead of a pandas DataFrame. If you’re working directly at a terminal on a file you just downloaded, the CLI gets you an answer with nothing to write beyond the SQL itself; if the result needs to feed into a larger Python program, the API version hands you a DataFrame you can keep working with.

Paging Through Results with OFFSET#

LIMIT on its own always starts from the top. Add OFFSET to skip a fixed number of rows first — useful for looking at results a page at a time, rather than only ever seeing the very top of a sorted list. Keep the same order_id tiebreaker from the section above — pagination is exactly where an undeterministic sort silently breaks, by repeating or skipping a row a reader already saw:

This skips the five rows the earlier query already returned — deterministically, because both queries now sort by the identical two keys — and shows the next three: the sixth and final 2209.8 row (O05263, the tied row LIMIT 5 correctly left out), then the two highest 2089.7 rows. LIMIT 3 OFFSET 5 is the same idea a paginated report or an API endpoint uses to serve “page 2,” and it now works correctly because there’s no ambiguity left in the sort — try removing , order_id from both queries and rerunning them a few times to see the tie problem the callout above described for yourself.

Practice Exercises#

Exercise 1: A different category, a different question#

Using either the CLI or Python, find the three highest-value line items in the Kitchen category instead of Bath. Change only the WHERE clause and the LIMIT.

Hint

Only two values need to change from this lesson’s query: 'Bath' becomes 'Kitchen', and LIMIT 5 becomes LIMIT 3. Everything else — the columns selected, the ORDER BY — stays the same.

Exercise 2: Filter on a date instead of a category#

Write a query against thistlewood_orders_flat.csv that keeps only rows where order_date >= '2024-03-01' (March 2024 onward), sorted by order_date ascending, showing the first 5 results. Notice that order_date behaves like a real date in the comparison — DuckDB inferred it as a DATE column, not text, so >= compares dates correctly rather than comparing strings character by character.

Summary#

DuckDB queries a file directly — a quoted path in a FROM clause is enough, with no CREATE TABLE and no separate load step, because it’s shorthand for read_csv_auto under the hood (confirmed identical via EXPLAIN). SELECT, WHERE, ORDER BY, and LIMIT all work exactly as they would against any table, and the CLI and Python API produced identical results from the identical query — the five same Bath-category line items, five units of the same product, sorted the same way.

Key Concepts#

  • File-as-table — a quoted file path in FROM reads that file directly; DuckDB infers its schema automatically.
  • DESCRIBE — reports a query’s (or file’s) inferred column names and types before you run anything against the data itself.
  • WHERE / ORDER BY / LIMIT — filter, sort, and cap a result set, working identically whether the source is a file or a table.

Why This Matters#

Most of the SQL you’ll write in this course looks exactly like the SQL you’d write against any database — the difference is what sits on the other side of FROM. Being able to point straight at a file and start asking real questions, with zero setup ceremony, is the specific convenience that makes DuckDB useful for the kind of one-off, exploratory analysis a full database server would slow down.
