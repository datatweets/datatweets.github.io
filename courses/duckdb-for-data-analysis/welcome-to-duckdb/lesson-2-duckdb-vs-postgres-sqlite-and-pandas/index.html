Welcome to Where DuckDB Fits#

Lesson 1 showed what DuckDB is: an in-process, columnar, vectorized SQL engine. On its own, that description doesn’t tell you when to reach for it instead of — or alongside — tools you may already use. This lesson places DuckDB next to three tools it gets compared to constantly: SQLite, Postgres, and pandas. Each one is genuinely good at what it was built for, and none of them is simply a worse version of DuckDB. The goal here is a clear, honest map, not a sales pitch.

By the end of this lesson, you will be able to:

  • Explain the difference between SQLite and DuckDB, two embedded databases shaped for opposite workloads
  • Describe why Postgres runs as a server, and what that buys you that an embedded database can’t
  • Contrast pandas’ DataFrame-first model with DuckDB’s SQL-directly-on-a-file model, with a runnable example of both
  • Pick the right tool for a given task, rather than defaulting to whichever one you already know

This lesson’s DuckDB and pandas code assumes the setup Lesson 3 walks through (pip install duckdb and pip install pandas, respectively) — only the SQLite example needs nothing extra, since sqlite3 ships in Python’s standard library. You can still read every example below without installing anything; just know the DuckDB-vs-pandas comparison later in this lesson needs both packages if you want to run it yourself.

This lesson’s code was run against DuckDB 1.5.5, verified on 2026-08-11 — the version and date this whole course is pinned to. If duckdb.connect() on your machine reports a newer patch version, the SQL and behavior below should still hold.

SQLite: Also Embedded, Built for the Opposite Shape#

Get the data

This lesson uses thistlewood_products.csv, hosted at https://datatweets.com/datasets/thistlewood/thistlewood_products.csv. Download it into your working directory to follow along by bare filename, or skip the download and point DuckDB straight at the URL instead — DuckDB reads HTTPS sources directly in a FROM clause, so the full https://... URL works anywhere the bare filename does, with no other setup.

SQLite is the tool DuckDB gets compared to first, because they share the exact property Lesson 1 covered: both are in-process — no server, just a library loaded into your program. Python even ships SQLite’s driver in its standard library, so there’s nothing to install to try it:

EXPLAIN QUERY PLAN reports a plain SCAN products — SQLite reads whole rows from its table and checks each one against the filter as it goes, because it’s a row-oriented engine. There’s no “columns projected” detail the way DuckDB’s plan showed in Lesson 1, because that concept doesn’t apply the same way to a row store: reading a row means reading all of it.

That’s not a shortcoming — it’s the right shape for what SQLite is usually asked to do: store and retrieve individual records reliably, one at a time, from something like a mobile app’s local storage, a browser’s local database, or a small application’s config file. Fast, transactional, single-row reads and writes are SQLite’s specialty — the same OLTP (online transaction processing) shape Lesson 1’s lock demo showed DuckDB deliberately isn’t optimized for. DuckDB’s columnar, vectorized design instead targets OLAP (online analytical processing): scanning and aggregating across millions of rows at once, exactly the opposite emphasis.

Same category, different job

Both SQLite and DuckDB are embedded, single-file, server-free databases — that similarity is worth remembering. What differs is what’s fast: SQLite for many small transactional reads/writes to individual rows, DuckDB for scanning and aggregating across whole columns. Picking between them is a question of workload shape, not which one is “better.”

Postgres: When You Need a Server#

Postgres is a different kind of tool altogether: a server-based, multi-user database. Instead of loading a library into your program, you run postgres as its own long-lived process — usually on a separate machine or container — and every application that wants to use it connects to it over the network, with authentication, connection pooling, and (critically) support for many clients writing to the same database at the same time.

That last point is exactly what Lesson 1’s lock experiment showed DuckDB does not do — a second process trying to open the same DuckDB file while another held it open got a hard IOException. Postgres is built precisely for the case DuckDB refuses: dozens or hundreds of application servers, all connected at once, all reading and writing concurrently, coordinated by the server process itself. That coordination has a cost — a server to run, patch, and scale — which is exactly the cost DuckDB’s embedded design avoids for workloads that don’t need it.

This course doesn’t re-teach Postgres or general SQL from scratch — the site’s own SQL & Databases course covers exactly that in depth, including running and administering Postgres itself. This course teaches the SQL it needs as it goes, and links back to specific lessons there later in this course for readers who want more.

pandas: DataFrames First, SQL Optional#

pandas is neither embedded nor server-based in the database sense — it’s a Python library built around one core object, the DataFrame, held entirely in memory as regular Python/NumPy data. There’s no SQL involved unless you bring in an extra tool: you load a file into a DataFrame first, and every question after that is answered with DataFrame methods like .groupby(), not SELECT statements.

See the difference directly — the same question, average product price by category, asked pandas’ way and DuckDB’s way:

Same answer, two different ergonomics. pandas’ read_csv call produces a DataFrame — a full, independent, in-memory copy of the file’s data — that then exists as its own Python object for as long as you keep it around. DuckDB’s read_csv_auto call inside the SQL string isn’t a separate load step at all: it’s part of the query itself, and DuckDB decides how much of the file it needs to touch to answer it (Lesson 1’s Projections: list showed exactly this). That distinction barely matters on a 60-row file — it matters enormously once a file is bigger than your computer’s memory, which a later module in this course covers directly.

None of this makes pandas the wrong tool. If your work is already DataFrame-shaped — feeding a machine learning library, doing row-by-row transformations pandas expresses well — SQL isn’t obviously better. DuckDB and pandas aren’t even mutually exclusive: DuckDB can query a pandas DataFrame directly, and a later module in this course covers that combination in depth.

Putting the Four Together#

This course’s own later modules teach SQL fundamentals and advanced analytics using DuckDB, and link out to the site’s SQL & Databases course at the exact matching lessons there for anyone who wants a deeper, Postgres-specific treatment of the same ideas. Nothing in this course positions DuckDB as a reason to skip learning Postgres or SQLite properly if your work needs them — it’s here because a huge share of everyday data analysis is neither “build a production multi-user app” nor “everything already fits comfortably as a DataFrame,” and that middle ground is exactly where DuckDB is strongest.

Practice Exercises#

Exercise 1: Run SQLite’s plan on a filtered, unindexed query#

Using the SQLite example above, insert two more product rows (any values) into the same in-memory table, then rerun EXPLAIN QUERY PLAN with a WHERE unit_price > 50 filter instead of the category filter. Confirm the plan still reports a plain table SCAN (SQLite has no index on unit_price in this example, so it must check every row).

Hint

Without a CREATE INDEX statement, SQLite can’t skip any rows before filtering — the “SCAN products” you saw earlier will look the same, just with a different filter expression.

Exercise 2: Time the pandas vs. DuckDB read#

Using Python’s time.perf_counter(), wrap the pd.read_csv(...).groupby(...) call and the con.execute(...).df() call from this lesson’s comparison, each in its own timer. Run both a few times and report what you see. Resist the urge to draw a “DuckDB is faster” conclusion from this alone — the file is only 60 rows, far too small for a timing difference here to mean anything; a later module measures this properly on data that’s big enough to matter.

Summary#

DuckDB, SQLite, Postgres, and pandas solve four different problems, and knowing which is which prevents reaching for the wrong one. SQLite and DuckDB are both embedded — no server — but SQLite’s row-oriented engine (confirmed via its own EXPLAIN QUERY PLAN) is shaped for fast individual-row transactions, while DuckDB’s columnar engine is shaped for scanning and aggregating across whole columns. Postgres trades the embedded model for a server, built specifically for many concurrent writers — the exact case Lesson 1’s lock error showed DuckDB isn’t built for. pandas isn’t a database at all: it’s an in-memory DataFrame library you load data into explicitly, rather than a SQL engine you query a file with directly.

Key Concepts#

  • OLTP vs. OLAP — OLTP (SQLite, Postgres) optimizes for many small transactional reads/writes; OLAP (DuckDB) optimizes for scanning and aggregating large amounts of data.
  • Embedded vs. server-based — SQLite and DuckDB run inside your process; Postgres runs as its own long-lived process other programs connect to over a network.
  • DataFrame-first vs. SQL-directly-on-a-file — pandas loads data into an in-memory object before you can query it; DuckDB’s SQL can read a file as part of the query itself.

Why This Matters#

Every one of these tools shows up in everyday data work, often on the same team in the same week. Knowing that SQLite, Postgres, DuckDB, and pandas are answers to different questions — not four competing answers to the same question — is what lets you pick correctly instead of by habit, and it’s exactly the judgment this course is building toward.
