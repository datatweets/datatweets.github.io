Welcome to CTEs and Subqueries#

Some questions can’t be answered in one flat query — “which products cost more than average” needs the average computed first; “which customers spent more than their own segment’s typical customer” needs a whole intermediate table of per-customer numbers before the comparison can even start. This lesson covers two tools for exactly that: a subquery, a query nested inside another query, and a CTE (common table expression), a named, temporary result you build with WITH and then query like a table.

By the end of this lesson, you will be able to:

  • Use a scalar subquery to compare every row against a single computed value
  • Use EXISTS with a correlated subquery to filter rows based on whether a related row exists elsewhere
  • Build a WITH CTE and query it like a table
  • Chain more than one CTE together to answer a question that needs two stages of aggregation
  • Use DuckDB’s own SQL extensions – EXCLUDE, GROUP BY ALL, QUALIFY, COLUMNS(*), FROM-first syntax, and SUMMARIZE – to write less standard SQL for patterns that come up constantly

This lesson’s code was run against DuckDB 1.5.5, verified on 2026-08-12 — the version and date this whole course is pinned to. If duckdb.connect() on your machine reports a newer patch version, the SQL and behavior below should still hold.

Scalar Subqueries: Compare Against a Single Computed Value#

A scalar subquery returns exactly one value, and can be used anywhere a single value is expected — including inside a WHERE clause, compared against a column:

(SELECT avg(unit_price) FROM products) runs first, produces one number ($216.91), and the outer query then compares every row’s unit_price against that single value — 28 of the 60 products clear it. This is exactly equivalent to computing avg_price in Python first (as the first line above does, for display) and writing WHERE unit_price > 216.91 — the subquery form just keeps the calculation inside the SQL itself, recomputed fresh every time the query runs rather than hardcoded.

Get the data

Every file this lesson uses was already introduced earlier in this module — thistlewood_products.csv and thistlewood_customers.csv in Lesson 1, thistlewood_orders.csv and thistlewood_order_items.csv in Lesson 3, and thistlewood_returns.csv in Lesson 4. All five are hosted at https://datatweets.com/datasets/thistlewood/ and readable directly by URL.

EXISTS: Filtering on Whether a Related Row Exists#

EXISTS answers a yes/no question per row: does at least one matching row exist somewhere else? Which customers have made at least one return?

The subquery inside EXISTS is correlated — notice WHERE o.customer_id = c.customer_id references c, the outer query’s table alias. DuckDB runs that inner check once per customer, and EXISTS returns true the moment it finds even one matching row, without caring how many matches there actually are. That’s different from JOIN-then-count, which would need DISTINCT to avoid counting a customer more than once if they had multiple returns; EXISTS is naturally a yes/no test and never double-counts.

WITH: Naming a Query So You Can Build On It#

A CTE gives a subquery a name and lets you query it like a table, using WITH <name> AS (<query>) before the main SELECT. Build one that computes total revenue per customer, then rank the top spenders:

customer_revenue is a three-table JOIN and GROUP BY, packaged behind a name — the outer SELECT * FROM customer_revenue ORDER BY revenue DESC LIMIT 5 reads no differently than querying a real table. This is the CTE’s main value over a raw subquery: naming a multi-step calculation makes the query that uses it far more readable, and (as the next section shows) lets you reference it more than once.

A CTE only exists for the query that defines it

customer_revenue isn’t a real table — it’s not saved anywhere, and a separate query run afterward can’t reference it. It exists only for the duration of the single WITH ... SELECT statement that defines it, recomputed every time that statement runs.

Chaining Two CTEs Together#

A single WITH can define more than one CTE, each one able to reference an earlier one — useful when a question genuinely needs two stages of aggregation. Which customers spend more than their own segment’s (retail or wholesale) average customer?

segment_avg is built directly on top of customer_revenue — a CTE that references an earlier CTE in the same WITH — and the final SELECT then joins the two together, comparing each customer’s own revenue against their segment’s average rather than the whole company’s flat average. 86 of the 180 customers clear their own segment’s bar; each segment only has two possible averages (retail and wholesale), so this is a genuinely different, more targeted comparison than the single-number scalar subquery earlier in this lesson.

DuckDB’s Friendly SQL: Syntax You Won’t Find in Postgres#

Everything so far in this module is standard SQL — it would run unchanged against Postgres or SQLite. DuckDB also adds a set of genuinely non-standard extensions on top, all aimed at the same thing: less typing for patterns that come up constantly in real analysis. None of it is required — the standard forms above always still work — but it’s worth knowing, because it’s the syntax most likely to make DuckDB feel different from every other SQL database you’ve used.

SELECT * EXCLUDE (...) — every column except the ones named, without listing the rest by hand:

SELECT * REPLACE (...) — every column as-is, except one or more transformed in place:

GROUP BY ALL / ORDER BY ALL — group or sort by every non-aggregated column in the SELECT list, without repeating each column name a second time:

QUALIFY — filters on a window function’s result directly, the way HAVING filters an aggregate, without wrapping the query in a subquery just to reference the window column in a WHERE:

Eight rows back — the single priciest product in each of the 8 categories — with no CTE or subquery needed to get there.

COLUMNS(*) — apply the same expression to every matching column at once, instead of writing it out per column:

One min(), applied to both remaining numeric columns (unit_price, cost) in a single pass — the alternative is min(unit_price), min(cost) written out by hand, which stops scaling once a table has a dozen numeric columns instead of two.

FROM table SELECT ... — FROM first, SELECT optional. If all you want is every column of a table, SELECT isn’t even required:

SUMMARIZE — one statement, a full profile of every column in a table: type, min, max, approximate distinct count, null percentage, and more, without writing a single aggregate by hand. This is often the very first thing worth running against a table you haven’t seen before — including back in Module 1, on the first CSV this course ever queried:

That one row already answers several real questions about product_id without a single SELECT count() or SELECT min() written by hand: it’s text, it ranges from 'P001' to 'P060', there are 67 approximately-distinct values in a 60-row table (an estimate, not an exact count — worth knowing SUMMARIZE trades precision for speed), and 0.00% of it is NULL.

None of this is required

Every query earlier in this module — and everywhere else in this course — uses standard SQL on purpose, so nothing here depends on knowing these extensions. Reach for them once the standard form starts feeling repetitive; EXCLUDE, GROUP BY ALL, and SUMMARIZE in particular are worth adopting early, since they save real typing on patterns you’ll hit in nearly every session.

Practice Exercises#

Exercise 1: A subquery for below-average products#

Adapt this lesson’s scalar-subquery example to find products priced below average instead of above. How many of the 60 products fall below the $216.91 average? (It won’t be exactly 32 — averages aren’t medians, and there’s no guarantee the split is even.)

Hint

Change only the comparison operator: WHERE unit_price < (SELECT avg(unit_price) FROM products). The count of “below average” plus “above average” plus any products priced at exactly the average (unlikely here, but check with =) should add up to 60.

Exercise 2: EXISTS the other way around#

Write a query using NOT EXISTS (the same correlated subquery from this lesson’s EXISTS example, negated) to find customers who have never made a return. Confirm the count matches 180 - 158 = 22 from this lesson’s numbers.

Summary#

A scalar subquery returns one value and can be compared against a column directly, as shown filtering products against its own average price. EXISTS with a correlated subquery answers a yes/no question per row — does a matching row exist elsewhere — confirmed here finding 158 of 180 customers with at least one return, without any risk of double-counting. A WITH CTE names a query so it can be read (and reused) like a table, and chaining two CTEs together let this lesson compare each customer against their own segment’s average revenue, rather than one flat company-wide number — a genuinely more targeted question than either single-table example could answer alone. Closing the module, DuckDB’s own SQL extensions — EXCLUDE/REPLACE, GROUP BY ALL/ORDER BY ALL, QUALIFY, COLUMNS(*), FROM-first syntax, and SUMMARIZE — showed the syntax that makes DuckDB feel genuinely different from a standard SQL database, confirmed identical to their standard-SQL equivalents wherever a direct comparison was possible.

Key Concepts#

  • Scalar subquery — a nested query returning exactly one value, usable anywhere a single value is expected.
  • Correlated subquery — a subquery that references a column from the outer query, evaluated once per outer row.
  • EXISTS — true if a correlated subquery returns at least one row; never double-counts multiple matches.
  • WITH CTE — a named, temporary query result, queryable like a table for the duration of the statement that defines it; CTEs can reference earlier CTEs in the same WITH.
  • DuckDB’s SQL extensions are optional, not a replacement for standard SQL — EXCLUDE/REPLACE skip listing columns by hand, GROUP BY ALL/ORDER BY ALL skip repeating column names, QUALIFY filters a window function without a wrapping subquery, COLUMNS(*) applies one expression to many columns at once, and SUMMARIZE profiles an entire table in one statement — confirmed here to match standard-SQL equivalents exactly, not just assumed to.

Why This Matters#

Most business questions need more than one step: compute something first, then compare against it. Subqueries and CTEs are how SQL expresses that without leaving the database — this lesson’s segment-average comparison would otherwise mean pulling data into Python, computing an average per group by hand, and joining it back manually. Keeping the whole calculation in SQL means it stays a single, re-runnable, verifiable query.
