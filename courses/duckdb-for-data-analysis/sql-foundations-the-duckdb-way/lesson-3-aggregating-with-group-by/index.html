Welcome to Aggregating with GROUP BY#

Every query so far has returned individual rows, filtered and sorted but still one row per order line item or customer. GROUP BY changes the shape of the answer entirely: instead of “here are the rows,” it answers “here’s one summary row per group.” This lesson aggregates Thistlewood Goods’ order line items by product and its orders by channel and status, filters those summaries with HAVING, and closes by checking a total this lesson computes against a number this course can independently confirm.

By the end of this lesson, you will be able to:

  • Group rows with GROUP BY and summarize each group with sum, avg, count, min, and max
  • Filter groups (not individual rows) with HAVING, and explain why that’s different from WHERE
  • Group by more than one column at once
  • Reconcile an aggregate against an independently-computed number, with a tolerance appropriate to rounding

This lesson’s code was run against DuckDB 1.5.5, verified on 2026-08-12 — the version and date this whole course is pinned to. If duckdb.connect() on your machine reports a newer patch version, the SQL and behavior below should still hold.

GROUP BY with Aggregate Functions#

Get the data

This lesson uses thistlewood_order_items.csv, and thistlewood_orders.csv, hosted at https://datatweets.com/datasets/thistlewood/thistlewood_order_items.csv, and https://datatweets.com/datasets/thistlewood/thistlewood_orders.csv. Download them into your working directory to follow along by bare filename, or skip the download and point DuckDB straight at the URLs instead — DuckDB reads HTTPS sources directly in a FROM clause, so the full https://... URL works anywhere the bare filename does, with no other setup.

Each row in thistlewood_order_items.csv is one product on one order. Grouping by product_id collapses all of a product’s line items into one summary row per product:

Every column after product_id is an aggregate function — count, sum, avg, min, max — each one collapsing many rows into a single value per group. P021 alone shows up on 259 separate order line items, selling 783 total units for $339,823.09 in revenue, at an average of $1,312.06 per line item, with individual line-item quantities ranging from 1 to 5 units. unit_price_at_sale’s per-product revenue turns out to have zero ties across all 60 products — checked directly the same way Lesson 2 checked a sort column, since ORDER BY revenue DESC above is itself a sort.

GROUP BY needs every non-aggregated column in the SELECT list

product_id appears in both the SELECT list and the GROUP BY clause. Every column you select that isn’t wrapped in an aggregate function has to appear in GROUP BY — DuckDB needs to know, for each output row, which single value of that column to show when the underlying group might otherwise have many.

HAVING: Filtering Groups, Not Rows#

WHERE filters individual rows before grouping happens; HAVING filters the groups themselves, after aggregation, and can reference an aggregate function directly:

WHERE count(*) > 250 would fail outright — count(*) doesn’t exist yet at the point WHERE runs, since grouping hasn’t happened. HAVING runs after GROUP BY has already produced its summary rows, which is exactly when “how many line items does this product have” becomes a question you can filter on.

Grouping by More Than One Column#

GROUP BY accepts a list of columns, producing one summary row per unique combination:

GROUP BY channel, status produces one row per (channel, status) pair that actually occurs — nine rows for three channels times three statuses, since every combination happens to be present in this data. web accounts for the largest share of orders in every status, which makes sense alongside web also being the largest single channel overall.

Grouping by a Calculated Date#

Grouping orders by month means computing a monthly key from order_date first. DuckDB offers more than one way to do this, and they don’t return the same type:

date_trunc('month', order_date) rounds a date down to the first of its month but returns a TIMESTAMP (with a 00:00:00 time attached), not a plain date or string — worth knowing if you planned to display it directly as a YYYY-MM label. strftime(order_date, '%Y-%m') sidesteps the question entirely by formatting straight to a VARCHAR grouping key, which is what this query uses above.

Reconciling a Total Against What This Course Already Knows#

This module’s guided project will need a trustworthy grand total for Thistlewood Goods’ order line items, so it’s worth establishing one now, checked two ways rather than trusted from a single query:

$9,195,043.62 — computed here as a single sum over all 14,054 line items in thistlewood_order_items.csv, and re-derived by summing 60 independently-rounded per-product totals. This is worth stating plainly rather than glossing over: agreement here confirms these two GROUP BY/aggregation queries are consistent with each other over this table’s own quantity and unit_price_at_sale columns — it does not independently confirm the file itself is correct, since both queries read the identical file and column. It also matches the grand total this site’s own Polars course established across the same 6,000 orders and 14,054 items in this dataset — a real, external cross-check available specifically because this course reuses the same underlying data rather than a fresh copy.

Why ‘within a cent,’ not exact equality

The comparison above uses abs(grand_total - resummed) < 0.01 instead of ==. Summing 60 already-rounded per-product totals and comparing to a single rounded total over all 14,054 rows happened to land exactly on the same cent here, but that’s not guaranteed in general — rounding many partial sums independently can drift a cent from rounding one combined sum. A tolerance-based comparison is the honest check; an exact == would pass here by coincidence and could fail elsewhere for a reason that has nothing to do with a real bug.

Practice Exercises#

Exercise 1: Aggregate orders by status#

Write a GROUP BY status query against orders that reports count(*) for each status (completed, cancelled, pending). Compute what percentage of all 6,000 orders each status represents.

Hint

SELECT status, count(*) AS n, round(100.0 * count(*) / 6000, 1) AS pct FROM orders GROUP BY status ORDER BY n DESC gets you both the counts and the percentages in one query.

Exercise 2: A stricter HAVING#

Using this lesson’s frequent_products query as a starting point, change the HAVING condition to count(*) > 250 AND sum(quantity) > 800. How many products satisfy both conditions, compared to the 11 that satisfied count(*) > 250 alone?

Summary#

GROUP BY collapses rows sharing a value (or combination of values) into one summary row per group, computed with aggregate functions like sum, avg, count, min, and max — demonstrated here on thistlewood_order_items.csv, grouped by product. HAVING filters those groups after aggregation, unlike WHERE, which filters individual rows before grouping ever happens. Grouping by more than one column, and grouping by a calculated key like a formatted month, both worked as shown, with date_trunc and strftime confirmed to return different types for the same underlying date. The lesson closed by reconciling this table’s $9,195,043.62 grand total two independent ways, within a cent — the standard every guided project in this course holds a number to before trusting it.

Key Concepts#

  • GROUP BY — collapses rows into one summary row per unique value (or combination of values) of the grouped column(s).
  • Aggregate functions — sum, avg, count, min, max, computed once per group.
  • HAVING — filters groups after aggregation; WHERE filters rows before it.
  • Tolerance-based reconciliation — comparing two independently-rounded totals with a small allowed difference, not exact equality.

Why This Matters#

Almost every real business question — “which products sell best,” “how many orders come from each channel,” “what did we sell last month” — is a GROUP BY question underneath. Reconciling a number against an independent check, the way this lesson’s grand total was, is what turns “the query ran” into “the number is trustworthy,” which the rest of this module keeps building on.

Want more depth on aggregation and grouping in SQL generally? See the SQL course’s own Aggregate Functions, Grouping Data with GROUP BY, and Grouping by Multiple Columns lessons.
