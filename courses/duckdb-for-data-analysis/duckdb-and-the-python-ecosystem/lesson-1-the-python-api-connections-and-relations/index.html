Welcome to the Python API#

Every earlier module used con.execute("<SQL string>"), then .fetchall() to get results — a cursor-style API, the same shape as Python’s built-in sqlite3 module. DuckDB’s Python API has a second way to build a query: con.sql(...), which returns a Relation — a lazy, chainable object representing a query, not yet run. This lesson compares them directly.

By the end of this lesson, you will be able to:

  • Compare con.execute()’s cursor-style API to con.sql()’s Relation object
  • Chain .filter() and .aggregate() calls onto a Relation to build a query step by step
  • Confirm a Relation is genuinely lazy — nothing runs until it’s materialized
  • Choose between raw SQL strings and the Relation API for a given task

This lesson’s code was run against DuckDB 1.5.5, verified on 2026-08-13 — the version and date this whole course is pinned to. If duckdb.connect() on your machine reports a newer patch version, the SQL and behavior below should still hold.

con.execute(): The Cursor-Style API#

Get the data

This lesson uses thistlewood_orders.csv, hosted at https://datatweets.com/datasets/thistlewood/thistlewood_orders.csv. Download it into your working directory to follow along by bare filename, or skip the download and point DuckDB straight at the URL instead — DuckDB reads HTTPS sources directly in a FROM clause, so the full https://... URL works anywhere the bare filename does, with no other setup.

Every module so far has used this pattern — a SQL string in, a fetch call to get results out:

con.execute(...) actually returns the connection itself, DuckDBPyConnection — set up to fetch results from whatever query just ran. It’s imperative: the SQL runs immediately, and .fetchone()/.fetchall() just reads whatever result is sitting ready.

Chaining Methods Instead of Writing SQL#

A Relation supports method calls that build a query step by step — .filter(), .aggregate(), .order(), and more — each one returning a new Relation rather than running anything:

3,895 — the same web-channel order count this course has confirmed before (Module 3). .filter("channel = 'web'") and .aggregate("count(*) AS n") each took a plain SQL expression as an argument, not a whole query — the chaining builds the query, one clause at a time, in Python rather than one long SQL string.

Two more chainable methods worth knowing: .project() selects specific columns (the Relation equivalent of a SELECT column list), and .distinct() removes duplicate rows:

.project() narrows the columns before anything else chains onto it; .limit(2) (another chainable method) caps the row count the same way SQL’s LIMIT does. .distinct() after .project("channel") gives exactly the three channel values this course has used throughout — store, web, phone — with no duplicates.

A Shared Default Connection: duckdb.sql()#

Every example so far explicitly created con = duckdb.connect() first. DuckDB also has a module-level duckdb.sql() function that skips that step, using an implicit default connection shared across the whole process:

quick_table was created by one duckdb.sql() call and queried by a completely separate one — no con object passed between them, because both used the same implicit default connection. That’s convenient for a short, throwaway script, but it comes at a real cost worth naming: unlike duckdb.connect(), which gives you an explicit, isolated connection you control, the default connection is shared process-wide, so a library or unrelated part of a larger program using duckdb.sql() without realizing it would land in the same namespace. Every other lesson in this course uses an explicit con = duckdb.connect() specifically to avoid that — worth doing the same in anything beyond a quick, disposable script.

Confirming It’s Actually Lazy#

“Lazy” means the chain of .filter()/.aggregate() calls builds a query plan without running anything — worth confirming directly rather than taking on faith. .sql_query() returns the actual generated SQL text a Relation represents, without executing it:

Every .filter() and .aggregate() call folded into one generated SQL statement — the exact same shape as if you’d written that whole query as a string yourself and passed it to con.execute(). The unnamed_relation_<hash> alias is generated fresh every run (it’ll be a different hash if you run this yourself) — only the query structure matters here, not that specific name. Nothing ran until .fetchone() was called two code blocks ago; building web_orders and web_order_count only ever constructed this query plan.

Which one to reach for

Raw SQL strings via con.execute() are usually clearer for a query you can write out completely in your head — most of what this course has taught so far. The Relation API earns its keep when a query is genuinely built up in pieces at runtime — adding a .filter() conditionally based on a Python variable, for example — where assembling a SQL string by hand would mean fragile string concatenation instead of composable method calls.

Calling Your Own Python Code from SQL: create_function()#

Everything so far has been DuckDB running SQL. con.create_function() goes the other direction: register an ordinary Python function once, then call it from inside SQL like any built-in function. This example brings in one more small Thistlewood Goods file, thistlewood_products.csv (also hosted at https://datatweets.com/datasets/thistlewood/thistlewood_products.csv, same download-or-URL choice as every other dataset in this course):

price_tier is a plain Python function with no DuckDB-specific code in it at all — create_function() is what makes price_tier(unit_price) a legal SQL expression, callable in a SELECT list, a WHERE clause, anywhere a built-in function could go. The two required type hints in the call (["DOUBLE"] for the argument, "VARCHAR" for the return) tell DuckDB what SQL types to expect on each side of the Python boundary.

A UDF is genuinely useful for logic that’s awkward in SQL – and genuinely slow for anything else

price_tier above could just as easily be a CASE expression, and for logic this simple, it should be — Module 9 measures directly why: a Python UDF runs once per row, in the Python interpreter, forfeiting DuckDB’s vectorized execution entirely, and the gap is dramatic at any real scale. Reach for create_function() when the logic genuinely can’t be expressed in SQL — calling an existing Python library, a regex too irregular for SQL’s string functions, a stateful calculation — not as a first choice for something a CASE expression or a built-in function already covers.

Practice Exercises#

Exercise 1: Chain three methods instead of two#

Starting from orders, chain .filter("status = 'completed'"), then .aggregate("channel, count(*) AS n", group_expr="channel"), then .order("channel"). Confirm the result matches running the equivalent WHERE/GROUP BY/ORDER BY SQL directly through con.execute().

Hint

Relation.aggregate(aggr_expr, group_expr) takes the aggregation expressions and the GROUP BY columns as two separate arguments — check orders.filter("status = 'completed'").aggregate("channel, count(*) AS n", "channel").order("channel").fetchall().

Exercise 2: Confirm .limit() doesn’t scan the whole file first#

Build orders.limit(5) and call .sql_query() on it before fetching anything. Confirm the generated SQL includes a LIMIT 5 clause, meaning DuckDB’s query planner can push the limit down rather than reading all 6,000 rows before truncating to 5.

Summary#

con.execute("<SQL>") runs a query immediately and returns the connection itself for fetching results — the cursor-style pattern every earlier module used. con.sql("<SQL>") returns a Relation instead: chaining .filter(), .aggregate(), .project(), .distinct(), and .limit() onto it builds a query plan without running anything, confirmed directly with .sql_query(), which showed the full generated SQL text before a single row had been read. The module-level duckdb.sql() function skips creating a connection entirely, sharing one implicit default connection process-wide — convenient for a quick script, risky for anything larger. Both con.execute() and con.sql() run the identical query underneath — the choice is about how you want to build that query, not what it does once it runs.

Key Concepts#

  • con.execute() runs a SQL string immediately; the connection itself becomes the cursor for .fetchall()/.fetchone().
  • con.sql() returns a Relation — a lazy, chainable representation of a query, not yet executed.
  • .filter(), .aggregate(), .project(), .distinct(), .order(), .limit() (and more) build a query step by step, each returning a new Relation.
  • .sql_query() reveals the actual generated SQL a Relation represents, confirming laziness directly rather than assuming it.
  • The module-level duckdb.sql() shares one implicit default connection across an entire process — fine for a short script, worth avoiding in anything larger in favor of an explicit duckdb.connect().

Why This Matters#

Most queries are clearest as a single SQL string, which is why this course has used con.execute() throughout. But a query assembled conditionally at runtime — different filters depending on user input, a pipeline step that only sometimes adds a clause — is exactly where building it up with chained Relation methods beats string concatenation, and knowing both APIs exist means reaching for the right one instead of forcing every query into the same shape.
