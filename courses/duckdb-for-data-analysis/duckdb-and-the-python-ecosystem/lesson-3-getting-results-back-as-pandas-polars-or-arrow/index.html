Welcome to Getting Results Back#

Lesson 2 queried DataFrames directly; this lesson goes the other way — turning a query’s result into whichever format the next step of a pipeline actually needs. .fetchall() (every earlier module) gives plain Python tuples. DuckDB also offers .df(), .pl(), and .to_arrow_table(), converting the identical result into pandas, Polars, or Arrow.

By the end of this lesson, you will be able to:

  • Get a query result back as a pandas DataFrame with .df()
  • Get the same result as a Polars DataFrame with .pl()
  • Get the same result as a PyArrow Table with .to_arrow_table()
  • Confirm all three represent identical data, and choose the right one for a real next step

This lesson’s code was run against DuckDB 1.5.5, verified on 2026-08-13 — the version and date this whole course is pinned to. If duckdb.connect() on your machine reports a newer patch version, the SQL and behavior below should still hold.

The Same Query, Three Formats#

Get the data

This lesson uses thistlewood_order_items.csv, and thistlewood_products.csv, hosted at https://datatweets.com/datasets/thistlewood/thistlewood_order_items.csv, and https://datatweets.com/datasets/thistlewood/thistlewood_products.csv. Download them into your working directory to follow along by bare filename, or skip the download and point DuckDB straight at the URLs instead — DuckDB reads HTTPS sources directly in a FROM clause, so the full https://... URL works anywhere the bare filename does, with no other setup.

Build one category-revenue query, then fetch it three different ways:

Three separate con.execute(query) calls, one per format — each one re-runs the query and converts the result differently. (.to_arrow_table() is the current, recommended method for a materialized Table; the older .fetch_arrow_table() is deprecated in favor of it. .arrow() is a different, still-current method — the next section covers exactly what it returns instead.)

Confirming They’re the Identical Data#

Different objects, different libraries — worth confirming they actually agree row for row rather than assuming the conversion is lossless:

Same eight categories, same revenue figures, same order — converting .df(), .pl(), or .to_arrow_table() changes the container, never the values inside it.

.arrow() Streams; .to_arrow_table() Materializes#

There’s a real, useful distinction inside the Arrow side of this that’s easy to miss: .arrow() doesn’t actually return a Table — it returns a RecordBatchReader, an object for reading results batch by batch rather than all at once:

.to_arrow_table() — the method used everywhere else in this lesson — skips the reader step and returns a fully materialized pyarrow.Table directly, which is what you want for a normal-sized result like this one. The RecordBatchReader form exists for genuinely large results where reading everything into memory as one Table isn’t practical; a later module’s work with larger-than-memory data will make that distinction matter more than it does on an eight-row category summary.

Real Interop: Writing Parquet with PyArrow Directly#

Arrow’s whole purpose is interop between tools — write the query result to Parquet using PyArrow’s own writer, not DuckDB’s COPY, then read it back with DuckDB to confirm nothing was lost crossing that boundary:

pq.write_table() is PyArrow’s own function, entirely separate from DuckDB’s COPY (Module 3) — and DuckDB reads the resulting file back correctly regardless, because Parquet is a shared, tool-agnostic format. This is what “Arrow for interop” actually looks like in practice: a query result leaving DuckDB’s world entirely, written by a different library, and still coming back exactly right.

Using Each Format for a Real Next Step#

Each format earns its place by what it lets you do immediately afterward, in that library’s own native way:

df["revenue"].sum() uses pandas’ own column-sum method directly — and lands on this course’s established grand total again, computed a third format-conversion path away from the original SQL GROUP BY. pl_df.filter(...) uses Polars’ native filtering syntax to find the 5 categories earning over a million dollars. arrow_tbl.schema shows Arrow’s own strongly-typed schema representation — useful when the next step is handing this data to another Arrow-native tool (writing Parquet with PyArrow directly, for instance) rather than doing more analysis in Python.

Picking a format

.df() for the broadest ecosystem compatibility — most plotting, machine learning, and statistics libraries expect pandas. .pl() when the next step is more Polars-native transformation, especially if you’re already working in a Polars-based pipeline. .to_arrow_table() for interop with other Arrow-native tools, or when you specifically want to avoid a pandas or Polars dependency in a step that just needs to pass data along.

Practice Exercises#

Exercise 1: Round-trip through all three formats#

Take arrow_tbl and convert it to pandas with arrow_tbl.to_pandas(), then compare it to df (the original .df() result). Confirm the two are equal using df.equals(arrow_tbl.to_pandas()).

Hint

pandas.DataFrame.equals() checks both values and dtypes match exactly — a stricter check than just comparing printed output.

Exercise 2: Confirm a fourth query gives a fourth-format result too#

DuckDB relation objects also support .fetchnumpy(), returning a dictionary of NumPy arrays. Run the same category-revenue query with .fetchnumpy() and confirm the revenue array’s .sum() also equals $9,195,043.62.

Summary#

.df(), .pl(), and .to_arrow_table() convert an identical query result into pandas, Polars, or PyArrow — confirmed here row for row, not just assumed equivalent because they came from the same query. .arrow() returns something genuinely different from .to_arrow_table() — a streaming RecordBatchReader rather than a materialized Table — confirmed by reading one all the way into a Table and checking it matches .to_arrow_table()’s result exactly. A PyArrow Table written to Parquet with PyArrow’s own writer, entirely outside DuckDB’s COPY, read back correctly through DuckDB — real cross-tool interop, not just a same-library round trip. Each format was put to a real, format-native next step: pandas’ .sum(), Polars’ .filter(), and Arrow’s own schema inspection — landing on this course’s $9,195,043.62 grand total a third independent way, computed through the pandas conversion path this time.

Key Concepts#

  • .df() returns a pandas DataFrame; .pl() returns a Polars DataFrame; .to_arrow_table() returns a PyArrow Table — all from the identical query.
  • The three formats represent identical data — confirmed here by comparing row tuples across all three, not assumed from the conversion succeeding.
  • .arrow() returns a RecordBatchReader (streaming), not a Table — genuinely different from .to_arrow_table(), not just an older name for the same thing; only .fetch_arrow_table() is actually deprecated.
  • Each format suits a different next step — pandas for broad ecosystem compatibility, Polars for native Polars transformations, Arrow for cross-tool interop, confirmed here with a real PyArrow-written Parquet file DuckDB reads back correctly.

Why This Matters#

A query result is rarely the final destination — it feeds a plot, a model, a further transformation, or another system entirely, and each of those expects a specific format. Knowing DuckDB converts to any of the three main ones directly, with the identical data underneath, means the choice of result format is about what’s next, not a limitation to work around.
