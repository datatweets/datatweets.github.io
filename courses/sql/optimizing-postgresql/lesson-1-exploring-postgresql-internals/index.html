Welcome to PostgreSQL Internals#

Before you can make a database faster, you have to understand what is inside it. In this lesson you take on the role of a data engineer who has just been handed a Postgres database from the U.S. Department of Housing and Urban Development (HUD). Nobody has documented its structure for you. There is no schema diagram, no data dictionary — just a connection string and a job to do.

The good news is that Postgres documents itself. Every Postgres database keeps a set of internal tables that describe its own structure: which tables exist, what columns they have, what types those columns are, and much more. In this lesson you will learn to read those internal tables and assemble your own description of the database from scratch.

By the end of this lesson, you will be able to:

  • Query the internal catalog tables to list a database’s tables
  • Distinguish user-created tables from Postgres’ own system tables using schemas
  • Map numeric type codes to human-readable type names
  • Read column metadata from both pg_catalog and information_schema
  • Build a JSON description of a database’s structure, including row counts

You only need a working knowledge of SQL. Every example runs in psql (or any SQL client), so you can follow along by typing the queries directly against your own copy of the database. Let’s open up Postgres and see what it knows about itself.

Data for this lesson

Engine: PostgreSQL. Dataset: homeless-by-CoC — U.S. homelessness counts by Continuum of Care, loaded from CSV.

Tables used: homeless_by_coc

Real-world source: HUD — PIT and HIC Data Since 2007 (the HUD homelessness point-in-time counts this homeless_by_coc data is based on). Load it into your own PostgreSQL instance and run the queries in psql or a GUI client.

The Internal Catalog Tables#

Every Postgres engine maintains a set of internal tables to manage its entire structure. These live in two documented groups: the information_schema and the system catalogs (in the pg_catalog group). Together they hold all the information about the data, table names, and types stored in the database. Whenever a client tool shows you the columns of a result, that information is being pulled from these internal tables.

The two groups overlap in what they describe but serve different purposes:

  • information_schema is an SQL-standard set of views. It is portable across database engines and uses plain text names, which makes it the friendlier place to start.
  • pg_catalog is Postgres-specific and lower level. It is faster, exposes more detail, and uses numeric identifiers (called OIDs) under the hood.

You will use both in this lesson, and you will see how they describe the same database from two different angles.

Listing All Tables#

The system catalog that lists every table is pg_tables, located in the pg_catalog schema. Before filtering anything, it helps to see just how much Postgres tracks. Count every row in pg_tables:

Sixty-nine tables — and you only loaded a handful yourself. Almost all of those are Postgres’ own internal bookkeeping, with names like pg_aggregate, pg_attribute, and pg_class. That is not what you came for. You need a way to separate the tables you care about from the engine’s machinery.

Working with Schemas#

The reason the count was so high is that it included Postgres’ internal tables. The fix comes from understanding schemas.

Schemas Are Folders for Tables#

A schema is a namespace that separates database tables into isolated groups — think of it as a folder for tables. When a Postgres database is created, three schemas are instantiated automatically:

  1. pg_catalog holds the system catalog tables.
  2. information_schema holds the information schema views.
  3. public is the default schema for user-created tables.

Every time you run a CREATE TABLE command without specifying a schema, Postgres places that table in public. So unless someone created a special schema for them, the HUD tables live in public.

You can prove this by grouping the tables in pg_tables by their schemaname column and counting each group:

The breakdown is striking: 62 tables belong to pg_catalog, 4 to information_schema, and only 3 to public. Those three are yours.

Because pg_tables exposes the schema of each table in its schemaname column, you can exclude the two internal schemas with a single NOT IN clause. While you are at it, pull the owner of each table too:

Now the result is short and meaningful. There are only three user-created tables, all owned by the postgres role. The homeless_by_coc table records the number of homeless residents for every state, city, and county in the United States; the other two carry supporting reference data.

Note

information_schema views follow no obvious prefix pattern, but pg_catalog tables almost always begin with pg_. Filtering by schemaname is far more reliable than trying to match name prefixes.

Describing the Columns#

Now that you know the three table names, you can inspect each table’s columns. The most portable place to do this is the information_schema.columns view, which has one row per column and uses plain text names for everything.

From Type Codes to Readable Types#

The information_schema gave you friendly type names, but Postgres does not store types that way internally. In the system catalogs, every column points at its type through a numeric OID (object identifier), and you have to translate those codes yourself. Learning to do this is worthwhile, because the low-level catalogs expose details information_schema hides — and the same join pattern shows up throughout Postgres tuning.

Joining pg_attribute to pg_type#

The catalog pg_attribute has one row per column and stores each column’s type as an OID in atttypid. The catalog pg_type maps that OID (its oid column) to a readable name (typname). Join them, and restrict to one table using the regclass cast, which turns a table name into its catalog identifier:

Two filters keep the output clean: attnum > 0 drops Postgres’ hidden system columns (which use negative numbers), and NOT a.attisdropped skips columns that were deleted but not yet cleaned up.

Notice the type_name differs slightly from what information_schema showed. The catalog reports the internal name int4 where information_schema reported the SQL-standard name integer. They describe the same type; they just speak different dialects.

So 25 is text, 23 is int4, and 1082 is date — exactly the codes attached to the homeless_by_coc columns. These OIDs are stable: bool is always 16, int4 is always 23. You will recognize them on sight before long.

Always Filter Identifiers Safely

When you wrap these catalog queries in application code, never paste a table name straight into a query string with text formatting. Pass values as bind parameters, and when you must inject an identifier such as a table name, use your driver’s identifier-quoting helper. Treating every query as if an attacker controls its inputs is the only habit that scales.

Counting the Rows#

A description of a database is far more useful when it tells you how big each table is. There are two ways to find out, and both matter for the lessons ahead.

Exact Counts#

The exact answer comes from COUNT(*). To compare all three tables in one result, stack them with UNION ALL:

homeless_by_coc dominates with 95,680 rows, while state_info holds just 51 (one per state, plus the District of Columbia). That size gap is exactly why query performance will matter: a join or filter that is instant on state_info can crawl on homeless_by_coc.

Your numbers will differ

The HUD source is updated over time, so your exact row counts depend on the snapshot you loaded. The relative picture — one very large fact table beside two small reference tables — is what stays the same and what matters for tuning.

Fast Estimates from the Planner#

COUNT(*) scans the whole table, which is fine for three tables but slow when you are surveying hundreds. Postgres keeps an estimate of each table’s row count in the catalog pg_class, in the reltuples column. The estimate is refreshed whenever the table is analyzed:

Right after ANALYZE, the estimates match the exact counts. Between analyses they drift, but they cost nothing to read — no table scan at all. This is the same statistic the query planner consults when deciding how to run your queries, which is why it reappears constantly in the next lesson on EXPLAIN.

Assembling a JSON Description#

You now have every piece you need: the table list, each table’s columns and types, and its row count. The final step is to combine them into one structured, readable document. Postgres can do this without leaving SQL, using its built-in JSON functions.

The function jsonb_build_object() constructs a JSON object from alternating keys and values, jsonb_agg() rolls a set of rows into a JSON array, and jsonb_pretty() formats the result with indentation. Put them together to describe homeless_by_coc in a single query:

Practice Exercises#

Exercise 1: List the Public Tables a Different Way#

You listed the user tables with pg_tables. The information_schema tracks them too. Write a query against information_schema.tables that selects table_name for rows where table_schema = 'public', ordered by name. Confirm you get the same three tables as the pg_tables approach.

Hint

The column is table_schema (not schemaname) in information_schema.tables, and the value you want is 'public'. Use single quotes around the value in the WHERE clause. You should see homeless_by_coc, state_household_incomes, and state_info.

Exercise 2: Translate a Type Code#

Using pg_catalog.pg_type, find the readable name for the OID 1082. Then look up 25. Cross-reference each against the type-code listing for homeless_by_coc — which columns use each one?

Hint

SELECT typname FROM pg_catalog.pg_type WHERE oid = 1082; returns date, and oid = 25 returns text. The year column is the date; state, coc_number, coc_name, and measures are all text.

Exercise 3: Compare Exact and Estimated Counts#

Run COUNT(*) on state_household_incomes, then read its reltuples value from pg_class. Run ANALYZE on the table and compare again. Which count is exact, and which is an estimate the planner relies on?

Hint

COUNT(*) is always exact but scans the table; reltuples is an estimate that costs nothing to read and is refreshed by ANALYZE. Right after an analyze they should agree — state_household_incomes has roughly 510 rows in the loaded sample.

Summary#

You started this lesson with an undocumented database and ended it with a complete, readable description built entirely from Postgres’ own internal tables. Along the way you learned how Postgres organizes its metadata into schemas, how the high-level information_schema and the low-level pg_catalog describe the same database differently, and how to translate Postgres’ internal type codes into names you can read.

Key Concepts#

  • Internal catalog tables — Postgres stores metadata about itself in the pg_catalog and information_schema schemas; pg_tables lists tables, pg_attribute and information_schema.columns describe columns, and pg_type maps type OIDs to names.
  • Schema — a namespace that groups tables; new databases get pg_catalog, information_schema, and public, and user tables default to public.
  • Type OID — the numeric identifier Postgres gives each column type (for example 25 for text, 23 for int4, 1082 for date); join pg_attribute to pg_type to translate it.
  • Row counts — COUNT(*) is exact but scans the table, while pg_class.reltuples is a free estimate the query planner uses; ANALYZE keeps the estimate current.
  • JSON in SQL — jsonb_build_object(), jsonb_agg(), and jsonb_pretty() let you assemble a structured, readable description of a database without leaving Postgres.

Why This Matters#

In real data engineering work, you are constantly handed databases you did not design. Being able to interrogate a database directly — to list its tables, inspect its columns, and measure its size without relying on someone else’s documentation — is a core skill. It is also the foundation for everything that follows: you cannot optimize what you cannot see. Now that you know the structure of the HUD database, you are ready to watch how Postgres runs queries against it.

Continue Building Your Skills#

You can now read a Postgres database from the inside out. That habit of inspecting before acting will serve you in every performance investigation you ever run. In the next lesson you will turn from what is in the database to how Postgres works with it — and you will meet the single most important tool for understanding query performance: EXPLAIN.
