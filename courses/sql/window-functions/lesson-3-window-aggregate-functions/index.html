Welcome to Window Aggregate Functions#

You already know aggregate functions — SUM(), AVG(), COUNT(), MIN(), MAX(). You have used them with GROUP BY to summarize groups of rows. In this lesson you will use those same functions as window aggregate functions, computed over an OVER() window instead of a GROUP BY group.

This familiarity is a double-edged sword. The functions look identical, but the behavior differs in an important way: GROUP BY returns one row per group, while a window aggregate returns a value for every row. Getting clear on that difference — and on where window functions are and are not allowed in a query — is the goal of this lesson.

By the end of this lesson, you will be able to:

  • Define window aggregate functions and how they differ from grouped aggregates
  • Add window aggregates to non-aggregate queries to keep detail rows
  • Combine window aggregates with GROUP BY queries
  • Explain why window functions cannot appear in WHERE, and work around it with a subquery

This lesson builds on the OVER(), PARTITION BY, ORDER BY, and framing concepts from Lessons 1 and 2. Let’s dive in.

Data for this lesson

Engine: PostgreSQL — the examples print small sample tables inline.

Tables used: trips, employees, phone_sales_quantity_by_month, phone_sales_by_month, phone_sales_quantity

Want to run them yourself? Download window_practice.db and use any SQLite client (SQLite supports window functions too), or recreate the tables in PostgreSQL with psql.

What Are Window Aggregate Functions?#

A window aggregate function is a regular aggregate (SUM, AVG, COUNT, and friends) applied over a window defined by OVER(). The function is the same; what changes is how it is applied and what comes back.

  • With GROUP BY, the aggregate produces one result per group, and you lose the detail columns.
  • With OVER(), the aggregate produces one result per row, and the detail columns stay.

Consider the trips table, where each row is one bike rental with its member_type, the trip duration in seconds, and a rider_rating:

The grouped version counts the trips and averages the duration for each member_type, but it collapses every rental into one summary row and drops bike_number and duration:

If you try to keep duration in that query, the database rejects it:

The window version, by contrast, keeps every detail row and attaches the per-member_type aggregate to each one:

Because each row keeps its own duration alongside the group’s average, you can compare the two directly — for example, duration - AVG(duration) OVER(PARTITION BY member_type) tells you how far each trip ran above or below the typical ride for that rider type. That comparison is awkward with GROUP BY but trivial with a window function.

Window Functions and the WHERE Clause#

Window functions have a strict rule about where they can appear in a query, and it trips up nearly everyone at first.

You can freely use a window function in the SELECT list of a filtered query. The window is computed over whatever rows survive the WHERE clause:

The average_salary here is 77900.0 — the average of only the IT rows, not the 83533.3 company-wide figure you saw earlier. The window function runs after WHERE has filtered the data, so it sees just the four IT employees.

But you cannot put a window function inside the WHERE clause itself:

Why: The Order of Execution#

SQL processes a query in a fixed logical order:

  1. FROM / JOIN — build the data set
  2. WHERE — filter rows
  3. GROUP BY — form groups
  4. HAVING — filter groups
  5. SELECT — choose columns; this is where window functions run
  6. ORDER BY — sort the result
  7. LIMIT / OFFSET — trim the result

Window functions are evaluated at the SELECT step. By the time WHERE, GROUP BY, and HAVING are being processed, the window results do not exist yet — so they cannot be referenced there. Putting a window function in WHERE would create a circular dependency, which is why the database refuses.

The Fix: A Subquery or CTE#

To filter on a window result, compute it in a subquery (or CTE) first, then filter the outer query. Here we keep only the trips that ran longer than the average ride for their own rider type:

The inner query produces type_avg as an ordinary column; the outer query can then filter on it normally. Note that the bar is different per partition — a 918-second Member trip clears the Member average (897.6) and survives, while an 918-second Casual trip would fall short of the Casual average (1101.0). This subquery-then-filter pattern is the standard way to keep only rows that beat a windowed value.

Combining Window Aggregates with Aggregate Queries#

You can mix a window aggregate into a query that already uses GROUP BY, but it requires care. Suppose you have monthly revenue per brand in phone_sales_by_month (revenue is quantity * unit_price), and you want each month’s revenue and a running brand-to-date total on the same rows:

The problem: after GROUP BY brand, month, the raw quantity and unit_price columns no longer exist as individual values — only the grouping keys and aggregated expressions are available. A window function in this query must operate on those same allowed building blocks. The fix is to apply the window function to the already-aggregated value:

The inner SUM(quantity * unit_price) totals each brand-month; the outer SUM(...) OVER(PARTITION BY brand ORDER BY month) then accumulates those monthly totals into a running brand-to-date figure. SQL does not allow plain nested aggregates, but here the window function is summing an aggregate, which is permitted. The rule to remember: in a grouped query, any expression inside a window function must either be in the GROUP BY clause or be wrapped in an aggregate.

Practice Exercises#

Use the trips, phone_sales_quantity, and employees tables.

Exercise 1: Compare to the Rider-Type Average#

Against trips, return member_type, bike_number, rider_rating, the average rating for each rider type (aliased average), and the difference between each row’s rider_rating and that average (aliased difference).

Hint

Use AVG(rider_rating) OVER(PARTITION BY member_type) for the average, and rider_rating - AVG(rider_rating) OVER(PARTITION BY member_type) for the difference.

Exercise 2: Above-Average Trips#

Return the bike_number, member_type, and duration of every trip that lasted longer than the average trip duration across the whole trips table. Remember the WHERE rule.

Hint

Build a subquery that selects the columns plus AVG(duration) OVER() AS avg_duration, then filter the outer query with WHERE duration > avg_duration.

Exercise 3: Monthly and Total Model Quantity#

Against phone_sales_quantity, return sales_date, model, the quantity sold per model per month (aliased monthly_model_quantity), and the all-time total quantity per model (aliased total_model_quantity). Group by model and sales_date.

Hint

Compute the monthly figure with SUM(quantity) and the total per model with SUM(SUM(quantity)) OVER(PARTITION BY model) — a window aggregate over the grouped sum.

Summary#

You used aggregate functions as window functions, computing SUM, AVG, MIN, MAX, and COUNT over an OVER() window so that every detail row keeps its data alongside the aggregate. You saw why window functions run at the SELECT step — and therefore cannot appear in WHERE, GROUP BY, or HAVING — and how a subquery or CTE lets you filter on a windowed value. Finally, you combined window aggregates with grouped queries by applying the window function to an already-aggregated expression.

Key Concepts#

  • Window aggregate function — an aggregate computed over an OVER() window, returning one value per row instead of one per group.
  • Detail plus aggregate — window aggregates let you keep raw columns next to summary values, enabling direct row-to-group comparisons.
  • Order of execution — window functions are evaluated at the SELECT step, which is why they are forbidden in WHERE/GROUP BY/HAVING.
  • Subquery filter — compute the window value in an inner query, then filter on it in the outer query.
  • Aggregate of an aggregate — SUM(SUM(x)) OVER() is valid in a grouped query because the window function operates on the grouped result.

Why This Matters#

Window aggregates are the bread and butter of analytical SQL. Comparing a value to its group’s average, building running totals and rolling averages, and adding a grand total beside per-group subtotals are everyday tasks in reporting and dashboards. Understanding the order of execution also saves you hours of confusion the first time the database refuses a window function in WHERE — you will know immediately to reach for a subquery.

Continue Building Your Skills#

Try rewriting a few of your old GROUP BY queries as window-aggregate queries and notice how much more you can show in a single result. Then practice the subquery-filter pattern until it is automatic — it unlocks “keep only the rows above the average” and countless variations. These patterns appear in nearly every analytics task you will face.
