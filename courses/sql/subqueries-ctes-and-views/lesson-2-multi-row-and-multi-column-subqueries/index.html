Welcome to Multi-Row and Multi-Column Subqueries#

A scalar subquery hands you one value. But many questions need a set of values — “which tracks belong to any of these genres?” — or even a whole table — “what is the average of each genre’s longest track?” For those, you need subqueries that return multiple rows or multiple columns.

In this lesson you will write multi-row subqueries that feed list operators like IN and NOT IN, and multi-column subqueries that stand in for tables in the FROM clause and in joins.

By the end of this lesson, you will be able to:

  • Write a multi-row subquery that returns several values in one column
  • Filter rows with IN and NOT IN against a subquery
  • Write a multi-column subquery that returns a table
  • Use a subquery as a table in the FROM clause
  • Join a subquery to a table or to another subquery

You should already understand scalar subqueries from Lesson 1. Let’s begin.

Data for this lesson

Database: chinook.db — a digital music store (SQLite).

Tables used: track, genre, album, artist

Open it in any SQLite client — DB Browser for SQLite, the sqlite3 CLI, or Python’s sqlite3 — to run every query yourself.

Multi-Row Subqueries: Returning a List#

A multi-row subquery returns several values in a single column — effectively a list. You cannot compare a column to a list with =, so you use the IN operator instead.

From a Hardcoded List to a Subquery#

Two genres in Chinook share the word “Metal”:

genre_idname
3Metal
13Heavy Metal

To count the tracks that belong to either metal genre, you might hardcode those ids:

This returns:

tracks_tally
402

But hardcoding (3, 13) means you must update the query every time the catalog changes. Instead, let a subquery generate those ids:

tracks_tally
402

The inner query returns the ids of every genre whose name contains “Metal” — here, the list (3, 13). The outer query then counts tracks whose genre_id appears in that list. If a new metal genre is added later, this query picks it up automatically.

Filtering with a Subquery List#

The same pattern filters albums. To return every album recorded by an artist whose name starts with the letter A:

Output (first rows):

album_idtitle
1For Those About To Rock We Salute You
2Balls to the Wall
3Restless and Wild
4Let There Be Rock
5Big Ones
6Jagged Little Pill

In all, 27 albums match. The subquery produces the list of matching artist_id values; the outer query keeps only albums whose artist_id is in that list. The key difference from a scalar subquery is the operator: you use IN, not =, because the subquery returns many values.

ANY and ALL: the standard-SQL form

Standard SQL also offers = ANY (subquery) and <> ALL (subquery). value = ANY (...) is exactly equivalent to value IN (...), and value <> ALL (...) is equivalent to value NOT IN (...). PostgreSQL — the other engine used in this course — supports ANY and ALL directly. SQLite does not recognize the ANY/ALL keywords, so the examples below use IN/NOT IN. Where you need “greater than every value in a set,” SQLite expresses > ALL (...) as > (SELECT MAX(...) ...); see the note at the end of this section.

The NOT IN Operator#

Sometimes the easier question is the negative one: not in a set. The NOT IN operator keeps rows whose value is absent from the subquery’s list.

Consider counting tracks that are not rock. Two genres carry the word “Rock” — Rock (1) and Rock And Roll (5) — but the non-rock genres share no common pattern. You have two clean options.

You can describe the non-rock genres directly with NOT LIKE:

tracks_tally
2194

Or you can build the list of rock genres and exclude the tracks that match it with NOT IN:

tracks_tally
2194

Both return the same count. The second reads especially well: “count tracks whose genre is not in the rock list.”

NOT IN and NULL

If the subquery’s list contains a NULL, NOT IN returns no rows at all, because a comparison against NULL is never true. Here every track has a non-null genre_id, so the two queries agree. When in doubt, add WHERE genre_id IS NOT NULL to the subquery.

Combining NOT IN with HAVING#

A subquery can itself contain a GROUP BY and HAVING. To list the albums that hold 23 or more tracks, you first build the list of albums that hold fewer than 23 and exclude them:

The subquery groups tracks by album and keeps the smaller albums. The outer query then returns the titles of every album not in that list — the twelve albums with twenty-three tracks or more.

Multi-Column Subqueries: Returning a Table#

A multi-column subquery returns several columns and rows — a whole table. You use it anywhere a table is allowed, most commonly in the FROM clause.

Why You Need This: Aggregating an Aggregate#

Suppose you want the average of each genre’s longest track. You cannot do this in one flat aggregation — you would be averaging maxima, which requires two passes. A subquery as a table solves it:

Read it inside-out. The inner query produces a small table — one row per genre with that genre’s longest track, expressed in minutes:

genre_idgenre_max_min
126.87
215.13
313.61
49.31

The outer query treats that result as a table and averages the genre_max_min column, giving a single number:

genre_max_min_avg
19.68

You have aggregated an already-aggregated table — something scalar and multi-row subqueries cannot do.

Practice the Pattern#

The same shape answers “what is the average number of tracks per genre?”:

genre_track_tally_avg
140.12

The inner query counts tracks per genre; the outer query averages those counts across all 25 genres.

Joining a Subquery#

Because a multi-column subquery behaves like a table, you can join it to a real table or to another subquery. Give it an alias, just as you would any table.

Joining a Subquery to a Table#

Let’s attach each genre’s average track length to the genre name. The subquery computes the averages; the join brings in the names:

Output (longest-averaging genres first):

nameavg_min
Sci Fi & Fantasy48.53
Science Fiction43.76
Drama42.92
TV Shows35.75
Comedy26.42

Notice the subquery has the alias t and includes genre_id, which is required so the join has a key to match on. The long averages at the top confirm these “genres” are really video collections.

Joining Two Subqueries Together#

You can even join two subqueries to each other. To compute the average number of tracks per album within each genre — tracks per genre divided by albums per genre — you build both aggregates separately and join them:

Output (first rows):

gnametracks_per_album
Easy Listening24
Hip Hop/Rap17
Comedy17
Pop16
Drama16
Bossa Nova15

Subquery tg counts tracks per genre (and carries the genre name); subquery ag counts the distinct albums per genre. The join links them on the genre id, and the outer query divides one count by the other. This is the standard recipe for combining two independent aggregations.

The ALL form: greater than every value

To find tracks longer than every track in the Rock And Roll genre (id 5), standard SQL would write milliseconds > ALL (SELECT milliseconds FROM track WHERE genre_id = 5). SQLite has no ALL, so express the same idea with MAX:

tracks_tally
3177

“Greater than the maximum” is exactly “greater than all,” and it runs everywhere.

Practice Exercises#

Use the Chinook database for each exercise.

Exercise 1: Tracks by Genre List#

Count the tracks whose genre name contains the word Latin. Use a subquery against the genre table to generate the matching genre_id values, and filter the track table with IN.

Hint

The subquery is (SELECT genre_id FROM genre WHERE name LIKE '%Latin%'). Filter track with WHERE genre_id IN (...). You should find 579 tracks.

Exercise 2: Artists With No Albums#

Return the names of artists who have no albums at all, using NOT IN and a subquery against the album table.

Hint

Select from artist where artist_id NOT IN (SELECT artist_id FROM album). There are 71 such artists.

Exercise 3: Average of Per-Album Track Counts#

Write a query that returns the average number of tracks per album. Use a multi-column subquery in the FROM clause that computes COUNT(*) grouped by album_id.

Hint

Inner query: SELECT album_id, COUNT(*) AS album_tally FROM track GROUP BY album_id. Outer query: SELECT ROUND(AVG(album_tally), 2) FROM (...). The answer is about 10.10.

Summary#

You expanded your subquery toolkit beyond single values. Multi-row subqueries return a list and pair with IN and NOT IN. Multi-column subqueries return a table and can sit in the FROM clause or be joined like any other table — which lets you aggregate already-aggregated data and combine independent aggregations.

Key Concepts#

  • Multi-row subquery — returns several values in one column; use with IN and NOT IN.
  • IN / NOT IN — operators that test whether a value is present in (or absent from) a subquery’s list.
  • ANY / ALL — the standard-SQL forms (= ANY equals IN; <> ALL equals NOT IN); available in PostgreSQL, replaced by IN/NOT IN/MAX/MIN in SQLite.
  • Multi-column subquery — returns a table; use it wherever a table is allowed (FROM, joins).
  • Subquery as a table — a subquery in FROM, given an alias, that the outer query reads like a real table.
  • Aggregating an aggregate — averaging or summing the rows of a grouped subquery, impossible in one flat query.

Why This Matters#

Real analysis constantly combines results: “compare against the items in this category,” “exclude albums that are too small,” “average the per-genre maxima.” Multi-row subqueries express the first two cleanly, while multi-column subqueries are how you stack one aggregation on top of another. Master both and you can answer layered business questions without exporting intermediate results to a spreadsheet.

Next Steps#

You can now return lists and tables from subqueries. Next, you will nest subqueries inside other subqueries and write correlated subqueries that depend on the row currently being processed.

Continue Building Your Skills#

You now have three subquery shapes at your disposal: scalar values, lists, and tables. Each unlocks a different class of question. Keep an eye out for moments when you would otherwise run two queries and combine the results by hand — that is almost always a chance to use a multi-row or multi-column subquery instead.
