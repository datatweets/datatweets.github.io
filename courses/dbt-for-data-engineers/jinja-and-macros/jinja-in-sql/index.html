Welcome to Jinja in SQL#

Every .sql file this project has written since Module 1 looked like SQL — but {{ ref('stg_cityflow__trips') }}, {{ source('cityflow', 'zones') }}, and Module 5’s {{ config(enabled = target.type == 'duckdb') }} were never SQL at all. They’re Jinja, a Python templating library dbt runs over every model before a single query reaches Postgres or DuckDB — the same templating engine Flask uses to render HTML, borrowed by dbt to render SQL instead, with the warehouse standing in for the browser. This lesson names it directly and shows exactly what it compiles to.

By the end of this lesson, you will be able to:

  • Tell {{ }} and {% %} apart by what each one compiles to, not just by convention
  • Use dbt compile --inline to inspect compiled SQL without writing a model file
  • Explain why swapping {{ }} and {% %} produces a compile error, not a warning

What {{ }} and {% %} Each Compile To#

dbt compile --inline compiles a query without writing a model file first:

Two different things happened. {{ ref('stg_cityflow__trips') }} — an expression — output "cityflow_warehouse"."public"."stg_cityflow__trips" directly into the query. {% set min_fare = 2.5 %} — a statement — output nothing at that line; it only made the variable min_fare available, and it was {{ min_fare }}, an expression again, that placed 2.5 into the where clause. dbt show --inline confirms the compiled query is what actually runs:

79,578 of CityFlow’s 81,013 trips have a fare_amount of at least $2.50 — the literal value {% set %} assigned and {{ }} then substituted.

Why Compilation Happens Before Execution#

Module 2 built CityFlow’s DAG using ref() and source(), and every model since has depended on dbt resolving those calls correctly before anything runs. That’s exactly what happened above: {{ ref('stg_cityflow__trips') }} isn’t a placeholder dbt fills in as a query executes — it’s Jinja, evaluated during a separate compile step that produces a complete SQL string before dbt hands anything to Postgres or DuckDB. dbt run and dbt build both compile first, execute second; dbt compile alone stops after the first step, which is why it’s useful here — it shows the intermediate artifact those other commands never pause to display.

This ordering is what makes {{ config(enabled = target.type == 'duckdb') }} work: target.type has to be known and enabled evaluated during compilation, before dbt even decides which nodes belong in the DAG for a given run. Compilation isn’t a formatting pass; it’s the step where dbt turns a templated file into the one unambiguous query a warehouse can execute.

A Compile Error From Swapping the Two#

{% %} expects a Jinja statement — a keyword like set, for, or if — not a bare expression. Writing {% min_fare %} where {{ min_fare }} was needed doesn’t silently do nothing; it fails to compile:

dbt’s Jinja parser tried to read min_fare as a statement keyword, found no such keyword, and refused to compile rather than guess — the same category of error a Python interpreter raises for a syntax mistake, not a warning. The compile step fails before anything is sent to Postgres, so a swapped delimiter never gets a chance to produce a bad query silently.

{# #} comments confirm the third delimiter’s behavior — they vanish before compilation, unlike a SQL -- comment:

The {# #} line is gone completely — removed, not commented out — since Jinja processes the template before dbt hands SQL to Postgres.

Context Variables Already in Scope#

{{ min_fare }} worked because {% set %} put min_fare into scope. dbt also puts several of its own variables into scope automatically, in every model — target, used in {{ config(enabled = target.type == 'duckdb') }}, is one:

target.name and target.type come from profiles.yml’s dev/dev_duckdb blocks, not from anything this query set — the object Module 5’s enabled expression read to decide, at compile time, whether zone_hour_report belonged in the DAG at all. env_var(), the function Module 2 used for DBT_LOCAL_ROOT, works the same way: a function dbt exposes inside every Jinja context, called with {{ }} because it returns a value. A handful of others exist — this (the current model’s relation name), var() (values passed from dbt_project.yml or the CLI), graph (the whole parsed DAG) — none used yet in this project, but all reachable through the identical {{ }} mechanism confirmed above.

Practice Exercises#

Exercise 1: A second {% set %} variable#

  • Using dbt compile --inline, write a query with two {% set %} variables — one numeric (like min_fare) and one string (a borough name) — used together in a where clause with and.
  • Confirm the compiled SQL substitutes both literal values correctly.
  • Compare zone_name = '{{ borough }}', with quotes written by hand, against zone_name = {{ borough }}, with none — only one produces valid SQL once compiled, since {{ }} inserts the literal value a Jinja expression evaluates to, nothing more. Run both through dbt show --inline and compare the resulting error to the Encountered unknown tag failure above — they belong to two different failure categories.

Exercise 2: Reading target/compiled/ directly#

  • Run dbt compile --select zone_revenue (no --inline) and find the resulting file under .dbt-local/cityflow_warehouse/target/compiled/cityflow_warehouse/models/marts/zone_revenue.sql.
  • Confirm its contents match what dbt compile’s stdout showed — the same file Postgres receives when dbt run executes the model.

Hint

--inline never writes a file under target/compiled/ for the query itself — only --select against an actual model file does. Exercise 2 checks a file that already exists from every earlier module’s dbt compile/dbt run calls.

Summary#

Jinja’s three delimiter pairs each compile to something categorically different, confirmed directly with dbt compile --inline: {{ }} always outputs a value, {% %} runs control flow and outputs nothing, and {# #} is removed entirely before compilation. Compilation is a distinct step that finishes before execution starts, which is why ref() and source() can safely resolve the DAG dependencies Module 2 relied on before any query touches a warehouse. Swapping {{ }} for {% %} isn’t a style mistake — it’s a compile error dbt raises, since {% %} expects a statement keyword and a bare variable name isn’t one.

Key Concepts#

  • {{ }} outputs, {% %} doesn’t — every ref(), source(), and config() call this project has written is {{ }} precisely because it needs to output something.
  • Compilation finishes before execution starts — dbt run/dbt build both compile, then execute; dbt compile alone stops after the first step.
  • dbt compile --inline inspects compiled SQL without a model file — a quick check that doesn’t require creating and cleaning up a throwaway .sql file.
  • A swapped delimiter fails to compile, not silently — {% min_fare %} produces Encountered unknown tag, caught before any query reaches a warehouse.
  • {# #} removes; -- survives — worth knowing before debugging a query that “should” have a comment in it.

Why This Matters#

Lesson 2 puts {% %} to work: a {% for %} loop pivots CityFlow’s trip counts across its boroughs into columns, and a {% if %} block changes what SQL compiles depending on a condition — the same category of mechanism {{ config(enabled = ...) }} already used, now built by hand.
