Welcome to the Guided Project#

Every other course in this Data Engineering path that touches NYC taxi data eventually reproduces the same numbers: 240,917 zone-hour buckets, 9,554,757 trips, $256,692,373.14 in revenue, first established by the Scaling Python course’s out-of-core capstone over three real months of 2024 data. This guided project reproduces it as a dbt model — the first time this path’s anchor has been built with dbt rather than pandas, PySpark, or a hand-rolled aggregator.

By the end of this project, you will be able to:

  • Point a dbt source at parquet files directly through DuckDB, with no data copied
  • Apply a quarantine window matching an established data-quality rule exactly
  • Reproduce a cross-course anchor figure to the cent, and explain what confirms it’s correct

Step 1: A Source With No Copy Behind It#

CityFlow’s Postgres warehouse holds one day of trip data on purpose — Module 1’s deliberate scope. Reproducing three months without duplicating 9.5 million rows into a second warehouse means reading the source parquet files directly, the read_parquet()-over-disk pattern the DuckDB course’s Module 8 already established for larger-than-memory data. yellow_tripdata_2024-01.parquet is already on disk from Module 1 Lesson 5; February and March join it from the same public NYC TLC Trip Record Data source:

Absolute paths, deliberately — a VIEW re-runs its own query fresh on every read, including read_parquet()’s own file list, so a relative path only works from whatever directory happens to be current at query time, not the directory the view was created from. dbt run shells out with its working directory set to the project folder, not the repo root, so a relative parquet path here would resolve incorrectly the moment dbt queries this view — the same class of problem DBT_LOCAL_ROOT already solved for the DuckDB file path itself back in Module 2 Lesson 4.

9,554,778 — the exact combined row count DATASETS.md already documented for these three files, confirmed once more. Checking the DuckDB file’s own size on disk confirms the “no copy” claim, not just in name:

274 KB for a view over 9.5 million rows — the data itself never left the parquet files sitting at the repo root; DuckDB reads them fresh every time the view is queried, the mechanism Module 2 Lesson 4 first proved for a single day of data, now doing the work at three-months scale. This distinction between a view and a table isn’t just a convenient materialization choice — it’s the only choice that makes this guided project possible at all. A TABLE materialization over the same query would force DuckDB to actually store every resulting row, the multi-hundred-megabyte cost this lesson exists to avoid paying for a report run once, checked, and moved on from.

Step 2: Staging, Then the Quarantine#

stg_cityflow_history__trips stays unfiltered, matching Module 3’s rename-only convention exactly. The quarantine — keeping only rows whose pickup_time genuinely falls inside the quarter — belongs one layer up, in a real intermediate model:

2024-01-01 00:00:00 through 2024-04-01 00:00:00, exclusive — the identical window the Scaling Python capstone’s pipeline used, confirmed directly in its own lesson source. {{ config(enabled = target.type == 'duckdb') }} on both models means neither is even considered when this project runs against Postgres — Jinja reading target.type at compile time, deciding whether a model exists at all before a single row is touched.

21 — the exact count the capstone’s pipeline reported, the 2002- and 2009-dated stray rows caught precisely where they should be, none of them a genuine January-through-March 2024 trip.

Step 4: Checked to the Cent#

Exact — every digit matches the Scaling Python capstone’s already-published figures, built here through a completely different mechanism: a dbt model chain (source, staging, intermediate, mart) compiled to SQL and run against DuckDB, instead of a hand-written streaming, chunked, parallel Python pipeline. Two independent implementations, the identical answer — the same discipline the capstone’s own lesson used to check itself against a brute-force baseline, dbt now a third confirmation.

Worth being precise about what “independent” means here. The underlying source data is identical either way — the same three parquet files, the same 9,554,778 raw rows — so this isn’t independent confirmation that the data itself is correct; a corrupted source file would fool every implementation equally. What it does confirm independently is that the logic is correct: the quarantine window, the zone-and-hour grouping, the revenue rounding, expressed once as pandas operations and once as compiled SQL, arriving at the identical figure through genuinely different execution paths. A bug specific to one engine’s SQL dialect or one library’s aggregation behavior would have shown up as a mismatch here, and none did.

Confirming DuckDB-Only Doesn’t Break Postgres#

Found 8 models against Postgres, not 11 — a disabled model isn’t merely skipped, it’s compiled out of the graph entirely for that target, so selecting one by name produces does not match any enabled nodes rather than a build attempt of any kind. A reader who never runs --target dev_duckdb never notices this guided project’s three models exist, and every other lesson’s dbt build continues to pass against Postgres exactly as before.

Practice Exercises#

Exercise 1: Verify the quarantined rows directly#

  • Query raw.trips_history for the 21 rows int_trips_quartered excludes — pickup_time < '2024-01-01' or pickup_time >= '2024-04-01'.
  • Check whether any of them show the 2002 or 2009 dates the Scaling Python capstone’s lesson named directly.

Exercise 2: A per-month breakdown#

  • Group int_trips_quartered by date_trunc('month', pickup_time) and confirm the three monthly trip counts sum to 9,554,757.
  • Compare the individual month totals against the row counts DATASETS.md documents for each source file (2,964,624 / 3,007,526 / 3,582,628), and if they don’t match, explain the difference using this lesson’s quarantine step.

Hint

DATASETS.md’s per-file counts are unfiltered row counts straight from each parquet file — this lesson’s quarantine step removes 21 rows from that total before the monthly breakdown is even possible.

Summary#

CityFlow’s dbt project reproduced this Data Engineering path’s recurring anchor for the first time this module: 240,917 buckets, 9,554,757 trips, $256,692,373.14 in revenue, checked to the cent against the Scaling Python capstone’s already-published figures. raw.trips_history, a DuckDB view over read_parquet(), held no copy of the 9.5 million source rows — the file itself stayed 274 KB. A quarantine window, the identical one the capstone’s pipeline used, removed exactly 21 stray rows before the final aggregation, and every model in this chain stayed cleanly disabled — SKIP, not ERROR — the moment this project runs against Postgres instead.

Key Concepts#

  • A dbt source can point at files directly through DuckDB, no copy required — read_parquet() inside a CREATE VIEW, the mechanism the DuckDB course’s Module 8 already established.
  • config(enabled = target.type == ...) makes a model target-conditional — compiled away entirely for a target it was never meant to run against, SKIP rather than a broken build.
  • Reproducing an established anchor is itself a form of verification — a third, independent implementation agreeing to the cent with two earlier ones is stronger evidence than either alone.
  • A quarantine window has to be applied exactly, not approximately — the same 2024-01-01/2024-04-01 bounds, confirmed against the original lesson’s source rather than re-derived from memory.

Why This Matters#

Module 5 closes here with CityFlow’s first real business-facing marts — zones, trips, and this guided project’s reproduction of a cross-course anchor — built on a staging layer Module 3 declared and Module 4 tested. Module 6 takes this project’s growing SQL duplication (three models now share nearly identical column lists) and DRYs it up with Jinja and real, reusable macros.
