Welcome to Fact and Dimension Modeling#

A dimension describes something. A fact records something that happened. CityFlow has both waiting in its staging layer: stg_cityflow__zones, one row per zone, describing it; stg_cityflow__trips, one row per trip, an event with a time and an amount. This lesson names the theory, then checks the naming convention this course’s blueprint assumed against what dbt Labs recommends today — and finds the two have drifted apart.

By the end of this lesson, you will be able to:

  • Distinguish a dimension from a fact by grain, not by table size or complexity
  • Explain what a star schema claims about how a fact and its dimensions relate
  • State dbt Labs’ current mart-naming guidance, confirmed rather than assumed

Grain: The Question That Defines a Fact or a Dimension#

“Grain” is the honest answer to one question: what does a single row in this table represent?

stg_cityflow__zones confirms its own grain directly: 265 rows, 265 distinct zone_id values, no repeats. stg_cityflow__trips has 81,013 rows, one per trip — every row is an event with a start time and a dollar amount, with no single column this project kept that could confirm uniqueness the same clean way (Module 4 Lesson 4’s unique_combination_of_columns finding, 20 apparent duplicates, is the honest reason why).

GrainKind
stg_cityflow__zonesone row per zonedimension — describes an entity
stg_cityflow__tripsone row per tripfact — records an event

A dimension is a table whose grain describes an entity — a zone, a customer, a product — the kind of thing a fact table’s rows point back at for context. A fact is a table whose grain is an event or a transaction — a trip, an order, a page view — the kind of thing that gets counted and summed. A star schema is the claim that follows: one fact table sits at the center, and many dimension tables radiate out from it, each describing a different attribute of the same event. trips (fact) points at zones (dimension) through pickup_zone; a more elaborate star could add a payment_types dimension, a drivers dimension, each joined the same way, none joined to each other directly.

Checking the Naming Convention#

This course’s blueprint, written before Module 1 started, planned this lesson around fct_ and dim_ prefixes — the traditional Kimball-style convention most dbt material still teaches. Checking docs.getdbt.com’s current best-practices guide directly turns up something worth stopping for:

✅ Name by entity using plain English: Use the core business concept that forms the grain of the mart — customers, orders, products, locations. ❌ Avoid departmental prefixes: creating finance_orders and marketing_orders for the same concept is an anti-pattern.

No fct_. No dim_. dbt Labs’ current guidance names a mart after the entity it represents, in plain English, organized into subfolders by business domain once a project has enough marts to need them. Star-schema thinking — grain, one fact referencing many dimensions — is exactly as useful a design framework as it always was; only the file-naming layer changed. A team with hundreds of models under the older fct_/dim_ convention has no urgent reason to rename all of them overnight — but a project starting today, following current documentation, lands on plain entity names by default.

This is why CityFlow’s zone and trip marts, built the rest of this module, are named zones.sql and trips.sql — plain entity names, with the theoretical vocabulary (“this is a dimension,” “this is a fact”) staying in this lesson’s prose rather than the filenames. The staging layer’s stg_ prefix is what makes the bare entity name available at the mart layer in the first place: stg_cityflow__zones claims the prefixed name, leaving zones free for the model that actually deserves it.

Practice Exercises#

Exercise 1: Grain, stated precisely#

  • Write one sentence each, in the exact “one row per ___” shape, stating the grain of stg_cityflow__trips, stg_cityflow__zones, and int_trips_summed_to_hour.
  • Decide which of the three is neither a fact grain nor a dimension grain in the traditional sense, and check that against what Lesson 1 already established about the intermediate layer.

Exercise 2: A second dimension, sketched#

  • CityFlow’s trip data has a pickup_time — an event on a specific date, at a specific hour.
  • Sketch, in prose, what a dates dimension for this project might contain (columns, grain), and what new question it would let a mart answer that zones alone cannot.
  • Decide whether every trip needs its own row in a dates dimension the way it needs one in trips itself, or whether the dimension’s grain should be coarser — and if coarser, roughly how many trips would each row in dates end up describing, across CityFlow’s one loaded day?

Hint

A date dimension’s grain is almost always one row per calendar day, holding derived attributes — day of week, is_weekend, month name — that would otherwise need to be recomputed in every mart that needs them.

Summary#

stg_cityflow__zones is CityFlow’s dimension — one row per zone, describing it. stg_cityflow__trips is CityFlow’s fact — one row per trip, an event with a time and an amount. Star-schema thinking, grain and the relationship between a fact and its dimensions, stays a useful design framework — but checking docs.getdbt.com’s current guidance found that dbt Labs no longer recommends fct_/dim_ prefixes at all, favoring plain entity names instead. CityFlow’s marts, built starting next lesson, follow the current guidance: zones and trips, not dim_zones and fct_trips.

Key Concepts#

  • Grain is the honest answer to “one row per what” — the question that distinguishes a fact from a dimension, independent of row count or complexity.
  • A star schema is one fact table referencing many dimension tables — never dimension-to-dimension joins, always through the fact at the center.
  • dbt Labs’ current mart-naming guidance favors plain entity names — confirmed against docs.getdbt.com, not assumed from a book or older dbt material.
  • Theory and file-naming convention are two different things — “this is a dimension” is a design claim; dim_zones.sql is a naming choice, and only the second has changed.

Why This Matters#

Lesson 3 builds zones next — CityFlow’s zone dimension, enriched with a computed is_airport flag no staging model would ever add, since a computation like that belongs at the mart layer, not the rename-only staging layer Module 3 established.
