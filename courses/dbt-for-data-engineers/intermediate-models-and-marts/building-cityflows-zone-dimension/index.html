Welcome to Building CityFlow’s Zone Dimension#

zones.sql is CityFlow’s first mart — the first model in this project meant to be queried directly, not just built on top of. Its job is small on purpose: pass through everything stg_cityflow__zones already has, and add exactly one thing a business question needs that staging was never allowed to compute.

By the end of this lesson, you will be able to:

  • Build a mart model that adds a computed column staging deliberately doesn’t
  • Debug a business rule against its edge cases before trusting an aggregate result
  • Test a mart the same way Module 4 tested a staging model

The Question is_airport Answers#

CityFlow’s zone lookup has 265 rows and no column stating outright whether a zone is an airport — service_zone comes close, but not cleanly:

service_zone = 'Airports' alone would catch JFK and LaGuardia, but miss Newark entirely — its service_zone is EWR, not Airports, because Newark sits outside the standard NYC TLC service-zone scheme. A one-condition rule looks correct until this exact row proves it isn’t.

The flag is worth building because airport pickups behave differently from the rest of CityFlow’s trip data in ways a mart’s consumers would otherwise rediscover by hand every time. Module 3 already found JFK Airport at the top of every revenue ranking this project has produced, well ahead of any non-airport zone — a single boolean column lets a future report filter to or exclude airport trips in one where is_airport clause, instead of every downstream query separately re-deriving which of the 265 zones happen to be airports.

Writing the Mart#

Two conditions, joined with or, catch all three airport zones — zone_name ilike '%airport%' catches any zone with “Airport” in its name regardless of service_zone, kept alongside service_zone in ('Airports', 'EWR') rather than relied on alone. JFK and LaGuardia would already be caught by either condition on its own; only Newark needs the second one — a rule this size still benefits from redundancy, since a future zone whose name happens to omit the word “Airport” (a private terminal, a heliport) would still have a chance of being caught by service_zone.

Confirming the Flag Against Every Airport Zone#

All three, including Newark despite its non-matching service_zone — the second condition caught exactly the row the first alone would have missed. 262 zones report False, and no zone name containing “airport” was left unflagged.

Testing the Mart#

All three pass — zone_id’s uniqueness survives the pass-through, confirmed directly at the mart layer rather than assumed to carry over automatically from staging, and is_airport never produces anything outside true/false, accepted_range’s way of bounding a boolean the same way it bounds a number.

Practice Exercises#

Exercise 1: A single-condition version, proven wrong#

  • Rewrite is_airport using only service_zone in ('Airports', 'EWR'), dropping the zone_name ilike check entirely.
  • Run it and confirm the count of flagged zones is identical to the two-condition version.
  • Explain why this simplification happens to work here, when the lesson’s own reasoning suggested a single-condition version could miss a row.

Exercise 2: A borough-level rollup#

  • Using zones, write a query grouping by borough and counting how many zones each has, with a separate column counting how many of those are airports.
  • Report which borough has the most zones overall, and whether it matches the borough with the most airport zones.

Hint

Re-read Exercise 1’s single-condition version carefully — “identical count” and “identical rows” are two different claims, and only one is guaranteed by this exercise.

Summary#

zones.sql, CityFlow’s first mart, passed through every column stg_cityflow__zones already had and added exactly one computed column: is_airport, requiring two conditions rather than one after checking all three real airport zones individually and finding Newark’s service_zone doesn’t match the pattern JFK and LaGuardia both do. Tested with unique and not_null on zone_id, the identical discipline Module 4 established for staging, now confirmed at the mart layer where a business computation was actually allowed to happen.

Key Concepts#

  • A mart is allowed to compute what staging isn’t — is_airport is exactly the kind of business logic Module 3’s staging convention rules out.
  • A business rule proven on aggregate counts alone can still be wrong — checking each of the 3 real airport zones individually is what caught Newark’s mismatched service_zone.
  • OR-ed conditions each need their own justification — a rule that happens to produce the right count isn’t the same as a rule that’s correct for the right reasons.
  • Mart-layer tests aren’t optional just because staging already tested the source — zone_id’s uniqueness is confirmed again here, at the layer it’s actually relied on.

Why This Matters#

Lesson 4 builds trips, CityFlow’s fact table — and joins it against zones for the first time, the exact operation Module 4 Lesson 3 ruled out at the staging layer and this module’s mart layer exists to allow.

Continue Building Your Skills#

Lesson 4 builds CityFlow’s trip fact table: trips.sql, joined against zones to enrich every one of 81,013 trips with a zone name and borough — this project’s first join in a mart, confirmed to preserve the exact one-row-per-trip grain a fact table needs.
