Welcome to CityFlow’s Warehouse#

Lesson 2 named the dbt Core version this course installs. This lesson installs it against something to point it at: a Postgres container running in Docker.

By the end of this lesson, you will be able to:

  • Stand up a Postgres warehouse in Docker and confirm it’s healthy
  • Explain why this course uses its own dedicated Python environment
  • Scaffold a dbt project with dbt init and confirm a live connection with dbt debug

A Warehouse in Docker#

.dbt-local/docker-compose.yml runs one service: Postgres 16, on a dedicated Docker network, with a named volume so data survives a restart. No custom image, no build step — an official Postgres image is the right choice here.

The named volume matters: without it, stopping and removing the container (something Docker does routinely during a restart or upgrade) would take every row this course loads into raw with it, and every later module’s warehouse state would need rebuilding from scratch. A named volume decouples the container’s lifecycle from the data’s — the same separation a production Postgres deployment relies on.

Healthy within seconds — the container’s healthcheck (pg_isready) confirms Postgres is accepting connections, not just that the process started.

A Dependency Conflict, and Why a Dedicated Environment Fixes It#

Installing dbt-core and dbt-postgres into whatever Python environment is already sitting around is the obvious next step — but a machine used for more than one project usually already has something installed that pins its own dependency versions. Here’s a concrete demonstration, in a throwaway environment with faust-streaming, a popular stream-processing library, already installed:

click is the library both dbt-core and faust-streaming use to parse command-line arguments. dbt-core pulls in a newer click than faust-streaming permits. The fix isn’t forcing one tool’s dependency to win over another’s — it’s giving each project its own environment, so their pinned versions never have to agree:

Clean, in its own environment. Every command in this course, from here forward, runs through .venv-dbt-course.

This is why venv, virtualenv, and pipenv exist at all. Any machine running more than one Python project long enough will eventually install two tools that pin incompatible versions of a shared dependency — click here, but it could just as easily be requests or pydantic. A dedicated environment per project is the standard fix, and it costs nothing beyond the disk space one more site-packages folder takes.

Scaffolding the Project#

dbt init generates the exact dbt_project.yml dbt Core 1.12 expects, with current comments and defaults, plus a starter models/example/ folder most tutorials leave in place unexamined.

Right after that command, listing every file under .dbt-local/cityflow_warehouse/ shows exactly what dbt init created:

models/example/ gets deleted before this course’s first model exists — it’s dbt’s generic starter, not CityFlow data. Leaving it in place means dbt run builds two example models nobody asked for. Deleting the folder without also cleaning up dbt_project.yml’s reference to it produces a harmless warning:

Removing that stale example: block from dbt_project.yml — leaving just +materialized: view as the project-wide default — clears the warning for good.

A Live Connection#

.dbt-local/profiles/profiles.yml holds what dbt_project.yml deliberately doesn’t: the connection details, kept separate so credentials never live inside version-controlled project files.

dbt debug, run against the live container, checks that every field of this connection actually works — not just that the file parses:

dbt debug runs three checks in sequence: that dbt_project.yml parses, that git is installed (dbt uses it internally for package installation, covered in Module 4), and only then the connection test against Postgres. A profiles.yml with a typo fails at the connection-test stage specifically — the first two checks passing tells you the files are fine, not that the warehouse is reachable.

That ordering explains a confusing failure mode: a machine with git missing entirely fails dbt debug at the second check, with an error that has nothing to do with Postgres. Read which of the three checks actually failed, not just that dbt debug failed — Module 4 needs git for something dbt does automatically: installing a package like dbt_utils from its own GitHub repository.

Practice Exercises#

Exercise 1: Break the connection on purpose#

  • Change port: 5438 to port: 5439 in profiles.yml — a port nothing is listening on.
  • Re-run dbt debug.
  • Check the failure message: does it tell you the port is wrong, or just that the connection failed?

Exercise 2: Confirm the conflict a second way#

  • Before deleting .venv-demo-conflict, activate it yourself and try import faust after installing dbt-core into it.
  • Decide: does the import itself fail, or does it succeed while something more subtle breaks?
  • Consider what that difference tells you about how much pip check’s warning alone would have told you without testing it directly.

Hint

A broken dependency pin doesn’t always mean an immediate import error — click’s own CLI-parsing behavior can change in ways that only surface when a specific command-line flag gets used, not on import.

Summary#

CityFlow’s warehouse is a Postgres 16 container, brought up with docker compose and confirmed healthy by its healthcheck. Installing dbt-core and dbt-postgres alongside faust-streaming produced a conflict with its pinned click version, caught by pip’s warning — so this course uses a dedicated .venv-dbt-course instead, confirmed clean by pip check. dbt init scaffolded a working project, and dbt debug confirmed a live connection to the container, running three checks in sequence rather than one.

Key Concepts#

  • A Docker healthcheck confirms readiness, not just that a process started — pg_isready inside the container is what healthy means here.
  • A dependency conflict is worth confirming, not assuming — pip’s own output caught a specific incompatibility before it touched a live course.
  • A dedicated environment is a deliberate boundary, not overhead — the same isolation .kafka-local/ and .airflow-local/ already draw at the Docker level.
  • dbt debug tests three things, not just one — project files, required dependencies, and the connection itself, in that order.
