Welcome to the Guided Project#

Every dbt model this course writes starts from the assumption that data already exists in the warehouse, in a raw schema, waiting to be transformed. This lesson makes that assumption true — a loader script, in plain Python, gets CityFlow’s trip data into Postgres before a single dbt model runs against it.

By the end of this lesson, you will be able to:

  • Load a dataset into Postgres using psycopg2 and a COPY statement instead of row-by-row inserts
  • Explain why this step is deliberately not written in dbt
  • Confirm a load’s correctness independently, against the warehouse directly

The Loader#

The data is the public NYC TLC Trip Record Data — the same January 2024 yellow-taxi month every course in this path uses. Fetch it once and keep it beside .dbt-local/load_trips.py:

Roughly 48 MB, in Parquet — the NYC TLC’s official format for this dataset since 2023: columnar and compressed, so a loader can read selectively (a handful of columns, not all nineteen) without decompressing the whole file first, unlike a CSV of the same data. .dbt-local/load_trips.py reads one day — January 1st, 2024 — out of that file:

81,013 rows, loaded in a fifth of a second. COPY streams the entire buffer to Postgres as one bulk operation, instead of the connection round-trip a loop of 81,013 individual INSERT statements would pay for each row. Bulk operations beat loops whenever the driver offers one — the same lesson this path’s earlier courses already applied to loading.

Why This Isn’t a dbt Model#

Nothing in this script imports dbt, and that’s deliberate. dbt Core has no mechanism for reading a parquet file or opening a connection to an external, non-warehouse source — its interface is SQL, run against a warehouse that already has the data. Getting data into the warehouse is the “EL” half of ELT, owned by whatever tool fits the source: a Python script with a database driver, an ingestion tool like Fivetran or Airbyte in production, or a stream landing directly into a database via Kafka Connect. dbt picks up from here — raw.trips is now exactly the kind of object a dbt source() declaration points at, which Module 3 does next.

Notice, too, what the loader kept and what it dropped. yellow_tripdata_2024-01.parquet ships nineteen columns — vendor IDs, rate codes, payment types, tolls, congestion surcharges, and more — and KEEP_COLUMNS selects exactly four. That’s a decision about what belongs in a raw schema, not an oversight: a raw table should hold what the transformation layer will need, trimmed of columns nobody’s models will reference.

Loading Once, Not Every Time#

Rerunning load_trips.py a second time is safe: DROP TABLE IF EXISTS raw.trips CASCADE at the top means every run starts from a clean slate rather than appending on top of whatever was already there. That’s the right behavior for a course lesson meant to be rerun freely while learning — and a deliberate limitation worth naming: a production loader meant to accumulate history across multiple days needs a different design, one this course builds once incremental loading becomes its own module.

CASCADE matters once Module 2’s models exist: stg_trips and everything downstream of it are views built directly on raw.trips, so a plain DROP TABLE refuses to run once those views depend on it. CASCADE drops those dependent views along with the table, and a later dbt run simply recreates them, since a view is nothing but a stored query. Rerunning this loader never loses any model’s logic, only the objects Postgres was holding.

That distinction is worth being precise about, because it’s easy to conflate “the data disappeared” with “the model definitions disappeared.” raw.trips is data, sitting on disk — gone the moment DROP TABLE ... CASCADE runs. stg_trips is a query, stored as text in a .sql file this loader never touches — gone from Postgres for exactly as long as it takes to rerun dbt run. Losing the first costs a 0.21-second reload; losing the second would mean rewriting logic by hand, something this course’s design never requires.

Confirming the Load Independently#

Trusting the script’s printed row count is one thing; querying the warehouse directly checks that the count is correct:

81,013 rows, spanning the entire day from midnight to two seconds before the next one begins, totaling $2,442,843.25 in revenue for CityFlow’s first day of January 2024. That row count, date range, and revenue figure are the facts every later module’s models get checked against.

Practice Exercises#

Exercise 1: Measure the INSERT alternative#

  • Write a second version of the loader that uses cur.executemany() with individual INSERT statements instead of copy_expert().
  • Load the identical 81,013 rows into a throwaway table and time it.
  • Compare the gap to what this lesson’s framing (“one bulk operation instead of a loop”) predicted.

Exercise 2: Load a second day#

  • Change LOAD_DATE to "2024-01-02" and rerun the loader.
  • Check whether raw.trips ends up holding both days, or whether the second run’s DROP TABLE IF EXISTS erases the first day’s rows.
  • Decide what the loader would need to do differently to accumulate multiple days instead of replacing them.

Hint

The loader’s own DROP TABLE line runs on every single execution, regardless of LOAD_DATE — read it literally before predicting the answer.

Summary#

load_trips.py, using pandas, psycopg2, and a COPY statement, loaded 81,013 NYC taxi trips from January 1st, 2024 into raw.trips in 0.21 seconds — deliberately not written in dbt, because reading a parquet file and connecting to an external source was never dbt’s job. A direct SQL query against the loaded table, independent of the script’s own printed output, confirmed the row count, date range, and $2,442,843.25 in total revenue. That table is now exactly what Module 3’s source() declarations point at.

Key Concepts#

  • COPY beats a loop of INSERT statements — one bulk operation instead of one round trip per row, measured at 0.21 seconds for 81,013 rows.
  • Loading isn’t dbt’s job, on purpose — dbt’s interface is SQL against a warehouse that already has the data; getting it there is a separate concern.
  • A tool’s printed claim is worth checking against the warehouse — the same independent-verification habit Lesson 4 established for a single model.
  • raw.trips is the starting fact for this course — every later module’s models get checked against the row count, date range, and revenue this lesson confirmed.

Why This Matters#

This closes Module 1. CityFlow’s warehouse is running, dbt Core is installed and connected, a first model has run, and trip data sits in a raw schema — everything Module 2 needs to build a dependency graph out of more than one model.
