Welcome to Orchestrating dbt with Airflow#

.airflow-local, the stack this path’s own Airflow course already stood up and this course has quietly run alongside without ever touching, has never once run dbt build. This lesson checks that directly, installs dbt properly inside the same containers, mounts CityFlow’s actual dbt project into them, and writes a working Airflow task that runs a dbt build as a subprocess — triggered live, confirmed against the actual task log and a genuine, logged-in screenshot of the Airflow UI.

By the end of this lesson, you will be able to:

  • Confirm whether a tool is genuinely installed inside a running container before assuming it is
  • Add a new dependency and a new volume mount to a shared Airflow stack without disturbing what already runs there
  • Write, trigger, and verify a working Airflow task that runs dbt build as a subprocess

Confirming dbt Isn’t There Yet#

.airflow-local’s own containers run the official Airflow image, with kafka-python already installed for this path’s Kafka course — nothing about dbt has ever been added to it. This project’s .venv-dbt-course is a Python environment built on the host, for the host’s own architecture; it was never going to be reachable from inside a Linux container regardless, so this check isn’t academic — it confirms the exact gap this lesson closes.

It’s worth being precise about why a shared virtual environment doesn’t already solve this, since the question is a natural one to ask before assuming a whole new install is necessary. A venv bundles two things together: a specific Python interpreter and the packages installed against it. .venv-dbt-course was built by running python3 -m venv on this Mac, against macOS’s own Python build. The Airflow containers run Linux, on the identical arm64 processor this Mac itself uses — Docker Desktop on Apple Silicon runs native arm64 containers, confirmed directly rather than assumed — but a shared CPU architecture doesn’t make a shared operating system. Python wheels compiled with C extensions, psycopg2 among them, are built per platform: a macosx-tagged wheel and a manylinux-tagged one for the identical package aren’t interchangeable, even on identical hardware. Even mounting .venv-dbt-course directly into a container, which this lesson deliberately doesn’t do, wouldn’t make dbt runnable there — the compiled extension built for macOS simply wouldn’t load inside a Linux process.

Installing dbt for Real#

.airflow-local/docker-compose.yaml already uses a documented mechanism for this — _PIP_ADDITIONAL_REQUIREMENTS, the same one the Kafka course’s own module used to add kafka-python:

Both already present — dbt-core==1.12.2 and dbt-postgres==1.11.0, pinned to the identical versions .venv-dbt-course runs on the host, appended to the existing _PIP_ADDITIONAL_REQUIREMENTS string alongside kafka-python==2.3.1 rather than replacing it. A second addition, a new volume line, mounts .dbt-local — CityFlow’s project directory, cityflow_warehouse/ and profiles/ together — into the container at /opt/airflow/dbt-local. Not a copy: the identical .sql files this entire course has written and verified on the host, read directly by whatever runs inside the container.

The identical top-level layout this project’s models/ directory has held since Module 1, visible from inside a container that was never part of this project’s development until this lesson. Nothing about this listing was generated for the occasion — it’s the same hello_cityflow.sql, the same intermediate/, marts/, staging/ split this course established back in Module 1 and has never once reorganized, read through a bind mount rather than copied file by file into the image.

A New Target for a New Environment#

profiles.yml gets a fourth working target now, following the identical pattern Lesson 1 already established for prod — same underlying idea, a genuinely different environment, isolated cleanly by its own schema:

host.docker.internal instead of localhost is the one difference that actually matters — confirmed reachable from inside this stack’s own containers back when this lesson’s infrastructure was first stood up, the identical Postgres port dev and prod already use, cityflow-warehouse’s own 5438 published straight through from the host. schema: airflow keeps every table this lesson’s own DAG creates physically separate from dev’s public, prod’s own prod, and anything a future staging_test target from Lesson 1’s own Exercise 1 might have created — the identical schema-based isolation this module has relied on since its first lesson, reused rather than reinvented for a fourth distinct environment.

The DAG Itself#

--select +zones +zone_revenue, not the bare zones zone_revenue Lesson 3’s own CI gate used — a genuine gotcha this module’s own guided project already caught once, back in Module 7: --select never rebuilds an unselected upstream dependency, and airflow’s own schema starts genuinely empty, with none of zones or zone_revenue’s own staging models built into it yet. The leading + pulls stg_cityflow__zones and stg_cityflow__trips into the same run, exactly as it would for any first build against a brand-new environment. raise RuntimeError(...) on a nonzero exit is this task’s own version of Lesson 3’s sys.exit-shaped gate — Airflow doesn’t read a Python function’s own return code the way a shell does; a raised exception is what marks a @task failed and shows red in the UI.

Triggering It For Real#

AIRFLOW__CORE__DAGS_ARE_PAUSED_AT_CREATION, this project-wide safety default since the Airflow course’s own Module 1, means cityflow_dbt_build sits paused the moment Airflow’s own scheduler first parses this file — a new DAG, on disk, correctly wired, still needs someone to unpause it before it will run at all, scheduled or triggered manually alike. airflow dags reserialize forces a full DB sync first, the same fix a new DAG not yet showing up in dags trigger/unpause always needs, then the unpause itself:

Triggering with -o json rather than the default table output is a deliberate choice, not a style preference — the default table wraps a run’s own dag_run_id across two lines when a real terminal is narrow enough, genuinely painful to parse reliably in a script. A second, worth-naming gotcha surfaces immediately after: airflow dags trigger’s own JSON output names this run’s own ID dag_run_id, but airflow dags list-runs’s own JSON output, checked next, names the identical field run_id — the same value, two different keys, depending on which subcommand printed it.

Matching on this specific run_id, not merely checking whether the word “success” appears anywhere in the output, matters more than it might look. cityflow_dbt_build already has real prior runs from earlier in this lesson — a check that only asked “does any successful run exist” would have passed instantly on the very first poll, regardless of whether the run just triggered had finished, or even started.

Confirming It in the Actual Task Log#

The log path is built directly from this specific run_id, the identical folder-naming convention .airflow-local/logs/ has used since Module 1 of the Airflow course — no globbing, no “whichever log file has the newest modification time,” since a newest-by-mtime search is exactly the kind of check that can pick a stale or still-being-written file the moment more than one run exists, which every retrigger of this lesson’s own code guarantees by the second time it runs. The retry loop exists for a related, honest reason: Airflow marks a task success in its own metadata database a moment before the task’s own log file finishes flushing to disk, a real timing gap worth waiting out rather than assuming away — and worth waiting out generously, since a busier machine (more concurrent Docker containers, a scheduler under real load) can stretch that gap well past a second or two.

The identical dbt build output format this course has read since Module 2, now captured from inside an Airflow task’s own log file rather than a terminal. Fifteen passes, three warnings this project has carried since Module 4 — fare_and_total_signs_agree’s own 111 sign-mismatched trips, stg_cityflow__trips’s own 20 duplicate combinations, stg_cityflow__zones’s own single NULL borough — zero errors, zero skips.

A Real Screenshot, Not a Mockup#

Opening http://localhost:8080/dags/cityflow_dbt_build/grid in a browser, logged in as airflow, shows the identical run this lesson just triggered:

Total success: 1 — read directly from the Airflow UI’s own Details panel, not narrated. A single task, run_dbt_build, a single run, six seconds from start to finish. This is the same UI Module 9’s own docs-site screenshots and this project’s own established Playwright tooling have always captured — extended here, for the first time, with a working login flow, since Airflow’s own webserver sits behind genuine authentication where the DuckDB UI and dbt’s own docs site never did.

Practice Exercises#

Exercise 1: A deliberately broken DAG run#

  • Add a genuinely broken column reference to zones.sql, the identical change Lesson 3 already made and reverted, and trigger cityflow_dbt_build again.
  • Confirm the task fails — red, not green — in a fresh screenshot, and read the actual RuntimeError message Airflow’s own task log records.
  • Restore zones.sql and confirm a subsequent trigger succeeds again.

Exercise 2: A second task, gated on the first#

  • Add a second @task to cityflow_dbt_build_dag, verify_row_count, that queries airflow.zones directly via docker exec cityflow-warehouse psql and confirms it holds exactly 265 rows — the identical NYC TLC zone anchor this project has checked since Module 5.
  • Wire it to run only after run_dbt_build succeeds, and confirm in the DAG’s own Graph view that Airflow draws a genuine dependency arrow between the two.

Hint

Exercise 2’s task ordering follows the identical TaskFlow pattern Module 2 of the Airflow course already established — calling one task’s own return value as another task’s argument is what draws the dependency, not a separate >> operator required for every case.

Summary#

dbt was confirmed genuinely missing from .airflow-local’s own containers before anything else changed. dbt-core==1.12.2 and dbt-postgres==1.11.0, pinned to match .venv-dbt-course exactly, were added to the stack’s own _PIP_ADDITIONAL_REQUIREMENTS; CityFlow’s dbt project got mounted into the containers at /opt/airflow/dbt-local, the identical files this course has always written. A new airflow target in profiles.yml, isolated by its own schema the same way Lesson 1’s prod target was, connects over host.docker.internal. A working Airflow DAG, cityflow_dbt_build, ran dbt build as a subprocess inside a @task, triggered live and confirmed successful against the actual task log — PASS=15 WARN=3 ERROR=0 — and a genuine, logged-in screenshot of the Airflow UI’s own DAG grid.

Key Concepts#

  • Confirm a tool is actually installed before assuming it — which dbt inside the running container, checked before any infrastructure change, not after.
  • _PIP_ADDITIONAL_REQUIREMENTS is this stack’s established mechanism for adding dependencies — the identical pattern the Kafka course already used for kafka-python, extended rather than replaced.
  • A mounted project directory is the actual files, not a copy — CityFlow’s .sql files, read directly by a container that was never part of this project’s development.
  • raise inside a @task is Airflow’s own version of a nonzero exit code — a Python function’s own return value never marks a task failed; an uncaught exception does.

Why This Matters#

A DAG triggered by hand, once, proves the mechanics work correctly — but a working production pipeline runs on a schedule, or in response to an upstream event, never waiting for someone to sit down and type a trigger command. The guided project builds exactly that next: a scheduled CityFlow refresh, running this project’s full staging-to-marts chain entirely on its own, automatically.
