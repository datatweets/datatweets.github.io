Welcome to Running dbt in CI#

Every single dbt build this course has ever run has been watched directly by a person reading the output. A working CI pipeline has no person watching — it has an exit code, and whatever runs next either happens or doesn’t, based entirely on whether that number is zero. This lesson writes the smallest script capable of making that decision correctly, then breaks CityFlow’s project on purpose to prove it decides correctly rather than just looking like it would.

By the end of this lesson, you will be able to:

  • Write a minimal CI gate that runs dbt build and returns its own unmodified exit code
  • Confirm the gate passes cleanly against a working project and fails cleanly against a genuinely broken one
  • Read a genuine failure sequence from dbt’s own output and explain exactly what ran, what didn’t, and why

The Gate Itself#

That’s the entire gate — no framework, no YAML pipeline config, nothing beyond subprocess and sys from Python’s own standard library. dbt build already returns a meaningful exit code on its own: 0 when every node it ran either passed or only warned, nonzero the moment anything actually errors. This function doesn’t invent a new signal to watch — it reads the one dbt already provides and passes it straight through.

This matters because it’s tempting to build something more elaborate: parsing dbt’s own console output for the word “ERROR,” counting how many tests warned versus failed, deciding pass or fail from some threshold computed after the fact. None of that is necessary, and every version of it risks disagreeing with what dbt build itself already decided. dbt’s own exit code already encodes the identical judgment a person reading the console output would make — a warned test is still a pass, an errored one isn’t — so re-deriving that judgment from parsed text is strictly more code with strictly more chances to get it wrong, checking a signal dbt has already computed correctly and handed over for free.

A real CI system — GitHub Actions, GitLab CI, a Jenkins pipeline, Airflow’s own BashOperator in the next lesson — doesn’t need to know anything about dbt specifically to use this function correctly. Every one of them already knows how to check whether a shell command’s exit code was zero; run_ci_gate exists purely to be that shell command, wrapped just enough to be callable from Python rather than typed at a prompt.

Running It Clean#

A genuine 0 — the identical exit code a scheduler, a CI runner, or a shell’s own $? would read to decide the next step in a pipeline is safe to run. This lesson selects zones and zone_revenue specifically for the same reason Lesson 1 did: both are cheap views, keeping this demonstration fast without needing the full twenty-one-model project to prove the gate itself works correctly.

Breaking It For Real#

The same discipline as every lesson before it, applied once more: a gate that has only ever passed hasn’t proven it can catch a genuine failure. zones.sql gets a genuinely broken column reference — a column that has never once existed in stg_cityflow__zones, added directly into the select:

A genuine 1. Whatever would have run next in a working pipeline — a deploy step, a downstream notification, a scheduler marking the whole run green — never gets the chance, because this function’s own return value is the only thing anything downstream ever checks.

Reading What Actually Happened#

The exit code alone says pass or fail, nothing more; dbt’s own full console output, read directly rather than only checked for its numeric return code, shows exactly what that failure looked like in practice:

zones’s own unit test fails first — not the model itself, and not a data test, but test_is_airport_catches_either_condition, the exact node Module 10 Lesson 4 already confirmed runs before its own model in dbt’s own scheduling order. Because that unit test errors on the identical broken SQL the model itself would have run, zones never gets a chance to attempt building at all — SKIP, not ERROR, since dbt never even tried it. Every one of zones’s own three data tests gets skipped for the same reason: they need a working zones table to query, and one was never created. One genuinely broken column reference, caught before the model that contains it ever ran, cascades into four separate SKIP results and a single ERROR — the entire reason dbt build’s own exit code is nonzero, and the entire reason this lesson’s own gate correctly refused to call it safe.

This is worth reading as more than an incidental detail. A team relying only on the exit code would have known this build failed without knowing why — a real, immediate answer either way, but one of them is far more useful when someone actually has to fix it. dbt build’s own console output, captured here and filtered down to just the lines that matter, is the difference between a CI notification saying “the CityFlow build failed” and one that can say, specifically, which node broke and which four downstream checks never even got the chance to run because of it. A real pipeline worth trusting logs both: the exit code a scheduler acts on immediately, and the full output somewhere a person can actually go read the moment that exit code comes back nonzero.

It’s also worth noticing what isn’t in this failure. zone_revenue, selected alongside zones in the identical dbt build call, never appears in the ERROR/SKIP output at all — it built and tested cleanly, unaffected by the broken column sitting in a completely different model. --select zones zone_revenue asked for two independent models with no dependency between them, and dbt’s own scheduler treated them exactly that way: one node’s own failure cascaded only through its own dependents, never bleeding into a sibling selection that happened to run in the identical command.

Confirming the Restore#

Restored, and passing cleanly again — the identical gate, run against the identical selection, now correctly reporting 0 once the broken column reference is entirely gone.

Practice Exercises#

Exercise 1: A gate that checks a specific model, not the whole selection at once#

  • Modify run_ci_gate to accept a required_pass list and check, after the build finishes, that every model in that list actually appears with a PASS or OK status in dbt’s own output — not just that the overall exit code was zero.
  • Consider a concrete scenario where this distinction matters directly: a build with --select naming five models where four succeed cleanly and the fifth gets skipped for a reason entirely unrelated to any of them.

Exercise 2: The fail-loudly parallel, named directly#

  • Reread this path’s PySpark Data Quality module, Lesson 4, “Failing Loudly,” from start to finish.
  • Name the one line of code in that lesson doing the identical job if result.returncode != 0: return result.returncode does here, and explain in one full sentence what’s genuinely the same about the two mechanisms despite one guarding a Spark job and the other a dbt build.

Hint

Exercise 2’s answer is sys.exit(1) — both mechanisms exist for the identical reason: a scheduler or pipeline has no way to know a job failed except by checking an actual process exit code, never by trusting that a job “seemed to run.”

Summary#

A minimal CI gate — a few lines of subprocess and sys, no framework — ran dbt build and returned its own unmodified exit code. Clean, it printed a genuine 0. A deliberately broken column reference in zones.sql made it return a genuine 1, and dbt’s own output showed exactly why: zones’s own unit test caught the broken SQL first, before the model itself was ever attempted, cascading into four separate SKIP results across the model and its own data tests, while zone_revenue, selected in the identical command, built and tested cleanly without any interference at all. Restored, the identical gate reconfirmed 0.

Key Concepts#

  • dbt build’s own exit code is the entire signal a CI pipeline needs — no custom success/failure logic has to be invented on top of it.
  • A unit test failing can prevent its own model from running at all — the model gets SKIP, not ERROR, since dbt never attempts a build it already knows depends on broken logic.
  • A gate that has only ever passed hasn’t proven anything — breaking the project on purpose and confirming a genuine nonzero exit code is the only way to trust the gate before relying on it.
  • This is the identical mechanism Course 2’s Data Quality module built for Spark — sys.exit(1) there, a checked subprocess.run(...).returncode here, both existing so a scheduler can act on a failure without a person watching.

Why This Matters#

A CI gate that runs on a laptop, checked by hand every single time, proves the mechanism works correctly — but nothing yet runs this gate automatically, on a schedule, without someone actually typing the command themselves.
