Welcome to State-Based Selection#

Every --select this course has written since Module 2 has named models directly — zones+, 1+trips+1, +daily_summary. None have ever asked a different question this lesson exists to answer: not “what does this model depend on,” but “what actually changed since the last time this project was built, and what does that affect.” This lesson makes a permanent change to CityFlow’s project, then asks dbt to find it without being told where to look.

By the end of this lesson, you will be able to:

  • Save a manifest snapshot as a working comparison baseline for state-based selection
  • Run dbt list --select state:modified+ against a genuine code change and confirm exactly what it detects
  • Diagnose a confirmed --state path-resolution gotcha this project’s working directory triggers

Saving a Baseline#

state:modified needs something concrete to compare against — a manifest saved from before whatever change is about to happen:

This manifest reflects CityFlow’s project exactly as it stands right now — every model’s compiled SQL, hashed and recorded, before the next section changes anything. state:modified doesn’t compare file timestamps or git history; it compares this saved manifest’s own record of each node’s compiled contents against whatever the project’s current manifest says the identical node compiles to the next time dbt parses it.

Copying target/manifest.json into .dbt-local/state/ rather than pointing --state straight at target/ is a deliberate choice, not an extra step for its own sake. target/manifest.json gets overwritten on every single dbt compile, dbt run, or dbt build this project ever runs from here forward — including the very next command in this lesson, which recompiles the project after the SQL change and would silently erase the baseline this comparison needs. A real CI pipeline hits the identical problem at a larger scale: the manifest from a prior successful deployment has to survive somewhere stable — usually an artifact store or a dedicated state directory checked into the pipeline’s own cache — precisely because the next run’s compile step will overwrite target/ before the comparison ever gets a chance to run.

A Permanent Change#

int_trips_summed_to_hour gets a genuinely new column — avg_fare, the average trip amount per zone per hour, a gap this model has genuinely had since Module 6 wrote it with only a sum() and never an avg() alongside it:

This isn’t reverted at the end of this lesson the way earlier “break it and restore it” demonstrations were — avg_fare is a permanent, useful improvement to a model that’s genuinely been missing it, kept in the project going forward. State-based selection needs a change that actually happened, not a temporary one undone before the lesson finishes.

Finding It Without Being Told Where to Look#

Exactly one model — the one this lesson actually edited, found by diffing two manifests, never told by name which file had changed. Adding + extends the selection to every downstream dependent that model actually has, the identical operator this course has used since Module 2:

Three models — int_trips_summed_to_hour itself, daily_summary, zone_hour_coverage. This is the identical set dbt list --select int_trips_summed_to_hour+ already named directly back in Module 9, without any manifest comparison at all — proof that state:modified+ isn’t discovering some different notion of “affected,” it’s finding the same dependency chain this project has always had, the moment the one node that actually changed is identified correctly. In a project with twenty-one models, a working team rebuilding only these three instead of all twenty-one is the entire point: the other eighteen never needed to run again, because nothing about their compiled SQL changed at all.

What State-Based Selection Doesn’t Catch#

state:modified isn’t a blanket “anything about this node is different” check — dbt’s own documentation lists specific categories it tracks: a model’s compiled body, its configs, its relation (database/schema/alias), upstream macro changes, contract changes — and, worth testing directly rather than assumed, persisted descriptions, but only conditionally:

A brand-new column description, added to a model that had none, and state:modified finds nothing at all. dbt’s own documentation names the exact reason: persisted descriptions only count as a modification when persist_docs is enabled — pushing descriptions into the warehouse as genuine COMMENT ON statements Postgres itself can see. Module 9 Lesson 1 already confirmed, live, that this project has never turned persist_docs on; obj_description() against stg_cityflow__zones came back empty then, and the identical reason applies here. A description-only change genuinely doesn’t affect anything dbt build would need to rerun — no compiled SQL changed, no warehouse metadata changed — so state:modified correctly, deliberately, treats it as nothing worth rebuilding.

A --state Gotcha#

The .resolve() call two code blocks back wasn’t decoration — leaving it out breaks this lesson’s entire premise, worth showing rather than quietly working around:

A relative --state path — the identical directory, .dbt-local/state, that worked correctly once resolved to an absolute one — fails from this project’s own working directory with a nonzero exit code, even though the file genuinely exists at that relative location. dbt resolves --state against something other than the shell’s own current working directory when a relative path is given; rather than track down the exact internal reason, the honest and portable fix is the one already used above — resolve the path to an absolute one in Python before ever handing it to the CLI, which sidesteps the ambiguity entirely regardless of what dbt’s own resolution logic turns out to be doing.

This is exactly the kind of gotcha that’s easy to miss entirely in a one-off terminal session and expensive to hit for the first time inside a real CI pipeline. Typed directly into a shell already sitting in this project’s own root, --state .dbt-local/state looks obviously correct — the directory is right there, one level down, spelled exactly as it appears on disk. A CI runner rarely shares that same assumption about its own working directory; a job’s working directory in a hosted pipeline is frequently some generated path unrelated to where a human would have typed the command by hand, which means a relative --state argument that happened to work on a laptop can fail silently, or fail with an error easy to misread as “the state file doesn’t exist” rather than “the path wasn’t where dbt expected it.” Resolving to an absolute path isn’t a workaround for one confusing error message — it’s the version of this command that behaves identically regardless of which directory happens to be current when it runs.

Practice Exercises#

Exercise 1: A config change, detected on its own terms#

  • Save a fresh baseline first, then change zones.yml’s is_airport test from severity: error (the untouched default) to an explicit config: severity: warn.
  • dbt’s documentation lists config changes as a category state:modified does track, unlike the persisted-description case this lesson just tested — confirm that directly rather than assuming it follows the identical pattern.

Exercise 2: state:modified versus a plain --select naming the same model#

  • Run dbt list --select int_trips_summed_to_hour+ directly, with no --state involved at all, and compare its output character-for-character against this lesson’s state:modified+ result from earlier.
  • Explain in one sentence why a team with dozens of models would still prefer the state:modified+ version in an automated pipeline, even though both commands can return the identical answer for a single known change.

Hint

Exercise 2’s answer is about who has to know which model changed — a person types a model’s name into --select; state:modified finds it without anyone having to know in advance.

Summary#

A manifest saved before any change became this lesson’s own comparison baseline. int_trips_summed_to_hour.sql got a genuine, permanent new column, avg_fare — the deliberately small change state-based selection was asked to detect. dbt list --select state:modified found exactly the one edited model; state:modified+ extended that to its two downstream dependents, daily_summary and zone_hour_coverage — the identical three nodes Module 9’s own direct int_trips_summed_to_hour+ selector already named, now discovered by diffing manifests instead. A --state gotcha surfaced along the way: a relative path fails from this project’s own working directory, fixed by resolving it to an absolute one before handing it to the CLI.

Key Concepts#

  • state:modified compares two manifests’ own compiled node contents, not file timestamps or git history — a saved-in-advance baseline is required.
  • state:modified+ extends the changed set to every downstream dependent that exists — the identical + operator this course has used since Module 2, now driven by a manifest diff instead of a named model.
  • A relative --state path can fail silently from a project’s own working directory — resolving to an absolute path first is the honest, portable fix.
  • State-based selection answers “what actually changed,” not “what depends on this” — the second question needs a person to already know a model’s name; the first one doesn’t.

Why This Matters#

state:modified+ is exactly the mechanism a working CI pipeline needs to rebuild only what a pull request actually touched, rather than this project’s entire twenty-one-model DAG on every single commit. Lesson 3 builds that pipeline directly — a minimal CI-style script gating a live dbt build on its own exit code.
