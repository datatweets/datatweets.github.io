Welcome to the Guided Project#

Lesson 1 confirmed a gap and closed two rows of it: stg_cityflow__zones and stg_cityflow__trips, the first models in this project ever to carry a description:. Nineteen remained then. This guided project closes every one of them — the same direct-count discipline that opened this module, run one more time to confirm there’s nothing left to find.

By the end of this lesson, you will be able to:

  • Write description: fields across an entire project’s remaining models in one pass, not one lesson at a time
  • Confirm full documentation coverage against manifest.json for both this project’s targets, Postgres and DuckDB
  • Capture and read a screenshot of a project’s complete lineage graph, opened with no --select filter at all

Confirming What’s Left#

Six .yml files now, not the five Lesson 1 opened this module against — models/exposures.yml, Lesson 4’s addition, is the fifth of those six with a description already. stg_cityflow__zones.yml and stg_cityflow__trips.yml make four. Seventeen models still have nothing: every mart, every intermediate model, every one of Module 7’s incremental-strategy demos, every DuckDB-only model from Module 5’s guided project. zones and int_trips_summed_to_hour sit in a slightly different state than the rest — both already have a .yml file, carrying real data_tests: blocks, just no description: inside it yet.

Writing Every Remaining Description#

zones and int_trips_summed_to_hour get their existing .yml files rewritten — description: added, every data_tests: block kept exactly as it was:

The other fifteen have no existing .yml file to preserve — a fresh one, description: only, is all each needs. Writing fifteen separate write_text() calls by hand would repeat the same four-line shape fifteen times; a dict keyed by model name, looped once, says the identical thing without the repetition:

Every description in that dict names a real, already-established fact about its own model — which module built it, what it does differently from its nearest sibling, what this course already confirmed about it — not a generic placeholder repeated seventeen times with the model name swapped in. int_trips_batch_append and int_trips_batch_merge read from the identical source with the identical shape, and their two descriptions say so directly rather than pretending each model is a novel discovery.

The loop itself is worth reading as carefully as the dict it walks. Each write_text() call produces the identical four-line shape Lesson 1 wrote by hand twice — version: 2, a models: list with one entry, that entry’s own name: and description: — because that shape is the whole minimum a .yml file needs to carry a description at all; columns: and data_tests: are optional additions this pass doesn’t need for the fifteen models that never had either before now. paths, a second dict keyed by the identical model names, exists only because this project’s models/ directory isn’t flat: int_trips_batch_append lives under intermediate/, stg_cityflow__trips_full under staging/, zone_hour_report two levels down under marts/reporting/ — the same directory structure the docs site’s left-hand navigation has mirrored since Lesson 2, now walked programmatically instead of read by eye.

Confirming Full Coverage, Both Targets#

dbt docs generate against this project’s default target confirms every model it can see is documented:

Eighteen, not twenty-one — zone_hour_report, int_trips_quartered, and stg_cityflow_history__trips are still genuinely absent from a manifest built against the default target, the exact finding Lesson 3 traced to their target.type == 'duckdb' gate. Their descriptions exist in .yml files on disk, but a description in a file the active manifest never includes proves nothing about whether it’s actually reachable. Regenerating against dev_duckdb specifically is the only way to confirm those three properly:

Twenty-one of twenty-one, against the one target where all twenty-one genuinely exist. Full coverage isn’t a claim this lesson makes once and trusts — it’s confirmed twice, once per target, since a single check against the default target alone would have silently missed three real models simply because they never showed up to be counted.

The Complete Lineage Graph#

The docs site’s own Overview page carries the same graph toggle every model page does — clicked here, with no --select filter typed into the explorer’s own bar at all, it draws the whole project rather than one model’s chain:

cityflow_history.trips_history, the source behind stg_cityflow_history__trips, appears at the bottom-left with nothing connected to it — the same target-exclusion finding from a few steps ago, visible here as an isolated node rather than a missing-node warning. zone_hour_report, int_trips_quartered, and stg_cityflow_history__trips are absent from this drawing entirely, for the identical reason they were absent from the Postgres-target manifest count: this screenshot was captured against the docs site currently serving that same manifest. A DuckDB-target screenshot would show all twenty-one; this one, honestly, shows the eighteen a Postgres-target reader would actually see.

Practice Exercises#

Exercise 1: Regenerating against dev_duckdb and re-screenshotting#

  • Regenerate the docs site against --target dev_duckdb, restart dbt docs serve against that manifest, and capture the identical Overview graph again.
  • Confirm all twenty-one models appear this time, including zone_hour_report’s own three-node DuckDB-only chain from Lesson 3.

Exercise 2: A description for a test, not a model#

  • data_tests: blocks can carry their own description: too, a field this lesson never touched.
  • Add one to stg_cityflow__trips’s dbt_utils.unique_combination_of_columns test, explaining in one sentence why it’s configured severity: warn rather than a hard failure.
  • Regenerate the docs and confirm it reaches manifest.json the same way every model-level description in this module already has.

Hint

Exercise 1’s screenshot is worth comparing side by side with this lesson’s own — eighteen nodes against twenty-one, the same gap Lesson 3 first found, now visible as a picture instead of a warning message.

Summary#

Nineteen models Lesson 1 left undocumented all got real description: fields — zones and int_trips_summed_to_hour rewritten with their existing tests preserved, the other fifteen written fresh through a single loop over a dict naming what this course already knows about each one. manifest.json confirmed full coverage against both this project’s targets: eighteen of eighteen Postgres models, twenty-one of twenty-one against dev_duckdb, the three target-gated models included only once the right manifest was checked. A screenshot of CityFlow’s complete lineage graph, opened from the docs site’s Overview page with no filter at all, closed this module — every source, every reachable model, and the one exposure Lesson 4 declared, visible together for the first time.

Key Concepts#

  • A description in an unreachable manifest proves nothing — zone_hour_report’s .yml file was correct from the moment it was written, but only a dev_duckdb-target check actually confirmed it landed anywhere reachable.
  • Full coverage means checking every target a project actually has, not just the default one — a single check would have silently missed three real models.
  • The Overview page’s own graph, filtered to nothing, draws the whole project — the same graph explorer Lesson 3 first opened on one model, here opened with an empty --select instead of a specific one.
  • 21 models, 23 yml files, 23 with a description — the exact gap Lesson 1 confirmed at this module’s opening, fully closed by its own final lesson.

Why This Matters#

Every model in CityFlow’s project can now explain itself to anyone who opens the docs site — no wiki, no tribal knowledge, no description living only in this course’s own prose the way every real finding did before this module started. Three separate tools closed three separate gaps this module found, and it’s worth holding them apart rather than treating “documentation” as one undifferentiated thing: description: fields explain what a model already is, the Lineage Graph confirms how models actually connect to each other, and an exposure names who reads a model’s output from somewhere this project can never see on its own. A project could have any one of the three without the other two — a fully described project with no exposures still can’t answer Lesson 4’s own question about zone_revenue; a project with a perfect lineage graph and zero descriptions still forces every reader back to a wiki for anything beyond a bare list of column names. CityFlow now has all three, and each one covers ground the other two genuinely can’t.

Module 10 tests something none of this module’s tools could. A description: field, the Lineage Graph, and an exposure all describe a model from the outside — what it’s called, what it depends on, who reads it. Not one of them checks whether the SQL inside a model actually does what its own description now claims. Module 10 tests something documentation never could: not what a model is, but whether its SQL logic actually does what it claims, checked against fixtures that don’t need real data to exist at all.

Continue Building Your Skills#

Module 10, Unit Tests and Advanced Testing, starts with the real distinction documentation can’t draw on its own: a data test checks rows that already exist, a unit test checks a model’s own transformation logic against a fixture built specifically to probe it — starting with the exact difference between the two, and why a project needs both.
