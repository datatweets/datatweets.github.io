Welcome to dbt docs generate and dbt docs serve#

Lesson 1’s descriptions are sitting in manifest.json, correctly, but nobody can browse a JSON file the way an actual site gets browsed. This lesson turns them into one: dbt docs generate builds it, dbt docs serve runs it, and a genuine screenshot — not a mockup standing in for one — confirms it actually works.

By the end of this lesson, you will be able to:

  • Explain the difference between what manifest.json and catalog.json each hold
  • Run dbt docs serve and confirm a local site is genuinely reachable
  • Capture and read an actual screenshot of CityFlow’s generated documentation

Two Files, Two Sources of Truth#

dbt docs generate writes two files with genuinely different sources of truth. manifest.json, confirmed in Lesson 1, comes entirely from this project’s own YAML — every description:, every data_tests:, every ref() this project has ever written. catalog.json comes from somewhere else entirely:

integer, text, timestamp without time zone — genuine Postgres types, read by dbt docs generate actually querying information_schema against the live warehouse, not copied from anywhere in stg_cityflow__zones.yml. Nothing in Lesson 1’s YAML ever stated a single column’s type; catalog.json knows them because it asked Postgres directly, the same way this project’s tests have always been checked against the actual database rather than trusted from a schema file alone.

That distinction has a real, honest consequence worth confirming rather than assuming: adding a genuinely new column to a model’s .sql file, without running dbt run first, doesn’t make it appear in catalog.json at all.

brand_new_column never shows up — catalog.json reflects what Postgres’s own zone_revenue view actually has, and that view was never rebuilt, so it never had a reason to change. dbt docs generate alone never runs a single model; it only ever reports on whatever’s already there. A model edited but never rerun leaves its docs page looking exactly as correct as it was before the edit, quietly wrong about what the .sql file currently says — a real reason dbt build before dbt docs generate matters as its own discipline, not an optional extra step.

Serving the Site for Real#

dbt docs serve --port 8095, started before this check ran, answers with a genuine 200 — an actual local HTTP server, not a static file opened directly in a browser. The distinction matters: the site’s own JavaScript fetches manifest.json and catalog.json live, over HTTP, the moment the page loads, which only works when something is actually serving them.

dbt docs generate --help names a real alternative worth knowing about even though this lesson doesn’t use it: --static, which bundles manifest.json and catalog.json directly into a single static_index.html, openable straight from disk with no server at all. That’s a genuinely different trade-off — a file that can be emailed, committed, or opened without dbt docs serve running, at the cost of never refreshing itself the way this lesson’s live server does every time its own JavaScript re-fetches the JSON files. dbt docs serve is the right choice while actively developing CityFlow’s project, checking documentation as it’s written; a static export is the right choice for sharing a snapshot of it with someone who isn’t running this project at all.

A Real Screenshot, Not a Mockup#

Navigating directly to stg_cityflow__zones’s own model page in a real browser, against the live docs server this lesson just started, shows Lesson 1’s work and this lesson’s catalog.json finding on the identical screen:

Every piece on this page came from somewhere this course has now directly verified: the Description panel is manifest.json’s own text, written in Lesson 1; the Type column is catalog.json’s genuine Postgres introspection, confirmed a few steps above; the Data Tests column reflects the identical data_tests: blocks this project has relied on since Module 4. No piece of this page is invented for the screenshot — it’s CityFlow’s actual project, rendered.

A Depends On tab sits alongside Description and Columns, unopened in this screenshot but worth naming here since Lesson 3 spends its whole time on the panel it leads to. For stg_cityflow__zones, it lists exactly one dependency: the cityflow.zones source Module 3 declared. That single-parent simplicity is deliberate on this project’s part, not a limitation of the docs site — a staging model that only ever renames columns off one source is supposed to have exactly one thing feeding it, and a docs page that showed anything more would be reporting a .sql file this project never wrote.

Look, too, at the left-hand navigation the screenshot captured in the same frame: hello_cityflow, intermediate, marts, staging, stg_cityflow__trips, stg_cityflow__trips_batch, stg_cityflow__trips_full, stg_cityflow__zones — the identical directory structure this project’s models/ folder has held since Module 1, mirrored exactly, not reorganized or relabeled for the docs site’s own convenience. dbt docs generate never invents a taxonomy of its own; it reflects the one this project already committed to on disk, the same folders every lesson in this course has read and written to directly.

Practice Exercises#

Exercise 1: A model with no description yet#

  • As of this lesson, only stg_cityflow__zones and stg_cityflow__trips carry a description: — every other model in the project, zones and trips included, still has nothing.
  • Navigate the running docs site to one of them and confirm what the Description panel shows when manifest.json has nothing to put there.
  • Capture a screenshot of it and compare directly against this lesson’s stg_cityflow__zones screenshot (Lesson 5’s guided project closes this gap for every remaining model, zones and trips included, so this exercise only has a real answer to find before that lesson runs).

Exercise 2: Confirming catalog.json updates when the schema does#

  • Add a genuinely new column to any staging model’s select, rerun dbt run for that model, then rerun dbt docs generate.
  • Confirm the new column appears in catalog.json without any change to the model’s .yml file — catalog.json reflects what Postgres actually has, live, every time it’s regenerated, independent of whatever documentation does or doesn’t exist for it.
  • Check the same new column’s row in the docs site’s Columns table directly: confirm its Type shows correctly (from catalog.json) while its Description column sits empty (since nothing in manifest.json was ever told about it) — the two files disagreeing about how much they each know, on the same page, for the identical column.

Hint

Exercise 1’s answer is worth looking at directly rather than guessing — an undocumented model’s Description panel doesn’t error or hide itself, it simply has nothing to show, an honest gap this course’s project still has plenty of until later lessons close it.

Summary#

dbt docs generate writes two files with genuinely different sources of truth: manifest.json, built entirely from this project’s own YAML, and catalog.json, built by actually querying Postgres’s own information_schema for actual column types — confirmed directly, integer/text/timestamp without time zone, none of it copied from anywhere in this project’s .yml files. dbt docs serve started a genuine local HTTP server, confirmed with a 200 response, and a screenshot showed CityFlow’s stg_cityflow__zones page rendering Lesson 1’s descriptions and this lesson’s column types together, on one page neither file alone could have produced.

Key Concepts#

  • manifest.json and catalog.json come from genuinely different places — one from this project’s own YAML, one from a live query against the warehouse itself.
  • A docs site being genuinely live means it’s actually served over HTTP — a 200 response, not a static file opened directly, since the page’s own JavaScript fetches its data live.
  • A screenshot proves the whole pipeline worked, not just one piece of it — description, column type, and test all rendering correctly together on the same page.
  • An undocumented model’s docs page isn’t broken — it simply has nothing to show where a description would go, an honest gap rather than an error.

Why This Matters#

That blue button in the bottom-right corner of every model page — visible in this lesson’s screenshot but never clicked yet — opens CityFlow’s actual lineage graph. Lesson 3 clicks it, and confirms directly that what it draws isn’t a separate picture of this project invented for the docs site’s own convenience, but the identical dependency graph ref() and source() have always defined, the same structure Module 2 first proved with --select alone, long before anything in this module ever rendered it as a picture on screen.
