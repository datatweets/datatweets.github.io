Welcome to Exposures#

Exercise 2 of the last lesson asked what an empty “Referenced By” list actually proves, and the honest answer was: nothing about anything outside this dbt project. zone_revenue could feed a dashboard forty people check every morning, and this project’s Lineage Graph would still draw it with nothing downstream — because nothing downstream inside dbt exists. This lesson closes that gap the only way dbt provides: declaring the consumer directly, in YAML, as an exposure.

By the end of this lesson, you will be able to:

  • Write an exposures: block declaring a downstream consumer of a CityFlow mart
  • Confirm an exposure lands in manifest.json, not just the source .yml file
  • Resolve an exposure’s complete upstream chain with dbt list --select +exposure:name

Declaring a Consumer#

CityFlow has no live dashboard anywhere — this course has never built one, and won’t pretend to. What it can do honestly is declare the shape a real one would take, using the exact fields dbt requires and nothing invented beyond them:

name, type, and owner are the only fields dbt requires — type must be one of dashboard, notebook, analysis, ml, or application, and owner needs at minimum a name or an email, confirmed against dbt’s own documentation before writing a single line here rather than guessed from a template. maturity is one field worth naming honestly rather than treating as decoration: its valid values are low, medium, and high, and dbt’s documentation describes high as a well-established dashboard trusted across an organization and low as a new or experimental analysis. medium here is a genuine judgment call, not a computed value — nothing about this exposure’s dependency chain can tell dbt how much an organization actually trusts a dashboard, so the field exists for a human to state that directly rather than have dbt guess at it. maturity, url, description, and depends_on are all optional, but depends_on is the field doing the actual work this lesson cares about: two ref() calls, the identical function every model in this project has used since Module 2, pointed at int_trips_pivoted_by_borough and zone_revenue instead of at another model.

Confirming It Reached the Manifest#

A clean exit proves the YAML parsed; it doesn’t prove dbt actually recognized this as an exposure rather than silently ignoring an unfamiliar block. manifest.json carries its own top-level exposures key, separate from nodes, worth reading directly:

depends_on.nodes already shows dbt resolved both ref() calls into fully qualified node IDs, the same resolution every model’s own depends_on has gone through since Module 2 — an exposure isn’t a comment describing a dependency, it’s a real edge in the same graph every --select command in this course has always operated on.

Resolving the Full Upstream Chain#

+exposure:name selects everything upstream of an exposure the same way +model selects everything upstream of a model — the identical + operator, pointed at a node type this course hasn’t selected from before. --resource-type needs naming twice, once for model and once for source, since sources are their own resource type rather than a kind of model:

Ten nodes, not the two named directly in depends_on. int_trips_pivoted_by_borough and zone_revenue were the only models this lesson wrote by hand, but +exposure:cityflow_borough_dashboard walks past both of them to everything either one is built on. int_trips_pivoted_by_borough reads trips, and trips itself reads two parents — stg_cityflow__trips_full and zones — the exact pair Lesson 3’s screenshot already drew. zones in turn reads stg_cityflow__zones, which reads the raw cityflow.zones source; stg_cityflow__trips_full reads its own cityflow.trips_full source directly. zone_revenue reads stg_cityflow__trips, which reads cityflow.trips — a separate source from the one trips depends on, since Module 7’s staging split a single-day load from a full-history one and this project has kept both ever since. A dashboard depending on two marts is really depending on three raw sources and five models in between, whether the dashboard’s owner realizes that or not — the exact kind of hidden depth an exposure’s upstream selector makes checkable in one command instead of left to guesswork.

Passing a selector with no leading + behaves differently, worth confirming rather than assuming from the +model/model+ pattern Module 2 already taught: --select exposure:cityflow_borough_dashboard, no + at all, returns only the exposure node itself, nothing upstream of it. The + isn’t decoration on the selector string — it’s the entire instruction to walk the graph in a direction; without it, dbt list answers “does this one node exist and match,” not “what does it depend on.”

--resource-type exposure on its own, with no --select at all, lists every exposure in the project the same way --resource-type model has listed models since Module 2:

One entry, listed with an exposure: prefix on its own name the same way a source’s own listing carries a source: prefix — dbt list treats exposures as a resource type on equal footing with models, sources, and tests, not an afterthought bolted onto the selector syntax after the fact.

The Docs Site’s Own Exposures Section#

The running docs site carries an Exposures entry in its left-hand navigation, alongside Sources and Projects, that was empty before this lesson and isn’t now. Opening cityflow_borough_dashboard’s exposure page:

An exposure’s own page carries the same Lineage Graph panel Lesson 3 spent its whole time reading — clicking it here draws the exposure itself as the rightmost node, with int_trips_pivoted_by_borough and zone_revenue as its two immediate parents, exactly matching depends_on.nodes from the manifest check above. The graph doesn’t stop treating an exposure as a special case; it’s one more node type in the same structure everything else in this module has already been reading.

Practice Exercises#

Exercise 1: A second exposure, a shorter chain#

  • Declare a second exposure, cityflow_ops_notebook, type: notebook, depending only on daily_summary.
  • Run dbt list --select +exposure:cityflow_ops_notebook --resource-type model --resource-type source and confirm its upstream chain is shorter than cityflow_borough_dashboard’s own — four nodes instead of ten, since daily_summary’s chain (confirmed in Lesson 3) never branches the way trips does.

Exercise 2: The Exposures category in the sidebar#

  • Navigate the running docs site’s Overview tab. Its left-hand navigation carries an Exposures section, grouped by type, sitting above Projects.
  • Confirm cityflow_borough_dashboard appears under a Dashboard category there, and consider what a second exposure with a different type (Exercise 1’s cityflow_ops_notebook, type: notebook) would add to that same section.

Hint

The sidebar groups exposures by type rather than listing every one flat — worth noticing directly rather than assuming it works the same way the Sources or Projects trees above it do.

Summary#

cityflow_borough_dashboard, a dashboard exposure with a real owner and two depends_on entries pointing at int_trips_pivoted_by_borough and zone_revenue, was declared for CityFlow for the first time — confirmed in manifest.json’s exposures key, not just the source .yml file. dbt list --select +exposure:cityflow_borough_dashboard resolved its complete upstream chain: ten nodes, not the two named directly, reaching back through both marts’ staging layers to three separate raw sources underneath them. The docs site’s own Exposures section rendered the same dependency, grouped by type in the sidebar and detailed on the exposure’s own page, with a Lineage Graph panel behaving exactly as it did for every model page in Lesson 3.

Key Concepts#

  • An exposure is a real edge in the manifest, not a comment describing one — depends_on.nodes resolves fully qualified node IDs the same way every model’s ref() calls do.
  • +exposure:name walks the exposure’s complete upstream chain — the identical + operator this course has used since Module 2, now starting from a node type outside nodes entirely.
  • A short depends_on list can hide a long real dependency — two named models resolved to ten actual upstream nodes once every ancestor was counted.
  • The docs site treats an exposure as one more node, not a special case — the same Details/Depends On/Lineage Graph layout every model page already carries.

Why This Matters#

Every earlier lesson in this module documented what already exists inside CityFlow’s project. An exposure documents something this project can’t see on its own — what reads its output once a dbt run finishes — closing the one blind spot no description: field or lineage graph, however complete, was ever going to close by itself. Consider the practical version of the question Exercise 2 of Lesson 3 raised: before this lesson, zone_revenue’s own “Referenced By” tab read empty, exactly the state that made deleting it look safe. Reload that same tab now, and it carries a new “Exposures” heading with cityflow_borough_dashboard listed underneath — the identical panel, still telling the truth, now able to tell a truth it couldn’t see before this lesson gave it something to report. Someone proposing to drop zone_revenue today would see that entry before touching a single line of SQL, rather than finding out a dashboard broke only after it did.
