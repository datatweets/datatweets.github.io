Welcome to Documenting Models and Columns#

Every genuine finding this course has made — a NULL borough, a duplicate-key trap, a cross-course anchor checked to the cent — has lived in this course’s own prose. None of it has ever lived in the project itself. This lesson checks that claim directly, then starts fixing it.

By the end of this lesson, you will be able to:

  • Confirm, directly against a project’s own files, how much of it is actually documented
  • Write description: fields at both the model and column level
  • Confirm a written description actually reaches dbt’s own manifest, not just the source .yml file

Confirming the Gap#

21 models, built across eight modules of this course’s narrative — and only one .yml file in the whole project has ever had a description: field at all: __sources.yml, the sources file Module 3 wrote back when this project first declared raw.trips and raw.zones. Every model, every mart, every snapshot — zones, trips, zone_hour_report, zones_snapshot — has never had one.

Writing the Descriptions#

stg_cityflow__zones and stg_cityflow__trips, Module 3’s original staging pair, get the first genuine descriptions in this project — at both the model level and the column level:

Nothing about the data_tests: blocks changed — every test this project already relied on is untouched. description: sits directly alongside them, in the identical file, at the identical level: a model-level description: under the model’s own name:, a column-level one under each column’s name:, the same place data_tests: has always lived.

Confirming It Actually Reached dbt#

dbt docs generate exiting cleanly proves the YAML parsed; it doesn’t prove the description text actually made it where it needs to go. Reading manifest.json directly, the file dbt docs serve will actually read from, confirms it did:

Every one of the three descriptions this lesson wrote is sitting in manifest.json, word for word, ready for dbt docs serve to render — not assumed from a clean exit code, confirmed by reading the exact file the docs site itself reads.

Postgres itself, worth checking honestly, doesn’t know any of this happened:

Empty. A description: in dbt’s own YAML lives in manifest.json, not as a real Postgres COMMENT ON — dbt docs generate never touches the warehouse’s own catalog metadata, only its own build artifacts. dbt does have a persist_docs config that would push descriptions into the warehouse as real COMMENT ON TABLE/COMMENT ON COLUMN statements, visible to any tool querying Postgres directly instead of dbt’s docs site — not configured here, worth naming honestly as a gap this lesson’s descriptions don’t close: someone querying stg_cityflow__zones straight from psql, the way every earlier lesson in this course has, still sees no documentation unless they specifically go looking in dbt docs serve.

That’s a deliberate choice for this module to leave alone rather than a mistake to fix. persist_docs needs relation: true/columns: true set in dbt_project.yml, applying to every model in the project at once — a permanent change to how every future dbt run behaves, not a one-off addition the way writing a description: field is. This module’s own scope is getting real documentation written and browsable through the tool dbt itself provides for exactly that purpose; deciding whether this project’s Postgres warehouse should carry that documentation as native comments too is a genuine, separate decision, left unmade rather than defaulted into silently.

Why This Beats a Wiki#

The parallel to this module’s own opening claim is worth drawing directly. Module 8’s zone 65 reassignment showed zones silently losing history the moment nothing was built to remember it — not because anyone intended that, but because nothing existed to catch the gap before it mattered. A wiki drifting out of sync with the codebase it describes is the identical failure shape: not a deliberate choice to stop documenting, just an absence of anything forcing the two to stay connected. description: fields don’t solve documentation the way a snapshot solved history — they solve it the same way a snapshot did, by putting the thing worth remembering somewhere it can’t quietly fall out of sync with what it’s describing.

A description written here lives in the identical file, in the identical commit, as the test it sits next to — borough’s description names the two genuine placeholder values in the same breath its accepted_values test enforces them. A wiki page describing the same column lives somewhere else entirely: a different tool, a different edit history, no mechanism connecting a change to one with a change to the other. The staging convention could be renamed, a column could be dropped, and a wiki page would say nothing about either until someone remembered to go update it — which, honestly, is the entire reason a wiki documenting an actively changing codebase tends to drift out of date within months of being written, not because anyone intends it to.

description: doesn’t fix that problem by being smarter; it fixes it by refusing to be a separate thing at all. The same dbt run that would fail if stg_cityflow__zones.sql and its .yml file disagreed about a column name is the same mechanism keeping a description physically incapable of drifting silently away from the model it describes — not because dbt checks the prose for accuracy, but because there’s nowhere else for the description to live.

Worth being honest, too, about what a description: field can’t fix. Everything this lesson writes explains what a model already is — its columns, its known placeholder values, its tests. None of it says who reads a model’s output once dbt run finishes, and a wiki page never answered that question any better than a description: field does. Lesson 4 closes that separate gap with an exposure, a different kind of documentation entirely: not what a model is, but what depends on it from outside this project. The two problems look similar — both are about a project explaining itself — but they need genuinely different tools, and confusing one for the other is its own honest mistake worth naming before it’s made.

Practice Exercises#

Exercise 1: Documenting a mart#

  • As of this lesson, zones, Module 5’s mart, still has no description: anywhere. Write one for the model level, plus is_airport, naming its two-condition OR logic.
  • Regenerate the docs and confirm the new description reaches manifest.json the same way this lesson’s staging descriptions did (Lesson 5’s guided project writes this same description for real, so check your answer against it once you get there).

Exercise 2: A description that would have caught a real mistake#

  • Write a description: for trips.trip_id explaining, in one sentence, why it’s the column unique_key should always be — the exact lesson Module 7’s Lesson 4 taught the hard way with a corrupted composite key.
  • Consider, honestly, whether a description like this would have prevented that lesson’s mistake, or only made it faster to diagnose once it happened.

Hint

Exercise 2 doesn’t have a clean answer — a description is prose a person has to read, not a constraint dbt enforces the way a unique test does. It’s worth being honest about what documentation can and can’t prevent, not just what it can explain after the fact.

Summary#

A direct count confirmed the gap before this lesson tried to close it: 21 models, 5 .yml files, only 1 with any description: field anywhere in this project. stg_cityflow__zones and stg_cityflow__trips, Module 3’s original staging pair, got the first genuine descriptions — model-level and column-level, including the two placeholder findings Module 3 already made about zone 264 and zone 265. Reading manifest.json directly confirmed every description actually reached the file dbt docs serve renders from, not merely the source .yml file.

Key Concepts#

  • description: lives at both the model and column level — the identical place data_tests: already lives, not a separate documentation system.
  • A clean dbt docs generate exit proves the YAML parsed, not that the description landed correctly — reading manifest.json directly is the actual confirmation.
  • Documentation-as-code can’t drift the way a wiki does — not because it’s smarter, but because there’s nowhere else for it to live except the file the model itself lives in.
  • A description explains; it doesn’t enforce — Exercise 2’s own honest limit, worth remembering before treating documentation as a substitute for an actual test.

Why This Matters#

manifest.json and catalog.json now hold actual descriptions for the first time — Lesson 2 turns them into something a person can actually browse: a local dbt docs site, generated and served.

Continue Building Your Skills#
