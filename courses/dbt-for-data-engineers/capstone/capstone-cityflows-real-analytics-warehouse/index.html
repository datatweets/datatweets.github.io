Welcome to the Capstone#

Eleven modules built eleven working pieces. Module 1 loaded a day of CityFlow’s trip data into a Postgres warehouse and ran a first model. Module 2 built a branching DAG with ref() and source(). Module 3 declared sources and shaped a proper staging layer. Module 4 tested it — generic tests, a singular test, dbt_utils. Module 5 built real marts and reproduced this path’s zone-hour-report anchor for the first time, inside dbt. Module 6 wrote macros to DRY up duplicated SQL. Module 7 converted a fact table to incremental, handling 9.5 million rows without a full rebuild every run. Module 8 recovered history a plain mart forgets, with a snapshot. Module 9 documented every model and read the lineage graph. Module 10 wrote unit tests catching logic no data test could ever see. Module 11 added a second environment and a scheduled Airflow DAG, and found a concurrency bug live along the way.

This module doesn’t add a twelfth piece. It asks a harder question of the other eleven, together: if this project’s source code is correct, does it actually reproduce a working warehouse from nothing, or has fifty lessons of accumulated manual fixes in the dev schema been quietly propping it up?

dev’s public schema has never been empty since Module 1 — every model, snapshot, and test has always run against a schema that already had something in it. This capstone builds against a schema that has nothing in it at all, checks that build with the same discipline every earlier module used, and then closes the loop against a number five other courses in this path have already reached by entirely different means.

By the end of this lesson, you will be able to:

  • Confirm a Postgres schema holds nothing before running a single line of dbt against it
  • Run this project’s complete, unrestricted dbt build — every model, every test, both snapshots — and read what a clean build from nothing actually looks like
  • Check full documentation coverage directly against the manifest, not by eyeballing the docs site
  • Write a new Postgres-native mart reusing macros this course wrote five modules ago, closing a gap Module 9 first found
  • Wire two Airflow tasks together with a real dependency, the first DAG in this course to chain more than one task
  • Reconcile CityFlow’s warehouse to the exact figure five earlier courses in this path already established, entirely in SQL

You’ll need this course’s own running Postgres warehouse (cityflow-warehouse, port 5438), the .airflow-local stack from Module 11, and .venv-dbt-course — nothing new to install. Let’s close the loop.

The Acceptance Criteria#

Before writing a line of this capstone, here is what “done” means, checked against output rather than trusted on faith:

  1. A schema confirmed empty before anything runs. Not assumed clean — checked directly against Postgres’s own catalog.
  2. A complete, unrestricted build, zero errors. Every model, every data test, every unit test, both snapshots — one dbt build, no --select narrowing what runs.
  3. Full documentation coverage, confirmed against the manifest. Every model with a description: field, checked in code, not by reading the docs site and hoping nothing was missed.
  4. A new report model, correct to the cent. capstone_zone_hour_report, built with existing macros, matching the anchor exactly.
  5. A two-task Airflow DAG, both tasks green. One task builds the project; a second, dependent task checks the reconciliation itself and fails the run if it’s wrong.

Step 1 — Confirm the Warehouse’s Raw Data Is Still There#

Everything this capstone builds depends on raw, the schema Module 1’s loader filled once and every later module has only ever read from. Before building anything new, confirm what’s actually sitting there:

Four tables, unchanged since the modules that loaded them: a day of trips from Module 1, the 265-zone lookup, Module 7’s 9,554,778-row full history, and Module 7 Lesson 4’s synthetic batch. raw is shared by name across every target this project has ever defined — dev, prod, airflow, and the new capstone target this lesson adds — because a dbt source() points at a fixed schema, not the target’s own output schema. That single fact is what makes the rest of this lesson possible: a brand new target can read this data without reloading a single row.

Nineteen, not the twenty-one Module 9 counted — zone_hour_report and its upstream int_trips_quartered are both gated target.type == 'duckdb', so a Postgres-target manifest never sees them at all, the identical absent-not-hidden behavior Module 9 Lesson 3 first proved. Summary#

CityFlow’s warehouse rebuilt itself from nothing: a schema confirmed empty, then one unrestricted dbt build — 19 models, 18 data tests, 3 unit tests, 2 snapshots — reaching PASS=39 WARN=3 ERROR=0 with no manual intervention. Documentation coverage checked directly against the manifest: 19 of 19. A new Postgres-native report model, capstone_zone_hour_report, reused Module 6’s hour_bucket and round_money macros to close the gap zone_hour_report’s DuckDB-only gate left open, landing on the exact anchor to the cent. A new two-task Airflow DAG — the first in this course to chain a real dependency — ran the complete build and then checked that reconciliation itself, both tasks screenshotted green. Five other courses in this path already reached 240,917 buckets, 9,554,757 trips, $256,692,373.14; this capstone is the sixth, entirely in SQL.

Key Concepts#

  • A source() points at a fixed schema, not a target’s own output schema — which is what let a brand new capstone target read raw’s existing data without reloading a single row.
  • Confirming a schema is empty beats assuming it is. This lesson dropped capstone outright and checked Postgres’s own catalog before building anything — the difference between “should be clean” and “is clean.”
  • A target.type gate works in either direction. zone_hour_report excludes Postgres; capstone_zone_hour_report excludes DuckDB — the identical mechanism, aimed the other way.
  • Airflow task dependencies (>>) only appear when a DAG actually needs one. Eleven prior DAGs in this course got by with a single task each; this capstone’s own two-step build-then-check finally needed real ordering.

Why This Matters#

A dbt project that only ever runs against a schema that’s accumulated fifty lessons of history hasn’t proven it can be rebuilt — it’s proven it can be maintained, which is a different and easier claim. This capstone rebuilt CityFlow’s entire warehouse against a schema that held nothing, using only the project’s own source code, and reached the identical, exact figure five other courses in this path already established through entirely different tools. That’s the actual claim a production dbt project has to be able to make: not that it currently works, but that it would still work if it had to start over.

What You’ve Built#

Twelve modules, one warehouse. Module 1 loaded a day of trips and ran a first model against a real Postgres warehouse in Docker. By Module 5, that warehouse had real marts and a first reproduction of this path’s own anchor figure. Module 7 made a 9.5-million-row fact table rebuild in seconds instead of minutes. Module 9 gave every model a description and a lineage graph. Module 10 caught logic no data test could see. Module 11 gave the project a second environment and taught it to run on a schedule, unattended. This capstone took the whole project and asked it to prove itself from nothing — and it did, in fifty-three seconds, with zero errors.

Every number in this lesson — the 9,554,778 raw rows, the 19 of 19 documented models, the 240,917 buckets, the 9,554,757 trips, the $256,692,373.14 — was measured against this course’s own infrastructure, the same discipline every module insisted on since Module 1 Lesson 1. Twelve modules, one warehouse, and one number that has now been true six different ways.

Practice Exercises#

Exercise 1: Prove the fresh build wasn’t a fluke#

  • Drop the capstone schema a second time and rerun Step 2’s build.
  • Confirm the identical PASS=39 WARN=3 ERROR=0 result.
  • Explain, in a sentence, why a build reaching the same exact pass count twice in a row is stronger evidence of reproducibility than reaching it once.

Exercise 2: Add a data test to the new report model#

  • capstone_zone_hour_report currently has three tests: two not_null checks and one uniqueness check. Using Module 4’s own dbt_utils.accepted_range pattern (already applied to zones.is_airport since Module 10), add a test confirming trips is never negative on any row.
  • Run it, confirm it passes against real data.
  • Break it on purpose by editing the model to allow a negative count and watch the test catch it.
