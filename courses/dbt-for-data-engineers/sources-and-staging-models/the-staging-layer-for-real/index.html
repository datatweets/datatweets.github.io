Welcome to the Staging Layer, For Real#

Module 2’s stg_trips proved the mechanism — a model reading a source, renaming a few columns, feeding everything downstream. This lesson names the convention that model should actually follow, checked directly against dbt Labs’ current best-practices documentation.

By the end of this lesson, you will be able to:

  • Name a staging model correctly using the stg_<source>__<entity> convention
  • Explain why a source’s declared name, not its schema, drives that naming
  • Distinguish what belongs in a staging model from what belongs one layer downstream

The Convention, From dbt Labs Directly#

docs.getdbt.com’s current best-practices guide is precise:

SegmentRule
stg_Fixed prefix on every staging model, no exceptions — the whole layer sorts together in any file browser or the dbt docs site.
<source>Names the source system, not necessarily the schema it lives in — the name declared under sources: in __sources.yml.
__A double underscore, not a single one, separates the source segment from the entity segment — deliberate, so a name containing its own underscore never becomes ambiguous.
<entity>Plural, matches one source table exactly — one staging model per source table, never more than one.

Applied to CityFlow: raw (the source name) plus trips (the entity) would read stg_raw__trips — technically correct, but a source named after the schema it lives in defeats the convention’s purpose. sources.yml’s name: key was always meant to be decoupled from schema: — Lesson 1 pointed out the two only match here by coincidence. Renaming the source itself from raw to cityflow — schema unchanged — makes the convention read the way it’s meant to: stg_cityflow__trips, naming what the data represents rather than which Postgres schema happens to hold it.

The guide is just as specific about how staging models sit on disk: subfolders under models/staging/ are organized by source system, one folder per system. A project pulling from Stripe, an internal application database, and a marketing platform would have three folders — staging/stripe/, staging/app_postgres/, staging/marketing/ — each holding that system’s own __sources.yml, staging models, and YAML property files together. CityFlow has exactly one source system, cityflow, so this project doesn’t yet need subfolders. The distinction matters for naming, not just tidiness: a second entity gets its own stg_cityflow__<entity> model beside stg_cityflow__trips; a second system would earn its own subfolder and its own __sources.yml.

What Belongs in a Staging Model, and What Doesn’t#

The convention isn’t just a naming rule — docs.getdbt.com is equally specific about what a staging model is allowed to do to its data.

Allowed: renaming columns to a consistent standard, type casting, small computed columns (a currency conversion, a derived flag), categorizing values into buckets.

Not allowed: joins (they duplicate computation and blur where a row came from) and aggregations (a staging model keeps the exact grain of its source table — one output row per one input row, always).

The reasoning behind “no joins” is worth sitting with, not just memorizing. If stg_trips joined raw.zones directly to add a zone name column, and a second staging model elsewhere also joined raw.zones for its own reasons, the same lookup logic would exist in two places — a discrepancy between them would surface as two different answers to what should be one question. Keeping the join out of staging and doing it once, in an intermediate or mart model both staging models can share, means there’s exactly one place that logic can go wrong.

Checking stg_trips.sql against the allowed/disallowed list, found by pattern rather than a hardcoded filename, since this exact model is the one Lesson 4 renames next:

No join, no aggregation — one computed column (total_amount - fare_amount as tip_and_fees), exactly the “basic computation” the convention allows, and the row count in equals the row count out. stg_trips was built correctly before this lesson named the rule it follows; what it’s missing is the naming convention itself, and its source’s own name still points at a schema label rather than a meaningful system name — both of which Lesson 4 fixes.

Practice Exercises#

Exercise 1: Name a hypothetical second entity#

  • If CityFlow’s zone lookup data (Lesson 5’s second raw table) is declared under the same cityflow source, work out what its staging model should be named, following the convention exactly.
  • Write the filename before Lesson 5 confirms it.

Exercise 2: Find a join that should never have been in staging#

  • Sketch (in prose, no need to run it) a stg_trips.sql variant that joins against a hypothetical raw.zones table to add a zone name column directly.
  • Using the convention’s own reasoning, identify which specific layer that join belongs in instead.
  • Explain why doing it in staging would make a later change to the zone lookup harder to trace.

Hint

The convention’s reasoning is about duplicated computation and losing track of a row’s origin — think about what happens if two different staging models both join the same lookup table independently.

Summary#

dbt Labs’ current staging convention names itself precisely: a fixed stg_ prefix, a source-system segment matching the name declared under sources:, a double underscore separating it from a plural entity segment, and one model per source table. Checked directly against stg_trips.sql, Module 2’s model already follows the transformation rules — no join, no aggregation, one small computed column. What it’s still missing, its full convention-compliant name, is exactly what Lesson 4 fixes.

Key Concepts#

  • stg_<source>__<entity> names three things, each with a job — a fixed layer marker, the source system, and the specific table, never blended into one ambiguous string.
  • A source’s declared name should describe the system, not the schema — raw was a placeholder; cityflow says what the data actually is.
  • Staging models rename and cast; they never join or aggregate — confirmed directly against stg_trips.sql’s own text.
  • One staging model per source table is a hard rule, not a guideline — the one-to-one relationship is what keeps a large staging layer navigable.

Why This Matters#

Lesson 4 does the rename this lesson set up: stg_trips becomes stg_cityflow__trips, the source gets renamed from raw to cityflow, and every downstream ref() in the project follows automatically.

Continue Building Your Skills#

Lesson 4 performs the rename live: stg_trips.sql becomes stg_cityflow__trips.sql, zone_revenue.sql and int_hourly_pattern.sql get their ref() calls updated, and dbt run confirms the entire project still produces the identical 81,013-trip, $2,442,843.25 figures afterward.
