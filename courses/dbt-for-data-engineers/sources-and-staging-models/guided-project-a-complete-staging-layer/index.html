Welcome to the Guided Project#

Every model this module has touched read from one table: raw.trips. This guided project gives CityFlow’s staging layer a second one — the NYC TLC’s official taxi zone lookup, 265 rows mapping every LocationID this project has been grouping trips by into a borough and zone name.

It’s also this project’s first dimension table, though nothing in this module has called it that yet — Module 5 introduces the vocabulary directly. A trip row changes constantly, one new record per ride; a zone almost never does, the same 265 rows describing the same 265 physical locations for as long as this course’s dataset holds January through March 2024 constant. That difference in how often a table’s rows change is why zones gets a freshness: null exemption a few steps ahead, and why joining zone_revenue against it, rather than against raw.trips directly, is the shape Module 5’s marts will build on.

By the end of this project, you will be able to:

  • Load a second raw table into the warehouse using the same loader pattern as the first
  • Declare a second source table with its own, independently correct freshness configuration
  • Stage it following the stg_<source>__<entity> convention, confirmed compliant like the first

Step 1: Loading CityFlow’s Zone Lookup#

The NYC TLC’s official zone reference — the same file the Data Engineering path’s scaling-python-for-data-engineering course uses — is hosted directly on this site, no separate download needed:

265 zones, 7 boroughs — Manhattan, Brooklyn, Queens, the Bronx, Staten Island, Newark’s own airport zone (EWR), and an “Unknown” catch-all the TLC’s schema reserves for unmatched trips. This loader follows the identical shape Module 1’s load_trips.py established: pandas to read the source, a DROP ... CASCADE for a clean rerun, and a psycopg2 COPY rather than row-by-row inserts, even on a table three orders of magnitude smaller than raw.trips.

Using the same pattern regardless of size is deliberate, not an oversight. A loader that switches strategies based on row count — row-by-row inserts for a small lookup table, COPY only once a table crosses some threshold — is a second code path to test, maintain, and eventually get wrong, for a performance difference that only ever matters on the larger table. One loading pattern, used everywhere, is simpler to reason about than two.

Step 2: Declaring the Second Source#

config: freshness: null — Lesson 2’s reference docs named this option; this is the first use of it. A lookup table like raw.zones gets loaded once and rarely touched again, so checking it against the same 24/48-hour thresholds raw.trips needs would either force an artificial reload schedule or produce a permanent, meaningless WARN. dbt source freshness confirms the exemption applies:

1 of 1 — only cityflow.trips gets checked; cityflow.zones never appears in a freshness run at all, exactly what freshness: null promises.

Getting this wrong runs in both directions. Leaving zones without any freshness: key at all wouldn’t cause an error — dbt simply skips freshness checking for any source table that never declares it, the same effective result as freshness: null. The explicit null matters anyway: a teammate reading __sources.yml months from now sees a deliberate choice, not an omission they might “fix” by adding thresholds that don’t belong there. The opposite mistake — copying trips’s 24/48-hour thresholds onto zones simply because it was the pattern already in the file — would make dbt source freshness report a permanent, unfixable WARN or ERROR on a table reloaded on a genuinely different schedule than daily trip data.

Step 3: Staging It#

Renaming only — location_id to zone_id for a consistent pattern with the rest of the project, zone to zone_name to avoid colliding with “zone” used elsewhere as a concept rather than a column — no join, no aggregation, the identical discipline stg_cityflow__trips follows. borough and service_zone pass through unrenamed: a staging model renames a column only when the source name is ambiguous or misleading, not on a blanket policy of touching every column. borough already means exactly what it says.

Step 4: Running the Whole Project, Then Naming a Zone#

JFK Airport, $435,503.41 — for the first time, a bare pickup_zone integer this project has been grouping by since Module 2 has an actual name attached to it. That query is a JOIN, run directly against Postgres to confirm the staging layer works, not a staging model — Lesson 3’s rule against joins in staging still holds. Building a model that joins zone_revenue against stg_cityflow__zones permanently is exactly the job Module 5’s mart layer exists for.

The result is worth sitting with, independent of the dbt mechanics that produced it. Two airports occupy the top two spots by revenue, ahead of every purely residential or commercial zone — consistent with ordinary intuition about taxi demand (airport trips run longer distances, at higher fares, than a typical Manhattan hop). A number a pipeline reports without ever being checked against a plausible real-world story is a number nobody has actually looked at; naming JFK Airport here, rather than leaving pickup_zone = 132 sitting in zone_revenue’s output, is what makes that sanity check possible for the first time.

Practice Exercises#

Exercise 1: A source-level freshness default, table-level override#

  • Move freshness: {warn_after: ..., error_after: ...} up to the cityflow source level, so it applies to every table by default.
  • Confirm zones still opts out correctly with its own freshness: null override.
  • Run dbt source freshness and check for the same “1 of 1, trips only” result Lesson 2’s inheritance rule predicts.

Exercise 2: Stage a third, hypothetical table#

  • CityFlow’s trip data has a payment_type column this course’s loader dropped back in Module 1 (KEEP_COLUMNS never included it).
  • Sketch, in prose, what a raw.payment_types lookup table and its own stg_cityflow__payment_types staging model would need to look like, following this lesson’s pattern.

Hint

The zone lookup’s own shape — an integer ID, a short set of descriptive text columns, loaded once and rarely refreshed — is a template most lookup tables share.

Summary#

CityFlow’s staging layer covers two tables now, not one: raw.zones, all 265 rows of the NYC TLC’s official zone lookup, loaded with the identical psycopg2/COPY pattern Module 1 established, declared as a second table under the cityflow source with freshness: null correctly exempting a rarely-refreshed lookup table, and staged as stg_cityflow__zones following the exact rename-only convention stg_cityflow__trips already follows. A closing verification query named CityFlow’s highest-revenue zone for the first time: JFK Airport, $435,503.41.

Key Concepts#

  • freshness: null opts a table out of staleness checks entirely — the correct choice for a lookup table refreshed rarely, confirmed by dbt source freshness skipping it.
  • A second staging model follows the identical convention as the first — stg_cityflow__zones and stg_cityflow__trips differ only in which table they read.
  • Staging still means rename-only, even for a lookup table — zero joins, zero aggregations.
  • A join belongs in a mart, not a verification query dressed up as one — this lesson’s own zone-naming query stayed a direct check against Postgres, never a permanent staging model.

Why This Matters#

Module 3 closes here with a two-table staging layer — sources declared and checked for freshness, models named by convention, nothing joined or aggregated prematurely. Module 4 puts that layer to its next test: data_tests:, run against both staging models, including a deliberately broken test caught and fixed.
