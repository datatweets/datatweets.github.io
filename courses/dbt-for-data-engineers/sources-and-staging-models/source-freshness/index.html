Welcome to Source Freshness#

A source declaration is a promise: this data exists, and a model can trust it. dbt source freshness is how that promise gets checked on a schedule, not assumed forever. This lesson runs it against raw.trips twice — first with a choice that looks reasonable and is quietly wrong, then with the fix, tested through all three states a freshness check can report.

By the end of this lesson, you will be able to:

  • Configure loaded_at_field and warn_after/error_after thresholds on a source
  • Explain why a business timestamp is usually the wrong choice for loaded_at_field
  • Run dbt source freshness and read a PASS, a WARN, and an ERROR STALE result correctly

A Plausible Mistake#

raw.trips already has a timestamp column: pickup_time, the moment each trip started. It’s tempting to point freshness at it directly:

ERROR STALE, correctly: pickup_time’s maximum value is 2024-01-01 23:59:55 — the last trip in CityFlow’s one loaded day. Measured against whenever this check runs, that’s well over two years old, nowhere close to the 48-hour error_after threshold. The check isn’t wrong. loaded_at_field: pickup_time was the wrong choice: pickup_time records when a trip happened, not when the row was loaded — two distinct moments a business timestamp conflates into one. A loader that ran five minutes ago against year-old source data will always report stale this way, correctly flagging that the field being checked is wrong, not that the load itself failed.

The Fix: A Load-Timestamp Column#

raw.trips needs a column that records when the row was loaded, not when the trip happened — something Module 1’s loader never added:

Two clearly different timestamps now sit side by side — _loaded_at reflects when the row landed; pickup_time still reflects the business event. Pointing loaded_at_field at the right column:

PASS — _loaded_at is seconds old, comfortably under the 24-hour warn_after threshold.

Confirming WARN and ERROR, Not Just PASS#

A freshness check that only ever gets shown passing hasn’t proven anything about the thresholds themselves. Backdating _loaded_at by hand tests both:

30 hours — past warn_after (24h), under error_after (48h) — reports WARN. 50 hours — past error_after — reports ERROR STALE, the same exit code a CI pipeline in Module 11 checks to decide whether a pull request can merge. All three states ran against the identical 81,013-row table with identical thresholds; only _loaded_at changed between runs.

Practice Exercises#

Exercise 1: A source-level default, overridden per table#

  • Move loaded_at_field and the freshness config up to the source level (alongside name: raw, above tables:), so every table under raw inherits it by default.
  • Declare raw.zones (Lesson 5’s second raw table) with freshness: null to opt it out entirely — a lookup table refreshed rarely doesn’t need the same staleness check as a daily load.
  • Confirm with dbt source freshness that raw.trips still gets checked and raw.zones is skipped.

Exercise 2: filter, for a source that’s only ever partially fresh#

  • Read the filter key in docs.getdbt.com’s freshness reference.
  • Write a filter expression that checks freshness only for rows where pickup_zone is not null.
  • Explain in a sentence what real-world situation that would protect against that an unfiltered check wouldn’t catch.

Hint

filter runs as a WHERE clause inside the freshness query itself — it changes which rows count toward “the newest row,” not which rows exist in the table.

Summary#

dbt source freshness against raw.trips, pointed at pickup_time, correctly reported ERROR STALE — a business timestamp isn’t a load timestamp, and the two-year gap between them proved it immediately. A _loaded_at column, added and set to the actual load time, fixed the check, and backdating it by hand confirmed all three states a freshness check can report: PASS when fresh, WARN past 24 hours, ERROR STALE past 48 — the identical table and thresholds throughout, only the timestamp changed.

Key Concepts#

  • loaded_at_field should point at a load timestamp, not a business timestamp — confirmed by the failure mode a business timestamp produces when the two diverge.
  • warn_after and error_after are independent thresholds — a source can be stale enough to warn without yet being stale enough to error.
  • dbt source freshness produces a real exit code — ERROR STALE is the same failure signal a CI pipeline checks, not just console text.
  • Testing a check means forcing every state it can report — a freshness check only ever shown passing hasn’t demonstrated its thresholds do anything.
