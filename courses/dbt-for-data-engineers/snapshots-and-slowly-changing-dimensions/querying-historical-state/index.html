Welcome to Querying Historical State#

zones_snapshot has held zone 33’s genuine transition since Lesson 3 — Brooklyn, then Queens, each with its own dbt_valid_from/dbt_valid_to window. This lesson asks the question that transition exists to answer: what was zone 33’s borough before the reassignment, and can this project actually answer that, correctly, from an actual query?

By the end of this lesson, you will be able to:

  • Write an “as of” query against a snapshot table using dbt_valid_from and dbt_valid_to
  • Confirm the identical query returns different, correct answers depending on the moment it asks about
  • Explain why zones itself can never answer the same question, no matter how it’s queried

The As-Of Query Pattern#

Zone 33’s Brooklyn row was valid from 05:27:12.495458 to 05:27:18.674646 — a genuine, if narrow, window this lesson’s timestamps happen to record. A query asking “what was zone 33’s state at any moment inside that window” should return Brooklyn:

dbt_valid_from <= :as_of and (dbt_valid_to > :as_of or dbt_valid_to is null) — the standard shape an as-of query against any Type 2 snapshot table takes, confirmed here computing its own :as_of moment directly from zone 33’s recorded boundary rather than a hardcoded timestamp, so this query lands inside the correct Brooklyn window no matter when this lesson actually runs. The same query, asked about right now instead:

The identical query, the identical table, a different :as_of moment — Brooklyn for a point inside the old window, Queens for right now. zones_snapshot isn’t storing two contradictory answers; it’s storing the one, correct answer for each of two genuinely different moments in CityFlow’s history.

The or dbt_valid_to is null half of the pattern isn’t optional decoration — it’s load-bearing, for a reason this course has already met once before. dbt_valid_to > :as_of alone would silently exclude every currently-valid row from the result, since SQL’s own NULL comparison rules mean NULL > anything never evaluates to true, the identical rule this project first ran into with zone 265’s genuine NULL borough back in Module 3. A snapshot’s dbt_valid_to is NULL specifically to mean “no end yet, still current” — and without the explicit is null check, an as-of query asking about right now would return nothing at all for every zone that’s never changed, since NULL, honestly, never claims to be greater than anything.

zones Itself Can Never Answer This#

zones answers correctly for right now — Queens — because right now is the only moment it has ever been able to talk about. There’s no dbt_valid_from or dbt_valid_to anywhere in its column list, because zones was never built to track them; every earlier module treated “what’s true now” as the only question worth answering, until Lesson 1 of this module showed exactly what that assumption costs. Querying zones for zone 33’s state “as of last week” isn’t a query this table can express incorrectly — it’s a query this table simply has no columns to express at all.

That distinction is worth being precise about, since it’s easy to conflate a wrong answer with an unaskable question. A query that returns Queens when the honest answer was Brooklyn would be a correctness bug — the kind Module 4’s testing habit exists to catch. zones never produces that bug, because it never claims to answer the historical version of the question in the first place; every one of its rows only ever describes the present, and nothing about its schema even pretends otherwise. The gap Lesson 1 found wasn’t zones lying about history — it was zones never having a mechanism to remember any.

The Same Pattern, Across Every Zone#

Asking the as-of query for right now, across every zone at once, returns exactly 265 rows — one currently-valid version per zone, matching what zones itself has always reported. Grouping the whole snapshot by zone_id and counting versions finds exactly one zone with more than one: zone 33, with its own two genuinely recorded states. Every other zone has a single, unbroken row, because nothing about them has genuinely changed since this module’s snapshots first ran.

This is also the honest reason a real snapshot table shouldn’t grow forever unmanaged in a project with genuinely frequent dimension changes. zones_snapshot will scale fine for a project this size — 265 rows growing by one per real change, an increment measured in single digits over this course’s own lifetime — but a dimension with thousands of rows and daily changes would accumulate history at a very different rate, and every as-of query would keep scanning that entire, ever-growing table unless it’s indexed on dbt_valid_from and dbt_valid_to specifically. Nothing in this lesson needed that index — 265 rows scan instantly regardless — but it’s worth naming as the first real operational concern this module’s approach eventually runs into, once a snapshot’s history stops being small enough to ignore.

Practice Exercises#

Exercise 1: A moment before the snapshot existed#

  • Run the as-of query for zone 33 at a timestamp well before zones_snapshot was first built — a year in the past, for instance.
  • Confirm what comes back, and explain honestly why an empty result here isn’t a bug in the query, but an accurate reflection of what this project’s snapshot actually knows: a snapshot’s history only ever starts the moment it was first run, never earlier.
  • Compare against the same as-of query for a moment one second before zone 33’s recorded dbt_valid_from — still empty, for the identical reason, even though that moment is only a fraction of a second outside the window this snapshot genuinely covers.

Exercise 2: A reusable as-of query for any zone, any moment#

  • Generalize this lesson’s as-of query into a version that takes both a zone_id and an :as_of timestamp as genuine parameters, rather than hardcoding zone 33.
  • Run it for a handful of other zones at the current moment and confirm every one returns its own single, unbroken row — the expected result for a zone whose history, so far, has never actually changed.

Hint

Exercise 1’s empty result is the honest answer, not a failure — a snapshot can only ever remember what happened after it started watching, the same genuine limitation any monitoring system built from this point forward has.

Summary#

The as-of query pattern — dbt_valid_from <= :as_of and (dbt_valid_to > :as_of or dbt_valid_to is null) — answered a genuine historical question for the first time in this project’s history: what was zone 33’s borough before this module’s reassignment happened? Run against zones_snapshot at a moment inside zone 33’s recorded Brooklyn window, the answer was Brooklyn; run at the current moment, the identical query correctly returned Queens. zones itself, queried the same way it’s always been, could only ever answer the second question — it has no dbt_valid_from or dbt_valid_to columns to ask the first one with at all. Extending the same pattern across all 265 zones confirmed exactly one zone’s history differs by moment: zone 33, the only one this module has actually changed.

Key Concepts#

  • An as-of query needs both boundaries — dbt_valid_from <= :as_of alone would match every row that started before the moment asked about, including ones already closed out; the dbt_valid_to half is what excludes those.
  • The identical query returns different, correct answers for different moments — not a contradiction, the entire reason a Type 2 snapshot table exists.
  • zones can’t answer a historical question incorrectly — it can’t ask it at all — no dbt_valid_from/dbt_valid_to columns means no vocabulary for “as of when.”
  • A snapshot’s history starts when the snapshot starts — an honest limitation, not a bug, confirmed directly by querying a moment before it existed.

Why This Matters#

Lesson 5’s guided project pulls every piece of this module together: a snapshot built end to end, a simulated change made against it for the first time in a single guided pass, and a historical query proving the SCD Type 2 record survived it — the complete loop Lesson 1 showed this project could never close before.
