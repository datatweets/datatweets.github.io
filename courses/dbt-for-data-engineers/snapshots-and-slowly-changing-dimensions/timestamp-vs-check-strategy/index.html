Welcome to Timestamp vs. Check Strategy#

Lesson 2 built zones_snapshot with strategy: check, the only option available at the time — raw.zones had no updated_at column, so strategy: timestamp wasn’t usable yet. This lesson retrofits that column, builds the timestamp-strategy counterpart, and then does the one thing a comparison like this actually needs: makes a change where the two strategies actively disagree.

By the end of this lesson, you will be able to:

  • Retrofit an updated_at column and configure strategy: timestamp against it
  • Explain exactly what each strategy compares to decide whether a row changed
  • Reproduce a case where a source that forgets to update its own timestamp defeats one strategy but not the other

Retrofitting updated_at#

Every one of CityFlow’s 265 zones now carries the identical baseline updated_at — an honest backfill, not a claim that this timestamp reflects when each zone was genuinely last touched, since raw.zones never tracked that before this lesson. stg_cityflow__zones.sql passes the new column straight through, the identical rename-only pattern this project’s staging layer has followed since Module 3:

Building the timestamp-Strategy Snapshot#

Same 265 rows, same starting shape as Lesson 2’s zones_snapshot — the two snapshots agree completely on CityFlow’s current state, which is exactly what makes the moment they diverge worth watching for. zones_snapshot_timestamp lives as its own genuinely separate table, distinct from zones_snapshot, stg_cityflow__zones, and zones — four different objects in this project now describing the same underlying zone data, each answering a slightly different question about it.

zones_snapshot itself gets rebuilt fresh here too, to guarantee both snapshots start from the identical Brooklyn baseline this section just reset zone 33 to, regardless of anything either snapshot may have already recorded before this lesson ran:

A Real Mistake: Reassigned, Timestamp Untouched#

Zone 33 — Brooklyn Heights — gets reassigned from Brooklyn to Queens, the identical kind of business event Lesson 1 already simulated for zone 65. This time, deliberately, the mistake a source system genuinely makes: the reassignment happens, but nothing bumps updated_at.

Borough changed; updated_at still reads the original 2024-01-01 baseline. Rebuilding stg_cityflow__zones and running both snapshots shows exactly what each strategy makes of that:

check strategy caught it — INSERT 0 1, one new row. timestamp strategy didn’t — INSERT 0 0, nothing added at all. Reading both tables directly confirms exactly what that split means:

zones_snapshot correctly closed out the old Brooklyn row and opened a new Queens one — check_cols compared zone_name, borough, and service_zone directly against what was already recorded, found borough different, and acted on it, with no interest in updated_at at all. zones_snapshot_timestamp still shows exactly one row, still Brooklyn, dbt_valid_to still NULL — as far as this snapshot knows, nothing about zone 33 has ever changed. timestamp strategy’s entire detection mechanism is comparing updated_at against what it already recorded; since that value never moved, there was nothing to compare against, and an actual change slipped through completely unnoticed.

Fixing It: Bumping updated_at Catches Up#

The moment updated_at actually moves, timestamp strategy catches up immediately and correctly — the strategy was never broken, it was only ever answering the exact question it’s designed to answer: has updated_at increased? For six minutes of this lesson’s clock time, the honest answer was no, even though borough itself had already changed. Six minutes is only this lesson’s own scale; nothing about timestamp strategy’s mechanism bounds how long that gap could run in a real production system. A source that forgets to bump its updated_at for a day, a week, or permanently would leave zones_snapshot_timestamp permanently unaware of a change that already happened, with no error anywhere to surface it — no constraint gets violated, no test written the way Module 4 taught this project to write them would fail, since dbt_valid_to is null and borough = 'Brooklyn' are both, individually, perfectly valid states for a row to be in. The gap is invisible specifically because nothing about it looks broken from inside the snapshot table itself.

zones_snapshot’s two rows for zone 33 — Brooklyn, then Queens, each with its own dbt_valid_from/dbt_valid_to window — are the first genuine answer this project has ever been able to give to a question zones itself has never been able to answer: not what zone 33 is, but what zone 33 was, at any specific moment its history actually covers. That’s the whole reason this lesson insisted on getting the strategy right before moving on — a snapshot with a gap in its own history is barely better than no snapshot at all, since the gap looks exactly like correctly-recorded, unchanging data from the inside.

Practice Exercises#

Exercise 1: A change check strategy would miss#

  • Reason through, without running it: is there a kind of change check strategy could miss that timestamp strategy would catch? Consider what happens if check_cols doesn’t list every column a source might actually change.
  • Confirm your reasoning by adding a genuinely new column to raw.zones, changing only that column’s value, and rerunning both snapshots.
  • Note timestamp strategy’s advantage in this scenario: it never needs to know which columns matter in advance — any change at all, in any column, is caught as long as the row’s updated_at genuinely reflects it, the exact trade this lesson’s real mistake exposed in reverse.

Exercise 2: Which strategy CityFlow’s zone data should genuinely use#

  • check strategy just caught a real mistake timestamp strategy missed — but check strategy also has to scan and compare every one of check_cols’s values on every run, for every row, while timestamp strategy only ever compares one column.
  • At CityFlow’s scale — 265 rows, both strategies finishing in well under a second either way — confirm directly whether that cost difference matters in practice: rerun both snapshots against unchanged data and compare their timing lines.
  • Write a sentence arguing for each strategy as CityFlow’s long-term choice for zones, then decide which you find more convincing for a dimension this small and this rarely-changing — and reconsider whether the same argument would still hold for a dimension the size of trips_full instead: 9.5 million rows, not 265.

Hint

Exercise 1’s answer depends on whether the new column is inside check_cols at all — a strategy can only ever catch a change in a column it’s actually configured to look at, a real limitation of check strategy specifically, not of snapshots in general.

Summary#

zones_snapshot_timestamp, built with a retrofitted updated_at column, agreed completely with Lesson 2’s check-strategy zones_snapshot until zone 33 was reassigned from Brooklyn to Queens without its updated_at bumped — a plausible mistake a source system genuinely makes. check strategy caught it immediately, comparing borough’s value directly and recording a second row. timestamp strategy missed it completely, since its entire detection mechanism depends on updated_at moving, and it never did — confirmed directly by reading both snapshot tables’ data, not assumed from either strategy’s documentation. Bumping updated_at afterward let timestamp strategy catch up correctly, confirming neither strategy is simply better; each is only ever as reliable as the specific thing it was configured to watch.

Key Concepts#

  • check strategy compares configured column values directly — it doesn’t need or care about any timestamp, real or retrofitted.
  • timestamp strategy trusts updated_at completely — a change that doesn’t move that column is invisible to it, no matter how real the underlying change was.
  • A retrofitted timestamp is honest about its own limits — this lesson’s baseline 2024-01-01 value for every zone doesn’t claim to be a genuine history, only an honest working starting point.
  • Neither strategy is simply better — check caught a real mistake here, but only because borough was inside check_cols; a source’s own discipline about updating its timestamp matters just as much as which strategy a snapshot picks.

Why This Matters#

zones_snapshot, the check-strategy snapshot, now holds a correctly-captured change for zone 33 — exactly what Lesson 4 needs to answer a historical question for the first time: what was zone 33’s borough before this lesson’s reassignment happened?
