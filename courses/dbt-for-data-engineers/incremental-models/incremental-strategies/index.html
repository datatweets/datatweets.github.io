Welcome to Incremental Strategies#

Lesson 2’s int_trips_full_incremental never needed to say which incremental strategy it wanted — dbt-postgres’s default, append, decided for it. append is only one of three strategies Postgres genuinely supports, and it has a real blind spot: it has no idea what to do with a row that already exists. This lesson builds the same scenario three times, once per strategy, to show exactly what that blind spot costs.

By the end of this lesson, you will be able to:

  • Configure unique_key and incremental_strategy on an incremental model
  • Explain the practical difference between append, delete+insert, and merge in terms of what SQL each executes
  • Recognize a duplicate-row bug caused by choosing the wrong strategy for data that gets corrected after the fact

A Source With No Natural Key#

NYC’s TLC trip data has never shipped a trip_id — every model this project has built from it so far has gotten by without one. A strategy comparison needs a stable identity to key off of, so this lesson assigns one directly, the same way a production pipeline would when its source system doesn’t provide one:

109,997 trips from February 1st, 2024, each with a trip_id assigned by row_number() — stable because it’s computed once, into a physical table, rather than recalculated on every read the way a view’s row_number() would be. _loaded_at, the same freshness column raw.trips has carried since Module 3, records when this batch landed: 2024-02-02, the day after the trips themselves happened, the same lag any batch-loaded pipeline has.

Three Models, One Source, Three Strategies#

Three identical row counts on this first run — unique_key and incremental_strategy only change what happens once a target already exists; a first build behaves the same regardless of strategy, exactly the way Lesson 2 already established for is_incremental() itself.

A Correction Lands With a New Day’s Data#

Trip 500’s fare corrected from $18.40 to $43.40 — a $25 adjustment, the kind a dispute or a meter recalibration might genuinely cause — landing with the identical _loaded_at timestamp as 105,470 brand-new February 2nd trips. Any pipeline reading _loaded_at to decide what’s new has to treat both the same way: as part of the same incoming batch, one correction mixed in among tens of thousands of genuinely new rows.

Three Strategies, Three Different Outcomes#

All three processed the identical 105,471 rows — 105,470 new arrivals plus trip 500’s correction — and even merge’s Postgres-reported verb differs from the other two. What each one actually did to its target table is a different question entirely:

append’s target holds 215,468 rows — one too many — because trip 500 now exists twice: once at its original $18.40 fare, once at its corrected $43.40. delete+insert and merge both land on the mathematically correct 215,467, trip 500 appearing exactly once, at the corrected fare. Every downstream sum(fare_amount) or count(*) built on int_trips_batch_append is now silently wrong by exactly one duplicated row — not a crash, not a warning, a number quietly overstating both the trip count and the revenue it represents.

Reading Each Strategy’s Executed SQL#

append runs exactly one statement: insert into ... select from a temp table holding the filtered rows — nothing checks whether trip_id already exists in the target, which is precisely why trip 500 landed twice. delete+insert runs two: a genuine delete from ... where trip_id in (select distinct trip_id from <temp>), removing every row whose key appears in the new batch, followed by the identical plain insert append uses — the delete is what keeps the count correct, clearing out trip 500’s stale row before its corrected one arrives. merge runs one statement that does both jobs at once: an actual SQL merge into ... using <temp> on (trip_id = trip_id) when matched then update ... when not matched then insert — an atomic upsert, not two separate operations a failure could interrupt between.

That last distinction is worth sitting with. delete+insert genuinely works, confirmed above by the identical correct row count merge also produced — but it works as two separate statements, and a failure between the delete and the insert — a dropped connection, a killed process, a disk filling up mid-run — would leave the target missing exactly the rows the delete removed, with the replacement rows never arriving. merge’s single statement has no such gap: either the entire upsert commits, or none of it does, since there’s only ever one statement to fail partway through. Neither strategy failed in this lesson’s own runs, so this isn’t a bug either one has — it’s a real difference in how much a genuine mid-run failure could cost, worth knowing before choosing between two strategies that otherwise land on the identical correct answer.

Practice Exercises#

Exercise 1: A second correction, a third arrival day#

  • Update trip 500 a second time (another fare adjustment) and insert February 3rd’s trips as a third batch, both stamped with a new, later _loaded_at.
  • Rerun all three models and confirm append’s target now holds trip 500 three separate times, while delete+insert and merge both still hold exactly one, at the latest fare.
  • Compute sum(fare_amount) across all three targets and compare directly: append’s sum is now wrong by the combined value of both stale copies, an error that compounds every time a correction lands.

Exercise 2: delete+insert’s delete, scoped correctly#

  • Read delete+insert’s executed delete from statement again, specifically its where trip_id in (select distinct trip_id from <temp>) clause.
  • Explain why this deletes only rows whose trip_id appears in the new batch, not the entire target table, and what would happen to every unaffected January row if that where clause were accidentally left off.

Hint

Exercise 2’s hypothetical — a delete from with no where clause at all — is exactly the kind of mistake unique_key-scoped deletes exist to prevent. Every one of int_trips_batch_delete_insert’s January-adjacent rows from Lesson 1 and 2’s work is completely unrelated to this lesson’s February batch, and a correctly-scoped delete never touches them.

Summary#

The identical scenario — 105,470 new trips landing alongside one corrected fare, both marked with the same _loaded_at — was run through all three incremental strategies Postgres genuinely supports. append duplicated the corrected trip, landing on 215,468 rows where 215,467 was correct, because its executed SQL is a single insert with no mechanism to check whether a key already exists. delete+insert and merge both landed on the correct count, confirmed by reading their executed SQL directly: an actual delete followed by a separate insert, and a single, real merge into ... when matched ... when not matched statement, respectively.

Key Concepts#

  • append has no concept of an existing row — its compiled SQL is always a plain insert, correct only when incoming rows are guaranteed genuinely new.
  • delete+insert clears stale rows before inserting fresh ones — two statements, scoped by unique_key to only the rows the new batch actually affects.
  • merge does both in one atomic statement — an actual SQL merge, not dbt’s own invention, doing the identical job delete+insert does in two steps.
  • A wrong strategy produces a wrong number silently — no error, no warning, just a row count and a revenue figure quietly overstated by exactly the rows that got duplicated.

Why This Matters#

Every strategy this lesson built depended on unique_key='trip_id' actually being unique. Lesson 4 tests what happens when it isn’t — a correctness trap this project’s multi-month data can genuinely produce.
