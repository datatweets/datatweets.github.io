Lesson 1 - Why Full Rebuilds Stop Scaling

Welcome to Why Full Rebuilds Stop Scaling#

Module 5’s guided project read three full months of NYC taxi history — 9,554,778 rows — but deliberately kept it DuckDB-only, a view over read_parquet() with no copy stored, since nothing in that module needed the data to persist as an actual table. This module needs exactly that: an incremental materialization has nothing to check a second run against without a physical table already in the warehouse. This lesson loads that history into Postgres for the first time, and uses it to measure something CityFlow’s original 81,013-row day was always too small to show.

By the end of this lesson, you will be able to:

  • Load a genuinely large dataset into Postgres using the chunked-COPY discipline this project already established
  • Measure, rather than assume, how long a full table rebuild actually costs
  • Explain why a materialized='table' model pays that same cost on every run, regardless of what changed

Loading CityFlow’s Full History Into Postgres#

load_trips_full.py reads all three parquet files — January through March 2024, the same source Module 5’s guided project and the Scaling Python capstone both already used — and loads them into a new table, raw.trips_full, in chunks of 500,000 rows:

9,554,778 rows — the exact count the Scaling Python capstone and Module 5’s DuckDB reproduction both already established, unfiltered, since this loader has no reason to quarantine anything the way Module 5’s guided project did for its aggregation. Chunking in batches of 500,000 rows, rather than one 9.5-million-row buffer, keeps memory bounded the same way this path’s earlier out-of-core lessons already taught: each chunk is read into a small StringIO buffer, streamed to Postgres, and discarded before the next one starts, so peak memory stays proportional to one chunk.

538 MB on disk works out to roughly 56 bytes per row for four narrow columns — a useful sanity check: a schema this narrow should never balloon into gigabytes just from adding a few more months of the same shape of data.

DROP TABLE IF EXISTS raw.trips_full CASCADE at the top of the loader is the same idempotency pattern Module 1’s load_trips.py established for raw.trips — rerunning this script is always safe, starting from a clean slate rather than appending duplicate rows. CASCADE matters for the same reason it did back then: once stg_cityflow__trips_full and anything built on top of it exist as views, a plain DROP TABLE refuses to run while something else still depends on it, and CASCADE drops those dependent views along with the table. A later dbt run simply recreates every dropped view fresh from its .sql file, since a view is nothing but a stored query.

Declaring the New Source#

stg_cityflow__trips_full — same rename-only shape, same four kept columns, as stg_cityflow__trips, Module 3’s staging model for the original single day — the identical staging convention applied to a table 118 times larger, without a single new rule needed.

Timing a Full Table Rebuild#

int_trips_full_loaded, materialized='table', is a plain passthrough of the full staging model — the smallest possible model that still forces Postgres to physically write every one of 9.5 million rows on every build:

6.22 seconds to build a table nobody asked to change — CityFlow’s data hasn’t grown or shrunk since the loader finished; this run just proves the model works. --full-refresh is worth naming even though it does nothing new on this model: the flag’s actual job is telling an incremental model to drop and rebuild from scratch instead of appending or merging, and int_trips_full_loaded isn’t incremental yet — materialized='table' only ever rebuilds from scratch, so --full-refresh changes nothing about what this run does. Lesson 2 is where that flag starts to matter. Running the model again, with no flag and nothing different about the underlying data, pays the identical cost:

7.64 seconds the second time — not faster, not cached, not skipped, because materialized='table' compiles to exactly the same statement every run: create table ... as (select ...), dropping and rebuilding from nothing regardless of whether the previous run’s table already had every row this one would produce. A dbt run with no changes anywhere in CityFlow’s data still pays the full 9.5-million-row cost, over and over.

The Real Scaling Problem, Quantified#

118 times more rows, roughly 50-60 times more wall-clock time — not linear, but unmistakably measurable, and CityFlow’s data has only ever grown across this course’s narrative. A table that takes 126 milliseconds to rebuild today doesn’t stay in that range forever; a project with genuinely large, continuously arriving data — the kind Course 3’s Kafka work streams in continuously — would make this exact materialized='table' model take minutes rather than seconds, on every run, whether one row changed or a million did.

Practice Exercises#

Exercise 1: Timing a materialized view instead#

  • Change int_trips_full_loaded’s config to materialized='view' and rerun it.
  • Confirm the build itself finishes near-instantly regardless of row count.
  • Explain why this doesn’t actually solve the scaling problem this lesson measured — consider what happens the moment something queries the view directly, compared to querying an already-built table.

Exercise 2: A third repeated run#

  • Run int_trips_full_loaded a third time, unchanged, and record its timing line.
  • Compare all three runs and confirm they fall within the same rough range rather than trending consistently faster or slower — none of them get meaningfully cheaper just because the data underneath hasn’t changed.
  • Note what dbt run’s output says about the model each time: every run reports CREATE/SELECT, never “unchanged” or “skipped” — dbt has no idea whether the rows it’s about to write are identical to the ones already in the table, since nothing in a materialized='table' model’s compiled SQL ever asks that question.

Hint

Exercise 1’s answer is really about where the cost moved, not whether it disappeared — a view defers the 9.5-million-row scan to query time instead of build time, and every query against it pays that scan fresh, the same way zone_hour_report’s DuckDB view read all of read_parquet() fresh in Module 5.

Summary#

CityFlow’s full 3-month trip history — 9,554,778 rows — was loaded into Postgres as a physical table for the first time, in 24.40 seconds via chunked COPY, since an incremental materialization needs a physical table to compare a second run against. int_trips_full_loaded, materialized='table', was timed rebuilding all of it in 5-8 seconds across three separate runs — the same cost every time, confirmed directly, contrasted against the same shape of build finishing in 126 milliseconds for CityFlow’s original single day.

Key Concepts#

  • materialized='table' rebuilds from nothing, every run — its compiled SQL is a full create table as select, with no mechanism to check what the table already held.
  • A measured cost is stronger evidence than an assumed one — three separate timed runs, not a single number taken on faith.
  • Row count and rebuild time scale together, though not linearly — 118× the rows cost roughly 50-60× the time here, on this machine, with this data.
  • A view defers the cost; it doesn’t remove it — Exercise 1’s point, worth carrying into every materialization decision from here forward.

Why This Matters#

Lesson 2 introduces the mechanism that actually avoids this cost: is_incremental(), and what genuinely changes in a model’s compiled SQL the moment it’s told which rows it already has.

Continue Building Your Skills#

Lesson 2 converts int_trips_full_loaded to materialized='incremental' and inspects its compiled SQL on two different runs — one where the table doesn’t exist yet, one where it does — to see exactly what is_incremental() changes.
