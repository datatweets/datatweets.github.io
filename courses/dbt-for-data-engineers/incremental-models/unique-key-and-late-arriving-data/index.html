Welcome to unique_key and Late-Arriving Data#

Every model Lesson 3 built used trip_id — a synthetic key, assigned once, genuinely unique by construction. Source data doesn’t always come with one, and a tempting substitute usually exists: some combination of columns that looks like it should identify a row uniquely. This lesson uses exactly that kind of tempting-but-wrong key, already confirmed elsewhere in this project’s data to collide, and shows precisely what trusting it costs — not a crash, not an error, a silent corruption of unrelated rows.

By the end of this lesson, you will be able to:

  • Recognize why a composite key that “looks” unique still needs to be checked, not assumed
  • Explain what happens when merge’s unique_key matches more than one target row
  • Fix a genuine correctness bug by switching to a truly unique key, and confirm the fix directly

A Key That Looks Reasonable#

(pickup_time, pickup_zone) is the kind of key a first pass at this problem might reach for — two columns, together specific enough to sound like they’d identify one trip. Module 7’s full 9.5-million-row history already settled whether that’s true:

9,554,778 rows, only 9,209,961 distinct (pickup_time, pickup_zone) pairs — 344,817 collisions, project-wide. Two people can genuinely hail a cab from the same zone in the same recorded second; NYC’s trip data was never designed to prevent that. unique_key, per dbt’s own documentation, is only ever as good as whether it’s actually unique — dbt trusts the config, and never independently verifies it.

Building the Model With the Wrong Key#

A first run behaves exactly like Lesson 3’s int_trips_batch_merge — no target exists yet, so there’s nothing for a wrong key to collide against. The trap only opens on a second run.

A Third Day Arrives#

110,603 new February 3rd trips, all correctly landing — 215,467 plus 110,603 is 326,070, and the count confirms every row arrived. Nothing looks wrong yet, because nothing has been corrected yet.

One Correction, Five Rows Affected#

Five distinct trips — different riders, different fares — that happen to share the exact same pickup timestamp and zone. (pickup_time, pickup_zone) was never able to tell them apart; nothing forced that fact into the open until now. Correcting one of them, trip_id 214908, the same kind of $25 fare adjustment Lesson 3 already simulated:

MERGE 5 — not an error, not a warning, a successful run reporting five rows affected by a correction to exactly one. dbt run’s own output gives no indication anything is wrong.

Every one of the five rows now reads trip_id 214908, fare 14.30 — trips 214909, 214910, 214911, and 214912 didn’t just fail to update correctly, their own identities were overwritten entirely. Postgres’s merge into ... on (pickup_time = pickup_time and pickup_zone = pickup_zone) matched all five existing target rows against the single corrected source row sharing their key, and updated every match — exactly what a merge is documented to do, applied faithfully to a key that was never actually unique. The bug isn’t in merge; it’s in trusting (pickup_time, pickup_zone) to mean what its name suggested.

Notice, too, what dbt run reported at the moment this happened: OK, a green checkmark, a clean exit code. Nothing in dbt’s output distinguishes a merge that correctly updated one matching row from one that incorrectly updated five, because dbt has no independent way to know which outcome was intended — it only knows the merge into statement it compiled ran without a database-level error, and Postgres genuinely didn’t error, since matching five target rows against one source row through a non-unique join key is valid SQL, however wrong the result turns out to be for this data. A test on trip_id — unique and not_null, the same generic tests Module 4 built this project’s whole testing habit around — would have caught this immediately, the moment dbt test ran against a target table now silently holding a duplicated trip_id. This lesson deliberately skipped writing one, to let the corruption stand un-flagged long enough to actually see it; a real project never should.

Fixing It With a Genuinely Unique Key#

int_trips_batch_merge, Lesson 3’s unique_key='trip_id' model, reads from the identical raw.trips_batch table — every arrival, every correction this lesson has made so far already sitting in it. A --full-refresh rebuilds it from scratch against that same data, the cleanest way to confirm what a genuinely unique key produces for the exact same rows the wrong one just corrupted:

Trip 214908 sits at its corrected $14.30 fare, and the other four — 214909 through 214912 — hold precisely the fares they always had: -5.1, 5.1, 8.6, 10.7, untouched. Both models read the identical raw.trips_batch, including the identical correction to the identical trip; the only difference between five corrupted rows and five correct ones is which column unique_key pointed at. trip_id genuinely identifies one row; (pickup_time, pickup_zone) only ever looked like it did.

Practice Exercises#

Exercise 1: delete+insert with the same bad key#

  • Rebuild int_trips_batch_bad_key with incremental_strategy='delete+insert' instead of merge, keeping the same unique_key=['pickup_time', 'pickup_zone'].
  • Run the identical trip-214908 correction again and check whether delete+insert’s own delete from ... where (pickup_time, pickup_zone) in (...) causes the same four-trip corruption, a different failure mode entirely, or something else.
  • Read its executed SQL from target/run/ to explain what you find, rather than guessing from the strategy’s name.

Exercise 2: A genuinely composite key that works#

  • (pickup_time, pickup_zone, fare_amount, total_amount) — all four columns together — was already shown in Module 7’s full-history data to collide only 1,925 times out of 9.5 million rows, far rarer than (pickup_time, pickup_zone) alone.
  • Rebuild int_trips_batch_bad_key once more with all four columns as unique_key and rerun the trip-214908 scenario. Confirm this narrower key avoids corrupting the other four trips.
  • Explain why “far rarer” collisions still isn’t the same guarantee trip_id provides, then write a unique test against this four-column key and confirm whether it passes cleanly on CityFlow’s current batch data — a passing test today says nothing about whether the same key stays collision-free once a fifth or sixth month of trips eventually gets added.

Hint

Exercise 2’s four-column key would correctly distinguish trip 214908 from the other four Zone-249 trips, since their fares genuinely differ — but two trips that happened to share every one of those four values too would still collide, the exact 1,925-row risk this lesson’s project-wide count already found.

Summary#

(pickup_time, pickup_zone) looked like a reasonable unique_key — two columns, specific-sounding — and Module 7’s full-history data had already confirmed it collides 344,817 times before this lesson ever ran a single query. Correcting one trip’s fare, trip_id 214908, one of five trips sharing that exact key, triggered a merge that reported success — MERGE 5, no error — while silently overwriting four unrelated trips’ identities and fares to match the one that actually changed. The identical correction, run through trip_id-keyed int_trips_batch_merge, updated exactly the one row that changed, the other four confirmed untouched.

Key Concepts#

  • unique_key is trusted, never verified — dbt has no mechanism to check that a configured key is actually unique; it compiles the strategy’s SQL as if it is.
  • A wrong key can fail silently — no error, no warning, just a successful-looking MERGE 5 quietly affecting rows nothing asked it to touch.
  • A composite key needs the same scrutiny a single column would get — “looks specific” isn’t the same claim as “confirmed unique,” and this project’s data already had the answer before this lesson asked the question.
  • The fix changed one line — unique_key='trip_id' instead of unique_key=['pickup_time', 'pickup_zone'], with everything else about the model identical.

Why This Matters#

Every model in this module so far has worked with data this project already had. Lesson 5’s guided project converts CityFlow’s trips mart — Module 5’s fact table — to incremental for real, sourced from the full multi-month history for the first time, with a unique_key chosen deliberately rather than assumed.
