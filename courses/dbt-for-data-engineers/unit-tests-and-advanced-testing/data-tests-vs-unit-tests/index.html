Welcome to Data Tests vs. Unit Tests#

zones.is_airport has carried a data test since Module 5: dbt_utils.accepted_range, confirmed passing on every build this course has run since. That test has never once checked whether is_airport’s logic is correct — only that the column holds true or false rather than something else. It’s a pass this project has trusted without ever asking what it was actually a pass of. This lesson checks what it’s actually verifying, then confirms a gap that check was never built to close.

By the end of this lesson, you will be able to:

  • Explain exactly what a data test checks, and what it structurally cannot
  • Confirm, by reading a compiled test’s SQL, what accepted_range verifies about is_airport
  • Explain what a unit test checks instead, and why it doesn’t need warehouse data to do it

What accepted_range Actually Checks#

That’s the whole test, dbt_utils’s own macro expanded in full. It selects every row currently sitting in zones and fails if any of them turns up in validation_errors — which only happens if is_airport is somehow less than False or greater than True, a comparison a boolean column could never actually fail in Postgres, since there’s no third value for one to hold. 1 = 2, the first line inside validation_errors, is dbt_utils’s own placeholder — a condition guaranteed false, there purely so every or clause below it can be appended without worrying about what comes before it syntactically. Neither of the two or branches that follow can ever fire either, for the identical structural reason: not is_airport >= False and not is_airport <= True are both always false for a genuine boolean value. This test has been passing since Module 5 and will keep passing forever, telling this project precisely nothing about whether Newark, JFK, or LaGuardia are correctly flagged — only that the column type is what it already had to be. A test that can structurally never fail isn’t a bad test written carelessly; accepted_range is doing exactly what it was built to do, a type-shape check, not a correctness check, and the two were never the same thing to begin with.

Confirming a Live Gap#

is_airport’s logic is two conditions joined by OR: zone_name ilike '%airport%' or service_zone in ('Airports', 'EWR'). Module 5 wrote both because a name-only check was believed to miss a zone. Worth confirming directly against CityFlow’s current data, rather than trusting that belief unchecked:

Both queries come back empty. Every zone CityFlow’s data currently marks as an airport by service_zone also has “airport” in its zone_name, and every zone zone_name catches also has the matching service_zone. Zone 1, checked directly, is named “Newark Airport” — a name-only ilike would have caught it after all. The two conditions behind is_airport’s OR are genuinely redundant against this project’s data, right now, not a close call decided in the name check’s favor.

That’s not a mistake in Module 5’s reasoning — a service_zone of Airports or EWR is independent signal that doesn’t depend on how a zone happens to be named, and a future zone rename or a new source with different naming conventions could make that condition matter again at any time. It’s an honest limit on what a data test checking today’s rows can prove: accepted_range passing says nothing about whether the OR’s second branch is dead code or a genuine safeguard, because every row in the warehouse right now happens to agree with both conditions at once. Six months from now, a TLC data refresh could add a private terminal zone named nothing like “airport” at all, still correctly tagged service_zone = 'Airports' — the exact case this OR was written for, sitting dormant until a row like that actually shows up. A data test can’t distinguish “this condition is currently untested” from “this condition is dead code”; both look identical from where a data test sits, checking only whatever rows happen to exist right now.

What a Unit Test Checks Instead#

A unit test doesn’t query zones at all. It runs zones.sql’s own compiled logic against rows supplied directly in YAML — rows that don’t have to exist in Postgres, don’t have to match anything CityFlow’s loader has ever inserted, and can be built specifically to separate the two conditions is_airport’s OR currently never gets to prove itself against. A fixture row named “Terminal Zone” with service_zone set to EWR isn’t CityFlow data and was never meant to be — it exists purely to ask the OR’s second branch a question the warehouse currently can’t.

The mental shift is worth stating plainly, since it’s easy to read “unit test” and assume it’s just a data test with extra steps. A data test always runs against zones itself — the actual view or table this project’s warehouse holds, built from whatever stg_cityflow__zones currently contains. A unit test never touches that view at all. dbt takes zones.sql’s own compiled select statement, substitutes the fixture rows in place of wherever ref('stg_cityflow__zones') appears, and runs the resulting query directly — the same transformation logic, pointed at data that was never loaded, never inserted, and exists only for the duration of that one test. Nothing about zones.sql itself has to change for this to work; the substitution happens entirely on dbt’s own side, swapping the input a ref() resolves to without touching a single line the model was written with.

Native to dbt since version 1.8, run the identical way every other test in this project already runs:

Fifteen data tests total, every one checking rows that already exist. Zero unit tests — this project has never once checked a model’s transformation logic against a fixture built to probe it. test_type:unit and test_type:data, the identical selector syntax this course has typed since Module 2, just applied to a distinction that only started to exist the moment this project’s first unit test gets written. Lesson 2 writes it, using is_airport’s confirmed gap as the reason it’s worth writing at all.

Practice Exercises#

Exercise 1: A data test that could never catch a logic bug#

  • stg_cityflow__trips’s pickup_zone column carries a dbt_utils.accepted_range test, 1 through 265. Compile it the same way this lesson compiled is_airport’s test.
  • Explain in one sentence why this test would keep passing even if a future rename swapped pickup_zone for a completely different, equally in-range column by mistake — a column meaning something entirely unrelated to a trip’s pickup location.

Exercise 2: Finding another redundant condition#

  • stg_cityflow__zones.yml’s borough column carries an accepted_values test naming all seven boroughs this project recognizes, including the literal string 'Unknown'. Query CityFlow’s data directly: does any zone currently have borough = 'Unknown' and a zone_name that would let you guess its true borough by eye?
  • Consider what that would mean for a data test versus a unit test checking the same column — and whether a fixture row proving the loader correctly preserves an 'Unknown' value, rather than silently coercing it to something else, would be worth writing even though accepted_values already covers the same column.

Hint

Exercise 1’s answer is the same shape as this lesson’s finding — a data test checks that a value looks right, never that it’s the right value for the right reason.

Summary#

is_airport’s accepted_range test, compiled and read directly, checks only that the column holds true or false — a check a boolean column could never fail regardless of whether the logic computing it is correct. A live query against CityFlow’s data confirmed a gap that test was never built to close: the two conditions behind is_airport’s OR are currently redundant, every zone service_zone catches also caught by zone_name, and vice versa. dbt list --select test_type:unit confirmed this project’s starting point — fifteen data tests, checking rows that already exist, zero unit tests checking logic against anything else.

Key Concepts#

  • A data test can only ever check rows that already exist — accepted_range passing on is_airport proves nothing about whether its logic is correct, only that today’s data happens to produce a valid boolean.
  • A unit test runs a model’s compiled SQL against fixture rows, not the warehouse — those rows don’t have to exist anywhere, which is exactly what lets them probe logic today’s data can’t.
  • A condition that’s currently redundant isn’t necessarily dead code — service_zone’s branch is independent signal that could matter again the moment a new zone or a renamed one breaks the coincidence confirmed here.
  • This project’s starting point: 15 data tests, 0 unit tests — confirmed directly with the identical dbt list --select syntax this course has used since Module 2.

Why This Matters#

is_airport’s confirmed gap isn’t hypothetical — it’s a condition in a live model that a data test cannot verify no matter how many times CityFlow’s warehouse gets rebuilt. Every future data refresh keeps that gap exactly as invisible as it is today, since a data test only ever reports on what currently exists. Lesson 2 writes the fixture that finally closes it.
