Welcome to the Guided Project#

round_money and hour_bucket, Module 6’s macros, have run inside this project since the day they were written — inside int_trips_summed_to_hour, zone_revenue, daily_summary, zone_hour_report, everywhere this project rounds a dollar figure or truncates a timestamp to the hour. Neither has ever been unit-tested directly. This guided project closes that gap the same way every gap this module found got closed: confirm what’s missing, write the smallest fixture that proves the logic, break it on purpose, and confirm the test notices.

By the end of this lesson, you will be able to:

  • Write a fixture that exercises two macros working together inside a single model
  • Diagnose and fix a genuine YAML type-coercion mismatch between an expect: value and a NUMERIC column
  • Confirm a single unit test protects both macros by breaking one and rerunning the identical test

Confirming Neither Macro Has Ever Been Unit-Tested#

Exactly two unit tests exist right now, from Lessons 2 and 3 — neither exercises round_money or hour_bucket. int_trips_summed_to_hour uses both together, in the same select: hour_bucket('pickup_time') twice, once directly as pickup_hour and once inside generate_surrogate_key, and round_money('sum(total_amount)') for hourly_revenue. A single fixture against this one model can cover both macros at once, rather than writing two separate tests for two separate models that each only use one.

Every prior unit test in this project has tested logic written directly inside the model it belongs to — zones.sql’s OR, trips.sql’s left join. hour_bucket and round_money are different: both live in macros/, called from several models this course has already written, and neither has ever been checked directly by anything more rigorous than reading the SQL and trusting it looked right. round_money in particular has appeared, unverified, inside zone_revenue, daily_summary, int_trips_summed_to_hour, and zone_hour_report since Module 6 — four separate places where a rounding mistake could have gone unnoticed, none of them checked until this lesson picks the one model that happens to call both macros at once.

Writing a Fixture That Exercises Both Macros#

Five trips, written specifically to test what each macro does at a genuine boundary rather than an arbitrary one: three trips in the same zone and hour, summing to a dollar figure that doesn’t round cleanly; one trip exactly one hour later, on the other side of hour_bucket’s own truncation; one trip in a different zone, at the identical hour as the first three.

zone_hour_key, the model’s own surrogate key column, is deliberately left out of every expect: row — dbt only checks columns the fixture explicitly names, and generate_surrogate_key’s own hash output isn’t something worth hardcoding by hand into a fixture when the columns it’s built from, pickup_zone and pickup_hour, are already being checked directly.

Running It — and a Real Gotcha#

A failure, on the very first attempt at running this fixture — worth reading carefully rather than assuming, on sight, that one of the two macros must be broken. dbt’s own diff shows hourly_revenue actual 7.0 against expected 7.00, and actual 5.0 against expected 5.00; the row worth 30.02 matched cleanly. The macros aren’t wrong. hourly_revenue: 5.00, written unquoted in the expect: block, parses as the YAML float 5.0 — Python drops a trailing zero a NUMERIC(...,2) column in Postgres never does, and dbt’s own comparison holds the two apart. 30.02 never hit this problem only because neither of its own digits happens to be a trailing zero.

Quoted as "30.02", "5.00", "7.00", every value passes — dbt compares the string against Postgres’s own NUMERIC representation, which preserves the trailing zero round(5.00, 2) always produces, instead of comparing against a Python float that silently dropped it the moment YAML parsed the fixture file. A worth-remembering rule for any future fixture on a rounded or fixed-scale column: quote the expected value whenever its scale matters, since YAML’s own numeric parsing doesn’t know or care that a NUMERIC(...,2) column is supposed to always show two digits after the decimal.

Three findings, all confirmed by this one pass: hour_bucket correctly separates the trip at 14:59:00 from the one at 15:00:00 — the boundary this fixture was built specifically to test, not an arbitrary hour split; round_money correctly rounds $30.015 to $30.02, Postgres’s own round-half-away-from-zero behavior for NUMERIC, confirmed rather than assumed; and the group by correctly separates zone 1’s own three-trip hour from zone 2’s single trip at the identical hour, proving the aggregation keys on both dimensions together, not either one alone.

Proving the Test Still Catches a Regression#

The same discipline as every prior lesson in this module, applied one last time: break one of the two macros deliberately, rerun the identical test, confirm it notices.

Removing round_money’s own round(..., 2) call leaves the raw, unrounded sum(total_amount) behind on all three rows — 30.015 instead of 30.02, the exact boundary this fixture was built to land on, now showing its own un-rounded third digit instead of getting collapsed away. 7.0 and 5.0 fail too, for a related but distinct reason: with no round() call left in the SQL at all, Postgres returns these two single-trip sums without the fixed two-decimal scale a NUMERIC(...,2) normally forces, so even amounts that were always whole numbers now print with only one decimal place. All three rows catch the regression, each exposing a different piece of what round_money actually does — fixing genuine rounding on the boundary case, and fixing scale on the two that were already exact.

Restored, and passing again — round_money and hour_bucket, working together inside int_trips_summed_to_hour since Module 6, now standing behind a fixture that’s already proven, live, twice over, that it notices the moment either macro breaks.

Practice Exercises#

Exercise 1: A fixture for hour_bucket alone#

  • Write a second unit test, this one against zone_revenue, which uses round_money twice — once for total_revenue, once for avg_tip_and_fees — but never calls hour_bucket at all.
  • Confirm directly, by reading zone_revenue.sql, that no fixture written against it could ever exercise hour_bucket.
  • Consider why int_trips_summed_to_hour was the right model to pick for testing both macros together in this lesson, rather than writing two separate single-macro tests against two separate models.

Exercise 2: The is_incremental() question, revisited#

  • int_trips_summed_to_hour is a plain view, not incremental — unlike trips in Lesson 3, this test needed no overrides: block at all.
  • Confirm this directly by reading the file: int_trips_summed_to_hour.sql carries no config() call whatsoever, materialized as a view purely by this project’s own default rather than any explicit setting.
  • Explain in one sentence why a unit test against a view never needs to decide between full-refresh and incremental mode the way an incremental model’s own test does.

Hint

Exercise 1’s answer follows directly from reading zone_revenue.sql’s own select list — a macro a model’s SQL never calls can’t be tested by any fixture built against that model, no matter how the fixture rows are written.

Summary#

int_trips_summed_to_hour got this project’s third unit test overall — five fixture trips exercising hour_bucket and round_money together for the first time since Module 6. The very first run failed on a genuine gotcha, not a macro bug: unquoted 5.00 and 7.00 in the expect: block parsed as plain YAML floats, silently dropping the trailing zero a NUMERIC column always carries. Quoting the values as strings fixed the comparison and confirmed all three findings at once — hour_bucket separating a 14:59:00 trip from a 15:00:00 one, round_money rounding $30.015 to $30.02, and the group by correctly keying on zone and hour together. Removing round_money’s own round() call entirely and rerunning the identical test produced a failure across all three rows — the boundary row exposing its own un-rounded third digit, the two exact-dollar rows losing their fixed two-decimal scale entirely — confirming the fixture protects the logic it claims to, restored and reconfirmed passing afterward.

Key Concepts#

  • One fixture can exercise two macros at once, when a single model happens to use both — no need for two separate single-purpose tests when one model’s logic already combines them.
  • YAML numeric parsing silently drops trailing zeros — quote an expect: value as a string whenever it’s compared against a fixed-scale NUMERIC column, or a correct macro can fail a test for a reason that has nothing to do with its own logic.
  • A fixture only proves what it was specifically built to probe — this lesson’s broken-macro test caught the rounding boundary directly, since the fixture was built specifically to land on one.
  • Testing macros directly isn’t possible in dbt — only the models that call them are, which is why this lesson picked the one model already using both round_money and hour_bucket together.

Why This Matters#

Three unit tests, four lessons, and one confirmed execution order now stand behind logic this project could never have checked with a data test alone — a redundant-but-not-dead condition, a join’s own behavior toward a row that’s never existed, and two macros this project has trusted on inspection since the day they were written and called from four separate models without ever being checked directly. Module 11 builds on all of it: deployment, CI, and the production patterns that decide when these tests actually run, not just whether they pass.
