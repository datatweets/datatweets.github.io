Welcome to Your First Real Messages#

The cluster from Lesson 3 is running. This lesson explains what it’s running — KRaft mode, and what it replaced — tours it visually through Kafdrop, and ends with a real message you produce and consume yourself from the command line.

By the end of this lesson, you will be able to:

  • Explain what ZooKeeper did for older Kafka clusters, and what KRaft replaced it with
  • Read a real Kafdrop cluster overview and topic detail page
  • Create a topic and produce/consume a message entirely from the command line
  • Recognize a normal, expected --timeout-ms exit from a genuine error

What KRaft Replaced#

For most of Kafka’s history, a cluster needed two separate distributed systems to run at all: the Kafka brokers themselves, and Apache ZooKeeper, a separate piece of software Kafka depended on to store cluster metadata (which topics exist, which broker leads which partition) and to elect a controller — the one broker responsible for making cluster-wide decisions like reassigning a partition’s leader when a broker fails.

Running ZooKeeper wasn’t optional and wasn’t free: it meant operating, monitoring, and scaling a second distributed system with its own failure modes, purely to support the first one. KRaft (Kafka Raft) removed that dependency entirely, in a change proposed as KIP-500 and shipped as production-ready starting with Kafka 3.3. Kafka’s own brokers now run the metadata quorum themselves, using the Raft consensus algorithm directly — the exact mechanism Lesson 3’s KAFKA_CONTROLLER_QUORUM_VOTERS setting configured, and the exact thing kafka-metadata-quorum.sh (used later in this lesson) reports on. One system instead of two, and — not incidentally — every recent official Kafka Docker image, including the one this course uses, ships KRaft-only; ZooKeeper support was removed from Kafka entirely as of Kafka 4.0.

Touring CityFlow’s Cluster in Kafdrop#

Kafdrop is running at http://localhost:9000 — open it, and the first thing it shows is a live cluster overview:

Two things worth reading carefully here. First, the Brokers table’s Controller column — exactly one broker shows Yes, the rest show No. That’s KRaft’s leader election from the previous section, made visible: of the three controller-eligible brokers KAFKA_CONTROLLER_QUORUM_VOTERS named, exactly one is currently active. Second, Total under-replicated partitions: 0 — with KAFKA_DEFAULT_REPLICATION_FACTOR: 3 from Lesson 3, every partition should have all three replicas in sync; a nonzero number here would mean a replica has fallen behind, worth investigating immediately rather than ignoring (Module 5 deliberately creates this condition to show what it looks like).

Clicking into the cityflow-hello topic (created for this lesson, ahead of the command-line walkthrough below) shows its own detail page:

The Partition Detail table is worth sitting with: each row is one partition, with its own Leader Node and its own In-sync Replica Nodes. Partition 0’s leader is broker 3; partition 1’s leader is broker 1; partition 2’s leader is broker 2 — Kafka spreads leadership across brokers automatically rather than making one broker the leader for everything, which is exactly what lets three brokers share both write and read load instead of one broker doing all the work while the other two sit idle as pure backups.

Your First Produce and Consume#

Kafdrop shows what’s already in a topic. This section puts something there yourself, entirely from the command line — no Python yet, that starts in Module 3. First, create the topic (recall from Lesson 3: KAFKA_AUTO_CREATE_TOPICS_ENABLE is false, so this step is required, not optional):

Now produce a real message. kafka-console-producer.sh reads lines from standard input and sends each one as a separate message — piping a single line in produces exactly one message, then the producer exits:

That command produces no output on success — the message is simply sent. Confirm it arrived by consuming it back:

Read that output in order, not by how alarming the middle looks: hello from CityFlow printed first — the actual message, consumed correctly, exactly as sent. The ERROR/TimeoutException block underneath isn’t a bug in this course’s setup; it’s --timeout-ms 5000 doing precisely what it’s documented to do — kafka-console-consumer.sh has no built-in “stop after N messages” flag, so --timeout-ms is the standard way to make an otherwise-infinite consumer exit automatically once 5 seconds pass with nothing new to read. The final line, Processed a total of 1 messages, is the tool’s own honest summary, and it’s correct: one message was produced, one message was consumed. Real Kafka consumers you write starting in Module 4 don’t use this flag or exit this way — this is a command-line convenience specific to the console tools, not how a production consumer behaves.

Refresh Kafdrop’s cityflow-hello topic page, click View Messages, and the exact same message is there to inspect visually:

Offset 0 — the first record ever written to whichever partition the producer’s default partitioner happened to route this key-less message to (partition 1, in this run; without a key, Kafka distributes messages round-robin-ish across partitions, a topic Module 3 covers with repeatable examples once keys enter the picture). No key, because this command never set one. A timestamp, set by the broker at the moment it received the message. The same message this course has now confirmed three separate ways: the console consumer’s own output, Kafdrop’s topic-level “Total available messages” count, and Kafdrop’s message-level view showing the literal text.

Practice Exercises#

Exercise 1: Produce three messages, one command#

Modify the produce command to send three separate lines with one invocation (printf 'one\ntwo\nthree\n' | docker exec -i ... instead of echo). Consuming with --from-beginning replays every message this lesson has produced to cityflow-hello so far, not just these three — confirm the consumer reports Processed a total of 4 messages (this lesson’s earlier “hello from CityFlow” plus the new three), and check Kafdrop’s Partition Detail table to see how the new messages distributed across cityflow-hello’s three partitions.

Hint

printf with embedded \n characters produces multiple stdin lines the same way pressing Enter between messages would in an interactive producer session.

Exercise 2: Confirm the controller can be any of the three brokers#

Run docker exec kafka1 /opt/kafka/bin/kafka-metadata-quorum.sh --bootstrap-server kafka1:29092 describe --status and find the LeaderId field. Cross-check it against Kafdrop’s own cluster overview page — confirm the broker ID Kafdrop marks Controller: Yes matches the LeaderId this command reports.

Summary#

ZooKeeper used to store Kafka’s cluster metadata and run controller elections as a separate distributed system; KRaft mode (KIP-500, production-ready since Kafka 3.3, and the only mode Kafka 4.0 supports at all) moved that responsibility into the brokers themselves via Raft consensus — the exact mechanism KAFKA_CONTROLLER_QUORUM_VOTERS configured in Lesson 3. Three Kafdrop screenshots showed CityFlow’s actual cluster: one elected controller out of three eligible brokers, zero under-replicated partitions, and per-partition leader/replica detail proving leadership is spread across all three brokers rather than concentrated on one. A topic, created explicitly, carried one message from kafka-console-producer.sh to kafka-console-consumer.sh, confirmed a third way in Kafdrop’s own message view — with an honest explanation of why --timeout-ms’s TimeoutException in the consumer’s output is an expected exit, not a failure.

Key Concepts#

  • KRaft replaced ZooKeeper — Kafka’s own brokers now run metadata storage and controller election via Raft consensus, one system instead of two, and the only mode Kafka 4.0 ships.
  • Exactly one broker is the active controller at a time — confirmed visually in Kafdrop and via kafka-metadata-quorum.sh describe --status’s LeaderId field.
  • Leadership is spread across partitions, not concentrated on one broker — each of cityflow-hello’s three partitions has a different leader broker.
  • --timeout-ms’s TimeoutException is a documented, expected exit for the console consumer tool specifically — not a sign anything is broken, and not how a real consumer (Module 4) behaves.

Why This Matters#

Being able to read a cluster’s real state — which broker is the controller, whether partitions are under-replicated, whether a “scary-looking” log line is actually an error — is a skill this entire course depends on, starting now rather than being deferred to an “operations” module at the end. Every lesson from here produces and consumes messages against this same cluster; knowing how to check it’s healthy and read what it’s telling you is the foundation everything else builds on.
