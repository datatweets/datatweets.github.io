Welcome to Apache Kafka for Data Engineers#

You’re joining CityFlow, a small mobility-analytics team already familiar from this site’s Data Engineering path — the team that profiled, chunked, parallelized, containerized, and orchestrated a batch analytics pipeline over real NYC taxi trip data in the courses before this one. Every one of those courses answered a version of the same question: how do you process data you already have, sitting in a file? This course answers a different question: how do you process data the moment it happens, before anyone has written it to a file at all? That’s event streaming, and Apache Kafka is the tool this course teaches to do it.

This first lesson installs nothing. Before you bring up a single container, you need to feel the actual problem Kafka exists to solve — not as an abstract claim, but as a real, broken piece of code you build yourself.

By the end of this lesson, you will be able to:

  • Explain what “tight coupling” between systems actually costs, concretely
  • Build a real point-to-point integration and watch it fail in a specific, avoidable way
  • Fix that failure with a minimal publish-subscribe pattern, in plain Python
  • Recognize the two things a plain in-memory fix still can’t do — setting up why Kafka exists

CityFlow’s Real Problem#

A taxi trip finishes. That single event — trip complete, this driver, this fare — matters to more than one system:

  • Billing needs to charge the rider.
  • Driver earnings needs to credit the driver.
  • Dispatch needs to mark the driver available for a new ride.

The most direct way to wire this up is exactly what it sounds like: the code that detects a trip is complete calls each of those three systems directly, one after another.

This works, and it’s how a lot of real systems start. complete_trip_point_to_point knows about all three downstream systems by name, calls each one directly, and moves on. Nothing here is wrong yet — the problem shows up under two conditions every real system eventually hits: growth, and failure.

The Growth Problem#

CityFlow’s product team wants a fourth thing to happen on trip completion: log the trip to analytics for reporting. Where does that code go? Directly into complete_trip_point_to_point, which now has to import, call, and know about a fourth system. A fifth request — notify the rider’s phone — means a fifth edit to the same function. The function that detects “a trip is complete” is not supposed to be an expert in billing, driver payments, dispatch, analytics, and notifications, but a point-to-point design forces it to become one, one integration at a time, forever. Every new downstream consumer is a code change to the producer.

The Failure Problem — Watch It Break#

Growth is an inconvenience. This next one is a real bug, not a hypothetical — trigger it directly:

Read that output carefully: billing being unreachable — a completely unrelated system to dispatch — silently stopped the driver from ever being marked available again. In a fleet this size, that’s a driver stuck “on a trip” in the dispatch system indefinitely, for a reason that has nothing to do with dispatch. This is what tight coupling actually costs: not just “hard to add a fourth system,” but “one system’s outage becomes every system’s outage,” purely because of call order in a function nobody meant to design that way.

A Minimal Fix: Publish-Subscribe#

The fix isn’t a smarter try/except around each call — it’s changing who’s responsible for knowing about whom. Instead of the trip-completion code calling billing, driver-earnings, and dispatch by name, it publishes one event to a small bus, and each interested system subscribes to hear about it independently:

The identical failure — billing still throws ConnectionError for trip T-1002 — no longer stops dispatch or driver-earnings. Each subscriber runs independently; one failing doesn’t cancel the rest. That alone fixes the failure problem this lesson opened with.

The growth problem is fixed too, and worth proving rather than just claiming:

bus.publish(trip3) is the exact same call it was before analytics existed. complete_trip_point_to_point’s equivalent in this new design — the code that fires when a trip completes — was never touched to add a fourth subscriber. That’s the actual shape of decoupling: producers publish without knowing who’s listening, and consumers subscribe without the producer’s code ever changing.

What SimpleEventBus Still Can’t Do#

This lesson’s fix works, and the pattern behind it is exactly right — but SimpleEventBus itself is a toy, and naming its limits honestly is what motivates the rest of this course:

  1. It has no memory. Once publish() returns, the event is gone. A subscriber that wasn’t running yet — or crashed and restarted — missed it forever. There’s no way to ask “what happened in the last hour,” because nothing was kept.
  2. It’s one process. bus, bill_customer_unreliable, and every subscriber all live inside the same Python program, on the same machine. A production fleet’s billing, dispatch, and analytics systems are separate services, often written in different languages, that can’t share an in-memory Python list.

Apache Kafka solves both problems at once by replacing “an in-memory list of function references” with a real, durable, distributed log that multiple independent processes can publish to and read from — durable enough that a subscriber that was down for an hour can catch up on everything it missed, and distributed enough that publishers and subscribers don’t need to run on the same machine, or even know each other exist beyond a shared topic name. Lesson 2 introduces that log directly.

Practice Exercises#

Exercise 1: Trigger the growth problem yourself#

Add a fifth downstream function, notify_rider(trip), to both complete_trip_point_to_point (Exercise: count exactly how many lines you had to touch) and to bus (count again). Confirm the gap between the two counts is the entire point of this lesson.

Hint

For the point-to-point version, you have to both define the function and add a call to it inside complete_trip_point_to_point. For the bus version, you only ever call bus.subscribe(notify_rider) — the publishing code doesn’t change at all.

Exercise 2: Prove the “no memory” limitation directly#

Create a new SimpleEventBus with zero subscribers, call .publish() on one trip, then call .subscribe() with a handler, and confirm the handler never sees that earlier trip. Explain in one sentence why this matters for a driver-earnings system that might be redeployed (and briefly offline) several times a day.

Summary#

A point-to-point trip-completion function that calls billing, driver-earnings, and dispatch directly has two real costs, both demonstrated here rather than just claimed: growing it needs the producer’s own code edited for every new consumer, and one downstream failure — billing going down — silently broke an unrelated system, dispatch, purely because of call order. A minimal in-memory publish-subscribe bus fixed both: a failing subscriber no longer blocks the others, and a fourth subscriber joined with zero changes to the publishing code. That bus still can’t survive a crash or run across more than one process — which is exactly the gap Kafka fills.

Key Concepts#

  • Tight coupling means a producer’s code has to know about, and call, every consumer by name — proven costly here two ways: harder to grow, and one failure cascades into unrelated systems.
  • Publish-subscribe decouples producers from consumers: publishers don’t know who’s listening, subscribers don’t require the publisher’s code to change.
  • A subscriber’s failure shouldn’t take down other subscribers — SimpleEventBus’s try/except per handler proved this directly, not just by assertion.
  • An in-memory bus has no memory and no distribution — both named limits this course’s next lesson starts fixing.

Why This Matters#

Every lesson in this course, from the first real Kafka topic onward, is solving a bigger version of exactly the two problems demonstrated here: let independent systems publish and subscribe to events without hardcoding who’s on the other end, and don’t let one system’s outage take down another. Kafka’s specific mechanics — partitions, offsets, consumer groups, replication — are all in service of that same idea at a scale and durability a Python list can’t reach.
