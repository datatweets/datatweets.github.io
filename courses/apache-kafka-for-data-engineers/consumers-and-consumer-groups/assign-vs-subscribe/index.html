Welcome to assign() vs. subscribe()#

Every consumer this module has built calls subscribe() and lets a consumer group decide which partitions it owns. Kafka offers a second way to read a topic that skips groups, rebalancing, and the lazy group-join Lesson 1 found hiding inside the first poll() — assign(), where the calling code names the exact partition it wants, and Kafka does exactly that and nothing more.

By the end of this lesson, you will be able to:

  • Read one specific partition directly with assign(), no group required
  • Explain why assign()’s assignment is immediate, unlike subscribe()’s
  • Use assign() with a group_id for offset tracking without triggering a rebalance
  • Recognize the real error Kafka raises if code tries to mix both modes

assign(): Immediate, No Group-Join#

Assign one exact partition and check consumer.assignment() right away — no poll() needed first:

Compare this directly against Lesson 1’s own finding: subscribe() leaves assignment() empty until the first poll() finishes a group-join handshake with the coordinator. assign() needs no handshake at all — there’s no group to join, no coordinator to negotiate with, just a direct instruction: “read exactly this partition.” consumer.assignment() reflects that instruction the instant assign() returns. seek_to_beginning(tp) then does what auto_offset_reset did implicitly for a group-managed consumer — position the read at the start of the partition’s log — and every one of the 20 records read back confirms it came from partition 2, exactly as instructed.

assign() With a group_id: Offsets, No Rebalancing#

assign() doesn’t require going without a group_id — set one anyway, and commits still work for offset tracking, without any rebalancing behavior kicking in:

The group_id here does exactly one job: it gives commit() somewhere to store this consumer’s offset for partition 2, so a later restart with the same group_id and the same assign() call can resume where it left off — Lesson 3’s offset mechanics, still available. What it does not do is trigger Lesson 2’s rebalancing behavior: adding a second consumer with the same group_id alongside this one wouldn’t split partition 2 between them or hand either one a different partition, because neither consumer ever subscribed to a group’s shared partition pool in the first place. assign() opts a consumer entirely out of that mechanism, deliberately, while still letting it use the group machinery for offset storage if that’s useful.

Mixing the Two Raises a Real Error#

Kafka doesn’t allow a consumer to be both self-directed and group-managed at once. Call subscribe() on a consumer that already called assign(), and it fails immediately:

The error message names all three legal configurations directly, and “some of each” isn’t one of them. This isn’t a kafka-python quirk — it reflects a real constraint in Kafka’s own consumer protocol: a consumer either participates in a group’s coordinated partition assignment, or it manages its own partitions directly, and mixing the two would leave the group coordinator and the manual assignment disagreeing about who owns what.

A Real Use for assign(): Reading Just the Last N Messages#

Manual control over exactly which offset to start from is what makes assign() genuinely useful for a debugging tool — “show me only the last 5 messages on this partition,” something a group-managed subscribe() consumer has no clean way to do, since it always starts from either the earliest unread offset or the very latest. Compute it directly with end_offsets():

end_offsets() reports the next offset that would be written — 20, meaning offsets 0 through 19 already exist. Subtracting 5 and calling seek() positions the consumer exactly 5 records from the end, and the five offsets read back — 15 through 19 — confirm it landed precisely where computed, not approximately. Kafdrop’s own message view does something similar visually, showing a topic’s most recent records; this is the same idea, built from assign() and seek() directly, callable from a script instead of a browser.

When Each One Is the Right Tool#

subscribe() is the right default for almost everything this course builds — CityFlow’s trip-event consumers, the guided project’s reconciliation workers, anything where parallel processing and automatic failover matter more than controlling exactly which partition a given process reads. assign() earns its place in narrower situations: a debugging tool that needs to inspect one specific partition without disturbing a running consumer group’s balance; a per-partition worker architecture where partition ownership is decided by deployment configuration rather than Kafka’s own rebalancing (common when partition-to-worker mapping needs to stay stable for reasons outside Kafka’s knowledge, like a downstream system keyed the same way); or exactly this lesson’s own debugging use — reading one partition in isolation to confirm what’s actually on it, the same job Kafdrop’s UI does visually, done here from Python instead.

The tradeoff underneath both choices is the same one Lesson 2 already measured, just seen from the opposite direction: subscribe() buys automatic failover — if a consumer in the group dies, Lesson 2’s own rebalance mechanism hands its partitions to whoever’s left, without any external system noticing or intervening. assign() gives up that safety net entirely; if a process managing an assigned partition dies, nothing else in the cluster knows or cares, and that partition simply stops being read until something restarts the exact process responsible for it. That’s a real cost, worth paying deliberately for the control assign() buys, not accepted by default because it happened to be the first API found in the documentation.

Practice Exercises#

Exercise 1: Assign two partitions at once#

Modify this lesson’s first example to assign() a list of two TopicPartition objects instead of one — partitions 0 and 2 of cityflow-assign-check. Confirm consumer.assignment() shows both, and that records read back come from both partitions, not just one.

Exercise 2: Confirm assign() never rebalances#

Start two separate consumers, both calling consumer.assign([TopicPartition(TOPIC, 2)]) — the exact same partition, not different ones — with no group_id set on either. Confirm both consumers can read the same messages from partition 2 independently, with neither one “losing” the partition to the other the way Lesson 2’s subscribe()-based consumers would if assign() triggered rebalancing.

Hint

Without a shared group_id, there’s no group at all for Kafka to rebalance — each assign() call is entirely local to its own consumer instance, unrelated to whatever any other consumer is doing.

Summary#

assign() gives a consumer immediate, precise control over exactly which partitions it reads — consumer.assignment() populates the instant assign() returns, with no lazy group-join like subscribe() needs, confirmed by reading 20 real messages from exactly the assigned partition and nothing else. Setting a group_id alongside assign() still enables offset commits for tracking, without triggering any of Lesson 2’s rebalancing behavior. Kafka’s consumer protocol treats the two modes as genuinely incompatible — mixing them raises a real IllegalStateError naming all three legal configurations, confirming this is a protocol-level constraint, not an implementation detail.

Key Concepts#

  • assign() is immediate; subscribe() is lazy — assignment() populates right away with assign(), versus needing a first poll() with subscribe().
  • assign() reads exactly what it’s told, confirmed here: every record came from the one assigned partition.
  • group_id still works with assign() — for offset tracking only, never for rebalancing.
  • Mixing assign() and subscribe() raises a real, protocol-level error — a consumer must pick one mode.

Why This Matters#

This module’s guided project uses subscribe(), deliberately — CityFlow’s reconciliation workers need automatic partition splitting and failover, exactly what a consumer group provides. Knowing assign() exists, and precisely what it trades away to get precise manual control, is what makes that choice a decision rather than the only option anyone showed you. It also means this lesson’s own “read the last 5 messages” pattern stays available as a real debugging tool for every topic this course builds from here — a quick way to check what actually landed on cityflow-trip-events without disturbing whatever consumer group is already reading it for real work.
