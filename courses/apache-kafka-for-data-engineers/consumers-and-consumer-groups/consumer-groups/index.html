Welcome to Consumer Groups#

Lesson 1 built one consumer and watched poll() join a group of one. This lesson adds more members to that same group, live, and watches Kafka do the thing a consumer group actually exists for: splitting a topic’s partitions across however many consumers are currently in the group, automatically, every time that number changes.

By the end of this lesson, you will be able to:

  • Run more than one consumer under the same group_id and confirm they split partitions
  • Watch a real rebalance happen when a consumer joins an active group
  • Watch a second real rebalance happen when a consumer leaves
  • Explain why partition count caps how many consumers a group can use productively

Why Threads, Not Separate Scripts#

This lesson runs three consumers inside one Python process, on three threading.Thread objects, rather than three separate terminal windows each running its own script — a deliberate choice, not a shortcut that changes what’s being demonstrated. Kafka has no idea whether consumer-A, consumer-B, and consumer-C are three threads, three processes, or three machines in different data centers — a consumer group’s rebalancing protocol only cares that three separate KafkaConsumer connections joined the same group_id, each with its own session to the group coordinator. Python’s GIL would matter if this lesson needed real CPU parallelism; it doesn’t, because consumer.poll() spends almost all of its time waiting on the network, not computing — exactly the kind of work threads handle well despite the GIL, since a thread blocked on a socket read releases the GIL for other threads to run. Three real, independent consumer group members, verified live, without needing three terminal windows to prove it.

One Consumer, All Six Partitions#

cityflow-rebalance-check has 6 partitions. Start a single consumer thread in the group and watch what it gets assigned once its own group-join (Lesson 1’s poll #0) finishes:

Exactly Lesson 1’s finding, seen again: the first check at 0.5s shows an empty assignment while the group-join is still in flight, and by 3.6s consumer-A owns all six partitions — the only member of cityflow-rebalance-demo, so it gets everything.

A Real Rebalance: Consumer B Joins#

Start a second consumer thread, in the same group, while consumer-A keeps running:

A real rebalance, triggered automatically the moment consumer-B joined: consumer-A’s assignment changed from all six partitions down to [0, 1, 2], and consumer-B picked up the other three, [3, 4, 5]. Nobody told either consumer which partitions to take — Kafka’s group coordinator recalculated the split the instant it saw a second member and reassigned both consumers to match, mid-run, without either one restarting.

A Second Rebalance: Consumer C Joins#

Add a third consumer, same group, same live topic:

Six partitions, three consumers, two apiece — consumer-A keeps [0, 1], consumer-B drops to [4, 5], consumer-C picks up [2, 3]. Every rebalance so far has kept the split as even as six divides: one consumer gets all 6, two consumers get 3 each, three consumers get 2 each.

A Third Rebalance: Consumer A Leaves#

Stop consumer-A and watch its partitions get picked back up:

A third real rebalance, this time triggered by a member leaving rather than joining — Kafka detects consumer-A’s absence (its consumer.close() sends an explicit leave-group notification, not just a silent timeout) and redistributes its two partitions between the two remaining members, back to a 3-and-3 split. The mechanism is identical whether a consumer joins or leaves: the group coordinator recalculates the assignment and every member gets told what it now owns.

Who Decides the Split? partition_assignment_strategy#

Something calculated these exact splits, and it’s worth naming: kafka-python defaults partition_assignment_strategy to a tuple of two assignors, tried in order — RangePartitionAssignor first, falling back to RoundRobinPartitionAssignor only if every group member doesn’t support range assignment. Confirm the default directly:

RangePartitionAssignor — the one this lesson’s rebalances actually used — sorts the group’s members and hands out contiguous ranges of partition numbers per topic, which is exactly the shape this lesson’s own output showed: [0, 1, 2]/[3, 4, 5] for two consumers, not some scattered pattern. Nothing in this lesson’s code chose this strategy explicitly — it’s what kafka-python uses unless told otherwise, the same “sensible default, override deliberately” pattern Module 3 Lesson 3 covered for acks and batching.

Why Partition Count Is a Hard Ceiling#

Add a hypothetical fourth consumer to this same group, and it would get zero partitions — not an error, just an idle process, because six partitions can’t be split more than six ways without some consumer getting nothing. This is Module 2 Lesson 1’s “partition count caps per-group consumer parallelism” claim, now demonstrated rather than just stated: a consumer group can never usefully run more members than the topic has partitions, and CityFlow’s 6-partition cityflow-trip-events (Module 2’s guided project) caps this course’s own consumer groups at 6 productive workers, a number this module’s own guided project puts to real use.

Practice Exercises#

Exercise 1: Confirm the assignment is a true partition, not a copy#

While consumer-A and consumer-B are both running with the [0, 1, 2]/[3, 4, 5] split from this lesson, produce a new message keyed so it lands on partition 4 (Module 2 Lesson 4’s technique). Confirm only consumer-B — the one currently assigned partition 4 — ever sees it, not consumer-A.

Exercise 2: Time how long a rebalance actually takes#

Using this lesson’s own logging pattern, measure the gap between a new consumer thread starting and the moment every member’s assignment stabilizes into its new split. Is it closer to 1 second or 10? What does that tell you about how quickly a real production consumer group recovers from a worker restarting?

Hint

This lesson’s own timestamps already contain the answer — measure the gap between each thread’s start and its first non-empty assignment.

Summary#

Three real rebalances, all triggered automatically by consumer group membership changing: one consumer starts with all 6 partitions, a second consumer joining splits them 3-and-3, a third joining splits them 2-2-2, and the first consumer leaving hands its partitions back to the remaining two as a 3-and-3 split again. No application code decided any of these splits — Kafka’s group coordinator recalculated and reassigned automatically every time, confirmed here by watching consumer.assignment() change live across three separate threads sharing one group_id.

Key Concepts#

  • Consumers sharing a group_id split a topic’s partitions between them — proven directly across three live membership changes.
  • A rebalance triggers on both joining and leaving — the same underlying mechanism, confirmed for both directions.
  • The split stays as even as the partition count allows — 6-and-0, then 3-and-3, then 2-2-2, then back to 3-and-3.
  • Partition count is a hard ceiling on productive group size — a fourth consumer here would get zero partitions, not an error.

Why This Matters#

This module’s guided project runs a real consumer group against cityflow-trip-events to reconcile CityFlow’s full trip history — knowing that Kafka handles the partition split automatically, correctly, and without any application code managing it directly, is what makes running multiple workers in parallel a safe default instead of a risk to engineer around.
