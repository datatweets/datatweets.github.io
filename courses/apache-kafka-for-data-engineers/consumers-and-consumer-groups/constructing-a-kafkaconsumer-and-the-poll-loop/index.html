Welcome to Consumers#

Every consumer this course has used so far — Module 2’s routing proofs, Module 3’s replay verification — wrote for record in consumer: and let kafka-python handle the details. That loop is convenient specifically because it hides something worth seeing directly: underneath it, the consumer is calling poll() again and again, and the very first call behaves differently from every one after it.

By the end of this lesson, you will be able to:

  • Construct a KafkaConsumer, subscribe it to a topic, and call poll() directly
  • Explain why the first poll() call after subscribe() returns nothing
  • Read consumer.assignment() to see which partitions a consumer actually owns
  • Name every field a real ConsumerRecord carries

poll(), Called Directly#

Produce five small messages, then subscribe a consumer and call poll() five times in a row, printing the assignment and the record count after each call:

subscribe() alone does not join the group — it only records which topic this consumer wants. The actual joining happens lazily, inside the first poll() call: poll #0 returns an empty dict with assignment() still showing an empty set, because that call spent its time on the group-join handshake (finding the group coordinator, being assigned partitions) rather than fetching records. Only from poll #1 onward does assignment() show all three partitions, and only from there does poll() start returning actual data — 2 records on the second call, 3 more on the third, 5 total, matching every message this lesson produced. poll #3 and #4 return empty because there’s nothing left to read, not because anything failed.

Three Constructor Arguments That Matter#

KafkaConsumer(...) in this lesson’s example set three arguments beyond bootstrap_servers, each one a real decision rather than boilerplate:

  • group_id — the name of the consumer group this instance joins. Every consumer sharing the same group_id splits a topic’s partitions between them (Lesson 2 proves this directly); a consumer with no group_id at all runs standalone, outside any group, a distinction Lesson 4 covers in full. "cityflow-poll-demo" here is arbitrary but meaningful — a real system would name it for what the group does, the same discipline Module 2 Lesson 5 applied to topic names.
  • auto_offset_reset — what to do when this consumer group has no committed offset yet for a partition (a brand-new group, exactly this lesson’s situation). "earliest" means start from the very beginning of the partition’s log; the alternative, "latest", would mean start from whatever’s produced after this consumer connects, silently skipping everything already there. Every lesson so far that needed to see previously-produced messages set this explicitly, because Kafka’s own default is "latest" — skipping history unless told otherwise.
  • value_deserializer — the mirror image of a producer’s value_serializer from Module 3. Bytes come off the wire; this function turns them back into a Python object, here reversing the exact json.dumps(v).encode() Module 3’s producers used to go the other direction.

Getting auto_offset_reset wrong is a genuinely common way to write a consumer that appears to work — no error, no warning — while silently missing every message produced before it started. It only shows up as a bug when someone asks “why didn’t my consumer see any of yesterday’s data?”

Why the for record in consumer: Loop Hides This#

Every prior lesson’s for record in consumer: pattern is kafka-python’s own convenience wrapper — internally, it calls poll() in a loop exactly like this lesson just did by hand, silently absorbing the empty first call and yielding records one at a time as later calls return them. That’s a reasonable default for reading a topic start to finish. It stops being enough the moment code needs to do something between batches — check consumer.assignment() to see which partitions this process currently owns, react differently to an empty poll than a non-empty one, or control exactly how long to wait for new records before giving up. poll(timeout_ms=...) is the primitive; the for loop is one specific, convenient way of driving it.

Every Field a ConsumerRecord Carries#

The records poll() returns aren’t dict values with only key/value — a real ConsumerRecord is a namedtuple with thirteen fields:

Most of these have come up already, produced by earlier modules and read back through for record in consumer: without ever naming the container that held them: topic, partition, offset, timestamp, key, value, and headers are the ones every lesson from here actually uses — the same fields Module 2 Lesson 2 sent and confirmed round-tripping through a producer, now seen from the consumer’s own side. The rest exist for narrower purposes: leader_epoch and checksum are internal consistency bookkeeping most application code never touches directly; serialized_key_size/serialized_value_size/serialized_header_size report the on-the-wire byte counts after whatever compression Module 3 Lesson 3 covered, useful for exactly the kind of “how much did that compression actually save in production” question that lesson answered with a one-off measurement instead of a live number.

Read one real record’s fields directly, rather than trusting the list of names alone:

headers comes back an empty list because this lesson’s own producer call never set any, exactly as Module 2 Lesson 2 predicted for a key-less or header-less send. serialized_value_size reports 10 bytes — the actual on-the-wire size of {"seq": 1} as JSON, not a Python-object size estimate, confirming it measures what the network actually carried.

Practice Exercises#

Exercise 1: Count how many empty polls it takes to join#

Subscribe a fresh consumer (a new group_id no group has used before) to a topic with no unread messages waiting, and call poll(timeout_ms=500) in a loop, printing consumer.assignment() after each call, until it’s non-empty. Does it always take exactly one empty poll, or can it vary? Run it three times and report what you see.

Exercise 2: Confirm subscribe() alone doesn’t reach the broker#

Immediately after consumer.subscribe([TOPIC]), without calling poll() at all, check consumer.assignment(). Then check consumer.topics() (a separate call that lists every topic the cluster has, requiring its own broker round trip). Explain in one sentence why assignment() can be empty here while topics() still returns real data.

Hint

topics() asks the broker for cluster metadata, a different request than the group-join poll() performs — a consumer can know what topics exist without yet knowing which partitions it personally owns.

Summary#

poll(), called directly instead of hidden behind a for loop, revealed something the convenient version never shows: the first call after subscribe() returns an empty dict with no partitions assigned yet, because that call spends its time joining the consumer group rather than fetching data — confirmed here across five real calls, with assignment() staying empty through the first and populated from the second onward. A ConsumerRecord carries thirteen real fields, most already used implicitly in earlier lessons without ever being named as a namedtuple.

Key Concepts#

  • subscribe() only records intent — it doesn’t join the group. The actual join happens lazily, inside the first poll() call.
  • The first poll() after subscribe() returns empty, confirmed directly: assignment() stayed set() until the second call.
  • for record in consumer: is poll() wrapped in a loop — convenient for simple reads, insufficient once code needs to react between batches.
  • ConsumerRecord has 13 fields, seven used constantly (topic, partition, offset, timestamp, key, value, headers) and six for narrower internal or diagnostic purposes.

Why This Matters#

Module 4’s guided project runs multiple consumer processes at once, each needing to know exactly which partitions it owns at any given moment — information that only poll() and assignment(), not the convenience loop, expose directly. Lesson 2 builds on this immediately: watching partition assignment change while a consumer group is running, which requires calling poll() in an explicit loop exactly like this lesson just did.
