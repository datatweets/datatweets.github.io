Welcome to Topics and Partitions#

Module 1 Lesson 2 built AppendOnlyLog in plain Python and mapped it directly onto Kafka’s vocabulary: a partition is that log, persisted and replicated. This lesson picks up exactly where that mapping left off, on the real cluster: what a topic is when it has more than one partition, and what that buys you that a single log genuinely can’t.

By the end of this lesson, you will be able to:

  • Define a topic precisely: a named stream backed by one or more partitions
  • Read a real kafka-topics.sh --describe output and explain every column
  • Explain why a topic with more partitions spreads leadership across more brokers
  • Recognize that “more partitions” is a parallelism decision, not a data-modeling one

A Topic Is a Name; Partitions Are Where the Data Lives#

A topic is the name producers write to and consumers read from — cityflow-trip-events, cityflow-hello, whatever you called it. The topic itself holds nothing. Every record actually lives in one of the topic’s partitions, and each partition is exactly the append-only log Module 1 Lesson 2 built by hand: an ordered, immutable sequence with its own offsets, replicated across brokers, with one broker acting as that partition’s leader — the only replica any producer or consumer talks to directly for that partition.

A topic with one partition is legal and simple: create it, and there’s exactly one log, with exactly one leader broker handling every write and every read. Confirm that directly:

One line, one partition. Read the columns left to right: Partition is the partition’s number (0, the only one here); Leader is the broker ID handling every read and write for it (broker 2); Replicas lists every broker holding a copy, leader first (2,3,1 — all three, since this topic asked for --replication-factor 3); Isr is the “in-sync replicas” subset actually caught up right now (all three here, meaning nothing has fallen behind — Module 5 deliberately breaks this to show what a lagging replica looks like). Every write to this topic, no matter which producer sends it or which broker that producer happens to connect to first, ultimately goes through broker 2, because there’s only one partition and it only has one leader.

Six Partitions, Six Chances to Spread the Load#

Now create a topic that asks for six partitions instead of one, with the same replication factor:

Six rows now, one per partition, and the Leader column is where this pays off: 1, 2, 3, 1, 2, 3 — Kafka spread the six partitions’ leadership evenly across all three brokers, two each, entirely on its own. That’s the real, mechanical reason a topic almost never stays at one partition: a one-partition topic caps every write at whatever a single broker can handle, and caps every consumer group at exactly one active reader per partition (Module 4 covers consumer groups in full, but the cap itself is visible right here — a topic literally cannot have more simultaneously active consumers in one group than it has partitions, because Kafka never splits a partition’s records between two group members). Six partitions means up to six brokers’ worth of write throughput and up to six consumers reading in parallel, from one topic.

Partition count is a parallelism knob, not a filing system

It’s tempting to think a topic should have one partition per “kind” of thing it holds — one per taxi zone, one per event type. That’s not what partitions are for, and Lesson 4 shows directly why: many different keys share a small number of partitions by design, via hashing, and that’s normal, not a limitation to work around.

Why This Actually Matters for CityFlow’s Volume#

This isn’t an abstract concern. Courses 1 and 2 already established CityFlow’s real scale: 9,554,757 trips across three real months (January–March 2024) of NYC taxi data. If every one of those trips became a Kafka message — which Module 3’s producer starts doing for real — a one-partition topic would force every single write through one broker’s one log, one after another, no matter how many producer processes CityFlow ran at once. Six partitions doesn’t mean “six times faster” automatically (network, disk, and broker CPU all still matter), but it does mean six independent logs, on potentially six different broker leaders, each accepting writes without waiting on the others — the actual mechanism, not a hand-wave, behind why real Kafka deployments almost never run single-partition topics for anything with real volume behind it.

The same math applies to reading. Module 4’s consumer groups let several consumer processes split a topic’s partitions between them, each one handling only its assigned partitions. A one-partition topic caps that split at one consumer doing all the work; a six-partition topic lets up to six consumers each handle a sixth of the load, in parallel, with Kafka itself managing which consumer owns which partition.

How Many Partitions Is Too Many?#

More partitions sounds like it’s always better, and it isn’t — this is well-documented Kafka operational guidance, not something six partitions on a demo cluster can measure directly. Every partition is a real set of files on every broker that replicates it, and every broker in a cluster has to track metadata for every partition it hosts, whether that partition is busy or sitting completely idle. Push partition counts into the thousands on a small cluster and three concrete costs show up: more open file handles per broker, slower leader elections when a broker restarts (every one of that broker’s led partitions needs a new leader chosen), and more replication traffic just to keep idle partitions in sync. None of that is a reason to fear partitions — six, sixty, even a few hundred is routine for a real cluster — but it is the honest other half of “more partitions, more parallelism”: the right number is driven by how much real parallel throughput a topic needs, not by making it as large as possible “to be safe.” Lesson 5’s guided project makes exactly this call for cityflow-trip-events, with a written reason instead of a guess.

Practice Exercises#

Exercise 1: Describe cityflow-hello again, with fresh eyes#

Module 1 created cityflow-hello with 3 partitions and 3 replicas. Run kafka-topics.sh --describe --topic cityflow-hello again now and identify which broker leads each of its three partitions. Cross-check the answer against the Partition Detail table in Kafdrop’s topic page for cityflow-hello — they must match, since Kafdrop reads this from the exact same cluster metadata --describe does.

Exercise 2: List every topic, not just one#

Run kafka-topics.sh --bootstrap-server kafka1:29092 --list and confirm both topics this lesson created are there alongside cityflow-hello and Kafka’s own internal __consumer_offsets topic (used to store consumer group commit positions — Module 4 explains it properly). --list shows names only; --describe is what you reach for once you need to know partition count, replication, or leadership for a specific one.

Hint

--describe without --topic describes every topic at once — useful once a cluster has more than a couple, though CityFlow’s is still small enough to name topics explicitly.

Summary#

A topic is a name; the data lives in its partitions, and each partition is the same append-only log Module 1 built in plain Python, now persisted and replicated on real brokers. A one-partition topic, created and described here, has exactly one leader broker handling every read and write. A six-partition topic, created and described the same way, spread its leadership across all three brokers automatically — two partitions per broker — which is the concrete, measured reason topics get more than one partition: parallelism for both writes and, per consumer group, reads.

Key Concepts#

  • A topic is a name; partitions hold the data — each partition is one append-only log with its own leader broker and its own set of replicas.
  • --describe’s columns: Partition, Leader, Replicas (leader first), and Isr (currently caught-up replicas) — read directly off a real cluster in this lesson.
  • More partitions spreads leadership across more brokers — confirmed directly: six partitions landed two leaders on each of three brokers, versus one partition’s single leader.
  • Partition count caps per-group consumer parallelism — a topic can never have more simultaneously active readers in one consumer group than it has partitions (Module 4 covers this fully).

Why This Matters#

Every design decision from here — how many partitions a topic should have, why a producer’s key determines where a message lands, how many consumers a group can usefully run — traces back to this lesson’s one measured fact: partitions are how Kafka spreads work across brokers and consumers, and a topic’s partition count is a real, consequential choice about how much parallelism that topic can ever support.
