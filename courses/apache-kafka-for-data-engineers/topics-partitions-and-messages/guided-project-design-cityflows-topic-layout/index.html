Welcome to This Module’s Guided Project#

Four lessons, four separate pieces: partitions spread leadership across brokers (Lesson 1), a message carries a key, value, timestamp, and headers (Lesson 2), topic creation carries consequential choices (Lesson 3), and keys deterministically route to partitions, which only guarantees ordering within one partition (Lesson 4). This lesson creates one topic — cityflow-trip-events, the exact name Module 3’s producer will write to — with every choice justified in writing against what this module actually measured, not picked by default.

By the end of this lesson, you will be able to:

  • Choose a partition count with a stated, defensible reason instead of an arbitrary number
  • Choose a replication factor and retention policy the same way
  • Create the topic with all of it set explicitly at once
  • Confirm zone-based key routing works on real CityFlow trip data

The Decision: Partition Count#

CityFlow’s NYC taxi data has 265 distinct pickup zones (Courses 1 and 2 already established this exact number). The tempting, wrong instinct is 265 partitions — one per zone. Lesson 1’s callout already named why that’s backwards: partitions are a parallelism knob, not a filing system, and Lesson 1’s own operational-cost section explained that partition count that high, for a demo cluster of 3 brokers, buys nothing but overhead (more file handles, slower leader elections, more replication traffic to keep mostly-idle partitions in sync) with no throughput need behind it.

The actual driver is parallelism this course will use: Module 4’s consumer group guided project runs multiple consumer workers sharing this exact topic, and a topic can never support more simultaneously active consumers, in one group, than it has partitions. Six partitions — the same count Lesson 1 measured directly, confirming leadership spreads two-per-broker across all three brokers evenly — gives room for up to six parallel consumers later without over-provisioning for a demo cluster this size. That’s the reason, written down: 6 partitions, chosen for consumer parallelism headroom at a scale this course’s cluster can actually support, not for one partition per zone.

The Decision: Replication Factor#

CityFlow’s cluster has exactly 3 brokers. Lesson 3 already proved, with an actual error, that replication factor can never exceed broker count — --replication-factor 5 failed outright on this cluster. The realistic range is 1, 2, or 3. Replication factor 1 means zero fault tolerance: any single broker failure loses that broker’s partitions’ only copy entirely, an unacceptable risk for CityFlow’s trip-completion events, which billing and driver-earnings both depend on downstream. Replication factor 3 — matching every topic this module has created so far — means each partition survives up to 2 simultaneous broker failures with its data intact, the maximum this cluster can offer. Replication factor 3, chosen for full fault tolerance on the cluster’s actual capacity, not a default left unexamined.

The Decision: Retention#

Kafka’s cluster default retention (7 days, unless changed) is a reasonable starting point for a lot of topics, but not necessarily the right one for trip events specifically — Module 4’s guided project reconciles consumed totals against Courses 1 and 2’s own numbers, which means a consumer built weeks after this topic starts filling up still needs to be able to replay a meaningful history. 30 days (retention.ms=2592000000) is this lesson’s choice: long enough that a consumer built well after the fact can still replay a full month of trip history, short enough not to accumulate data forever on a demo cluster with no long-term storage need. cleanup.policy=delete (not compact) because trip-completion events are genuinely event-shaped, per Lesson 2’s own distinction — every one is a distinct historical fact worth keeping until it ages out, not a “latest value per key” state update.

The Decision: Key#

Pickup zone (PULocationID, the same column Courses 1 and 2 already use) — not trip_id, which would spread every trip randomly across partitions with no useful ordering guarantee, and not a random UUID. Keying by pickup zone means every trip event for a given zone is guaranteed to arrive at its consumer in the exact order Kafka received it (Lesson 4’s ordering guarantee), which is exactly what a per-zone dashboard or a zone-level aggregation pipeline — Module 9’s stream-processing module builds one — needs to be correct.

Creating the Topic#

All four decisions, applied at once:

Leadership: broker 1 leads partitions 0 and 5, broker 2 leads 1 and 3, broker 3 leads 2 and 4 — two each, the exact balanced spread Lesson 1 predicted for six partitions on three brokers. Configs confirms both overrides took: cleanup.policy=delete and retention.ms=2592000000 (30 days in milliseconds), alongside the cluster’s own min.insync.replicas=2 default.

Proving the Key Choice on Real Trip Data#

Produce five trip events, using CityFlow’s actual NYC taxi zone lookup table for zone names — two of them sharing the same pickup zone on purpose:

Both JFK Airport (zone 132) trips — t-0001 and t-0005 — landed on partition 3, confirming the key-routing determinism Lesson 4 proved: any consumer assigned partition 3 sees every JFK pickup event in the exact order they were produced. The other three zones happened to collide on partition 2, the same “small sample, uneven-looking spread” behavior Lesson 4’s five-key example showed directly — with only four distinct zone keys sent against six partitions, this is expected, not a design flaw; CityFlow’s full volume spans all 265 zones, at which point the spread evens out the way Lesson 4’s 300-key experiment demonstrated.

Practice Exercises#

Exercise 1: Confirm the topic survives a broker restart#

Restart just kafka2 (docker restart kafka2 from .kafka-local/), wait about 15 seconds for it to rejoin, then run --describe --topic cityflow-trip-events again. Confirm PartitionCount, ReplicationFactor, and the Configs line are all unchanged — topic metadata is itself replicated via the KRaft controller quorum (Module 1 Lesson 4), so a single broker restarting doesn’t lose it.

Exercise 2: Write the justification for cityflow-zone-revenue#

Module 9’s aggregation topic will hold running per-zone revenue totals, updated continuously rather than one immutable event per trip. Using this lesson’s own reasoning template (partition count, replication, retention, key), write a one-paragraph justification for that topic’s likely settings, paying particular attention to whether cleanup.policy should be delete or compact given Lesson 2’s event/state distinction.

Hint

A running total per zone is the “latest value for this key” shape Lesson 2 called state, not an event — that’s the exact case cleanup.policy=compact exists for.

Summary#

cityflow-trip-events now exists on CityFlow’s cluster, with every setting chosen for a stated reason rather than accepted as a default: 6 partitions for consumer-parallelism headroom this module measured directly, replication factor 3 for full fault tolerance at this cluster’s actual size, 30-day retention for meaningful replay without unbounded growth, and pickup-zone keys for the exact ordering guarantee a per-zone consumer needs. Five trip events, produced with actual NYC taxi zone data, confirmed the key choice works: both JFK Airport events landed on the same partition, in order, exactly as Lesson 4 predicted.

Key Concepts#

  • Partition count should follow actual parallelism needs, not key cardinality — 6 partitions for cityflow-trip-events, not 265 (one per zone), justified against Module 4’s own consumer-group plans.
  • Replication factor should match the fault tolerance actually needed, capped by broker count — 3, the cluster’s maximum, for CityFlow’s billing-critical trip events.
  • Retention and cleanup policy follow from what a topic’s data represents — delete with a bounded window for event-shaped data, versus compact for state (Lesson 2).
  • Key choice determines the ordering guarantee consumers actually get — pickup zone, proven directly on trip data, matches the per-zone ordering this course’s later modules depend on.

Why This Matters#

Module 3’s producer starts writing real, paced CityFlow trip events to this exact topic. Module 4’s consumer group guided project depends on its 6 partitions for real parallel consumption. Every one of those modules inherits a decision made here, with a reason attached — which is the entire point of this module: not memorizing kafka-topics.sh flags, but treating each one as a real, consequential design choice.
