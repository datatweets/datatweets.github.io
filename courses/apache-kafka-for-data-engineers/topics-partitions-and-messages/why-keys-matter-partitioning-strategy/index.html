Lesson 4 - Why Keys Matter: Partitioning Strategy

Welcome to Why Keys Matter#

Lesson 2 named the key as one of a message’s four fields and said it’s used for routing. This lesson proves exactly what that means: the same key sent five times, watched land on the same partition every single time, and a resize that changes where a key routes — demonstrated directly, not described.

By the end of this lesson, you will be able to:

  • Prove that the same key always routes to the same partition, on a given partition count
  • Explain hash-partitioning without needing to reimplement a hash function
  • State precisely what “ordering is guaranteed within a partition” means, and doesn’t mean
  • Predict what happens to a key’s routing when a topic’s partition count changes

Same Key, Same Partition — Proven, Not Assumed#

Send the same key five separate times to a fresh three-partition topic and record which partition each one lands on:

Five sends, five identical results. This isn’t luck — it’s Kafka’s default partitioner, which runs the key’s bytes through a hash function and takes the result modulo the topic’s partition count. The exact hash function doesn’t need memorizing (Kafka’s Java client and kafka-python both use a variant of Murmur2); what matters is that it’s deterministic — the same input bytes always produce the same hash, so the same key always produces the same partition number, for as long as the partition count doesn’t change (the next section shows exactly what happens when it does).

Different Keys Spread — But Not Perfectly Evenly#

Send five different keys once each to the same topic:

Three of five keys landed on partition 1 — taxi-001, taxi-042, and zone-downtown, none of which share anything meaningful in common. That’s expected, not a bug: a hash function’s job is to spread inputs evenly on average, over many keys, not to guarantee any particular small sample looks balanced. With only three partitions and five keys, some collisions are simply likely — the next section proves the “on average” half directly, once there are more partitions worth spreading across.

What “Ordering Within a Partition” Actually Means#

Kafka’s ordering guarantee is precise, and this lesson’s own data proves both halves of it. Every message keyed taxi-042 landed on partition 1, in the order sent — offset 0, then 1, then 2, and so on, because partition 1 is exactly the append-only log from Module 1 Lesson 2: writes go to the end, in arrival order, always. That’s the guarantee: within one partition, message order is exactly the order Kafka received them in, and any consumer reading that partition sees them in that same order, every time.

What it doesn’t mean: two messages with different keys — say a taxi-042 event and a zone-airport event — have no ordering guarantee relative to each other at all, even if taxi-042’s event was produced first. They likely live on different partitions entirely (partition 1 versus partition 0, per this lesson’s own output), and different partitions are read independently, by potentially different consumers, with no cross-partition sequencing. This is exactly why key choice is a design decision, not an afterthought: if CityFlow’s downstream billing service needs to see every event for one taxi in the exact order they happened, keying by taxi_id is what makes that true — and keying by something else, like a random UUID, would silently break it.

A Resize Changes the Mapping#

Grow the same topic from three partitions to five with the same kafka-topics.sh --alter Lesson 3 already used, then send taxi-042 again. Running the CLI command via subprocess keeps this demo in one script, but it’s the identical command you’d type directly at a terminal:

Partition 1 before the resize; partition 4 after. Nothing about taxi-042 changed — the hash of those bytes is identical every time — but hash(key) % partition_count changes its output whenever partition_count changes, exactly as Lesson 3’s warning promised. Every taxi-042 message produced before the resize is still on partition 1, in order, exactly where it was. Every taxi-042 message produced after the resize goes to partition 4. A consumer that only reads partition 1, expecting to see “everything for taxi-042,” would silently miss every message produced after the resize — not an error, just quietly wrong, which is precisely why this is one of the more consequential reasons Lesson 1 and Lesson 3 both treated partition count as a decision to get right upfront rather than a number to bump casually later.

There’s no built-in warning for this either — Kafka doesn’t refuse a resize because it would change key routing, and no error appears anywhere in this lesson’s --alter output. The only defense is knowing, going in, that this is what a resize does, which is exactly why Lesson 5’s guided project treats cityflow-trip-events’ partition count as a number to research and justify once, rather than a starting guess this course expects to revisit casually later.

At Real Volume, the Spread Evens Out#

The five-key sample earlier landed three of five keys on the same partition — a small, expected-to-be-lumpy sample. Prove the “on average” half of hash-partitioning directly, on the topic as it stands now (5 partitions, after the resize above): send 300 distinct keys (taxi-0000 through taxi-0299) and count how many land on each partition.

300 keys across 5 partitions works out to 60 apiece if the split were perfect; the real spread here — 54 to 71 — is close, not exact, which is exactly what a good hash function produces on a sample this size. CityFlow’s real trip-event producer in Module 3 sends millions of keys, not 300, and at that volume the spread narrows even further as a share of the total, which is the practical payoff of hash-partitioning: no coordination, no lookup table, no central “which partition next” decision — just a deterministic function of the key, applied independently by any producer, that happens to balance out over real volume.

Practice Exercises#

Exercise 1: Confirm determinism on a different key#

Pick a key this lesson never used — "taxi-999", say — and send it 5 times to cityflow-key-routing-check (now at 5 partitions). Confirm all 5 sends land on the same partition as each other, then run it again in a fresh script and confirm it’s still the same partition as the first run — proving the hash is stable across process restarts, not just within one script’s lifetime.

Exercise 2: Key by something that changes meaning#

Produce messages keyed by pickup_zone (an integer like 132, JFK’s real zone ID from Courses 1-4) instead of taxi_id. Explain in a sentence what ordering guarantee this gives you that keying by taxi_id doesn’t, and what it loses.

Hint

Keying by zone guarantees every event for that zone arrives in order on one partition — useful for a per-zone dashboard — but events for the same taxi, if it crosses zones, can now land on different partitions entirely.

Summary#

The same key, sent five times, landed on the same partition every time — proof, not assertion, of Kafka’s deterministic default partitioner. Different keys spread across partitions unevenly on a small sample, which is expected hash behavior, not a bug. Ordering is guaranteed within one partition and only within one partition — messages with different keys have no ordering guarantee relative to each other at all. Growing a topic’s partition count changes the hash-to-partition mapping for every key going forward, without touching a single message already written, which is exactly the gotcha Lesson 3 warned about, now demonstrated directly: taxi-042 moved from partition 1 to partition 4 the moment the topic grew from three partitions to five.

Key Concepts#

  • Hash-partitioning by key is deterministic — the same key always produces the same partition, for a fixed partition count, proven by five identical results across five separate sends.
  • A small sample of keys won’t distribute perfectly evenly — expected hash behavior, not a defect; real volume evens out.
  • Ordering is guaranteed within a partition, not across partitions — the actual scope of Kafka’s ordering promise, no broader.
  • Changing partition count changes key routing for future messages — demonstrated directly: taxi-042 moved from partition 1 to partition 4 after a resize from 3 to 5 partitions, with every prior message staying exactly where it was.

Why This Matters#

Module 3’s real CityFlow producer keys every trip event by pickup zone specifically because of what this lesson proved: that choice determines which events are guaranteed to arrive in order relative to each other, and which aren’t. Module 4’s consumer groups build directly on the same fact — a consumer assigned one partition sees a strict, ordered slice of the topic, never the whole picture by itself. Every module from here assumes you understand partition-level ordering as something proven on this cluster, not read once and taken on faith.
