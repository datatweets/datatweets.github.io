Welcome to Producer Configuration#

Every producer this course has built so far used whatever kafka-python defaults to. This lesson changes that on purpose, three separate times, and measures what each change actually costs or saves — acks, batching, and compression — instead of describing them as abstract tradeoffs to take on faith.

By the end of this lesson, you will be able to:

  • Explain what acks=0, acks=1, and acks='all' each actually wait for, and measure the cost difference
  • Explain why batch size and linger.ms change throughput, with a measured example
  • Enable compression and measure its effect on a batch of trip data
  • State precisely what enable_idempotence=True prevents, without overselling it

acks: How Much Confirmation Is Enough?#

acks controls what a producer waits for before considering a message “sent.” Measure all three real settings sending 500 messages each:

Read this in order of what’s actually being waited for. acks=0 doesn’t wait at all — the producer fires the message and considers it done the instant it leaves the client, fastest at 4442 msg/s, and also the riskiest: if the write never reaches a broker (a network blip, a broker down at that exact instant), the producer has no way to know. acks=1 waits for the partition’s leader broker specifically to write the message to its own log, a little slower at 4182 msg/s, but still exposed to one failure mode — if the leader acknowledges and then fails before replicating to the other two brokers, that message is gone. acks='all' waits for every in-sync replica to have the message — min.insync.replicas=2 on this cluster (Module 2 Lesson 3 confirmed this setting), so two full broker writes have to complete before the producer moves on — slowest at 3405 msg/s, and the only one of the three that survives a single broker failing right after the write.

None of these numbers make one setting universally “correct.” CityFlow’s billing-relevant trip-completion events belong on acks='all' — a lost billing event is a serious business problem, worth roughly 23% less throughput on this measurement to avoid. A high-volume, loss-tolerant metrics stream might reasonably run acks=0 and accept the risk for the speed. Module 6 covers this tradeoff in full, including what acks='all' still doesn’t protect against on its own.

Batching: linger.ms and batch.size#

Kafka producers don’t send one network request per message by default — they group queued messages into batches, and linger.ms/batch.size control how eagerly. Measure the extremes directly: batches capped tiny versus batches allowed to grow large, with a short wait to let them fill:

A 5.3x difference between two batching configurations, on the exact same broker, same topic, same message count. A batch_size of 200 bytes holds barely more than one of these padded messages, so the producer ends up sending nearly one network request per message — paying a full round trip’s overhead 3000 times. linger_ms=20 tells the producer “wait up to 20 milliseconds to see if more messages show up before sending this batch,” and batch_size=1048576 (1 MB) gives it plenty of room to pack many messages into each request once it does send — far fewer round trips for the same 3000 messages. The cost of linger_ms=20 is exactly what it sounds like: up to 20 milliseconds of added latency per batch, waiting to see if more arrives. For CityFlow’s guided-project replay producer later in this module, that tradeoff is an easy one — a few milliseconds of batching delay is invisible next to the seconds-scale pacing already built into a realistic trip-event replay.

Compression: Smaller Bytes Over the Wire#

compression_type tells the producer to compress each batch before sending it. gzip needs no extra library — it’s part of Python’s standard library, and kafka-python uses it directly:

The send works exactly like an uncompressed one — same RecordMetadata, same partition/offset semantics; compression happens transparently inside the client and gets reversed transparently by any consumer reading the batch back. What it’s actually worth is easier to see by measuring bytes than by trusting the concept. Take 150 January 2024 trip events — the same ones Lesson 2 produced — and compress the raw JSON with Python’s own gzip module directly:

89.6% smaller, on trip data — not a synthetic worst case. JSON compresses unusually well precisely because it repeats itself constantly: every one of these 150 events repeats the literal strings "pickup_time", "pickup_zone", "fare_amount", and "total_amount", which gzip’s compression catches immediately. The tradeoff is CPU, not network — compressing and decompressing costs processor time on both ends, usually far cheaper than the network transfer it avoids, especially between separate machines on an actual network rather than this course’s cluster running on localhost.

A First Look at Idempotent Producers#

One more setting worth naming here, deliberately not fully explained yet: enable_idempotence=True.

It runs exactly like any other producer — the difference is invisible from the outside, which is the point. What it actually prevents, precisely: if a producer sends a message, the broker writes it, but the acknowledgment gets lost on the way back (a network blip after a successful write), a non-idempotent producer’s retry logic would send that same message again, creating an actual duplicate the broker has no way to recognize as one. enable_idempotence=True has the broker track a sequence number per producer so a resent message with a sequence number it’s already seen gets silently deduplicated instead of written twice. What it does not prevent: a producer crashing and a replacement process resending data from scratch, or two logically different messages that happen to represent the same real-world event (Lesson 5’s guided project touches on why that distinction matters for a replay producer specifically). Module 6 covers idempotent and transactional producers in full, including exactly where the guarantee stops.

Practice Exercises#

Exercise 1: Measure acks on a bigger batch#

Repeat the acks=0 vs. acks=1 vs. acks='all' comparison with 2000 messages instead of 500. Does the relative gap between the three grow, shrink, or stay about the same proportionally? Explain what that tells you about whether the difference is a fixed per-message cost or something that compounds.

Exercise 2: Combine batching and compression#

Construct one producer with both a large batch_size (encouraging bigger batches) and compression_type="gzip" set together, and send 150 padded messages ({"seq": i, "padding": "x" * 200}). Compare its total elapsed time against a producer using neither setting. Which of the two — batching or compression — do you expect to matter more for this specific payload, and why?

Hint

Compression works on a whole batch at once — a bigger batch gives gzip more repeated structure to find, so the two settings aren’t fully independent of each other.

Summary#

Three separately measured producer settings: acks traded 23% throughput (4442 down to 3405 msg/s) for acks='all'’s full replication guarantee versus acks=0’s no guarantee at all. Batching traded a few milliseconds of added latency for a 5.3x throughput gain (3369 to 17911 msg/s) by packing far more messages into each network request. Compression traded CPU time for an 89.6% reduction in bytes sent over the wire, measured on trip data rather than assumed. enable_idempotence=True was introduced narrowly and precisely: it prevents duplicate writes from a producer’s own retry after a lost acknowledgment, and nothing broader than that — Module 6 covers the rest.

Key Concepts#

  • acks trades throughput for durability guarantee strength — measured here at 4442/4182/3405 msg/s for acks=0/1/'all', each waiting for progressively more confirmation.
  • Batching trades latency for throughput — a measured 5.3x gap between tiny, unbatched sends and large, briefly-delayed ones.
  • Compression trades CPU for network bytes — 89.6% smaller on a batch of trip events, because JSON’s repeated field names compress well.
  • enable_idempotence=True prevents one specific failure mode — duplicate writes from a producer’s own retry, not every kind of duplicate a distributed system can produce.

Why This Matters#

Lesson 5’s guided project has to make actual versions of every one of these decisions for CityFlow’s own trip-event replay — how much durability the billing-relevant events need, whether the pacing already built into a realistic replay makes batching’s latency cost irrelevant, and whether compressing a stream of already-small JSON events is worth the CPU. Having measured numbers behind each tradeoff, taken on this exact cluster, is what makes those choices defensible instead of guessed.
