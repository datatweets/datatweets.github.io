Welcome to Error Handling#

A producer that never fails doesn’t need error handling; a real one does, and this lesson triggers two genuinely different failures on purpose to show why one handling strategy doesn’t cover both. Lesson 1’s Exercise 2 already surfaced a hint of this — an unreachable broker fails before a future even exists. This lesson goes further: two failures that both happen on a perfectly reachable cluster, at two different points in a send’s real lifecycle.

By the end of this lesson, you will be able to:

  • Trigger and correctly handle a failure that raises directly from .send()
  • Trigger and correctly handle a failure that only surfaces after .send() returns successfully
  • Explain why these two failure classes need two different handling strategies
  • Recognize a bare except: pass as data loss, not error handling

Failure Class 1: Fails Before a Future Even Exists#

Module 2’s cluster runs with KAFKA_AUTO_CREATE_TOPICS_ENABLE=false — producing to a topic that was never explicitly created doesn’t silently create it, it fails. Trigger this on purpose, with max_block_ms set low so the failure arrives in seconds instead of the 60-second default:

Look carefully at where the try block actually catches this: around producer.send(...).get(timeout=5) — the whole expression, not just .get(). That’s not a stylistic choice. Before a producer can send anything, it needs the topic’s metadata (which partitions exist, which broker leads each one), and .send() blocks internally waiting for that metadata before it ever returns a future — Lesson 1’s Exercise 2 found the same thing happens even earlier, at KafkaProducer(...) construction, when the bootstrap servers themselves are unreachable. A nonexistent topic is a step further along: the client is reachable, but the specific metadata it needs never arrives, so .send() itself raises KafkaTimeoutError directly. There is no future to attach an add_errback to here — the failure happens before one exists.

Failure Class 2: Fails After a Future Already Exists#

A different failure: send a message larger than Kafka’s broker-side message.max.bytes limit (roughly 1 MB by default). This one behaves completely differently:

Notice what didn’t happen: producer.send(...) didn’t raise anything, and producer.flush() didn’t raise anything either — the try/except around flush() printed nothing at all. The message was accepted into the client’s send queue without complaint (max_request_size=2_000_000 told the client it was allowed to try), and only the broker’s own limit rejected it, after the fact, once the client actually attempted the send. That rejection surfaced exactly one place: the errback. on_success never fired at all — successes_seen stayed empty — confirming the message genuinely failed rather than partially succeeding.

The same failure surfaces through .get() too, for code using the synchronous style instead of callbacks:

Same exception, same information, delivered through whichever mechanism the calling code actually uses to wait for a result — .get() raises it directly; the callback-based version delivers it to add_errback. What both have in common, and what distinguishes this from Failure Class 1: a future genuinely existed here. The client accepted the message, queued it, attempted to send it, and only then learned the broker wouldn’t take it.

Two Failures, Two Handling Strategies — On Purpose#

These aren’t the same kind of failure wearing different clothes, and code that handles only one of them silently drops the other. A try/except wrapped only around .get() — not the .send() call that produces it — would still catch Failure Class 2 (the future exists, .get() still raises from it) but would let Failure Class 1 propagate uncaught out of the .send() call itself, since the exception happens before .get() is even reached. An add_errback registered on a future, by contrast, can only ever catch Failure Class 2 — Failure Class 1 never produces a future for add_errback to attach to in the first place. A producer that only checks add_errback for problems, assuming it’s a complete safety net, would let a nonexistent-topic misconfiguration crash the whole process instead of failing gracefully.

The one strategy that’s never correct for either: a bare except: pass around the whole thing. It would swallow Class 1’s exception, swallow Class 2’s, and leave no trace anywhere that CityFlow lost a trip event — no log line, no metric, no retry, nothing. Module 6 covers what a production system does instead (dead-letter topics, structured retry, alerting); this lesson’s job is narrower and more foundational: know which failure you’re actually looking at before deciding what to do about it.

Not Every Error Even Reaches Your Code#

One more real detail worth knowing before writing error-handling code: kafka-python’s producer doesn’t hand every failure straight to except/add_errback on the first attempt. Its retries setting defaults to inf — unlimited — bounded in practice by delivery_timeout_ms, which defaults to 120000 (two minutes). For a genuinely transient failure — a leader election still in progress, a momentary network hiccup — the client retries automatically, on its own, and the calling code never sees anything unless every retry fails within that two-minute window.

MessageSizeTooLargeError from this lesson’s own example is different: retrying the exact same oversized message would fail identically every time, no matter how many attempts or how much time passes, so it’s a genuinely non-retriable condition, and this lesson’s errback fired promptly rather than after anything close to a two-minute wait — confirmation that kafka-python recognizes the distinction rather than blindly retrying everything. This matters for how much error-handling code to write on top of what the client already does: wrapping every .send() in custom retry logic for failures the client already retries internally is redundant work solving a problem that doesn’t exist, while assuming every error is automatically retried (and therefore skippable to handle) is exactly how a message-too-large error, or a nonexistent-topic error, ends up silently unhandled.

Practice Exercises#

Exercise 1: Confirm .send() alone (without .get()) still raises for Class 1#

Remove .get(timeout=5) from this lesson’s first example, leaving just producer.send("cityflow-topic-that-does-not-exist", {...}) inside the try block. Does KafkaTimeoutError still get raised and caught? What does this confirm about exactly which call — .send() or .get() — is doing the actual blocking-and-failing for this specific failure class?

Exercise 2: Trigger Class 2 with .get() and a shorter timeout#

Repeat the oversized-message example with .get(timeout=2) (a shorter timeout than this lesson used) instead of .get(timeout=10). Does the exception change — does a KafkaTimeoutError show up instead of MessageSizeTooLargeError, or does the broker’s rejection still win the race? Explain what that tells you about how quickly Kafka actually rejects an oversized message once it reaches a broker.

Hint

The broker’s MessageSizeTooLargeError response typically arrives well under 2 seconds on a local cluster — the timeout would need to be set unreasonably short to actually race it.

Summary#

Two real producer failures, triggered on purpose, behave completely differently. Producing to a nonexistent topic makes .send() itself raise KafkaTimeoutError before any future exists — there’s nothing for add_errback to catch, so this failure needs a try/except wrapped around the .send() call itself. Producing an oversized message succeeds at .send() and only fails once the broker rejects it — surfacing through .get() raising, or through add_errback firing, with flush() itself never raising and the success callback never firing either. Confusing which class of failure a piece of code needs to handle — or worse, catching neither with a bare except: pass — is exactly how a real pipeline loses data with no trace of it happening.

Key Concepts#

  • Some failures raise directly from .send(), before any future is returned — a nonexistent topic, or an unreachable broker (Lesson 1), both confirmed here.
  • Other failures surface only after .send() succeeds — an oversized message is accepted into the queue, then rejected by the broker, surfacing via .get() or add_errback.
  • add_errback cannot catch a failure that never produces a future — it only ever sees the second class.
  • A bare except: pass is data loss with no trace, not error handling — the discipline this lesson builds toward is knowing which failure is which before deciding what to do.

Why This Matters#

Lesson 5’s guided project produces real trip events continuously, and a real pipeline eventually hits both of these failure classes for real — a topic that was never created because of a typo, a message that grew unexpectedly large. Knowing exactly where each failure surfaces, confirmed here rather than assumed, is what makes the guided project’s own error handling correct instead of a guess that happens to work until it doesn’t.
