Welcome to Producers#

Every message this course has sent so far — Module 2’s demo topics, the trip events that proved key routing — used a KafkaProducer built quickly, almost in passing, to get to the point being demonstrated. This lesson slows down and looks at the producer itself: what .send() actually returns, what .get() costs compared to not calling it, and how a callback delivers the same information without paying that cost.

By the end of this lesson, you will be able to:

  • Construct a KafkaProducer and explain what .send() returns
  • Measure the real cost of blocking on .get() after every send
  • Use add_callback/add_errback to get the same delivery confirmation without blocking
  • Choose sync vs. async deliberately, based on what a specific piece of code actually needs

What .send() Actually Returns#

producer.send(topic, value) doesn’t send anything and wait — it queues the message on the client and returns immediately with a FutureRecordMetadata, a placeholder for a result that hasn’t arrived yet. Calling .get(timeout=...) on that future is what actually blocks: it waits until the broker acknowledges the write (or the timeout expires) and then returns real RecordMetadata — the partition and offset the message landed at, confirmed in Module 2’s own lessons every time a result.partition/result.offset got printed. Nothing about .send() itself is slow; the cost lives entirely in what you do with the future it returns.

Measuring the Real Cost of .get()#

Send 200 messages two ways: calling .get() after every single one, versus firing all 200 and calling .flush() once at the end.

Now the same 200 messages, fired without waiting on each one:

Same broker, same topic, same message count — 555 messages a second calling .get() after each send, versus 1788 messages a second sending 200 and flushing once, a 3.2x difference measured on this run. The reason is exactly what Lesson 1 of Module 1 taught about point-to-point coupling, applied here to a network call instead of a function call: .get() forces the loop to wait for a full broker round trip before it’s allowed to send the next message, one at a time. Without .get(), the client is free to batch multiple queued messages into fewer network requests — Lesson 3 measures exactly how much that batching alone is worth, separately from this lesson’s sync-vs-async gap.

Why List All Three Brokers?#

Every KafkaProducer in this course so far has passed bootstrap_servers=["localhost:9092", "localhost:9093", "localhost:9094"] — all three brokers. It’s tempting to assume the producer opens and maintains a connection to all three permanently, but that’s not what bootstrap_servers is for. Prove it directly: construct a producer with only one broker listed, and send messages that should land across multiple partitions:

Messages still landed on partitions led by different brokers, even though only kafka1 was ever named. That’s because bootstrap_servers is only used for the producer’s very first connection — enough to ask “what does this cluster’s metadata look like?” and get back the full picture: every broker, every topic’s partition-to-leader mapping. From there, the producer talks directly to whichever broker actually leads the partition a message is headed to, discovered from that metadata, not from the list originally passed in. Listing all three in this course’s examples isn’t about permanent connections — it’s resilience for that first handshake: if kafka1 happened to be down when a producer started, kafka2 or kafka3 could still answer the initial metadata request and get it running.

Callbacks: The Same Guarantee, Without Blocking#

Calling .get() isn’t the only way to know a send succeeded — a future also accepts callbacks, run automatically once the result is known, with no blocking required in the calling code at all:

add_callback registers a function to run with the real RecordMetadata once the send succeeds; add_errback registers one to run with the exception if it fails instead. Neither one blocks the line that registered them — future.add_callback(on_success) returns immediately, and on_success only actually runs later, on the client’s own internal thread, whenever the broker’s acknowledgment arrives. producer.flush() here is only present to make sure every queued message is actually sent before the script exits and prints results — in a long-running producer (Module 3’s own guided project, and every real production pipeline), callbacks fire continuously in the background without anything needing to call flush() after each one.

Choosing Sync vs. Async on Purpose#

Neither approach is universally correct, and this lesson’s own numbers show why. .get() is the right choice when the calling code genuinely can’t proceed without knowing the result — CityFlow’s billing service, for instance, might need to confirm a charge event was durably written before telling a driver their payout is final. Callbacks (or no confirmation at all, for truly disposable data) are the right choice when throughput matters more than per-message confirmation — exactly the guided project’s own situation later in this module, replaying tens of thousands of trip events where waiting on each one individually would make the replay run at a fraction of real pace for no benefit. The mistake to avoid isn’t picking one over the other; it’s picking neither deliberately and defaulting to whatever the first code example happened to use.

Practice Exercises#

Exercise 1: Measure the gap at a larger scale#

Repeat this lesson’s sync-vs-async comparison with 1000 messages instead of 200. Report both throughput numbers and the ratio between them — is the gap bigger, smaller, or about the same proportionally? Explain in one sentence why a fixed per-message network round trip should scale roughly linearly either way.

Exercise 2: Combine a callback with error handling#

Send a message to cityflow-producer-check with both add_callback and add_errback registered, so the flow works normally. Then, in a separate script, deliberately construct a KafkaProducer pointed at an unreachable address (bootstrap_servers=["localhost:19999"], with api_version_auto_timeout_ms=3000 so it fails in a few seconds instead of the default minute) and observe exactly where the failure happens. Does it happen inside .send(), or somewhere else entirely? Lesson 4 explains why the answer matters.

Hint

An unreachable broker fails even earlier than .send() — right at KafkaProducer(...) construction, with a NoBrokersAvailable exception, before there’s any producer object to call .send() on at all. There’s no future here for add_errback to ever attach to.

Summary#

producer.send() returns a future immediately, without waiting for the broker; .get() blocks on that future until RecordMetadata comes back, and this lesson measured exactly what that blocking costs — 555 messages a second calling .get() after every send, versus 1788 messages a second sending all 200 and flushing once, a measured 3.2x gap. add_callback/add_errback deliver the identical partition/offset (or exception) information without blocking the sending code at all, which is what makes a high-throughput producer like this module’s guided project practical. Neither sync nor async is the “right” choice in general — the decision depends on whether the calling code needs to know the result before moving on.

Key Concepts#

  • .send() returns a future immediately — nothing about queuing a message is slow by itself.
  • .get() blocks until a real broker acknowledgment arrives — measured here at roughly a third the throughput of not blocking, 555 vs. 1788 msg/s.
  • add_callback/add_errback deliver the same result without blocking — the mechanism a high-throughput producer needs.
  • The choice is deliberate, not automatic — sync where a result is genuinely needed before proceeding, async where throughput matters more than per-message confirmation.

Why This Matters#

Every producer this module builds from here uses async sending as the default, precisely because of the number measured in this lesson — a replay producer that called .get() after every one of thousands of trip events would run at a fraction of the pace this module’s guided project needs. Knowing why, with a measurement behind it, is what makes that choice a decision instead of a habit. The bootstrap_servers finding matters too, in a quieter way: it’s the first hint that a Kafka client’s relationship with a cluster is discovered dynamically from metadata, not hardcoded from a config list — the exact same principle Module 4’s consumer groups and Module 5’s failure scenarios both build on, where a client keeps working correctly even as which broker leads which partition changes underneath it.
