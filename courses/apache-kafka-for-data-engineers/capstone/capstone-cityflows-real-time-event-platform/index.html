Welcome to the Capstone#

Look at what eleven modules built. Module 1 stood up a 3-broker cluster and moved a first message across it. Modules 2 through 6 wrote producers and consumers that survive rebalances, broker failures, and duplicate deliveries. Module 7 added a schema registry and proved evolution rules against a live compatibility check. Module 8 moved data to and from MySQL and Elasticsearch without a line of hand-written producer or consumer code. Module 9 processed a live stream two ways – Faust and Spark – and proved they agree. Module 10 pointed Airflow at the cluster and watched a DAG fail on purpose when lag crossed a threshold. Module 11 built a second cluster and mirrored into it. Every module left one working piece behind, and this capstone wires them into a single pipeline.

It also closes something bigger than eleven modules. Two earlier courses in the Data Engineering path answered the same question about CityFlow’s trip data with different tools: Scaling Python for Data Engineering with pandas, PySpark for Data Engineering with a distributed engine. Both landed on 240,917 zone-hour buckets, 9,554,757 trips, $256,692,373.14 in revenue. This capstone answers it a third way, using this course’s own live cluster – and if the answer is even one trip or one cent different, the fault is in this lesson, not the anchor.

By the end of this lesson, you will be able to:

  • Validate live trip events against a schema this lesson registers itself, matching the actual fields this course’s producers have used since Module 4
  • Watch a Faust table’s live state match an independent recomputation of the same events, exactly
  • Diagnose and fix a genuine Kafka Connect sink limitation that Module 8’s source connector never had to face
  • Wire Module 10’s own lag-checking Hook and a three-task Airflow DAG around a pipeline this lesson just built
  • Reconcile a 9.5-million-message topic to a figure two other courses already established, using nothing but the filtering discipline Module 4 taught in this course’s first week

You’ll need this course’s own running cluster (kafka1-kafka3, Schema Registry, Kafka Connect, MySQL, Elasticsearch), the .airflow-local stack from Module 10, and confluent-kafka, kafka-python, faust-streaming, and pyspark from the shared environment – nothing new to install. Let’s close the loop.

The Acceptance Criteria#

Before writing a line of this pipeline, here is what “done” means, checked against output rather than trusted on faith:

  1. A schema this lesson registers itself, matching production data. Not a toy schema – fields that match exactly what cityflow-trip-events has carried since Module 4, validated and decoded byte-for-byte.
  2. A live Faust aggregation, cross-checked. The table’s own reported state for a specific zone must match an independent recomputation of the identical events exactly, not approximately.
  3. Two sinks, both exact. A MySQL table and an Elasticsearch index, both populated through Kafka Connect, both holding the same 45 zones with the same figures.
  4. A three-task Airflow DAG, green. Lag, the MySQL count, and the Elasticsearch count, checked by tasks that fail if any of them is wrong.
  5. The full corpus, reconciled exactly. 9,554,757 trips, 240,917 buckets, $256,692,373.14 – the identical figures Courses 1 and 2 already published, computed a third way.

Step 1 – Confirm the Stream Is Still There#

cityflow-trip-events has carried CityFlow’s full first-quarter taxi data since Module 4’s guided project, live through eleven modules of tests, demos, and broker-kill drills since. Before building anything new on top of it, confirm what’s actually there:

Every message ever produced to this topic is still countable directly with a plain admin call – no need to consume the whole thing just to know how much is there:

Module 4’s guided project loaded exactly 9,554,778 trip rows. This topic now holds 267 more than that. Nothing is wrong – across eleven modules, several lessons produced a handful of check or demo messages directly onto this exact topic name rather than a dedicated one, and none of them were ever cleaned up. That’s an honest fact about a cluster that’s stayed up for this whole course, not a data-loss problem, and Step 7’s reconciliation is where it gets resolved – the same date-window filter Module 4 used to quarantine 21 corrupted rows turns out to catch these 267 stray messages too, for the identical reason: they don’t carry a January-March 2024 pickup timestamp.

Step 4 – Sink to a Real Database and Search Index#

Each zone’s final totals get published as a small JSON message, keyed by zone, to cityflow-capstone-zone-revenue. The first attempt at a JDBC sink connector, matching Module 8’s own source-connector pattern, fails immediately:

A limitation Module 8’s JdbcSourceConnector never exposed: a source connector only needs to serialize rows outward, but a sink connector needs to know a message’s exact field names and types to build a working SQL statement – information a plain, schemaless JSON blob (schemas.enable=false, this cluster’s default since Module 8) simply doesn’t carry. The fix is the same one-setting flip Module 8 Lesson 1 demonstrated for a different reason: wrap each result in Connect’s own JSON schema envelope, and tell this one connector to expect it:

Both sinks, both exact – 45 zones through Kafka Connect, into two systems that have never spoken to each other, both agreeing with the pipeline’s own live Faust table.

Step 7 – Closing the Loop#

Every earlier step worked against a 20,000-event slice. This step reads the entire topic – 9,555,045 messages, the number Step 1 found, stray test messages and all – through Spark Structured Streaming, filtered by the identical January-March 2024 window Module 4 established in this course’s first week:

288 quarantined – the 21 corrupted-timestamp rows Module 4 already knew about, plus the 267 stray messages Step 1 found, all excluded by the identical window filter for the identical reason: none of them carry a genuine January-March 2024 pickup time. Everything else lands exactly on 240,917 buckets, 9,554,757 trips, $256,692,373.14 – the figure two other courses, using two other tools, already established.

Summary#

CityFlow’s real-time event platform runs end to end: 20,000 trip events validated against a schema this lesson registered to match production data exactly, processed live by a Faust table whose state matched an independent recomputation to the cent, sunk through two Kafka Connect connectors into a MySQL table and an Elasticsearch index – both exact, after a genuine JDBC sink limitation got diagnosed and fixed rather than worked around. A three-task Airflow DAG checked lag and both sinks in five seconds. Then, at full scale, the entire 9,555,045-message topic reconciled – 288 messages quarantined for the same reason 21 always were – to the exact figure Courses 1 and 2 of the Data Engineering path established: 240,917 buckets, 9,554,757 trips, $256,692,373.14.

Key Concepts#

  • A sink connector needs schema information a source connector never did. JdbcSinkConnector failed on schemaless JSON specifically because it has to map fields to SQL columns; JdbcSourceConnector in Module 8 never faced that requirement.
  • A live aggregation and an independent recomputation should agree exactly, not approximately. Faust’s own table and a plain Python script landed on the identical $58,469.17 for zone 137.
  • Orchestration and reconciliation can run on genuinely different schedules. The Airflow DAG health-checks the live pipeline in seconds; the full-corpus reconciliation runs separately, by design – the Lambda split Module 11 Lesson 3 named, put to use here.
  • A cluster that’s stayed up for eleven modules still reconciles exactly, once filtered the same way it always was – 267 stray messages excluded for the same reason the original 21 corrupted rows were.

Why This Matters#

A number one pipeline reports is a claim. A number three different courses – pandas, a distributed Spark engine, and now a live Kafka platform with a schema registry, a stream processor, two Connect sinks, and an orchestrator – all land on exactly is closer to a fact CityFlow’s own data can be trusted to have produced.

What You’ve Built#

Step back from this one lesson and look at eleven modules plus this one. Module 1 stood up a cluster and moved a single message. By Module 6, that message survived broker failures and duplicate sends. Module 7 gave it a contract. Module 8 moved it to and from external systems without hand-written code. Module 9 processed it live, two ways, proven to agree. Module 10 watched it with an orchestrator. Module 11 mirrored it to a second cluster and reasoned honestly about what running Kafka at scale actually costs. This capstone took every one of those pieces – schema validation, live processing, dual sinks, lag monitoring, orchestration – and ran them together, closing the loop against two other courses’ own independently-verified answer.

Every number in this lesson – the 20,000 validated events, the $58,469.17 matched twice, the 45 rows and 45 documents, the five-second DAG run, the 9,555,045 messages and the 240,917 buckets – was measured on this course’s own infrastructure, the same discipline every module insisted on from Lesson 1 of Module 1. Twelve modules, one platform, and one number that never moved.

Practice Exercises#

Exercise 1: Validate the full corpus, not a slice#

Adapt Step 2’s validation script to process the entire 9,555,045-message topic instead of a 20,000-event slice. Estimate how long it would take, using this course’s own measured Avro-validation throughput as a basis, before running it – then run it and compare.

Exercise 2: Add a fourth reconciliation source#

CityFlow’s platform now has three independent answers to the same question – pandas, distributed Spark, and this course’s own live Kafka platform. Using Module 9 Lesson 3’s Faust table pattern, sketch (in prose, not code) what a fourth, Faust-based full-corpus reconciliation would need to handle that this lesson’s 20,000-event slice never had to: specifically, what happens to a stateful table’s memory footprint at 9.5 million keys instead of 45.

Hint

Zone counts stay small no matter the data volume – but a table keyed by something with much higher cardinality (trip_id, for instance) would face a completely different scaling question. Which key space does revenue-by-zone actually use, and why does that matter here?
