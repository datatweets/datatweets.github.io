Lesson 2 - Avro, and Why It's Kafka's Default Choice

Welcome to Avro#

Lesson 1 proved the cost of having no schema at all. This lesson introduces the format Kafka’s own ecosystem defaults to for having one: Apache Avro — not because it’s the only option, but because of what it measurably costs on the wire compared to the JSON this course has used since Module 1.

By the end of this lesson, you will be able to:

  • Write an Avro schema definition for a real event
  • Measure Avro’s binary encoding directly against the identical JSON record
  • Explain why Avro’s per-message savings compound at scale, not just per record
  • State briefly how JSON Schema and Protobuf compare, and why this course uses Avro

An Avro Schema Is Just Written-Down JSON#

An Avro schema is itself JSON — a field list with a name and type for each one, nothing exotic:

This is exactly the kind of written, checkable contract Lesson 1’s crash needed and never had — every field, its type, all in one place instead of implied by whatever a producer happens to send. fastavro, a pure-Python Avro library, can serialize a record against this schema directly, no registry required yet:

The same five values, the identical record, encoded two ways: 108 bytes as JSON, 24 as Avro — measured directly, not an estimate from documentation. JSON pays for every field name as literal text on every single message: "pickup_zone" costs 13 bytes of key name whether the value it’s attached to is 1 or 999999. Avro’s binary encoding never writes the field name at all — the schema already says field two is pickup_zone, an integer, so the wire format just writes the integer’s bytes and nothing else.

Reading It Back Needs the Schema — On Purpose#

Avro’s compactness has a direct consequence: unlike JSON, which is self-describing text a human or a program can read without any external context, Avro’s binary payload is meaningless without the exact schema it was written against.

With the schema, decoding recovers the exact original record. Without it, the bytes aren’t even valid UTF-8 — json.loads() doesn’t fail with “wrong format,” it fails trying to decode the raw bytes as text at all, because Avro’s binary encoding was never meant to be read without its schema alongside it. That’s the tradeoff behind Avro’s compactness: the size savings come specifically from not writing anything self-describing into the payload, which means both the producer and every consumer need a reliable way to get the exact right schema for every message. A file on someone’s laptop doesn’t scale to “every consumer, always has the right schema” — which is precisely the gap Lesson 3’s Schema Registry closes: a shared, queryable source of truth every client can reach automatically instead of a copy-pasted .avsc file trusted to stay in sync by hand.

The Gap Holds — and Compounds — At Scale#

One record’s savings are a curiosity; a topic carrying millions of records is where they matter. Encode 1,000 realistic TripEvent records both ways:

Even after accounting for the small per-message overhead Schema Registry’s real wire format adds — a 5-byte header identifying which registered schema ID decoded this message, covered directly in Lesson 3 — Avro still lands at roughly a quarter the size of the identical JSON stream. That gap is disk space on every broker replica (three copies, per Module 5), network bytes on every produce and fetch request, and page-cache pressure under real load — all scaling with message count, not staying fixed the way a one-record comparison might suggest.

Briefly: JSON Schema and Protobuf#

Avro isn’t the only structured option, and Kafka doesn’t require it — Schema Registry supports all three of the following, and picking one is a real, if brief, decision:

  • JSON Schema validates that a JSON document matches a shape, but the wire format stays JSON — field names still travel with every message, so it doesn’t recover Avro’s size advantage. Its appeal is that the payload itself stays human-readable.
  • Protobuf (.proto files, compiled to generated code) is binary and compact like Avro, with strong typed code generation as its main draw — widely used in gRPC services. It requires a compile step most Avro workflows don’t, since Avro’s schema can be read and used directly as JSON without code generation.
  • Avro, this course’s choice, pairs schema-as-JSON (no separate compiler needed) with a compact binary wire format and a data model built specifically around schema evolution — which Lesson 4 needs directly, and which is the actual reason Kafka’s own tooling (Confluent’s Schema Registry chief among it) treats Avro as the default rather than an arbitrary pick.

Practice Exercises#

Exercise 1: Measure a wider record#

Add three more fields to the schema (driver_id: string, trip_duration_seconds: int, distance_miles: double) and re-measure the JSON-vs-Avro gap on a single record. Does the ratio grow, shrink, or stay roughly the same as more fields are added?

Exercise 2: Find the field-name-repetition cost directly#

For the original 5-field schema, compute the total byte length of just the JSON field names ("trip_id", "pickup_zone", and so on, including their quotes and colons) in one record. How much of JSON’s 108 bytes is that alone, and how does it compare to Avro’s entire 24-byte encoding?

Hint

Sum len(f’"{name}":’) for every field name in the schema – that’s the exact tax JSON pays per message for something Avro’s schema already knows and never repeats.

Summary#

The identical TripEvent record measured 108 bytes as JSON and 24 as Avro — a direct measurement, not a claim from documentation — because Avro’s schema defines field order and type once, so the wire format never repeats a field name the way JSON does on every single message. At 1,000 records the advantage holds even after adding Confluent’s real per-message schema ID header: 109,000 bytes of JSON against 29,000 of Avro, still a 3.76x gap. JSON Schema keeps JSON’s verbosity while adding validation; Protobuf matches Avro’s compactness but needs a compile step Avro doesn’t; Avro’s combination of a JSON-native schema and genuine binary compactness is why it’s Kafka’s own tooling’s default, not an arbitrary choice.

Key Concepts#

  • An Avro schema is itself just JSON — a field list with names and types, directly checkable, no separate schema language.
  • Avro never writes a field name on the wire — the schema already says what field two is; the payload just writes the value.
  • Avro’s payload is unreadable without its exact schema — the direct tradeoff for its compactness, and the reason a shared registry has to exist.
  • The size gap compounds with scale — measured at 4.5x for one record, still 3.76x at 1,000 including real wire-format overhead.
  • JSON Schema, Protobuf, and Avro trade off differently — validation-only-on-JSON, compile-step-required-binary, and schema-native-binary respectively.

Why This Matters#

A schema on its own is still just a local file until something enforces it across every producer and consumer that touches a topic — which is exactly what Lesson 3’s Schema Registry does, running as a real, separate service this course’s own cluster can reach.
