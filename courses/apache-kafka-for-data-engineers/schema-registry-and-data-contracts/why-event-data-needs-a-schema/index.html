Lesson 1 - Why Event Data Needs a Schema

Welcome to Schema Registry and Data Contracts#

Six modules, and every single one has trusted that a producer and a consumer agree on what a message’s keys mean, purely by convention — nothing enforced it. This lesson breaks that convention on purpose, on CityFlow’s own cluster, and watches exactly what happens.

By the end of this lesson, you will be able to:

  • Reproduce a genuine breaking change in event data with no schema involved
  • Explain precisely what “data contract” means, and why implicit contracts fail silently
  • Distinguish a breaking change from a safe one, before either has a name
  • State what a real fix needs to guarantee, before Lesson 3 introduces the tool that does

A Routine Refactor, Shipped With No Coordination#

CityFlow’s fare pipeline has one producer and one consumer, written by different people, coordinating only through a shared understanding of what a trip event looks like — never written down, never enforced. A teammate renames fare_amount to total_fare in what looks like a harmless cleanup, ships it, and the consumer — unmodified, unaware, still expecting the old name — keeps running against live production data:

Three events processed cleanly — 12.50 + 13.50 + 14.50 = 40.5, correct so far. The fourth event, the first one written under the renamed field, crashes the consumer outright: record["fare_amount"] looks for a key that simply doesn’t exist anymore. Nothing about this required malice or even carelessness — a rename that looked completely safe from inside the producer’s own codebase took down a consumer that never saw the change coming, mid-stream, with three more events sitting unread behind the crash.

What “Data Contract” Actually Means#

A data contract is the shape a producer and consumer agree an event will have — which fields exist, what type each one is, which are required. Nothing about Kafka itself enforces this: a topic is bytes in, bytes out, and json.dumps() will happily serialize any dictionary a producer hands it, renamed fields and all. The contract, until this module, has lived entirely in the shared understanding between whoever wrote the producer and whoever wrote the consumer — which is exactly why it broke the moment those two people stopped being the same person coordinating in real time.

This isn’t a JSON-specific problem, and it isn’t solved by switching formats alone. The actual requirement is a schema: a written-down, checkable definition of an event’s shape, plus something that can compare a proposed change against it and say yes or no before a bad shape ever reaches a topic. That’s what Lesson 3’s Schema Registry provides — this lesson’s job was only to prove, directly, why that enforcement needs to exist at all.

A Second, Quieter Failure: Wrong Type, No Crash At All#

The KeyError above is the loud failure — impossible to miss, a stack trace pointing straight at the problem. A type change on a field that’s still present is often worse, because nothing crashes at all. Change pickup_zone from an integer zone code to a friendlier descriptive string, and watch a zone-revenue aggregation quietly stop counting anything from it:

No exception anywhere. No stack trace, no crash, no log line demanding attention. Half the trips simply stop counting toward zone 132’s revenue the moment pickup_zone becomes a string a lookup dictionary keyed by integers was never going to match — if zone in zone_revenue returns False and the else branch quietly moves on. A report built on this number would just look slightly low, for reasons nobody would think to investigate without already suspecting the data itself. Between the two failures this lesson has now produced, this one is the more dangerous of the two: a loud crash gets fixed fast because someone notices immediately; a quiet undercount can run for weeks before anyone questions a number that merely looks a little off.

Not Every Change Is a Breaking Change#

The rename above breaks things because a field the consumer depends on disappeared. Contrast it with a change that wouldn’t have broken this same consumer at all — adding an entirely new field the consumer never looks at:

Adding a field is additive — nothing that already worked stops working. Renaming, removing, or changing the type of a field a consumer actually reads is what breaks things. This distinction — additive versus destructive — is precisely what “compatibility” means once Lesson 4 gives it a formal name and a registry that checks it automatically instead of a human guessing correctly every time.

Practice Exercises#

Exercise 1: Break it a different way#

Modify this lesson’s producer so the fourth event keeps the key fare_amount but changes its value from a number to a string ("12.50" instead of 12.50). Does the consumer crash the same way, a different way, or not at all? What does that tell you about the difference between a missing field and a field with an unexpected type?

Exercise 2: Make the consumer defensive, and see what it costs#

Rewrite the consumer to use record.get("fare_amount", 0) instead of record["fare_amount"]. It won’t crash anymore — but what silently wrong number does it report instead, and is that actually better than crashing?

Hint

A consumer that silently defaults a missing required field to 0 doesn’t fix the data contract problem – it just trades a loud, visible failure for a quiet, wrong number that might not get noticed for weeks.

Summary#

A real consumer crashed with a genuine KeyError the moment an upstream rename shipped with no coordination — three events processed correctly, the fourth one fatal, three more left unread behind it. Nothing in this pipeline enforced any agreement about what a trip event’s fields were; the contract existed only as an unwritten understanding between two people, and it broke the instant they stopped talking to each other in real time. That gap — an implicit, unenforced contract — is exactly what this module’s remaining lessons close.

Key Concepts#

  • A data contract is the agreed shape of an event — which fields exist, what type each is, which are required.
  • Nothing about Kafka itself enforces a data contract — a topic is just bytes; enforcement has to come from somewhere else.
  • A missing field crashes a consumer that depends on it — proven here with a real KeyError, not a hypothetical.
  • A wrong-typed field can fail silently instead — no crash, just a lookup that quietly stops matching, often more dangerous than a loud failure precisely because nobody notices right away.
  • Not every change is breaking — adding a field is additive; renaming, removing, or retyping a field a consumer reads is destructive.

Why This Matters#

This lesson’s crash is the exact motivating problem for everything from here on: Avro gives the contract a real, checkable definition (Lesson 2), Schema Registry enforces it centrally instead of by convention (Lesson 3), and compatibility modes give “breaking vs. safe” a precise, automatically-checked answer (Lesson 4) — closing the gap this lesson just proved exists, with real evidence instead of a warning to take on faith.
