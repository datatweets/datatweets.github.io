Welcome to This Module’s Guided Project#

Four lessons, four separate pieces: a plain consumer loop lost its own state on restart (Lesson 1), a stateless Faust agent tagged trips correctly (Lesson 2), a stateful Faust table recovered 99.44% of itself from a genuine kill (Lesson 3), and Spark Structured Streaming reconciled CityFlow’s entire corpus to a published batch figure in under a minute (Lesson 4). This guided project puts Faust and Spark side by side against identical data and checks whether they actually agree — not with a number from elsewhere, but with each other.

By the end of this lesson, you will be able to:

  • Run the identical aggregation through two independent stream processors
  • Reconcile two engines’ output zone by zone, not just by a matching total
  • Reconcile a full-corpus streaming result against an established batch figure
  • Explain what agreement between two different engines actually proves

The Identical Subset, Through Spark#

Three independent computations — a plain Python sum(), a Faust table, a Spark DataFrame aggregation — all landing on $443,145.04. More than that: all 36 zones the subset actually touched match between Faust and Spark individually, to the cent, with zero mismatches. Two completely different execution engines, one Python-async and one JVM-columnar, agree with each other exactly, not just separately with the same external number.

The Full Corpus, Against the Published Batch Figure#

The subset proves the two engines agree with each other. This proves Spark agrees with a number this platform already trusts — CityFlow’s entire real trip topic, reconciled to the exact figures the PySpark course’s own capstone established from a static file, reusing Lesson 4’s job unchanged:

Exact, on all three figures, matching Course 1’s own published ground truth — the same reconciliation Lesson 4 already ran, confirmed again here as the second half of this guided project rather than assumed to still hold.

Why Two Separate Checks, Not One#

The 15,000-trip subset and the 9,554,757-trip full corpus prove two different things, and neither one alone would be enough. Cross-engine agreement on the subset proves Faust and Spark implement the same aggregation semantics correctly — but a 15,000-row subset is small enough that a subtle bug affecting only a rare edge case (a specific timestamp format, a zone code at the boundary of what either engine’s type inference expects) could easily slip through undetected simply because that edge case never appeared in the sample. The full-corpus check against Course 1’s published figures closes exactly that gap: at 9.5 million actual rows, drawn from a production-shaped dataset rather than a curated sample, anything that would only misbehave on unusual data has millions of chances to actually show up. Passing the small check first, then the large one, is what makes this guided project’s reconciliation trustworthy — either alone would leave a specific class of bug undetected that the other one is built to catch.

Practice Exercises#

Exercise 1: Reconcile with a different sample size#

Rerun this lesson’s cross-engine comparison with 50,000 trips instead of 15,000. Does the zone-by-zone mismatch count stay at zero? What would a nonzero mismatch count actually indicate, given that both engines are reading the identical topic?

Exercise 2: Break the reconciliation on purpose#

Change Faust’s aggregation key from pickup_zone to dropoff_zone while leaving Spark’s grouped by pickup_zone. Rerun the comparison. How many mismatches show up now, and why does this prove the reconciliation check itself is actually checking something real?

Hint

Exercise 2 is a deliberate negative control – if the check can’t catch an obviously wrong comparison, it wasn’t proving anything the first time it passed either.

Summary#

CityFlow’s revenue-by-zone aggregation, built independently in Faust and Spark Structured Streaming against the identical 15,000-trip subset, matched exactly — $443,145.04 on both, and zero mismatches across all 36 zones compared individually. Spark then reconciled CityFlow’s entire trip corpus to the exact figures the PySpark course’s own batch capstone already published: 240,917 buckets, 9,554,757 trips, $256,692,373.14. Two engines, two scales, checked against each other and against an independent published ground truth — not just internally consistent, but externally verified twice over.

Key Concepts#

  • Reconciling two engines against each other is a stronger check than either alone — agreement that isn’t just both matching one shared assumption.
  • Zone-by-zone comparison catches what a matching total can hide — two wrong numbers that happen to cancel out would still pass a total-only check.
  • A streaming reconciliation against a batch figure is verification, not demonstration — the numbers either match Course 1’s published ground truth exactly, or they don’t.
  • Both engines processed data at genuinely different scale — a 15,000-trip subset for cross-engine agreement, the entire 9.5-million-row corpus for the published-figure check.

Why This Matters#

This module replaced “move data as-is” with “transform and aggregate it while it’s still moving” — and this guided project is the proof that doing so doesn’t cost correctness, checked from two independent directions rather than trusted on faith. Module 10 moves to orchestrating and monitoring the pipelines this course has built across every module so far — batch jobs that depend on streaming checkpoints, and Airflow watching a real Kafka consumer’s lag directly.
