Welcome to Reliable Data Delivery#

Module 4 Lesson 2 introduced manual offset commits and warned that when you commit relative to when you process changes what happens if the consumer dies at the wrong moment. This lesson stops treating that as a warning and turns it into three precisely defined guarantees, two of which get proven here with a real process killed by SIGKILL — the same uncatchable, no-cleanup signal a real crash or kill -9 sends.

By the end of this lesson, you will be able to:

  • Define at-most-once, at-least-once, and exactly-once precisely, not just by name
  • Predict which guarantee a given commit-before-or-after-processing pattern produces
  • Explain what a real killed process proves that a diagram can’t
  • Connect delivery guarantees directly to Module 4’s own offset-commit findings

Three Guarantees, Defined Precisely#

  • At-most-once: each message is processed zero or one times. Never duplicated, but a crash at the wrong moment can lose one outright.
  • At-least-once: each message is processed one or more times. Never lost, but a crash at the wrong moment can process one twice.
  • Exactly-once: each message is processed exactly one time, no loss and no duplication. Kafka can deliver this, but only with additional machinery — idempotent and transactional producers, covered in Lesson 3 — layered on top of at-least-once, not as a separate mode you simply switch on.

The dividing line between the first two isn’t the consumer’s logic — it’s a single ordering decision: does commit() happen before a message is processed, or after? Module 4 Lesson 2 already showed manual commits are safer than enable_auto_commit’s five-second timer; this lesson shows that manual commits still split into two genuinely different guarantees depending on where exactly they sit relative to the processing step.

Setting Up the Proof#

Thirty sequentially numbered events, one partition, and a worker process that can commit either before or after “processing” a message (here, appending its sequence number to a log file — standing in for whatever real work a consumer does):

consumer.commit() in the at_most_once branch runs before the message is written to log_file — the offset is safely advanced, then the “processing” happens. In the at_least_once branch it’s the reverse: write first, commit after. os.kill(os.getpid(), signal.SIGKILL) is a real, uncatchable process kill, identical in effect to kill -9 from a terminal — no finally block runs, no cleanup, no graceful shutdown, exactly the failure mode delivery guarantees exist to survive.

At-Most-Once: Committed, Then Lost#

Seq 15’s offset was committed, then SIGKILL hit before the line was ever written. On restart, the worker resumes from the committed offset — past seq 15 — and never sees it again. Zero duplicates, one message gone, permanently. That’s at-most-once, produced by a real kill, not asserted from a definition.

At-Least-Once: Processed, Then Duplicated#

Seq 15 got written to the log, then SIGKILL hit before commit() ran. The committed offset still points at seq 15, so on restart the worker fetches it again, processes it again, and writes it to the log a second time. Zero messages lost, one duplicate. Same crash, same message, opposite outcome — entirely determined by which side of commit() the processing landed on.

Exactly-Once: What It Actually Requires#

Neither demo above can be turned into exactly-once by rearranging commit() alone — there is no ordering of “commit” and “process” that survives an arbitrary crash with neither loss nor duplication, because the two actions are fundamentally not atomic with each other on the consumer side. Kafka’s real answer isn’t a third ordering; it’s additional protocol machinery: an idempotent producer so retried sends don’t create duplicates at the write side, and, for anything that reads from Kafka and writes back to Kafka, transactions that make a group of writes atomic across topics and partitions. Lesson 3 builds both and proves what they do and don’t cover — including the common overclaim that “idempotent producer” alone means “exactly-once consumer processing,” which it does not.

Tying This Back to Module 4#

Module 4 Lesson 2’s ConsumerRebalanceListener.on_partitions_revoked() committed offsets before a rebalance took partitions away — an at-least-once pattern, deliberately chosen because losing an offset commit at rebalance time risks reprocessing, which Module 4’s own bulk load treated as the acceptable failure mode over silent loss. That choice weighed the two guarantees this lesson just proved directly: at-least-once’s cost is a duplicate, which downstream processing can usually detect and discard; at-most-once’s cost is a message that’s simply gone, with no signal that anything is even missing. That asymmetry is why at-least-once is the default most real systems reach for, and why Lesson 4 builds a consumer pattern that safely retries within it instead of just hoping duplicates never happen.

Practice Exercises#

Exercise 1: Move the kill point and re-observe#

Change kill_after from 15 to 0 (the very first message) and rerun both demos. Does the pattern hold at the boundary — first message lost under at-most-once, first message duplicated under at-least-once?

Exercise 2: Commit every 5 messages instead of every 1#

Modify the at-least-once worker to call consumer.commit() only every 5th message instead of after each one, keeping the kill point at seq=15. How many duplicates appear on restart now, and why does batching commits change the size of the duplicate window rather than eliminating it?

Hint

Batched commits trade commit overhead for a wider window of “already processed but not yet acknowledged” work – the same tradeoff Module 3 Lesson 3 measured on the producer side with acks, now showing up on the consumer side instead.

Summary#

At-most-once and at-least-once aren’t abstract labels — they’re the direct, provable consequence of whether commit() runs before or after processing, demonstrated here with a real SIGKILL against a real consumer process rather than a diagram. Committing before processing loses seq 15 outright when the kill lands at the wrong instant; committing after processing duplicates it instead. Exactly-once needs more than reordering these two calls — it needs the idempotent producer and transactional machinery Lesson 3 builds next.

Key Concepts#

  • At-most-once: zero or one deliveries — never duplicated, can lose a message.
  • At-least-once: one or more deliveries — never lost, can duplicate a message.
  • The dividing line is commit-before-processing vs. commit-after-processing, proven here with an identical crash producing opposite outcomes.
  • Exactly-once needs additional protocol machinery (idempotent producers, transactions) — it isn’t a third commit ordering.

Why This Matters#

Every reliability setting the rest of this module configures — broker-side settings in Lesson 2, idempotent and transactional producers in Lesson 3, safe consumer retries in Lesson 4 — exists to either strengthen or safely live within one of these two guarantees. Understanding that the guarantee comes from an ordering decision, provable with a real crash, is what makes the rest of this module’s configuration choices legible instead of a list of settings to memorize.
