Welcome to MirrorMaker 2#

Lesson 1 named three real reasons to run a second Kafka cluster. This lesson builds one — kafka-dr, a genuinely separate single-broker cluster with its own identity — and replicates a live topic into it with MirrorMaker 2, Kafka’s own built-in cross-cluster replication tool. Every number in this lesson is measured against that real, running pair of clusters.

By the end of this lesson, you will be able to:

  • Stand up a second, independently identified Kafka cluster
  • Configure and run MirrorMaker 2 between two real clusters
  • Verify replicated data byte-for-byte and measure real replication lag
  • Recognize two genuine MirrorMaker 2 operational gaps before they cost debugging time in production

A Genuinely Separate Second Cluster#

kafka-dr is a real, single-broker KRaft cluster — its own CLUSTER_ID, its own storage volume, its own controller quorum of one. It shares kafka-net, the same Docker network the primary 3-broker cluster runs on, for the same reason Module 10 Lesson 2 joined Airflow to that network: reachability by real hostname, not a workaround.

Two genuinely different cluster identities, confirmed directly rather than assumed from the compose file’s own separate CLUSTER_ID variable. kafka-dr runs at replication factor 1 deliberately — a single broker has nothing to replicate to internally, and forcing RF 3 onto one broker would just fail to start, an honest reflection of its role as a small standalone target rather than a scaled-down copy of the primary cluster’s own topology.

Configuring MirrorMaker 2#

mm2.properties names both clusters, which direction to replicate, and which topics to mirror:

primary->dr.enabled = true with dr->primary.enabled = false makes this deliberately one-directional — data flows from the primary cluster into the DR cluster, never back, matching the disaster-recovery use case Lesson 1 named. Every *.replication.factor setting is forced to 1 because kafka-dr only has one broker to satisfy it with; MM2’s own internal topics (offsets, status, configs) need somewhere to live too, and they inherit whichever cluster’s constraints apply. The three refresh/sync intervals are set to 5 seconds specifically for this lesson’s testing — MM2’s own defaults are far longer, and that gap is exactly what this lesson’s second gotcha exposes.

MirrorMaker 2 runs as its own process, using the same connect-mirror-maker.sh script every Kafka distribution ships:

Twenty-five messages, produced only to the primary cluster, never touching the DR cluster directly:

Not “close” — identical, sorted and compared value by value. This is the same discipline Module 7’s Avro reconciliation and Module 9’s Faust-vs-Spark cross-check both insisted on: a replication claim only counts once it’s verified this directly.

Measuring Replication Lag#

A single message, timestamped at the moment it’s sent, times exactly how long MirrorMaker 2 takes to make it visible on the DR cluster — polling the DR topic’s own end offsets rather than guessing at a fixed sleep:

Roughly a third of a second, on this lab’s own single-machine, single-Docker-network setup — the loopback-adjacent number Lesson 1 already flagged as not representative of cross-region distance, but a directly measured floor for what MirrorMaker 2’s own processing overhead costs before any network distance is added on top.

Gotcha 1: A Warning MM2’s Own Logs Never Explain#

sync.topic.configs.enabled = true makes MM2 keep the mirrored topic’s configuration in sync with the source — and it fails, repeatedly, logged as a bare warning with no further detail:

The obvious guess — that min.insync.replicas=2 on the source topic can’t be synced onto a single-broker DR cluster — turned out wrong when tested directly:

That identical change succeeds instantly when applied directly with Kafka’s own tooling. Enabling full exception logging on MirrorMaker 2’s own log4j2 pattern (%ex{full} added to the format string) produced no additional output at all — the warning carries no underlying exception with it, by design or by omission, not by any logging misconfiguration on this lab’s part. The honest conclusion: this specific warning is reproducible and harmless in this setup (the topic mirrors correctly regardless), but its root cause is not diagnosable from MirrorMaker 2’s own logs, even at maximum verbosity — confirmed by testing, not assumed. A production deployment hitting this warning would need to reproduce the config-sync operation manually, the same way this lesson just did, rather than trust the log to explain itself.

Gotcha 2: A Ten-Minute Default Most Local Setups Never Trigger#

emit.checkpoints.enabled = true makes MirrorMaker 2 track, per consumer group, where that group’s offsets on the source cluster translate to on the DR cluster — the mechanism a real failover depends on to resume consuming from close to the right place. It only works for groups MM2 has actually discovered, and discovery runs on its own separate schedule from topic discovery:

Twenty-four seconds — with refresh.groups.interval.seconds explicitly set to 5 for this lesson. Left at its documented default, that interval is 600 seconds — ten full minutes — before a consumer group created after MirrorMaker 2 started gets checkpointed at all. A local, short-lived test that creates a topic, starts MM2, creates a consumer group, and checks for checkpoints within the first minute — a completely reasonable thing to try — will see nothing and reasonably conclude checkpointing is broken, when it’s actually just waiting on an easy-to-miss default.

Practice Exercises#

Exercise 1: Reverse the direction#

Add dr->primary.enabled = true to mm2.properties, restart MirrorMaker 2, and produce a message directly to a topic on kafka-dr. Does it appear back on the primary cluster prefixed dr.<topic>? What risk does enabling both directions at once introduce for a topic name that exists identically on both clusters already?

Exercise 2: Trigger the 10-minute default#

Remove refresh.groups.interval.seconds from mm2.properties entirely, restart MirrorMaker 2, and create a new consumer group immediately after. Time how long checkpoints actually take to appear — does it match the documented 600-second default closely, or does something else about this lab’s setup change the number?

Hint

Ten minutes is a long time to sit and watch a terminal – write the polling loop this lesson already built, point it at a longer deadline, and let it tell you the real answer instead of watching the clock yourself.

Summary#

kafka-dr — confirmed by distinct cluster IDs, not assumed — stands as a genuine second Kafka cluster. MirrorMaker 2 replicated 25 messages into it byte-for-byte, and a single message’s own replication lag measured 0.339 seconds end to end. Two gaps surfaced under direct testing: a config-sync warning whose cause stayed invisible even under full exception logging, confirmed not to be a simple RF mismatch by testing the identical change manually; and a consumer-group checkpoint delay driven by a refresh.groups.interval.seconds default (600 seconds) that’s separate from topic discovery entirely, and easy to miss on a first from-scratch MM2 setup.

Key Concepts#

  • MM2 needs two separately identified clusters — confirmed by distinct CLUSTER_IDs, not assumed from configuration alone.
  • Replication claims need byte-for-byte verification — count and content, matching the discipline this course has used since Module 7.
  • Not every log warning explains itself — this lesson’s config-sync warning stayed opaque even at full exception verbosity, confirmed by direct testing rather than left as a guess.
  • Group discovery and topic discovery run on separate schedules — refresh.groups.interval.seconds defaults to 10 minutes, independent of how fast topics themselves get picked up.
