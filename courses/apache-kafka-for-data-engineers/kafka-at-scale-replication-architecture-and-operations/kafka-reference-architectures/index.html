Welcome to Reference Architectures#

Ten modules of this course each solved one problem in isolation — replication, schemas, connectors, stream processing, orchestration. This lesson steps back and reads the whole thing at once, as a real data platform someone could hand to a new engineer and ask “how does this fit together?” The answer turns out to match four well-established Kafka reference patterns almost exactly, component for component.

By the end of this lesson, you will be able to:

  • Name four common Kafka reference architecture patterns
  • Match each pattern against a real, already-built piece of CityFlow’s platform
  • Explain honestly what CityFlow’s platform does not implement, and why that’s a legitimate scope choice
  • Read any new Kafka deployment against these same patterns instead of starting from a blank page

Pattern 1: The Event-Streaming Backbone#

The most basic Kafka pattern: one durable, replayable log sitting between producers and consumers that don’t know about each other. cityflow-trip-events — 6 partitions, replication factor 3, min.insync.replicas=2 — has been exactly this since Module 1. Producers (the bulk-load script from Module 4’s guided project, individual trip-event producers throughout) never know or care who reads the topic. Consumers (Module 5’s consumer groups, Module 9’s Faust and Spark jobs, Module 8’s Elasticsearch sink) never know or care who wrote it.

That decoupling is the whole point of this pattern, and it’s why every other pattern in this lesson is really just a different use of the same backbone, not a separate piece of infrastructure. A platform team adding a fifth consumer of trip events next month wouldn’t touch the producers, the topic configuration, or any existing consumer — the same property Module 5 demonstrated directly when three independent consumer group workers read the identical topic without coordinating with each other at all.

Pattern 2: CDC and Data Integration#

Module 8 built exactly this pattern: a JDBC source connector reading MySQL rows into Kafka, an Elasticsearch sink connector reading those same messages back out into a searchable index — data integration through configuration, not hand-written producer/consumer code. Kafka Connect exists specifically for this pattern, at a scale where writing a bespoke script per source-and-destination pair stops being maintainable.

Named precisely: what CityFlow’s platform runs is polling-based integration (mode: incrementing, reading new rows on a timer), not true change-data-capture. Module 8 Lesson 4’s own decision framework covered this distinction directly — polling misses deletes and adds real latency (measured at roughly 10.31 seconds per poll cycle against a hand-written producer’s 0.17 seconds), while a real CDC tool like Debezium reads the database’s own write-ahead log and captures every change, including deletes, with far lower latency. CityFlow’s MySQL container has log_bin=ON, confirmed CDC-ready infrastructure — but Debezium itself was never deployed, a genuine, named scope boundary rather than an oversight glossed over as “basically the same thing.”

Pattern 3: Real-Time Stream Processing#

Module 9 built this pattern twice, deliberately, at two different scales: Faust processing cityflow-trip-events message by message with a stateful table backed by its own Kafka changelog, and Spark Structured Streaming reading the same topic through a one-hour tumbling window, both computing revenue aggregates directly off the live stream rather than a landed batch file.

This pattern’s defining property, proven directly rather than asserted: the computation happens while data is still moving, not after it’s been written somewhere else and read back. Kafka is not just a transport in this pattern — it’s the thing being computed over, continuously, with the topic’s own retention window standing in for how far back a stream processor can “look” without a separate batch fallback.

Pattern 4: The Lambda Split — Batch and Speed Paths Reconciled#

This is the pattern CityFlow’s platform demonstrates most concretely, because Module 9’s guided project didn’t just build both halves — it proved they agree. The PySpark course’s own capstone computed $256,692,373.14 in revenue across 9,554,757 trips by reading a static batch file. Module 9’s Spark Structured Streaming job read the identical trips as a live Kafka stream and landed on the exact same figure, to the cent, in well under a minute.

That’s a real Lambda architecture, worked concretely: a batch layer (the PySpark course’s static-file job) and a speed layer (this course’s live Kafka stream processing) computing the same business metric through genuinely different mechanisms, reconciled against each other rather than trusted independently. A platform running true Lambda in production keeps both layers permanently, using the speed layer for low-latency approximate answers and the batch layer as the periodically-recomputed source of truth — this course’s version proved the two layers can agree exactly, the property the whole pattern depends on, rather than assuming it.

What CityFlow’s Platform Doesn’t Implement#

Naming gaps plainly is as much a part of reading an architecture as naming what’s there. Three real, deliberate scope boundaries:

No true CDC. Already covered above — Module 8’s integration pattern is polling-based, a legitimate and common real-world choice, but not the lower-latency, delete-aware pattern a Debezium deployment would provide.

No schema-on-read data lake. CityFlow’s data lands in a search index (Elasticsearch) and gets processed in flight (Faust, Spark), but nothing in this course writes trip events to columnar, schema-on-read storage (Parquet on object storage, a table format like Iceberg or Delta) for long-term, ad hoc analytical querying independent of Kafka’s own retention window. A real platform at CityFlow’s scale would likely add this — Kafka’s retention is measured in days, not years, and a data lake is where “years” lives.

No multi-tenant governance layer. Every topic, connector, and consumer group in this course belongs to one team’s worth of concerns. A real platform serving many teams typically adds quota enforcement, schema governance beyond Module 7’s compatibility rules, and access control per topic — none of which this course’s single-tenant lab needed to build to prove its architectural patterns.

Practice Exercises#

Exercise 1: Place a new component#

CityFlow’s product team wants a Slack notification the moment average fare in any zone exceeds a threshold, computed continuously as trips stream in. Which of this lesson’s four patterns does that component belong to, and which existing CityFlow component (named specifically) would it most resemble in shape?

Exercise 2: Argue for or against adding Debezium#

Using Module 8 Lesson 4’s own decision framework and this lesson’s gap list, write two or three sentences arguing whether CityFlow’s platform should add a real Debezium-based CDC connector next, or whether the current polling-based integration is good enough for its actual use case. Justify either answer against real measured numbers (the poll-latency figures Module 8 measured), not general Kafka reputation.

Hint

“Good enough” is a real, defensible engineering answer when the measured latency a pattern provides already meets the actual requirement – the question is whether CityFlow’s use case genuinely needs sub-second freshness or delete-awareness, not whether CDC is generally “better.”

Summary#

CityFlow’s own ten-module platform maps directly onto four established Kafka reference patterns: an event-streaming backbone decoupling producers from consumers, a CDC-style (in practice, polling-based) data integration pipeline built with Kafka Connect, a real-time stream-processing pipeline running at two different scales, and a Lambda-style batch/speed split whose two layers were proven to agree exactly rather than assumed to. Three real gaps — no true CDC, no schema-on-read lake, no multi-tenant governance — are named plainly as deliberate scope boundaries, not oversights.

Key Concepts#

  • One durable log serves every pattern in this lesson — the event-streaming backbone is the shared foundation every other pattern builds on top of.
  • Polling-based integration and true CDC are genuinely different patterns — CityFlow’s platform implements the former, with Debezium-ready infrastructure never deployed.
  • A proven Lambda split beats an assumed one — Module 9’s exact-figure reconciliation is what makes CityFlow’s batch/speed split a real architectural claim, not a diagram.
  • Naming what’s missing is part of reading an architecture — a platform’s real scope includes what it deliberately didn’t build.
