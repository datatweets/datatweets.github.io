Lesson 3 - Consumer Lag and Broker Health Monitoring

Welcome to Standalone Monitoring#

Lesson 2 built a monitoring check inside Airflow. This lesson steps outside it entirely: plain Python scripts, run directly against CityFlow’s cluster, using nothing but kafka-python’s admin client — the same library the Airflow Hook wraps, called here without any orchestration around it at all. Airflow will schedule scripts like these later in this module; first, they need to exist and be trusted.

By the end of this lesson, you will be able to:

  • Sweep every consumer group on a cluster for lag in one script
  • Read cluster metadata: controller identity, broker list, live topic config
  • Detect under-replicated partitions the same way Kafka’s own tools do
  • Recognize what an abandoned consumer group’s lag actually looks like

Every Consumer Group, One Sweep#

Lesson 2’s compute_group_lag() checked exactly one group. A health check worth running doesn’t know in advance which groups matter — it lists every active group on the cluster and reports on all of them:

Eight of these nine groups look exactly like what a healthy cluster should show: zero lag, or a small, bounded number left over from a lesson’s own last run. One doesn’t. cityflow-faust-throughput-check — Module 9 Lesson 3’s throughput measurement against the full cityflow-trip-events topic — is sitting on 9,288,741 messages of lag. That group was never meant to keep consuming; the throughput test read a fixed window and stopped, and its committed offset simply never advanced past that point. Kafka itself has no opinion about this — the group’s offsets sit in __consumer_offsets indefinitely, unless offsets.retention.minutes eventually expires them. A cluster-wide sweep is what actually surfaces this: not an error, not a crash, just a number a human has to look at and decide whether it matters.

This is the honest case for monitoring over spot-checking: Lesson 2’s single-group check would never have found this, because it only ever asked about the one group it already knew to ask about.

Real Cluster Metadata#

describe_cluster() reports exactly what every broker agrees is true about the cluster right now — no polling loop, no topic involved at all:

That cluster_id is the identical value every earlier module’s connections have reported since Module 1 — the cluster’s own permanent identity, unaffected by which broker happens to be controller at any given moment. Broker 3 holding the controller role here is itself just current state; Module 6’s leader-election lessons already proved that role moves during a real outage, and a health check that only ever assumes one broker is the controller would silently go stale the moment a real failover happened.

Under-Replicated Partitions, Computed Directly#

describe_topics() returns each partition’s real replica list and its real in-sync-replica (ISR) set — a partition is under-replicated exactly when those two lists differ in size, the identical definition kafka-topics.sh --describe --under-replicated-partitions uses internally:

Every partition healthy — all three replicas in sync, on every partition. Module 6 Lesson 2 forced exactly this metric to fail on purpose, killing a broker mid-write and watching a partition’s ISR set shrink below its replica count; this script is the same check that lesson’s proof relied on, generalized into something schedulable.

Reading Live Config Off a Running Broker#

describe_configs() reads a topic’s actual current configuration directly from the cluster — not the value a script last set it to, the value a broker is enforcing right now:

min.insync.replicas=2 here is exactly the setting Module 6’s acks=all producers have depended on for the whole course — reading it back live, from the broker itself, is how a real health check confirms a critical safety setting hasn’t drifted, rather than trusting whatever a setup script claimed to configure once.

Practice Exercises#

Exercise 1: Decide what to do about the abandoned group#

cityflow-faust-throughput-check’s lag will never shrink on its own — nothing is consuming it. Using kafka-consumer-groups.sh --describe --group cityflow-faust-throughput-check, confirm it independently, then decide: would you reset its offsets to the topic’s current end (accepting the group will never process the messages it skipped), delete the group entirely, or leave it? Justify the choice in terms of what the group was actually for.

Exercise 2: Trigger a real under-replicated partition#

Stop one CityFlow broker container (docker stop kafka2) and rerun this lesson’s describe_topics() script against cityflow-trip-events. Does every partition’s ISR set actually shrink, or only the ones broker 2 was a replica for? Restart the broker afterward and confirm the ISR set recovers.

Hint

A partition’s leader moving is a separate event from its ISR set shrinking – describe_topics() reports both, and they don’t always change together the way you’d expect.

Summary#

A cluster-wide lag sweep — every real consumer group, one script — found something a single-group check never would have: an abandoned group carrying 9,288,741 messages of real lag. Broker health gets the identical standalone-script treatment: describe_cluster() for real controller and broker identity, describe_topics() to compute under-replicated partitions by comparing replica and ISR list lengths, and describe_configs() to confirm a topic’s critical settings haven’t drifted from what a broker is actually enforcing.

Key Concepts#

  • A cluster-wide sweep catches what a targeted check can’t — an abandoned consumer group with millions of messages of lag, invisible to any check that only asks about groups it already expects.
  • Under-replicated is a direct comparison, not a special API — len(isr) < len(replicas), computed straight from describe_topics().
  • Live config beats remembered config — describe_configs() reads what a broker is enforcing right now, not what a setup script once requested.
  • Kafka never expires an abandoned group’s lag on its own — offsets sit in __consumer_offsets until offsets.retention.minutes passes or someone acts.

Why This Matters#

Lesson 4 turns from reading cluster state to changing it — resetting a consumer group’s offsets and altering a live broker’s config, the genuinely riskier half of administration this module has been building toward.

Continue Building Your Skills#

Lesson 4 puts a real admin safety habit into practice: dry-run every destructive command against a real, named target before it ever executes for real, starting with the exact kind of offset reset Exercise 1 just asked about.
