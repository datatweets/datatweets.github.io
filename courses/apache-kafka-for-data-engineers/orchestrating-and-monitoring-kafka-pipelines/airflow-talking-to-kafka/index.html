Welcome to Cross-Cluster Networking#

.airflow-local/ and .kafka-local/ are two entirely separate Docker Compose projects, each with its own network, brought up independently across nine modules of this course and Course 4’s own orchestration lessons. Neither has ever needed to talk to the other — until now. This lesson makes that connection real, hits a genuine networking gotcha doing it, and ends with an Airflow Hook whose numbers are proven correct against Kafka’s own tooling.

By the end of this lesson, you will be able to:

  • Explain why host.docker.internal looks like the right fix here and isn’t
  • Join two independent Docker Compose projects’ networks deliberately
  • Build an Airflow Hook that wraps a plain, Airflow-free function
  • Run a real Airflow DAG task that computes real Kafka consumer lag

The Fix That Doesn’t Work#

Every broker in this cluster publishes two listeners — confirmed back in .kafka-local/docker-compose.yml since Module 1:

PLAINTEXT_HOST is exactly what every script in this course has used from the host machine’s own Python: localhost:9092, localhost:9093, localhost:9094. Docker Desktop’s host.docker.internal hostname resolves to the host machine from inside any container, so the obvious move for an Airflow task — itself running inside a container — is to reuse those same host-published ports:

Run from inside airflow-local-airflow-scheduler-1, the TCP connection to port 9092 succeeds — but the call itself fails:

The reason is exactly what PLAINTEXT_HOST://localhost:9092 says, read literally: after the initial bootstrap connection, the broker hands the client back localhost:9092 as the address to use for the real data connection — its own advertised address, not the one the client dialed in on. From inside the Airflow scheduler container, localhost means that container itself, not the host machine. The bootstrap succeeds because port 9092 really is reachable; every request after it fails, because the broker’s own advertised listener is unreachable from where the client actually is. This is a genuine, confirmed Kafka behavior, not a firewall or Docker networking bug — the exact same mismatch that would trip up any external system, Airflow included, trying to reach a cluster whose advertised listeners were configured for one specific vantage point.

The Fix That Does: Sharing a Network#

Kafka’s other listener, PLAINTEXT://kafka1:29092, is the one every container already inside kafka-net uses — Kafka Connect, Schema Registry, and every broker talking to every other broker. The real fix isn’t a different hostname; it’s putting Airflow’s own containers on that same network, so kafka1:29092 resolves and connects exactly the way it does for every other service already there:

kafka-net is declared external: true because it already exists — created by .kafka-local/docker-compose.yml’s own networks: block, not by this file. Recreating the two containers picks up the change:

That connection now resolves for the same reason it resolves for Kafka Connect: airflow-webserver and airflow-scheduler sit on kafka-net right alongside kafka1, kafka2, kafka3, and every other service .kafka-local/docker-compose.yml runs, all reachable by their real container hostnames.

A Real Hook, Not a Simulated One#

Course 4’s own Sensors, Hooks & Connections lesson is the deeper reference for what a Hook is and why Airflow separates connection details from task logic; this lesson applies that pattern to Kafka instead of a database. The lag math itself stays plain Python, no Airflow import at all — the same split cityflow_alerting.py already established for on-failure callbacks:

Kafka never reports “lag” as a single number anywhere in its own protocol — every tool that shows it, kafka-consumer-groups.sh included, computes this exact subtraction: a partition’s log-end offset (its real high-water mark, from end_offsets()) minus that partition’s last offset the group actually committed (from list_consumer_group_offsets()).

Practice Exercises#

Exercise 1: Break the Connection on purpose#

Delete the cityflow_kafka Connection (airflow connections delete cityflow_kafka) and rerun airflow dags test cityflow_kafka_lag_check 2026-01-01. What exception does get_bootstrap_servers() raise, and where in the task log does it show up? Recreate the Connection afterward.

Exercise 2: A second group, a second call#

Pick any other consumer group this course has created (cityflow-rebalance-demo is a safe choice) and call CityFlowKafkaLagHook().get_group_lag(...) against it directly. Does an inactive group with no committed offsets on some partitions behave the way compute_group_lag()’s docstring says it should?

Hint

A partition the group never committed to reports committed_offset=-1 in this function’s output – its lag is defined as the full log-end offset, since nothing has ever been read.

Summary#

host.docker.internal reaches Kafka’s bootstrap port but never delivers a real message, because the broker’s own PLAINTEXT_HOST advertised listener points back at localhost — meaningless from inside a different container. Joining airflow-webserver and airflow-scheduler to kafka-net directly fixes that at the network layer. CityFlowKafkaLagHook, a real Airflow Hook wrapping a plain, Airflow-free lag-computation function, reports the exact same total lag as kafka-consumer-groups.sh — proven by cross-checking, not assumed — and a DAG task run through Airflow’s actual scheduler reproduces that same number one layer higher.

Key Concepts#

  • host.docker.internal fails here for a specific, confirmed reason — the broker’s advertised listener for that port points back at localhost, which means the wrong host from inside a container.
  • Sharing a Docker network is the real fix — joining kafka-net lets Airflow’s containers use the same internal hostnames every other Kafka-side service already uses.
  • A Hook should wrap plain logic, not contain it — compute_group_lag() has no Airflow import; the Hook only adds where the connection details come from.
  • Lag is always a subtraction — log-end offset minus committed offset, the same math every tool that reports lag performs.
