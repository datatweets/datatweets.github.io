Welcome to Cluster Administration#

Every earlier lesson in this module read state: lag numbers, broker metadata, replica lists. This lesson changes it — pausing a running connector, moving a consumer group’s committed offsets, growing a topic’s partition count, altering a live broker’s configuration. Every one of these operations can go wrong in a way that reading state never can, so this lesson insists on one habit before every single one: confirm the real target, and dry-run it first when the tool offers that option.

By the end of this lesson, you will be able to:

  • Pause and resume a real Kafka Connect connector through its REST API
  • Dry-run a consumer-group offset reset before ever executing it
  • Grow a topic’s partition count, and explain why it can’t shrink back
  • Change a live broker’s config and account for its real propagation delay

Pausing a Connector Without Deleting It#

Module 8 only ever deleted connectors between lessons. A real operator doesn’t always want that — pausing stops a connector’s tasks without losing its configuration or its committed offsets, exactly the difference between “stop reading for now” and “forget this connector ever existed”:

Notice the connector’s state flips to PAUSED immediately, but its one task still reports RUNNING two seconds later — the worker propagates a pause to its tasks asynchronously, so a script that only checks the connector’s own top-level state might act on a pause before every task has actually stopped polling. Checking tasks[].state too, not just connector.state, is the honest version of “confirm the real target” applied to Connect specifically: know what’s actually still running, not just what was asked to stop.

Resetting Offsets: Dry Run First, Always#

Resetting a consumer group’s offsets is the clearest case in this whole module for why “dry run first” isn’t optional caution — it’s the only way to see the real, exact effect before it’s irreversible. kafka-consumer-groups.sh refuses to reset offsets for an active group at all, and offers --dry-run for exactly this reason:

The dry run shows exactly what would change — every partition reset to offset 0 — with nothing actually committed yet. Only after confirming that’s the real, intended target does --execute replace --dry-run:

Lesson 2 measured this exact group’s lag at 12. Resetting to earliest doesn’t clear lag — it creates it, by making every message the group had already committed past look unread again. Lag went from 12 to 30 (the full 10 + 0 + 20 messages across all three partitions), the precise, predictable outcome the dry run already showed before --execute ever ran.

Growing a Topic’s Partitions: A One-Way Door#

Topic partition counts move in exactly one direction:

Three partitions became six, without error. Trying the reverse — even back to the topic’s own original count — fails immediately, not eventually:

Kafka enforces this at the protocol level — there’s no --force, no workaround short of deleting the topic and recreating it, which loses every message on it. It’s a genuine, confirmed one-way door, and the reason isn’t arbitrary: Module 4 already established that a keyed message’s partition is hash(key) % partition_count. Growing the partition count changes that mapping for every future message with the same key — existing messages don’t move, but a consumer relying on “all of this key’s messages land on the same partition” needs to know the count just changed, right when this command succeeds.

Changing a Live Broker’s Config#

AdminClient.alter_configs() changes a running broker’s or topic’s configuration without a restart — genuinely live, not scheduled for the next deploy:

error_code=0 means the request succeeded — but reading the value back immediately afterward showed the previous value, not the new one, in this lesson’s own testing. A second read, moments later, showed the correct 3600000. This is a real, confirmed propagation gap, not a bug in either the client or the broker: alter_configs() returns as soon as the controller accepts the change, before every broker in the cluster has necessarily applied it locally. A script that alters a config and immediately asserts on the new value in the same breath can catch a false negative that has nothing to do with whether the change actually worked.

Practice Exercises#

Exercise 1: Reset to a specific offset, not just earliest#

Using --reset-offsets, reset cityflow-orchestration-monitor to a specific offset (--to-offset 5) instead of --to-earliest, with --dry-run first as always. Predict the resulting lag for the partition you target before running --execute.

Exercise 2: Time the propagation delay#

Rerun this lesson’s alter_configs() example against a fresh topic, but poll describe_configs() in a tight loop immediately afterward (no sleep) until the new value actually appears. Roughly how long does the propagation take on this cluster?

Hint

Ask whether the delay is closer to milliseconds or seconds before you start polling – it changes how tight a loop actually makes sense.

Summary#

Every destructive operation in this lesson followed the same shape: confirm the real target, dry-run when the tool offers it, then execute. Pausing a connector stops its tasks without losing its config, though a task can lag its connector’s own reported state by a couple of seconds. Resetting offsets moved cityflow-orchestration-monitor’s lag from 12 to 30, exactly as its dry run predicted. A topic’s partition count grew from 3 to 6 and then refused to shrink back — a genuine, protocol-level one-way door. A live broker’s config changed for real, with a confirmed propagation delay before every broker agreed on the new value.

Key Concepts#

  • Dry-run before execute, every time a tool offers it — kafka-consumer-groups.sh --dry-run shows the exact outcome before anything commits.
  • A connector’s task state can lag its own connector state — check both before assuming a pause has fully taken effect.
  • Partition counts only increase — Kafka enforces this at the protocol level, with real consequences for keyed-message routing.
  • A successful admin call doesn’t mean every broker has caught up yet — alter_configs() can return success before the new value is visible everywhere.
