Welcome to Kafka Connect vs a Custom Producer/Consumer#

Three lessons built real connectors and made them work. This lesson asks the harder question honestly: when is a connector actually the right choice, and when does this course’s own Module 1-through-7 approach — a hand-written producer or consumer — still win? Two real limitations, measured directly, anchor the answer.

By the end of this lesson, you will be able to:

  • State the measured latency cost of polling-based source connectors
  • Prove, with a real deleted row, exactly what polling modes miss
  • Explain what change-data-capture is and why this course’s database is ready for it
  • Apply a genuine decision framework instead of defaulting to “Connect is easier”

Measuring the Real Latency Cost of Polling#

A JDBC source connector doesn’t know the instant a row is inserted — it finds out the next time it polls. Insert one row and time exactly how long it takes to reach Kafka, against a hand-written producer inserting and producing in the same script:

Roughly 60 times slower, measured directly, not estimated — and this isn’t even the worst case. The exact gap depends on where an insert lands relative to the connector’s poll cycle: a row inserted the instant after a poll finishes has to wait the entire next interval before it’s seen at all. Lowering poll.interval.ms narrows this gap at the cost of hitting the database harder, repeatedly, whether anything changed or not — a tradeoff that doesn’t exist for a hand-written producer, which fires exactly once per real insert and never has to ask “did anything change?” at all.

The Gap Polling Can’t Close: Deletes#

mode: incrementing only ever asks “what has a higher ID than last time?” — a deleted row doesn’t have a higher ID, it has no ID at all. Confirm this directly against real data instead of taking it on faith:

MySQL genuinely has one row left; Kafka still reports every message it has ever produced, including the one for a trip that no longer exists anywhere in the source of truth. This isn’t a misconfiguration — it’s what incrementing and timestamp modes fundamentally cannot see, because both work by asking the database “what’s new?” instead of “what changed?”

Change-Data-Capture: The Third Option, Already Half-Built Here#

Change-data-capture (CDC) tools read a database’s own replication log directly — the same stream a real replica database consumes — rather than repeatedly querying tables. Every insert, update, and delete appears as an event, with no polling delay and no missed deletes, because CDC isn’t asking the database anything; it’s reading what the database already recorded happening.

This course’s own MySQL container is already configured for it:

Binary logging is genuinely enabled — real infrastructure a tool like Debezium (a CDC connector for Kafka Connect, not installed in this course) would read directly. This module doesn’t deploy it — polling-based JDBC connectors are the more approachable starting point, and every gap this lesson just measured is worth understanding on its own before reaching for a more complex tool that fixes them. But the option isn’t hypothetical: the replication log this course’s docker-compose.yml already turns on is exactly what a real CDC deployment would consume.

A Genuine Decision Framework#

JDBC Source ConnectorHand-Written Producer
Setup effortConfiguration onlyCode, tests, deployment
LatencyBounded by poll.interval.ms — secondsImmediate — milliseconds
Sees deletesNo (incrementing/timestamp) — needs CDCOnly if the application code explicitly emits one
Complex transformationsLimited to what SMTs supportAnything the language can express
Standard integrations (DB, search, cloud storage)A configured connector often already existsReinventing a well-solved problem
Operational maintenanceAn ops team edits JSON configA dev team owns and redeploys code

Neither column is the universal right answer. CityFlow’s trips table, append-only and simply shaped, is exactly Connect’s strong case — Lesson 2 and 3 built that pipeline in configuration, correctly, without a single custom class. A pipeline that needs to react to a delete, apply business logic no standard transform expresses, or guarantee sub-second latency is exactly where this course’s Modules 1 through 6 — hand-written, in full control — remain the right tool, not a fallback for when Connect “doesn’t work.”

Practice Exercises#

Exercise 1: Measure the latency gap at a smaller poll interval#

Rerun this lesson’s latency measurement with poll.interval.ms set to 500 instead of 5000. How much does the gap close, and what does the JDBC connector have to do more often to achieve that?

Exercise 2: Design a hybrid#

Sketch (in comments, no code required) how CityFlow might use both: Connect for the accounts and fare-schedule tables that rarely change and never get deleted, and a hand-written producer for wherever cancellations — a genuine delete — need to be reflected immediately.

Hint

The real decision variable across both exercises is the same: does the downstream system need to know about deletes and changes, or only ever-growing inserts?

Summary#

A JDBC source connector took just over 10 seconds to move one row into Kafka against a hand-written producer’s 0.17 — a measured ~60x gap, not a documented estimate. A deleted MySQL row never disappeared from Kafka at all under incrementing mode — confirmed directly, not assumed from how the mode is documented to work. This course’s own MySQL database already runs with binary logging enabled, real infrastructure a CDC tool like Debezium would use to close both gaps at once — not deployed here, but genuinely available, not hypothetical. Kafka Connect and hand-written code solve different problems well; the right choice depends on what CityFlow’s own data does, checked against a working framework instead of a slogan.

Key Concepts#

  • Polling-based source connectors have bounded, measurable latency — just over 10s at a 5-second poll interval, confirmed directly.
  • incrementing and timestamp modes cannot see deletes — proven with a row that vanished from MySQL and never left Kafka.
  • Change-data-capture reads the replication log directly, seeing every change with no polling delay — this course’s MySQL is already configured for it.
  • The right tool depends on the data’s shape and the pipeline’s requirements — not a blanket preference for configuration over code, or the reverse.

Why This Matters#
