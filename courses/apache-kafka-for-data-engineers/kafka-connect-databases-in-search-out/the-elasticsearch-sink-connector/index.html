Welcome to the Elasticsearch Sink Connector#

Lesson 2 moved data into Kafka. This lesson moves it back out — a sink connector reading cityflow-mysql-trips and writing every record into Elasticsearch, ending with an index CityFlow’s own support team could actually query.

By the end of this lesson, you will be able to:

  • Configure an Elasticsearch sink connector against a real Kafka topic
  • Diagnose a real connector failure from its task status and stack trace
  • Fix a missing-key failure using a source-side transform
  • Prove an index is genuinely searchable, not just populated

A Sink Connector, and an Immediate Real Failure#

CityFlow’s five trips, sourced the same way Lesson 2 built — but without the fix this lesson is about to need:

key.ignore: false tells the sink connector to use each Kafka message’s key as the Elasticsearch document’s _id — and every message this source connector has produced has a null key, since nothing in Lesson 2’s configuration ever set one. The task fails outright rather than silently generating IDs or dropping records — a real, deliberate design choice, not a bug: a sink connector inventing IDs on its own would make every re-run produce duplicate documents instead of safely overwriting the same ones.

The Fix: Promote trip_id Into the Message Key#

A transform modifies a record as it passes through a connector, before it’s written. Two chained here turn the value’s trip_id field into the actual Kafka message key:

Every message now carries trip_id as its actual Kafka key — a change made on the source side, so it applies no matter how many different sinks eventually read this topic, not just the Elasticsearch one this lesson is building.

The Sink, Redeployed — and a Real Range Query#

Document _id=3 matches trip_id=3 exactly, because the transform’s key became the document ID Elasticsearch actually uses. The range query returns precisely trips 3 and 5 — fare_amount of 32.00 and 22.10, the only two above 20 — a real numeric comparison Elasticsearch could only run because Lesson 2’s value.converter.decimal.format=NUMERIC fix made fare_amount an actual number instead of a base64 string nothing could meaningfully compare.

Why the Key Matters: Updates Overwrite, They Don’t Duplicate#

The point of using trip_id as the document ID isn’t just to fix the crash — it’s what makes a second message for the same trip safe. Produce an updated version of trip 3 directly, same key, changed fare:

Still five documents, not six — Elasticsearch’s own _version field jumped to 2, showing this was an update to the existing document, not a new one. This is the real payoff of a stable document ID: CityFlow can re-send a trip as many times as an upstream process needs to — a retry, a correction, a timestamp-mode connector re-reading a genuinely modified row — and the index always converges on the latest value for that trip instead of accumulating duplicates. key.ignore: true would have generated a new random ID for every message, turning every re-send into a phantom extra document.

This is the same idempotency concern Module 6 built an entire lesson around, just showing up in a different system: Lesson 3 of that module measured a non-idempotent Kafka producer landing hundreds of duplicate messages under retry, fixed by giving the broker something stable to recognize a repeat by. Elasticsearch’s _id-based indexing is that identical idea, one hop further downstream — a sink connector re-delivering the same record after a worker restart, a rebalance, or an at-least-once redelivery converges on one document instead of drifting into duplicates, precisely because the ID is derived from trip_id and not left to chance.

Practice Exercises#

Exercise 1: Prove re-syncing doesn’t duplicate documents#

Stop the source connector, reset its offsets, and let it re-read all five rows from scratch while the sink connector keeps running. Does the document count in Elasticsearch stay at 5, or does it double? What does key.ignore: false guarantee here that key.ignore: true would not?

Exercise 2: Query by a field the range query didn’t use#

Run a term query against pickup_zone for a specific zone code from this lesson’s data. Does it return the expected trip? What does this prove about every field in the document, not just fare_amount?

Hint

schema.ignore=true means every field in the JSON value became a queryable document field automatically – nothing needed to be declared in Elasticsearch ahead of time.

Summary#

An Elasticsearch sink connector failed immediately against keyless messages with a specific DataException — not a vague error, a precise statement of exactly what was missing. A source-side transform fixed it by promoting trip_id into the actual Kafka message key, and the redeployed sink connector produced five documents whose IDs match those keys exactly. A range query against fare_amount returned exactly the two trips that qualify, proving the index is genuinely searchable — and proving it specifically because Lesson 2’s decimal fix made that field an actual number in the first place.

Key Concepts#

  • key.ignore: false uses the Kafka message key as the Elasticsearch document ID — a null key fails the task outright rather than silently generating one.
  • A transform modifies a record before it’s written — ValueToKey plus ExtractField$Key promotes a value field into the actual message key.
  • Setting the key on the source side benefits every downstream sink, not just the one that needed it first.
  • A searchable index needs correctly-typed fields — this lesson’s numeric range query only works because Lesson 2 fixed fare_amount’s encoding first.

Why This Matters#

CityFlow now has a real, working MySQL-to-Kafka-to-Elasticsearch pipeline, built entirely from configuration. Lesson 4 steps back and asks the harder question directly: when does this approach actually beat a hand-written producer or consumer, and when doesn’t it?
