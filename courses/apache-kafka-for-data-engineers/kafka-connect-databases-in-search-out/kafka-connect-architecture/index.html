Welcome to Kafka Connect#

Every producer and consumer this course has written since Module 1 was Python, run as a script the reader controlled directly. This module introduces something structurally different: a long-running service that moves data in and out of Kafka based on configuration, not custom code. This lesson brings that service up and moves live data through it before explaining a single term.

By the end of this lesson, you will be able to:

  • Start a Kafka Connect worker and confirm it’s running
  • Explain what a worker, a connector, and a task each are, concretely
  • Distinguish a source connector from a sink connector
  • Move MySQL rows into a Kafka topic with zero producer code

Bringing Up the Pipeline#

Kafka Connect, MySQL, and Elasticsearch all run behind Docker Compose’s pipeline profile — off by default, since not every module needs them:

That kafka_cluster_id is the identical cluster ID every earlier module’s brokers report — Connect isn’t a separate system with its own opinion about what cluster it belongs to; it’s a client of the exact same 3-broker cluster, just one built to run connectors instead of custom scripts.

Workers, Connectors, and Tasks#

A worker is the Connect process itself — the kafka-connect container, one JVM, listening on port 8083. This course runs it in distributed mode, the same mode a real production deployment uses: workers coordinate through a group.id (kafka-connect-cluster, set in .kafka-local/connect/start-connect.sh) and store their state in Kafka itself, not on local disk:

_connect-configs holds every connector’s configuration, _connect-offsets tracks how far each connector has progressed (a JDBC source connector’s last-read row ID, for instance), and _connect-status tracks whether each connector and task is running, paused, or failed. A worker restarting reads all three back from Kafka and resumes exactly where it left off — the same durability this course has relied on for every topic since Module 1, now backing the framework itself.

A connector is one configured integration — “read this MySQL table” or “write to this Elasticsearch index.” A connector doesn’t move data directly; it splits the work into one or more tasks, the units a worker actually schedules and runs, so a connector reading ten tables can parallelize across ten tasks on the same or different workers. This lesson’s connector runs with tasks.max: 1, one task, since one small table doesn’t need to be split.

Source vs. Sink#

Every connector is one of exactly two kinds:

  • Source connectors read from an external system and write into Kafka — a database, a filesystem, an API. Lesson 2’s JDBC source connector is this kind.
  • Sink connectors read from Kafka and write to an external system. Lesson 3’s Elasticsearch connector is this kind.

Both directions use the identical worker, the identical REST API, and the identical internal topics — only the connector’s own connector.class and configuration determine which direction data actually flows.

Converters: How a Row Becomes JSON Bytes#

A converter is what turns Connect’s internal, structured record into the bytes that actually land on a topic — the same job value_serializer does for KafkaProducer, just configured once at the worker level instead of once per script. This course’s worker (.kafka-local/connect/start-connect.sh) sets both key.converter and value.converter to JsonConverter, with schemas.enable=false — plain JSON, no wrapper, matching every message this course has produced by hand since Module 1.

Flip that one setting and the same three rows look very different on the wire:

Every single message now carries its own full schema, inline, repeated on every record — exactly the cost Module 7 Lesson 2 measured Avro avoiding, except here there’s no registry to swap the repeated schema for a 4-byte ID. Connect also ships an AvroConverter that talks directly to the real Schema Registry Module 7 already stood up, giving connectors the identical compact, registry-backed encoding this course’s own producers use — this module keeps converters at schemas.enable=false deliberately, so the JSON on the wire stays easy to read while everything else about Connect is new.

Three rows in a real MySQL table, moved into a real Kafka topic by JSON configuration alone:

The very first version of this lesson skipped that step and every write failed silently with UNKNOWN_TOPIC_OR_PARTITION in the worker’s logs — the identical failure mode this course has already met, now showing up inside a framework instead of a script.

Practice Exercises#

Exercise 1: Watch the connector recover from a bad config#

Register a second connector pointing connection.url at a database that doesn’t exist (jdbc:mysql://cityflow-mysql:3306/does_not_exist). Check its status. Does the connector itself fail, or does only the task fail? What does the trace field in the task’s status contain?

Exercise 2: Split the work across more tasks#

Create a second small table and add it to table.whitelist alongside the first, with tasks.max raised to 2. Check GET /connectors/{name}/status again — does Connect actually assign one task per table, or does it decide differently?

Hint

JdbcSourceConnector assigns roughly one task per table when tasks.max allows it, but the exact split is the connector’s own decision, not a guarantee – check the real tasks list rather than assuming.

Summary#

A real Kafka Connect worker, running in distributed mode against the identical 3-broker cluster every earlier module has used, moved three MySQL rows onto a Kafka topic through nothing but a REST POST — no KafkaProducer, no polling loop, no manual offset tracking. A connector splits its work into tasks that a worker schedules and runs; state for all of it lives in three Kafka topics, not on local disk. The one real gotcha this cluster forces on every producer — auto.create.topics.enable=false — applies to Connect’s own internal producer exactly the same way it applies to hand-written code.

Key Concepts#

  • A worker is the Connect process — this course runs one, in distributed mode, coordinating through Kafka itself.
  • A connector configures one integration; tasks do the actual work — a connector can split into multiple tasks for parallelism.
  • Source connectors write into Kafka; sink connectors read from it — every connector is exactly one of the two.
  • auto.create.topics.enable=false applies to Connect too — create the target topic explicitly before starting a connector, or every write fails silently.

Why This Matters#

Lesson 2 builds a real JDBC source connector against CityFlow’s own schema, not a throwaway table — everything this lesson proved about workers, tasks, and topic creation applies directly, just aimed at data that matters.
