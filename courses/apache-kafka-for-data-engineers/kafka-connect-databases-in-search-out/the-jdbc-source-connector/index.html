Welcome to the JDBC Source Connector#

Lesson 1 proved Connect can move data with configuration alone, using a throwaway table. This lesson builds the genuine article: a JDBC source connector against CityFlow’s own trip data, configured properly, including a gotcha this lesson actually hit and fixed rather than avoided by picking a cleaner example.

By the end of this lesson, you will be able to:

  • Configure a JDBC source connector’s incremental mode correctly
  • Explain what incrementing, bulk, and timestamp modes each actually do
  • Recognize and fix Kafka Connect’s default base64 decimal encoding
  • Prove incremental mode only ever ships new rows, never a full re-scan

Want more depth on the database side? The SQL & Databases course covers relational database design, querying, and Python integration in full — this lesson uses MySQL specifically, where that course focuses on PostgreSQL, but the JDBC concepts here transfer directly.

CityFlow’s Trips Table, and a First Connector#

Five real trip rows, the same shape TripEvent has used since Module 2 — minus a schema, since this table lives in MySQL, not Kafka:

mode: incrementing is the mode built for exactly this shape of table: trip_id only ever goes up, so the connector can remember the highest ID it’s already read and ask for only what’s newer next time — no timestamp column required, no re-reading rows that haven’t changed.

A Real Gotcha: fare_amount Comes Out Base64-Encoded#

Read the topic back with a plain consumer:

"Bzo=" is not corrupted data — it’s 18.50, correctly encoded as base64 bytes representing Kafka Connect’s internal Decimal logical type. MySQL’s DECIMAL(10,2) maps to that logical type by default, and Lesson 1’s JsonConverter with schemas.enable=false has no schema available to say “this base64 blob means a decimal” — it just emits the raw bytes as a base64 string, technically correct and completely unreadable. This is a real, well-known Kafka Connect default, not a bug this lesson introduced to make a point.

The Fix: value.converter.decimal.format=NUMERIC#

The first thing worth trying — numeric.mapping: best_fit, a JDBC-connector-specific setting for unbounded NUMERIC columns — does not fix this, confirmed directly against this exact connector before reaching for the setting that does. DECIMAL(10,2) has a fixed, known precision and scale, so the connector keeps using the Decimal logical type regardless; the actual fix lives in the converter itself:

Two things confirmed at once, in a single result. First, incremental mode: inserting trips 6 and 7 produced exactly two new messages, not a re-read of all seven — the connector remembered trip_id=5 as its last position and asked MySQL for only what came after it. Second, the fix: trips 6 and 7 show fare_amount as a plain, readable number, while trips 1 through 5 — already written to the topic before the config changed — stay exactly as they were. A converter fix changes how new messages get encoded; it doesn’t rewrite what’s already on disk, the identical lesson Module 7’s schema evolution taught about data already committed to a topic.

Validating a Config Before It Ever Deploys#

Connect exposes a validation endpoint that checks a connector config for real, specific problems without actually creating anything — worth reaching for before POST /connectors, not after a failed deploy:

A specific, actionable message naming the exact missing field — the same class of precise error Module 7’s Schema Registry gave for an incompatible schema, this time for a connector config instead. Running every new connector config through /config/validate first catches exactly this kind of real, easy-to-make mistake before it becomes a connector stuck in a failed state on a running worker.

The Three Modes, Briefly#

  • incrementing: tracks a strictly increasing column (trip_id here). Simple, reliable, but blind to updates — a row that changes after being read never gets re-sent.
  • timestamp: tracks a “last modified” column instead, so updates get picked up, not just inserts. Needs a reliable, indexed timestamp column that’s actually updated on every write.
  • bulk: re-reads the entire table on every poll, no tracking column needed at all — simplest to configure, and the most expensive by far on anything but a small, slow-changing table.

CityFlow’s trips table only ever gets new rows appended, never edited in place, so incrementing is the correct, cheapest choice — the same kind of mode-to-data-shape matching Module 5 taught for acks and Module 6 taught for delivery guarantees, applied here to a connector’s read strategy instead.

Practice Exercises#

Exercise 1: Try timestamp mode#

Add an updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP column to trips, reconfigure the connector with mode: timestamp and timestamp.column.name: updated_at, then UPDATE an existing row’s fare_amount. Does the updated row get re-sent to Kafka? Would incrementing mode have caught that change?

Exercise 2: Measure bulk mode’s real cost#

Reconfigure the connector to mode: bulk against the same table and watch the topic for two full poll intervals. How many total messages land, and how does that number relate to the table’s row count and the number of polls?

Hint

bulk mode’s message count should be exactly (row count) x (number of polls that ran) – if it isn’t, something about the poll timing assumption is off, not the mode itself.

Summary#

A JDBC source connector, configured with mode: incrementing against a strictly increasing trip_id, moved CityFlow’s trip rows into Kafka — and its default decimal encoding turned fare_amount into an unreadable base64 string, a genuine Kafka Connect behavior fixed with one specific converter setting, value.converter.decimal.format=NUMERIC, not the more obvious-looking numeric.mapping setting that doesn’t actually touch it. Two rows inserted after the fix proved both incremental mode’s actual behavior — only new rows ship, never a full re-scan — and the converter fix’s exact scope — it changes future encoding, never past messages.

Key Concepts#

  • mode: incrementing tracks a strictly increasing column and asks for only what’s newer each poll — proven directly, not assumed.
  • Kafka Connect’s default Decimal logical type encodes as base64 under a schema-less JSON converter — a real default, not a bug.
  • value.converter.decimal.format=NUMERIC is the actual fix — numeric.mapping looked plausible and didn’t work.
  • A converter change never rewrites already-written messages — only new writes reflect it, the same principle Module 7 proved for schema changes.

Why This Matters#

Lesson 3 moves to the other end of the pipeline: an Elasticsearch sink connector reading this exact topic and writing every trip into a real, queryable search index — the base64-vs-numeric distinction this lesson just fixed will matter again the moment a document needs to be range-queried by fare amount.
