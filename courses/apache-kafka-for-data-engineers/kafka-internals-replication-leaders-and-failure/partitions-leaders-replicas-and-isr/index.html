Welcome to Leaders, Replicas, and ISR#

Module 2 introduced Leader, Replicas, and Isr as columns in kafka-topics.sh --describe output, enough to explain why more partitions spread work across more brokers. This lesson slows down on exactly what those three columns mean relative to each other, and proves the distinction that matters most for Module 6’s reliability settings: Replicas and Isr are not the same list, and the gap between them is where a real broker failure actually shows up.

By the end of this lesson, you will be able to:

  • Define leader, replica, and in-sync replica precisely, not just by column name
  • Explain why Replicas never changes but Isr can shrink at any moment
  • Watch ISR shrink by stopping one real broker, and recover when it returns
  • Read the min.insync.replicas setting as the number the ISR must never drop below

Three Columns, Three Different Guarantees#

A fresh, healthy topic — four partitions, replication factor 3:

Three different questions, three different answers:

  • Leader — the one broker every produce and fetch request for this partition actually talks to right now. Partition 0’s leader is broker 3; every write and every read for partition 0 goes through it, and only it.
  • Replicas — the fixed, assigned set of brokers that should hold a copy of this partition, decided when the topic was created (or altered) and unchanged until an administrator explicitly reassigns it. Partition 0’s replica set, 3,1,2, doesn’t change just because one of those brokers goes offline.
  • Isr — “in-sync replicas”: the subset of Replicas that are, right now, caught up closely enough to be trusted for acks='all' durability. On a healthy cluster Isr equals Replicas, exactly what this output shows — every replica is caught up, so the two lists match.

Elr and LastKnownElr are empty here — a newer safety mechanism (eligible leader replicas, for a narrower unclean-recovery scenario) that this course’s clusters never trigger under normal operation, worth knowing the columns exist without needing their full mechanics for what this module builds.

Watching Isr Actually Shrink#

Replicas and Isr matching is the healthy case, not a guarantee. Stop one real broker and describe the same topic again:

Look at what changed and what didn’t. Replicas is untouched on every partition — 3,1,2 for partition 0 still lists broker 3, because the assignment hasn’t changed, only broker 3’s availability. Isr dropped broker 3 everywhere it appeared, shrinking from three members to two on every partition. And exactly one leader changed: partition 0, which broker 3 was leading, moved to broker 1 — the other three partitions kept their existing leaders because broker 3 wasn’t leading them in the first place, only replicating.

Restart the stopped broker, and the story reverses on the replication side, but not on leadership:

Isr is back to three members on every partition — broker 3 caught up and rejoined. Leader for partition 0, though, stayed on broker 1. Rejoining the in-sync replica set and reclaiming leadership are two separate things, exactly the same distinction Lesson 1 found for the controller itself: coming back healthy earns a broker its way back into the ISR automatically, but not automatically back into leadership.

How Fast Does Catching Up Actually Take?#

Rejoining Isr isn’t instant in principle — a broker that missed writes while it was down has real data to fetch before it’s caught up enough to be trusted again. Measure it directly: produce 500 messages, stop broker 3, produce 2,000 more while it’s down, then restart it and check kafka-log-dirs.sh’s offsetLag — the exact metric a broker uses internally to know how far behind a partition still is:

offsetLag: 0 on every partition, checked moments after broker 3 restarted — 2,500 messages’ worth of catch-up, on this local cluster, finished faster than the time it took to run the check. That’s not a guarantee this course can make about every cluster (a genuinely large backlog, a slow network, or a much bigger message volume would show a real non-zero lag during the window Kafka calls a replica “catching up”), but it’s the honest, measured result here: for CityFlow’s data volumes, ISR recovery isn’t a slow process to plan around, it’s a fast one to trust.

min.insync.replicas: The Number Isr Must Never Drop Below#

cityflow-isr-check was created with min.insync.replicas=2. That number is a promise, not a description: with acks='all' (Module 3 Lesson 3), a produce request only succeeds once every member of the current Isr has the write — and if Isr ever shrinks below min.insync.replicas, the broker refuses new acks='all' writes outright rather than accept one with a weaker guarantee than promised. Losing one broker out of three, dropping Isr from 3 to 2, still satisfies min.insync.replicas=2 — writes kept succeeding through the outage this lesson just ran. Losing a second broker at the same time would not: Lesson 3 traces exactly what a produce request does at each step, including what happens the moment Isr drops below what min.insync.replicas requires.

Practice Exercises#

Exercise 1: Stop a different broker and predict the result first#

Before running anything, predict which partitions’ Isr will shrink and which partition’s Leader will change if you stop kafka1 instead of kafka3 (use cityflow-isr-check’s Replicas and Leader columns from this lesson’s first --describe output to work it out). Then run it and check your prediction against the real output.

Exercise 2: Confirm Replicas order isn’t the current leader#

Pick any partition from this lesson’s own output where the leader is not the first broker listed in Replicas — partition 0, Replicas: 3,1,2 but Leader: 1, is one. Explain in one sentence why the first-listed replica being the “preferred” leader doesn’t mean it’s necessarily the current one, given what this lesson already showed about leadership not moving back automatically after a broker recovers.

Hint

A resize, a restart, or a rebalance can all leave the current leader different from the preferred one — Replicas’ order records a preference, not a live fact. Lesson 4’s hands-on lab covers the tool that manually restores it.

Summary#

Three columns, three different guarantees, proven directly rather than assumed: Leader is the one broker actually serving a partition’s traffic right now, Replicas is the fixed assignment of brokers that should hold a copy, and Isr is the live, honestly-reported subset of Replicas currently caught up enough to trust. Stopping one real broker shrank Isr from three to two on every partition it touched, while Replicas stayed exactly the same — and moved leadership only for the one partition that broker was actually leading. Restarting it restored Isr fully but left leadership wherever it had already moved, the same “rejoin, but don’t automatically reclaim” behavior Lesson 1 found for the controller itself.

Key Concepts#

  • Leader, Replicas, and Isr answer three different questions — who serves traffic now, who’s assigned to hold a copy, and who’s actually caught up.
  • Replicas is a fixed assignment; Isr is live and can shrink instantly — confirmed by stopping one broker and watching only Isr change.
  • A broker rejoining restores its ISR membership, not its leadership — the same asymmetry the controller itself showed in Lesson 1.
  • min.insync.replicas is the floor Isr must not cross for acks='all' writes to keep succeeding — Lesson 3 traces exactly what happens when it does.

Why This Matters#

Module 6’s reliability settings — acks, min.insync.replicas, unclean.leader.election.enable — are all decisions about this exact gap between Replicas and Isr. Nothing in that module will make sense as anything but memorized flags without having watched the gap open and close on a real cluster first, which is precisely what this lesson just did. This module’s own hands-on lab and guided project (Lessons 4 and 5) build directly on today’s finding too: offsetLag and Isr membership are exactly what a real recovery script would check to confirm a stopped broker is genuinely safe to trust again, not just running.
