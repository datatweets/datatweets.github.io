Welcome to the Guided Project#

This project ties the whole module together by walking you through the cycle that defines confident, everyday Git use: clean up, then oops, then rescue. You will do it in two parts, each a self-contained scenario you can run on your own machine.

In Part 1, you’ll inherit a messy feature branch — the kind every developer produces while working: a string of wip commits and a last-minute typo fix. You’ll use interactive rebase to squash that noise into a single, clearly-named commit that’s ready to share. In Part 2, you’ll engineer a small disaster. You’ll git reset --hard away two good commits as if you’d mistyped the command, watch them seemingly vanish, and then use git reflog to find them again and bring them back. Together these two skills are the safety net under all the history-rewriting you learned this module.

By the end of this project, you will be able to:

  • Squash several messy wip commits into one clean commit with interactive rebase
  • Write a meaningful combined commit message during a squash
  • Recognize that git reset --hard doesn’t truly delete your commits right away
  • Use git reflog to find and recover commits you thought were lost

A quick note before you begin: as in the earlier lessons, the commit hashes below come from a verified run, and yours will differ — Git derives them from your content, author, and timestamp. Match on the messages and the shape of the output, not the exact characters.

Let’s build.

Part 1 — Inspect the Messy Branch#

Picture a feature branch where you’ve been building a small URL-slug helper in slugify.py. You committed early and often, which is good practice — but the names are throwaway:

The bottom commit, Add text utils, is a reasonable starting point. The three above it — wip, keep hacking, and fix trailing dash — are the trail of work-in-progress. Nobody reviewing your code needs to see “keep hacking” as a separate moment in history. Those three commits represent one logical change: building the helper. Your goal is to fold them into a single commit with a name that explains the what and why, not the when.

You want to reshape the top three commits, so you’ll rebase the last three interactively.

To merge them, you keep the first as pick and change the other two to squash — that tells Git to fold each one into the commit above it:

Save and close the file. Git now opens a second editor holding all three original messages stacked together, so you can write the message for the single combined commit. Delete the throwaway lines and write something a reviewer would thank you for:

Save that, and the three commits collapse into one:

The history is now clean: a clear feat: add slugify helper commit sitting on top of your starting point, with all the messy intermediate steps gone. This is exactly the branch you’d want to open a pull request from. Notice the new commit has a brand-new hash (778c719 here) — squashing is a form of rewriting history, so it produces a fresh commit. That’s safe because you only did it to local, un-pushed work.

Part 2 — Engineer the Disaster#

Now switch scenarios. Imagine a different small repo — a data-analysis writeup in analysis.md — where you’ve made three commits of careful work:

  • Add analysis outline (the starting point)
  • Add cleaning step
  • Add summary stats

You meant to run a harmless command, but instead you typed git reset --hard HEAD~2 — moving your branch back two commits and discarding everything since. Here’s the moment it happens:

It looks like a catastrophe. git log shows only Add analysis outline. The Add cleaning step and Add summary stats commits are gone from the log entirely — as if an hour of effort just evaporated. This is the exact disaster that makes people fear git reset --hard.

Here’s the good news: those commits are not actually deleted. reset only moved your branch pointer; the commits themselves are still sitting in the repository, unreferenced, waiting to be found.

Part 2 — Recover With Reflog#

The tool that saves you is git reflog. While the ordinary log only shows commits reachable from where your branch currently points, the reflog records every place HEAD has been — including the commits you just reset away. Run it:

There they are. HEAD@{0} is the reset you just did. But HEAD@{1} — commit fdcbc6d, “Add summary stats” — is the exact tip your branch had before the reset. That’s the commit you want back, and recovering it brings Add cleaning step along too, since it’s that commit’s parent.

To recover, point your branch back at the lost commit with another reset --hard — this time using the hash from the reflog:

All three commits are back exactly as they were. The “disaster” is undone. Note that fdcbc6d is the hash from this verified run — in your own repo you’d copy whatever hash the reflog shows on the HEAD@{1} line.

The everyday rhythm of confident Git

These two skills together are the heartbeat of fearless Git use: shape your history deliberately, and know you can always recover. Interactive rebase lets you polish messy work into something clear before you share it, and the reflog means a wrong reset or a botched rebase is almost never fatal — Git remembers where you’ve been. Two reminders, though. Only rebase local, un-pushed commits, since rewriting shared history breaks everyone who built on it. And the reflog is a local safety net that expires over time (entries are pruned after about 90 days by default), so it rescues recent mistakes, not ancient ones.

Practice Exercises#

Each exercise pushes one of the two skills a little further. Work through the steps before opening the hint.

Exercise 1: Predict the reword result#

You start git rebase -i HEAD~3 on a three-commit branch and change only the middle line from pick to reword, leaving the other two as pick.

  • Predict how many editor windows Git opens after you save the todo list, and what each one is for.
  • Predict which of the three commits end up with new hashes, and which keep their old ones.
  • Run it and check both predictions against git log --oneline before and after.

Hint

Only one extra editor opens — the message editor for the reworded commit. The commit below the reworded one (older) keeps its hash; the reworded commit and every commit above it (newer) get new hashes, because a rebase replays them and their parent chain changed.

Exercise 2: Debug a broken squash#

A teammate wanted one clean commit and no debug commit, but their squash produced a final commit with two messages stacked in its body and a stray leftover debug print commit still present. Here is the todo list they saved:

  • Identify the two lines that are wrong and say what each one should be instead.
  • Explain why squash on line 2 produced the stacked message.
  • Write the corrected todo list that yields one commit with a single message and no debug commit.

Hint

Line 2 should be fixup, not squash — fixup folds the change in but discards that commit’s message, so nothing gets stacked. Line 3 should be drop (or the line deleted), so the debug commit is removed instead of kept. The fixed list is pick / fixup / drop.

Exercise 3: Recover from a bad rebase#

Do an interactive rebase that goes wrong on purpose, then use the reflog to undo the entire rebase and get your original branch back.

  • Make a branch with three or four commits and start git rebase -i across them.
  • In the todo list, drop a commit you know you still need, then save.
  • Run git reflog and find the entry from just before the rebase started.
  • git reset --hard back to that hash, then confirm with git log that the dropped commit has returned.

Hint

In the reflog, look for the entry just before the rebase lines — it often reads rebase (start) or shows your branch tip from before. Reset to that hash with git reset --hard <hash>, exactly as you did in Part 2. The reflog records the pre-rebase state too, so a bad rebase is just as recoverable as a bad reset.

Summary#

In this project you ran the full clean-up-and-recover cycle on your own. Part 1 took a messy feature branch — wip, keep hacking, fix trailing dash — and used git rebase -i HEAD~3 with the squash action to fold three throwaway commits into a single, well-named feat: add slugify helper commit ready to share. Part 2 simulated the classic disaster: a git reset --hard HEAD~2 that appeared to destroy two good commits, followed by a rescue with git reflog — which revealed that HEAD@{1} still pointed at the lost work, letting you git reset --hard straight back to it. Polish, oops, rescue: that’s the loop you’ll run for the rest of your career.

Key Concepts#

  • Interactive rebase (git rebase -i) — reshape your recent local commits; squash folds several into one.
  • Combined commit message — during a squash, Git lets you write one clear message for the merged commit.
  • git reset --hard — moves your branch pointer and discards changes, but doesn’t immediately delete the underlying commits.
  • git reflog — a local record of everywhere HEAD has been; the tool for finding and recovering “lost” commits.

Why This Matters#

Messy local history and the occasional catastrophic command are facts of everyday development — not signs you’re doing it wrong. What separates a confident developer from an anxious one is knowing that both are fixable: you can always polish your commits before sharing, and you can almost always recover work you thought was gone. Once reflog is in your toolkit, git reset --hard and interactive rebase stop being scary and become exactly what they are — powerful, routine tools. That confidence is the outcome of this module.

Continue Building Your Skills#

You’ve now done the complete cycle hands-on: you can take a tangle of wip commits and turn it into history a reviewer will appreciate, and you can rescue good work from an accidental reset --hard using the reflog. With deliberate rewriting and reliable recovery both under your belt, you’re ready to move beyond your own machine and let GitHub do work for you — automating checks, protecting branches, and publishing — in Module 8.
