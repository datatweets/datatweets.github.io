Welcome to the Guided Project#

Every tool this module built comes together here: group_by().agg() for per-customer totals, .rank() for overall standing, and .over() for a percent-of-segment figure – combined into one customer_report() function, run once against all 180 Thistlewood customers, and checked against the module’s own $9,195,043.62 grand total.

By the end of this lesson, you will be able to:

  • Combine group_by().agg(), .rank(), and .over() into one complete reporting function
  • Build an overall rank and a within-segment percentage in the same pipeline
  • Verify a multi-part report against more than one independently-known number
  • Recognize a business insight a combined report can surface that a single aggregation can’t

The Complete Report Function#

Three tools, one function: group_by("customer_id").agg(...) collapses line items down to one row per customer (total_spend, n_orders); .rank(method="ordinal", descending=True) gives each customer a distinct overall standing by spend; .over("segment") broadcasts each segment’s total spend back onto every customer in it, so pct_of_segment can be computed without a second, separate query.

Running the Report#

All 180 Thistlewood customers, one row each. Thistlewood’s #1 customer by spend: C0030, Grace Thatcher, $85,748.78 across 43 orders – edging out C0118, Isabella Holloway (this module’s own 49-order tie-leader from Lesson 5), who ranks 3rd overall by total spend despite placing more orders. Order count and total spend track together, but they’re not the same ranking.

Correctness Proof: The Grand Total, Again#

The report’s 180 total_spend values have to sum back to the same $9,195,043.62 grand total this module established in Lesson 1 – a report that drops or double-counts a customer would fail this check:

The $9,195,043.62 grand total matches exactly – the fourth time this module has independently reproduced that same number (Lesson 1’s channel and category breakdowns, Lesson 3’s completed/cancelled/pending split, and now this customer-level report). All 180 total_spend values are also distinct, unlike Lesson 5’s n_orders tie – so overall_rank here needed no tie-breaking decision at all.

Correctness Proof: Segment Percentages Sum to 100#

Verify the .over("segment") computation the same way Lesson 4 verified its category percentages – every segment’s pct_of_segment values should sum to 100%:

156 retail customers, $8,046,009.53 in spend; 24 wholesale customers, $1,149,034.09 – the two segment totals sum to the identical grand total, and each segment’s pct_of_segment values sum to exactly 100. Every check in this module, from Lesson 1’s channel breakdown through this final report, keeps landing on the same numbers, computed a different way each time.

A Business Insight the Combined Report Surfaces#

overall_rank alone would rank C0140, Aria Hensley, 8th out of 180 – unremarkable at a glance. pct_of_segment tells a sharper story:

C0140 is Thistlewood’s #1 wholesale customer – 6.33% of the entire $1,149,034.09 wholesale segment, a meaningfully concentrated share, even though overall_rank (measured against all 180 customers, retail included) only places her 8th. overall_rank alone would have buried this fact; pct_of_segment, computed by the same .over() this module built in Lesson 4, surfaces it directly.

Two rankings, two questions

overall_rank answers “how does this customer compare to every other Thistlewood customer, regardless of segment?” pct_of_segment answers a different question: “how large is this customer relative to others in their own category?” Both are correct; a report that only computed one would have missed the other story.

Practice Exercises#

Exercise 1: Add a segment rank#

Add pl.col("total_spend").rank(method="ordinal", descending=True).over("segment").alias("segment_rank") to customer_report(). Confirm C0140 gets segment_rank == 1 (Thistlewood’s top wholesale customer) despite an overall_rank of 8.

Exercise 2: Find the median spend per segment#

Using report, group_by("segment").agg(pl.col("total_spend").median().round(2).alias("median_spend")). Confirm the retail median is noticeably lower than the wholesale median, and explain in one sentence what that gap suggests about how the two segments buy.

Summary#

customer_report() combined group_by().agg(), .rank(), and .over() into one function, producing a complete performance row for all 180 Thistlewood customers: total_spend, n_orders, overall_rank, and pct_of_segment. The report’s 180 total_spend values summed to the exact $9,195,043.62 grand total this module established in Lesson 1 – the same number reproduced a fourth independent way – and every segment’s pct_of_segment values summed to exactly 100%. The combined report surfaced a genuine business insight a single aggregation would have missed: C0140 ranks only 8th overall, but is Thistlewood’s #1 wholesale customer at 6.33% of that segment’s total.

Key Concepts#

  • A complete report is usually several window/aggregation tools combined, not one – group_by().agg() for the base numbers, .rank() for standing, .over() for group-relative share, run together in one function.
  • A report’s total should still recombine to an independently-known number – this lesson’s $9,195,043.62 match, for the fourth time in this module, is that same discipline applied to a full report instead of a single query.
  • Overall rank and within-group share answer different questions – and a report that only computes one can hide an insight the other would surface.
  • No ties in total_spend made overall_rank unambiguous here – worth confirming explicitly (n_unique() == height) rather than assuming, especially after Lesson 5 found ties in a different column.

Why This Matters#

A customer performance report is exactly the kind of recurring business artifact this course has been building toward since Module 1: several aggregation and window tools, combined into one function, run against real data, and checked against independently-known numbers rather than trusted on sight. This module’s own $9,195,043.62 grand total, reproduced correctly across five structurally different queries – channel breakdown, category breakdown, conditional status split, category-level window percentages, and now a full per-customer report – is proof that group_by, conditional aggregation, and .over() all work together correctly, not just individually.
