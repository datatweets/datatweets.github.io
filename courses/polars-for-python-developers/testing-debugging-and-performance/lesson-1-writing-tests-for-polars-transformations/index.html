Welcome to Writing Tests for Polars Transformations#

Every guided project in this course has ended the same way: compute a result, then check it against a number you already trust. That check has always lived in a print() statement you read once and moved past. This lesson turns it into something that keeps checking for you – a pytest test suite for clean_orders(), the cleaning function Module 4 built and the capstone reused without changing a line.

By the end of this lesson, you will be able to:

  • Explain the difference between testing a transformation’s shape (row count, schema, dtypes) and its values (does a specific row end up correct)
  • Write plain assert-based pytest test functions against a Polars transformation
  • Run a pytest suite programmatically with pytest.main() and read its console output
  • Recognize what a passing test suite proves, and what it doesn’t

The Transformation Under Test#

clean_orders() takes thistlewood_orders_raw.csv – a 795-row export with three duplicated order_ids, nine null city values, six null email values, twelve non-ISO date strings, and five negative quantity/unit_price rows – and returns a cleaned 792-row table. Load it once here, the same way the capstone did:

A print() telling you the shape changed from 795 to 792 is exactly the kind of check this course has run since Module 1 – read once, trusted, and forgotten the moment the script ends. The rest of this lesson turns that one-off check into a suite that runs the same way every time, on every future change to clean_orders().

Testing Shape vs Testing Values#

Two questions sound similar but check different things. A shape test asks “does the result have the right structure” – row count, column count, dtypes, no unexpected nulls – without looking at any one value. A value test asks “is this specific piece of data correct” – did row X end up with the right number in it. A transformation can pass every shape test and still be wrong: dropping the wrong three duplicate rows would still leave 792 rows and no nulls, and every shape test above would pass regardless of which three got dropped.

O00473 is one of the nine rows with a null city in the raw file; clean_orders() recovers it by joining to thistlewood_customers.csv on customer_id. The shape check above would pass even if the join recovered the wrong customer’s city for that row – only checking the actual value catches that. A test suite needs both kinds of check, and neither one substitutes for the other.

Writing pytest Tests#

pytest collects any function named test_* in a file and runs each one, reporting assert failures with the exact values involved. Rather than describe what a test file “would” look like, build one as a string, write it to a temporary file, and run it with pytest.main() – the same programmatic entry point pytest itself uses when you run pytest from a shell, minus the shell:

That output is pytest’s own, not a simulation of it – seven tests ran against the actual clean_orders() output and every one passed, and pytest.main() returned 0, the same exit code a CI pipeline checks to decide whether a build is green. The temp file’s exact name varies run to run (tempfile.NamedTemporaryFile generates a random suffix), which is why the path above is shown trimmed to ...tmpXXXXXX_test.py – everything else in that block is exactly what running this code prints. os.remove(test_path) cleans the temp file up afterward, the same idempotent pattern Module 10 established for every file this course writes.

Why write the test file as a string

In a real project, clean_orders() would live in its own module (pipeline.py), and a test_clean_orders.py file next to it would simply from pipeline import clean_orders. This lesson writes the test file as a self-contained string, redefining clean_orders() inside it, because this course’s lessons are each one standalone script – there’s no separate pipeline.py to import from. The test-writing technique is identical either way: test_* functions with plain assert statements, run by pytest.

What a Passing Suite Proves – and Doesn’t#

Seven green tests is evidence clean_orders() behaves as expected on thistlewood_orders_raw.csv today. It is not proof the function is bug-free on data it hasn’t seen – a raw file with a duplicate order_id pattern this suite never checked, or a date format outside the three clean_orders() coalesces across, would still slip through untested. A test suite is only as good as the cases someone thought to write down; growing it as new edge cases turn up (the next section’s exercises ask you to add one) is part of the job, not a one-time setup step.

Practice Exercises#

Exercise 1: Add a test for the negative-value fix specifically#

The five known negative quantity/unit_price rows in thistlewood_orders_raw.csv aren’t just “non-negative in the output” – they should be the absolute value of what they were in the raw file. Write test_negative_values_become_their_absolute_value(): find a row in raw where quantity < 0, note its order_id, and assert that the same row in cleaned has quantity == abs(original_value).

Hint

raw.filter(pl.col("quantity") < 0).select("order_id", "quantity").head(1) finds one such row directly – then compare it to cleaned.filter(pl.col("order_id") == that_id)["quantity"][0].

Exercise 2: Write a test that should fail, and confirm it does#

Add a deliberately wrong test – assert cleaned.height == 999 – to the test source string and rerun pytest.main([test_path, "-v"]). Confirm the exit code is no longer 0 and that pytest’s output names the failing assertion and the actual vs. expected values. Remove the wrong test afterward.

Hint

pytest prints an assert 792 == 999 line (or similar) for a failed test, showing both sides of the comparison – that’s the detail a bare print() check never gave you.

Summary#

clean_orders(), Module 4’s cleaning function, got a seven-test pytest suite: five shape tests (row count, no duplicate order_ids, no nulls in city/email, non-negative quantity/unit_price, order_date as a Date dtype) and two value tests (O00473 recovers city “Missoula” from the customers table, O01005’s raw "07-Jan-2024" string parses to 2024-01-07). pytest.main() ran the suite from inside the lesson’s own script and printed pytest’s console output – seven tests, seven passes, exit code 0.

Key Concepts#

  • A shape test checks structure (row count, dtypes, null counts) without inspecting any single value – necessary but not sufficient on its own.
  • A value test checks that a specific row holds the specific correct data – the only kind of test that catches a transformation doing the wrong thing while still looking structurally fine.
  • pytest.main([path, "-v"]) runs a test file programmatically and returns an exit code (0 for all passed), the same mechanism a CI pipeline relies on.
  • A passing suite proves what it checked, not everything – test coverage is a running list of cases someone thought to write down, not a guarantee against every possible input.

Why This Matters#

Every guided project so far has verified a result once, by hand, and moved on. A test suite verifies it every time clean_orders() changes – add a fourth date format, fix a new edge case, refactor the join – without anyone having to remember to re-check the old cases by hand. That’s the payoff of testing a data transformation: not catching today’s bug, but catching tomorrow’s regression before it reaches a report someone trusts.
