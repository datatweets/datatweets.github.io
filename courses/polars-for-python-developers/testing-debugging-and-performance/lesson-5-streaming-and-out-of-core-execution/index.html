Welcome to Streaming and Out-of-Core Execution#

Every query this course has run so far assumes the data fits comfortably in memory – Thistlewood’s largest file, thistlewood_order_items.csv, is 14,054 rows, nowhere close to straining a laptop’s RAM. Streaming execution exists for the opposite situation: a dataset too large to load into memory all at once. This lesson explains what that mode buys you, confirms it produces identical results to ordinary in-memory execution, and measures plainly what happens when you reach for it on data that was never big enough to need it.

By the end of this lesson, you will be able to:

  • Explain what bounded, chunked execution means and why it matters for data larger than RAM
  • Run the same query with engine="streaming" and engine="in-memory", and confirm they agree exactly
  • Read a benchmark that shows streaming isn’t automatically faster, and explain why that’s the expected result at this data’s scale
  • Know where in collect()’s current API engine= fits, alongside optimizations=QueryOptFlags(...) from Module 10 Lesson 5

What Streaming Execution Buys You#

The default way Polars runs a .collect()ed query – engine="in-memory" – reads each source file’s needed columns into RAM in full, then processes them. That’s fast and simple, right up until a file (or the intermediate result of a join) is larger than the machine’s available memory, at which point “read it all into RAM first” isn’t an option at all. Streaming execution (engine="streaming") processes a query in bounded chunks – reading, filtering, and partially aggregating one piece of the data at a time, never holding the whole dataset in memory simultaneously. The trade is more processing steps and more coordination overhead in exchange for a memory ceiling that doesn’t grow with the input size.

The engine= Parameter#

Module 10 Lesson 5 already established collect()’s current signature directly from this installed version: engine= accepts "auto" (the default, which falls back to "in-memory"), "in-memory", "streaming", and "gpu" for CUDA hardware this course doesn’t use. There is no streaming=True parameter on this Polars version – engine="streaming" is its replacement.

engine= is orthogonal to everything Module 10 and Lesson 4 covered about query plans – scan_csv() vs read_csv(), partition pruning, predicate and projection pushdown, and optimizations=QueryOptFlags(...) all still apply exactly the same way regardless of which engine ultimately runs the plan. A query built the same way as every earlier lesson’s – pl.scan_*(), chained lazy operations, then .collect() – simply gets one more choice at the very last step: how the already-optimized plan gets executed. That separation is deliberate on Polars’ part: deciding what work a query needs to do (the plan) and deciding how to execute that work (the engine) are independent questions, which is exactly why swapping engine="in-memory" for engine="streaming" below changes nothing about the query’s structure or its .explain() output – only which engine carries the already-planned work out.

The same join, filter, and aggregation, run under two different execution modes, land on byte-identical numbers – .equals() confirms it directly rather than eyeballing two printed tables. That’s the first thing worth confirming any time you switch execution modes: correctness before anything else, the same discipline Lesson 3 applied to eager vs lazy.

Timing Both, Plainly#

Streaming’s whole purpose is a memory ceiling, not raw speed – but it’s worth checking rather than assuming. Time both engines on this same query, several runs each, the same method Lesson 3 used:

Streaming measured modestly slower here, not faster – 5.46ms against 4.47ms. That’s the expected result, not a disappointing one: thistlewood_order_items.csv and thistlewood_orders_timestamped.csv together are around 20,000 rows, comfortably inside memory on any machine running this course. Streaming’s chunked processing adds coordination overhead – splitting the work into pieces, tracking partial state across chunks – and on data this small, that overhead is pure cost with no memory-pressure problem to solve in exchange. The conclusion isn’t “streaming is slower than in-memory” as a general claim; it’s “streaming’s benefit is a memory ceiling that doesn’t apply until the data needs one, and this course’s data never reaches that point.”

This is worth sitting with, because it cuts against a natural assumption: many tutorials introduce streaming as the “big data” mode and leave the implication that it’s a strict upgrade, something you’d reach for by default once you know it exists. The measurement above says otherwise for anything at Thistlewood’s scale. That doesn’t make streaming a niche feature – production pipelines that read from cloud object storage or aggregate logs spanning hundreds of gigabytes rely on it precisely because engine="in-memory" isn’t an option there at all. It does mean the decision to use it should follow from the data’s actual size, not from a rule of thumb that bigger-sounding tools are always the safer default.

When streaming pays off

Streaming’s value shows up on data too large to fit in RAM at all – a source file that’s tens of gigabytes, or an intermediate join result that would exhaust memory if materialized in full. Thistlewood’s data, at roughly 20,000 rows across the files this lesson uses, never approaches that threshold, so this lesson can’t demonstrate a dramatic streaming win. What it can demonstrate, and did, is that engine="streaming" produces the identical answer engine="in-memory" does – which is what you’d want confirmed before trusting it on data large enough for the memory benefit to matter.

Practice Exercises#

Exercise 1: Confirm correctness on a query with a join and a filter, not just a group_by#

Using thistlewood_orders_timestamped.csv and thistlewood_returns.csv, build a lazy query that joins them on order_id, filters to reason == "damaged", and selects order_id and return_date. Run it with both engine="in-memory" and engine="streaming", and confirm the results match with .equals().

Hint

pl.scan_csv("thistlewood_orders_timestamped.csv", try_parse_dates=True).join(pl.scan_csv("thistlewood_returns.csv", try_parse_dates=True), on="order_id", how="inner") gives you the joined LazyFrame to filter and select from.

Exercise 2: Try engine=“auto” and confirm which engine it uses#

Run the Lesson’s main query with engine="auto" (or no engine= argument at all, since "auto" is the default) and confirm its result matches engine="in-memory"’s result with .equals(). Based on Module 10 Lesson 5’s finding that "auto" falls back to "in-memory", explain in one sentence why you’d expect this, rather than a surprise.

Hint

q.collect() with no engine= argument at all uses the same default as engine="auto" – compare both against engine="in-memory"’s result to double-check the fallback holds.

Summary#

engine="streaming" processes a query in bounded chunks instead of loading every source file into memory at once – a memory ceiling that matters once data no longer comfortably fits in RAM. Run against the same join-filter-group_by query as Lesson 3, engine="streaming" and engine="in-memory" produced byte-identical results, confirmed with .equals(). Timed across 7 runs each, streaming measured modestly slower (5.46ms vs 4.47ms median) on Thistlewood’s roughly 20,000-row files – the expected outcome, since streaming’s chunking overhead has nothing to buy back on data this small, and this lesson reported that plainly rather than manufacturing a benefit the data can’t support.

Key Concepts#

  • Streaming execution processes data in bounded chunks, capping memory use regardless of input size, in exchange for coordination overhead.
  • engine="streaming" and engine="in-memory" produce identical results – confirmed with .equals(), the same correctness-first discipline every benchmark in this module has used.
  • Streaming isn’t a general speedup – it measured slower on data small enough to fit comfortably in memory, which is the expected result, not a failure of the feature.
  • collect()’s engine= parameter is where streaming lives on this version – there is no streaming=True argument, matching Module 10 Lesson 5’s direct signature check.

Why This Matters#

It would be easy to reach for engine="streaming" on the assumption that it’s simply the “big data” setting and therefore always safer or faster to use. This lesson’s own numbers say otherwise for data at Thistlewood’s scale – streaming cost slightly more, not less, here. Knowing when a tool’s benefit does and doesn’t apply is as valuable as knowing the tool exists at all, and that distinction only comes from measuring rather than assuming.
