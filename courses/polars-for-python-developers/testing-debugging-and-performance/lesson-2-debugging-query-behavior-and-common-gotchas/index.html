Welcome to Debugging Query Behavior and Common Gotchas#

A query that runs without error can still be wrong. Module 10 Lesson 5 found exactly that: a lazy group_by() on a hive-partitioned scan that silently returned a total 12× too large, on this installed Polars version, caught only because it was checked against a number already known. This lesson turns that discovery into a process you can apply to any suspicious result, then runs the same process against two more gotchas verified directly against Thistlewood’s data.

By the end of this lesson, you will be able to:

  • Apply a repeatable debugging process: reconcile against a known total, read .explain(), isolate the smallest reproducible case
  • Explain, using Module 10’s verified pre_partition_hive example, why a query plan is the tool for diagnosing a wrong answer, not just a slow one
  • Recognize two more common Polars gotchas – null propagation in comparison filters, and a join silently breaking on invisible whitespace – and know how to catch each one

A Debugging Process#

Guessing at fixes for a wrong number wastes more time than it saves. The process this lesson uses, and the one every case below follows, has four steps:

  1. Notice the number is suspicious – it doesn’t match a total you already trust, or the row count doesn’t match a shape you expect.
  2. Reconcile against something already known – a grand total from an earlier lesson, an expected row count derived from the data’s own structure.
  3. Read .explain() – look inside the plan for evidence of what actually ran, not what you assumed ran.
  4. Isolate the smallest reproducible case – strip the query down to the minimum that still shows the wrong behavior, which usually makes the cause obvious.

Case 1: The Hive-Partition group_by Overcount#

Module 10 Lesson 5 built thistlewood_lake/, a Parquet directory partitioned by year and month, and found that grouping the lazy scan directly by its own partition columns returned a wrong answer. Rebuild the same shape of lake here under a different name, so this lesson’s own gate run never touches Module 10’s files, and reproduce the bug from scratch:

Step 2: Reconcile#

There are 24 (year, month) partitions in this lake – two years times twelve months – so 288 rows is twelve times too many. This course’s grand total, reconciled since Module 7, is $9,195,043.62:

Both numbers are wrong by the same factor, twelve, which is itself a clue – an error that scales a result by a clean integer multiple usually means something got counted once per some repeated unit, not a random miscalculation.

Step 3: Read .explain()#

The plan opens with UNION, not a single AGGREGATE – 24 near-duplicate plan blocks, one per partition file, each one scanning more of the lake than it should and summing overlapping totals into the union. That is the twelve found in step 2: this lake has 24 files, and the union effectively lets multiple files’ data bleed into each other’s aggregate before combining, twelve times too much per group.

Step 4: Isolate the Smallest Reproducible Case#

The original query grouped by two columns. Does the bug need both?

A single-column group_by("year") reproduces the same shape of bug in two lines instead of the original multi-step pipeline – 24 rows where there should be 2, the identical value repeated once per partition file. The smallest case makes the cause unmistakable: year is both a hive-partition column and the group key, and the bug triggers whenever those overlap, regardless of what else is in the group_by().

Fix and Verify#

Module 10 Lesson 5 traced this to pre_partition_hive, a collect() optimization enabled by default that mishandles a group_by() on hive-partition columns when those columns also exist as regular columns inside each file. Disabling it fixes both the original query and the isolated case:

24 rows, $9,195,043.62 – matching both the expected row count and the known grand total. This is the process that found the bug in the first place; re-running it as a named worked example is what makes it repeatable the next time a group_by() on partitioned data looks fine but isn’t.

A plan that runs without error can still be wrong

Nothing about lake.group_by(["year", "month"]).agg(...).collect() raised an exception or a warning – it returned a plausible-looking DataFrame that was wrong by a clean 12×. .explain() is the tool for catching this kind of bug, not just a slow query: a UNION of 24 near-duplicate plan blocks where you expected one AGGREGATE is visible the moment you look, but invisible if you never check.

Case 2: Null Propagation in Comparison Filters#

thistlewood_orders_raw.csv has nine rows with a null city. A filter that excludes one specific city might look like it should keep every other row, nulls included – reconcile that assumption against the actual row count:

No row in this data has city == "Boston", so a filter for “not Boston” should, intuitively, keep all 795 rows. It kept 786 – nine short, and the null-city count in the result is zero. Polars follows the same three-valued logic as SQL: comparing null to anything, including with !=, produces null, not True, and .filter() drops rows where the condition isn’t True. The nine null-city rows silently vanished, not because they equaled "Boston", but because the comparison couldn’t be evaluated at all.

Adding an explicit .is_null() branch recovers the nulls on purpose, rather than as an accidental side effect of a differently-written filter. The fix depends on what you actually want: sometimes dropping nulls from a != filter is correct behavior, and the gotcha is only in assuming it either way without checking.

Case 3: Invisible Whitespace Breaking a Join#

thistlewood_products_raw.csv (Module 5’s messy category data) has inconsistent capitalization on purpose – "Kitchen", "KITCHEN", "kitchen". Join it against a small canonical reference table on category and see how many rows fail to match:

Case capitalization explains most of that – "KITCHEN" won’t match "Kitchen" on an exact join. But look closer at which raw values had no match, and check their character length, not just how they print:

"Bath" appears in this list – char_length 5, one character longer than the canonical "Bath" (char_length 4). Printed side by side in a terminal, a trailing space is invisible; .str.len_chars() is what actually catches it. "Decor" (6 characters) has the same problem next to "Decor"’s expected 5. An anti join against the reference table, followed by checking length rather than trusting the printed value, is what surfaces this – exactly Case 1’s “read the plan, don’t assume” habit applied to strings instead of a query plan.

.str.strip_chars() removes the invisible whitespace, .str.to_titlecase() fixes the case, and every one of the 61 rows now matches a canonical category.

Practice Exercises#

Exercise 1: Isolate Case 1’s bug with a single partition column and a filter added#

Rebuild thistlewood_debug_lake (or reuse it in the same script), then run lake.filter(pl.col("month") <= 6).group_by("year").agg(pl.col("order_revenue").sum().round(2).alias("revenue")).collect(). Does adding a filter before the group_by() change whether the bug appears? Report the row count and whether optimizations=QueryOptFlags(pre_partition_hive=False) is still needed to fix it.

Hint

The bug is specifically about the group_by() step, not anything upstream of it – a filter added before the group-by narrows which rows get aggregated but doesn’t change whether pre_partition_hive mishandles the aggregation itself.

Exercise 2: Find another whitespace mismatch on your own#

thistlewood_products_raw.csv also has a subcategory column. Using the same anti-join-plus-str.len_chars() process as Case 3, check whether any subcategory values in thistlewood_products.csv (the canonical file) fail to match the raw file’s values for the same product_id, and report what you find.

Hint

Join the two files on product_id, then compare subcategory from each side directly with pl.col("subcategory") != pl.col("subcategory_right") rather than assuming a mismatch means the same whitespace problem – verify before concluding.

Summary#

One four-step process – notice, reconcile against a known total, read .explain(), isolate the smallest reproducible case – diagnosed three different Polars gotchas. Case 1 revisited Module 10 Lesson 5’s pre_partition_hive bug: 288 rows and $110,340,523.44 instead of 24 rows and $9,195,043.62, isolated down to lake.group_by("year") alone reproducing the identical 12× overcount in two lines, and fixed with optimizations=QueryOptFlags(pre_partition_hive=False). Case 2 showed != silently dropping all nine null-city rows from a filter, a three-valued-logic gotcha fixed by adding an explicit .is_null() branch. Case 3 showed a category string with an invisible trailing space breaking a join that looked fine when printed, caught by .str.len_chars() and fixed with .str.strip_chars().str.to_titlecase().

Key Concepts#

  • A four-step debugging loop – notice, reconcile, .explain(), isolate – applies to query-plan bugs and string-matching bugs alike, not just performance problems.
  • An overcount by a clean integer multiple is a clue, not a random error – Case 1’s 12× pointed straight at “something counted once per partition file.”
  • Comparing anything to null produces null, not True or False, so != filters silently exclude null rows unless you add an explicit .is_null() branch.
  • Two strings that print identically can still differ – .str.len_chars() catches invisible whitespace a printed comparison never will.

Why This Matters#

A query that runs without error is not the same as a query that’s correct, and none of this lesson’s three bugs would have surfaced from reading code alone – each one needed the result checked against something already known before it revealed itself. That is the same discipline this course has practiced since Module 7, applied here to the moment something goes wrong instead of the moment something goes right.
