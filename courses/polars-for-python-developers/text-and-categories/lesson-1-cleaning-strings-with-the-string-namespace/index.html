Welcome to Cleaning Strings with the String Namespace#

Module 4 cleaned Thistlewood’s order data – nulls, bad numbers, mixed date formats. This module’s mess looks different: the values aren’t missing or out of range, they’re just written inconsistently. thistlewood_products_raw.csv is a 61-row variant of the canonical 60-row thistlewood_products.csv, where the category and product_name columns say the right thing in the wrong shape. This lesson opens Polars’s string namespace – every string method lives under .str. – and runs its core cleaning functions against the messy columns to see exactly what each one does.

By the end of this lesson, you will be able to:

  • Read a messy text column and quantify its problem with .is_in() and a direct inequality check, the same discipline Module 4 used for numeric and null problems
  • Use .str.strip_chars() to remove leading/trailing whitespace, and recognize what it does not fix
  • Use .str.to_lowercase() and .str.to_uppercase() to transform casing, and explain why transforming isn’t the same as normalizing
  • Use .str.len_chars() to measure a string column before and after a fix, as a checkable signal that something changed

A Messy Catalog#

61 rows, one more than the canonical catalog’s 60. Every column reads in as a plain type – nothing crashed, nothing came in null. The underlying problems here are inside the strings themselves, and the first one to check is category.

Problem 1: A Category Column with 22 Distinct Strings#

Thistlewood only sells products in 8 canonical categories: Kitchen, Bath, Bedding, Lighting, Storage, Decor, Furniture, Outdoor. Check category against that canonical list with .is_in(), the same validation tool Module 4 used on channel and status:

14 of 61 rows fail the check, and the column has 22 distinct strings even though there are only 8 canonical categories – the other 14 “extra” strings are case and whitespace variants of the same 8 canonical values, not new categories. Look at three of them directly:

P006 is all-uppercase, P045 is all-lowercase, and P012’s Bath looks fine printed but carries a trailing space the print output doesn’t show. Three different products, three different ways of writing a category Thistlewood already has a canonical spelling for.

Fixing Whitespace with str.strip_chars()#

.str.strip_chars() removes leading and trailing whitespace from every value in a string column – exactly what P012’s "Bath " needs:

P012 shows no visible change here because the trailing space it lost doesn’t render in a printed cell – but the strip happened: check exactly which rows .str.strip_chars() changes by comparing the stripped column back against the original:

Only 4 of the 14 non-canonical rows change – P006 and P045 aren’t in this list at all. .str.strip_chars() only touches leading/trailing whitespace; it has nothing to say about KITCHEN or decor, whose problem is casing, not whitespace. This is the first lesson of the string namespace: each function fixes one specific kind of problem, and knowing which one you’re looking at matters before reaching for a fix.

strip_chars() doesn’t touch what’s in the middle

.str.strip_chars() only removes whitespace from the edges of a string. A value like "Carrara Marble Ladle" with doubled spaces inside it comes out of .str.strip_chars() unchanged in the middle – the next section shows this in the data, and Lesson 2’s regex tools are what fix an internal whitespace problem.

Transforming Casing with to_lowercase() / to_uppercase()#

.str.to_lowercase() and .str.to_uppercase() transform every character’s case, unconditionally:

Both functions run on every row regardless of its starting case – to_lowercase() on an already-lowercase decor is a no-op, and to_uppercase() on KITCHEN is too. Neither one, by itself, gives you Thistlewood’s canonical spelling ("Kitchen", "Bath", "Decor" – capitalized first letter, the rest lowercase). to_lowercase() gets every value into one consistent case, which is useful as a first step, but “consistent” isn’t the same as “correct” – Lesson 3 finishes the job with .str.to_titlecase().

Measuring a Fix with str.len_chars()#

.str.len_chars() counts characters per row – a plain integer you can compare before and after a fix, the same before/after discipline Module 4 used for row and null counts:

P007’s canonical product name is "Carrara Marble Ladle" (21 characters), but this row’s raw value is 26 – 5 extra characters from doubled spaces and leading/trailing whitespace. P028’s canonical value is already the right length; its only problem is casing. Now apply .str.strip_chars() and measure again:

P007’s length drops from 26 to 22 – the 4 characters of leading/trailing whitespace are gone – but 22 is still more than the canonical 21, because "Carrara Marble Ladle" still has its doubled internal spaces after stripping. P028 doesn’t move at all: .str.strip_chars() has nothing to fix there, since its problem is entirely casing. .str.len_chars() didn’t fix anything itself, but it gave a checkable number proving exactly how much .str.strip_chars() did and didn’t do.

Confirm across the whole file how many product_name rows .str.strip_chars() changes:

3 rows – the whitespace-messy ones. The other 3 messy product_name rows (a casing problem, like P028) aren’t touched by .str.strip_chars() at all, the exact same split this lesson already found in category.

Practice Exercises#

Exercise 1: Find every row str.strip_chars() would change, across both columns#

Using raw, build one combined check: (pl.col("category") != pl.col("category").str.strip_chars()) | (pl.col("product_name") != pl.col("product_name").str.strip_chars()). Filter with it and confirm the result has 7 rows (4 category whitespace rows plus 3 product_name whitespace rows, no overlap between them).

Exercise 2: Confirm to_lowercase() is idempotent#

Take raw["category"], apply .str.to_lowercase() twice in a row (.str.to_lowercase().str.to_lowercase()), and confirm the result is identical to applying it once. Explain in one sentence why a casing transform being idempotent is a useful property for a cleaning step you might accidentally run twice.

Hint

Compare the two Series with .equals() rather than == plus .all() – either works, but .equals() is the more direct tool for “are these two entire columns identical.”

Summary#

thistlewood_products_raw.csv (61 rows) has a category column with 22 distinct strings instead of the canonical 8, and 14 rows whose category string doesn’t match Thistlewood’s canonical spelling. .str.strip_chars() fixed exactly 4 of those 14 rows (the whitespace ones) and 3 of 6 messy product_name rows – leaving the casing-only rows (KITCHEN, decor) and the internal-whitespace problem ("Carrara Marble Ladle") untouched. .str.to_lowercase()/.str.to_uppercase() transform casing unconditionally but don’t produce Thistlewood’s canonical spelling on their own. .str.len_chars() gave a checkable number (26 -> 22, still short of the canonical 21) proving exactly how much each fix did and didn’t accomplish.

Key Concepts#

  • Quantify a text problem with .is_in() and inequality, not eyeballing – 14 non-canonical category rows and 22 distinct strings were both counted numbers, not impressions.
  • Each .str function fixes one specific problem – .str.strip_chars() only touches edges; casing functions only touch case. Neither one alone produces a correct, canonical value.
  • .str.len_chars() as a before/after signal – a plain integer comparison proves whether a fix changed a value, and by how much, the same discipline Module 4 used for row and null counts.

Why This Matters#

Real text data almost never arrives with one clean problem – it’s whitespace and casing and sometimes something regex-shaped, all mixed into the same column. Knowing exactly which .str function fixes which specific problem, and checking the result with an exact count rather than trusting how a value looks when printed, is what keeps a cleaning script honest instead of just optimistic.

Continue Building Your Skills#

.str.strip_chars() and the casing functions handled part of the mess, but doubled internal whitespace, the respelled duplicate product name, and a way to pull values out of text are all still open.
