Welcome to the Guided Project#

Every tool this module built comes together here: Lesson 3’s format round-trips, Lesson 4’s partitioned Parquet lake, and Lesson 5’s pruned, pushed-down queries – including the real pre_partition_hive fix Lesson 5 verified was necessary. build_local_analytics_workflow() combines all of it into one function that builds the lake from scratch, answers a targeted revenue question with a lazy query, and writes a small aggregated summary to SQLite – checked against this course’s own grand total twice before you trust it.

By the end of this lesson, you will be able to:

  • Combine lake-building, a pruned lazy query, and a corrected group-by aggregation into one reusable function
  • Apply Lesson 5’s pre_partition_hive fix in a real pipeline rather than as an isolated example
  • Write a small, already-aggregated result to SQLite and read it back with the pattern Lesson 3 established
  • Verify a multi-step local analytics workflow against an independently-known total, the same discipline every guided project in this course has used

The Complete Workflow Function#

Four steps, one function: build the lake from the canonical CSVs (Lesson 4’s pattern), answer a real pruned-and-pushed-down question with a lazy filter (Lesson 5’s Q1-2024-web query), aggregate a small summary with the pre_partition_hive fix Lesson 5 verified was necessary (optimizations=QueryOptFlags(pre_partition_hive=False)), and write that summary out to SQLite (Lesson 3’s format).

Running the Workflow#

$866,475.78 for Q1 2024 web orders, matching Lesson 5’s result exactly. The summary holds 72 rows – 24 year-month partitions × 3 channels – with revenue summing to $9,195,043.62 and n_orders summing to 6,000, both the correct totals this module has now used the pre_partition_hive fix to reach twice.

Reconciling After the SQLite Round Trip#

The function already read the summary back from thistlewood_analytics.db. Confirm the round trip changed nothing about the numbers, only the storage:

Two separate reconciliations, both passing: the SQLite round trip preserved the summary exactly, and the summary’s total matches a grand total computed completely independently, straight from thistlewood_order_items.csv, with no dependency on the lake, the partitioning, or any of this lesson’s own code. That is the strongest form of verification this course uses – not “did the pipeline agree with itself,” but “does the pipeline agree with the raw data it started from.”

Practice Exercises#

Exercise 1: Add a returns-adjusted view to the summary#

thistlewood_returns.csv holds every returned line item. Extend build_local_analytics_workflow() (or write a new function that reuses its summary) to also report total n_orders with at least one return per month, using a join against thistlewood_returns.csv. Confirm the returned-order count is smaller than n_orders for every row.

Hint

Join thistlewood_returns.csv’s order_id (after joining it to orders_with_revenue for year/month) and count n_unique("order_id") per year/month, the same shape of aggregation this lesson already used for n_orders.

Exercise 2: Confirm the workflow is idempotent#

Call build_local_analytics_workflow() twice in a row and confirm the second call’s summary is identical to the first with .equals(). Explain in one sentence why this only works because Lesson 4’s shutil.rmtree("thistlewood_lake", ignore_errors=True) runs at the start of every call.

Hint

Without removing the old thistlewood_lake/ directory first, write_parquet(partition_by=[...]) would add a second file to each partition directory rather than replacing it – the second run’s lake would double-count every row.

Summary#

build_local_analytics_workflow() combined every tool this module built: Lesson 4’s partitioned-lake construction, Lesson 5’s pruned-and-pushed-down lazy query and its verified pre_partition_hive fix, and Lesson 3’s SQLite round trip. The Q1 2024 web-revenue query matched Lesson 5’s result exactly ($866,475.78), and the 72-row monthly-channel summary reconciled to the course’s $9,195,043.62 grand total two separate ways – once through the SQLite round trip, and once against a completely independent recomputation straight from thistlewood_order_items.csv.

Key Concepts#

  • A local analytics workflow is usually several of this module’s tools combined, not one – building the lake, querying it lazily, and persisting a small result, the same combining pattern every guided project in this course has used for its own tools.
  • A query-plan fix belongs in the pipeline itself, not just in the lesson that discovered it – optimizations=QueryOptFlags(pre_partition_hive=False) moved from Lesson 5’s isolated example directly into this lesson’s production function.
  • Writing only the small, already-aggregated result to SQLite – not the full lake – keeps the persisted database tiny while still making the summary queryable with ordinary SQL later.
  • The strongest reconciliation check compares a pipeline’s output to the raw data it started from, not just to itself – this lesson’s summary matched a grand total computed fresh from thistlewood_order_items.csv, with no dependency on any of this lesson’s own intermediate steps.

Why This Matters#

A local analytics workflow like this one – build a lake, answer targeted questions lazily, persist small aggregated results – is a genuinely reusable shape for a great deal of real, laptop-scale data work: no server, no cluster, just files, a query engine, and disciplined verification. The pre_partition_hive fix folded into this lesson’s function is the concrete payoff of Lesson 5’s whole point: a query plan can be wrong in a way that never raises an error, and the only defense is checking results against something you already know, every time, not just when something looks suspicious.
