Welcome to Query Plans and Optimization Habits#

Lesson 2 first showed a .explain() plan changing shape once a .select() and .filter() were chained onto a scan. This lesson takes that same skill to thistlewood_lake/ – a partitioned directory instead of one file – and adds one more thing a query plan can reveal: not just that an optimization happened, but, in one verified case on this Polars version, that trusting an optimization’s result without checking it would have been a mistake.

By the end of this lesson, you will be able to:

  • Read a .explain() plan for evidence of partition pruning, projection pushdown, and predicate pushdown together
  • Use the current collect() API surface correctly – engine= and optimizations=QueryOptFlags(...), not the deprecated individual boolean flags
  • Reconcile a lazy query’s result against an independently-known total, and know what to do when it doesn’t match
  • Explain, with a worked example, why “the plan changed” and “the plan is correct” are two different questions

A Realistic Query: Q1 2024 Web Revenue#

A dashboard question with a concrete answer: what did web orders bring in during the first quarter of 2024? Filter to year == 2024, month <= 3, and channel == "web", then select only what’s needed and check the plan before collecting anything:

Three things worth reading in that plan, all at once:

  • Partition pruning. Parquet SCAN [thistlewood_lake/year=2024/month=1/00000000.parquet, ... 2 other sources] means the scan only touches 3 files – January, February, and March of 2024 – out of the lake’s 24. The year == 2024 and month <= 3 filters were resolved against the directory structure itself, before a single row of any other partition was read.
  • Predicate pushdown. The combined SELECTION line shows all three filter conditions folded into the scan, the same pattern Lesson 2 showed for a single-file CSV scan.
  • Projection pushdown. PROJECT 5/9 COLUMNS – fewer than all 9 columns in the lake’s schema get read out of the 3 matching files, even though this query only ultimately needs 2 (order_id, order_revenue); the plan’s internal projection count reflects what the scan step itself needs before the final simple π 2/2 trims it down further.

Compare that scan-file count to a query with no filters at all:

... 23 other sources – all 24 files, since nothing filters which partitions matter. Side by side, the difference partition pruning makes is right there in the file count: 24 files with no filter, 3 files once year and month narrow the scan to a single quarter.

Now collect the filtered query and verify it:

532 orders, $866,475.78, matching the naive eager equivalent exactly. The plan showed pruning and pushdown happening; the numbers confirm the plan didn’t change the answer – only how much work it took to get there.

The Current collect() API: engine= and QueryOptFlags#

Every optimization above ran under collect()’s defaults. Checking help(pl.LazyFrame.collect) directly against this installed version (1.43.0) shows what those defaults actually are today, rather than assuming an older API still applies:

Two details matter for writing correct, current code:

  • There is no streaming=True parameter. Older Polars tutorials describe collect(streaming=True) for out-of-core execution – that argument doesn’t exist on this version. Its replacement is engine="streaming", one of collect()’s engine= choices (alongside the default "auto", which falls back to "in-memory", and "gpu" for CUDA hardware this course doesn’t use).
  • The individual boolean flags (predicate_pushdown, projection_pushdown, and the rest) are deprecated as of Polars 1.30.0, in favor of a single optimizations=QueryOptFlags(...) object. They still work – every plan in this lesson ran under their True defaults – but new code should reach for QueryOptFlags instead when an optimization needs to be turned off, which is exactly what the next section needs to do.

A Real Optimization Bug: Grouping by Partition Columns#

Lesson 4 grouped a partitioned lake by year and month – but only after calling .collect() first, on the resulting DataFrame, not directly on the lazy scan. Here’s why that distinction was load-bearing, not a stylistic choice. Try the natural-looking lazy version: group the scanned lake by year, month, and channel directly, before collecting:

864 rows and $110,340,523.44 – but there are only 24 partitions × 3 channels = 72 possible (year, month, channel) combinations in this data, and this course’s grand total, reconciled at least six times since Module 7, is $9,195,043.62. Both numbers are wrong, and neither raised an error or a warning. This is exactly the kind of failure this course’s “verify against a known total” habit exists to catch – and it did.

The plan is the diagnosis. Instead of one aggregate over one pruned scan, the optimizer split the query into a UNION of 24 near-duplicate AGGREGATE blocks – one per partition file – each one scanning far more sources (... 11 other sources) than it should and applying a near-meaningless SELECTION: col("year")...is_in(...) filter, rather than correctly limiting each branch’s aggregate to its own single file’s rows. The result is a group-by that effectively recomputes overlapping totals across branches of the UNION and sums them together – 864 rows instead of 72, revenue roughly 12× too high.

This comes from pre_partition_hive, an optimization enabled by default in QueryOptFlags that tries to push a group_by on hive-partition columns down into per-partition aggregates before combining them – an idea that, on this installed version (Polars 1.43.0), produces a wrong answer specifically when the partition columns are also present as regular columns inside each file, exactly as Lesson 4 flagged when the lake was built. Disabling that one optimization fixes it:

72 rows – the correct 24 × 3 combinations – and $9,195,043.62, matching the course’s grand total exactly.

A default optimization can be wrong, not just slow

It’s tempting to treat query-plan optimizations as a pure performance concern – something that only affects how fast a query runs, never what it returns. This lesson found a verified counterexample on Polars 1.43.0: group_by() directly on a LazyFrame scanned from a hive-partitioned directory, using collect()’s defaults, returned a result 12× too large – caught only because the number was checked against an independently-known total. collect(optimizations=QueryOptFlags(pre_partition_hive=False)) fixes it for this exact case. The general habit matters more than this one flag: when a lazy pipeline reaches a group_by on columns that came from a partitioned scan, verify the result against something you already know before trusting it.

Practice Exercises#

Exercise 1: Reproduce the bug on a single-key group-by#

Run lake.group_by(["year"]).agg(pl.col("order_revenue").sum().round(2).alias("revenue")).collect() and report the row count and total. There should only be 2 possible year values in this data – compare what you get to that expectation, then fix it with optimizations=QueryOptFlags(pre_partition_hive=False) and confirm the corrected total splits $9,195,043.62 across exactly 2 rows.

Hint

The uncorrected version should also badly overcount here, the same shape of problem this lesson found with three group keys – the bug isn’t specific to grouping by more than one partition column.

Exercise 2: Confirm a non-partition group-by is unaffected#

Run lake.group_by(["channel"]).agg(pl.col("order_revenue").sum().round(2).alias("revenue")).collect() – grouping only by channel, which is not a hive-partition column. Confirm this one returns the correct 3 rows and the correct grand total with collect()’s plain defaults, no QueryOptFlags needed, and explain in one sentence why grouping by a non-partition column doesn’t trigger the same bug.

Hint

pre_partition_hive specifically targets group-by keys that match a scan’s hive-partition columns (year and month here) – channel was never a partition key for this lake, so that optimization path never engages for it.

Summary#

Filtering thistlewood_lake/ to Q1 2024 web orders and reading its .explain() plan showed partition pruning (3 of 24 files scanned), predicate pushdown (a combined SELECTION at the scan), and projection pushdown (PROJECT 5/9 COLUMNS) together in one plan – 532 rows, $866,475.78, verified against a naive equivalent. collect()’s current API replaces the deprecated streaming=True and individual boolean flags with engine= and optimizations=QueryOptFlags(...), confirmed directly against this installed version’s own signature. That distinction mattered concretely: grouping the lazy lake directly by its own hive-partition columns returned a result 12× too large on Polars 1.43.0, caught by checking it against the course’s own $9,195,043.62 grand total and diagnosed with .explain(), which showed a UNION of 24 near-duplicate per-file plans from the pre_partition_hive optimization. collect(optimizations=QueryOptFlags(pre_partition_hive=False)) fixed it, verified exactly.

Key Concepts#

  • .explain() shows partition pruning, predicate pushdown, and projection pushdown together – fewer scanned files, a SELECTION line at the scan, and a reduced PROJECT count, all readable in one plan.
  • collect()’s current API is engine= and optimizations=QueryOptFlags(...) – the old streaming=True parameter doesn’t exist on this version, and the individual boolean flags are deprecated in its favor.
  • A default optimization can silently produce a wrong result – pre_partition_hive’s default behavior on this Polars version overcounted a group-by on hive-partition columns 12×, verified directly rather than assumed correct.
  • Reconciling a result against a known total works as a bug-finding tool, not only a closing sanity check – it’s what caught this lesson’s overcounted total before it could be trusted.

Why This Matters#

A query plan is more than a performance diagnostic – this lesson’s central example is proof that it can be the only thing standing between a wrong number and a report someone acts on. A dashboard built on lake.group_by(["year", "month", "channel"]).collect() with no verification step would have silently shipped a revenue figure twelve times too large, with a plan that ran without error and a result that looked like a plausible table. The habit this course has built since Module 7 – reconcile every aggregate against something you already know – is what turns “the code ran” into “the code is right,” and this lesson is the sharpest example yet of why that gap is real.
