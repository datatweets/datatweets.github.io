Welcome to Invalid Values and Inconsistent Categories#

Lesson 1 found 5 rows with a negative quantity or unit_price, and 3 duplicate order_ids. Both are values problems, not type problems — -13 is a perfectly valid Int64, just not a valid quantity. This lesson fixes both, plus a direct check that Thistlewood’s categorical columns (channel, status) haven’t drifted into inconsistent values either.

By the end of this lesson, you will be able to:

  • Detect out-of-range numeric values with a boolean filter, separately from type validity
  • Choose and justify a correction strategy for negative values instead of silently applying .abs()
  • Validate categorical columns against a known set of valid values with .is_in()
  • Deduplicate duplicate rows with .unique() and justify a keep-first/keep-last/flag decision

Finding the Negative Values#

Neither quantity nor unit_price can be negative in Thistlewood’s business — you can’t order -13 units or sell something for -$264.52. 3 rows have a negative quantity, 2 have a negative unit_price.

Don’t Silently .abs() — Flag, Then Correct#

.abs() alone would “fix” the numbers, but it would also silently erase the fact that something was wrong. A better fix records which rows were corrected before correcting them, so the correction is auditable rather than invisible:

The two flag columns preserve exactly what Lesson 1 found — 3 corrected quantities, 2 corrected prices — so anyone reviewing this cleaned data later can filter was_negative_quantity and see precisely which rows were touched and why, instead of a silent, unexplained change.

Why abs() is the justified choice here

Taking the absolute value is defensible in this specific case because a sign-flip is a well-known data-entry error pattern (a return processed as a negative sale, a minus key typo) — not because negative numbers are “obviously” supposed to be positive in general. The next section verifies that these particular corrected values match the independently-known-correct numbers, which is what makes .abs() the right call here rather than a guess.

Verifying the Correction Against Independent Data#

Every corrected value matches the quantity/price rolled up independently from thistlewood_order_items.csv — proof this was a genuine sign-flip error with a recoverable true value, not a guess dressed up as a fix.

Validating Categorical Columns#

channel and status are the two categorical columns in this file. Before assuming they’re fine, check them against Thistlewood’s known valid value sets:

Zero for both — this file’s messiness was limited to the problems Lesson 1 already catalogued, and channel/status didn’t drift. That’s a result worth confirming rather than assuming, and it’s the same .is_in() pattern you’d use on a file where categories had drifted (Module 5 covers that problem directly, on Thistlewood’s product catalog).

Deduplicating the Duplicate order_ids#

O02003’s two rows are identical across every column — a double-submission, not two conflicting versions of the same order. .unique(subset=["order_id"], keep="first") drops 3 rows and lands exactly on 792, matching the real canonical Q1 2024 order count.

Why keep-first was the safe choice here

keep="first" only matters when duplicate rows differ — here they don’t, so keep="first" and keep="last" produce identical results. In a file where duplicates did disagree (say, two different unit_price values for the same order), you’d need a solid reason to prefer one over the other — commonly “the later row reflects a correction” (keep="last") — rather than picking one arbitrarily.

Practice Exercises#

Exercise 1: Confirm keep=“last” gives the same result here#

Rebuild deduped with keep="last" instead of keep="first", and confirm the resulting DataFrame has the same shape (792 rows) and that O02003’s surviving row has the same quantity/unit_price either way. Explain in one sentence why this dataset’s duplicates make the keep choice irrelevant.

Exercise 2: A flag-for-review alternative#

Instead of deduplicating immediately, add a pl.col("order_id").is_duplicated().alias("flagged_for_review") column to raw (don’t drop anything yet), and print just the flagged rows. When might flagging instead of immediately deduplicating be the safer choice in a production pipeline (hint: think about who should look at the 3 duplicated rows before they’re silently dropped)?

Summary#

The 5 rows with a negative quantity or unit_price were flagged with two boolean columns before correcting them with .abs() — an auditable fix, not a silent one — and every corrected value was verified against an independent rollup from thistlewood_order_items.csv. channel and status were checked against their known valid value sets and found clean (0 invalid rows for both). The 3 duplicate order_ids, confirmed to be exact re-submissions, were removed with .unique(subset=["order_id"], keep="first"), landing on exactly 792 rows — matching the canonical Q1 2024 order count.

Key Concepts#

  • A valid dtype doesn’t mean a valid value — -13 is a perfectly good Int64; range/business-rule checks (< 0, .is_in([...])) catch what dtype checks can’t.
  • Flag before you correct — recording which rows were changed, and why, keeps a correction auditable instead of silently invisible.
  • .is_in() for categorical validation — checks a column’s actual values against a known valid set; confirming a column is clean is just as informative a result as finding it isn’t.
  • .unique(subset=..., keep=...) — a deduplication decision, with the keep choice justified by whether duplicate rows disagree.

Why This Matters#

Negative-number data-entry errors and double-submitted records are two of the most common real-world data-quality problems, and both are easy to “fix” carelessly — a blind .abs() or a blind .unique() with no record of what changed. Flagging before correcting, and verifying corrections against an independent source, is what turns a plausible-looking fix into a provably correct one.
