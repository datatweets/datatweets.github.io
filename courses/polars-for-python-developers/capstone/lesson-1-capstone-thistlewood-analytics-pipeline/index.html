Welcome to the Capstone#

Every module in this course built one reusable piece: Module 4 taught you to clean thistlewood_orders_raw.csv back to a checkable standard. Module 8 taught you to join Thistlewood’s tables with a diagnostic that flags a bad join the moment it happens. Modules 9 and 10 taught you to aggregate, persist, and read back results without losing or duplicating a row. This lesson runs all of it once, in order, against Thistlewood’s Q1 2024 quarter — the same quarter Module 1’s very first guided project and Module 4’s cleaning project both already worked with.

By the end of this lesson, you will be able to:

  • Build a complete ingest-clean-join-aggregate-write pipeline out of tools from five different modules
  • Verify each stage of a pipeline before moving to the next one, rather than checking only the final output
  • Reconcile a new pipeline’s results against totals a course already established, instead of trusting a plausible-looking number
  • Recognize and fix a verified Polars behavior where tied rows in a .sort() following a parallel group_by() aren’t returned in a guaranteed order

This lesson builds up one script, section by section, the same way you’d build it yourself: read the code in order, and each block uses variables the block before it defined.

Stage 1: Ingest#

The raw file is the same messy Q1 2024 export Module 4 opened in its first lesson — a “raw quarterly export” with three duplicated order_ids, nine null city values, six null email values, twelve non-ISO order_date strings, and five negative quantity/unit_price rows.

.is_duplicated() flags every row that shares an order_id with another row — dividing by 2 turns “6 rows flagged” into “3 order IDs appear twice,” the same 795-row, five-problem shape Module 4 already established in detail. This lesson doesn’t re-derive each problem the way Module 4 did; it confirms the ingested file still matches that known catalog before cleaning it.

Stage 2: Clean#

clean_orders() is Module 4’s guided-project function, unchanged: recover city/email by joining thistlewood_customers.csv, parse order_date across three date formats with pl.coalesce, correct negative quantity/unit_price with .abs(), and drop duplicates with .unique(keep="first").

795 rows down to 792 — one row per order, ready for the reconciliation this course insists on before trusting a cleaning step.

Verify the Clean#

“Clean” only means something if it’s checkable. Compare cleaned against the canonical thistlewood_orders.csv, filtered to the same quarter, on two axes: row count and an independently-computed revenue figure.

Row counts match exactly, and the 46-cent gap between cleaned’s order-level revenue (quantity times a rounded average price) and the order-item rollup’s exact revenue is the identical gap Module 4’s guided project already found and explained: cleaned["unit_price"] is a rounded per-order average, so multiplying it back out re-introduces a tiny bit of rounding drift. Seeing the same 46 cents here, from the same file, confirms this pipeline’s cleaning step behaves exactly like Module 4’s — nothing new to explain, just a known, harmless property reproduced.

Stage 3: Join#

The cleaned orders give order-level facts (order_date, channel, status). Everything else — which products sold, who bought them, whether an item came back, whether a promotion was active — lives in four more tables. Bring thistlewood_order_items.csv in first, filtered down to only this quarter’s order IDs with a semi join (Module 8’s tool for “keep matching rows from the left table, add no columns”), then join the rest on:

(order_id, product_id) is the composite key for returns — Module 8’s lesson on this exact join found it prevents a fan-out that order_id alone would cause. The promotions step reuses join_where() for the non-equality date-range match, exactly like Module 8’s guided project, then joins the small match table back with an ordinary left join so every line item is kept whether or not it matched a promotion.

Verify the Join#

Every step landed exactly where expected: the semi join shrinks 14,054 order-item rows down to this quarter’s 1,892, and every enrichment join afterward stays unchanged — no fan-out, no dropped rows. The last line is worth pausing on: zero rows matched an active promotion. That isn’t a bug in join_where(); Thistlewood’s earliest promotion in thistlewood_promotions.csv starts on 2024-04-16, so no category promotion was running at all during Q1 2024. A join that correctly returns nothing when there’s nothing to match is doing its job — the diagnostic table above confirms it stayed unchanged rather than silently dropping rows it shouldn’t have.

Why check a join that finds nothing

It would be easy to assume 0 matches means the join_where() condition is wrong. Checking the promotion date range directly (promotions.filter(...)) confirms the cause: this data has no Q1 2024 promotions, not a join bug. Verifying why a number is zero, instead of assuming it should be, is the same discipline as verifying why a number is nonzero.

Stage 4: Aggregate#

With full built and verified, answer three business questions a Thistlewood stakeholder would ask, scoped to completed orders — cancelled and pending orders never shipped, so they don’t belong in a revenue report:

Before ranking the top products, though, there’s a gotcha worth catching on purpose.

A Ranking Gotcha: Ties After a Parallel group_by()#

Two products, P018 and P046, both sold exactly 125 units this quarter — an exact tie. Run the same group_by().sort() twice in a row and compare:

Two calls to the identical expression, on the identical data, in the same process, disagree on which product leads and which product sits in third place. This is a real, verified behavior of the installed Polars version (1.43.0): group_by() runs in parallel across threads for speed, and its output row order isn’t guaranteed — a .sort() on a column with ties inherits whatever order the rows happened to arrive in, which can differ run to run. You might see True if you run this yourself; that would just mean the parallel execution happened to interleave the same way twice, not that the underlying order is guaranteed.

The fix is a deterministic tie-break: add a second sort key that has no ties, like product_id, so every tied group resolves the same way every time.

Bath leads at $223,675.54, ahead of Kitchen at $175,419.73 — the same ranking Module 1’s much simpler flat-file analysis found for this exact quarter. web dominates the channel breakdown at $801,776.72, and 65 of 733 completed orders (8.87%) had at least one return.

Verify the Aggregate#

Two checks: do the category and channel breakdowns each sum back to the same total, and does that total match a number this course has already proven correct?

This is the strongest kind of reconciliation this course uses: not “does this pipeline agree with itself,” but “does this pipeline, built with today’s cleaning-and-join code, land on the exact number a completely different lesson already established from a completely different file.” $1,171,856.43 across 733 orders and 1,749 line items is Module 1 Lesson 5’s own total, computed from thistlewood_orders_flat.csv — a pre-joined file this capstone never touches. $1,262,892.88 is Module 4 Lesson 6’s order-item rollup for the same 792 orders, all statuses included. Both match exactly. No new grand total was invented for this capstone; it connects to numbers the course already proved.

Stage 5: Write the Outputs#

Persist the full enriched pipeline to Parquet — a flat file rather than a partitioned lake, because 1,892 rows for one quarter is small enough that partitioning would add directory overhead without buying anything back in query performance. Persist the smaller, already-aggregated summaries to SQLite, where a stakeholder could query them directly with SQL. Both writers self-clean first, the idempotent pattern Module 10 established: os.remove() runs before every write, so re-running this pipeline never doubles a row or leaves two versions of a table behind.

thistlewood_capstone.db ends up with four small tables: the category and channel breakdowns, the top-5 product ranking, and a summary_report table holding the same four headline numbers the closing report prints — so a stakeholder with nothing but a SQL client can already answer “how much did Q1 make” without asking anyone to re-run this script.

Verify the Round Trip#

.equals() confirms the Parquet file holds the exact same 1,892-row, 22-column table that’s still sitting in memory — no dtype drift, no row loss. Reading revenue_by_category back from SQLite and summing it lands on the identical $1,171,856.43 one more time, and summary_report reproduces the report’s own headline numbers, unprompted, straight from the database file on disk.

Stage 6: The Summary Report#

The last piece is the one a stakeholder reads — a short, printed report built from numbers this lesson has now verified three separate times: once against each other, once against the SQLite round trip, and once against two other lessons’ independently-established totals.

Eight lines, and every number in them traces back through a verified step: ingest, clean (matched to canonical data), join (every step flagged OK), aggregate (reconciled to two other lessons’ totals), write, and a round trip back off disk. That chain is the entire point of this course — not any single trick, but the habit of checking before trusting, applied consistently enough that a report like this one can be handed to someone who’ll act on it.

Practice Exercises#

Exercise 1: Net-of-returns revenue#

Using completed, compute the refund amount for returned line items (return_quantity * unit_price_at_sale, summed and rounded to 2 decimals) and subtract it from total_revenue to get a net-of-returns figure. Report what percentage of gross revenue was refunded, and compare it to Module 8’s guided project, which found 2.18% refunded across the full two-year dataset — is Q1 2024 higher or lower, and does that surprise you?

Hint

completed.filter(pl.col("was_returned")).select((pl.col("return_quantity") * pl.col("unit_price_at_sale")).round(2).alias("refund"))["refund"].sum() gives the refund total — the same shape of calculation Module 8’s guided project already used.

Exercise 2: Confirm the pipeline is idempotent#

Run every code block on this page a second time in the same session. Confirm thistlewood_capstone_pipeline.parquet and thistlewood_capstone.db end up identical to the first run (the deterministic parts — everything except the “unfixed” tie-order demonstration, which is non-deterministic on purpose). Explain in one sentence why the os.path.exists(...) checks before each write make this safe to re-run.

Summary#

This capstone built one pipeline out of five modules’ tools: Module 4’s clean_orders() took thistlewood_orders_raw.csv from 795 rows to a verified 792, matching canonical Q1 2024 data exactly. Module 8’s check_join() diagnostic ran across a six-step join pulling in customers, order items, products, returns, and promotions, flagging every step OK — including a zero-match result for promotions, confirmed as a feature of the data rather than a join bug. Aggregation surfaced a verified Polars behavior — tied rows after a parallel group_by() aren’t returned in a guaranteed order — and fixed it with a deterministic tie-break key. The resulting $1,171,856.43 in completed-order revenue matched Module 1 Lesson 5’s own total exactly, and the $1,262,892.88 all-status figure matched Module 4 Lesson 6’s canonical rollup exactly. Parquet and SQLite outputs, written idempotently, round-tripped back to the identical numbers, closing with an eight-line report any Thistlewood stakeholder could read.

Key Concepts#

  • A capstone reconciles to numbers the course already proved, not a new total invented for the occasion — this lesson’s two independent matches (Module 1, Module 4) are stronger evidence than any single new calculation could be on its own.
  • A join-quality diagnostic should run on every step of a full pipeline, not just a lesson’s isolated example — check_join() caught nothing wrong here, but its zero-match promotions result is exactly the kind of surprising-but-correct outcome this diagnostic exists to catch, not flag as broken.
  • group_by()’s output order isn’t guaranteed under parallel execution, so a .sort() on a column with ties needs an explicit, unique tie-break key to be reproducible — verified directly on the installed Polars version rather than assumed.
  • Idempotent writes (os.remove() before every write_parquet/write_database call) make a pipeline safe to re-run without doubling data, the same pattern Module 10 established and this capstone reuses without modification.

Why This Matters#

An analytics pipeline is rarely one clever trick — it’s cleaning, joining, aggregating, and persisting, each done carefully and each checked before the next step builds on it. This lesson’s biggest number, $1,171,856.43, isn’t impressive because it’s large; it’s trustworthy because it was computed twice, by two different lessons, using two different files, and landed on the identical figure to the cent. That is the entire argument this course has been making since Module 1: verify, don’t assume, and a result you can reconcile against something else you already know is worth infinitely more than one that merely looks plausible.
