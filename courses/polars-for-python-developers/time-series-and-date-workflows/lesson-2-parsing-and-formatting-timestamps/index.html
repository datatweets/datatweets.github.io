Welcome to Parsing and Formatting Timestamps#

Lesson 1’s order_timestamp_utc parsed cleanly because every row used the same Z-suffixed ISO-8601 string. Timestamp exports are rarely that consistent, and this lesson’s file proves it: thistlewood_orders_timestamps_raw.csv, the same Q1-2024 order timestamps reformatted into four different raw-export string styles. The job is the same one Module 4 Lesson 1 set for thistlewood_orders_raw.csv’s messy dates – detect exactly what’s wrong, with exact counts, then fix it correctly.

By the end of this lesson, you will be able to:

  • Detect and count multiple inconsistent timestamp string formats in one column
  • Explain why a single no-format .str.to_datetime() call can fail on some rows and succeed on others
  • Parse each detected format correctly with an explicit format= string
  • Format an already-parsed datetime back into a human-readable display string with .dt.strftime()

Meeting the Messy Export#

The first six rows already show four visibly different string shapes in order_timestamp_utc – MM/DD/YYYY HH:MM AM/PM, an ISO string with a numeric +00:00 offset, an ISO string with no seconds at all, and an ISO string ending in Z. order_date is untouched (still the clean "YYYY-MM-DD" string this course has used since Module 1); only the timestamp column carries this lesson’s messiness.

Detecting and Counting Every Format#

Guessing at four regexes and hoping they cover every row isn’t good enough – classify every row and confirm the counts add up to the full file:

283 rows in the Z-suffixed format, 193 with an explicit +00:00 offset, 204 in MM/DD/YYYY HH:MM AM/PM, and 112 with seconds dropped entirely – every one of the 792 rows lands in exactly one of the four groups, none left over.

Why a Single Parse Call Isn’t Enough#

Polars can auto-detect a timestamp format without a format= argument – but only when every row actually shares one shape. Try it directly on this column:

Exactly 316 failures – the 204 mm_dd_yyyy_ampm rows plus the 112 iso_no_seconds rows, matching the classification counts above precisely. Auto-detection handles iso_z and iso_offset (283 + 193 = 476 rows) because both are unambiguous ISO-8601 variants; it can’t guess the other two shapes reliably, and raises rather than silently guessing wrong.

Auto-detection succeeds silently, then fails loudly

The dangerous version of this problem isn’t the error above – it’s a file where auto-detection happens to succeed for every row in a small test sample, then hits a differently-formatted row once run against the full dataset. Detecting and counting every format up front, the way this lesson just did, catches that risk before it becomes a partial, silently-wrong parse.

Parsing Each Format Correctly#

Filter to each detected group and parse it with its own explicit format= string, then recombine:

Every one of the 792 rows now has a clean Datetime(time_unit='us', time_zone='UTC') value, 0 nulls. %z in the iso_offset format string matches a numeric UTC offset (+00:00) directly; time_zone="UTC" is still passed alongside every format string so all four groups land on the same tz-aware dtype rather than four subtly different ones.

format= alone doesn’t guarantee a time zone

format="%Y-%m-%dT%H:%M:%SZ" parses the literal Z character correctly, but Polars doesn’t infer a time zone from a literal in a format string – without time_zone="UTC" alongside it, the result is a naive Datetime(time_zone=None), even though the source string encoded UTC. Pass time_zone explicitly whenever the source data’s zone is known, rather than relying on the format string to imply it.

Formatting a Clean Datetime Back to a Display String#

Parsing turns a string into a typed datetime; .dt.strftime() does the reverse, for anywhere a report needs a human-readable string instead of a raw dtype:

%B gives the full month name, %I:%M %p gives 12-hour time with an AM/PM marker – the same strftime directive language Python’s own datetime module uses, since Polars’ .dt.strftime() follows it directly. Once a column is a typed Datetime, formatting it for display is independent of whatever string format it originally arrived in.

Practice Exercises#

Exercise 1: Add a fifth format on purpose#

Add one row to a copy of raw with order_timestamp_utc set to an unambiguous but new string shape, e.g. "2024-01-15 14:23:07" (space instead of T, no Z). Re-run the classification when/then chain and confirm it lands in the "unknown" bucket rather than silently matching one of the four existing patterns.

Hint

Use pl.concat([raw, new_row_df], how="vertical") to add the row, where new_row_df is a one-row pl.DataFrame built with the same schema as raw.

Exercise 2: Count parsed timestamps by hour of day#

Using parsed, extract the hour with .dt.hour() and group_by("hour").agg(pl.len().alias("n")).sort("hour"). Confirm the result has 24 rows (one per hour, 0-23) and note which hour has the fewest orders.

Summary#

thistlewood_orders_timestamps_raw.csv mixed four timestamp string formats across 792 Q1-2024 rows – a regex classifier counted them exactly (283 iso_z, 193 iso_offset, 204 mm_dd_yyyy_ampm, 112 iso_no_seconds, 0 unclassified). A single no-format .str.to_datetime() call failed on exactly the 316 rows auto-detection couldn’t guess (the AM/PM and seconds-omitted groups); parsing each group separately with its own explicit format= and time_zone="UTC", then recombining, recovered all 792 rows with 0 nulls. .dt.strftime() formatted the clean result back into a readable display string using the same directive language as Python’s own datetime.

Key Concepts#

  • Detect and count every format before parsing – a regex-based classification that accounts for 100% of rows (0 unknown) is the same discipline Module 4 Lesson 1 applied to messy dates, now applied to timestamps.
  • .str.to_datetime() without a format auto-detects unambiguous ISO-8601 variants, but raises on shapes it can’t guess – verified directly: exactly 316 of 792 rows failed here, matching the two formats auto-detection couldn’t handle.
  • format= alone doesn’t set a time zone – a literal Z or offset in the format string is matched as text, not converted into time_zone metadata; pass time_zone= explicitly when the source zone is known.
  • .dt.strftime() formats a typed datetime back into a string, independent of whatever raw format it was originally parsed from.

Why This Matters#

A raw export with more than one timestamp format is common enough that “parse once, assume it worked” is a risk worth taking seriously – a partial auto-detected parse can silently drop or null rows that a full classification pass, like this lesson’s, catches immediately, with exact counts instead of a vague sense that “some rows look weird.” That same discipline – detect and count before transforming – is why Module 4’s messy-date cleanup and this lesson’s messy-timestamp cleanup land on the same shape of solution.
