Welcome to Date, Datetime, and Duration Types#

Every lesson before this one treated order_date as either a plain string or something to sort and filter without asking what type it was. This module starts by asking that question directly, and introduces a new file: thistlewood_orders_timestamped.csv, the same 6,000 canonical Thistlewood orders with one new column, order_timestamp_utc – this course’s first time-zone-aware datetime column. Polars gives you three related types for this kind of work – pl.Date, pl.Datetime, and pl.Duration – and this lesson builds and verifies each one against Thistlewood’s own data before the rest of the module puts them to work.

By the end of this lesson, you will be able to:

  • Cast a plain date string to a pl.Date column with .str.to_date()
  • Read a UTC timestamp column as pl.Datetime and explain what “time unit” and “time zone” mean for that dtype
  • Compute elapsed time as a pl.Duration between two dates, and convert it to a plain integer day count
  • Recognize a casting footgun: changing a Datetime’s time unit can silently drop its time zone

Casting order_date to a pl.Date Column#

thistlewood_orders.csv has always stored order_date as plain text. thistlewood_orders_timestamped.csv carries the same column, still as text on disk – casting it to a typed column is the first step:

.str.to_date() parses a "YYYY-MM-DD" string into pl.Date, Polars’ type for a calendar day with no time-of-day component at all – exactly what order_date represents. This is the same distinction Module 2 Lesson 4 made for other columns: on disk, everything is a string; the dtype only exists once you cast it.

Meeting order_timestamp_utc: A Time-Zone-Aware Column#

order_timestamp_utc is different – it carries a time-of-day and a time zone. Reading the file with try_parse_dates=True picks both dtypes up directly, no manual casting required:

pl.Datetime takes two things pl.Date doesn’t need at all: a time unit (how finely time is stored – order_timestamp_utc lands on "us", microseconds) and a time zone ("UTC" here, because the source string ended in Z, the ISO-8601 marker for UTC). try_parse_dates=True detected both from the string format alone; Lesson 2 covers what happens when a file’s timestamps aren’t this consistent.

us, not ns

Polars’ default Datetime time unit is microseconds ("us"), confirmed directly against this installed version (Polars 1.43.0) – not nanoseconds. Nanosecond precision (pl.Datetime("ns")) exists and is occasionally needed for very high-frequency data, but nothing in this course’s data needs it, and every Datetime column built in this module defaults to "us" unless cast otherwise.

A Casting Footgun: Time Unit Changes Can Drop the Time Zone#

Changing a Datetime column’s time unit looks like it should only touch precision. It doesn’t – pl.Datetime’s time_zone parameter defaults to None, and a cast fully replaces the dtype rather than adjusting one piece of it:

Both calls report Datetime(time_unit='ns', ...) – the difference is entirely in what follows: pl.Datetime("ns") alone means “nanoseconds, and no time zone,” full stop, while pl.Datetime("ns", time_zone="UTC") keeps it. If a column arrives UTC-aware and only the precision needs to change, time_zone="UTC" has to be passed explicitly in the same cast() call, or the time zone silently disappears – no error, no warning, just a Datetime that looks almost identical in a printed schema but no longer carries the information Lesson 5 depends on to convert to a customer’s local time correctly.

Cast the whole dtype, not one piece of it

.cast(pl.Datetime(...)) is not a partial update. Every argument you don’t pass resets to its default – time_unit has no default (it’s required), but time_zone defaults to None. If a column is time-zone-aware and you’re only changing precision, always pass both: .cast(pl.Datetime("ns", time_zone="UTC")).

pl.Duration: Elapsed Time Between Two Dates#

Subtracting one pl.Date from another produces pl.Duration – an elapsed span, not a date:

order_age prints as 731d for readability, but its actual dtype is Duration(time_unit='us') – the same microsecond default every Datetime in this lesson has used, even though every value here happens to land on a whole number of days. .dt.total_days() converts a Duration into a plain integer day count, which is usually more useful for filtering or sorting than the Duration type itself:

Duration Between Two Dates: Orders and Their Returns#

reference_date - order_date used one fixed date. thistlewood_returns.csv gives a second, more useful case: the span between an order and its return, both dates already in the data:

Every one of the 450 returns falls between 3 and 30 days after its order – matching Module 1’s own generator rule for thistlewood_returns.csv exactly, now confirmed with Duration arithmetic instead of taken on faith from the file’s documentation.

Practice Exercises#

Exercise 1: Cast and compare order ages by channel#

Using with_age_days from this lesson, group_by("channel").agg(pl.col("order_age_days").mean().round(2).alias("avg_age_days")). All three channels should land close to each other – explain in one sentence why order_age_days (measured from a single fixed reference date) wouldn’t be expected to differ much by channel.

Hint

order_age_days depends only on order_date, and orders are spread roughly evenly across channels throughout the same two-year window – nothing about channel should systematically shift when an order happened.

Exercise 2: Find the slowest-returning reason#

Using returns_with_days and the reason column from thistlewood_returns.csv, group by reason and compute the mean days_to_return. Which return reason takes longest on average, and does that make intuitive sense given what the reason describes?

Hint

You’ll need reason in the join – add it to the .select() alongside order_id and order_date on the returns side, since returns_with_order_date already includes every column from returns.

Summary#

pl.Date stores a calendar day with no time-of-day component; .str.to_date() cast order_date from a plain string into one. pl.Datetime adds a time unit ("us", microseconds, confirmed as this Polars version’s default) and an optional time zone – order_timestamp_utc read in directly as Datetime(time_unit='us', time_zone='UTC'), this course’s first time-zone-aware column. Casting a Datetime’s time unit without also passing time_zone silently drops it, confirmed directly against the installed version. pl.Duration is the elapsed span between two dates or datetimes – reference_date - order_date produced a 731-day span, and joining thistlewood_returns.csv to order_date confirmed all 450 returns fall between 3 and 30 days after their order (mean 16.58), matching Module 1’s own generator rule.

Key Concepts#

  • pl.Date is a calendar day; pl.Datetime adds time-of-day and an optional time zone – order_timestamp_utc needed the second type; order_date only ever needed the first.
  • Polars’ default Datetime/Duration time unit is microseconds ("us"), not nanoseconds – confirmed directly against Polars 1.43.0, not assumed.
  • Casting a Datetime’s dtype replaces every argument you don’t specify – time_zone defaults to None, so changing time unit alone silently drops an existing time zone unless it’s passed explicitly in the same cast() call.
  • pl.Duration is what two Date/Datetime values subtract into – .dt.total_days() (or the matching hour/minute/second accessor) converts it to a plain integer for filtering, sorting, or aggregating.

Why This Matters#

A datetime column that silently loses its time zone during a routine-looking cast is exactly the kind of bug that doesn’t announce itself – the schema still prints Datetime, the values still look like timestamps, and nothing errors until a later time-zone conversion (Lesson 5) produces a wrong local time with no warning attached. Verifying dtype behavior directly, the way this lesson did for time unit and time zone both, is the same discipline Module 1’s own audit established for this course: check what the installed library actually does before writing prose that assumes it.
