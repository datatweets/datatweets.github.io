Welcome to Rolling and Dynamic Time Windows#

Module 7 Lesson 5 built a rolling average over monthly Kitchen-category revenue – but that rolling window counted rows, three months at a time, with no calendar date anchoring it at all. This lesson builds a time-based rolling window over the 731 daily revenue buckets Lesson 3 produced: a 7-day rolling total anchored to elapsed calendar time, not row position, plus a 30-day rolling baseline used to flag unusually high-revenue days.

By the end of this lesson, you will be able to:

  • Build a time-based rolling window with DataFrame.rolling(index_column=, period=)
  • Explain how a time-based rolling window differs from Module 7’s row-count-based .rolling_mean()
  • Choose between a partial-window default and a strict full-window-only rolling calculation
  • Flag days whose revenue significantly exceeds their own recent rolling baseline

Rebuilding the Daily Series#

Start from Lesson 3’s daily bucketing:

A Time-Based 7-Day Rolling Total#

DataFrame.rolling(index_column=, period=) groups every row with every other row whose index_column falls within period of it – a time-anchored window, not a fixed row count:

n_days_in_window grows from 1 to 7 across the file’s first week, then holds at 7 from 2024-01-07 onward – the window only includes days that exist within the trailing 7-day span, so it starts partial and fills in naturally. 2024-01-07’s rolling_7d_total ($84,049.20) matches Lesson 3’s own 2024-01-01 weekly bucket exactly – the same 7 calendar days, summed by two different mechanisms, landing on the identical number.

Time-Based vs. Row-Based: Why the Mechanism Is Different#

Module 7 Lesson 5’s .rolling_mean(window_size=3) operated on 24 monthly rows with no date column driving the window at all – it counted rows, and assumed (correctly, since the data was already one row per month, evenly spaced) that 3 rows meant 3 months. DataFrame.rolling(index_column=, period=) makes no such assumption; it looks at the actual day values and includes whatever days fall in range, which matters the moment your data has gaps or uneven spacing.

By default, .rolling() returns a partial-window result for the first few rows rather than null (confirmed above: n_days_in_window starts at 1, not 7). If a report specifically needs the discipline Module 7’s row-based version had – no output until the window is completely full – rolling_sum_by() (the expression-level equivalent) exposes a min_samples parameter for exactly that:

min_samples=7 nulls the first 6 days – the same edge behavior Module 7’s .rolling_mean(window_size=3) had, now expressed with a time window instead of a row count. Which one to use depends on the report: a dashboard that needs a number for every day (even an early, partial one) wants the default; a report that must never present a misleadingly-small rolling window as if it were complete wants min_samples set to the window’s own length.

rolling_sum_by() is marked unstable

Polars’ own docstring for rolling_sum_by() (and its sibling rolling_mean_by(), rolling_max_by(), etc.) marks the function “unstable” as of this installed version (1.43.0) – its signature may change in a future release without that counting as a breaking change. DataFrame.rolling() carries no such warning. Both are used in this lesson because both are correct today; worth re-checking rolling_sum_by()’s signature against whatever Polars version you’re running before relying on it in production code.

A Rolling Baseline for Flagging Unusual Days#

A 30-day rolling average gives every day a “recent normal” to compare itself against:

97 of 731 days sit at 1.5x or higher than their own trailing 30-day average – 2024-05-18 peaks at 2.6x. This “compare each row to its own recent trailing window” pattern is exactly what Lesson 6’s guided project builds into a full transaction-monitoring report.

Practice Exercises#

Exercise 1: A 14-day rolling window#

Repeat the rolling total calculation with period="14d" instead of "7d". Confirm n_days_in_window grows to 14 and holds there, and report the 14-day rolling total for 2024-01-14.

Hint

Reuse the exact .rolling(index_column="day", period=...) pattern from this lesson – only the period string needs to change.

Exercise 2: Flag by channel instead of overall#

DataFrame.rolling() accepts a group_by= parameter. Rebuild the daily series grouped by channel as well as day, then compute a per-channel 30-day rolling average with .rolling(index_column="day", period="30d", group_by="channel"). Confirm each channel gets its own independent rolling baseline rather than one shared across all three.

Summary#

DataFrame.rolling(index_column="day", period="7d") built a time-anchored rolling revenue total over Thistlewood’s 731 daily buckets – the window starts partial (1 day, then 2, up to 7) and holds at 7 days from there, with 2024-01-07’s rolling total matching Lesson 3’s own weekly bucket exactly. This differs from Module 7 Lesson 5’s row-count-based .rolling_mean(), which had no date column driving it at all; rolling_sum_by(..., min_samples=7) reproduces that same strict, null-until-full behavior with a time window instead. A 30-day rolling average flagged 97 of 731 days at 1.5x or more their own recent baseline, the highest at 2.6x on 2024-05-18.

Key Concepts#

  • DataFrame.rolling(index_column=, period=) windows by elapsed calendar time, not row count – correct even when rows aren’t evenly spaced, unlike a row-count rolling window.
  • The default rolling window returns a partial result before it’s full (min_samples=0) – pass min_samples (available on the rolling_*_by() expression functions) to require a full window before returning anything but null.
  • A rolling baseline turns an absolute number into a relative one – “$30,715 in revenue” means little alone; “2.6x this day’s own 30-day average” is immediately legible.
  • rolling_sum_by() and its siblings are marked unstable in this Polars version – DataFrame.rolling() is not; check which guarantee you need before choosing.

Why This Matters#

A rolling window that silently counts rows instead of elapsed calendar time is correct exactly as long as your data stays perfectly regularly spaced – and wrong the moment it doesn’t, with no error to announce the mistake. Building the time-based version directly against Thistlewood’s own daily gaps (weekends and slow days included) is the discipline that makes a rolling calculation trustworthy on data that was never perfectly regular to begin with, which describes almost all data in practice.
