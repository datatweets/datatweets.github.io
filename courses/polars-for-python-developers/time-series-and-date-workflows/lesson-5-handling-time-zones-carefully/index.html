Welcome to Handling Time Zones Carefully#

Every timestamp this module has worked with so far has stayed in UTC. This lesson converts it: every one of Thistlewood’s 6,000 orders gets a local timestamp, based on the ordering customer’s own state. That single sentence hides two Polars behaviors worth understanding before writing this code – .dt.convert_time_zone() only accepts one fixed zone per call, and pl.concat() treats two different time zones as two distinct dtypes. Both are demonstrated directly below, not assumed.

By the end of this lesson, you will be able to:

  • Map a state column to its primary IANA time zone, as a documented simplification
  • Explain why .dt.convert_time_zone() can’t take a per-row column, and work around it by grouping
  • Recombine per-zone groups into one column without hitting a schema mismatch on time zone
  • Confirm Arizona’s fixed, no-DST offset directly, and see it contrasted against a DST transition in Thistlewood’s own order data

Mapping State to IANA Time Zone#

thistlewood_customers.csv’s state column has 22 distinct values, spanning four broad US time regions. Mapping each to its primary IANA zone is a deliberate simplification – a few US states do span more than one zone (Idaho is an example: most of the state is Mountain time, but its panhandle is Pacific), and this course maps every customer’s state to a single representative zone rather than modeling that split:

.replace_strict() maps every state value through the dictionary and raises if any value isn’t a key – exactly what you want here, since a state this course’s data doesn’t cover shouldn’t silently pass through as null.

A Limitation: convert_time_zone() Takes One Fixed Zone#

The obvious next step – pl.col("order_timestamp_utc").dt.convert_time_zone(pl.col("local_tz")), converting each row to its own zone in one expression – doesn’t work:

.dt.convert_time_zone()’s time_zone parameter is typed str – one literal zone per call, not a column of different zones. The fix is to group rows by their target zone first, convert each group with its own literal string, then put the groups back together:

A Second Limitation: Concatenating Different Time Zones#

Putting converted_parts back together with pl.concat() looks like it should just work – Lesson 1 of Module 8 already established how="vertical" requires matching schemas, and every part here has the same column names and types. Try it anyway:

This is exactly Module 8 Lesson 1’s rule, applied somewhere less obvious: the time zone is part of a Datetime column’s dtype, not just a formatting detail, so local_ts in the America/Chicago group and local_ts in the America/Boise group are two distinct dtypes, and pl.concat(..., how="vertical") refuses to stack them – correctly, since silently merging two columns with different time zones into one would make every downstream calculation ambiguous about what zone a given row’s local_ts was even in.

The fix: strip the time zone off each converted column with .dt.replace_time_zone(None), keeping only the naive local wall-clock value, and rely on the separate local_tz string column (already present in every group) to record which zone that wall-clock time belongs to:

All 6,000 orders recombine correctly, each with its own customer’s local wall-clock time alongside the local_tz label that gives that number meaning.

Converting UTC to local is never ambiguous

.dt.convert_time_zone() never needs the ambiguous=/non_existent= handling you may have seen mentioned elsewhere for time zones, because the source (order_timestamp_utc) is already an unambiguous, tz-aware instant – every UTC moment maps to exactly one local wall-clock reading, even across a DST transition. Those parameters belong to .dt.replace_time_zone(), used when assigning a zone to an already-naive local timestamp – a spring-forward gap (a local time that never happened) or a fall-back overlap (a local time that happened twice) only arises there, not here.

Arizona: Confirming the No-DST Claim Directly#

Arizona is this lesson’s deliberate contrast case: America/Phoenix observes Mountain Standard Time year-round and never switches to daylight saving time, unlike almost every other US zone. Confirmed directly with Python’s zoneinfo, not asserted from memory:

Arizona holds UTC-7 in both January and July. Colorado starts at the same UTC-7 in January (Mountain Standard Time) but shifts to UTC-6 in July (Mountain Daylight Time) – the two states share the same winter offset and disagree every summer.

A DST Transition, in Thistlewood’s Own Order Data#

The US spring-forward transition in 2024 happened at 2:00 AM local time on March 10. Three Thistlewood orders from Mountain-zone customers, filtered to a window straddling that date, show the offset shift directly:

Order O04642, placed before the transition, converts to MST (UTC-7); orders O01719 and O00847, placed after 2:00 AM on March 10, both convert to MDT (UTC-6) – Polars picked the correct abbreviation and offset for each timestamp automatically, based on exactly when it fell relative to the transition, with no manual DST handling required from this code at all. Note also that pl.col("order_timestamp_utc") >= pl.datetime(2024, 3, 8, time_zone="UTC") needed an explicit time_zone="UTC" on the literal – comparing a tz-aware column to a naive pl.datetime() literal raises a SchemaError for the same reason the concat above did: the time zone is part of the dtype being compared.

Practice Exercises#

Exercise 1: Count orders by local hour, Arizona vs. a DST state#

Filter with_local to Arizona customers, extract .dt.hour() from local_ts, and compare the distribution to the same extraction for California customers (also Pacific, but observes DST). Both distributions should look similar in shape – the point of this exercise is confirming the pipeline runs correctly for both, not finding a difference.

Hint

with_local.filter(pl.col("state") == "AZ")["local_ts"].dt.hour().value_counts().sort("local_ts") gives one distribution; repeat with state == "CA" for the other.

Exercise 2: Find every order placed in the redundant fall-back hour#

The 2024 US fall-back transition happened at 2:00 AM local time on November 3 (clocks went back to 1:00 AM, so 1:00-1:59 AM happened twice). Filter with_local to Mountain-zone orders on 2024-11-03 and inspect their local_ts hour values. Because with_local was built from an unambiguous UTC source, explain in one sentence why none of these rows needed ambiguous= handling, even though the underlying local time briefly repeated.

Summary#

Mapping thistlewood_customers.csv’s 22 states to 7 IANA zones and converting every order’s UTC timestamp to local time surfaced two Polars limitations, both confirmed directly: .dt.convert_time_zone() accepts only one literal zone string per call (a TypeError results from passing a column), so converting per-customer zones requires grouping by target zone first; and pl.concat() refuses to stack columns with different time zones (a SchemaError, since the zone is part of the Datetime dtype), fixed by stripping to a naive local column with .dt.replace_time_zone(None) before recombining. zoneinfo confirmed Arizona holds a fixed UTC-7 offset year-round while Colorado shifts to UTC-6 in summer, and three Thistlewood orders straddling the actual March 10, 2024 spring-forward date showed that exact MST-to-MDT shift in converted order timestamps.

Key Concepts#

  • .dt.convert_time_zone() takes one literal zone string, never a per-row column – converting to varying target zones means grouping by the target zone and converting each group separately.
  • Time zone is part of a Datetime column’s dtype, not just formatting – pl.concat() refuses to stack columns with different time zones, the same schema-matching rule Module 8 Lesson 1 established for vertical concatenation generally.
  • Converting an unambiguous UTC source to local time never needs ambiguous=/non_existent= handling – those parameters belong to .dt.replace_time_zone(), for assigning a zone to an already-naive local timestamp, a different operation from converting an already-aware one.
  • Arizona holds a fixed UTC offset year-round; most other US states’ offsets shift twice a year – confirmed directly with zoneinfo, and shown in converted Thistlewood order timestamps straddling an actual transition date.

Why This Matters#

Time-zone bugs are notoriously silent – a Datetime column with the wrong (or missing) zone still looks like a valid timestamp right up until a report shows an order placed at 3 AM local time that a human knows couldn’t be correct. Confirming both of this lesson’s limitations directly, rather than writing code that happened to work on a single-zone test case, is what keeps a per-customer local-time conversion correct across all 7 zones this dataset actually uses – and DST transitions besides.
