Welcome to Non-Equality and As-Of Joins#

Every join so far matched rows where a key was exactly equal on both sides. Business questions frequently need something looser: “was this promotion active when this order happened?” isn’t an equality condition at all, it’s a range. This lesson covers two Polars tools built for exactly that: join_where() for an explicit non-equality condition, and join_asof() for matching each row to its nearest counterpart in time.

By the end of this lesson, you will be able to:

  • Express a range condition (start_date <= order_date <= end_date) with join_where()
  • Explain why join_where() performs an inner join only, and what that means for rows with no match
  • Use join_asof() to match each row to its nearest prior counterpart by date, optionally within a group
  • Recognize the gap between “nearest match” and “still valid match” that join_asof() alone doesn’t check

A Non-Equality Condition: Was a Promotion Active?#

thistlewood_promotions.csv has 25 promotions; 15 of them apply to an entire category rather than one product. The question this section answers: which order-item rows were purchased while their category had an active promotion?

join_where() takes any number of boolean expressions across the two frames and keeps only the row pairs where every one of them is True – here, a matching category and an order_date that falls inside [start_date, end_date]. No equality join can express “between these two dates”; join_where() is built for exactly this. 745 of the 14,054 order-item rows – about 5.3% – were bought while their category had an active promotion.

join_where is an inner join only

join_where() “performs an inner join, so only rows where all predicates are true are included” (from Polars’ own docstring, verified directly against the installed 1.43.0). The 13,309 order-item rows with no matching active promotion simply don’t appear in active_promos at all – there’s no left/right/full variant. To keep every order-item row while adding promotion info only where it applies, join the small match table (order_id, product_id, promo_code) back onto the full order-item table with an ordinary left join on those same keys – exactly what Lesson 6’s guided project does.

An As-Of Join: Nearest Promotion Before a Return#

join_asof() answers a different question: for each row, what’s the closest match in another table, by date, without needing an exact range condition? Match each of the 450 returns to the most recent same-category promotion that had already started by the return date:

strategy="backward" finds each return’s most recent same-category promotion whose start_date is at or before the return_date – by_left/by_right="category" keeps the search confined within matching categories, the same idea as .over()’s grouping in Module 7. Early returns like R00003 (2024-01-15) get null: no Bedding promotion had even started yet by that date. Promotions matched here: 211 of 450.

The Gap: Nearest Doesn’t Mean Still Active#

join_asof() guarantees the nearest prior start_date – it says nothing about whether that promotion’s end_date had already passed by the return date. Check both:

Of the 211 returns join_asof() matched to a promotion, 179 – the large majority – were matched to one that had already ended by the return date; only 32 returns happened while a matching promotion was still live. join_asof() did exactly what it promises (nearest prior start_date, correctly, every time), but “nearest” and “currently valid” are two different questions – the second one needs the explicit end_date check this section just ran, the same discipline join_where()’s exact range condition already builds in for free. That’s the practical tradeoff between the two tools: join_where() is exact but inner-only; join_asof() keeps every row but only guarantees nearness, not validity.

Practice Exercises#

Exercise 1: Product-specific promotions with join_where#

Repeat the first section’s join_where(), but use the 10 product-specific promotions (promotions.filter(pl.col("product_id").is_not_null())) matched on product_id instead of category. Confirm the match count is smaller than 745, and explain in one sentence why.

Exercise 2: Forward instead of backward#

Re-run the join_asof() with strategy="forward" instead of "backward". Confirm this finds each return’s next promotion to start after the return date, rather than the most recent one before it, and compare the match count to the 211 found above.

Summary#

join_where() matched 745 of the 14,054 Thistlewood order-item rows to an active category promotion using a non-equality condition (start_date <= order_date <= end_date), keeping only the rows where every condition held, since join_where() performs an inner join only. join_asof() matched 211 of the 450 returns to their nearest prior same-category promotion by start_date – and a follow-up check found that only 32 of those matches were still active on the return date, with 179 already expired and 239 returns having no prior promotion at all.

Key Concepts#

  • join_where() expresses arbitrary boolean conditions, including ranges – >=/<= conditions an equality join can’t represent, but the result is inner-only: unmatched rows on either side are simply absent.
  • join_asof() finds the single nearest match by an ordered key, optionally scoped with by/by_left/by_right, using strategy="backward" (nearest at-or-before) or "forward" (nearest at-or-after).
  • “Nearest” is not “still valid” – a join_asof() match only guarantees proximity; an explicit follow-up condition (like the end_date check here) is needed to confirm the match still applies.
  • A small match table from either tool can be left-joined back onto the full table – the standard way to keep every original row while adding the (sometimes-missing) match info as extra, possibly-null columns.

Why This Matters#

“Was X true at the time Y happened?” is one of the most common analytical questions there is – was a promotion active, was a customer’s subscription valid, was a price in effect – and neither an equality join nor eyeballing dates by hand answers it reliably. This lesson’s 745-row promotion match and its 32-vs-179 active-vs-expired split are both concrete proof that the right tool (join_where()’s exact range, or join_asof() plus an explicit follow-up check) gets a more accurate answer than either “always match” or “never match” would.
