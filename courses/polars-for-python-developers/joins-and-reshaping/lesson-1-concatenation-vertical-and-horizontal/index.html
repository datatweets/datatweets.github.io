Welcome to Concatenation – Vertical and Horizontal#

Every join this course builds from Lesson 2 onward combines rows by matching a key. Concatenation is different, and simpler: it combines frames that already line up – either the same columns stacked as more rows, or the same rows extended with more columns – with no key matching at all. pl.concat() is the tool, and this lesson uses it against two Thistlewood tables to show exactly what “already line up” requires, and what happens when it doesn’t.

By the end of this lesson, you will be able to:

  • Stack Thistlewood data vertically with pl.concat(..., how="vertical")
  • Explain exactly what schema requirement vertical concatenation enforces, and what error it raises when that requirement is broken
  • Rebuild a table horizontally from column subsets with pl.concat(..., how="horizontal_extend")
  • Recognize horizontal concatenation as positional, not key-based – and know the silent risk that comes with that

Stacking Orders Back Together, Vertically#

thistlewood_orders.csv spans two full years. Split it into two date-range subsets, then use pl.concat() to stack them back into one:

3,008 2024 orders and 2,992 2025 orders stack back into the exact 6,000-row table pl.read_csv("thistlewood_orders.csv") produced directly – how="vertical" requires both frames to share the identical column names, in the identical order, with compatible dtypes, and simply appends one frame’s rows underneath the other’s.

What Happens When Schemas Don’t Line Up#

how="vertical" isn’t forgiving about column names. Rename one column in one of the two frames and try again:

A ShapeError, not a silent partial result – pl.concat(..., how="vertical") checks the two schemas match before stacking a single row, and refuses outright the moment they don’t. That’s exactly the behavior you want from a stacking operation: two files from slightly different exports, one with a renamed column, should fail loudly, not merge into a table with a bogus null-filled column on one side.

vertical vs vertical_relaxed

This course only uses how="vertical", which requires exact dtype matches column-by-column. Polars also offers how="vertical_relaxed", which allows compatible-but-different dtypes (an i32 column stacked with an i64 column, for instance) and upcasts automatically – worth knowing exists, but not something this lesson’s Thistlewood columns need, since every subset here already shares identical dtypes.

Rebuilding Customers Horizontally#

Vertical concatenation adds rows; horizontal concatenation adds columns, by matching row position across frames – no key involved at all. Split thistlewood_customers.csv into two column subsets, then put them back together side by side:

how="horizontal_extend" placed identity_cols’ 4 columns and location_cols’ 4 columns side by side, row 0 next to row 0, row 1 next to row 1, and so on – reconstructing all 180 Thistlewood customers exactly, because both subsets came from splitting the same table’s columns, so their row order was guaranteed to already match.

horizontal_extend is the current spelling

As of Polars 1.42.1, how="horizontal" is deprecated for this null-padding behavior – calling it emits a DeprecationWarning and points to how="horizontal_extend" instead, which is what this lesson uses throughout. how="horizontal" itself isn’t going away; a future release changes it to require equal heights rather than pad, which only matters if your two frames don’t already have the same row count.

The Risk: Horizontal Concatenation Trusts Row Position, Not a Key#

identity_cols and location_cols lined up correctly because they came from the same 180-row table split by column. That guarantee disappears the moment the two frames don’t already share row-for-row order – and Polars doesn’t check for that, or even require the heights to match:

No error, no warning about a row-count mismatch – short_location had only 5 rows (customers.head(5)), and pl.concat(..., how="horizontal_extend") silently padded the missing 175 rows with null. Every customer past the 5th got a null city and null state, and nothing in the output flags that as unusual. This is why horizontal concatenation is used sparingly in practice: it is correct only when you can already prove the two frames’ row order matches, the way splitting one table by columns proves it. Combining two separate tables by a shared identifier is a join, not a concatenation – the subject of every remaining lesson in this module.

Why this lesson didn’t use how=‘horizontal’

how="horizontal_extend" is the forward-compatible name for exactly the operation this lesson demonstrates (placing frames side by side, null-padding included). Using the plain how="horizontal" name here would print a DeprecationWarning on every run without changing today’s result – this lesson names the operation Polars 1.42.1+ wants you to reach for.

Practice Exercises#

Exercise 1: Concatenate orders by channel instead of by year#

Using orders.filter(pl.col("channel") == "web"), orders.filter(pl.col("channel") == "store"), and orders.filter(pl.col("channel") == "phone"), concatenate all three subsets with pl.concat(..., how="vertical") and confirm the result’s row count equals orders.height.

Exercise 2: Rebuild thistlewood_products.csv horizontally#

Split products into two column subsets of your own choosing (e.g. product_id, product_name, category in one and the rest in the other), concatenate them with how="horizontal_extend", and confirm the rebuilt table equals the original with .select(products.columns).equals(products).

Summary#

pl.concat(..., how="vertical") stacked 3,008 2024 orders and 2,992 2025 orders back into the exact 6,000-row thistlewood_orders.csv, and raised a ShapeError the moment two frames’ column names stopped matching. pl.concat(..., how="horizontal_extend") rebuilt all 180 Thistlewood customers exactly from two column subsets that shared row order by construction – and the same call on two subsets with different row counts didn’t error at all, silently null-padding the shorter one instead.

Key Concepts#

  • Vertical concatenation stacks matching columns as more rows – it requires identical column names, order, and dtypes across every frame, and fails loudly (ShapeError) the moment they don’t match.
  • Horizontal concatenation places matching rows as more columns, by position – how="horizontal_extend" is the current, forward-compatible spelling as of Polars 1.42.1.
  • Horizontal concatenation trusts row order, not a key – it’s only correct when you can prove the frames already line up row-for-row, and it silently null-pads a shorter frame rather than erroring on a mismatch.
  • A mismatch between two separate tables belongs to a join, not a concatenation – concatenation combines frames that already agree on shape; joins combine frames related by a key, which is what the rest of this module covers.

Why This Matters#

Concatenation looks like the simplest way to combine two datasets, and it is – right up until the assumption it depends on (matching schema for vertical, matching row order for horizontal) turns out to be false. Vertical concatenation fails loudly the moment that assumption breaks. Horizontal concatenation does not: it will happily null-pad a mismatch without a warning, which is exactly why it’s reserved for cases – like splitting and rebuilding one table – where the row correspondence is provably guaranteed, never assumed.
