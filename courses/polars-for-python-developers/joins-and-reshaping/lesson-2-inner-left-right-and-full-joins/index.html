Welcome to Inner, Left, Right, and Full Joins#

A join combines two tables by matching a key – customer_id, order_id, product_id – rather than by row position. Which rows survive when a key doesn’t match on one side is exactly what separates the four classic join types. This lesson runs all four against Thistlewood data twice: once where the keys already line up perfectly, and once where they don’t, so the four join types produce four row counts worth explaining rather than memorizing.

By the end of this lesson, you will be able to:

  • Run inner, left, right, and full joins with .join(..., on=..., how=...)
  • Verify, rather than assume, whether two tables’ keys fully match
  • Explain a join’s row count by what’s missing on each side, not by rule alone
  • Use coalesce=True to merge a full join’s duplicated key column back into one

First: A Relationship With No Mismatch At All#

Before comparing join types, check whether thistlewood_orders.csv and thistlewood_customers.csv have any unmatched keys at all:

Zero orders lack a matching customer, and zero customers have placed zero orders (an anti join – covered fully in Lesson 3 – is exactly how you check this directly rather than guess). With no mismatch on either side, all four join types return the identical 6,000 rows: there’s nothing for left, right, or full to add beyond what inner already keeps. That’s a clean result, and worth stating plainly – but it also means orders and customers can’t demonstrate what makes the four join types different. orders and returns can.

Where a Mismatch Exists#

Only some orders have a matching return. Run the same four joins against thistlewood_orders.csv and thistlewood_returns.csv:

Four join types, two different outcomes – and each one is explained by what’s true about the data, not by rule alone:

  • inner (450 rows): keeps only orders that have a return. 450 of the 6,000 orders do.
  • left (6,000 rows): keeps every order, matched or not – the 5,550 orders with no return get null in every returns column.
  • right (450 rows): keeps every return, matched or not, plus its order columns. Because every return’s order_id exists in orders (verified in Lesson 1’s spirit: there’s no orphaned return_id), right here lands on the exact same 450 rows as inner.
  • full (6,000 rows): keeps every row from both sides, matched or not. Because returns’ keys are a subset of orders’ keys, full here lands on the exact same 6,000 rows as left.

right and full aren’t always redundant

right matched inner here, and full matched left, specifically because returns’ order_id values are a subset of orders’ – not because right and full are always redundant. If even one return referenced an order_id that didn’t exist in orders (it doesn’t here, but it easily could in messier data), right and full would each grow by exactly that many extra rows, with null order columns – rows inner and left would never show at all.

A Closer Look at the Matched Rows#

Each of the 450 matched rows carries both the order’s own columns (order_date, channel) and the return’s columns (return_id, reason, return_date) on the same row – the whole point of joining by key rather than concatenating by position: O04985 and its return R00001 end up together because their order_id values match, regardless of where either row happened to sit in its own file.

Practice Exercises#

Exercise 1: Confirm the left join’s null count by hand#

Using orders.join(returns, on="order_id", how="left"), filter for pl.col("return_id").is_null() and confirm the count equals orders.height - returns["order_id"].n_unique().

Exercise 2: Join order_items to products and check for any mismatch#

Run all four join types on items.join(products, on="product_id", how=...). Before running them, use an anti join each direction to check whether any mismatch exists at all – predict what you’ll see, then confirm it.

Summary#

orders.join(customers, on="customer_id", how=...) returned the identical 6,000 rows for all four join types, because an anti join confirmed there’s no mismatch at all between the two tables. orders.join(returns, on="order_id", how=...) told a different story: inner and right both landed on the 450 matched rows, left and full both landed on the 6,000-row orders table – four join types, two distinct outcomes, each one explained by exactly what’s missing (or not) on each side, never assumed from the join type’s name alone.

Key Concepts#

  • A join’s row count is a fact about the data, not the join type – right matching inner, and full matching left, both happened here because of a verifiable property of the keys (one side’s keys are a subset of the other’s), not because those pairs are always equivalent.
  • Verify a mismatch before assuming a join type will show one – an anti join (Lesson 3) directly answers “does every key on this side have a match?” rather than guessing from row counts alone.
  • left and full both keep every row from the frame(s) they’re anchored to – the unmatched rows get null in every column from the other side.
  • coalesce=True merges a full join’s duplicated key column – without it, a full join leaves both order_id and order_id_right, since either side’s key could be the one that’s null for an unmatched row.

Why This Matters#

The four classic join types are usually taught as a fixed rule – “left keeps everything on the left” – without the follow-up that matters: how many rows does that turn out to be, for this data? This lesson’s $0$-mismatch result on orders/customers and its 5,550-row mismatch on orders/returns are both outcomes of the same four join types, run against two different relationships – the row count was never something to memorize, only something to check.

Continue Building Your Skills#

Inner, left, right, and full joins all keep at least the matched columns from both sides. Lesson 3 turns to three join types that behave differently: semi and anti joins, which never add a single column from the other table, only filter by whether a match exists – and a cross join, which ignores keys entirely and pairs every row with every row.
