Welcome to the Guided Project#

This is the final lesson of the course, and it is the one where every instrument you built gets bolted onto the same bench. Across eight modules you learned to measure Docent — the documentation Q&A assistant that answers questions about Meridian, a serverless database, from its docs — one dimension at a time: whether an answer is correct, whether the retriever fed the model the right page, what a live run costs, and whether a change is safe to ship. Each of those was a separate tool. In this capstone you wire all of them into a single, runnable evaluation-and-observability harness and run it end to end, live on claude-haiku-4-5, over a small versioned golden dataset.

The point of assembling them is that no single number tells you whether Docent is ready. A quality score with no cost accounting hides a bill; a cost dashboard with no correctness score hides a broken answer; a passing test suite with no guardrail ships an injection. A production harness produces one consolidated report — a dataset you trust, a score you can defend, a root-cause diagnosis for each failure, a cost and latency budget, and a single ship/block verdict — and it traces every number back to a discipline you can name. That report is the deliverable. We build it in five stages, one per teaching thread of the course, and we deliberately mix deterministic layers (dataset validation, string metrics, retrieval recall, the guardrail, the gate logic — the same number on every run) with live layers (Docent’s answers and the judge’s verdicts on claude-haiku-4-5, which wobble run to run) so you can see exactly which parts of an eval you can trust to the byte and which you read as an honest example.

By the end of this project, you will be able to:

  • Assemble a versioned, validated golden dataset and drive an entire eval suite from it
  • Score the same answers two ways — a reproducible string metric and a live calibrated judge — and read the disagreement as signal, not noise
  • Diagnose each failure as a retrieval or a generation problem using recall on gold document ids, and account for the run’s cost, tokens, and latency percentiles without ever logging a secret
  • Apply a guardrail and a CI-style regression gate that returns a single PASS/FAIL verdict — and trace every number in the final report back to the module that produced it

Stage 1: Assemble and Validate the Golden Dataset (Module 2)#

Everything downstream reads from the dataset, so it is built and validated first. We assemble a small versioned golden set of ten cases drawn from the Meridian docs: nine factual questions, each carrying a reference answer, the doc id of the page that actually contains it, and a category; plus one deliberately out-of-scope case (a MongoDB-aggregation question the docs don’t cover) whose correct behavior is a refusal. We then validate the set — every case has a non-empty question and reference, a category from a fixed set, and a doc id that exists in the corpus (or None for the out-of-scope case) — and fingerprint it with a content hash so the exact dataset behind any run is identifiable. This stage touches no model, so it reproduces to the byte.

Ten cases, zero validation problems, and a stable fingerprint of 8e21fccd85fe that is identical on the re-run line — because nothing here calls a model, this stage produces the same bytes every single time. Two design choices carry the whole rest of the harness. First, each factual case records its doc id: that one label is what lets Stage 3 ask “did the retriever even fetch the right page?” instead of merely “was the answer wrong?” Second, the out-of-scope case (q10) has reference text that says the correct behavior is a refusal — so the same scoring and gating machinery that grades factual answers can also grade “did Docent correctly decline?” without a special code path. The fingerprint is the versioning discipline from Module 2 in miniature: any run can be traced back to the exact dataset behind it.

The key lives in the environment, never in the code

Every live block in this project constructs the client as anthropic.Anthropic() with no arguments — the SDK reads ANTHROPIC_API_KEY from the environment. The key never appears in a variable you print, a dataset field, or (as you’ll see in Stage 4) a single trace record. This is not incidental to an observability lesson: the fastest way to turn a helpful log into a security incident is to serialize the whole request, key included. Log the tokens, the latency, and the cost — never the credential.

Stage 2: Score Every Answer Twice — Deterministic Metric and Live Judge (Modules 3 + 4)#

Now the harness makes its live calls. We route every model call through a small traced() wrapper — the observability primitive from Module 7 that Stage 4 will read back — so that scoring and cost accounting happen in one pass. For each golden case we run Docent live once, then score its answer two ways. The deterministic metric (Module 3) is normalized exact-match and token-level F1 against the reference: pure string arithmetic, no model, perfectly reproducible given the answer. The calibrated judge (Module 4) is a second claude-haiku-4-5 call that grades correct or incorrect versus the reference, judging meaning rather than wording — and, for the out-of-scope case, treating a refusal as correct. Reporting both is the point: where they disagree is where the string metric is lying and the judge is right.

This one table is the entire Module 3 versus Module 4 lesson, made concrete. Exact-match is 0.00 across all ten cases — not because Docent is wrong, but because it answers in full sentences ("The Pro plan costs $25 per month.") while the reference is a terse fragment ("25 dollars per month"), and a strict string comparison scores every paraphrase as a miss. Token-F1 rescues partial credit (mean 0.49), rewarding overlap, but it still can’t tell that "HTTP 429." fully answers a reference of "429". The live judge lands at 0.90 correct, because it grades meaning: it credits the nine correct paraphrases the string metric threw away. The deterministic line is byte-identical on the re-run — string arithmetic has no randomness, so the same answers always yield the same score — but note what that does and doesn’t guarantee: exact-match is robustly 0.00 every run (a verbose answer never matches a terse reference), while the mean token-F1 is a function of the exact live wording, so its aggregate will shift a few points between runs as the answers do (this run happened to land at 0.49). The judge score, like the answers it grades, is likewise a live measurement that drifts a point between runs. And the one case the judge marks incorrect (q09) is not a paraphrase problem at all: Docent genuinely refused a question it should have answered. That failure is the thread we pull in Stage 3.

Read the metric disagreement as a map, not a contradiction

It is tempting to see exact-match 0.00 next to judge 0.90 and conclude one of them is broken. Neither is. Exact-match is doing exactly its job — flagging that not one answer is a verbatim match — and that is useful: it tells you the reference answers are terse and the model is verbose, which matters for any downstream system that string-matches Docent’s output. The judge is doing its job too, seeing through the phrasing to the meaning. The disagreement is the signal: the nine cases where EM=0 but the judge says correct are exactly the paraphrases, and the one case where both fail (q09) is the real bug. A mature eval runs the cheap deterministic metric as a fast tripwire and reserves the paid judge for the cases where wording could hide a right answer — which is why the harness computes both instead of picking one.

Stage 3: Diagnose Each Failure — Retrieval or Generation (Module 5)#

The judge told us that q09 is wrong; Module 5 tells us why, and therefore what to fix. Docent is two systems — a retriever and a generator — and its keyword retrieve() quietly pulls the wrong pages for certain questions. We compute recall@2 deterministically over the nine factual cases using each case’s gold doc id (recall is set arithmetic over ids — no model, fully reproducible), then apply one rule to every judged-incorrect answer: if the relevant doc was not retrieved, it’s a RETRIEVAL failure (fix the search); if it was retrieved and the answer is still wrong, it’s a GENERATION failure (fix the prompt). Same symptom, opposite cure.

Retrieval recall@2 is 0.89 — eight of nine gold pages made the top two — and identical on the re-run, because retrieval depends only on the deterministic keyword scorer, not the model. The single zero is q09, the Free-plan rate-limit question: its gold page is ratelimits, but the retriever returned ['backups', 'auth'], so the generator never saw the “60 requests per minute” fact and — honestly, given two unrelated pages — refused. That is a false refusal, and the diagnosis rule pins it precisely: recall = 0 means the fix belongs in the search (fuzzy matching, embeddings, a wider k), not the prompt. No amount of prompt-tuning could have saved this answer, because the answer was never in the context. This is the payoff of carrying the doc label from Stage 1: it converts “wrong answer” into a routed ticket.

Stage 4: Observe the Run — Tracing, Cost, and Latency (Module 7)#

Every live call in Stages 2 and 3 already flowed through the traced() wrapper, so the observability layer needs no re-run — it just reads the log it has been quietly building. Module 7’s discipline is: turn each model call into a structured record (span, model, tokens, latency, cost — and not the key), then aggregate into the numbers a team actually watches, including the percentiles that reveal the slow tail an average hides. We print one sample record, roll up the run into a mini dashboard, and persist the trace to a tempfile directory — never the repo.

The whole evaluation cost about 0.7 of a cent: 20 live calls (ten to run Docent, ten to run the judge), 4,549 tokens, and $0.00706 at the claude-haiku-4-5 list price of $1 per million input and $5 per million output tokens. Latency tells the more interesting story — the mean is 1806 ms but p95 is 3257 ms, roughly double the median of 1580 ms, which is exactly the slow-tail signal an average would smother: most calls are quick, but one in twenty takes over three seconds, and that is the number a latency SLA is written against. The sample record shows what discipline buys you — span, model, tokens, latency, and cost, and conspicuously no key. These are live measurements, so the exact tokens, cost, and latencies shift between runs (a slow network call moves p95 more than anything the model does); the shape — Docent and judge calls balanced, cost in the sub-cent range, a p95 well above the median — is what’s stable. The trace lands in a temp directory, never in your source tree.

Stage 5: Gate the Release — Guardrail and CI Regression (Module 8)#

The last stage decides whether Docent ships. Module 8 adds two defenses. A guardrail inspects incoming input before it reaches the model and blocks what shouldn’t be answered — prompt-injection attempts and off-topic requests. A CI-style regression gate then applies a threshold on the judge pass rate plus a hard critical-case rule — the out-of-scope question must still refuse — and emits a single ship/block verdict. The guardrail and the gate logic are deterministic: given the same inputs and the same recorded answers, they return the same decision every run.

The guardrail behaves correctly on all three probes: it allows the legitimate docs question, blocks the injection (matched against the injection patterns), and blocks the off-topic weather question (its tokens share nothing with the corpus vocabulary). Then the gate makes the ship call. The judge pass rate of 0.90 clears the 0.85 threshold, and the critical out-of-scope case q10 still refuses, so the verdict is PASS — ship. Notice what the gate does not do: it does not pretend Docent is perfect. The 0.90 leaves exactly one failure — q09, the retrieval bug Stage 3 already diagnosed — riding along above the threshold as a known, non-critical regression, ticketed for the next sprint rather than blocking the release. What would block a deploy is the critical rule: if q10 had fabricated an answer instead of refusing, the gate would return FAIL regardless of the pass rate, because a confident answer to a question outside the docs is the kind of failure you never ship. The re-run line confirms the verdict is deterministic given the recorded run.

The Final Report#

Here is the single consolidated readiness report the harness produces, the artifact a team would actually read before a release:

  • Dataset: 10 versioned cases (9 factual + 1 out-of-scope refusal), fingerprint 8e21fccd85fe, validated with 0 problems and reproducible to the byte.
  • Deterministic score: exact-match 0.00, mean token-F1 0.49 — identical on re-run.
  • Judge score: 0.90 correct on a live claude-haiku-4-5 judge, which credits the 9 correct paraphrases the string metric scores as 0.
  • Judge-vs-human trust caveat: the 0.90 is a calibrated judge’s opinion, not ground truth — it wobbles a point run to run and, like any judge, should be periodically checked against human labels before it is trusted as the gate’s headline number.
  • Retrieval recall@2: 0.89 — the single miss is the Free-plan false refusal (q09), diagnosed RETRIEVAL (fix the search, not the prompt).
  • Cost & latency: 20 live calls, 4,549 tokens, $0.00706, latency p50 1580 ms / p95 3257 ms — the key never written to any log.
  • Gate verdict: judge 0.90 ≥ 0.85 threshold and the critical out-of-scope case still refuses → PASS — ship, with the retrieval fix ticketed next.

And here is the same report traced stage by stage to the module that produced each number. Why Evaluation Matters (Module 1) is the frame: the entire harness exists to replace “Docent looks fine” with the numbers above, and the exact-match-0.00-versus-judge-0.90 gap is precisely the “looks fine” trap made measurable. Building Eval Datasets (Module 2) produced the 10-case set, its fingerprint 8e21fccd85fe, and the doc-id labels that made everything downstream diagnosable. Deterministic & Reference Metrics (Module 3) produced exact-match 0.00 and token-F1 0.49 — fast, free, reproducible, and honestly limited. LLM-as-Judge (Module 4) produced the 0.90 correct rate that saw through the paraphrases, along with the standing caveat that a judge is a model to be calibrated, not an oracle. Evaluating RAG (Module 5) produced recall@2 = 0.89 and the rule that routed the one failure to RETRIEVAL rather than the prompt. Evaluating Agents & Tool Use (Module 6) is the adjacent discipline this harness is built to grow into: Docent here answers in a single pass, but the moment it is allowed to act, the same split-and-diagnose instinct extends from the final answer to the tool calls and the trajectory. Observability & Tracing (Module 7) produced the 20-call, 4,549-token, $0.00706 dashboard with p50 1580 ms and p95 3257 ms — and the no-key-in-the-log rule. Production Monitoring & Guardrails (Module 8) produced the guardrail that blocked the injection and the off-topic probe, and the gate that turned judge 0.90 plus a held critical refusal into a single PASS — ship.

Practice Exercises#

Exercise 1: Trace one number back through every module#

The report ends with PASS — ship, but a single verdict is only as trustworthy as the chain of numbers behind it. Pick the judge score of 0.90 and, without writing new code, walk it backward through the harness: which module’s artifact does it depend on, which module’s metric would have hidden the very failure it caught, and which module’s gate consumed it? Then decide, honestly, whether 0.90 is a number you would actually gate a production release on — and what you would want to see before you trusted it.

Hint

Follow the data, not the code. The 0.90 depends on the Module 2 dataset (a different golden set gives a different number), it caught the q09 failure that Module 3’s token-F1 rewarded with 0.21 rather than flagging, and it fed the Module 8 gate as the pass rate compared against 0.85. The trust question is the Module 4 lesson resurfacing at the end of the course: a judge is a model, so before you gate on it you want its agreement with human labels measured on a sample — otherwise you are shipping on the opinion of an unaudited grader. The instinct to carry forward is that no single number is self-justifying; each one is only as good as the stage that produced it.

Exercise 2: Find the number that fixing the retrieval bug would move — and the one it wouldn’t#

Stage 3 diagnosed q09 as a RETRIEVAL failure. Imagine you fix it — a wider k, better matching — so ratelimits now reaches the generator and Docent answers “60 requests per minute” correctly. Reason through the report without running anything: which of the seven headline numbers change, and by how much, and which stay exactly where they are? Use the answer to articulate what a diagnosis actually buys a team.

Hint

Retrieval recall@2 climbs from 0.89 toward 1.00 (nine of nine), and the judge pass rate climbs from 0.90 toward 1.00 as the false refusal becomes a correct answer — but exact-match stays pinned at 0.00 (the corrected answer is still a verbose paraphrase), token-F1 barely moves, and the cost and latency shape is unchanged because you fixed the search, not the model. That contrast is the whole value of Module 5’s diagnosis: it told you the lever to pull was retrieval, so you could predict which numbers would respond before spending a sprint. A quality score alone would have told you Docent was 90 percent good; the diagnosis told you the missing 10 percent lived in the retriever.

Exercise 3: Decide where the harness is thinnest before you trust it in production#

You built a working end-to-end harness on ten cases, and every stage passed. That is exactly when to be most skeptical. Across all eight modules, name the single weakest assumption this harness rests on — the one that, if it broke silently, would let a genuinely bad Docent release sail through PASS. Then say which module’s discipline you would invest in first to shore it up, and why that one over the others.

Hint

There is no single right answer, which is the point — but the strongest candidates all trace to Module 2 and Module 4. Ten cases is a thin dataset: a real regression in a slice you didn’t sample (say, region questions) would never appear in recall@2 or the judge score, so the gate would pass a broken release with a clean conscience — this is the coverage-and-slicing lesson from Building Eval Datasets. The close runner-up is the uncalibrated judge from LLM-as-Judge: if the judge drifts lenient, the pass rate inflates and the 0.85 threshold stops meaning anything. Most teams invest in the dataset first, because every other number in the report is computed against it — a judge calibrated on a biased dataset is precisely calibrated to the wrong thing.

Summary#

You assembled the entire course into one runnable evaluation-and-observability harness and ran it end to end on Docent, live on claude-haiku-4-5. You built and validated a versioned golden dataset (10 cases, fingerprint 8e21fccd85fe) and drove every downstream stage from it. You scored each answer twice — a deterministic string metric (exact-match 0.00, token-F1 0.49, reproducible) and a live judge (0.90 correct) — and read their disagreement as the map of where wording hid a right answer. You computed retrieval recall@2 = 0.89 and used the gold doc ids to diagnose the one failure as RETRIEVAL rather than generation. You traced every live call into a cost-and-latency dashboard (20 calls, 4,549 tokens, $0.00706, p50 1580 ms / p95 3257 ms) without ever logging the key. And you gated the release with a guardrail and a CI-style threshold-plus-critical-case rule that returned a single verdict — PASS, ship — while leaving the known retrieval bug ticketed for next sprint. The final report ties each number to the module that produced it.

Key Concepts#

  • End-to-end harness — one pipeline that carries a single golden dataset through scoring, diagnosis, observability, and gating, producing one consolidated readiness report instead of eight disconnected numbers.
  • Deterministic vs live layers — dataset validation, string metrics, retrieval recall, the guardrail, and the gate logic reproduce to the byte; Docent’s answers and the judge’s verdicts are live and honestly wobble run to run. Knowing which is which is what makes the report trustworthy.
  • Metric–judge disagreement as signal — exact-match 0.00 next to judge 0.90 is not a contradiction; it is a map showing which answers are correct paraphrases (string metric under-credits) versus a real failure (both fail).
  • Recall-based failure diagnosis — the gold doc id turns a wrong answer into a routed ticket: recall = 0 means fix the retriever, recall = 1 with a wrong answer means fix the prompt.
  • Threshold-plus-critical gate — a release ships when the aggregate score clears a threshold and every critical case (here, the out-of-scope refusal) holds; the critical rule can block a deploy even when the aggregate looks fine.

Why This Matters#

A production LLM system is never “good” along one axis. It is correct-enough and affordable and fast-enough and safe and diagnosable, all at once, and a team ships or holds based on all of those together. The harness you built is what turns that judgement into an artifact: it measures each dimension with the right instrument, keeps the deterministic and live layers clearly separated so you know how much to trust each number, routes every failure to the team that can fix it, and collapses the whole picture into one verdict a release process can act on. That is the difference between “Docent seems fine” and a report that says “0.89 recall, one retrieval bug ticketed, $0.007 per eval, p95 3.3 seconds, critical refusal held — ship.” Every real LLM application you take to production will need exactly this consolidation, because the questions that decide a release — is it good, is it safe, what does it cost, and what breaks if we ship — are never answered by a single score.

Continue Building Your Skills#

You started this course by letting Docent fool you — reading a few answers, deciding it worked, and learning not to trust that instinct. You are ending it holding the antidote: a harness that would never let “looks fine” reach production, because it measures what your eyes can’t. Look back at the arc. Module 2 taught you that a metric is only as honest as the dataset behind it; Modules 3 and 4 taught you that some quality you can score with code in milliseconds and some you need a model to judge — and that both are limited in ways you must respect; Module 5 taught you that a wrong answer has an address; Modules 6 and 7 taught you to follow a request through its steps and to account for every token and millisecond it spends; and Module 8 taught you to turn all of it into a gate that says ship or block. The capstone’s real lesson is that these were never separate skills. They are one practice — the discipline of not believing an LLM system is good until you have measured it — and the harness is just that discipline written down and made to run. Take the instinct with you: when you build the next assistant, the next agent, the next retrieval pipeline, do not ask whether it looks right. Build the small, honest harness that tells you, keep the deterministic and the live parts clearly labeled, and let the report — not the demo — decide whether it ships.
